### 0.3 面试官风格

这位面试官明显是 **“先验收事实，再讨论设计”** 的风格，主要特征有四个：

1. 不接受“网关、SDK、插件都可以”这类能力列表，只问“你实际用了哪个”。
2. 会用具体反例验证方案，例如“昨天选 A、今天选 B”和“本地大分支已经改了很多”。
3. 会主动比较最简单替代方案，例如 `grep + Coding Agent`，要求证明新增系统的净价值。
4. 关注技术演进，明确把 2026 年的 Agent Skills 和更强模型作为新的竞争基线。

应对这类面试官，答案必须使用以下顺序：

> **当前实际是 X。请求链路是 A -> B -> C。这样选是因为 Y。它目前还有 Z 限制。**

不要先说“理论上有三种方式”，也不要先讲完整技术史。

### 0.4 本场最关键的四个问题

#### 1. 实际部署形态迟迟没有说清

面试官连续使用了以下问法：

- “它是独立部署的应用、SDK，还是插件？”
- “什么样的插件，Coding Agent 怎么引用？”
- “实际技术方向是哪一种？”
- “我知道这几种都可以，我问你实际用哪一种。”
- 最后由面试官确认：“本地运行的 SQLite。”

这说明候选人的答案大概率一直停在逻辑架构或可选接入方式，没有在第一句明确：

> **这个项目实际采用的是本地插件形态，数据落本地 SQLite；插件在模型调用前做 Recall，在一轮提交后做 Capture。它不是集中式记忆中台，也不是让所有业务系统统一调用的远端 SaaS。**

这是本场最明确的表达失分点。

#### 2. 记忆系统的目标容易被误解成“扩大上下文窗口”

面试官两次确认：是不是因为模型窗口有限，所以中间加一层记忆系统；既然窗口仍然有限，记忆系统到底起什么作用？

正确边界是：**它不改变物理上下文上限，而是让固定窗口只保留当前必要信息。** 跨会话信息按需召回，大 Tool Result 外移后只留摘要、任务状态和引用，需要精确细节时再回读原文。

#### 3. CodeWiki 没有先绑定“当前代码 Revision”

面试官用“大分支、本地大量未提交改动”反复追问，说明普通的“Git Diff + 增量更新”回答没有击中问题。真正的问题是：

> **本轮检索使用的图、Chunk、向量和实际读取的源码，是否属于同一个工作区快照？**

当前 CodeWiki 能记录当前 Commit，也能通过 Git Diff 和文件 Hash 做增量，但图、Chunk 和 Wiki 仍是当前快照，没有完整不可变 Revision；对未提交的大量改动和分析期间继续变化的代码，也没有全链路快照一致性保证。这里必须先承认边界，再讲版本化方案。

#### 4. CodeWiki 的当前竞争基线已经变化

面试官接受“项目立项时模型没有现在强”这一历史原因，但马上追问现在的 Agent Skills。这表示他在判断：**这个项目当年为什么做可以解释，但今天是否还有继续维护的价值，必须重新证明。**

答案不能再说“Coding Agent 不会理解仓库”。成熟 Agent 已经能搜索、读文件、维护上下文甚至建立自己的轻量索引。CodeWiki 只能在 **跨模块结构证据、可重复复用、来源引用、团队共享和大仓库成本** 上争取增量价值，而且必须用对照评测证明。

## 一、开场、项目难度与个人贡献

### Q1. 请先做一下自我介绍

**推荐答案（60 到 90 秒）：**

> 我毕业后在招银网络科技工作，正式岗位和主要生产职责是 **[按真实人事和工单填写]**。我的技术经历分成两条：一条是 Java 后端，主要负责 **[真实业务模块]**；另一条是 AI 应用工程，做过 AI 周报、CodeWiki 和 Agent Memory。
>
> CodeWiki 解决代码知识的结构化和可追溯问题：先用 AST 和代码图提取确定性事实，再通过 GraphRAG 和带来源校验的 Wiki 提供给人和 Coding Agent。Agent Memory 则分成跨会话长期记忆和单任务 Context Offload 两条链，重点是按需召回、压缩大工具结果，同时保留原文恢复路径。
>
> 我在这些项目里的真实角色分别是 **[按 RACI 填写]**。我希望下一份工作继续做后端工程与 Agent Runtime 的结合，深入上下文管理、工具调用、可观测性和生产可靠性，而不只是封装一次模型 API。

**注意：**

- 不要一口气讲完三个项目的全部技术栈。
- 先定义“我是做什么的”，再给两个项目证据。
- AI 与 Java 的真实年限不要相互覆盖或重复计算。

### Q2. 简历上几个项目都写“独立负责”，是全部由你一个人开发吗？

**现场风险：** “独立负责”很容易被理解为需求、设计、前后端、测试、部署和运营全部一个人完成。如果实际有团队协作，直接回答“是”会放大后续真实性风险。

**推荐答案：**

> 不是“所有环节和所有代码都由我一个人完成”。我这里的“独立负责”指的是 **[技术方案 Owner / 核心模块 Owner / 从需求到交付的主责任人，按事实选择]**。
>
> 以 Agent Memory 为例，需求由 **[填写]** 提出，架构和核心链路由 **[填写]** 负责，宿主接入、测试、部署和验收分别由 **[填写]** 完成。我本人负责 **[列出 2 到 4 项可证明工作]**，没有负责的是 **[前端 / 运维 / 生产发布等真实边界]**。
>
> 所以更准确的说法是“我主导了技术主线并对核心交付负责”，不是“项目里只有我一个人”。

### Q3. 哪个项目整体技术挑战最大？不是单点，是整体落地难度

**面试官确认的现场口径：** 候选人认为 CodeWiki 整体更难。

**推荐答案：**

> 如果看整体落地，我会选 CodeWiki。难点不只是某个算法，而是要把扫描、AST、多语言解析、跨文件关系、社区检测、GraphRAG、Wiki 生成与校验、增量更新、SQLite/PostgreSQL 存储、API/CLI/MCP 入口串成一条一致链路。
>
> 它还有三个很难回避的工程矛盾：第一，跨文件调用无法做到编译器级绝对准确，要给推断边保留置信度和来源；第二，模型生成的 Wiki 必须被源码引用约束，不能只是“看起来正确”；第三，代码持续变化后，图、Chunk、向量和文档必须一起失效或更新。Agent Memory 也复杂，但 CodeWiki 的数据类型更多、链路更长，一致性边界也更宽，所以整体落地难度更高。

## 二、Agent Memory：为什么做、怎么接、怎么工作

### Q7. 为什么单独做一个记忆系统，不让每个 Agent 自己管理自己的记忆？

**推荐答案：**

> 因为“每个 Agent 各存一点历史”只能解决局部问题，不能自动解决记忆生命周期。我们想统一处理的是：什么值得写、原始证据怎么保留、重复和冲突怎么更新、跨会话如何召回、上下文预算怎么控制、错误如何纠正，以及删除如何传播。
>
> 但统一的是 **Memory Core 和数据契约**，不是强制所有 Agent 共享同一份记忆。每个 Agent、Session、用户或项目仍然要有自己的 Scope。宿主只负责提供生命周期事件，Core 负责 Capture、抽取、检索和 Offload。这样不同 Agent 不必各自重写一套，但数据也不会因为“统一系统”就无边界混在一起。
>
> 当前项目仍有企业级 Tenant 身份和完整删除闭环的缺口，所以我会说“复用统一内核”，不会说“已经是成熟的多租户记忆中台”。

### Q8. 所以不是你们自己的 Agent 需要记忆，而是内部人员调用大模型时，中间加一层来解决窗口限制，对吗？

**回答原则：先纠正前提，避免顺着面试官的误解继续讲。**

**推荐答案：**

> 不完全是。我刚才没有把边界说清楚。它服务的对象是 **带会话和工具调用的 Agent Runtime / Coding Agent**，不是给所有普通大模型 API 请求统一加一个代理层。
>
> 它解决两类问题：第一，用户偏好、长期规则和历史事件需要跨会话保留；第二，一个 Coding Agent 长任务里会产生大量 Tool Result，需要从当前上下文卸载但仍可追溯。普通单轮问答如果没有这两类需求，不一定需要接这套系统。

**如果真实业务确实包含普通内部大模型助手：** 应把“普通助手入口”和“Coding Agent 入口”分别说清，不能用“内部大模型用户”笼统概括全部场景。

### Q9. 模型的上下文窗口还是有限，记忆系统主要发挥什么作用？

**推荐答案：**

> 它没有把模型的 128K 或 200K 物理窗口变大，作用是提高固定窗口的有效利用率。
>
> 跨会话链路中，原始消息、原子记忆、场景和 Persona 分层保存，每轮只注入稳定画像、导航和少量相关记忆，不把全部历史塞回去。单个长任务里，大 Tool Result 先完整落到 `refs`，当前 Prompt 只保留摘要、任务图和引用；需要精确错误、参数或行号时，再按引用读取一两条原文。
>
> 所以它省掉的是“所有历史长期常驻”的 Token，不是让信息免费存在，也不是保证上下文再也不会满。

### Q10. 你负责了架构设计？整体架构是什么？

**推荐答案（先讲两条链，再讲接入和存储）：**

> 是，架构主线由我负责 **[如与事实不符则调整]**。系统有一个宿主无关的 Memory Core，外面通过 Host Adapter 接 Agent，里面分两条链。
>
> 第一条是长期记忆：一轮对话提交后先保存 L0 原始消息；后台从新增消息提取 L1 原子记忆，类型是 persona、episodic 和 instruction；相关 L1 再聚合成 L2 场景 Markdown；L3 是更短、更稳定的 Persona。调用模型前用全文和向量 Hybrid Recall 找少量相关 L1，并按需要下钻 L2 或 L0。
>
> 第二条是 Context Offload：完整 Tool Result 先写入 `refs`，Prompt 中保留 L1 摘要；再按任务边界生成 Mermaid 任务图。上下文压力升高时，用摘要替换原结果或移除旧消息，模型需要细节时通过 `node_id -> result_ref` 回到原文。
>
> 两条链都遵循“原始证据和派生摘要分开、前台轻处理、后台最终一致、失败不阻塞主对话”。

### Q11. 它到底是独立部署应用、SDK、插件，还是其他东西？

**这是本场必须重答的一题。**

**推荐答案：**

> **这个项目实际采用的是本地插件形态，数据落本地 SQLite，并配合 JSONL、Markdown 和 refs 文件。** 它和 Agent 运行在同一台机器，通过宿主生命周期 Hook 接入，不是面向全公司的集中式远端记忆服务。
>
> Core 设计上也支持通过独立 HTTP Gateway 接其他宿主，但那是另一种接入能力，不是我这次项目实际采用的主部署方式。刚才我把“支持哪些形态”和“实际用了哪种形态”混在一起了。

**回答到这里先停。** 面试官继续问时，再展开插件生命周期和数据流。

### Q12. 什么样的插件？Coding Agent 怎么引用它？

**推荐答案：**

> 插件不是让模型自己 import 一个 SDK，而是接在 Agent Runtime 的生命周期上。
>
> 模型调用前，宿主触发 `before recall`，插件把当前用户问题和 Scope 交给 Core，Core 从本地 Store 取少量相关记忆，包装成独立的记忆区注入上下文。一轮对话完成后，宿主触发 `turn committed`，插件捕获原始消息并调度后台抽取。会话结束时再刷新未处理任务。
>
> 如果要做 Tool Result Offload，宿主还需要提供稳定的 `tool_call_id`、完整 Tool Result 和可调整的消息上下文。新 Coding Agent 只要暴露这些生命周期点，就写一个 Adapter；如果拿不到这些事件，就只能接部分长期记忆能力，不能承诺零改造兼容所有 Agent。

### Q13. 网关、Sidecar、SDK、插件都能做，你实际是哪一种技术路线？

**推荐答案（10 秒版）：**

> **实际是本地进程内插件，SQLite 本地存储。** Sidecar Gateway 是适配其他宿主的能力，不是本次主部署路线。

这是面试官想要的答案。不要再从四种方案的优缺点开始讲。

### Q14. 落地过程中踩过什么坑，引发过什么问题？

**推荐答案（选一个真实经历重点讲，以下不要全部冒充线上事故）：**

> 一个比较典型的问题是 **记忆自我污染**。Recall 注入的 `<relevant-memories>` 如果下一轮又被 Capture 当作用户原话保存，系统会反复记住自己生成的内容，错误会被越放越大。我们后来把原始用户输入和增强后的 Prompt 分开，Capture 时优先使用原始输入，并过滤系统注入标签、框架消息和大段代码。
>
> 第二个是 **双写一致性**。L0/L1 的 JSONL 是审计证据，SQLite/向量索引是在线检索真相，两边不在一个事务里。Embedding 或索引写失败时，原文还在但语义检索可能暂时缺失。处理上先保住原始证据和 FTS，Embedding 后台补，同时需要对账与幂等重建，不能把双写说成强一致。
>
> 如果面试官问“实际引发了什么结果”，必须补充 **[真实现象、发现方式、影响范围、修复和回归测试]**。没有生产事故记录时，应说“这是测试中发现的故障模式”，不要包装成线上事故。

### Q15. 昨天讨论同一件事时用方案 A，今天改成 B，系统怎么知道是同一件事？

**推荐答案：**

> 当前系统不是先做一个绝对准确的“主题 ID 判定”，而是两阶段处理。
>
> 写入时，新事实会先用向量或 FTS 找相似旧记忆，再由模型结合主体、事件和上下文判断 `store / skip / update / merge`。读取时，当前问题同时走关键词和向量召回，再用 RRF 合并；因此即使今天换了表达，仍有机会召回昨天同项目、同技术点的记录。
>
> 但我要承认，当前没有完整的“实体 + 属性 + 项目 Scope + 生效时间”确定性 Schema。A 到 B 究竟是替代、并存还是不同分支，模型判断仍可能错。下一版更稳的方式是把决策记录建成结构化事件：`project_id`、`topic`、`decision`、`valid_from`、`supersedes` 和来源消息都明确保存。判断不了时并存并标冲突，不硬覆盖。

### Q16. 同一个主题每天都聊，后面是不是每次要捞出全部历史再总结，效率会很差？

**推荐答案：**

> 不会每次把这个主题的全部原始历史捞出来再总结。系统使用的是分层和有界召回。
>
> 原始消息保留在 L0；值得长期使用的信息提成 L1；同主题内容在后台更新或合并进 L2 场景；L3 只保留紧凑画像。在线 Recall 默认只取少量 Top-K 候选，全文和向量并行，再受 Token Budget 限制。通常先返回索引级摘要或当前规范记录，只有需要争议核对时才下钻 L0 原话。
>
> 这样查询成本主要和候选集、索引和最终 Top-K 有关，不和全部历史线性增长。但后台聚合、SQLite 写竞争和热点用户积压仍然是真实成本，需要监控队列最老年龄、Embedding 欠账和 Recall 延迟，不能说分层后性能问题自动消失。

### Q17. 记忆数据是存在 SQLite 吗？

**推荐答案：**

> 当前本地部署里，SQLite 保存元数据、FTS5 全文索引和可选的 sqlite-vec 向量索引；L0/L1 的原始追加证据还会保存在 JSONL，L2/L3 是 Markdown，Offload 原始工具结果放在 refs 文件里。所以准确说法是 **“SQLite 是在线检索 Store，但不是唯一真相载体”**。

## 三、CodeWiki：pgvector、增量与版本一致性

### Q18. 除了 SQLite 的轻量向量能力，实际项目中还用过哪些向量库？

**推荐答案：**

> 实际项目里用过 PostgreSQL 的 `pgvector`，是在 CodeWiki 中。CodeWiki 默认 Local-first 走 SQLite + FTS5 + sqlite-vec；需要集中式部署时，Store 可以切到 PostgreSQL，全文检索用 `tsvector + GIN`，向量用 pgvector。
>
> 我没有实际落地过 Milvus、Qdrant 或 Weaviate，就不会把理论了解说成项目经验。

### Q19. 哪个项目用了 pgvector？具体表怎么设计？

**推荐答案：**

> 是 CodeWiki。源码首先按符号范围生成 `code_chunk`，主要字段包括 `id`、`repo_id`、`node_id`、`file_path`、`start_line`、`end_line`、`content`、`content_hash` 和 `token_count`。
>
> Embedding 分成元数据和物理向量两层：
>
> - `code_chunk_embedding` 保存 `repo_id`、`chunk_id`、`model`、`dimensions`、`content_hash` 等关联信息，并通过 `(repo_id, chunk_id, model)` 保证唯一。
> - 物理向量按维度放在 `code_chunk_embedding_vec_<dimensions>`，例如 1536 维就是 `code_chunk_embedding_vec_1536`，字段使用 `vector(1536)`。
>
> 按维度分表是因为不同 Embedding 模型可能是 768、1024 或 1536 维，PostgreSQL 的 vector 列维度固定，不能把不同维度硬塞在同一列。模型和 Content Hash 还用于复用相同内容的 Embedding。

### Q20. 索引具体怎么建？

**推荐答案：**

> 这里有三类索引，职责不同：
>
> 1. `code_chunk_embedding` 上用 `(repo_id, chunk_id, model)` 唯一索引保证一段代码在同一模型下只有一份有效 Metadata。
> 2. PostgreSQL 的代码文本检索在 `code_chunk` 的 `to_tsvector` 表达式上建 GIN 索引，用于符号名、路径和代码文本的关键词召回。
> 3. 每个按维度的 pgvector 表上建 HNSW cosine 索引，用于近似向量检索；查询还必须按 `repo_id` 和 `model` 限定，避免不同仓库和不同向量空间混查。
>
> GraphRAG 不是只查向量：符号搜索、FTS、向量命中先形成 Seed，再沿代码图扩展。向量不可用时，符号、全文和图检索仍能工作。

**不要补不存在的参数：** 如果没有真实 DDL 记录，不要现场编 `m`、`ef_construction`、`lists` 或召回延迟。

### Q21. 向量数据更新和维护踩过什么坑？

**推荐答案：**

> 更新不是原地修改浮点数组，而是跟源码 Chunk 生命周期走。代码内容或位置变化后通常生成新的 Chunk ID；本轮 Active ID 与旧 ID 做差集，旧 Chunk 失效，新 Chunk 再补 Embedding。同模型、同 Content Hash 的向量可以复用。
>
> 当前一个真实缺口是 **孤儿物理向量**：Chunk 删除后，Embedding Metadata 会级联失效，但按维度的向量表不是 `code_chunk` 的外键子表；现有删除顺序没有证明物理向量行一定同步清干净。所以只能说旧向量不会再通过有效 Metadata 参与正常检索，不能说磁盘里绝对没有残留。
>
> 另一个问题是模型升级。不同 Embedding 模型的向量空间不能混用，必须按模型和维度建新索引、后台 Reindex、切流后再清旧分区，不能只重算新增数据。

### Q22. 基于上个版本拉了一个大分支，本地代码改动很多，但向量还是旧版本，怎么办？

**推荐答案（先承认当前边界）：**

> 这个问题成立。**如果检索索引仍对应上一个 Commit，而当前 Agent 正在读大量未提交的新代码，检索结果就可能是旧的，不能直接拿来指导修改。**
>
> 当前 CodeWiki 会用 Git Diff 和文件 Hash 找 changed/new/deleted 文件，MCP Lite 启动时也可以检查文件变化并触发一次增量更新，这能降低过期概率。但它维护的还是当前工作区快照，Graph、Chunk、Wiki 和源码读取还没有统一绑定一个不可变 Revision，所以不能说已经彻底解决大分支和并发修改的一致性问题。
>
> 最小可用方案有三步：
>
> 1. 索引 Scope 绑定 `repo + branch/worktree + revision`，未提交改动再计算 working-tree content hash，不能让不同分支共用一个“当前索引”。
> 2. 每次检索前比较当前 Commit、Git status 和文件 Hash；有变更就增量更新受影响的 Chunk、图和向量。更新完成前要明确返回 `stale`，而不是静默使用旧索引。
> 3. 检索结果和 Source Ref 携带 `revision_id + content_hash`；Agent 真正读文件前再次校验。取证后文件又变了，就让本轮结果失效并重检，不能把旧证据当新代码。
>
> 更完整的下一版是不可变 Snapshot 和版本化图，让每次分析、检索、Wiki 生成都固定在同一个 Revision 上。

### Q23. 如果都要频繁切换和更新，为什么不让 Coding Agent 自己 grep、读文件、分析？

**推荐答案：**

> 对小仓库、一次性改动或本地变化特别快的分支，我也会直接用成熟 Coding Agent 搜索和读代码，没必要强行加 CodeWiki。这个反例是成立的。
>
> CodeWiki 的目标场景是反复出现的跨模块问题和团队知识复用：它把类、函数、调用关系、源码范围和 Wiki 沉淀成可重复查询的结构化证据，同一条依赖关系不必每个会话都重新推断；回答还能回到文件和行号核对，也可以通过 MCP 给不同 Agent 使用。
>
> 但这只是价值假设，不是天然优势。今天的 Coding Agent 已经很强，最终要用同一批真实任务做三组对照：原生 Agent、Agent + 简单 Repo Map/Skill、Agent + CodeWiki，比较任务成功率、跨模块召回、引用正确性、Token、索引成本和陈旧率。如果 CodeWiki 的维护成本高于增量收益，就应该缩小到 Lite Graph/Repo Map，甚至直接不用。

### Q24. CodeWiki 在今天还有什么不能被普通 grep 替代的能力？

**推荐答案：**

> `grep` 很擅长精确找字符串，但它不会天然回答“这个接口影响哪些调用方”“一个 Symbol 的定义、引用、继承和路由关系是什么”，也不会持久保存带来源的模块说明。CodeWiki 的增量价值主要是代码结构图、跨文件关系、社区结构和可引用文档。
>
> 同时要承认，跨文件 Calls/References 当前仍是启发式的，反射、动态派发和运行时注册会漏；它不是编译器，也不是成熟 LSP 的替代品。因此真正合理的产品形态应是：先让 Agent 用原生搜索解决简单问题，只有需要结构化、多跳和共享证据时再调用 CodeWiki，而不是所有请求都强制经过平台。

## 四、Agent Skills 与新一代代码分析方式

### Q25. 现在有很多帮助 Agent 快速分析代码的 Skills，你有研究过吗？

**推荐答案：**

> 有。我把 Skill 理解成 **可发现、按需加载的过程知识**，而不是另一个向量数据库。一个 Skill 通常用 `SKILL.md` 描述适用场景和步骤，需要时再加载 references、scripts 或模板；真正读代码、搜索、运行测试的还是 Agent 的 `read`、`grep`、`bash`、LSP 或 MCP 工具。
>
> 我重点关注了三个设计点：第一，渐进披露，启动时只暴露名称和描述，命中任务后才读完整说明；第二，把分析流程写成可验证步骤，例如先读入口和构建文件，再画模块关系，再核对调用证据；第三，产物尽量落成普通 Markdown、JSON 或仓库内文件，便于人审阅和 Git 管理。
>
> 如果只做过资料研究，没有实际写过或运行过 Skill，要明确说“研究和试用”，不要说成生产落地。

### Q26. 如果让你重新设计 CodeWiki，哪些 Skill 理念值得借鉴？

**推荐答案：**

> 我会借鉴五点：
>
> 1. **默认不预建重索引。** 先让 Agent 用 Skill 指导原生搜索、Repo Map、AST 或 LSP 处理一次性任务；只有高频、跨模块场景再建立持久图索引。
> 2. **渐进披露。** 先返回模块目录、Symbol 和短摘要，需要时再加载调用图、源码片段或完整 Wiki，减少一次性上下文。
> 3. **文件是真相源。** 生成的分析、决策和模块说明优先落到仓库内 Markdown/JSON，索引只是可重建的派生层，避免数据库成为不可见黑盒。
> 4. **每次先校验当前工作区。** Skill 在执行前读取 Commit、分支和 dirty files；产物携带 Revision 与内容 Hash，过期就重新分析。
> 5. **组合而不是替代。** Skill 决定分析步骤，`grep/read/LSP` 提供实时事实，CodeWiki MCP 只在需要图扩展、跨会话复用或团队共享时提供增强。
>
> 这会把 CodeWiki 从“所有仓库都先全量建 RAG 平台”收缩成“轻量实时分析优先，持久知识按收益升级”的分层产品。

### Q27. Skill 不使用 RAG 数据库，它怎么分析代码？生成的文档存在哪里？

**推荐答案：**

> Skill 本身只是过程说明，不负责神奇地“记住整个仓库”。它通过 Agent 已有工具实时读取文件、`grep`/`rg` 搜索、运行脚本、查询 LSP 或调用 MCP；分析结果可以直接进入当前上下文，也可以按 Skill 约定写成仓库内的 Markdown、JSON、Repo Map 或其他 Artifact。
>
> 要区分三类存储：
>
> - Skill 定义存在 `SKILL.md` 及其 `references/`、`scripts/`、`assets/` 目录。
> - 本次会话和工具轨迹通常由 Agent Harness 保存，例如本地 JSONL Session。
> - 真正需要复用的分析文档，按约定写入工作区或项目文档目录，由 Git 版本化；如果只是一次性分析，也可能只存在当前会话，不会自动沉淀成永久文档。
>
> 所以“不用向量库”不等于“不存东西”，而是使用文件系统、会话日志和实时工具代替预先维护的语义索引。规模变大、查询重复度升高时，仍可以给这些文件增加 FTS、Repo Map 或可重建索引。

### Q28. Skill、Prompt、Tool 和 RAG 的边界是什么？

**参考答案：**

> Skill 告诉模型“这类任务应该按什么步骤做”；Prompt 是当前请求实际进入模型的指令和上下文；Tool 赋予模型读取文件、搜索、执行命令等能力；RAG 是从外部知识中召回相关内容的机制。Skill 可以指导 Agent 何时调用 RAG 或 CodeWiki，但 Skill 本身既不是权限系统，也不是数据库。

由于没有候选人声道和结束语，不能确定是否通过。仅从追问模式看：

- **不是明显的“项目造假淘汰”**：面试官愿意继续下钻 pgvector、版本一致性和 Skills，说明项目仍有可信度。
- **也不是明显的“技术通过”**：部署形态需要面试官反复逼问，核心产品又被最简单替代方案挑战，说明回答没有形成稳定优势。
- 如果岗位偏 **AI 应用和快速交付**，CodeWiki 过重、Skills 跟进不足会是风险。
- 如果岗位偏 **Agent 基础设施和知识工程**，Memory Core、Hybrid Recall、Offload 和 pgvector 仍有匹配点，但必须提升表达确定性。

综合判断：**中等偏弱，存在较高候选人比较风险。**

## 七、五个必须练熟的短答案

### 1. 记忆系统到底是什么形态？

> 实际是本地进程内插件，数据主要落 SQLite，原始证据和高层摘要还分别用 JSONL、Markdown 和 refs 文件。插件在模型调用前 Recall，一轮提交后 Capture。独立 Gateway 是可选适配能力，不是这次项目实际采用的主部署方式。

### 2. 它是不是扩大了模型窗口？

> 不是。它不改变物理窗口，只让固定窗口用得更有效：跨会话信息按需召回，大工具结果外移后只留摘要、任务状态和引用，需要精确细节再读原文。

### 3. A 方案变成 B 方案，怎么知道是同一件事？

> 当前先用 FTS 和向量找相似候选，再结合上下文做新增、跳过、更新或合并；读取时也用 Hybrid Recall。它能处理很多表达变化，但还没有完整的项目、主题和生效时间 Schema，所以不能保证所有 A/B 变更都判断正确。下一版要把决策和 supersedes 关系结构化。

### 4. 本地代码大量变化，旧向量怎么办？

> 旧索引不能直接用。先比较 Commit、dirty files 和内容 Hash，对变更文件增量重建；索引必须按 repo、worktree 和 revision 隔离，检索结果携带 Revision 和 Source Hash，读文件前再校验。当前实现能做 Git Diff/Hash 增量，但还没有完整不可变快照，这是现有限制。

### 5. 为什么不直接让 Coding Agent grep？

> 小仓库和一次性任务我也会直接用 Agent，不强加 CodeWiki。CodeWiki 只在反复的跨模块问题、结构关系、带来源文档和团队复用上可能有增量价值。这个价值必须和原生 Agent、Repo Map/Skill 做同任务对照；没有净收益就应该降级成轻量工具或不用。

## 九、推荐反问

这场没有保留反问环节。若进入下一轮，可以围绕面试官已经暴露的关注点反问：

1. **这个岗位当前最优先的 Agent 场景是什么：物流业务自动化、内部研发提效，还是 Agent 平台建设？**
2. **团队更倾向让 Agent 实时读取业务系统，还是先建设可持久的知识和记忆层？目前最大的失败案例是什么？**
3. **你们评估 Agent 项目时最关注任务成功率、人工节省、延迟还是模型成本？是否已有基线任务集？**
4. **岗位中传统后端、AI 应用开发和 Agent Runtime 的预期占比分别是多少？**
5. **代码和物流业务数据对外部模型的使用边界是什么，是否有内网模型网关和审计要求？**

反问的目的不是展示名词，而是确认岗位到底需要“快速做业务 Agent”，还是“建设通用 Agent 基础设施”。这两类岗位对 CodeWiki 和 Memory 项目的评价标准完全不同。
