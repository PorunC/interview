### 0.2 本场最关键的三个问题

1. **基础知识回答没有形成连续得分。** 面试官在 `@Autowired` / `@Resource`、MyBatis-Plus、ConcurrentHashMap、ReentrantLock、AQS、事务传播、分布式事务、GC 上连续下探，且多次以“不太清楚”“没有”“pass”结束。这会直接影响“三年 Java 后端”的可信度。

3. **离职理由被面试官反证。** 如果理由只是“公司不能用 Claude/Codex”，面试官很容易反问：“你个人可以学，为什么一定要离职？”必须把根因改为 **工作内容、生产落地空间和职业方向不匹配**，工具只是表象。

## 二、React 与 Java 基础题

### Q9. React 中箭头函数的 `this` 指向哪里？

**标准答案：**

> 箭头函数没有自己的 `this`，它在定义时词法捕获外层作用域的 `this`，不能通过 `call`、`apply`、`bind` 改变。普通函数的 `this` 则取决于调用方式。
>
> 在 React 函数组件和 Hooks 中通常不使用 `this`；在类组件中，箭头函数常用于事件处理器，因为它会捕获组件实例的 `this`，避免手动 `bind`。

```javascript
class Counter extends React.Component {
  state = { count: 0 };

  handleClick = () => {
    // this 词法绑定到 Counter 实例
    this.setState(({ count }) => ({ count: count + 1 }));
  };
}
```

### Q10. 你用类组件还是 Hooks？Hooks 和类组件生命周期怎么对应？用过哪些 Hooks？

**推荐答案：**

> 我主要使用函数组件和 Hooks。Hooks 不是把类组件生命周期一一改名，而是按“副作用”组织逻辑，大致可以这样对应：
>
> - `useEffect(fn, [])`：组件提交到 DOM 后执行一次，类似 `componentDidMount`；返回的 cleanup 在卸载时执行。
> - `useEffect(fn, [deps])`：首次提交和依赖变化后执行；下一次 effect 前先执行上一次 cleanup，覆盖了 mount、update、unmount 三段行为。
> - `useEffect(fn)`：每次提交后都执行。
> - `useLayoutEffect`：DOM 更新后、浏览器绘制前同步执行，只用于需要测量布局等场景，避免阻塞绘制。
>
> 我常用 `useState` 管局部状态，`useEffect` 处理请求或订阅，`useMemo` 缓存昂贵计算，`useCallback` 稳定回调引用，`useRef` 保存 DOM 引用或跨渲染可变值，复杂状态会用 `useReducer`。我不会为了“优化”到处使用 `useMemo/useCallback`，只有在计算昂贵或引用稳定确实影响子组件时使用。

**加分点：** React 18 的开发环境 Strict Mode 可能额外执行一次 setup/cleanup 来暴露不安全副作用，不能把它误判为生产环境执行两次。

### Q11. `@Autowired` 和 `@Resource` 有什么区别？底层怎么实现？推荐哪个？

**标准答案：**

> `@Autowired` 是 Spring 注解，默认按类型注入；有多个同类型 Bean 时结合 `@Qualifier`、`@Primary` 或名称消歧。`@Resource` 来自 Jakarta/JSR-250，语义上优先按名称匹配，Spring 找不到同名 Bean 时可回退到类型匹配。
>
> 底层上，`@Autowired` 主要由 `AutowiredAnnotationBeanPostProcessor` 解析，`@Resource` 主要由 `CommonAnnotationBeanPostProcessor` 解析；两者最终都在 Bean 创建和属性填充阶段向 `BeanFactory` 解析依赖并注入。
>
> 我实际推荐 **构造器注入**。单构造器在现代 Spring 中可以不写 `@Autowired`，依赖显式、便于单元测试，也能让字段保持 `final`，避免字段注入导致隐藏依赖。只有确实需要按名称注入时才使用 `@Qualifier` 或 `@Resource(name = "...")`。

```java
@Service
public class PaymentService {
    private final PaymentRepository paymentRepository;

    public PaymentService(PaymentRepository paymentRepository) {
        this.paymentRepository = paymentRepository;
    }
}
```

### Q12. `ThreadLocal` 是做什么的？项目中用过吗？有什么风险？

**标准答案：**

> `ThreadLocal` 为同一个线程保存一份独立变量，常用于请求上下文、traceId、租户信息或无法逐层传参的框架状态。它不是让对象线程安全，而是用线程隔离避免共享。
>
> 在线程池中线程会复用，使用后必须在 `finally` 中 `remove()`。`ThreadLocalMap` 的 key 是弱引用、value 是强引用；key 被回收后，如果线程长期存活而 value 没清理，可能造成内存泄漏，也可能把上一个请求的用户上下文带到下一个请求。

```java
try {
    REQUEST_CONTEXT.set(context);
    chain.doFilter(request, response);
} finally {
    REQUEST_CONTEXT.remove();
}
```

**如果项目没直接用：**

> 业务代码里我没有主动用过，所以不会说“用过”。但我知道 Spring 事务同步、日志 MDC 等框架场景会使用类似的线程上下文机制，也知道在线程池和异步切换时上下文不会自动传播，需要显式传递或使用框架支持。

### Q13. 用 MyBatis-Plus Lambda 写：统计年龄大于 20 且性别为男的学生数

```java
Long count = studentMapper.selectCount(
    Wrappers.<Student>lambdaQuery()

```

也可以使用：

### Q14. `HashMap` 和 `ConcurrentHashMap` 有什么区别？Java 8 如何保证并发安全？

**标准答案：**

> `HashMap` 不保证线程安全，并发写可能出现覆盖、数据不可见或结构状态不一致。`ConcurrentHashMap` 支持高并发读写，并提供 `putIfAbsent`、`compute` 等原子复合操作；它不允许 `null` key 或 `null` value，避免并发读取时无法区分“没有映射”和“值为 null”。
>
> Java 8 的 `ConcurrentHashMap` 不再使用早期版本的 Segment。底层是数组加链表/红黑树：空桶插入主要用 CAS；桶内发生冲突时对桶头节点做细粒度 `synchronized`；链表达到阈值且数组容量足够时树化；读取主要依赖 `volatile` 可见性，不需要给整个表加锁。扩容时多个线程可以协助迁移。
>
> 但“容器线程安全”不等于多步业务操作原子。例如 `if (!map.containsKey(k)) map.put(k, v)` 仍有竞态，应使用 `putIfAbsent` 或 `computeIfAbsent`。

### Q15. 什么是可重入锁？不可重入会怎样？`ReentrantLock` 和 AQS 是什么关系？

**标准答案：**

> 可重入指同一个线程已经持有锁时，可以再次获取同一把锁；锁内部维护 owner 和持有次数，释放相同次数后才真正解锁。它解决同一调用链中外层方法加锁后又进入同锁保护的内层方法的问题。不可重入锁在这种情况下会让线程等待自己释放锁，形成自我死锁。
>
> `ReentrantLock` 相比 `synchronized` 还支持可中断获取、超时尝试、公平锁以及多个 `Condition`。必须在 `finally` 中解锁。

```java
lock.lock();
try {
    updateState();
} finally {
    lock.unlock();
}
```

> AQS（`AbstractQueuedSynchronizer`）是很多 JUC 同步器的基础。它用一个 `volatile state` 表示同步状态，通过 CAS 修改状态，并用 FIFO 等待队列管理竞争线程，失败的线程会 park，状态释放后再 unpark。`ReentrantLock` 用 AQS 的独占模式实现；`Semaphore`、`CountDownLatch` 等也基于 AQS 的共享或独占机制。

### Q16. Spring 事务有哪几种传播行为？主要解决什么问题？

**先给一句话：**

> 事务传播行为解决的是：**一个带事务的方法调用另一个带事务的方法时，内层方法应该加入现有事务、创建新事务、挂起事务，还是禁止事务。**

| 传播行为 | 含义 | 常见场景 |
|---|---|---|
| `REQUIRED` | 有事务就加入，没有就新建；默认值 | 大多数业务写操作 |
| `REQUIRES_NEW` | 挂起外层事务，始终新建独立事务 | 独立审计记录；需注意连接池和一致性 |
| `NESTED` | 在当前事务中建立保存点，可局部回滚 | 单库、驱动支持 savepoint 的局部失败 |
| `SUPPORTS` | 有事务就加入，没有就非事务执行 | 可选事务的只读逻辑 |
| `NOT_SUPPORTED` | 挂起当前事务，以非事务方式执行 | 不应占用长事务的操作 |
| `MANDATORY` | 必须在已有事务中，否则抛异常 | 强制由上层控制事务边界 |
| `NEVER` | 必须无事务，有事务则抛异常 | 明确禁止事务环境的逻辑 |

**易错点：** Spring 声明式事务通常基于代理，同一个类中的 `this.innerMethod()` 自调用可能绕过代理，导致 `@Transactional` 和传播配置不生效。

### Q17. 什么是幂等？在程序里怎么保证？

**标准答案：**

> 幂等指同一个业务请求执行一次或多次，最终业务结果一致。它不是“接口永远只执行一次”，而是重复到达不会产生重复扣款、重复订单或重复消息副作用。
>
> 以支付回调为例：
>
> 1. 上游传稳定的业务号或幂等键，例如 `paymentNo`。
> 2. 数据库对业务号建立唯一索引，这是最终兜底。
> 3. 在本地事务中检查状态并做条件更新，例如只有 `PROCESSING` 才能变成 `SUCCESS`。
> 4. 建立幂等记录，保存处理中、成功、失败和原始响应；重复请求返回第一次的结果。
> 5. 下游消息消费者也按事件 ID 去重，并允许安全重试。
> 6. 定时对账处理超时和未知状态。
>
> 分布式锁只能减少并发竞争，不能替代唯一约束、状态机和事务；锁过期或服务重启后，数据库约束仍必须兜底。

### Q18. 微服务如何保证分布式事务一致性？强一致性是什么？

**推荐答案：**

> 我会先按业务要求选择一致性等级，而不是默认所有跨服务操作都做强一致。强一致性要求事务完成后所有参与方立即看到同一结果，通常需要 XA/2PC 或强一致数据库能力，代价是耦合、延迟和可用性下降。
>
> 对大多数业务流程，我更倾向最终一致：服务 A 在同一个本地事务里写业务表和 outbox 事件，后台可靠投递到 MQ；服务 B 以事件 ID 幂等消费，失败自动重试，超过阈值进入死信和人工处理；再配合状态机、补偿操作和定时对账。这样避免“数据库提交了但消息没发出”的双写问题。
>
> 对必须跨服务协调的长流程，可按场景选择 TCC 或 Saga；TCC 控制强但侵入大，Saga 用一系列本地事务和补偿动作，适合长事务但只保证最终一致。金融核心账务应尽量把不可分割的记账放在同一强一致边界内，跨系统通知再异步化。

**如果没有设计经验：** 可以诚实说“我没有主导过分布式事务框架选型”，但必须继续讲清自己参与过的本地事务、幂等、消息重试或对账实践，以及如果设计会如何取舍。

### Q19. Minor GC 和 Full GC 有什么区别？

**标准答案：**

> Minor GC，也常叫 Young GC，主要回收年轻代的 Eden 和 Survivor 区，存活对象复制到 Survivor 或晋升老年代。它通常更频繁、停顿更短，但仍一般会有 STW。
>
> Full GC 通常会处理整个 Java 堆，包括年轻代和老年代，很多收集器还会处理元空间，停顿显著更长。常见诱因包括老年代空间压力、晋升失败、元空间不足、显式 `System.gc()` 或收集器退化。
>
> `Major GC` 这个词在不同资料和收集器中含义不完全一致，面试时最好明确所指收集器。以 G1 为例，更准确的术语是 Young GC、Mixed GC 和 Full GC；Mixed GC 会同时回收年轻代和部分老年代 Region，并不等于 Full GC。

## 三、AI Coding 与本人贡献

### Q20. 这些项目是从 0 到 1 吗？你写代码和 AI 写代码的比例是多少？是不是你不写代码？

**面试官担心：** 不是反对 AI 生成代码，而是确认你是否还能做架构判断、定位问题并为结果负责。

**推荐答案：**

> 三个项目的需求澄清、架构设计、数据边界、接口、验收指标和上线责任由我负责。AI 主要生成局部实现草稿、测试样例、重复性适配代码和文档初稿；核心数据模型、并发与事务边界、权限、评测、故障处理以及最终代码 review 由我决定。
>
> 如果一定要按代码量估算，我会根据真实 Git diff 给一个区间：[按真实记录填写]。但这个比例容易误导，因为 AI 可能一次生成很多最终被删除的代码。更准确的说法是：**AI 可以产出草稿，我对进入主干的每一行代码负责**。所有代码都要经过静态检查、单元测试、集成测试和人工 review，不会把模型输出直接推到生产。

**必须准备一个具体例子：**

> 例如在 [真实模块] 中，AI 先生成了 [采集器/解析器] 的初版，但它没有处理分页、重试和幂等。我补了 cursor 持久化、指数退避、唯一键和失败告警，并用异常用例验证。这个例子比报“70% 是 AI 写的”更能证明能力。

### Q21. 你使用 AI Coding 的完整开发流程是什么？

**参考答案：**

> 1. **需求和约束先行**：先写清业务目标、输入输出、不可违反的约束、数据权限和验收指标。
> 2. **设计切片**：我先定模块边界、接口、数据模型和风险点，把任务切成可独立验证的小变更。
> 3. **给 AI 最小必要上下文**：只提供相关文件、接口和测试，不把整个公司仓库或敏感数据上传外部工具。
> 4. **生成与解释**：让 AI 先给方案或 patch，并要求说明假设；复杂逻辑先讨论再写代码。
> 5. **人工 review**：检查正确性、异常路径、事务、并发、权限、可维护性和依赖风险。
> 6. **自动验证**：运行格式化、静态检查、单测、集成测试和安全扫描；失败信息再反馈给 AI 修复。
> 7. **小步提交**：每个提交只做一件事，保留可回滚性和审计记录。
> 8. **上线与复盘**：灰度、监控、告警，线上 bad case 回到测试集和 prompt/规则中。

一句话：**AI 缩短实现反馈周期，但需求判断、风险控制和验收责任不外包给模型。**

## 四、项目一：AI 周报系统

### Q22. 这个项目到底解决什么问题？是省掉每个人填周报，还是把大家的周报再汇总？

**本场最大表达问题之一：** 面试官连续追问后仍不清楚业务对象，说明项目介绍先讲了“自动化、采集、LLM”，却没有说原流程由谁做、哪一步被替代。

**推荐答案：**

> 原流程不是让一百个人先写完周报、系统再简单汇总，而是 [按真实业务说明责任人] 每周需要登录多个内部系统，手工导出、清洗、核对数据，再按固定结构写成运营/研发周报。单轮需要约 8 到 10 小时。
>
> 系统直接从获批的数据源通过 API、数据库只读查询或文件接口采集数据，完成字段映射、去重、统计和异常校验，再生成并推送周报，把端到端时间缩短到约 20 分钟。因此它主要省掉的是 **跨系统采集、重复整理、核对和撰写**。如果某些主观进展仍只能由员工输入，那部分不会假装被自动化。

**一定要补齐四个名词：** `谁每周在做 → 从哪里取数据 → 产出给谁看 → 哪些人工步骤被省掉`。

### Q23. 数据怎么自动采集？大模型用在哪？这是不是没有大模型也能做？

**推荐答案：**

> 数据采集与统计本身不依赖大模型，主要是定时调度、连接器、字段标准化、增量游标、去重、重试和对账。所有数字由确定性代码计算，不能让 LLM 算数。
>
> LLM 只用于非确定性的表达层：把已经验证的结构化指标组织成自然语言，按固定章节提炼亮点、异常和风险，并支持不同受众的表达方式。生成后会把文本中的数字回查结构化结果，不一致就重试或回退到模板。
>
> 所以诚实地说，固定模板完全可以实现基础周报；LLM 的增量价值是减少人工写作和让叙述适应不同数据变化，而不是负责采集、统计或凭空做根因分析。项目的核心价值是端到端自动化，LLM 是其中一层，不需要为了“AI 项目”夸大它的占比。

### Q24. 最终是 Dashboard 还是文字？采集代码是谁写的？

**参考答案：**

> 当前主要交付物是 [按真实情况：结构化文字周报/邮件/页面]，不是把普通 Dashboard 包装成 AI。数据层会保留结构化指标，便于审计和后续可视化；LLM 生成的是固定结构下的文字叙述。
>
> 采集代码的第一版有 AI 辅助生成，但数据源协议、字段映射、分页、重试、幂等、权限和测试由我设计并验收。我不会把“AI 生成初稿”说成“系统自己完成开发”，最终生产责任在我。

## 五、项目二：CodeWiki 代码智能平台

### Q25. CodeWiki 到底是什么？解决什么问题？生成什么样的文档？

**推荐答案（先用场景定义产品）：**

> CodeWiki 是面向中大型代码库的持续更新代码知识平台。它解决的不是“看不懂某一行代码”，而是新人接手或开发跨模块需求时，不知道入口、调用链、数据模型和影响范围，需要人工在多个仓库里跳转阅读。
>
> 离线侧先解析仓库的 AST 和符号关系，建立函数、类、模块、接口及调用/依赖图；再生成一本有目录的代码知识库，内容包括系统总览、模块职责、关键业务流程、接口和数据模型、核心调用链，以及可回到源码位置的引用。在线侧支持自然语言提问，先语义召回相关代码，再沿依赖图补齐上下游，最后让模型基于证据回答。
>
> 它不是一次性让模型“扫一下仓库写 Markdown”，而是把结构化代码事实、可追溯文档、问答检索和增量更新组合在一起。

### Q26. 直接让 Claude/Codex 扫仓库不就可以了吗？CodeWiki 的不可替代价值是什么？

**推荐答案：**

> 小仓库和一次性问题，直接让成熟 Coding Agent 扫仓库确实更省事，我不会说 CodeWiki 全面优于它。CodeWiki 主要解决三类企业场景：
>
> 1. **持久化与共享**：一次扫描得到的上下文通常属于当前会话；CodeWiki 把知识沉淀成团队可复用、可检索、可审计的资产。
> 2. **确定性结构**：函数调用、继承和模块依赖由 AST/静态分析得到，不依赖模型每次重新猜调用链。
> 3. **增量更新与大仓库**：基于 git diff 更新受影响节点和页面，不需要每个开发者每次全量重扫。
>
> 成熟 Coding Agent 负责交互式执行，CodeWiki 更像它的企业代码知识底座。最合理的方向不是替代 Claude/Codex，而是通过 MCP 或内部工具接口把 CodeWiki 的结构化检索能力提供给它们。

### Q27. 把源码交给模型有没有安全问题？

**标准答案：**

> 有，所以安全边界必须先于模型能力。公司代码只能进入经过批准的内网模型或企业网关，不能发送到个人 Claude/Codex 账号。服务账号只读访问授权仓库，索引和向量库按项目、租户和权限隔离；敏感文件、密钥、证书、生产配置通过路径规则和 secret scanner 在入模前过滤；日志不记录完整源码和凭证；所有检索和生成保留审计记录。
>
> 即使模型部署在公司内部，也不等于自动安全，还需要最小权限、数据保留策略、模型服务方契约、跨境边界、索引删除和员工离职后的权限回收。

### Q28. 给一个最实用、最能提升效率的使用场景

**推荐答案：**

> 例如一名新同事要修改“网联支付回调后的状态更新”逻辑。传统方式是先找 Controller，再逐层追 Service、领域对象、数据库表、消息发送和下游对账，跨模块阅读可能需要两小时。
>
> 在 CodeWiki 中，他先问“支付成功回调后，订单状态、账务记录和通知分别在哪里更新”。系统先命中回调入口，再沿调用图补齐核心 Service、事务边界、消息生产者和相关表，返回一条带源码引用的调用链，并提示可能受影响的测试和模块。开发者不是直接相信模型结论，而是点击引用核对代码。这样把“找入口和补全上下文”从约两小时缩短到 30 分钟左右。

**面试表达原则：** 场景必须包含 `谁 → 什么时候 → 问什么 → 系统返回什么 → 节省什么`，不能只说“新人入职时用”。

### Q29. 为什么使用 GraphRAG？它和 MCP 是什么关系？

**推荐答案：**

> 普通向量 RAG 擅长找到语义相似片段，但代码改动经常需要“不相似但结构相关”的上下文，例如调用方、被调用方、接口实现和共享数据结构。GraphRAG 先语义召回种子节点，再沿调用/依赖边扩展有限跳数，并按向量相关性、图距离和节点类型重排，在 token 预算内组装证据。
>
> MCP 是工具和上下文接入协议，GraphRAG 是内部检索与知识组织方法，两者不是同一层。当前如果还没有 MCP 接入，应直接说“尚未接入”；下一步可以把 `search_symbol`、`get_callers`、`get_impact_scope` 等能力包装成 MCP tools，让 Claude Code、Codex 或其他 Agent 调用。

### Q30. 你用过 SDD 吗？

**这里的 SDD 大概率指 Spec-Driven Development。**

**诚实回答：**

> 我没有完整使用过某个品牌化的 SDD 框架，所以不会直接说“熟练使用”。但我的开发过程采用了相同原则：先把需求写成可验收的规格，再产出架构和接口设计，把规格拆成任务与测试，然后让人或 AI 按规格实现，最后用验收用例验证，而不是一句 prompt 直接生成整个项目。
>
> 如果用于 CodeWiki，我会先定义 spec：支持哪些语言、文档页面 schema、源码引用必须满足什么约束、增量更新的正确性、检索延迟和评测集；再由设计文档确定 AST 适配器、图 schema、生成/校验状态机，最后把每条 acceptance criterion 映射到自动测试。这样 AI Coding 的上下文更稳定，变更也可追溯。

**如果面试官所指不是 Spec-Driven Development：** 先确认全称，不要凭缩写硬答。

## 六、项目三：Agent 长期记忆与上下文压缩系统

### Q31. 这个系统主要解决什么问题？是不是让模型的上下文窗口变大？

**推荐答案：**

> 它不改变模型物理上的上下文窗口，而是提高固定窗口的有效利用率。Agent 长任务会产生大量对话、工具日志和重复信息；全部塞入 prompt 会增加成本并稀释重点，粗暴摘要又会丢关键证据。
>
> 系统分成两条链路：长期记忆把跨会话有价值的事实、场景和偏好沉淀下来，下一轮按需召回；短期上下文压缩把大段工具输出卸载到外部存储，只在 prompt 中保留结构化摘要、任务状态和可回查引用。这样减少当前上下文占用，同时保留恢复和追溯能力。

### Q32. L0-L3 分层为什么有用？各层分别是什么？

**推荐答案：**

> 分层不是把同一份内容复制四遍，而是按信息粒度、可信度和使用频率管理：
>
> - **L0 原始证据层**：完整对话或事件记录，可追溯，但体积最大，通常不直接全部注入 prompt。
> - **L1 结构化记忆层**：从对话抽取事实、偏好、约束和事件，带来源、时间、置信度和状态，是日常检索主力。
> - **L2 场景层**：把多条相关 L1 聚合成稳定场景或经验，例如某类任务的工作习惯和失败模式。
> - **L3 Persona 层**：更长期、跨场景的用户偏好和特征，只保存稳定信息，不存每轮细节。
>
> 查询时先根据当前问题召回相关 L1/L2，再按需要附带少量 L3；只有核验争议时才回到 L0。系统通过“按需召回”减少 token，而不是把四层一起塞给模型。

### Q33. 这里的“用户画像”指谁？是从 Git commit 分析开发者吗？为什么多轮对话会不一致？

**推荐答案：**

> 这里的“用户”指使用 Agent 的人；在 coding agent 场景里通常是开发者，但画像来源主要是用户与 Agent 的交互、明确偏好和任务行为，不是仅凭 Git commit 给员工打标签。Git 数据如果使用，也只能作为经过授权的辅助业务信号，不能偷换成个人评价。
>
> 多轮会话可能出现信息变化或冲突，例如用户先说默认用 Java 17，后来项目切到 Java 21；也可能是场景不同，例如一个仓库用 Maven，另一个用 Gradle。系统不能简单覆盖：先区分事实类型和作用域，再用时间、来源可信度和显式程度判断；新事实可以 supersede 旧事实，但保留历史和引用；无法判断时并存并在需要时向用户确认。

### Q34. 人物画像只保留特点，那以前聊过的细节不是仍然很大吗？还能分析吗？

**推荐答案：**

> 历史细节仍保存在 L0，但正常请求不会全量读取。系统先用 query 做混合召回：BM25 负责专有名词和精确关键词，向量检索负责语义相似，再用 RRF 融合排序；只取 top-k 的 L1/L2 和必要引用。Persona 只是稳定背景，不承担保存全部历史的职责。
>
> 如果摘要不足，可以通过记忆条目的 source id 回到对应 L0 片段，而不是回放所有会话。也就是说：**保存可以完整，注入必须稀疏；摘要负责导航，原文负责举证。**

### Q35. 这套架构是谁设计的？是论文方案、架构师方案，还是公司任务？你为什么会去找论文？

**推荐答案（按真实边界调整）：**

> 业务问题来自公司在长任务 Agent 中遇到的上下文膨胀和跨会话遗忘，我负责把问题转成技术方案并实现核心模块。L0-L3 不是凭空发明，我先复现线上 bad case，定义 token、召回准确率和任务通过率指标，再调研分层记忆、检索融合、context offloading 等论文和开源实现，比较适用条件后做工程化组合。
>
> 我把“原创”定义为针对业务约束做出的系统设计、取舍和实现，不会把业界已有概念包装成自己发明。面试时我能明确说出：哪些思想来自公开研究，哪些接口、调度、存储、冲突处理和多宿主适配是我设计，哪些模块由同事协作。

**必须准备：** 说出 2-3 个真实参考来源、一个没有照搬的设计，以及一个实验或 bad case 如何改变了方案。不要只说“网上搜论文”。

### Q36. Harness 主要解决什么问题？Hermes 和它有什么不同？

> **转写歧义**：原声道在“Harness / Hermes”处识别不稳定。结合项目资料，最可能是在问这两个概念的区别；若下次再出现，应先复述全称确认。

**参考答案：**

> Agent Harness 是一个抽象的控制层，它把 LLM 放进可控运行环境，负责 agent loop、上下文组装、工具调用、状态持久化、超时重试、权限审批、沙箱、trace、成本和终止条件。模型负责下一步决策，Harness 负责把决策安全、可靠地执行。
>
> Hermes 则是一个具体的 Agent 宿主/运行环境，不是和 Harness 同层的抽象概念。可以说 Hermes 内部实现了一套 Harness；我的记忆系统通过 HTTP Gateway/sidecar 接入 Hermes，Hermes 负责会话和工具执行，记忆服务提供 `capture`、`recall`、`search` 和 session end 等能力。
>
> 我项目里的关键设计是 host-neutral：OpenClaw 通过 hooks 接入，Hermes 通过 Gateway HTTP 接入，内部都调用同一个 `TdaiCore`。所以 **Harness 是机制，Hermes 是具体宿主，Memory 是 Harness 可调用的一个能力子系统**。

## 七、反问环节与面试官透露的信息

### 7.1 面试官明确透露

| 主题 | 信息 | 对候选人的含义 |
|---|---|---|
| 面试流程 | 技术面约两轮；HR 已聊过，后续可能还有价值观/谈薪面；最多约两轮 | 下一轮仍可能继续考技术基础和项目设计 |
| 团队痛点 | 需求爆发增长，文档缺乏，开发效率跟不上需求速度 | CodeWiki、SDD、AI Coding 治理是最直接切入点 |
| AI 工具预算 | 正在申请额度，原则上保障工作使用；看重产出价值，不想过度限制 token | 团队对 AI Coding 开放，但治理和 ROI 可能仍在建设中 |
| 工程体系 | 使用 K8s 等较新技术，但流程成熟度不如招银；偏创业团队 | 个人职责可能更宽，文档、测试和平台能力需要自己补位 |

### 7.2 这段信息反推岗位画像

这个岗位很可能不只是完成 Java 需求，还需要承担以下工作：

1. 用 AI Coding 缩短需求实现周期，但建立代码 review、测试和安全边界。
2. 为快速增长的系统补齐代码知识、接口文档和业务流程文档。
3. 把成熟金融机构的工程纪律带进创业团队，但不能照搬重流程。
4. 在模型额度、数据安全和实际产出之间做取舍。

### 7.3 下一轮建议反问

挑 3-4 个问，不要全部照单念：

1. **岗位边界**：这个岗位是新增还是替补？Java 业务交付、AI 研发提效和平台建设三部分大约各占多少？
2. **首要任务**：入职前三个月最希望解决的是需求吞吐、文档缺失、代码质量，还是某个具体 AI 产品？成功指标是什么？
3. **CodeWiki 场景**：当前文档缺失主要是架构文档、业务规则、接口文档还是新人 onboarding？代码分多少仓库和语言？
4. **AI 安全**：公司批准使用哪些模型和 Coding Agent？源码能否出境？prompt、代码和工具调用是否留审计日志？
5. **工程质量**：需求增长很快时，测试覆盖、PR review、灰度和回滚的底线是什么？最近最常见的返工原因是什么？
6. **团队协作**：香港、深圳、成都团队如何分工？技术决策和业务优先级分别由谁拍板？
7. **工作节奏**：常态工作时间、上线窗口、值班、周末支持和补休机制怎样？

## 八、面试官视角的逐项评价

### 8.1 得分项

1. **经历组合与团队痛点匹配。** 银行后端经验能理解金融系统对安全、事务和审计的要求，CodeWiki 又直接对应“文档缺、研发效率跟不上”。
2. **三个项目都有生产化叙事。** 周报有时间节省，CodeWiki 有实际查询和理解时长，Agent Memory 有 token 和任务通过率指标，比只做 demo 更有说服力。
3. **愿意使用 AI Coding。** 对创业团队而言，能接受新工具并快速实现是正向信号。
4. **反问拿到了实质信息。** 团队痛点、token 策略和工程成熟度都比泛问企业文化更有价值。

### 8.2 主要失分项

1. **Java 基础广度与深度不足。** 这不是单点忘记，而是从容器、锁、AQS、事务到 GC 连续失分。对三年 Java 后端候选人，这是本场最大风险。
2. **回答没有先命中问题。** 面试官连续重复“主要解决什么”说明回答可能先铺背景、后给结论，或用相关术语替代了直接答案。
3. **项目价值被技术细节遮住。** 面试官听到采集、GraphRAG、分层记忆，却没立刻听懂用户、流程和收益。
4. **AI 生成代码的责任边界不清。** 如果只说“采集代码是模型生成的”，会让对方怀疑你不具备脱离工具定位和修复问题的能力。
5. **离职动机过度绑定工具。** “不能用先进 AI 工具”不足以支撑换工作，且容易显得忽视金融机构合理的安全约束。
6. **公司调研方法显得单一。** 只说问过 AI，无法证明核验过监管主体、业务模式、资金口径和负面信息。

### 8.3 面试官风格

- **强打断、强澄清。** 他会在听到模糊名词时立即打断，要求把人数、角色和业务对象落到具体层级。
- **偏实用主义。** 他不追求漂亮定义，反复问“主要解决什么”“什么时候用”“为什么不能直接用现成工具”。
- **技术覆盖广但术语口音/转写不稳定。** `ReentrantLock`、Harness、Hermes 等被识别得比较混乱。候选人应礼貌确认术语，而不是在没听清时猜答案。
- **重视 AI 带来的交付速度。** “token 便宜，产出价值更重要”说明团队愿意为有效提效付费，但也会追问 ROI。

## 九、结果判断与后续策略

### 9.1 本轮结果判断

**结论：中性偏弱，是否推进取决于岗位权重。**

- 如果招聘标准是 **Java 后端为主、AI 为加分项**：本场基础题失分较集中，推进风险较高。
- 如果标准是 **AI 研发提效/知识工程为主、Java 能完成业务接入即可**：CodeWiki 与团队痛点高度匹配，仍有进入下一轮的理由。
- 结束语没有直接约面，只说比较候选人，是典型候选池信号，不应解读为通过，也不是明确拒绝。

### 9.2 二面前最高优先级

1. **补 Java 硬基础**：Spring 注入与事务代理、JUC/AQS、集合并发、JVM 内存与 GC、MyBatis-Plus 常见 CRUD。
2. **每个项目练一个 30 秒版和 2 分钟版**：第一句必须说明用户和问题，最后一句必须说明结果与边界。
3. **准备 AI Coding 责任链**：拿一个真实 commit，能说清 AI 生成什么、你改了什么、测试如何发现问题。
4. **准备 CodeWiki 现场方案**：针对丰泊“需求增长、文档缺失”，设计 30/60/90 天落地路径。
5. **核实 Harness/Hermes 与 SDD**：做到能用一句话定义、用项目映射、说清没做过的边界。

### 9.3 可直接用于二面的 30/60/90 天思路

> **前 30 天**：访谈开发和业务，统计文档缺口、需求 lead time、返工原因和新人常问问题；选一个高频、低风险仓库做试点，建立源码安全和评测基线。
>
> **31-60 天**：上线增量索引和带源码引用的 Wiki/问答 MVP，先覆盖系统总览、模块职责、关键调用链和接口；接入现有 AI Coding 工具，所有回答可回到源码证据。
>
> **61-90 天**：用真实任务评估理解耗时、回答正确率、文档新鲜度和需求 cycle time；把 bad case 变成回归集，再决定扩语言、扩仓库或加入 SDD 流程。不会一开始就承诺“AI 自动写完所有文档和需求”。

## 十、复习速记

### 十句话先背熟

1. 箭头函数没有自己的 `this`，词法捕获定义处外层 `this`。
2. Hooks 按副作用组织逻辑，不是类生命周期 API 的机械改名。
3. `@Autowired` 默认按类型，`@Resource` 语义上优先按名称；实际推荐构造器注入。
4. `ThreadLocal` 是线程隔离，不是线程安全；线程池中必须 `finally remove()`。
5. Java 8 `ConcurrentHashMap` 用 CAS + 桶级 `synchronized` + 红黑树，不是整表锁。
6. 可重入锁允许同一线程重复获取；AQS 用 `state + CAS + 等待队列` 实现同步器骨架。
7. 事务传播解决嵌套调用时加入、创建、挂起或禁止事务的问题。
8. 幂等靠业务键、唯一索引、状态机和重复结果，不只靠分布式锁。
9. 周报的数据采集和统计不需要 LLM；LLM 负责有约束的表达。
10. Harness 是 Agent 控制机制，Hermes 是具体宿主，Memory 是可接入的能力子系统。

### 三个项目统一回答公式

> **谁遇到什么问题 → 原流程为什么慢/不准 → 我设计了什么确定性主链路 → LLM 只负责哪一层 → 如何校验和降级 → 用什么指标证明有效 → 当前边界是什么。**

这个公式比堆叠“GraphRAG、L0-L3、AI Coding”更能让面试官迅速理解项目价值。
