# 货拉拉 · 大数据平台开发工程师 · 三面 Leader 面试准备与答案

> 本文根据公开可检索的货拉拉面试经验帖、候选人的中文/英文简历、三个内部项目材料，以及货拉拉一面和二面真实复盘整理。
>
> **重要边界**：公开面经来自不同年份、岗位和职级，只用于判断问题类型，不代表当前团队固定流程。候选人自己的二面记录优先级最高；Hadoop、Spark、Data Agent、语义层和评测平台的具体内部情况，以二面面试官现场透露为准。
>
> 本文答案全部采用第一人称口语化表达。方括号内容涉及个人事实，必须在面试前用事实清单补齐，不能临场编造。

## 0. 先给结论

货拉拉三面应按**技术 Leader 综合面**准备，而不是按纯 HR 面准备。公开经验显示，Leader 面通常有两种形态：

1. 继续问线程池、Hadoop、Hive、索引、排序和场景设计；
2. 减少八股，重点观察项目真实性、沟通表达、困难复盘、跨领域学习和岗位动机。

结合你的二面结果，最可能的判断标准是：

- 你能不能把 AI 项目中的数据契约、增量更新、质量校验和评测迁移到大数据平台；
- 你是否愿意同时做 Hadoop/Spark 基础设施和 Data Agent，而不是只做模型调用；
- 你能否准确区分“当前已经实现”“本人亲自负责”和“下一版设计”；
- 二面暴露的基础和项目细节缺口是否属于可补齐问题；
- 你是否具备独立推进、跨团队协作和长期稳定投入的能力。

建议准备时间按以下比例分配：

| 方向 | 比例 | 准备目标 |
|---|---:|---|
| Ownership、行为和动机 | 40% | 项目边界、冲突、失败、推进、离职和职业规划 |
| 大数据平台与 Data Agent | 35% | Hadoop/Spark、数据治理、语义层、NL2SQL、评测和可观测性 |
| Java 与基础复核 | 25% | B+树、并发、线程池、Kafka、索引和常见场景 |

### 1.2 从面经得到的可靠结论

1. **Leader 面不是固定模板。** 同一公司不同岗位可能从技术深挖转为项目沟通，也可能继续问大数据组件。
2. **面试官通常会把时间交给候选人表达。** 你的答案越笼统，越容易被评价为“沟通可以但深度不足”。
3. **数据岗位会关注业务治理。** 不只问组件，还会问指标口径、数据漂移、DQC、业务方协作和下游推进。
4. **面试官允许存在知识盲区，但不接受包装。** “没有直接生产经验”可以接受，“把设计稿说成已上线”会降低信任。
5. **大数据平台岗位的技术复核不会因为项目偏 AI 而消失。** Hadoop/Spark、Kafka、索引、线程池和数据一致性仍要准备。

### 1.3 和你的二面信息合并后的高概率判断

你的二面面试官已经说明团队同时负责 Hadoop/Spark 基础设施、Data Agent、NL2SQL、语义层、本体和评测/可观测性。因此三面很可能围绕下面的主线展开：

> 你过去做的是 AI 应用和知识工程；如果加入团队，你能否把这些经验迁移为可靠的数据平台能力，并且诚实面对 Hadoop/Spark 生产经验的差距？

## 2. 个人定位与开场答案

### Q1. 请用一分钟介绍一下自己

> 我是陈柏润，本科毕业于深圳大学软件工程专业，毕业后在招银网络科技从事 Java 后端和 AI 应用开发。我的主线不是单纯调用模型，而是把模型放进一条有数据校验、检索、状态管理和失败处理的工程链路里。

>
> 这三个项目共同涉及数据契约、幂等写入、增量更新、质量校验、评测和故障回放。货拉拉团队同时做大数据基础设施和 Data Agent，这和我的迁移方向比较一致。我会区分自己已经实际使用过的技术和需要补齐的 Hadoop、Spark 生产能力，不把 AI 项目包装成完整大数据平台经验。

### Q2. 为什么想来货拉拉？

> 二面了解到团队不是单纯做 AI Demo，而是同时维护 Hadoop、Spark 等基础设施，并在建设 Data Agent、语义层、NL2SQL 和评测能力。我的优势是 Java 后端、数据处理、知识检索和 Agent 工程化，可以参与数据契约、质量校验、语义建模和评测闭环。
>
> 我希望下一阶段把局部提效项目推进成有真实数据、真实用户和长期运维的平台能力。货拉拉这个团队正好同时具备传统数据底座和 Data 加 AI 的场景，所以比只做模型封装更符合我的发展方向。

### Q3. 为什么想做大数据平台，而不是继续做 AI 应用？

> 我并不是要从 AI 应用切换到完全不相关的方向。过去三个项目让我看到，模型效果最后受数据质量、指标口径、检索版本、权限和评测影响。大数据平台解决的是这些更底层、更长期的问题。
>
> 我希望把已有的 AI 工程经验放到更可靠的数据链路里，例如先由语义层约束表、字段、指标和权限，再让模型生成候选 SQL 或解释，最终由系统完成校验、执行、对账和追踪。这样 AI 才能真正服务业务数据，而不是只生成一段文本。

### Q4. 为什么离开现在的工作？

> 我希望下一阶段能持续参与有真实用户和正式业务目标的 AI 与数据平台建设，而不只是局部工具或个人探索。当前经历让我积累了后端和 AI 工程基础，但在大数据计算、语义层和评测平台方面还有继续深入的空间。
>
> 我认可现在的工作经验，也不会把离职原因归结为某个工具能不能用。更重要的是工作内容和我下一阶段想承担的系统责任不完全一致，所以我在寻找更贴近数据平台和 Data Agent 的团队。

### Q5. 你没有完整 Hadoop/Spark 生产经历，为什么认为自己适合？

> 这是我的明确差距，我不会把 NumPy、GraphRAG 或本地 Memory 直接说成 Hadoop/Spark 生产经验。但我已有的能力可以迁移：多源采集、数据清洗、任务状态、幂等写入、重试补数、质量校验、版本化、Trace 和失败回放。
>

## 3. 简历与项目真实性

### Q9. 三个项目之间是什么关系？为什么会做这三个？

> 这三个项目不是三个互不相关的 Demo。AI 周报解决多源数据采集、统计和解释；CodeWiki 解决代码知识的结构化、检索和版本更新；Memory 解决 Agent 在长任务中的历史信息保留和上下文成本。
>
> 它们共同训练了我处理非结构化输入、建立中间表示、做检索和状态管理、控制模型边界以及设计评测闭环的能力。项目先后和并行阶段按公司内部记录回答，不根据代码日期推断时间。

### Q10. 简历写“独立负责”，具体独立到什么程度？

> 我会按阶段拆开，而不是把“独立负责”理解成一个人完成所有事情。我的直接责任是 **[按真实 RACI 填写需求、设计、核心实现、联调、测试或发布]**；产品、测试、运维和最终验收由 **[填写协作者和负责人]** 参与。
>
> 对我能用代码、评审记录或发布记录证明的部分，我可以讲输入、输出、失败模式和验证方式；没有证据的团队成果，我不会全部算到自己头上。

### Q11. 你三个项目中最有技术含量的是哪个？

> 如果看平台化难度，我会选 CodeWiki 或 Memory，但原因不是用了更多模型。CodeWiki 的难点是把多语言代码映射成稳定 IR，再维护图、向量、源码引用和 revision 一致性；Memory 的难点是把原始对话、结构化事实、场景和画像分层，并处理检索、冲突和上下文预算。

> 如果看业务稳定性，AI 周报的难点是让多源数据、状态和推送链路可靠，模型只负责可回溯的解释。具体选哪个要看岗位更重视数据平台、知识工程还是 Agent 运行时。

### Q13. 如果产品或业务方和你意见不一致，你怎么处理？

> 我会先确认双方争论的是目标、指标、约束还是实现方式。比如业务方希望模型直接回答“为什么指标下降”，我会先把问题拆成查数、口径、归因和下钻，确认当前数据是否具备因果证据。
>
> 然后给出最小可交付方案和风险边界：先交付可核对的指标和证据，再逐步增加解释能力。如果仍然无法达成一致，我会把选项、成本、风险和建议写清楚，请最终 Owner 决策，而不是把个人偏好包装成技术结论。

### Q14. 多个任务同时很急，你怎么排优先级？

> 我会按业务影响、线上风险、依赖关系、截止时间和可逆性排序。线上数据错误或权限问题优先于新功能；阻塞多个团队的公共依赖优先于单个局部优化；高风险且不可逆的发布需要先做验证和回滚方案。
>
> 我会把优先级和延期影响同步给相关负责人，不会默默同时承诺所有任务。必要时把工作拆成“先保证正确性和可用性的最小版本，再补体验和性能”。

### Q15. 你如何推进一个跨团队项目？

> 我会先确定业务 Owner、技术 Owner、输入数据 Owner、验收人和上线责任人，再把接口、口径、时间点和失败处理写成可确认的清单。对于数据项目，尤其要提前确认字段含义、时区、延迟、补数和权限。
>
> 推进过程中用里程碑和风险清单跟踪，阻塞超过约定时间就升级，不把问题留到上线前。验收不只看“接口能调用”，还要看数据质量、指标对账、失败重试和回滚。

### Q16. 你做过的一个错误或失败是什么？

> 我会讲一个真实且边界清楚的案例。比如在 CodeWiki 的增量设计中，如果只按变动函数更新，类属性或公共类型变化可能让旧向量继续被召回。这个问题说明文件级 Git diff 不是完整的语义影响分析。
>
> 正确的修正是按属性、包含类和反向依赖计算 Dirty Set，重建受影响 chunk 和向量，绑定新 revision，经过引用和问答回归后再原子切换。当前项目是否已经完成这套修正，我会明确说当前状态；如果只是复盘设计，就不会说成已上线能力。

### Q17. 你收到过什么负面反馈？后来怎么改？

> 二面暴露出我有时能讲出技术名词，但底层定义和工程闭环不够精确，例如 B+树叶子链、`volatile` 语义、类属性变化和 Memory 冲突定位。
>
> 我现在用“先定义，再讲步骤、状态、边界和验证”的方式回答。项目上也把 revision、source_ref、事实键、冲突状态和回归校验补进设计，而不是只描述检索或模型判断。

### Q18. 你如何证明简历上的指标？

> 我会先说明指标定义、基线、样本、时间窗口、实验变量和数据来源。比如 Memory 的 Token 降低是特定数据集和配置下的离线结果，不能说成所有线上请求平均下降；通过率是任务通过，不等于模型准确率。
>
> 如果某项信息只能从内部报告确认，我会给出报告或埋点口径；如果当前拿不到完整证据，就主动说明这是估算或待核验，不临场编造 QPS、用户数和 SLA。

## 4. 大数据平台与 Data Agent 场景题

### Q19. 你会怎样设计 Data Agent 的问数链路？

> 我会先把自然语言解析成带指标、维度、时间、过滤、粒度和权限的结构化意图。然后从版本化语义层获取指标定义、表字段、关联关系、血缘、数据更新时间和权限范围，再让模型生成候选 SQL。
>
> SQL 先经过 AST 白名单、只读权限、行列级权限、扫描量和超时限制，再执行并做结果行数、单位、时间口径和数值对账。最后模型只根据已验证结果生成解释，并返回指标定义、数据时间和来源。全链路保存 Trace，便于评测和回放。

### Q20. 语义层解决什么问题？

> 语义层不是简单把表结构塞进 Prompt，而是把指标、维度、口径、关联、权限、时间有效期、负责人和数据质量状态结构化。它解决的是“同一个业务词在不同表里含义不一样”“模型生成了能执行但口径错误的 SQL”这类问题。
>
> 指标和关系需要版本化，变更要有 Owner、审批、兼容策略和回归样本。模型可以提出查询，但不能成为业务口径的最终来源。

### Q21. NL2SQL 生成错误或越权怎么办？

> 模型输出先不执行。服务端校验语法树，只允许授权的 SELECT、表、字段和函数；使用只读账号或只读副本，设置超时、扫描量和结果行数限制，禁止 DDL、DML、多语句和危险函数。
>
> 字段权限、脱敏、租户和业务范围由服务端控制，不交给 Prompt。校验失败时返回可解释错误或让用户补充条件，不能让模型通过自由文本绕过安全规则。

### Q22. 如何处理数据漂移、数据迟到和口径不一致？

> 我会把质量分为结构、时效、完整性、唯一性、分布和业务对账。数据漂移先确认是源字段变化、分布变化、时间窗口错误还是业务规则变化，再由 DQC、Schema Registry、血缘和告警定位影响范围。
>
> 迟到数据按事件时间和处理时间区分，允许窗口内补数，窗口外走修订或回溯任务；重要指标要保留版本和修订记录。口径冲突不能靠模型猜，应该由指标 Owner 确认并在语义层版本化。

### Q23. Spark 和 Flink 怎么选？

> Spark 更适合大规模离线批处理、SQL 和成熟数仓作业；Flink 更适合持续流处理、事件时间、有状态计算和低延迟窗口。实际选择还要看数据时效、状态规模、回放、运维成本和团队生态。
>
> 我没有把没有直接投产的组件说成自己的生产经验。如果是迁移设计，我会先明确延迟、吞吐、状态、容错和补数要求，再选择组件，而不是简单说“Flink 一定更快”。

### Q24. 数据量增长 100 倍，你先优化哪里？

> 先测量瓶颈，不直接加机器。依次看数据源吞吐、分区设计、Shuffle、数据倾斜、小文件、序列化、存储布局、下游扫描范围和任务并发。
>
> 优先做能减少数据量和重复计算的改动，例如合理分区、列裁剪、预聚合、热点拆分、合并小文件和缓存复用；同时保留回放和对账能力，避免为了速度牺牲正确性。

### Q25. Kafka 多分区怎样保证消息顺序？

> Kafka 只能保证单分区内的顺序。要保证同一个会话、订单或任务的消息顺序，就用稳定业务键做分区键，让同一键进入同一分区；生产端设置幂等，消费端按 offset 和业务序列号处理。
>
> 如果需要跨分区全局顺序，通常要重新评估需求和吞吐成本，不能靠消费者线程睡眠实现。数据库落库还要用幂等键、版本号或条件更新防止重复和乱序覆盖。

### Q26. 分库分表时不同地区数据量不均怎么办？

> 先确认查询和写入的业务键，再评估按地区、用户、订单或时间分片。单纯按地区可能造成热点和容量不均，可以采用复合分片键、热点地区二次拆分、逻辑路由和扩容预案。
>
> 路由规则要版本化，迁移要支持双读校验、分批搬迁和回滚；不能只改 hash 算法后让历史数据全部失联。跨分片查询要限制范围并明确一致性和分页代价。

### Q27. 如何设计数据平台的评测？

> 我会分三层。结果层看 SQL 正确性、数值一致性、指标口径、约束满足和用户任务成功；过程层看检索召回、工具选择、参数、错误恢复、越权和无依据结论；系统层看 P50/P95 延迟、Token、成本、超时、失败率和资源使用。
>
> 样本集要版本化，固定样本使用确定性 grader，主观解释使用 rubric 和多人评审。每次错误都保留 Trace，定位是语义层、检索、规划、工具执行还是生成，不能只报一个综合准确率。

### Q28. 你会监控什么？

> 数据链路看新鲜度、完整性、重复率、迟到率、DQC 失败、补数积压和对账差异；计算平台看任务成功率、P95、Shuffle、倾斜、资源和小文件；Agent 链路看语义解析、检索、SQL 校验、执行、模型延迟、Token、成本和人工纠错。
>
> 每条链路都要有 Trace ID、业务日期、数据版本和失败阶段。告警要能区分可重试、需要补数和需要人工确认的情况，不能只记录一条“任务失败”。

### Q29. 你的三个项目哪些能力能迁移到数据平台？

> AI 周报可以迁移多源采集、窗口、完整性 Gate、模块状态、重试、补数和结果对账；CodeWiki 可以迁移结构化 IR、版本化索引、依赖影响分析和引用追踪；Memory 可以迁移事件追加、异步抽取、幂等 Capture、检索预算、Trace 和失败恢复。
>
> 不能直接迁移的是具体 Hadoop/Spark 集群经验、团队内部数据规模和生产 SLA。这部分我会通过真实任务补齐，而不是把项目中的本地组件等同于企业级平台。

## 5. 三个项目高概率深挖

### Q30. AI 周报系统的核心价值是什么？为什么需要 LLM？

> 系统先解决的是多源数据采集、完整性检查、确定性指标计算和周期性发送，核心价值不是“调用了大模型”。LLM 的增量价值是基于已经验证的指标做异常解释、趋势归纳和文字组织，减少人工逐模块阅读和撰写。
>
> 如果只需要数字表格，脚本和模板就够；如果使用 LLM，数字、阈值和证据仍由程序控制，模型不能重新计算事实。

### Q31. 周报状态成功但消息发送失败怎么办？

> 分析完成和发送完成必须是两个状态，不能分析成功就把整条链路标记为成功。更可靠的做法是在同一事务里写入 `REPORT_READY` outbox 事件，独立 sender 按 `report_id` 幂等发送，发送成功后更新 `SEND_STATUS`。
>
> 对 429、超时和 5xx 做指数退避加 jitter；连续失败进入告警或人工补发。当前材料如果没有完整 outbox 实现，我会明确说这是针对现有状态缺口的改进设计。

### Q32. CodeWiki 为什么需要 GraphRAG？

> 普通向量 RAG 更容易召回语义相似但互相孤立的代码片段，而代码问题经常需要回答谁调用谁、接口落到哪个实现、修改一个类影响哪些方法。图保存确定的调用、导入、继承和定义关系，关键词/向量补充标识符和自然语言召回。
>
> 查询时先按仓库、revision 和权限过滤，再做候选召回、图扩展和上下文预算，最后把带源码引用的 context pack 给模型。是否比普通 RAG 更好要用同一数据集上的正确率、引用有效率、耗时和 Token 做对照，不能只用“用了图”证明效果。

### Q33. CodeWiki 的多语言 DSL 如何定义？

> 我会把它称为语言无关的代码 IR。节点至少包含 `repo_id、revision、symbol_id、kind、qualified_name、signature、file、start_line/end_line、parent_id`；边包含 `source_id、target_id、relation_type、source_ref、revision、confidence`。
>
> tree-sitter 和规则/类型分析负责从各语言 AST 中抽取这些确定事实，LLM 只根据 IR、调用链和源码片段生成解释。无法确认的动态关系标低置信度，不能让模型猜一个确定调用关系。

### Q34. 类属性新增或类型变化，向量怎样更新？

> Git diff 只是文件级线索。属性变化后先定位属性、包含类和引用它的符号，重新计算类摘要和内容哈希；类级 chunk、引用该属性的函数级 chunk、文档和反向依赖一起加入 Dirty Set。
>
> 新向量绑定新的 `revision` 和 `content_hash`，在 staging namespace 写入，经过引用、数量和代表性问答回归后原子切换；旧向量先标记不可检索，保留一段时间后清理。当前项目如果没有完整实现这条链路，要明确说“这是我对当前缺口的修正版设计”。

### Q35. Memory 是什么形态？是不是共享服务？

> 当前更准确的说法是本地、单用户的 Memory 组件/服务，宿主通过 Hook 在模型调用前 Recall、回合结束后 Capture，数据保存在用户本机。它不是已经完成的共享多租户平台。
>
> 如果未来服务化，需要增加用户、项目、Agent、权限 scope、幂等键、租约、审计、删除传播和故障降级。接口兼容不等于已经完成云化。

### Q36. Memory 四层何时写入？

> L0 先追加保存不可变原始对话和事件引用；L1 在用户明确要求记住、会话边界、重要事实检测或异步保底任务触发时抽取结构化事实；L2 在多个事实形成同一场景或任务结束时聚合；L3 只有稳定、可复用、无冲突并达到置信度的偏好才晋升。
>
> 当前实现如果使用“每五条消息加 5/15 分钟和 1 小时保底”，我会说明这是成本控制策略，不把固定轮数说成通用记忆理论。

### Q37. Memory 新旧事实冲突怎样定位？

> 先把事实规范化为 `subject、attribute、value、scope、valid_time、source_ref、confidence、status`，用实体、属性和 scope 找候选；BM25 或向量只负责补充召回，不能独立证明冲突。
>
> 明确的新值替代旧值时标记 `supersedes`，互补信息做 merge，时间和作用域不清时保留 conflict 并追问。LLM 只能提出动作，服务端校验版本、来源、权限和安全规则后落库，旧事实保留历史和引用。

### Q38. 你的 Memory 指标是否能代表线上效果？

> 不能直接代表。WideSearch、PersonaMem 是特定数据集、模型、Host、Prompt 和配置下的离线结果，能说明在该实验条件下的变化，不能外推为所有线上请求的平均收益。
>
> 严格复现时要固定 Baseline、模型、工具、数据集、随机性和运行次数，同时记录 Token、通过率、方差、成本和失败类型。上线后还要看召回准确性、错误记忆、删除完整性和 P95 延迟。

### Q39. 如果不用你的 Memory，直接让 Agent 自己搜索可以吗？

> 简单的一次性任务可以，不能为了证明 Memory 有价值而否认这一点。Memory 的价值在于跨会话保留稳定事实、在多轮任务中减少重复确认、对上下文外置结果提供可追溯引用，以及按权限和 scope 管理历史信息。
>
> 是否值得建设要和基线比较：任务成功率、Token、延迟、错误记忆率、删除完整性和维护成本。如果普通 Agent 已经能稳定完成，就应该缩小 Memory 的范围，而不是继续堆层数。

### Q40. 如果你现在重做三个项目，最先改什么？

> 周报先把分析状态和发送状态拆开，使用 outbox、幂等 report_id 和可重试状态；CodeWiki 先补 revision-aware index、Dirty Set、属性/重命名影响分析和质量回归；Memory 先补事实 Schema、冲突状态、证据引用、异步队列和删除传播。
>
> 我不会优先继续增加模型或语言支持，因为当前更大的风险是正确性、版本一致性、可观测性和评测不足。

### Q41. 你使用了多少 AI 生成代码？

> 我会按真实变更回答：AI 可能帮助我生成样板、测试草稿或局部实现，但需求拆解、架构取舍、风险判断、代码修改、测试和发布责任仍由我或对应 Owner 承担。具体比例如果没有可靠统计，我不会报一个看起来漂亮的数字。
>
> 我可以拿一项真实变更说明 AI 生成了什么、我改了什么、执行了哪些测试、谁 Review 和谁发布。不能因为仓库里有生成代码就把全部责任归给 AI，也不能把团队代码全部算成自己写的。

### Q42. 你的项目中最需要承认的边界是什么？

> 三个项目都不是完整的企业级平台。周报的外部发送一致性、CodeWiki 的动态语言和全量依赖影响分析、Memory 的多租户和事实冲突治理，都存在需要继续建设的边界。
>
> 但我能把边界讲清楚，并给出可验证的演进路径：版本化、幂等、状态机、权限、评测、Trace、回滚和失败恢复。相比把 Demo 说成平台，这样更接近真实工程责任。

## 7. 快速技术复核题

这些题来自货拉拉大数据平台和后端公开面经，以及你的二面实际题。每题至少练成 30-60 秒答案。

### Q51. B+树为什么适合数据库索引？

> B+树是多路平衡树，内部节点保存分隔键和子指针，真正的记录或记录指针集中在同层叶子，叶子按序连接。高扇出降低树高和磁盘随机 IO，叶子链支持范围查询；分裂、合并和父键调整是更新成本。

### Q52. `volatile`、锁和原子类怎么选？

> `volatile` 主要保证可见性和有序性，不保证 `i++` 这种复合操作的原子性；复合不变量用 `synchronized` 或 `ReentrantLock`；简单单变量 CAS 更新可用原子类。选型还要说明锁范围、超时、中断、死锁和性能边界。

### Q53. 线程池的执行顺序是什么？

> 线程数未达到 core 时创建核心线程；核心线程满后入队；队列满且未达到 maximum 时创建非核心线程；队列和线程都满时执行拒绝策略。生产环境要有界队列、线程命名、异常处理、监控、优雅关闭和合理拒绝策略。

### Q54. 线程越多越好吗？

> 不是。CPU 密集任务线程过多会增加上下文切换，IO 密集任务可以适度多一些，但仍受连接数、内存、下游容量和队列限制。线程数要通过任务性质、等待比例、P95 延迟和资源监控调整，而不是套一个固定公式。

### Q55. 如何解决 Spark 数据倾斜？

> 先定位倾斜 key、分区大小和 Shuffle 阶段，再根据原因选择方式：热点 key 加盐后局部聚合再去盐、广播小表、预聚合、调整分区和拆分热点；同时要考虑结果正确性和额外网络成本。没有监控数据时不直接承诺某个优化一定有效。

### Q56. 如何保证数据处理幂等？

> 先定义业务唯一键和输入版本，再用唯一约束、条件更新或 upsert 防止重复写；外部副作用用 outbox、幂等 request_id 和发送状态隔离。重试只能安全重试可恢复错误，不能把“重复执行没有报错”当成幂等证明。

### Q57. 100 万个数求最大 100 和最小 100 怎么做？

> 维护一个大小为 100 的最小堆保存最大 100，维护一个大小为 100 的最大堆保存最小 100；遍历每个数，堆未满就加入，满了再和堆顶比较并替换。时间复杂度 O(n log 100)，额外空间 O(100)，不需要全部排序。

### Q58. Redis 热 Key 怎么处理？

> 先确认访问集中是正常热点还是异常流量，再用本地缓存、热点副本、读扩散、分片 Key、限流和预热缓解；同时设置过期抖动避免雪崩。不能只把一个 Key 复制到多个节点而不考虑一致性和更新成本。

### Q59. 数据库联合索引怎样判断是否生效？

> 先看索引列顺序、查询条件、排序、范围条件和数据分布，使用 `EXPLAIN` 验证。最左匹配不是“只要出现第一列就一定高效”；遇到范围、函数、隐式类型转换、低选择性或优化器成本判断，都可能导致后续列利用不足或选择其他计划。

### Q60. 进程、线程和协程怎么区分？

> 进程提供资源隔离，线程是进程内的调度执行单位，协程通常是用户态更轻量的执行单元，由运行时调度。协程切换成本低，但阻塞调用、共享状态和调度模型仍需处理；轻量不等于无限并发。
