## 二、项目一：AI 周报系统

### Q4. 一周审了一人天，这个一人天怎么审出来的？怎么计算？

**参考答案**：
> 这里的一人天不是根据 Git 提交、代码量或任务复杂度推算员工工时，那样既不准确，也容易变成员工绩效判断。它表示的是**生成一轮网联运营保障周报，改造前后总人工投入的差值**。
>
> 改造前，从多个运营系统取数、清洗、核对、分析到组装，一轮总人工投入大约是 8 到 10 小时；改造后自动链路大约 20 分钟完成，人工主要做异常检查和最终确认。按简历现有的保守估算口径，把这 20 分钟也从原人工投入里扣除，单周净节省约 7.7 到 9.7 小时；按一年约 50 个工作周、每天 8 小时折算，大约是 48 到 60 人天，所以取接近下限的整数，写成“约 50 人天”。
>
> 这个数字是工时估算，不是财务审计结果，也不包含一次性研发成本。面试前我还要核实 20 分钟究竟是系统周转时间，还是仍需人工参与的时间；如果它只是机器运行时间，就必须用实际人工复核时长重新计算。我也会把 8 到 10 小时的内部记录、异常补数和维护成本一起说清；实际记录不支持时，我就不用这个数字。

### Q5. 这个东西不用 LLM 做也可以吗？听起来就是个 workflow。

**参考答案**（诚实承认边界 + 讲 LLM 的真实价值）：
> 纯数据采集、确定性统计和固定模板确实可以做出基础周报，所以我不会为了强调 AI 而说大模型不可替代。当前系统里的 SQL 是预先写好的，数据完整性和数字都由程序判断；LLM 只接收已经整理好的模块结果，做异常解释、趋势归纳和文字组织。
>
> 它的现实价值是减少人工逐模块阅读数据和撰写说明的时间，让每周变化较大的异常内容不必全靠固定规则穷举。最终仍按固定结构输出表格加文本，并通过内部消息接口推送。
>
> 当前没有自然语言追问 RAG，也没有让模型自由生成 SQL。以后如果业务确实需要交互式查数，我会把它作为下一版单独设计，并补只读权限、Schema 范围、SQL AST 校验、超时和审计；不会反过来把未来方案说成现在已经有。

### Q9. ⚠️ 自研多语言 AST 解析引擎，本质上还是理解代码模块，有没有对标过 Codex / Cursor？核心竞争力在哪？

> 这是 CodeWiki 的**生死线问题**，面试官在压力测试。策略：**诚实承认通用场景打不过 + 给出细分场景的差异化 + 不假装全面超越**。

**参考答案**：
> 对标过。诚实说：**通用场景打不过 Codex / Cursor**——它们的 codebase indexing 已经很强，开箱即用、体验打磨好，我自研不可能全面超越。
>
> 但在**特定细分场景**有差异化，这是核心竞争力：

| 维度 | Codex / Cursor 原生 | 我的 CodeWiki |
|------|---------------------|---------------|
| 相似度检索 | 具体机制不猜，按实际任务测 | FTS + 可选 Vector + 图扩展 |
| **跨模块依赖召回** | 可通过原生搜索、索引或 Agent 探索 | **确定性结构边优先扩展，跨文件边带启发式和置信度** |
| 大仓库成本 | 可能有宿主索引或缓存，不能一概说每次重扫 | 有离线建图成本，在线可复用 |
| 工作区新鲜度 | 取决于宿主版本和索引策略 | 有 Git Diff/Hash 增量，但当前没有统一不可变 Revision |
| 通用易用性 | 极强（开箱即用） | 需要建图、维护和陈旧治理 |

> **核心论点**：代码里有一部分结构关系可以由解析器确定性提取，比如定义、包含和显式导入；跨文件 `calls/references` 仍可能受动态分派、重名和缺失类型信息影响，所以我用 confidence 和 provenance 标出启发式边。相比让模型每次从零猜依赖，这样更容易复用、审计和定位，但我不会承诺绝不漏边。
>
> 诚实定位：**不是替代 Codex / Cursor，而是在反复的跨模块问题、可追溯引用和团队知识复用场景提供可选增强**。小仓库、一次性任务或本地变化特别快的分支，原生 Agent 往往更合适。是否值得接入要比较原生 Agent、Repo Map/Skill 和 CodeWiki 三组的任务结果与总成本，不能只靠定性矩阵证明。

## 四、项目三：Agent 长期记忆 + 上下文压缩系统

### Q10. 做这个事情的背景是什么？

**参考答案**：
> 两个痛点驱动：
> 1. **agent 跨会话失忆**：每次新会话 agent 不记得用户历史，体验割裂，无法做长期个性化。
> 2. **长对话 token 爆炸**：业务场景里多轮对话很容易撑爆模型窗口，不压缩没法持续工作。
>
> 所以我把系统拆成两条链路。长期记忆里，L0 保存原始对话证据，L1 抽取 `persona / episodic / instruction` 三类原子记忆，L2 把相关记忆组织成场景，L3 生成长期 Persona；它不是“会话摘要逐层晋升”。短期上下文链路则把大 Tool Result 外移到 refs，在 Prompt 里保留摘要和可回查引用。前者解决跨会话记忆，后者解决单次长任务的上下文膨胀。

### Q11. 系统已投产覆盖多个业务渠道，是以什么形式插入到其他业务渠道的？是塞到 Copilot 里去吗？

**参考答案**：
> 先纠正两个前提。第一，“已投产覆盖多个业务渠道”必须由真实入口、用户和部署记录证明；没有证据时只说具备多 Host 接入能力。第二，要把系统支持的形态和本次实际部署分开。
>
> 按当前现场口径，主部署是**本地插件 + SQLite**，不是塞进 Copilot 黑盒，也不是面向所有渠道的集中式记忆 SaaS。插件在模型调用前 Recall，一轮提交后 Capture；宿主仍负责 Agent Loop 和工具执行。`TdaiCore` 设计上还可通过 Hook 或 HTTP Gateway/sidecar 接其他宿主，但这些属于适配能力，某个业务是否真的采用必须逐项举证。
>
> `user_id` 或 Session 字段只能做数据关联，不能自动证明企业级多租户隔离。真实生产还需要可信身份、强制 Scope、授权、审计和删除传播，不能因为字段存在就说渠道之间已经安全隔离。

### Q12. 做这个时有没有参考业界方案？有没有看 ClaudeCode / 淘宝编码的源码？跟 ClaudeCode 比有哪些亮点？

> ⚠️ **现场风险**：你说没看过淘宝编码源码，面试官追问"后续对比过吗"。**诚实承认没看全是对的，但要有自己的亮点论点**，不能只说"没看过"。

**参考答案**：
> 参考过 Mem0 / Letta 这类开源记忆方案的**设计思路**（看过文档和部分代码，没全读）。**ClaudeCode / 淘宝编码的源码我没看全**，诚实承认——不是不看，是优先级排在了"把自己的系统跑通验证"上，对标做得不够细，这是我下来要补的。
>
> 我能确认的当前特点主要有三点：
> 1. **证据入口**：L0 保留原始消息，L1 记录 `source_message_ids`，需要时可以回到来源消息核对。但这个字段还没有逐条做“ID 一定存在、内容一定被原文蕴含”的硬校验，所以我不会把它说成严格 span 溯源。
> 2. **新旧记忆处理**：新 L1 会先召回相似旧记录，再由 LLM 在 `store / skip / update / merge` 四个动作里判断。它能做语义去重和记录更新，但当前没有实体属性状态机、事实置信度公式、低置信候选区，也没有“出现多次就自动晋升 L3”。
> 3. **长期记忆和短期卸载分开**：L0-L3 管跨会话记忆；Context Offload 把 Tool Result 原文放到 refs，只在当前上下文保留摘要和引用。当前没有按时间衰减自动改权重，也不能把这条链说成“近期原文、中期摘要、远期蒸馏”的时间分层状态机。
>
> 下一版我会先补来源 ID 存在性和 Claim-Evidence 蕴含校验，再单独设计 evidence confidence、实体属性的时间与作用域、冲突版本和用户纠错事件。至于这些能力是不是优于 ClaudeCode，必须比较明确版本和公开实现，没看完整源码时我不会替对方下结论。

## 五、软素质题

### Q13. 收到多个需求都紧急、人力不够、有 DELAY 风险，怎么处理？

**参考答案**：
> 1. **不闷头扛**：第一时间向上 + 向需求方同步风险，**别等到 deadline 才说做不到**——逾期前预警是基本职业素养。
> 2. **重新排序**：拉需求方对齐"紧急"的真实定义——是真紧急还是"想要快"。按 **业务影响 × 时间紧迫度** 重新排优先级，而不是谁催得凶谁先。
> 3. **砍范围而非赶工**：与其压缩所有需求的质量（埋雷），不如协商砍掉非核心范围先上 MVP，或分期交付。
> 4. **争取资源**：若确实是资源问题，带着排好的优先级和影响评估去争取加人或调期——**带方案去谈，不是只带问题**。
>
> 核心：**透明同步 + 重新对齐优先级 + 砍范围而非压质量**。

### Q14. 和同事一起开发，技术文档分歧大，怎么推进达成共识、落地？

**参考答案**：
> 1. **先把分歧点列清楚**：不是各自讲完整方案，而是先对齐"我们到底在哪几点上不一致"——很多分歧其实是误解而非真分歧。
> 2. **用事实而非立场讨论**：每方给出方案的依据（性能要求 / 可维护性 / 成本 / 团队现状），用约束条件说话，不拼嗓门。
> 3. **找共同目标**：回到"这个系统要解决什么问题"，用目标倒推方案，容易达成一致——分歧往往因为各自盯着局部优化。
> 4. **设决策机制**：实在谈不拢，明确决策权归属（**谁 owner 谁拍板**），并记录 dissenting opinion，事后可复盘。
>
> 原则：**不追求全员认同，追求有依据的决策 + 记录分歧**。民主讨论，集中决策。

### Q15. AI agent 时代，程序员的 coding 能力还是核心竞争力吗？

**参考答案**（开放题，给有判断的答案）：
> coding 能力的**形式**在变，但**核心价值**没变。
>
> AI 能写代码，但程序员的核心竞争力从来不是"打字打代码"，而是**把模糊需求转化为确定系统**的能力——拆解问题、定义边界、设计架构、权衡取舍、保证可靠性。这些 AI 替代不了。
>
> 变化的是：**纯实现型 coding 的价值在下降，系统设计 + 工程判断 + 把 AI 用好的能力在上升**。所以核心竞争力的内涵在扩大，不是消失。**能把 AI 当杠杆放大自己产出的程序员，会比不用 AI 的更有竞争力。**
>
> 我自己的体感：vibe coding 让"能写代码"贬值，让"能判断代码好坏、能定义边界"升值。

## 七、复盘：这场的得失与风险

### 风险点（下来要补）：
1. **对标竞品拿不出量化数据**——面试官反复追问 Codex / Cursor / ClaudeCode 对标，只讲定性差异化不能证明今天仍有净收益。下来要用同一批任务比较原生 Agent、Agent + Repo Map/Skill、Agent + CodeWiki，至少统计任务成功率、跨模块召回、引用正确性、Token、索引时间和陈旧率。不能只比较“无图谱 RAG vs GraphRAG”，否则避开了真正的最强替代方案。
2. **ClaudeCode / 淘宝编码源码没看**——诚实承认是对的，但面试官明显在意。下来至少把 ClaudeCode 的公开设计文档 / 架构文章读一遍，能讲出"ClaudeCode 怎么做的、我的差异在哪"，比"没看过"强。
3. **"在用吗"答得虚**——如果项目真没继续用，诚实说"验证完核心能力后转入下个阶段"比硬撑"在用"强。面试官能听出来虚实。

### 得分点（继续巩固）：
- 周报系统"数字与叙述分离"原则讲得清楚，LLM 边界划得明白。
- CodeWiki 对标 Cursor 的防御矩阵有理有据（诚实承认通用打不过 + 细分差异化）。
- 软素质三题（多需求 / 文档分歧 / coding 价值）答得有方法论、有判断。
- 记忆系统亮点（幻觉治理 / 分层生命周期）有深度。

### 下来必做：
1. **建 CodeWiki 的 benchmark**——量化原生 Agent、Repo Map/Skill 与 CodeWiki 在跨模块任务上的净收益，并加入大分支未提交改动和索引过期用例。
2. **读 ClaudeCode / 淘宝编码的公开设计**——能讲对标差异，不再只能说"没看过"。
3. **准备项目"使用情况"的脱敏数据**——覆盖几个场景、谁在用、用了多久、有没有线上故障，被问时不卡壳。
4. **卓誉给 1000 刀/月 Claude Code 额度**——说明公司对 AI 工具支持力度大、是真在用 AI 做事，进去大概率要深度用 Claude Code，提前熟悉。
