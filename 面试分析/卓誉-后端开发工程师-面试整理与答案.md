## 二、项目一：AI 周报系统

### Q4. 一周审了一人天，这个一人天怎么审出来的？怎么计算？

**参考答案**：
> 工时核算是关键设计：**不让 LLM 凭空"算"工时**——工时由**确定性逻辑**得出：
> - 从多源数据（Git 提交记录、任务关联、代码量、CI 记录）按**预设规则**折算工时。
> - 比如：有提交且有任务关联的算有效工时，按提交时间跨度 + 代码改动量 + 任务复杂度系数折算。
> - LLM 只把**算好的工时数据**组织进周报叙述，不参与计算。
>
> 这里的边界是：**算数用规则，表达用 LLM**——这正是周报系统的核心设计原则。让 LLM 算数是幻觉重灾区，工时数字必须确定性可追溯。

### Q5. 这个东西不用 LLM 做也可以吗？听起来就是个 workflow。

**参考答案**（诚实承认边界 + 讲 LLM 的真实价值）：
> 纯数据采集 + 模板填充确实能做出基础周报，**大模型不是必需的**。诚实说：**只定时推数字周报，确实不需要 LLM**。
>
> LLM 的价值在两点：
> 1. **自然语言交互**：周报推出来后，用户能直接追问（"这周 A 模块提交为什么少了"），不用翻系统查。
> 2. **数据解读**：把数字组织成有重点的叙述（亮点 / 异常 / 趋势），降低阅读成本，而不是干巴巴一串数。
>
> 但底线很清楚：**数字必须准（规则算），表达要自然（LLM 生成）**。LLM 只在交互和解读层有价值，不碰统计。

### Q9. ⚠️ 自研多语言 AST 解析引擎，本质上还是理解代码模块，有没有对标过 Codex / Cursor？核心竞争力在哪？

> 这是 CodeWiki 的**生死线问题**，面试官在压力测试。策略：**诚实承认通用场景打不过 + 给出细分场景的差异化 + 不假装全面超越**。

**参考答案**：
> 对标过。诚实说：**通用场景打不过 Codex / Cursor**——它们的 codebase indexing 已经很强，开箱即用、体验打磨好，我自研不可能全面超越。
>
> 但在**特定细分场景**有差异化，这是核心竞争力：

| 维度 | Codex / Cursor 原生 | 我的 CodeWiki |
|------|---------------------|---------------|
| 相似度检索 | 强 | 持平 |
| **跨模块依赖召回** | 靠模型自己摸索，可能漏 | **图结构精确扩展，不漏调用方** |
| 大仓库成本 | 每次重扫，贵 | 离线建图，在线检索，省 token |
| 增量更新 | 弱（markdown 易过期） | git diff 局部更新 |
| 通用易用性 | 极强（开箱即用） | 需要建图，有门槛 |

> **核心论点**：代码的调用关系、依赖关系是**确定性的**——这层用 AST 静态解析建图，比让模型"自己读仓库猜依赖"更准、更省、更可解释。Codex / Cursor 让模型自己摸索跨模块依赖，可能漏；我用图结构精确扩展，不漏。
>
> 诚实定位：**不是替代 Codex / Cursor，是在"超大仓库 + 跨模块精确依赖 + 企业内定制"这个细分场景的补强**。两者分层互补，不是替代关系。

## 四、项目三：Agent 长期记忆 + 上下文压缩系统

### Q10. 做这个事情的背景是什么？

**参考答案**：
> 两个痛点驱动：
> 1. **agent 跨会话失忆**：每次新会话 agent 不记得用户历史，体验割裂，无法做长期个性化。
> 2. **长对话 token 爆炸**：业务场景里多轮对话很容易撑爆模型窗口，不压缩没法持续工作。
>
> 所以做了一套**单用户多会话的分层记忆 + 上下文压缩系统**：L0 原始对话 → L1 会话摘要 → L2 结构化事实 → L3 长期画像，逐层蒸馏压缩，跨会话召回。

### Q11. 系统已投产覆盖多个业务渠道，是以什么形式插入到其他业务渠道的？是塞到 Copilot 里去吗？

**参考答案**：
> 是**作为独立模块接入 agent 链路**，不是塞进 Copilot 黑盒里。形态上：
> - 记忆层和压缩层是独立服务，对外提供记忆存取 / 召回 / 压缩的接口。
> - 各业务渠道的 agent 调用这套接口，按 user_id 隔离记忆。
> - [如果接了 Copilot 类工具：部分场景嵌入了 Copilot 类工具的上下文管理，但核心记忆治理是独立模块，不是把逻辑写死在 Copilot 里]。
>
> 为什么独立：runtime 本身的调度 / 工具调用 / 流式输出造轮子性价比低，我们的差异化价值在**记忆治理和上下文管理**，集中精力做深，不重复造 runtime。

### Q12. 做这个时有没有参考业界方案？有没有看 CoCo / 淘宝编码的源码？跟 CoCo 比有哪些亮点？

> ⚠️ **现场风险**：你说没看过淘宝编码源码，面试官追问"后续对比过吗"。**诚实承认没看全是对的，但要有自己的亮点论点**，不能只说"没看过"。

**参考答案**：
> 参考过 Mem0 / Letta 这类开源记忆方案的**设计思路**（看过文档和部分代码，没全读）。**CoCo / 淘宝编码的源码我没看全**，诚实承认——不是不看，是优先级排在了"把自己的系统跑通验证"上，对标做得不够细，这是我下来要补的。
>
> 但从公开信息和我的实践看，我们设计的亮点方向：
> 1. **幻觉治理**：记忆系统最大的坑是"一次幻觉被固化成长期错误事实，后面反复召回放大"。我们做了 **span 溯源（抽取事实必须给原文出处）+ 置信度晋升（低置信度不直接进 L3，多次确认才晋升）+ 冲突检测（同属性值变化时可变覆盖 / 不可变降置信度）**。这层多数开源方案没做深。
> 2. **分层 + 生命周期**：不只存取，还管遗忘 / 过期 / 冲突——时效衰减降权归档、L0 冷归档、被覆盖旧值软删可溯源。
> 3. **上下文压缩的业务感知**：不是黑盒截断，而是近期原样保留 / 中期摘要 / 远期蒸馏，按时间衰减决定压缩力度。
>
> 诚实补充：**没看过 CoCo 源码是我的短板，不硬编亮点**。如果有对标数据我会更稳，这是我要补的功课。

## 五、软素质题

### Q13. 收到多个需求都紧急、人力不够、有 DELAY 风险，怎么处理？

**参考答案**：
> 1. **不闷头扛**：第一时间向上 + 向需求方同步风险，**别等到 deadline 才说做不到**——逾期前预警是基本职业素养。
> 2. **重新排序**：拉需求方对齐"紧急"的真实定义——是真紧急还是"想要快"。按 **业务影响 × 时间紧迫度** 重新排优先级，而不是谁催得凶谁先。
> 3. **砍范围而非赶工**：与其压缩所有需求的质量（埋雷），不如协商砍掉非核心范围先上 MVP，或分期交付。
> 4. **争取资源**：若确实是资源问题，带着排好的优先级和影响评估去争取加人或调期——**带方案去谈，不是只带问题**。
>
> 核心：**透明同步 + 重新对齐优先级 + 砍范围而非压质量**。

### Q14. 和同事一起开发，技术文档分歧大，怎么推进达成共识、落地？

**参考答案**：
> 1. **先把分歧点列清楚**：不是各自讲完整方案，而是先对齐"我们到底在哪几点上不一致"——很多分歧其实是误解而非真分歧。
> 2. **用事实而非立场讨论**：每方给出方案的依据（性能要求 / 可维护性 / 成本 / 团队现状），用约束条件说话，不拼嗓门。
> 3. **找共同目标**：回到"这个系统要解决什么问题"，用目标倒推方案，容易达成一致——分歧往往因为各自盯着局部优化。
> 4. **设决策机制**：实在谈不拢，明确决策权归属（**谁 owner 谁拍板**），并记录 dissenting opinion，事后可复盘。
>
> 原则：**不追求全员认同，追求有依据的决策 + 记录分歧**。民主讨论，集中决策。

### Q15. AI agent 时代，程序员的 coding 能力还是核心竞争力吗？

**参考答案**（开放题，给有判断的答案）：
> coding 能力的**形式**在变，但**核心价值**没变。
>
> AI 能写代码，但程序员的核心竞争力从来不是"打字打代码"，而是**把模糊需求转化为确定系统**的能力——拆解问题、定义边界、设计架构、权衡取舍、保证可靠性。这些 AI 替代不了。
>
> 变化的是：**纯实现型 coding 的价值在下降，系统设计 + 工程判断 + 把 AI 用好的能力在上升**。所以核心竞争力的内涵在扩大，不是消失。**能把 AI 当杠杆放大自己产出的程序员，会比不用 AI 的更有竞争力。**
>
> 我自己的体感：vibe coding 让"能写代码"贬值，让"能判断代码好坏、能定义边界"升值。

## 七、复盘：这场的得失与风险

### 风险点（下来要补）：
1. **对标竞品拿不出量化数据**——面试官反复追问 Codex / Cursor / CoCo 对标，你只能讲定性差异化，没有"召回率提升 X%""跨模块任务完整度 X%"这类数据。**这是最致命的短板**。下来必须建一个 benchmark：同一批跨模块任务，对比"无图谱 RAG"vs"GraphRAG"，拿召回完整度 / 修改正确率的数据。即使数据不完美，有数比没数强太多。
2. **CoCo / 淘宝编码源码没看**——诚实承认是对的，但面试官明显在意。下来至少把 CoCo 的公开设计文档 / 架构文章读一遍，能讲出"CoCo 怎么做的、我的差异在哪"，比"没看过"强。
3. **"在用吗"答得虚**——如果项目真没继续用，诚实说"验证完核心能力后转入下个阶段"比硬撑"在用"强。面试官能听出来虚实。

### 得分点（继续巩固）：
- 周报系统"数字与叙述分离"原则讲得清楚，LLM 边界划得明白。
- CodeWiki 对标 Cursor 的防御矩阵有理有据（诚实承认通用打不过 + 细分差异化）。
- 软素质三题（多需求 / 文档分歧 / coding 价值）答得有方法论、有判断。
- 记忆系统亮点（幻觉治理 / 分层生命周期）有深度。

### 下来必做：
1. **建 CodeWiki 的 benchmark**——量化"GraphRAG vs 普通 RAG"在跨模块任务上的差异，哪怕小规模。
2. **读 CoCo / 淘宝编码的公开设计**——能讲对标差异，不再只能说"没看过"。
3. **准备项目"使用情况"的脱敏数据**——覆盖几个场景、谁在用、用了多久、有没有线上故障，被问时不卡壳。
4. **卓誉给 1000 刀/月 Claude Code 额度**——说明公司对 AI 工具支持力度大、是真在用 AI 做事，进去大概率要深度用 Claude Code，提前熟悉。
