# 三个项目与全部真实面试：问题、正确答案和来源映射

> 整理范围：`面试分析/` 下现有 13 场真实面试复盘。
>
> 使用方法：先在第二至第八节复习统一答案，再到第九节按公司核对现场题号。相同问题只维护一份答案，避免不同复盘之间出现口径冲突。
>
> 收录规则：只把复盘中明确记录的提问、连续追问和面试官挑战算作现场题；“可能追问”“下一轮建议题”不冒充现场原题。

## 0. 使用规则与事实边界

### 0.1 三种回答标签

| 标签 | 含义 | 面试时怎么说 |
|---|---|---|
| **当前实现** | 能从项目材料、源码或真实复盘确认 | 直接讲链路、取舍、失败语义和现有限制 |
| **下一版设计** | 合理的系统设计，但当前项目没有完整实现 | 先说“当前没有”，再说“如果重做，我会……” |
| **待本人确认** | 团队、时间、用户、QPS、薪资、模型、投产、事故等个人事实 | 只填可核验事实；没有证据就不报数字 |

### 0.2 统一事实口径

1. **AI 周报**：程序负责取数、完整性、统计和数字；LLM 只做有依据的异常解读、趋势归纳和文字表达。
2. **CodeWiki**：主链路是 RepoScanner -> AST -> Code Graph -> GraphRAG -> Wiki/Ask；向量是可选索引，不是系统地基。
3. **Agent Memory**：跨会话长期记忆 L0-L3 与单任务 Context Offload 是两条不同链路；它们都不会扩大模型物理上下文窗口。
4. WideSearch、PersonaMem 等数字只能表述为特定数据集、模型和配置下的离线结果，不能说成线上平均收益。
5. 当前没有完整的企业级多租户身份、硬删除传播、稳定事实字段锁和全链路 Retrieval Trace；这些只能作为演进方向。
6. “独立负责”不等于“所有代码都是一个人写”或“带团队”。需求、设计、编码、联调、测试、发布和验收必须逐阶段说明真实 RACI。

## 2. AI 周报系统统一正确答案

详细版本见 [AI 周报系统专项面试问答](../问题/01-AI周报系统/AI周报系统-专项面试问答.md)。

### W01：项目解决什么问题，价值和模型是什么？

这是网联运营保障周报，不是统计员工 Git/Jira 进度。原流程每周从多个系统取错误日志、慢 SQL、大事务、失败交易、TPS 和响应时间，再人工核对、分析和组装。系统把它改成自动日批，价值首先来自自动采集、校验和确定性统计；LLM 只减少逐模块阅读与写说明的成本。

“约 50 人天”必须说明是改造前后年度人工投入差值的估算，不是财务审计。具体模型、上线时间、当前是否仍使用均为 **[待本人确认]**，不要用模型名字代替系统设计。

### W02：数据源、格式和完整链路是什么？

当前材料确认的数据源包括北斗、园方、AN1LOG、CKTRANS、CKSLOWSQL、FTCLOG 等业务、交易和日志系统。外部响应可以是 JSON、表格或日志，但进入分析前必须归一成带 `source、business_date、metric、value、status` 的内部结构。

链路是：按业务日期采集 -> 清洗落表 -> 七天完整性 Gate -> 各模块确定性统计 -> LLM 分段解读 -> 固定模板组装表格加文本 -> 内部消息推送。不同来源可以给出相关性线索，但当前没有因果图和自动实验，不能说成已经证明根因。

### W03：API 不稳定、历史补拉和幂等怎么做？

限流应放在连接器级共享 token bucket；只对超时、429 和可恢复 5xx 重试，遵守 `Retry-After`，使用有上限的指数退避加 jitter。采集任务以原始数据窗口为主键，不以补跑日期为主键。

幂等依赖稳定业务键和唯一约束，例如 `source_id + window_start + metric_key`，写入用事务性 upsert。`pending/success` 只是状态，不等于幂等。当前实现每天回看近 15 天 Pending 数据；“租约、`next_retry_at`、死信、输入版本和自动失效重算”是更完整的下一版设计。

### W04：如何验证数据准确？

准确性分三层：采集层核对时区、分页、行数、唯一键和源端总量；指标层用固定输入/期望输出做单测，并与历史人工报表并行核对；生成层把模型输出中的数字和 `evidence_id` 回查事实表，不一致就拒绝该段并回退模板。

上线后持续看缺失率、迟到率、重复率、指标差异和 LLM 校验失败率。使用 NumPy、Python 或“不让 LLM 算数”本身都不是准确性证明。

### W05：LLM 如何分段，模板是否变化？

按周报语义章节和 Token Budget 分段，例如资源、调用链、慢 SQL和长事务。每段输入是已验证指标、基线、阈值和证据 ID，模型按固定 Schema 输出摘要、异常和引用。程序负责聚合数字与最终章节，模型不能在 Reduce 阶段重新计算指标。

大模型加入后可以让异常说明随数据变化，但最终表格和章节骨架仍是确定性模板。分段的价值是控制上下文、隔离失败、单独重试和审计，不是简单把文本平均切块。

### W06：没有 LLM 能不能做，项目现在还有没有价值？

可以。固定采集、规则统计和模板足以完成基础周报。LLM 的增量价值是对每周变化的异常做受证据约束的解释和归纳，避免把所有说明规则都人工穷举。若业务只要数字表格，应优先不用 LLM。

当前维护状态、使用人群和最后更新时间是 **[待本人确认]**。回答应承认工作流底座的价值，不声称 LLM 不可替代。

### W07：Text-to-SQL 如何防删库、越权和 Schema 错误？

先纠正前提：当前周报不是 Text-to-SQL，查询和统计 SQL 由程序预先编写。若下一版支持自然语言查数，应使用只读账号/只读副本、授权后的 Schema 子集、SQL AST 白名单、行列权限、超时与扫描量限制、执行前 `EXPLAIN`、结果限行和完整审计；禁止多语句、DDL/DML 和危险函数。

Schema 通过结构化 catalog 提供表、字段、类型、业务含义、关联、敏感级别和更新时间，而不是把整个库 DDL 无差别塞进 Prompt。

### W08：多系统日志如何做根因诊断？

这属于从周报能力迁移出的 **下一版设计**。先收业务影响、Trace/请求 ID、RED 指标、数据库/MQ、结构化日志、发布配置变更、预期/观测拓扑和 Runbook；统一时间、时区和实体标识后，寻找“第一个异常信号”，而不是最后一个报 500 的服务。

模型只整理“候选假设、支持证据、反证、缺失证据和下一条查询”。必须通过原始日志、请求回放、配置对照、Feature Flag 或受控回滚验证后，才能称为根因。

### W09：拓扑、Trace 断链和自动修复怎么处理？

预期拓扑来自注册中心、RPC 配置、API 契约、静态代码和基础设施；观测拓扑来自 Trace、Service Mesh、网关和消息系统，两者都要带版本与时间窗口。关联优先使用 W3C Trace Context，再用 message ID、业务流水号，最后才用拓扑、实例、时间窗和错误码做不确定推断。

自动修复只能分级：低风险、可回滚、验证充分的 Runbook 动作可自动执行；改代码应在隔离分支生成补丁、跑测试/静态扫描/回归并人工审批，绝不能由模型直接改生产。

## 3. CodeWiki 统一正确答案

详细版本见 [CodeWiki 全链路源码级深入分析](../问题/02-CodeWiki/CodeWiki-全链路源码级深入分析.md)。

### C01：CodeWiki 是什么，强 Coding Agent 时代还有什么价值？

CodeWiki 是本地优先的代码智能平台：把仓库解析为可追溯代码图，用符号、全文、可选向量和受限图扩展为 Ask/Wiki 提供证据。它不替代 Claude Code、Codex 或 Cursor；一次性小仓库任务通常直接用强 Agent 更合适。

它的净价值在反复跨模块问题、精确源码引用、团队知识复用和可审计 Wiki。是否值得使用要以原生 Agent、Repo Map/Skill、CodeWiki 三组任务的正确率、耗时、Token、建索引成本和新鲜度比较，而不是宣称“GraphRAG 一定更强”。

### C02：完整架构和 GraphRAG 流程是什么？

离线链路是 RepoScanner -> tree-sitter AST/语言增强器 -> 统一 Symbol IR -> Code Graph/Community -> 符号级 Source Chunk -> FTS/可选 Vector。在线链路先通过符号、路径、FTS 和可选向量找 Seed，再在跳数和节点数预算内扩图，按五因子排序并装成 Context Pack，最后供 Ask、Wiki、CLI 或 MCP 使用。

这里的 GraphRAG 是“代码图约束的检索增强”，不是照搬微软 GraphRAG；MCP 是把已有能力暴露给 Agent 的协议，不是检索算法。

### C03：tree-sitter 是开源的，自研了什么，支持哪些语言？

tree-sitter 只提供语法树底座。自研价值在各语言 Capture Spec 与 Augmenter、统一 Symbol IR、稳定 ID、跨文件启发式解析、置信度和 provenance、增量缓存、图存储、检索和 Agent 工具化。结构边相对确定，跨文件 Calls/References 受动态分派和类型缺失影响，不能说成编译器级完整调用图。

支持语言和本人熟练度要分开说：解析器支持不等于本人精通该语言。具体语言清单和熟练度按当前项目和本人事实回答。

### C04：节点、边和 Chunk 怎么设计？

节点包括仓库、目录、文件、类、函数、方法、接口、Endpoint、Schema、Config 等；边包括 contains、defines、imports、exports、calls、references、inherits、implements、routes_to 和 uses_config，边带方向、置信度、是否推断和来源。

当前是符号级 Chunk，一个符号对应精确文件和行范围，没有把超大函数二次切片。因此“大函数切成两个 Chunk 后是什么边”的正确回答是先纠正前提。下一版如要切，可用 `parent_symbol_id + ordinal + line_range` 和相邻片元回带，是否建 Sequential Edge 应由评测决定。

### C05：如何检索、组装上下文并控制 Token？

Seed 来自符号名/路径、节点 FTS、源码 FTS 和可选向量；扩图受最大跳数和节点数限制。候选按语义、关键词、图距离、节点重要度和源码新鲜度排序，再受最大 Chunk 数和近似 Token Budget 约束装包。

当前没有实现 Lost in the Middle 的头尾双端布局，也不能说 8000 的近似预算保证最终 Prompt 一定不超。下一版应对比降序、头尾双端和按证据类型分区，并在最终序列化后再次精确计数。

### C06：向量库怎么选，如何更新、删除和建索引？

本地优先场景用 SQLite/FTS 和可选 sqlite-vec；服务化、多并发和关系数据共存可用 PostgreSQL + pgvector。向量是增强，不启用 Embedding 时符号、FTS 和图仍可工作；只有规模、过滤、延迟和运维需求明确时才考虑独立向量数据库。

记录以稳定 `chunk_id` 定位，保存 `repo_id、revision、path、symbol_id、content_hash、model、dimension`。内容 Hash 变化时 upsert 新向量，删除 Chunk 时按外键/事务删除索引。HNSW 适合低延迟近邻查询但更新删除和内存成本更高；IVFFlat 需要训练并依赖 lists/probes 调参。具体生产使用过哪些库是 **[待本人确认]**。

### C07：多分支、历史版本和 Dirty Workspace 怎么保证一致？

正确的数据主键应绑定不可变 `repo_id + revision + path/symbol`。历史 Commit/Tag 要切到隔离 worktree 或快照单独建索引；不能把多个版本静默写进同一在线图。工作区有未提交修改时，要么实时覆盖索引并标记 dirty revision，要么直接拒绝旧索引回答并让 Agent 读当前文件。

当前实现有 Git Diff/Hash 增量，但没有贯穿图、向量、Wiki 和引用的统一不可变 Revision，因此不能承诺任意历史查询或强一致 Dirty Workspace。这是必须主动承认的现有缺口。

### C08：如何治理幻觉和源码安全？

幻觉来自模型先验、召回遗漏/噪声、陈旧索引、上下文冲突和无证据生成。治理链是：精确 Source Ref、受限 Context Pack、答案引用、引用存在性/行范围校验、必要时读取原文、低证据时拒答，以及按固定问题集评测。

源码安全需要本地/私有模型或获批网关、最小权限、仓库 ACL、Secret 扫描与脱敏、Prompt Injection 隔离、审计、保留期和删除传播。当前项目不具备完整 SaaS 多租户安全，不能只因“本地优先”就说没有风险。

### C09：MCP、Skill、Prompt、Tool、RAG 和 SDD 的边界是什么？

Prompt 定义本轮指令；Tool 提供可执行能力；MCP 标准化 Tool/Resource 的暴露；Skill 是渐进披露的过程知识，指导 Agent 何时、怎样使用工具；RAG 提供外部事实检索；SDD 用可审查 Spec 驱动实现和验收。它们可以组合，但互不替代。

CodeWiki 可把 analyze/search/graph/wiki 暴露成 MCP Tool，也可把“先读 repo map、再按需查图”的过程写成 Skill。生成文档可留在仓库 Markdown/JSON 并由 Git 管理；Skill 不使用数据库时通常依赖 Agent 的 read/grep/LSP/MCP 动态探索。

### C10：能否检测模块设计或架构坏味道？

图可以检测可计算候选，如循环依赖、层级逆向、热点中心、跨层调用、孤立模块和过度耦合；但“职责不清”“边界合理”需要架构规则或人工判断。正确做法是输出规则、证据边、置信度和受影响节点，不能让模型凭感觉宣布架构违规。

### C11：谁在用、是否仍在使用、是不是一个人做？

用户量、查询量、上线时间、当前采用场景和团队分工全部是 **[待本人确认]**。可回答的结构是：谁在什么工作流中使用、观察窗口多长、查询如何去重、本人负责哪些阶段、同事负责什么。没有日志就说验证过核心能力，不把试验工具包装成长期生产平台。

## 4. Agent Memory 统一正确答案

详细版本见 [AI 记忆系统全链路源码级深入分析](../问题/03-Agent-Memory/Agent-Memory-全链路源码级深入分析.md)。

### M01：为什么做 Memory，它是否扩大上下文窗口？

它解决两个问题：跨会话失忆和单次长任务里工具日志挤占上下文。长期链路沉淀可检索的用户事实、经历和指令；Offload 链路把大 Tool Result 外移并保留摘要与引用。两者都不改变模型的物理窗口，只减少无关内容、提高有效信息密度和证据可恢复性。

长上下文不必然“整体准确率下降”，更具体的故障是中间约束被忽略、相似历史互相干扰、旧状态覆盖新状态、重复工具调用和预算耗尽。应称为 context degradation，而不是把所有问题统称为幻觉。

### M02：实际部署形态和宿主怎么接入？

先答物理事实：主路线是 **本地插件 + SQLite**。插件接 Agent Runtime 生命周期，在模型调用前 Recall，一轮提交后 Capture；JSONL 保存原始证据，Markdown 保存 Scene/Persona，Tool Result 原文放 refs。`TdaiCore` 还支持 Hook 或 HTTP Gateway/sidecar 适配，但“架构支持”不等于某宿主已正式投产。

新宿主至少要提供模型前注入和轮次提交事件；Offload 还要求稳定 Tool Call/Result ID 和可修改的消息上下文。因此不能说“任何工具都能零改造接入”，也不能把 `user_id` 字段当作可信身份和多租户授权。

### M03：整体架构和 L0-L3 分别是什么？

L0 是清理后的原始对话证据；L1 是 `persona / episodic / instruction` 三类可检索原子记忆；L2 把相关 L1 组织为场景 Markdown；L3 是保守生成的长期 Persona。它们不是“会话摘要逐级晋升”，越往上越聚合，但职责不同。

架构上 Capture 先保证 L0，再由后台 Runner 增量生成 L1/L2/L3；Recall 走 FTS、向量和 RRF；稳定画像与 Scene Navigation 常驻，相关 L1 稀疏注入，L2/L0 按需下钻。

### M04：什么时候存，为什么异步，是否跨会话？

L0 在一轮提交后增量持久化；L1 只处理新增消息；L2 按调度窗口聚合；L3 按冷启动、增量阈值或修复条件更新。重处理不阻塞用户响应，Checkpoint 保存游标以便重启续跑。

核心目标是跨会话，但当前身份与隔离粒度仍受宿主提供的路由字段约束，不能包装成完整企业多租户。异步链路是最终一致，刚纠正的事实是否下一轮可见需要 read-your-writes 或同步覆盖层，这是中台化演进问题。

### M05：什么时候加载各层，是否每次读取全部历史？

L3 Persona 和完整 Scene Navigation 放 system 后缀；与 query 相关的少量 L1 放 user 前缀；L2 Scene 正文由 Agent 按需读取；L0 只在核验原话或争议证据时搜索。每轮都重读全部历史是错误设计。

检索以 query 为输入，FTS 和向量各取候选，再用 RRF 融合并限 K。超时可降级为不注入动态记忆，主 Agent 仍继续；不能让记忆服务故障拖垮主链路。

### M06：事实冲突和“身高 167/165/穿鞋 170”怎么处理？

当前实现先召回相似旧记忆，再由 LLM 决定 `store / skip / update / merge`；在线 Store 保存当前记录，JSONL 保留追加历史。它不是完整的实体属性状态机，也没有可靠事实置信度，不能说成“自动选出真值”。

下一版要把 observation 与 canonical fact 分开，记录实体、属性、值、单位、时间、来源、作用域和 measurement context。“穿鞋 170”与裸足身高不是同一属性；167 和 165 判断不了时并存待核验，不能机械取最新、最大或平均值。

### M07：如何减少抽取幻觉，置信度和用户确认怎么做？

当前已有三层约束：只从新增消息抽取；L1 保存 `source_message_ids` 可回 L0；写入前召回相似候选并做四动作判断。真实缺口是来源 ID 尚未逐条完成存在性和 Claim-Evidence 蕴含硬校验；`priority` 和 Offload `score` 也都不是事实置信度。

下一版应分开记录 evidence confidence、冲突状态和纠错事件，增加 Schema 校验、来源蕴含、低置信候选区与用户可查看/编辑/删除入口。用户确认只在高风险冲突时请求，并给出来源与影响；不能把“用户会主动确认”当默认前提。

### M08：Context Offload、结构化摘要和 Mermaid 到底解决什么？

真正释放上下文的是先把原始 Tool Result 持久化到 refs，再在 Prompt 中保留受 Schema 约束的摘要、任务状态、`node_id` 和 `result_ref`。Mermaid 只是任务画布和证据索引，不是压缩本身。

需要精确内容时按引用读取相关片段，而不是把全部原文重新灌回窗口。读回会临时增加 Token，但总体仍通过“平时只留摘要、按需局部恢复、用后可再卸载”避免所有历史长期常驻。

### M09：何时压缩，为什么不只用宿主自带 Compact？

当前 Offload 的 Mild/Aggressive/Emergency 阈值按宿主窗口比例触发，而不是对所有模型死记某个 K 值；主文档默认示例是约 50%、85%、95% 的三档处理。换 128K 模型时还要为系统提示、输出和工具调用预留 headroom，并用任务集校准。

宿主 Compact 通常生成整体摘要，简单且通用；本系统额外保留结构化任务状态和可回查 Tool Result。两者可以组合：先做可逆 Offload，再在必要时使用宿主 Compact。不能宣称自研方案全面替代原生能力。

### M10：和 OpenClaw、CoCo、Mem0 等方案如何比较？

OpenClaw 原生 Memory、Mem0、Letta、Zep 等各有 scope、抽取、更新和检索能力，不能用过时版本下结论。当前项目的特化点是把跨会话长期记忆与 Coding Agent 工具结果的可恢复 Offload 分开，并保留 source/result refs。

公平比较必须固定产品版本、底模、Embedding、任务集、Token Budget、重试和超时，报告任务正确率、Token、写入/召回延迟、错误注入和删除能力。没完整读过 CoCo 源码时就明确说没有，不替竞品编能力。

### M11：Benchmark 数字怎样正确表述？

| 能力 | 数据集 | 基线 | 使用系统后 | 正确口径 |
|---|---|---:|---:|---|
| 长任务通过率 | WideSearch | 33% | 50% | 增加 17 个百分点，相对提升 51.52% |
| 长任务 Token | WideSearch | 221.31M | 85.64M | 降低 61.38% |
| 长期记忆问答 | PersonaMem | 48% | 76% | 增加 28 个百分点 |

这些是特定离线实验，不是线上平均收益。评测 Harness 要固定模型、Prompt、窗口、超时和任务集，多次运行报告均值/方差；还应测抽取 Precision/Recall、冲突动作 Macro-F1、Recall@K/MRR、证据一致率、错误注入率和纠错残留率。

### M12：每轮查询数据库，吞吐和延迟怎么控制？

当前本地插件的 SQLite 访问与多租户中台不是同一规模。当前链路靠稀疏 Top-K、后台抽取、超时降级和按需下钻控制延迟；真实用户量、P95 和 QPS 是 **[待本人确认]**。

若设计中台，应做可信租户分片、索引分区、查询并发预算、热点缓存、请求合并、读写隔离、队列背压和降级；缓存键必须包含用户/租户、记忆 Revision、检索策略和权限版本，不能只给 Recall 文本加普通 TTL。

### M13：SQLite、更新和删除的真实边界是什么？

本地默认用 SQLite/JSONL/Markdown/refs 的组合；SQLite WAL 改善读写并发，但不是分布式数据库。L1 的 update/merge 会替换在线记录并保留 JSONL 历史；L2/L3 重新生成相应文档。

当前无法保证一次“删除用户记忆”同步清除 JSONL、FTS、向量、Scene、Persona、refs、备份和外部 Trace，因此不能承诺硬删除闭环。完整方案需要统一删除事件、各存储消费、审计状态、失败重试和验证报告。

### M14：用户画像是谁，早期细节还找得到吗？

Persona 描述对话用户的稳定偏好、背景和协作方式，不是从 Git Commit 给开发者打绩效标签。L3 只保存稳定摘要，L2 提供场景导航，具体事实仍在 L1，原话仍在 L0；“上层简洁”和“底层可追溯”同时成立。

如果处理第三方画像，必须额外解决知情同意、用途限制、数据最小化、可删除和敏感属性治理，不能直接复用个人 Agent 的默认假设。

## 5. Java、React 与 Web 框架正确答案

### J01：箭头函数 `this`、Hooks 与类组件

箭头函数没有自己的 `this`，在定义位置词法捕获外层 `this`，`call/apply/bind` 不能改变它。React 函数组件没有实例 `this`；类组件事件处理常用箭头函数避免绑定丢失。

`useEffect` 不是生命周期方法的一一替代：无依赖数组时每次提交后执行，空数组通常在挂载后执行并在卸载时 cleanup，带依赖时在依赖变化后 cleanup 再执行。`useLayoutEffect` 在浏览器绘制前同步执行；常用 Hook 还包括 `useState/useReducer/useMemo/useCallback/useRef/useContext`。

### J02：`@Autowired` 与 `@Resource`

`@Autowired` 是 Spring 注解，默认按类型解析，可配 `@Qualifier`，底层由 BeanPostProcessor 处理；`@Resource` 是 Jakarta/JSR 注解，通常先按名称再按类型，Spring 同样负责注入。现代代码优先构造器注入：依赖显式、便于测试、支持不可变字段，也能更早暴露循环依赖。不要把二者差异简化成“一个按类型、一个只按名称”。

### J03：`ThreadLocal`、并发 Map、可重入锁与 AQS

`ThreadLocal` 为同一线程保存上下文副本，常用于 Trace/事务上下文；线程池中必须在 `finally` 里 `remove()`，否则会串数据和泄漏。`HashMap` 非线程安全；Java 8 `ConcurrentHashMap` 读操作多为无锁，写入使用 CAS、桶头 `synchronized`，扩容可协助迁移，不允许 null。

可重入表示同一线程持锁时可再次获取并用计数释放；不可重入会自我死锁。`ReentrantLock` 基于 AQS：AQS 用 `state`、CAS 和 CLH 风格等待队列管理竞争，Lock 再提供公平/非公平、可中断和 Condition。

### J04：MyBatis-Plus Lambda 统计题

```java
long count = studentMapper.selectCount(
    Wrappers.<Student>lambdaQuery()
        .gt(Student::getAge, 20)
        .eq(Student::getGender, Gender.MALE)
);
```

枚举/数据库实际字段值按项目调整。Lambda Wrapper 的优势是字段重构安全；`COUNT(*)` 应由数据库执行，不要先查列表再在 Java 里计数。

### J05：事务传播、幂等和分布式事务

Spring 常见传播中，`REQUIRED` 加入或新建事务，`REQUIRES_NEW` 挂起外层并新建，`NESTED` 在支持时使用 Savepoint；`SUPPORTS/MANDATORY/NOT_SUPPORTED/NEVER` 分别表示支持、强制、挂起、禁止事务。注意同类自调用可能绕过代理，异常被吞也可能导致不回滚。

幂等靠业务幂等键、唯一约束、状态机/版本号和结果复用，不是只靠 Redis 锁。分布式事务按场景选本地事务 + Outbox/Inbox、Saga/TCC 或少量强一致 2PC；银行扣款等强约束要明确账本和补偿边界，不能把“最终一致”说成“完全不会短暂不一致”。

### J06：Minor/Full GC 与 JDK 17/21

Minor/Young GC 主要回收年轻代，通常较频繁、停顿较短；Full GC 涉及整个堆并常伴随类卸载/压缩，代价更高，触发和行为取决于收集器。排查应看 GC Log、分配速率、晋升、老年代占用、停顿和堆转储，不能只背触发条件。

若生产仍是 JDK 8，就如实说。JDK 17 的 record、sealed class 和模式匹配改善领域建模；JDK 21 的虚拟线程适合大量阻塞 I/O，但要评估 pinning、连接池、ThreadLocal、监控和框架兼容。升级先做依赖盘点、回归和性能基线，不是只换语法。

### F01：Django、FastAPI、Express/Koa、Spring Boot 如何比较？

统一按定位、默认能力、并发模型、生态、类型与运维比较：Django 是 batteries-included；FastAPI 是类型提示驱动的 ASGI API 框架；Express 是极简 middleware/router；Koa 是更小的 async 洋葱内核；Spring Boot 是带 IoC、自动配置、Actuator 和完整企业生态的 opinionated platform。

选型看团队语言、领域复杂度、依赖生态、类型安全、延迟模型和维护周期。不能用“用户少选 Python、用户多就重写 Java”作通用结论，性能瓶颈通常先在数据库、网络和业务设计。

### F02：约定优于配置与异常处理

约定减少重复决策、让 Starter 和标准目录快速落地；代价是隐式装配和配置来源变多，偏离默认假设时排障困难。应提供合理默认、显式覆盖、类型化配置、启动校验、Condition Report 和生效配置可观测性。

每处都 `try/catch` 再包装 `AppException` 是反模式，会丢语义、重复日志和破坏堆栈。只在能够恢复、补充领域语义或跨边界转换时捕获；保留 cause，在 Controller/Consumer 等责任边界统一映射错误码并记录一次日志。

### F03：从零设计 Web 框架与编译期 DI

先限定目标，再设计小内核：Router、Request/Response、Middleware、类型化校验/序列化、模块与 DI、生命周期、配置、错误边界、日志/Metrics/Trace、健康检查、测试 Harness 和插件 SPI。数据库、认证、缓存和 MQ 作为标准扩展，不硬编码进内核。

DI 采用构造器注入和构建期生成。模块显式声明 Provider、依赖类型和 Scope；编译插件形成依赖 DAG，检查缺失/重复绑定、循环依赖和 Scope 泄漏，失败即中止构建，再生成工厂代码和 manifest。`Provider<T>/Lazy<T>` 只延迟实例化，不能用来掩盖缺失依赖。

## 6. Agent Runtime、模型路由与 AI Coding 正确答案

### A01：Prompt Engineering、Harness 和 Loop Engineer

Prompt Engineering 不只是写一句指令，而是明确角色、输入/输出 Schema、可用工具、证据边界、失败/拒答条件和 few-shot，并用版本化评测集验证。Harness 是围绕模型的执行外壳：循环、工具、状态、预算、权限、观测、恢复和评测。Loop 是“模型决策 -> 工具执行 -> 结果回填 -> 再决策”直到终止条件，不应无限运行。

Hermes 更常指具体模型/Agent 项目或协议实现，Harness 是系统层概念；比较前先确认面试官所指版本，不能只凭名字判断功能。

### A02：LangGraph 和 State 怎么设计？

LangGraph 适合需要显式状态、分支、循环、Checkpoint、人工介入和恢复的 Agent 工作流。State 只保存跨节点需要的最小事实，如 `messages、task、plan、tool_results/ref、attempt、status、error`；大对象外置为 Artifact Ref，Reducer 明确定义追加、覆盖和幂等合并。

项目没实际用过就说“了解并能说明适用边界”，不要把自研调度器包装成 LangGraph。简单线性调用不需要为了框架而上图。

### A03：LLM -> Workflow -> Agent、Skill 与 Vibe Coding 趋势

演进不是单向替代：LLM 提供生成能力，Workflow 保证确定流程，Agent 负责动态决策，Harness 把它变成可治理运行时，Skill 把领域过程知识按需交给 Agent。下一阶段重点会从“会调用模型”转向上下文工程、评测、权限、状态恢复、工具生态和人机协作。

Vibe Coding 可以快速生成脚手架、CRUD、测试草稿和局部组件，但人仍负责规格、架构、不变量、Review、调试和验收。AI 代码占比是 **[待本人确认]**，最好用一个真实 Commit 说明输入、修改和验证，不用百分比证明能力。

### A04：多模型 Gateway 和 100ms/500ms 路由设计

请求先做任务分类和合规过滤，再从本地/内存中的模型能力表筛出候选，用延迟、成本、离线质量、实时健康和策略权重在 100ms 内决策；数据面异步写审计事件，不在主路径查慢数据库。

500ms Failover 依赖短连接/首 Token 超时、熔断器、预热备用、幂等请求 ID 和可重放请求。质量未知时靠离线基线、在线显式/隐式反馈、少量探索和 Shadow 流量更新先验；模型抖动用滑动窗口、趋势/错误率、降权缓冲、半开探测恢复。每次审计保存策略版本、候选集、特征快照、选择原因、Fallback 和结果。具体使用模型、账号和网关是 **[待本人确认]**。

### A05：Coding Agent 如何编辑文件，Tool 参数怎么设计？

Agent 先读取文件和版本/Hash，模型生成结构化 Tool Call，工具在工作区执行 patch，再返回 diff、诊断和测试结果；模型根据结果继续修正。工具本身受路径 Scope、权限、大小、并发版本和沙箱约束，不能让模型直接任意写磁盘。

编辑工具至少需要 `path、expected_hash/version、patch或range+replacement`，并支持 dry-run；返回 `applied、new_hash、diff、diagnostics`。跨文件变更需要原子计划或逐文件可恢复日志，冲突时拒绝覆盖并重新读取。

### A06：三个项目的延迟怎么答？

周报是离线批处理，优先完整性、可恢复和总完成时间；CodeWiki 把扫描建图放离线，在线限制 Seed、跳数、Chunk 和 Token；Memory 把抽取聚合放后台，Recall 限 K、设超时并可降级。不同系统不能共用一个“P95 越低越好”的答案。

实时眼镜等场景要做流式 ASR、端侧 VAD/轻量特征、云端增量推理、取消过时请求、短建议先出和后台丰富结果；这是场景设计，不是三个现有项目的投产能力。

## 7. 互动小说记忆系统正确答案

### S01：Coding Agent Memory 如何迁移到多角色互动小说？

把 `WorldState` 客观真相、不可变 `EventLog`、各角色 `CharacterBelief`、稳定 Profile/Relationship 和当前 `StoryState` 分开。角色可以相信错误信息，WorldState 仍保持真实；角色不在场的事件不能自动进入其 Belief。

### S02：如何召回而不泄漏世界信息？

先按 `story_id、timeline_id、scene_id、speaker_id` 做数据层权限过滤，再在可见集合内按近期性、语义、实体关系、目标、情绪和因果距离排序。禁止先全局召回再只靠 Prompt 要求模型保密；生成后还要做 claim-to-memory 检查。

### S03：新人物或地点怎样入图？

生成文本先转为 proposal，不直接写 canonical world。依次做实体消歧、Schema/规则校验、时间线与事实一致性检查，合法后才分配 ID、提交 EventLog，并按可见性更新相关角色 Belief；retcon 必须显式创建版本或新 timeline。

### S04：玩家不推进时，开放世界怎样继续？

用 World Tick/Narrative Director 维护角色目标、资源、未解决钩子、前置条件、冷却和 tension curve。规则/规划器生成候选事件并评分，LLM 只负责表现文本。即“状态机决定发生什么，模型决定怎样讲”。

### S05：如何评测互动叙事记忆？

正确性看角色知情泄漏率、世界事实/时间线冲突率、Persona 一致性、事件实体 Recall@K、新实体重复/误合并、纠错残留、200/500 轮后的延迟和成本；体验另看剧情推进率、重复情节、选择影响度、留存和主观评分。安全与泄漏指标不能用满意度替代。

## 8. Ownership、协作与 HR 正确答案

### H01：自我介绍怎么答？

用 60-90 秒讲“身份与主栈 -> 三个项目各一句业务问题/链路/结果 -> 为什么匹配岗位”。身份统一说“任职于招银网络科技有限公司，服务招商银行相关应用”，除非劳动合同主体能证明，否则不说自己是招商银行信息技术部员工。

英文版本同样用 Background -> Three projects -> Fit，不追求复杂词汇。完整英文材料见 [英文面试目录](../问题/05-英文面试/README.md)。

### H02：“独立负责”与团队角色怎么答？

按项目逐阶段列 RACI：需求澄清、架构、核心实现、前端、测试、发布和运营分别谁 Responsible/Accountable/Consulted/Informed。结论可以是“我对技术主线端到端负责，但产品决策、测试、平台和发布由相应同事共同完成”，前提是事实支持。

团队人数、项目周期、用户量、本人是否带人、前端是否由同事协助均为 **[待本人确认]**，不能套用统一数字。

### H03：交付、估时、延期和技术分歧怎么答？

先把需求拆成可验收工作包，明确依赖、风险和 Definition of Done；估时用历史相似项、三点估算和关键路径，并把不确定性写进区间。用看板、里程碑、燃尽/剩余工作和风险清单跟踪，发现关键路径滑动、阻塞老化或范围增长就提前预警。

有分歧时先对齐约束和评价维度，用 PoC/数据比较，Owner 按事先约定的决策权拍板并写 ADR。多个紧急需求则按业务影响和时限重排，优先砍范围/分期，不通过无限加班掩盖资源冲突。真实例子必须换成本人 STAR。

### H04：求职动机、离职原因和发展路径怎么答？

回答结构是“为什么这个业务 -> 现有能力怎样迁移 -> 还要补什么”，并引用面试当天核验的公司信息。离职只讲正向方向：希望 AI 应用成为正式业务目标，持续接触用户、评测和产品闭环；不贬低现公司，也不编造内部转岗受阻。

发展路径可说短期交付一个可验证场景，中期独立负责模块/方向，长期成长为 AI 应用架构负责人。公司名称、岗位、业务变化后必须重写，不能跨公司复用动机。

### H05：薪资、住址、离职和入职时间怎么答？

全部为 **[待本人确认]**。薪资先统一月薪/年包、固定/浮动和税前口径，再给基于岗位范围与市场的区间；住址只说通勤相关的必要范围；入职时间按当前交接要求给可兑现日期，不沿用旧复盘日期。

### H06：金融信息渠道和海外社媒可信度怎么答？

只列实际长期使用的渠道和频率。正式事实优先回到公司公告、交易所/监管 Filing、财报和权威数据源；研报和新闻用于分析，Twitter/X 等社媒只作为线索并做交叉核验。没用过 Bloomberg/Wind 就直说，不用堆平台名冒充金融能力。个人投资习惯同样按真实情况回答。

### H07：越界私人问题和第三方数据合规怎么答？

与岗位无关的情感、家庭、征信等问题可以礼貌设界：“这部分比较私人，我可以说明与履职直接相关的稳定性、入职和合规信息。”不要为了推进面试无限暴露隐私。

第三方聊天截图、语音和微表情涉及非用户本人的个人信息，必须明确知情同意、用途限制、最小化、保留期、访问审计和删除权。智能眼镜“让对方不知道被分析”是严重合规和伦理风险，不能只讨论技术可行性。

### H08：哪些事实绝不能由答案库代填？

以下统一标记 **[待本人确认]**：项目日期与重叠关系、真实数据源数量/数据量、团队规模、RACI、用户量、QPS/P95/SLA、部署/CI/CD、当前模型与账号渠道、项目采用状态、事故、AI 代码占比、当前薪资、Offer 和入职日期。模板只能帮你组织事实，不能把未知变成经历。

## 10. 复习优先级

4. H02/H08：Ownership、团队、用户、项目日期、模型和指标证据。

### 第二优先级：最新面试新增能力

1. F01-F03：Web 框架比较、异常边界、从零设计框架与编译期 DI。
2. M11、S01-S05：公平 Benchmark 和互动叙事记忆设计。
3. A04-A06：模型路由、Coding Agent 工具和不同系统的延迟目标。
4. W08-W09：日志 RCA、拓扑、Trace 断链和自动修复边界。

- 每个回答能否先用一句话给结论，再展开链路、取舍和边界。
- 是否把“当前实现”和“下一版设计”说反。
- 所有数字能否说明数据集、样本、基线、公式和观察窗口。
- 所有个人事实是否已在 [事实核对清单](../问题/00-总览/面试前个人事实核对清单.md) 中关闭。
