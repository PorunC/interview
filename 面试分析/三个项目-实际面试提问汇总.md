> 整理范围：`面试分析/` 下现有 17 场真实面试复盘。
>
> 使用方法：本文是一份可以独立复习的完整答案库。第二至第四节直接收录三个简历项目的 W/C/M 答案，第五至第九节收录公共技术、场景设计和行为面答案，第十节按公司反查现场题号。外部链接只用于源码细节和延伸阅读，不承担主答案。

> 收录规则：只把复盘中明确记录的提问、连续追问和面试官挑战算作现场题；“可能追问”“下一轮建议题”不冒充现场原题。

## 0. 使用规则与事实边界

### 0.1 三种回答标签

| 标签 | 含义 | 面试时怎么说 |
|---|---|---|
| **当前实现** | 能从项目材料、源码或真实复盘确认 | 直接讲链路、取舍、失败语义和现有限制 |
| **下一版设计** | 合理的系统设计，但当前项目没有完整实现 | 先说“当前没有”，再说“如果重做，我会……” |
| **待本人确认** | 团队、时间、用户、QPS、薪资、模型、投产、事故等个人事实 | 只填可核验事实；没有证据就不报数字 |

### 0.2 统一事实口径

1. **AI 周报**：程序负责取数、完整性、统计和数字；LLM 只做有依据的异常解读、趋势归纳和文字表达。
2. **CodeWiki**：主链路是 RepoScanner -> AST -> Code Graph -> GraphRAG -> Wiki/Ask；向量是可选索引，不是系统地基。
3. **Agent Memory**：跨会话长期记忆 L0-L3 与单任务 Context Offload 是两条不同链路；它们都不会扩大模型物理上下文窗口。
4. WideSearch、PersonaMem 等数字只能表述为特定数据集、模型和配置下的离线结果，不能说成线上平均收益。
5. 当前没有完整的企业级多租户身份、硬删除传播、稳定事实字段锁和全链路 Retrieval Trace；这些只能作为演进方向。
6. “独立负责”不等于“所有代码都是一个人写”或“带团队”。需求、设计、编码、联调、测试、发布和验收必须逐阶段说明真实 RACI。
7. 货拉拉一面、货拉拉二面、颂拓和 Autel 的新复盘已回流到统一题库；现场明确问过的题与单场建议题分开标注，未知的现场编码题不杜撰。
8. Suunto 面试官透露的团队、环境和云化信息只作为当场公司观察，不自动等于候选人的实际交付经历；产品名、模型名和 Benchmark 口径仍需本人核验。

## 2. AI 周报系统完整答案

### W01：项目解决什么问题，价值和模型是什么？

**口语化回答：**

> 我会先给结论：这是网联运营保障周报，不是统计员工 Git/Jira 进度。原流程每周从多个系统取错误日志、慢 SQL、大事务、失败交易、TPS 和响应时间，再人工核对、分析和组装。系统把它改成自动日批，价值首先来自自动采集、校验和确定性统计；LLM 只减少逐模块阅读与撰写说明的成本。


“约 50 人天”必须说明是改造前后年度人工投入差值的估算，不是财务审计。具体模型、上线时间、本人贡献和当前使用状态均为 **[待本人确认]**，不能用模型名称代替系统设计。

### W02：数据源、格式和完整链路是什么？

**口语化回答：**

> 我会先给结论：当前材料确认的数据源包括北斗、园方、AN1LOG、CKTRANS、CKSLOWSQL、FTCLOG 等业务、交易和日志系统。外部响应可以是 JSON、表格或日志，但分析前必须归一成带 `source、business_date、metric、value、status` 的内部结构。


链路是：按业务日期采集 -> 清洗落表 -> 七天完整性 Gate -> 各模块确定性统计 -> LLM 分段解读 -> 固定模板组装表格加文本 -> 内部消息推送。不同来源只能提供相关性线索；当前没有因果图和自动实验，不能说已经证明根因。

### W03：API 不稳定、历史补拉和幂等怎么做？

**口语化回答：**

> 我会先给结论：限流应放在连接器级共享 token bucket；只对超时、429 和可恢复 5xx 重试，遵守 `Retry-After`，使用有上限的指数退避加 jitter。采集任务以原始数据窗口为主键，不以补跑日期为主键。


幂等依赖稳定业务键和唯一约束，例如 `source_id + window_start + metric_key`，写入用事务性 upsert。`pending/success` 只是状态，不等于幂等。当前实现每天回看近 15 天 Pending 数据；租约、`next_retry_at`、死信、输入版本和自动失效重算是下一版设计。

### W04：如何验证数据准确？

**口语化回答：**

> 我会先给结论：准确性分三层：采集层核对时区、分页、行数、唯一键和源端总量；指标层用固定输入/期望输出做单测，并与历史人工报表并行核对；生成层把模型输出中的数字和 `evidence_id` 回查事实表，不一致就拒绝该段并回退模板。


上线后持续看缺失率、迟到率、重复率、指标差异和 LLM 校验失败率。使用 NumPy、Python 或“不让 LLM 算数”本身都不是准确性证明。

### W05：LLM 如何分段，模板是否变化？

**口语化回答：**

> 我会先给结论：按周报语义章节和 Token Budget 分段，例如资源、调用链、慢 SQL 和长事务。每段输入是已验证指标、基线、阈值和证据 ID，模型按固定 Schema 输出摘要、异常和引用。程序负责聚合数字与最终章节，模型不能在 Reduce 阶段重新计算指标。


大模型加入后可以让异常说明随数据变化，但最终表格和章节骨架仍是确定性模板。分段的价值是控制上下文、隔离失败、单独重试和审计，不是简单把文本平均切块。

### W06：没有 LLM 能不能做，项目现在还有没有价值？

**口语化回答：**

> 我会先给结论：可以。固定采集、规则统计和模板足以完成基础周报。LLM 的增量价值是对每周变化的异常做受证据约束的解释和归纳，避免把所有说明规则都人工穷举。若业务只要数字表格，应优先不用 LLM。


当前维护状态、使用人群和最后更新时间是 **[待本人确认]**。回答应承认工作流底座的价值，不声称 LLM 不可替代。

### W07：Text-to-SQL 如何防删库、越权和 Schema 错误？

**口语化回答：**

> 我会先给结论：先纠正前提：当前周报不是 Text-to-SQL，查询和统计 SQL 由程序预先编写。若下一版支持自然语言查数，应使用只读账号/只读副本、授权后的 Schema 子集、SQL AST 白名单、行列权限、超时与扫描量限制、执行前 `EXPLAIN`、结果限行和完整审计；禁止多语句、DDL/DML 和危险函数。


Schema 通过结构化 Catalog 提供表、字段、类型、业务含义、关联、敏感级别和更新时间，而不是把整个库 DDL 无差别塞进 Prompt。

### W08：多系统日志如何做根因诊断？

**口语化回答：**

> 我会先给结论：这属于从周报能力迁移出的 **下一版设计**。先收业务影响、Trace/请求 ID、RED 指标、数据库/MQ、结构化日志、发布配置变更、预期/观测拓扑和 Runbook；统一时间、时区和实体标识后，寻找“第一个异常信号”，而不是最后一个报 500 的服务。


模型只整理“候选假设、支持证据、反证、缺失证据和下一条查询”。必须通过原始日志、请求回放、配置对照、Feature Flag 或受控回滚验证后，才能称为根因。

### W09：拓扑、Trace 断链和自动修复怎么处理？

**口语化回答：**

> 我会先给结论：预期拓扑来自注册中心、RPC 配置、API 契约、静态代码和基础设施；观测拓扑来自 Trace、Service Mesh、网关和消息系统，两者都要带版本与时间窗口。关联优先使用 W3C Trace Context，再用 message ID、业务流水号，最后才用拓扑、实例、时间窗和错误码做不确定推断。


自动修复只能分级：低风险、可回滚、验证充分的 Runbook 动作可自动执行；改代码应在隔离分支生成补丁、跑测试/静态扫描/回归并人工审批，绝不能由模型直接改生产。

### W10：两个来源的数据冲突、时间标签不一致，怎样处理？

**口语化回答：**

> 我会先给结论：先统一来源、指标、单位、时区和窗口，再分别保留 `event_time`、`ingest_time`、来源版本和质量状态。来源权威度、完整性、新鲜度和时间对齐只能用于排序，不能把不确定的数字静默覆盖；无法裁决时保留冲突、标记待核验并在周报中显式提示。当前项目没有自动因果裁决器。


### W11：429、超时和历史补采怎样重试，如何避免重复？

**口语化回答：**

> 我会先给结论：连接器级共享限流器先尊重 `Retry-After`，只对超时、429 和可恢复 5xx 做有上限的指数退避与 jitter，并受单次运行 Deadline 约束。任务以 `source_id + window + metric_key + input_version` 形成幂等键，落库用唯一约束和事务性 upsert；重试状态、死信、租约和回放游标要可观测。


API 重试解决“没拿到或暂时失败”，来源冲突解决“拿到了但口径不同”，不能混成一个问题。

### W12：周报数字怎样和模型叙述、对账结果闭环？

**口语化回答：**

> 我会先给结论：数字、汇总、排序和同比由程序确定性计算；LLM 只消费已验证指标、阈值和 `evidence_id`，输出摘要、异常和引用。生成后校验引用存在、数字与事实表一致、时间范围匹配，失败就回退到模板或进入人工核对。


若把周报能力迁移到运动或数据平台，仍要保留源端总量、落库行数、迟到/重复率和最终产物的对账记录。当前没有完整证据时，不把“准确率”说成模型指标。

## 3. CodeWiki 完整答案

### C01：CodeWiki 是什么，强 Coding Agent 时代还有什么价值？

**口语化回答：**

> 我会先给结论：CodeWiki 是本地优先的代码智能平台：把仓库解析为可追溯代码图，用符号、全文、可选向量和受限图扩展为 Ask/Wiki 提供证据。它不替代 Claude Code、Codex 或 Cursor；一次性小仓库任务通常直接用强 Agent 更合适。


它的净价值在反复跨模块问题、精确源码引用、团队知识复用和可审计 Wiki。不能说现代 Coding Agent 只是 grep；是否值得使用要以原生 Agent、Repo Map/Skill、CodeWiki 三组任务的正确率、耗时、Token、建索引成本和新鲜度比较，而不是宣称 GraphRAG 一定更强。

### C02：完整架构和 GraphRAG 流程是什么？

**口语化回答：**

> 我会先给结论：离线链路是 RepoScanner -> tree-sitter AST/语言增强器 -> 统一 Symbol IR -> Code Graph/Community -> 符号级 Source Chunk -> FTS/可选 Vector。在线链路先通过符号、路径、FTS 和可选向量找 Seed，再在跳数和节点数预算内扩图，按语义、关键词、图距离、节点重要度和新鲜度排序，装成 Context Pack，最后供 Ask、Wiki、CLI 或 MCP 使用。


这里的 GraphRAG 是“代码图约束的检索增强”，不是照搬微软 GraphRAG；MCP 是把已有能力暴露给 Agent 的协议，不是检索算法。

### C03：tree-sitter 是开源的，自研了什么，支持哪些语言？

**口语化回答：**

> 我会先给结论：tree-sitter 提供的是 CST/可查询语法树底座，项目再把需要的节点映射成 AST 风格统一结构。自研价值在各语言 Capture Spec 与 Augmenter、统一 Symbol IR、稳定 ID、跨文件启发式解析、置信度和 provenance、增量缓存、图存储、检索和 Agent 工具化。


结构边相对确定，跨文件 Calls/References 受动态分派和类型缺失影响，不能说成编译器级完整调用图。支持语言和本人熟练度要分开说；具体语言清单和本人贡献是 **[待本人确认]**。

### C04：节点、边和 Chunk 怎么设计？

**口语化回答：**

> 我会先给结论：节点包括仓库、目录、文件、类、函数、方法、接口、Endpoint、Schema、Config 等；边包括 `contains、defines、imports、exports、calls、references、inherits、implements、routes_to、uses_config`，边带方向、置信度、是否推断和来源。


当前是符号级 Chunk，一个符号对应精确文件和行范围，没有把超大函数二次切片。因此面试官问“大函数切成两个 Chunk 后是什么边”时要先纠正前提。下一版如要切，可用 `parent_symbol_id + ordinal + line_range` 和相邻片元回带，是否建 Sequential Edge 由评测决定。

### C05：如何检索、组装上下文并控制 Token？

**口语化回答：**

> 我会先给结论：Seed 来自符号名/路径、节点 FTS、源码 FTS 和可选向量；扩图受最大跳数和节点数限制。候选按语义、关键词、图距离、节点重要度和源码新鲜度排序，再受最大 Chunk 数和近似 Token Budget 约束装包。


当前没有实现 Lost in the Middle 的头尾双端布局，也不能说近似预算保证最终 Prompt 一定不超。下一版应对比降序、头尾双端和按证据类型分区，并在最终序列化后再次精确计数。

### C06：向量库怎么选，如何更新、删除和建索引？

**口语化回答：**

> 我会先给结论：本地优先场景用 SQLite/FTS 和可选 sqlite-vec；服务化、多并发和关系数据共存可用 PostgreSQL + pgvector。向量只是增强，不启用 Embedding 时符号、FTS 和图仍可工作；只有规模、过滤、延迟和运维需求明确时才考虑独立向量数据库。


记录以稳定 `chunk_id` 定位，保存 `repo_id、revision、path、symbol_id、content_hash、model、dimension`。内容 Hash 变化时 upsert 新向量，删除 Chunk 时同步删除索引。HNSW 适合低延迟近邻查询但更新删除和内存成本高；IVFFlat 需要训练并调 lists/probes。具体生产使用过哪些库是 **[待本人确认]**。

### C07：多分支、历史版本和 Dirty Workspace 怎么保证一致？

**口语化回答：**

> 我会先给结论：正确主键应绑定不可变 `repo_id + revision + path/symbol`。历史 Commit/Tag 要切到隔离 worktree 或快照单独建索引；不能把多个版本静默写进同一在线图。工作区有未提交修改时，要么实时覆盖索引并标记 dirty revision，要么拒绝旧索引回答并让 Agent 读当前文件。


当前实现有 Git Diff/Hash 增量，但图、向量、Wiki 和引用尚未贯穿统一不可变 Revision，因此不能承诺任意历史查询或 Dirty Workspace 强一致。

### C08：如何治理幻觉和源码安全？

**口语化回答：**

> 我会先给结论：幻觉来自模型先验、召回遗漏/噪声、陈旧索引、上下文冲突和无证据生成。治理链是精确 Source Ref、受限 Context Pack、答案引用、引用存在性/行范围校验、必要时读取原文、低证据时拒答，以及固定问题集评测。


源码安全需要本地/私有模型或获批网关、最小权限、仓库 ACL、Secret 扫描与脱敏、Prompt Injection 隔离、审计、保留期和删除传播。当前项目不具备完整 SaaS 多租户安全，不能只因“本地优先”就说没有风险。

### C09：MCP、Skill、Prompt、Tool、RAG 和 SDD 的边界是什么？

**口语化回答：**

> 我会先给结论：Prompt 定义本轮指令；Tool 提供可执行能力；MCP 标准化 Tool/Resource 的暴露；Skill 是渐进披露的过程知识，指导 Agent 何时、怎样使用工具；RAG 提供外部事实检索；SDD 用可审查 Spec 驱动实现和验收。它们可以组合，但互不替代。


CodeWiki 可把 analyze/search/graph/wiki 暴露成 MCP Tool，也可把“先读 Repo Map、再按需查图”写成 Skill。生成文档可以留在仓库 Markdown/JSON 并由 Git 管理；Skill 不使用数据库时通常依赖 Agent 的 read/grep/LSP/MCP 动态探索。

### C10：能否检测模块设计或架构坏味道？

**口语化回答：**

> 我会先给结论：图可以检测可计算候选，如循环依赖、层级逆向、热点中心、跨层调用、孤立模块和过度耦合；但“职责不清”“边界合理”仍需要架构规则或人工判断。正确产物是规则、证据边、置信度和受影响节点，不能让模型凭感觉宣布架构违规。


### C11：谁在用、是否仍在使用、是不是一个人做？

**口语化回答：**

> 我会先给结论：用户量、查询量、上线时间、当前采用场景和团队分工全部是 **[待本人确认]**。回答结构是：谁在什么工作流中使用、观察窗口多长、查询如何去重、本人负责哪些阶段、同事负责什么。没有日志就说验证过核心能力，不把试验工具包装成长期生产平台。


### C12：Neo4j、关系型存储和 Git diff 怎样分工，增量更新为什么不能只跑 diff？

**口语化回答：**

> 我会先给结论：图数据库适合保存节点、边、方向、置信度和关系遍历；关系型存储适合仓库/Revision 元数据、任务状态、唯一约束、审计和事务；文件或对象存储保留源码快照和原文证据。三者通过稳定的 `repo_id + revision + symbol_id` 关联，不能让图数据库单独承担版本事实。当前是否实际使用 Neo4j、由什么触发更新是 **[待本人确认]**。


Git diff 只能告诉我可能受影响的文件和行，不能保证文档正确更新。函数重命名、移动、删除、宏/动态调用和跨文件类型变化可能让旧节点、边、向量、Wiki 和 Citation 残留。增量流程应把 diff 作为候选集合，再按内容 Hash、符号稳定 ID、反向依赖和删除 tombstone 重算受影响子图，最后在同一 Revision 下原子发布；无法证明一致时标记 stale 并回退读原文。

延伸阅读：[CodeWiki 全链路源码级深入分析](../问题/项目/02-CodeWiki/CodeWiki-全链路源码级深入分析.md)。

## 4. Agent Memory 完整答案

### M01：为什么做 Memory，它是否扩大上下文窗口？

**口语化回答：**

> 我会先给结论：它解决两个问题：跨会话失忆和单次长任务里工具日志挤占上下文。长期链路沉淀可检索的用户事实、经历和指令；Offload 链路把大 Tool Result 外移并保留摘要与引用。两者都不改变模型物理窗口，只减少无关内容、提高有效信息密度和证据可恢复性。


长上下文不必然整体准确率下降，更具体的故障是中间约束被忽略、相似历史互相干扰、旧状态覆盖新状态、重复工具调用和预算耗尽。应称为 Context Degradation，不把所有问题统称为幻觉。

### M02：实际部署形态和宿主怎么接入？

**口语化回答：**

> 我会先给结论：先答物理事实：主路线是 **本地插件 + SQLite**。插件接 Agent Runtime 生命周期，在模型调用前 Recall，一轮提交后 Capture；JSONL 保存原始证据，Markdown 保存 Scene/Persona，Tool Result 原文放 refs。`TdaiCore` 还支持 Hook 或 HTTP Gateway/sidecar 适配，但“架构支持”不等于某宿主已经正式投产。


新宿主至少要提供模型前注入和轮次提交事件；Offload 还要求稳定 Tool Call/Result ID 和可修改的消息上下文。因此不能说任何工具都能零改造接入，也不能把 `user_id` 字段当可信身份和多租户授权。

### M03：整体架构和 L0-L3 分别是什么？

**口语化回答：**

> 我会先给结论：L0 是清理后的原始对话证据；L1 是 `persona / episodic / instruction` 三类可检索原子记忆；L2 把相关 L1 组织为场景 Markdown；L3 是保守生成的长期 Persona。它们不是“会话摘要逐级晋升”，越往上越聚合，但职责不同。


Capture 先保证 L0，再由后台 Runner 增量生成 L1/L2/L3；Recall 走 FTS、向量和 RRF；稳定画像与 Scene Navigation 常驻，相关 L1 稀疏注入，L2/L0 按需下钻。

### M04：什么时候存，为什么异步，是否跨会话？

**口语化回答：**

> 我会先给结论：L0 在一轮提交后增量持久化；L1 只处理新增消息；L2 按调度窗口聚合；L3 按冷启动、增量阈值或修复条件更新。重处理不阻塞用户响应，Checkpoint 保存游标以便重启续跑。


核心目标是跨会话，但当前身份与隔离粒度仍受宿主路由字段约束，不能包装成完整企业多租户。异步链路是最终一致，刚纠正的事实是否下一轮可见需要 Read-your-writes 或同步 Overlay，这是中台化演进问题。

### M05：什么时候加载各层，是否每次读取全部历史？

**口语化回答：**

> 我会先给结论：L3 Persona 和完整 Scene Navigation 放 system 后缀；与 Query 相关的少量 L1 放 user 前缀；L2 Scene 正文由 Agent 按需读取；L0 只在核验原话或争议证据时搜索。每轮重读全部历史是错误设计。


检索以 Query 为输入，FTS 和向量各取候选，再用 RRF 融合并限 K。超时可降级为不注入动态记忆，主 Agent 继续；不能让记忆服务故障拖垮主链路。

### M06：事实冲突和“身高 167/165/穿鞋 170”怎么处理？

**口语化回答：**

> 我会先给结论：当前实现先召回相似旧记忆，再由 LLM 决定 `store / skip / update / merge`；在线 Store 保存当前记录，JSONL 保留追加历史。它不是完整实体属性状态机，也没有可靠事实置信度，不能说自动选出真值。


下一版把 observation 与 canonical fact 分开，记录实体、属性、值、单位、时间、来源、作用域和 measurement context。“穿鞋 170”与裸足身高不是同一属性；167 和 165 判断不了时并存待核验，不能机械取最新、最大或平均值。

### M07：如何减少抽取幻觉，置信度和用户确认怎么做？

**口语化回答：**

> 我会先给结论：当前已有三层约束：只从新增消息抽取；L1 保存 `source_message_ids` 可回 L0；写入前召回相似候选并做四动作判断。真实缺口是来源 ID 尚未逐条完成存在性和 Claim-Evidence 蕴含硬校验；`priority` 和 Offload `score` 也不是事实置信度。


下一版分开记录 evidence confidence、冲突状态和纠错事件，增加 Schema 校验、来源蕴含、低置信候选区与用户可查看/编辑/删除入口。只在高风险冲突时请求用户确认，并给出来源与影响；不能把用户主动确认当默认前提。

### M08：Context Offload、结构化摘要和 Mermaid 到底解决什么？

**口语化回答：**

> 我会先给结论：真正释放上下文的是先把原始 Tool Result 持久化到 refs，再在 Prompt 中保留受 Schema 约束的摘要、任务状态、`node_id` 和 `result_ref`。Mermaid 只是任务画布和证据索引，不是压缩本身。


需要精确内容时按引用读取相关片段，而不是把全部原文重新灌回窗口。读回会临时增加 Token，但总体通过“平时只留摘要、按需局部恢复、用后可再卸载”避免所有历史长期常驻。

### M09：何时压缩，为什么不只用宿主自带 Compact？

**口语化回答：**

> 我会先给结论：当前 Offload 的 Mild/Aggressive/Emergency 阈值按宿主窗口比例触发，而不是对所有模型死记某个 K 值；主文档默认示例约 50%、85%、95%。换 128K 模型时还要为系统提示、输出和工具调用预留 headroom，并用任务集校准。


宿主 Compact 通常生成整体摘要，简单且通用；本系统额外保留结构化任务状态和可回查 Tool Result。两者可以组合：先做可逆 Offload，再在必要时使用宿主 Compact。不能宣称自研方案全面替代原生能力。

### M10：和 OpenClaw、ClaudeCode、Mem0 等方案如何比较？

**口语化回答：**

> 我会先给结论：OpenClaw 原生 Memory、Mem0、Letta、Zep 等各有 scope、抽取、更新和检索能力，不能用过时版本下结论。当前项目的特化点是把跨会话长期记忆与 Coding Agent 工具结果的可恢复 Offload 分开，并保留 source/result refs。


公平比较必须固定产品版本、底模、Embedding、任务集、Token Budget、重试和超时，报告任务正确率、Token、写入/召回延迟、错误注入和删除能力。没完整读过某个方案源码时就明确说没有，不替竞品编能力。

### M11：Benchmark 数字怎样正确表述？

**口语化回答：**

> 我会先把数据口径说清楚：这些数字只能在固定数据集、基线和配置下解释，不能直接当成线上平均收益。

| 能力 | 数据集 | 基线 | 使用系统后 | 正确口径 |
|---|---|---:|---:|---|
| 长任务通过率 | WideSearch | 33% | 50% | 增加 17 个百分点，相对提升 51.52% |
| 长任务 Token | WideSearch | 221.31M | 85.64M | 降低 61.38% |
| 长期记忆问答 | PersonaMem | 48% | 76% | 增加 28 个百分点 |

这些是特定离线实验，不是线上平均收益。评测 Harness 要固定模型、Prompt、窗口、超时和任务集，多次运行报告均值/方差；还应测抽取 Precision/Recall、冲突动作 Macro-F1、Recall@K/MRR、证据一致率、错误注入率和纠错残留率。任何“40% 到接近 30%”等转写不清的数字都不能写入事实口径。

### M12：每轮查询数据库，吞吐和延迟怎么控制？

**口语化回答：**

> 我会先给结论：当前本地插件的 SQLite 访问与多租户中台不是同一规模。当前链路靠稀疏 Top-K、后台抽取、超时降级和按需下钻控制延迟；真实用户量、P95 和 QPS 是 **[待本人确认]**。


若设计中台，应做可信租户分片、索引分区、查询并发预算、热点缓存、请求合并、读写隔离、队列背压和降级；缓存键必须包含用户/租户、Memory Revision、检索策略和权限版本，不能只给 Recall 文本加普通 TTL。

### M13：SQLite、更新和删除的真实边界是什么？

**口语化回答：**

> 我会先给结论：本地默认用 SQLite/JSONL/Markdown/refs 的组合；SQLite WAL 改善读写并发，但不是分布式数据库。L1 的 update/merge 会替换在线记录并保留 JSONL 历史；L2/L3 重新生成相应文档。


当前无法保证一次“删除用户记忆”同步清除 JSONL、FTS、向量、Scene、Persona、refs、备份和外部 Trace，因此不能承诺硬删除闭环。完整方案需要统一删除事件、各存储消费、审计状态、失败重试和验证报告。

### M14：用户画像是谁，早期细节还找得到吗？

**口语化回答：**

> 我会先给结论：Persona 描述对话用户的稳定偏好、背景和协作方式，不是从 Git Commit 给开发者打绩效标签。L3 只保存稳定摘要，L2 提供场景导航，具体事实仍在 L1，原话仍在 L0；“上层简洁”和“底层可追溯”同时成立。


如果处理第三方画像，必须额外解决知情同意、用途限制、数据最小化、可删除和敏感属性治理，不能直接复用个人 Agent 的默认假设。

### M15：单用户本地 Memory 扩展到 ToC 多租户，最先补什么？

**口语化回答：**

> 我会先给结论：先承认边界：当前项目核心是 Local-first、本地 SQLite 和宿主适配，不是已经验证过的 ToC 高并发平台。中台化时把 `tenant_id/user_id/device_id/agent_id/session_id` 组成可信 scope，由服务端注入而不是让模型填写；原始消息先写 Outbox，抽取、Embedding、去重和冲突检测异步执行；同一 scope 通过版本号、幂等键和有序事件避免乱序。


在线 Recall 采用权限过滤后的稀疏 Top-K、热缓存和读写隔离，按租户/用户分片并限制并发、队列年龄、向量查询和下游模型额度。超时或 Memory 服务不可用时降级到当前会话和已缓存画像。删除要传播到 L0-L3、FTS、向量、缓存、refs、备份和外部 Trace。所有 P95、QPS 和用户量仍是 **[待本人确认]**。

### M16：相对时间“昨天/今天”怎样落库，运动数据的权威事实放哪里？

**口语化回答：**

> 我会先给结论：写入时同时保存原文和解析上下文：`raw_text、reference_time、timezone、event_time_start/end、resolver_version、source_id、confidence`。例如“昨天跑了十公里”不能只落成字符串，也不能脱离用户时区让模型日后猜；无法确定时保留时间区间并请求澄清。


对运动 Agent，距离、配速、心率、睡眠、GPS 和潜水记录等权威事实应放结构化/时序存储，带设备、采集时间、数据新鲜度和授权范围；Memory 只保存偏好、目标和可追溯摘要。向量检索不替代精确数值、时间和设备查询。

### M17：LRU 是否等于 Agent Memory 的遗忘策略？

**口语化回答：**

> 我会先给结论：不等于。LRU 只按最近访问淘汰热缓存，无法表达低频但重要、安全约束、事实置信度、scope、过期和用户删除。长期记忆应把 L0 作为证据归档，L1 保存带来源、时间和作用域的事实，L2/L3 可重建；淘汰或降级综合语义重要性、跨任务复用、置信度、时效、访问信号和合规策略。


模型只能提出动作，服务端校验并保留版本。任何新设计都不能把缓存淘汰直接称成语义遗忘。

### M18：Skill、Hook、本地服务、Gateway 和 Mem0 怎样公平比较？

**口语化回答：**

> 我会先给结论：Skill 是告诉 Agent 何时、怎样使用能力的过程知识；Hook 是宿主生命周期事件的接入点；本地 Memory Service 是执行 Capture/Recall/Offload 的进程边界；Gateway/sidecar 是跨宿主网络适配。它们不是互斥产品选项，也不能从“有 Hook”推出已经是云服务。


Mem0 等成熟方案应在固定版本、底模、Embedding、任务集、窗口、Prompt、重试和超时下比较，报告事实抽取、冲突更新、Recall@K、证据一致率、延迟、Token、成本、租户隔离和删除能力。没有同条件实验就说“了解其能力并能设计公平 Benchmark”，不直接声称自研更好。

## 5. 大数据、ToC、Agent 安全与无人机调度答案

### D01：Kafka 分区、offset、重复消费和幂等

**口语化回答：**

> 我会先给结论：分区提供并行度和分区内有序，offset 是消费者在分区中的进度；消费组通过分区分配实现水平扩展。至少一次投递下，提交 offset 和业务写入不是天然一个事务，重平衡、超时和重试都可能重复。因此业务侧用事件 ID/窗口键、唯一约束、状态机或 Inbox/Outbox 做幂等；只有真正需要时才使用 Kafka 事务，不能把提交 offset 说成业务 exactly-once。


### D02：Kafka 怎样避免消息丢失？

**口语化回答：**

> 我会先给结论：先明确目标是“生产端不丢、Broker 不丢、消费端不丢”。生产端开启幂等生产与合适的 `acks`，Broker 配置副本、ISR 和最小同步副本，消费者处理成功后再提交 offset；监控 lag、Under-replicated Partitions 和发送/落库失败。跨系统副作用仍需要幂等或事务性 Outbox，Kafka 本身不能替业务保证最终结果。


### D03：Flink watermark、窗口和迟到数据怎么处理？

**口语化回答：**

> 我会先给结论：Watermark 是对事件时间进度的估计，用来触发窗口计算；允许乱序时间决定窗口何时关闭，迟到数据可进入 side output、更新窗口结果或补偿任务。要区分 event time、processing time 和 ingest time，并定义迟到上限、结果版本和下游是否接受更新。Watermark 不是消息到了就按时间排序，也不能修复源端时间戳错误。


### D04：Flink checkpoint 和 exactly-once 的关系是什么？

**口语化回答：**

> 我会先给结论：Checkpoint 保存算子状态和输入进度，用于故障恢复；端到端 exactly-once 还要求 Source 可重放、状态一致快照以及 Sink 支持事务或幂等提交。Barrier 对齐可能造成反压和延迟，非对齐 checkpoint 是取舍而不是免费优化。没有幂等 Sink 时，恢复后仍可能重复写出，不能只背“开 checkpoint 就 exactly-once”。


### D05：Spark、Flink 和 Hive 怎样选？

**口语化回答：**

> 我会先给结论：Spark 更适合批处理、离线 ETL 和大规模 SQL；Flink 更适合持续流处理、有状态计算和低延迟事件；Hive 主要是离线数仓 SQL/表格式生态。选型看数据时效、状态、回放、成本和团队运维能力。没有真实使用过的组件按设计题回答，不把学习经验写成生产交付。


### D06：ETL 补数、回放和数据质量怎样做？

**口语化回答：**

> 我会先给结论：每个任务要有可重放的输入窗口、版本、Manifest 和幂等输出键；补数不直接覆盖未知结果，而是产生新的 run/version，经对账和质量门禁后发布。质量至少检查完整性、唯一性、合法范围、跨表一致、及时性和源端总量；失败要定位到 source/window/partition，并保留原始输入和处理状态。


### D07：海量 Top K、数据倾斜和小文件怎么答？

**口语化回答：**

> 我会先给结论：Top K 先做分区内 Top K，再合并全局堆，避免把全部数据拉到单点；数据倾斜通过热点识别、拆分热点 Key、随机前缀/两阶段聚合和合理并行度处理；小文件通过批量写、Compaction、合理分区和文件大小目标治理。优化前先用 Stage、Shuffle、输入分布和文件统计确认瓶颈，不能只调并行度。


### D08：大数据平台和 AI 项目经验怎样对齐？

**口语化回答：**

> 我会先给结论：可迁移的是采集、清洗、窗口、幂等、重试、补数、对账、质量和任务状态；Kafka/Flink/Spark/Hive/ClickHouse 的实际使用、吞吐和延迟必须有代码或监控证据。没有完整生产平台经历时，坦诚说明差距，再用一条真实 Java/数据交付、现场编码和系统设计证明基础能力。


### D09：关闭 AI Coding 后怎样完成现场编码，题面未知时怎样复盘？

**口语化回答：**

> 我会先给结论：现场按“澄清输入输出和约束 -> 说出方案与不变量 -> 编写可运行代码 -> 主动测普通/边界/异常样例 -> 分析复杂度 -> 接并发或规模 Follow-up”推进。优先练 HashMap、滑动窗口、Top K、LRU、区间、BFS/DFS、堆和批量聚合。


货拉拉转写只确认面试官要求关闭 AI Coding/代码补全，没有记录实际题面、候选人代码、测试输出或结果。正确复盘口径就是“题面和结果未知”，不能从准备题库中任选一道冒充现场原题，也不能据此推断通过或淘汰。

### Q60A：Agent 和 Workflow 的边界是什么？（Autel）

**口语化回答：**

> 我会先给结论：Workflow 的下一步主要由代码、状态机和硬约束决定，适合采集、校验、调度和安全门禁；Agent 让模型在明确工具和预算内决定下一步，适合意图理解、候选规划和非结构化信息处理。无人机调度不能把整条链路交给 Agent：LLM 只产出结构化意图或候选方案，约束引擎、优化器和飞控分别负责合法性、优化和实时安全。能用确定性流程解决的部分不需要增加 Agent。


### Q230/M17：LRU 能不能直接表示 Agent Memory 的遗忘？

**口语化回答：**

> 我会先给结论：不能。LRU 只按最近访问淘汰热缓存，无法表达低频但重要、事实置信度、有效期、安全约束、scope 和用户删除。保留 L0 原始证据，L1 保存带来源/时间/作用域的事实，L2/L3 保存可重建的场景和画像；遗忘或降级综合语义重要性、跨任务复用、时效、冲突和合规策略。模型可以提出 `skip/update/archive`，服务端必须校验、留版本并执行删除传播。


### Q231/M16：相对时间“昨天”“今天”怎样落库？

**口语化回答：**

> 我会先给结论：写入时结合 reference time 和用户时区解析，记录 `raw_text`、`reference_time`、`timezone`、`event_time_start/end`、解析器版本、来源 ID 和置信度。“昨天跑了十公里”应变成该时区前一天的日期区间，同时保留原文；无法确定时保存区间并澄清。查询和冲突使用标准化时间，展示和审计使用原文。


### Q232/M15：单用户本地 Memory 怎样扩展成 ToC 多租户服务？

**口语化回答：**

> 我会先给结论：当前项目是 Local-first、本地 SQLite 和宿主适配，不是已验证的 ToC 高并发平台。中台化先建立服务端注入的 `tenant/user/device/agent/session` scope，原始事件走 Outbox，抽取、Embedding、去重和冲突治理异步化；在线 Recall 做权限前置过滤、分片、热缓存、并发预算、超时和降级。版本号和幂等键保证乱序与重复不污染记忆，删除事件传播到 L0-L3、索引、缓存、refs、备份和外部 Trace。QPS/P95/用户量只能引用真实监控。


### Q233/M16：健康、运动和 GPS 数据应不应该全部放进向量 Memory？

**口语化回答：**

> 我会先给结论：不应该。距离、配速、心率、睡眠、HRV、GPS 路线和潜水记录等权威事实应放结构化或时序存储，带设备、采集时间、单位、数据新鲜度和授权范围；Memory 更适合保存偏好、训练目标和可追溯摘要。向量用于找相关背景，不替代精确的时间、数值、设备和权限查询。输出还要区分训练建议、设备说明和医疗诊断，后者应拒答或转官方/人工渠道。


### Q234/C12：Git diff 能否保证 CodeWiki 的知识图谱增量更新正确？

**口语化回答：**

> 我会先给结论：不能。diff 只是受影响候选的线索，函数重命名、移动、删除、动态调用和跨文件类型变化可能留下旧边、旧向量、Wiki 和引用。增量流程应基于 `repo_id + revision + symbol_id`、内容 Hash、反向依赖和删除 tombstone 重算受影响子图，并在同一 Revision 下原子发布；无法证明一致时标记 stale，回退读取当前源码。当前只有 Diff/Hash 增量思路，不能承诺完整统一 Revision 强一致。


### Q235：大 Tool Result 压缩前怎样保证关键内容不丢？（Autel）

**口语化回答：**

> 我会先给结论：先把原文作为不可变 Artifact 保存，再按 Tool Schema 和业务规则定义 must-keep 字段，例如 ID、状态、数字、时间、错误码、权限和引用。结构化字段由程序抽取，模型只摘要非结构化内容；输出必须通过 Schema、数字/状态一致性、引用存在性和 Citation 校验。摘要不可信就回退抽取片段或原文。BM25/向量是之后怎样取回，不是压缩时不丢信息的保证。


### Q236：无人机调度 Agent 中 LLM、约束引擎、优化器和飞控分别做什么？

**口语化回答：**

> 我会先给结论：LLM 负责把自然语言转成结构化任务意图、解释候选方案和处理非结构化信息；约束引擎校验禁飞区、电量、载荷、时间窗、通信和权限；优化器在合法解空间内做多机分配和动态重规划；飞控负责实时姿态、避障、返航和最终安全闭环。任何 LLM 输出都必须经过 Schema、权限和硬约束验证，不能直接发飞控指令。


### Q237：复杂 Agent 怎样证明不是 Demo？

**口语化回答：**

> 我会先给结论：同时测最终结果和执行轨迹：任务成功率、约束违规率、危险动作拦截率、工具选择/参数正确率、状态恢复率、动态重规划耗时、人工介入率、成本和 P95。离线用固定任务集和仿真做回归，线上先 shadow mode，再小范围灰度；注入模型超时、遥测断链、工具重复和调度冲突，验证降级、回滚和审计。满意度不能替代安全指标。


### Q238：早期 Demo 怎样走向稳定环境和 App 云化？

**口语化回答：**

> 我会先给结论：先隔离开发、临时测试和稳定环境的配置、数据、模型和版本，并给每次运行可追踪的 Run/Revision。质量门禁从 Schema/契约测试、关键场景回放、Trace、成本和安全检查开始；上线用灰度、shadow、可回滚制品和明确的 Drain/告警。App 云化从低风险只读、低敏数据开始，先和 App 团队定 API/事件契约、数据新鲜度和删除责任，再逐步同步运动数据，不能因为团队有云服务额度就声称完成生产云化。


### Q239：大数据平台岗位中，AI 项目经验怎样如实对齐？

**口语化回答：**

> 我会先给结论：能迁移的是数据契约、采集与补数、幂等更新、质量校验、任务状态、回放和故障治理；Kafka、Flink、Spark、Hive、ClickHouse 等组件是否实际使用必须逐项说明。若没有完整生产数仓经历，把它说成当前差距，并用现场编码、系统设计和一条可核验的 Java/数据交付证明基础能力。货拉拉转写没有记录实际编码题面和结果，不能杜撰题目或通过结论。


### T01：怎样设计 Suunto ToC 运动智能体整体架构？

**口语化回答：**

> 我会先给结论：用户身份和设备绑定经过授权后，App 通过 API Gateway 调用 Agent Orchestrator；Orchestrator 按任务选择训练历史、设备状态、路线、产品手册、天气或账户工具。数据层分为权威业务数据、时序运动数据、文档知识和派生特征；模型只接收当前问题所需的最小、带时间和来源的数据。


设备同步和 App 数据先进入事件/同步层，按设备事件时间和接收时间保存；训练、睡眠、GPS、心率和 HRV 经过质量校验后进入时序或分析存储；用户偏好和对话 Memory 另存。Agent 输出附数据时间、来源和适用边界；健康或潜水安全回答必须经过规则校验，并有保守拒答、人工或官方文档兜底。这是迁移设计，不是当前项目已上线能力。

### T02：ToC Agent 的高并发和成本怎样控制？

**口语化回答：**

### T03：运动 Agent 如何避免把健康数据当成诊断结论？

**口语化回答：**

> 我会先给结论：先限定产品边界：可以解释训练趋势、设备功能和官方训练建议，不能根据单次 HRV、心率或睡眠数据做医疗诊断，也不能替代潜水电脑的安全计算。数据进入模型前校验时间、设备、单位、质量和授权；回答保留来源和采样时间。

### T04：App 数据没有充分上云，怎样与 App 团队逐步迁移？

**口语化回答：**

### U01：怎样设计无人机智能调度 Agent 和动态重规划？

**口语化回答：**

> 我会先给结论：输入包括任务目标、区域和时间窗，设备能力、载荷、电量、健康状态、机巢、天气、空域/禁飞区、通信覆盖和优先级。LLM 把自然语言转成版本化 `MissionSpec`；约束引擎先做硬规则过滤，再由 CP-SAT/MILP、带时间窗 VRP 或领域启发式算法分配飞机、路线和时段；仿真/安全校验通过后，高风险任务再人工审批和下发。

### U02：飞行业务的 Context 与 Memory 怎样分层？

**口语化回答：**

> 我会先给结论：Telemetry/Event Log 保存不可变遥测、命令和事件；Current State Store 保存飞机、机巢、任务和空域的最新权威状态；Mission Working Memory 保存当前计划、约束、未完成项和 Artifact 引用；Operational Knowledge 保存 SOP、设备手册、故障知识和历史案例；长期偏好只保存经审核的业务偏好，不能覆盖法规和安全规则。

### U03：模型不可用、输出非法或调度冲突时怎样降级？

**口语化回答：**

> 我会先给结论：模型输出先过 Schema、范围、权限和安全规则校验；无法解析可有限重试结构化修复，仍失败就回退模板化任务创建或人工操作。模型超时不影响正在执行的飞控任务，系统继续使用最近一次已批准计划。

### U04：怎样评测无人机调度 Agent？

**口语化回答：**

## 5.1 货拉拉二面：基础八股、CodeWiki 增量与 Memory 治理

> 来源：[货拉拉二面复盘](./货拉拉-大数据平台开发工程师-二面面试整理与答案.md)。以下答案直接收录在总题库中；“现场题”表示转写明确出现，“修正版”是针对现场回答的可复述版本。团队的 Hadoop/Spark、Data Agent、语义层和评测平台是面试官当场透露的信息，不是候选人的项目经历。

### HL2-B01：二叉树是什么？

**现场题；修正版：**

> 二叉树由根节点和递归的左右子树组成，每个节点最多有两个子节点，分别是左孩子和右孩子，可以只有一个孩子或没有孩子。二叉搜索树还额外要求左右子树满足键值顺序，不能把一般二叉树和二叉搜索树混为一谈。

### HL2-B02：二叉树如何遍历？

**现场题；修正版：**

```text
preorder(node):
    if node == null: return
    visit(node); preorder(node.left); preorder(node.right)

inorder(node):
    if node == null: return
    inorder(node.left); visit(node); inorder(node.right)

postorder(node):
    if node == null: return
    postorder(node.left); postorder(node.right); visit(node)
```

> 三种递归遍历时间均为 O(n)，栈空间 O(h)；层序遍历用队列，时间 O(n)。树很深时可改显式栈。

### HL2-B03：B+树的结构和用途是什么？

**现场题；修正版：**

> B+树是多路平衡搜索树。内部节点保存有序分隔键和子指针，记录或记录指针集中在同层叶子节点，叶子按键排序并用链表相连。高扇出降低树高和磁盘随机 IO，叶子链适合范围查询；插入删除可能触发分裂、合并和父节点键调整。

### HL2-B04：进程和线程的区别是什么？

**现场题；修正版：**

> 进程是资源隔离和分配单位，拥有独立虚拟地址空间；线程是进程内的调度执行单位，共享进程的代码、堆和文件等资源，但各自有栈、程序计数器和寄存器上下文。进程隔离强、创建切换成本通常更高；线程共享方便但必须处理竞态和同步。线程能并发执行，不代表一定并行。

### HL2-B05：上下文切换保存什么？

**现场题；修正版：**

> 保存程序计数器、通用寄存器、栈指针、处理器状态/标志寄存器和内核调度所需的线程状态。页表、地址空间等主要属于进程上下文，不应说每次线程切换都完整切换页表；这些内容由 PCB/TCB 等内核结构管理。

### HL2-B06：Java 共享变量怎样保证同步？

**现场题；修正版：**

> 复合操作需要互斥时用 `synchronized` 或 `ReentrantLock`；需要超时、公平、可中断或多条件队列时用 `Lock/Condition`。单变量 CAS 更新可用原子类。`volatile` 保证可见性和有序性，不保证 `i++` 原子性；读多写少可考虑读写锁。生产代码还要说明锁范围、释放、死锁和线程安全集合。

### HL2-B07：线程池核心参数和执行顺序是什么？

**现场题；修正版：**

> 核心参数是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory` 和拒绝策略。任务到达时先创建核心线程；核心线程满后入队；队列满且未到最大线程数才创建非核心线程；队列仍满则执行拒绝策略。队列容量、任务是 CPU 还是 IO 密集、线程命名、监控、异常处理和优雅关闭都需要一起设计；无界队列可能使最大线程数失效并掩盖堆积。

### HL2-P01：CodeWiki 的业务价值是什么？

**现场题；修正版：**

> CodeWiki 面向老项目接手和跨模块维护，把静态代码事实、依赖关系、版本视图和源码引用沉淀为团队共享知识。强 Coding Agent 适合一次性探索，CodeWiki 在反复跨模块查询、团队复用、版本对照和可审计引用上提供增量价值，是否值得建设要用正确率、耗时、Token、索引成本和新鲜度做基线比较。

### HL2-P02：多语言 DSL 怎样定义？AST 和 LLM 各做什么？

**现场题；修正版：**

> DSL 是语言无关代码 IR。节点可包括仓库/版本、文件、类、函数、接口和配置，字段包含稳定 `symbol_id`、签名、限定名、文件行号、父节点和 `revision`；边包含 `calls/imports/inherits/implements/defines`、来源和置信度。Tree-sitter 和规则/类型分析负责把各语言 AST 映射到 IR，LLM 只基于 IR、调用链和源码证据生成解释，不负责把源代码“猜译”为 DSL。

### HL2-P03：为什么用 GraphRAG，图和向量怎样存？

**现场题；修正版：**

> 代码问题依赖调用、实现和模块关系，普通向量 RAG 容易返回孤立片段；GraphRAG 用确定关系扩展上下文，BM25/向量补充标识符和语义召回。节点和边必须绑定 `repo_id + revision`、源文件行号和置信度；向量记录绑定 `symbol_id/chunk_id + revision + content_hash`。查询先做权限和版本过滤，再混合召回、图扩展和引用校验。

### HL2-P04：代码变动后如何增量更新？

**现场题；修正版：**

> Git diff 只是变更线索。新 revision 重新解析受影响文件，通过稳定符号 ID 识别新增、删除、修改和重命名；再依据反向依赖计算 Dirty Set，重建受影响节点、边、文档 chunk 和向量，做引用/数量/问答回归。校验通过后原子切换当前 revision，失败保留旧版本回滚。类属性或公共类型变化也要使包含方法和相关调用方失效，不能只更新改动函数。

### HL2-P05：类属性新增或类型变化，向量是否更新？

**现场题；修正版：**

> 要先定位属性、包含类和引用它的符号，按规范化内容哈希判断类摘要和方法上下文是否变化；受影响的类级、函数级 chunk 和文档都加入 Dirty Set，重新嵌入并绑定新 revision。旧向量先标记不可检索，待新版本校验通过后切换，不能因为最小节点是函数就跳过属性引起的语义变化。

### HL2-M01：Memory 四层何时写入？

**现场题；修正版：**

> L0 先追加保存不可变原始对话和事件引用；L1 在用户明确要求记住、会话边界、重要事实检测或异步保底任务触发时抽取结构化事实；L2 在多个事实形成同一场景或任务结束时聚合；L3 只有稳定、可复用、无冲突且满足置信度的偏好才晋升。固定“每五条消息”和定时任务可以是当前实现的成本策略，但不是普适的记忆生命周期规则。

### HL2-M02：事实冲突怎样发现、更新和合并？

**现场题；修正版：**

> 先按 `subject/entity、attribute、scope、valid_time` 建立事实候选键，再用向量/BM25 召回可能相关条目；检索只找候选，不能单独证明冲突。新值明确替代旧值时标记 `supersedes`，互补信息做 merge，时间/作用域不清时保留 conflict 并追问。LLM 只提出动作，服务端按版本、权限、来源可信度和安全规则校验后写入，旧证据保留历史和引用。

### HL2-M03：检索哪些层，是否每轮都检索？

**现场题；修正版：**

> 主要检索 L1 结构化事实，按需扩展 L2 场景；L0 用于证据回溯，L3 作为低频画像条件。每轮无条件检索会增加延迟，应做意图门控、Token/数量预算、权限过滤并记录 Retrieval Trace；与历史无关的问题可以跳过或只取极少量画像。

### HL2-M04：Memory 如何集成到应用？

**现场题；修正版：**

> 当前是本地单用户组件，通过 Hook 在模型调用前 Recall、回合结束后 Capture；不是已完成的共享多租户服务。通用 Gateway 可以提供 `recall(query, scope, as_of, budget)`、`capture(events, idempotency_key)`、`delete` 和 `health`，返回 `memory_id/source_ref/revision/confidence`。若未来做 HTTP/MCP 网关，还需补租户、权限、审计、重试、删除传播和故障降级。

### HL2-H01：最近在学习什么？

**现场题；修正版：**

> 最近重点学习 Data Agent 工程化，包括语义层/指标口径、NL2SQL 安全校验、数据血缘、评测集、可观测性和失败回放。流程是把 schema、权限和业务定义结构化，模型生成候选 SQL 或解释，经过 AST/只读权限/数值对账和固定样本回归。Three.js 是个人练习，不作为生产平台经验。

## 6. Java、React 与 Web 框架正确答案

### J01：箭头函数 `this`、Hooks 与类组件

**口语化回答：**

> 我会先给结论：箭头函数没有自己的 `this`，在定义位置词法捕获外层 `this`，`call/apply/bind` 不能改变它。React 函数组件没有实例 `this`；类组件事件处理常用箭头函数避免绑定丢失。


`useEffect` 不是生命周期方法的一一替代：无依赖数组时每次提交后执行，空数组通常在挂载后执行并在卸载时 cleanup，带依赖时在依赖变化后 cleanup 再执行。`useLayoutEffect` 在浏览器绘制前同步执行；常用 Hook 还包括 `useState/useReducer/useMemo/useCallback/useRef/useContext`。

### J02：`@Autowired` 与 `@Resource`

**口语化回答：**

> 我会先给结论：`@Autowired` 是 Spring 注解，默认按类型解析，可配 `@Qualifier`，底层由 BeanPostProcessor 处理；`@Resource` 是 Jakarta/JSR 注解，通常先按名称再按类型，Spring 同样负责注入。现代代码优先构造器注入：依赖显式、便于测试、支持不可变字段，也能更早暴露循环依赖。不要把二者差异简化成“一个按类型、一个只按名称”。


### J03：`ThreadLocal`、并发 Map、可重入锁与 AQS

**口语化回答：**

> 我会先给结论：`ThreadLocal` 为同一线程保存上下文副本，常用于 Trace/事务上下文；线程池中必须在 `finally` 里 `remove()`，否则会串数据和泄漏。`HashMap` 非线程安全；Java 8 `ConcurrentHashMap` 读操作多为无锁，写入使用 CAS、桶头 `synchronized`，扩容可协助迁移，不允许 null。


可重入表示同一线程持锁时可再次获取并用计数释放；不可重入会自我死锁。`ReentrantLock` 基于 AQS：AQS 用 `state`、CAS 和 CLH 风格等待队列管理竞争，Lock 再提供公平/非公平、可中断和 Condition。

### J04：MyBatis-Plus Lambda 统计题

**口语化回答：**

> 我会先说结论：这类统计应让数据库完成 COUNT，代码只负责构造类型安全的查询。

```java
long count = studentMapper.selectCount(
    Wrappers.<Student>lambdaQuery()
        .gt(Student::getAge, 20)
        .eq(Student::getGender, Gender.MALE)
);
```

枚举/数据库实际字段值按项目调整。Lambda Wrapper 的优势是字段重构安全；`COUNT(*)` 应由数据库执行，不要先查列表再在 Java 里计数。

### J05：事务传播、幂等和分布式事务

**口语化回答：**

> 我会先给结论：Spring 常见传播中，`REQUIRED` 加入或新建事务，`REQUIRES_NEW` 挂起外层并新建，`NESTED` 在支持时使用 Savepoint；`SUPPORTS/MANDATORY/NOT_SUPPORTED/NEVER` 分别表示支持、强制、挂起、禁止事务。注意同类自调用可能绕过代理，异常被吞也可能导致不回滚。


幂等靠业务幂等键、唯一约束、状态机/版本号和结果复用，不是只靠 Redis 锁。分布式事务按场景选本地事务 + Outbox/Inbox、Saga/TCC 或少量强一致 2PC；银行扣款等强约束要明确账本和补偿边界，不能把“最终一致”说成“完全不会短暂不一致”。

### J06：Minor/Full GC 与 JDK 17/21

**口语化回答：**

> 我会先给结论：Minor/Young GC 主要回收年轻代，通常较频繁、停顿较短；Full GC 涉及整个堆并常伴随类卸载/压缩，代价更高，触发和行为取决于收集器。排查应看 GC Log、分配速率、晋升、老年代占用、停顿和堆转储，不能只背触发条件。


若生产仍是 JDK 8，就如实说。JDK 17 的 record、sealed class 和模式匹配改善领域建模；JDK 21 的虚拟线程适合大量阻塞 I/O，但要评估 pinning、连接池、ThreadLocal、监控和框架兼容。升级先做依赖盘点、回归和性能基线，不是只换语法。

### F01：Django、FastAPI、Express/Koa、Spring Boot 如何比较？

**口语化回答：**

> 我会先给结论：统一按定位、默认能力、并发模型、生态、类型与运维比较：Django 是 batteries-included；FastAPI 是类型提示驱动的 ASGI API 框架；Express 是极简 middleware/router；Koa 是更小的 async 洋葱内核；Spring Boot 是带 IoC、自动配置、Actuator 和完整企业生态的 opinionated platform。


选型看团队语言、领域复杂度、依赖生态、类型安全、延迟模型和维护周期。不能用“用户少选 Python、用户多就重写 Java”作通用结论，性能瓶颈通常先在数据库、网络和业务设计。

### F02：约定优于配置与异常处理

**口语化回答：**

> 我会先给结论：约定减少重复决策、让 Starter 和标准目录快速落地；代价是隐式装配和配置来源变多，偏离默认假设时排障困难。应提供合理默认、显式覆盖、类型化配置、启动校验、Condition Report 和生效配置可观测性。


每处都 `try/catch` 再包装 `AppException` 是反模式，会丢语义、重复日志和破坏堆栈。只在能够恢复、补充领域语义或跨边界转换时捕获；保留 cause，在 Controller/Consumer 等责任边界统一映射错误码并记录一次日志。

### F03：从零设计 Web 框架与编译期 DI

**口语化回答：**

> 我会先给结论：先限定目标，再设计小内核：Router、Request/Response、Middleware、类型化校验/序列化、模块与 DI、生命周期、配置、错误边界、日志/Metrics/Trace、健康检查、测试 Harness 和插件 SPI。数据库、认证、缓存和 MQ 作为标准扩展，不硬编码进内核。


DI 采用构造器注入和构建期生成。模块显式声明 Provider、依赖类型和 Scope；编译插件形成依赖 DAG，检查缺失/重复绑定、循环依赖和 Scope 泄漏，失败即中止构建，再生成工厂代码和 manifest。`Provider<T>/Lazy<T>` 只延迟实例化，不能用来掩盖缺失依赖。

## 7. Agent Runtime、模型路由与 AI Coding 正确答案

### A01：Prompt Engineering、Harness 和 Loop Engineer

**口语化回答：**

> 我会先给结论：Prompt Engineering 不只是写一句指令，而是明确角色、输入/输出 Schema、可用工具、证据边界、失败/拒答条件和 few-shot，并用版本化评测集验证。Harness 是围绕模型的执行外壳：循环、工具、状态、预算、权限、观测、恢复和评测。Loop 是“模型决策 -> 工具执行 -> 结果回填 -> 再决策”直到终止条件，不应无限运行。


Hermes 更常指具体模型/Agent 项目或协议实现，Harness 是系统层概念；比较前先确认面试官所指版本，不能只凭名字判断功能。

### A02：LangGraph 和 State 怎么设计？

**口语化回答：**

> 我会先给结论：LangGraph 适合需要显式状态、分支、循环、Checkpoint、人工介入和恢复的 Agent 工作流。State 只保存跨节点需要的最小事实，如 `messages、task、plan、tool_results/ref、attempt、status、error`；大对象外置为 Artifact Ref，Reducer 明确定义追加、覆盖和幂等合并。


项目没实际用过就说“了解并能说明适用边界”，不要把自研调度器包装成 LangGraph。简单线性调用不需要为了框架而上图。

### A03：LLM -> Workflow -> Agent、Skill 与 Vibe Coding 趋势

**口语化回答：**

> 我会先给结论：演进不是单向替代：LLM 提供生成能力，Workflow 保证确定流程，Agent 负责动态决策，Harness 把它变成可治理运行时，Skill 把领域过程知识按需交给 Agent。下一阶段重点会从“会调用模型”转向上下文工程、评测、权限、状态恢复、工具生态和人机协作。


Vibe Coding 可以快速生成脚手架、CRUD、测试草稿和局部组件，但人仍负责规格、架构、不变量、Review、调试和验收。AI 代码占比是 **[待本人确认]**，最好用一个真实 Commit 说明输入、修改和验证，不用百分比证明能力。

### A04：多模型 Gateway 和 100ms/500ms 路由设计

**口语化回答：**

> 我会先给结论：请求先做任务分类和合规过滤，再从本地/内存中的模型能力表筛出候选，用延迟、成本、离线质量、实时健康和策略权重在 100ms 内决策；数据面异步写审计事件，不在主路径查慢数据库。


500ms Failover 依赖短连接/首 Token 超时、熔断器、预热备用、幂等请求 ID 和可重放请求。质量未知时靠离线基线、在线显式/隐式反馈、少量探索和 Shadow 流量更新先验；模型抖动用滑动窗口、趋势/错误率、降权缓冲、半开探测恢复。每次审计保存策略版本、候选集、特征快照、选择原因、Fallback 和结果。具体使用模型、账号和网关是 **[待本人确认]**。

### A05：Coding Agent 如何编辑文件，Tool 参数怎么设计？

**口语化回答：**

> 我会先给结论：Agent 先读取文件和版本/Hash，模型生成结构化 Tool Call，工具在工作区执行 patch，再返回 diff、诊断和测试结果；模型根据结果继续修正。工具本身受路径 Scope、权限、大小、并发版本和沙箱约束，不能让模型直接任意写磁盘。


编辑工具至少需要 `path、expected_hash/version、patch或range+replacement`，并支持 dry-run；返回 `applied、new_hash、diff、diagnostics`。跨文件变更需要原子计划或逐文件可恢复日志，冲突时拒绝覆盖并重新读取。

### A06：三个项目的延迟怎么答？

**口语化回答：**

> 我会先给结论：周报是离线批处理，优先完整性、可恢复和总完成时间；CodeWiki 把扫描建图放离线，在线限制 Seed、跳数、Chunk 和 Token；Memory 把抽取聚合放后台，Recall 限 K、设超时并可降级。不同系统不能共用一个“P95 越低越好”的答案。


实时眼镜等场景要做流式 ASR、端侧 VAD/轻量特征、云端增量推理、取消过时请求、短建议先出和后台丰富结果；这是场景设计，不是三个现有项目的投产能力。

## 8. 互动小说记忆系统正确答案

### S01：Coding Agent Memory 如何迁移到多角色互动小说？

**口语化回答：**

> 我会先给结论：把 `WorldState` 客观真相、不可变 `EventLog`、各角色 `CharacterBelief`、稳定 Profile/Relationship 和当前 `StoryState` 分开。角色可以相信错误信息，WorldState 仍保持真实；角色不在场的事件不能自动进入其 Belief。


### S02：如何召回而不泄漏世界信息？

**口语化回答：**

> 我会先给结论：先按 `story_id、timeline_id、scene_id、speaker_id` 做数据层权限过滤，再在可见集合内按近期性、语义、实体关系、目标、情绪和因果距离排序。禁止先全局召回再只靠 Prompt 要求模型保密；生成后还要做 claim-to-memory 检查。


### S03：新人物或地点怎样入图？

**口语化回答：**

> 我会先给结论：生成文本先转为 proposal，不直接写 canonical world。依次做实体消歧、Schema/规则校验、时间线与事实一致性检查，合法后才分配 ID、提交 EventLog，并按可见性更新相关角色 Belief；retcon 必须显式创建版本或新 timeline。


### S04：玩家不推进时，开放世界怎样继续？

**口语化回答：**

> 我会先给结论：用 World Tick/Narrative Director 维护角色目标、资源、未解决钩子、前置条件、冷却和 tension curve。规则/规划器生成候选事件并评分，LLM 只负责表现文本。即“状态机决定发生什么，模型决定怎样讲”。


### S05：如何评测互动叙事记忆？

**口语化回答：**

> 我会先给结论：正确性看角色知情泄漏率、世界事实/时间线冲突率、Persona 一致性、事件实体 Recall@K、新实体重复/误合并、纠错残留、200/500 轮后的延迟和成本；体验另看剧情推进率、重复情节、选择影响度、留存和主观评分。安全与泄漏指标不能用满意度替代。


## 9. Ownership、协作与 HR 正确答案

### H01：自我介绍怎么答？

**口语化回答：**

> 我会先给结论：用 60-90 秒讲“身份与主栈 -> 三个项目各一句业务问题/链路/结果 -> 为什么匹配岗位”。身份统一说“任职于招银网络科技有限公司，服务招商银行相关应用”，除非劳动合同主体能证明，否则不说自己是招商银行信息技术部员工。


英文版本同样用 Background -> Three projects -> Fit，不追求复杂词汇。完整英文材料见 [英文面试目录](../问题/05-英文面试/README.md)。

### H02：“独立负责”与团队角色怎么答？

**口语化回答：**

> 我会先给结论：按项目逐阶段列 RACI：需求澄清、架构、核心实现、前端、测试、发布和运营分别谁 Responsible/Accountable/Consulted/Informed。结论可以是“我对技术主线端到端负责，但产品决策、测试、平台和发布由相应同事共同完成”，前提是事实支持。


团队人数、项目周期、用户量、本人是否带人、前端是否由同事协助均为 **[待本人确认]**，不能套用统一数字。

### H03：交付、估时、延期和技术分歧怎么答？

**口语化回答：**

> 我会先给结论：先把需求拆成可验收工作包，明确依赖、风险和 Definition of Done；估时用历史相似项、三点估算和关键路径，并把不确定性写进区间。用看板、里程碑、燃尽/剩余工作和风险清单跟踪，发现关键路径滑动、阻塞老化或范围增长就提前预警。


有分歧时先对齐约束和评价维度，用 PoC/数据比较，Owner 按事先约定的决策权拍板并写 ADR。多个紧急需求则按业务影响和时限重排，优先砍范围/分期，不通过无限加班掩盖资源冲突。真实例子必须换成本人 STAR。

### H04：求职动机、离职原因和发展路径怎么答？

**口语化回答：**

> 我会先给结论：回答结构是“为什么这个业务 -> 现有能力怎样迁移 -> 还要补什么”，并引用面试当天核验的公司信息。离职只讲正向方向：希望 AI 应用成为正式业务目标，持续接触用户、评测和产品闭环；不贬低现公司，也不编造内部转岗受阻。


发展路径可说短期交付一个可验证场景，中期独立负责模块/方向，长期成长为 AI 应用架构负责人。公司名称、岗位、业务变化后必须重写，不能跨公司复用动机。

### H05：薪资、住址、离职和入职时间怎么答？

**口语化回答：**

> 我会先给结论：全部为 **[待本人确认]**。薪资先统一月薪/年包、固定/浮动和税前口径，再给基于岗位范围与市场的区间；住址只说通勤相关的必要范围；入职时间按当前交接要求给可兑现日期，不沿用旧复盘日期。


### H06：金融信息渠道和海外社媒可信度怎么答？

**口语化回答：**

> 我会先给结论：只列实际长期使用的渠道和频率。正式事实优先回到公司公告、交易所/监管 Filing、财报和权威数据源；研报和新闻用于分析，Twitter/X 等社媒只作为线索并做交叉核验。没用过 Bloomberg/Wind 就直说，不用堆平台名冒充金融能力。个人投资习惯同样按真实情况回答。


### H07：越界私人问题和第三方数据合规怎么答？

**口语化回答：**

> 我会先给结论：与岗位无关的情感、家庭、征信等问题可以礼貌设界：“这部分比较私人，我可以说明与履职直接相关的稳定性、入职和合规信息。”不要为了推进面试无限暴露隐私。


第三方聊天截图、语音和微表情涉及非用户本人的个人信息，必须明确知情同意、用途限制、最小化、保留期、访问审计和删除权。智能眼镜“让对方不知道被分析”是严重合规和伦理风险，不能只讨论技术可行性。

### H08：哪些事实绝不能由答案库代填？

**口语化回答：**

> 我会先给结论：以下统一标记 **[待本人确认]**：项目日期与重叠关系、真实数据源数量/数据量、团队规模、RACI、用户量、QPS/P95/SLA、部署/CI/CD、当前模型与账号渠道、项目采用状态、事故、AI 代码占比、当前薪资、Offer 和入职日期。模板只能帮你组织事实，不能把未知变成经历。
