## 二、技术面问题清单 + 参考答案

### 【项目一】AI 周报系统

**面试官问**:
- 是不是做了数据收集清洗？从人工到多个运营系统取数，改成程序采集，再由大模型分析？
- 数据分析是大模型做的吗？大模型只负责生成最终展示内容？

**面试官判断**:这个项目相对简单,快速带过了。("那我就没有问题了")

**参考答案(定位这个项目的话术)**:
> 这个项目不是统计员工 Git、Jira 或 CI 进度的工作周报，而是公司内部的**网联运营保障周报**。原来每周需要人工从多个运营和日志系统取错误日志、大事务、慢 SQL、失败交易、TPS、响应时间等数据，再做核对、分析和组装。
>
> 我把它改成了一条日终批处理链路：程序按业务日期调用内部接口或执行预先写好的 SQL，把数据写入对应表；等上一周七天的数据状态都完整后，再按模块做确定性统计。LLM 不自由写 SQL，也不负责计算数字，只对已经算好的结构化结果做分段异常解读、趋势归纳和文字组织。最后系统按固定模板组装成表格加文本，通过内部消息接口推送。
>
> 所以我的分工原则是：**取数、完整性和数字由程序负责，模型只负责有依据的解读和表达**。当前也没有把自然语言追问或 Text-to-SQL 包装成已经上线的能力；如果以后要做，那是独立的下一版设计。

> 💡 加分点:主动点出"不让 LLM 算数、只让它做表达"——这正是面试官想听的"知道 LLM 边界"的意识。

### 【项目二】GraphRAG 代码生成平台(重点被追问)

#### Q1:讲一下 GraphRAG 在代码生成平台里的流程

**参考答案**:
> 整体分四步:**离线建图 → 多路找 Seed → 受限扩图 → 证据装包**。
> 1. **离线建图**:用 tree-sitter 提取类、函数、方法、接口、路由等符号，归一成节点和关系边；每个符号生成一个带精确文件、行范围的 Source Chunk。向量是可选索引，不是系统地基。
> 2. **在线找 Seed**:先查节点 FTS、符号名和路径，同时查源码 Chunk FTS；配置了 Embedding 才追加 Vector Search。Chunk 命中会合并回所属节点，所以不能说第一入口只有向量。
> 3. **受限扩图**:从 Seed 找调用方、被调用方、所属模块等关联，受最大跳数和节点数限制。定义和行范围来自 AST，跨文件 Calls/References 则是启发式解析，会保留 confidence 和 provenance，不能说百分百不漏。
> 4. **证据装包**:候选 Chunk 按语义、关键词、图距离、节点重要度和新鲜度排序，在数量和近似 Token Budget 内装包，再追加相关社区和图事实给模型。

#### Q2:chunk 怎么切分?函数级吗?

**参考答案**:
> 当前是**符号级** Chunk，Class、Function、Method、Schema、Endpoint 等一个符号对应一个精确源码范围。函数是最常见的一类，但不是唯一类型。当前**没有对超大函数做二次切分**；如果单个 Chunk 超过 Context Budget，可能被跳过，这是现有边界。

#### Q3:节点和边怎么设计?(节点是函数,边是什么)

**参考答案**:
> - **节点**:不只函数，还包括仓库、目录、文件、类、方法、Endpoint、Schema 等，节点带文件、行范围、签名和注释等元数据。
> - **边**:包括 contains、defines、imports、exports、calls、references、inherits、implements、routes_to、uses_config 等，带方向、类型、confidence、is_inferred 和 provenance。
> - **可信边界**:Contains、Defines 这类结构关系相对确定；跨文件 Calls/References 依赖名称、同文件和 Import Scope 等启发式解析，遇到歧义会保守放弃建边。因此图能补结构上下文，但不能包装成编译器级精确调用图。

#### Q4:同一个大函数被切成两个节点,边怎么定义?(面试官特意追问)

**参考答案(先纠正前提，再讲方案)**:
> 这个前提和当前实现不一致。**现在一个符号对应一个 Source Chunk，没有把大函数切成两个 Chunk，所以也没有 Intra-function Sequential Edge 或共享 Parent Chunk ID。** 当前风险反而是超大函数可能因为超过预算被跳过。
>
> 如果下一版要解决，我会给切片保留 `parent_symbol_id + ordinal + line_range`，命中一段时带回相邻段。顺序关系先放 Chunk Metadata，不急着污染代码语义图；是否需要建 Sequential Edge，要由检索评测决定。面试时要把这段明确说成演进方案，不是当前实现。

#### Q5:检索到代码后,按什么优先级组装上下文?(面试官反复追问,这题答得不够好)

**面试官的关键提示**:"prompt 排在前面和最后面的信息特别重要,你怎么排这个优先级?"
**你当时的回答**:只按相关性排序 → 面试官明显觉得不够。

**参考答案(当前实现 + 改进方向)**:
> 当前先做**五因子线性排序**：语义命中、关键词命中、图距离、节点重要度和源码新鲜度，然后按得分顺序在最多 Chunk 数和近似 Token Budget 内装包。没有向量时语义项为 0，FTS、符号和图仍能工作。
>
> 我会主动说明：**当前还没有实现 Lost in the Middle 的头尾双端布局**，Context Pack 也是按 Source Chunks、Community Summaries、Community Relationships、Graph Facts 的结构顺序追加。下一版我会用同一批代码问题对比降序、头尾双端和按证据类型分区，观察引用正确率和答案完整度，再决定是否上线，不能把一个合理想法说成已实现。

### 【项目三】上下文压缩 / 长期记忆系统(被追问最深)

#### Q1:是你一个人做的吗?

坦诚说明独立负责 / 主导的部分即可。

#### Q2:四层设计分别是什么?(L0/L1/L2/L3)

**参考答案(基于当前实现)**:
> 我把记忆分成四层,从"原始"到"抽象":
> - **L0 — 原始对话证据层**:保存清理掉框架注入噪声后的用户和助手消息、消息 ID、会话和时间信息，作为审计和原话检索依据。
> - **L1 — 原子记忆层**:只抽取 `persona / episodic / instruction` 三类结构化记忆，可检索、去重和更新；它不是会话摘要。
> - **L2 — 场景层**:把相关 L1 按工作、项目、偏好等主题组织成 Scene Markdown，提供主题上下文和导航。
> - **L3 — 长期画像层**:生成紧凑的 `persona.md`，沉淀相对稳定的身份、偏好、能力和长期协作方式。
> 越往上越聚合，但各层不是简单的“摘要逐级晋升”：L1 是原子事实，L2 是场景组织，L3 是 Persona 生成。

#### Q3:记忆系统是跨会话的吗?

**参考答案**:核心目标是跨会话记忆。同一用户的 L0 证据会产生可跨 Session 检索的 L1 记忆，并进一步组织成 L2 场景和 L3 Persona。当前已有用户路由字段，但不能把它夸成已经完成企业级多租户身份和授权治理。

#### Q4:什么时候存?怎么存?

**参考答案**:
> 分两个时机:
> - **实时/增量存**:会话进行中,L0 原始记录实时落库。
> - **后台分节奏处理**:L1 按增量消息做原子记忆抽取；L2 在 L1 完成后按调度窗口聚合场景；L3 根据新增记忆阈值、冷启动或修复等条件更新 Persona。三层节奏不同，重处理不放在用户响应主链路。

#### Q5:存的时候出现事实冲突 / 反事实怎么办?(比如今天说叫 A,明天说叫 B)

**你当时的回答**:用覆盖策略。
**面试官追问**:所以是覆盖,不是纠错?

**参考答案(当前能力和缺口分开讲)**:
> 当前不是一个固定的“同字段直接覆盖”状态机。新 L1 入库前，先用 Vector，失败时退 FTS，召回相似旧记忆，再让 LLM 在 `store / skip / update / merge` 四个动作里判断。`update/merge` 会替换在线 Store 的当前记录，L1 JSONL 保留追加历史，便于审计。
>
> 真实缺口是：目前没有完整的实体-属性 Schema，也没有“可变属性自动覆盖、不可变属性自动标冲突”的确定性规则，更没有事实置信度字段。下一版才会先识别实体、属性和作用域，区分可变状态与稳定属性；判断不了时并存并降权，而不是让模型盲目覆盖。

#### Q6:大模型抽取判断错误(幻觉)怎么办?怎么保证长期记忆准确?(核心追问)

**参考答案(这是长期记忆系统的命门,要重点答)**:
> 当前已经做了三件事：只从本批新增消息抽取；L1 记录保存 `source_message_ids`，能回到 L0 找来源消息；入库前用相似候选加 LLM 四动作判断做去重和更新。
>
> 但我要主动讲边界：`source_message_ids` 还没有逐条做“ID 一定存在 + 内容一定被原文蕴含”的硬校验，所以不能说成逐字 span 校验；L1 的 `priority` 是重要程度，Offload 的 `score` 是摘要可替代程度，都不是事实置信度。当前也没有低置信候选区、按出现频次自动晋升 L3 或隐式反馈闭环。
>
> 下一版我会补来源 ID 校验和 Claim-Evidence 蕴含检查，再单独建 evidence confidence、冲突状态和纠错事件。这样回答比把规划包装成“五层防护”更经得起源码追问。

#### Q7:怎么取?什么时候加载 L0/L1/L2/L3?

**参考答案**:
> 当前自动注入分两块：稳定的 **L3 Persona 正文 + 完整 Scene Navigation** 放在 system prompt 后缀；与本轮 query 相关的少量 **L1 原子记忆**放在 user prompt 前缀，默认最多 5 条。
>
> **L2 场景正文不是每轮全量常驻**，Agent 根据 Scene Navigation 按需读取；L0 原文也不自动灌入，需要核对原话或争议证据时，再调用会话搜索下钻。简单说就是：稳定画像和目录常驻、相关事实稀疏注入、场景正文和原话按需查。

## 五、复盘:本场答得好 / 需改进

### 答得到位
- 周报系统"LLM 只做生成不做统计"的边界意识。
- GraphRAG 基本流程、函数级切分讲清楚了。
- 记忆分层设计整体清晰。

### 明显需要改进(下次务必补上)
1. **上下文组装优先级**——要讲清当前五因子排序和预算装包；Lost in the Middle 的头尾布局只能作为待评测方案，不能补成当前事实。
2. **大函数切分的边**——先纠正前提：当前没有二次切分和 Sequential Edge；`parent_symbol_id + ordinal` 是下一版方案。
3. **事实冲突**——当前是候选召回 + LLM 判断 `store/skip/update/merge`；实体属性状态机和事实置信度是待补能力。
4. **幻觉约束长期记忆**——当前有 `source_message_ids` 和原始记录可追溯，但没有严格 span/蕴含校验、候选区或自动晋升，面试必须讲清边界。
5. **工程侧(部署/CICD/并发/API 池)**——别一问就卡,准备好具体数字和流程。

### 这场面试的定位启示
- George 是**算法工程师**,问得非常偏"应用层算法工程"(RAG 图设计、记忆治理、幻觉),不是纯后端。你要把自己的项目**往"AI 应用工程"叙事上靠**,而不是"后端叙事"。
- 公司核心痛点是**幻觉治理**,你的记忆系统里"幻觉约束"那套答案正好戳中他们的痛点——面试和后续都要强调这块。
