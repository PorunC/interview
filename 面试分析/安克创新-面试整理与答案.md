## 二、技术问题清单 + 参考答案

### 【项目一】AI Agent 长期记忆 + 上下文压缩系统

#### Q1:长期记忆和上下文压缩是 for 你们内部自研 agent runtime,还是基于已有 runtime 二开?

**参考答案**:
> 是基于已有 runtime 二开。我们没有从零造 agent runtime,而是在现有 runtime(如 Copilot 的 agent 链路)之上,把**记忆层和上下文压缩层**作为独立模块接入。原因:runtime 本身的调度、工具调用、流式输出这些造轮子性价比低;我们的差异化价值在**记忆治理和上下文管理**这块,集中精力做深。

#### Q2:Copilot 自己就有上下文压缩,你们的压缩和它有什么区别?(被追问)

**参考答案**:
> Copilot 的压缩是**通用的、被动的、黑盒的**——它对超长上下文做截断/摘要,但不理解业务语义,也无法定制。我们做的是**可定制、分层的主动压缩**:
> - **分层压缩**:不是一刀切摘要,而是分 L0~L3(原始/会话摘要/结构化事实/长期画像),不同层不同压缩策略、不同保留优先级。
> - **业务感知**:哪些信息该留、哪些可丢,可以按业务场景配置(比如代码 agent 保留函数签名和依赖,丢掉闲聊)。
> - **可控可观测**:压缩了什么、丢了什么可追溯,而不是 Copilot 黑盒一截了之。
> 简单说:Copilot 的压缩是"被动省 token",我们的是"主动管理记忆质量"。

#### Q3:现在还用千问吗?(确认当前模型)

如实回答当前用的模型(千问 / DeepSeek / 其他)。

#### Q4:对接 DeepSeek V4 Pro 的上下文压缩,策略怎么设计?到多少 k 做压缩?怎么设计?

**参考答案(分阈值 + 分层触发)**:
> 不是无脑到某个阈值才压,而是**多触发点 + 分层**:
> 1. **阈值触发**:设定上下文用到模型窗口的一定比例(比如 DeepSeek V4 Pro 128k 窗口,用到 ~80% 即 ~100k 时)启动压缩,留出余量避免溢出。这个阈值不是固定值,要结合单轮增量预留动态算。
> 2. **轮次触发**:每 N 轮对话做一次轻量摘要增量更新,避免堆积。
> 3. **分层处理**:
>    - 近期上下文(最近 K 轮)**原样保留**(模型对近期信息注意力高,不该压)。
>    - 中期上下文做**摘要压缩**(L1)。
>    - 远期上下文抽**结构化事实**(L2)和**画像**(L3)。
> 4. **保留锚点**:压缩时保留关键实体/函数签名/决策点作为"锚点",便于回溯到 L0。
> 核心思路:**近期不压、中期摘要、远期蒸馏**,按时间衰减决定压缩力度。

### 【项目二】CodeWiki(GraphRAG / AST 代码图谱)—— 本场被挑战最狠

#### Q5:这其实就是做了个语法树(AST)解析吧?跟 Claude Code 插件的 MCP(Go/Python 等语法解析)有什么区别?

**面试官的潜台词**:这东西现成的都有,你做的有啥不一样?

**参考答案(要从"解析"升级到"图谱语义")**:
> 表面都是语法解析,但区别在**输出的结构和使用方式**:
> - 现成 MCP/插件做的是**单文件/单语言的语法解析**,给模型提供"这个文件的符号表/定义位置",本质是**定位工具**。
> - 我们做的是**跨文件、跨模块的代码知识图谱**:不只解析单个文件,而是把整个仓库的**函数调用关系、模块依赖关系、数据流**建成一张图(GraphRAG)。模型检索时不是"找一个定义",而是"找到一段代码 + 它的所有上下游依赖",把**完整的调用链上下文**一次性补全。
> 价值差异:模型改一个函数时,现成工具可能只给函数本体,我们能把"谁调用它、它调用谁、共享什么数据结构"一起喂进去,改起来不会漏掉调用方。**单点解析 vs 全局图谱**,这是核心区别。

#### Q6:这个图谱是给人用的吗?具体起什么作用?

**参考答案**:
> 主要给**模型/agent 用**(RAG 检索底座),也附带给人看(可视化依赖关系)。核心作用:当代码 agent 需要理解或修改跨模块代码时,用图谱做检索,把相关上下文(不止相似代码,还有依赖代码)喂给模型,提升跨模块理解的准确率。

#### Q7(杀手锏问题):我直接用 Claude Code 对仓库做 init,生成一个 markdown 长期记忆,跟你这个 GraphRAG MCP 区别多大?模型自己抓重点做长期记忆,是不是比做成 GraphRAG MCP 给模型更优?

**这是全场最难的问题,Dennis 直接表达"我理解模型自己抓重点做长期记忆可能更优"。你必须有力反驳,否则 CodeWiki 的价值就塌了。**

**参考答案(核心:确定性 vs 概率性、可更新 vs 一次性、结构化 vs 自由文本)**:
> 这两种是不同思路,各有场景,但做成 GraphRAG 有几个 Claude Code init 替代不了的优势:
>
> 1. **确定性 vs 概率性**:Claude Code init 让模型自己读仓库、自己总结重点存成 markdown——这是**概率性**的,模型可能漏掉关键依赖、可能总结错。GraphRAG 基于 **AST 静态解析**,调用关系、依赖关系是**确定性、精确**的,不会漏调、不会幻觉。代码这种"错一个调用链就跑不通"的场景,精确性比模型的"聪明总结"更重要。
>
> 2. **增量更新 vs 全量重扫**:仓库每天在变,Claude Code 的 markdown 记忆**怎么增量更新**?要么过期失效,要么重新 init 全扫(成本高)。GraphRAG 的图可以**基于 git diff 增量更新**只变动节点,维护成本低、始终新鲜。
>
> 3. **检索精度**:markdown 是自由文本,模型从一大段文本里"自己找"相关部分,召回靠语义相似度,容易漏。GraphRAG 是**结构化检索**,按图结构精确扩展(调用它的、它调用的),召回准、可解释。
>
> 4. **规模**:大仓库(几十万行)Claude Code init 一次性扫成本极高,且 markdown 膨胀后检索质量下降;GraphRAG 离线建图、在线按需检索,规模可扩展。
>
> **公平地说**:Claude Code init 适合**小仓库、快速上手、不需要精确依赖**的场景;GraphRAG 适合**大仓库、跨模块、需要精确依赖关系**的工程化场景。两者不是替代关系,是分层互补。

> 💡 这题答不好 CodeWiki 直接被判"没价值"。核心论点就一句:**代码的调用关系是确定性的,该用确定性方法(AST 图)而不是概率性方法(模型总结)来保证精确。**

#### Q8(承上,可能追问):那如果模型够强,以后能自己扫准了,GraphRAG 还有意义吗?

**参考答案**:
> 即使模型再强,两个根本约束不变:① **成本**——每次重新扫描大仓库的 token 成本远高于查一次图;② **确定性**——工程场景里"可能对"和"一定对"是两种东西,生产级代码理解要的是后者。GraphRAG 把确定性的部分交给工程,把需要语义理解的部分交给模型,是更稳的分工。

### 【项目三】AI 周报系统 —— 被挑战"没大模型也能做" + "做不了根因分析"

#### Q9:没大模型,我配固定模板 + 自动采集 pipeline 也能做吧?

**参考答案(承认 + 补差异)**:
> 纯数据采集 + 模板填充确实能做出基础周报,**大模型不是必需的**。但加大模型的价值在两点:
> 1. **自然语言交互**:周报推出来后,老板/员工能直接用自然语言追问("这周 A 模块提交为什么少了"),不用再去翻系统——这是固定模板做不到的。
> 2. **数据解读**:固定模板只能列数字,大模型能把数字组织成有重点的叙述(哪些是亮点、哪些是异常),降低阅读成本。
> 但要诚实说:**如果只需要定时推数字周报,确实不需要大模型**,大模型的价值在交互和解读层。

#### Q10:大模型介入后,推送的周报模板变了吗?

**参考答案**:模板结构没变(还是固定板块),变的是**内容生成方式**——数字仍由脚本统计(保证准),文字描述和重点提炼由大模型生成。模板一致是为了用户习惯稳定,大模型只填充内容。

#### Q11:做成自动化?定时采集 + 生成 + 推送?

确认:是,每周定时触发,自动采集→生成→推送。

#### Q12:大模型写 SQL,如果它写了 DROP/DELETE 把表删了,怎么拦截?

**参考答案(多层防护)**:
> 1. **SQL 权限隔离**:给大模型的数据库连接用**只读账号**,DDL/DML(删改)语句在数据库层直接拒绝——这是最硬的兜底。
> 2. **SQL 预校验**:执行前用 SQL parser 解析,白名单只允许 SELECT,出现 DROP/DELETE/UPDATE/ALTER 直接拦截。
> 3. **关键词黑名单**:对生成 SQL 做关键词检查。
> 4. **沙箱库**:复杂场景下查的是只读副本或脱敏副本,动不到生产。
> 核心原则:**永远不信任模型生成的 SQL 直接打生产,权限 + 解析双保险。**

#### Q13:怎么把表名和表描述精确给到模型?(模型得知道有哪些表才能查)

**参考答案**:
> 维护一份**表元数据(schema 字典)**:每张表的表名、字段、字段含义、业务说明,做向量化。用户提问时先检索相关表 schema,把"表名 + 字段说明"作为上下文喂给模型,模型基于精确 schema 生成 SQL。不是把全库 schema 灌进去(太大),而是按 query 相关性召回相关表。

#### Q14(产品杀手锏问题):老板看周报发现销量下滑,问"为什么销量下滑"——根因分析,你们系统现在能解决吗?

**面试官直接说"感觉你们现在解决不了"。要诚实承认现状,再给设计方案。**

**参考答案**:
> **诚实承认**:目前做不到真正的根因分析,现在只能回答"数据是什么"(查数 + 描述),回答不了"为什么"。这是当前系统的明确边界。

#### Q15:如果让你设计,怎么让这个智能体既能回答数据问题,又能找根因?

**参考答案(分层设计:数据层→归因层→验证层)**:
> 我会把它拆成三层能力:
>
> 1. **数据层(现有)**:Text-to-SQL,回答"是什么",拉出指标现状。
>
> 2. **归因层(新增核心)**:不是让模型直接"猜"原因(会幻觉),而是建一套**归因分析能力**:
>    - **多维下钻**:销量下滑 → 按维度拆解(地区/品类/渠道/时段),定位下滑集中在哪个切片。
>    - **对比基线**:和历史同期、目标值对比,判断是趋势性下滑还是异常波动。
>    - **关联分析**:把可能相关的指标(库存、促销、竞品、流量、客诉)一起拉出来,看相关性。
>    - 这些用**确定性计算/规则**做,把候选原因缩小到几个,而不是让模型凭空猜。
>
> 3. **推理 + 验证层**:把"数据层拉的事实 + 归因层的候选原因"喂给大模型,让模型做**假设推理**("可能是 X 促销结束了导致 Y 品类下滑"),但要**回查数据验证假设**(真去查 X 促销期间的销量),验证通过才输出,不通过就标注"待确认"。
>
> **关键设计原则**:归因的"找候选原因"尽量用确定性方法(下钻/对比/关联),把模型用在"组织叙述 + 生成可验证假设"上,**绝不让模型直接编原因**——这跟周报"不让模型算数只让它表达"是同一个原则。

> 💡 这题 Dennis 是在考你的**产品思维 + 系统设计**,不是考你有没有做过。答出"数据/归因/验证三层 + 归因用确定性、推理用模型、结论要回查"就到位了,而且这套思路和你周报系统"不让模型算数"的原则一脉相承,可以呼应。

#### Q16:平时用什么 coding agent?什么模型?AI 代码生成率多少?

#### Q17:Cursor / Claude Code / Codex 这种 coding agent 怎么实现对代码文件的编辑的?

**参考答案(核心:工具调用 + 文件操作协议,不是模型直接改文件)**:
> 模型本身不直接碰文件,是通过**工具调用(tool use)**实现的:
> - agent 给模型暴露一组文件操作工具(读文件 read_file、写文件 write_file、按范围编辑 edit_file/str_replace、创建文件、删除、搜索 grep/glob 等)。
> - 模型在推理后输出**结构化的工具调用指令**(指定文件路径、操作类型、内容/范围),agent runtime 执行这些指令真正改文件。
> - 关键点:编辑多采用**基于锚点的局部替换**(如指定 old_string → new_string),而不是整文件重写,减少 token、降低改错风险。
> - 执行后再读回文件验证,形成"读→改→验"循环。

#### Q18:如果是你设计这个 coding agent 工具,会设计哪几个参数?

**参考答案(给一组合理参数)**:
> 我会设计这几类参数:
> - **文件操作类**:file_path(目标文件)、operation(read/write/edit/delete/search)、
> - **编辑定位类**:old_string / new_string(锚点替换)或 line_range(行范围),edit 必须给精确定位,不能整文件覆盖。
> - **校验类**:dry_run(只预览不写)、verify_after(改完是否自动读回校验)。
> - **上下文类**:context_window(读文件时带几行上下文)、max_bytes(防读超大文件)。
> - **安全类**:allow_overwrite、backup(改前是否备份)。
> 核心设计原则:**编辑要锚点定位而非整体重写、操作要可预览可回滚、读文件要限大小防爆 token。**

## 四、复盘:本场难点 + 改进

### Dennis 的风格特征
- **不因你做过就认可**:每个项目都先问"现成的/模型原生能不能做",逼你证明差异化。
- **产品思维重**:周报那题不问技术实现,问"老板问根因你能不能解决"——考的是你懂不懂业务。
- **诚实可加分**:Q14 你若硬说"能解决根因"反而露怯,诚实承认 + 给设计方案是更优解。

### 必须打磨的 3 个"防御性答案"
1. **CodeWiki vs Claude Code init**(Q7):核心论点 = **代码调用关系是确定性的,该用 AST 图而非模型总结保证精确;且图可增量更新、可结构化检索**。这题是 CodeWiki 的生死线。
2. **周报根因分析设计**(Q15):**数据层/归因层(确定性下钻+对比+关联)/推理验证层**,归因用确定性、推理用模型、结论要回查。呼应"不让模型算数"原则。
3. **SQL 安全**(Q12):**只读账号 + SQL parser 白名单 + 关键词黑名单**,永不信任模型 SQL 直打生产。

### 和前几场对比的启示
- 卓誉(Ashley 旁的场):问你**对标 Codex/Cursor 的差异化**。
- Ashley:问你**记忆系统的幻觉治理**。
- 安克:问你**和 Claude Code 原生能力的差异化** + **业务根因分析**。
→ **同一个 CodeWiki,三个公司三种问法**。你要准备的不是"一个答案",而是能从**精度/增量/规模/检索/业务**多角度 defending 的"防御矩阵"。文档里 Q5/Q7/Q8 就是这套矩阵。

### 战略提醒
安克明确"没有技术困难,困难在推动业务拥抱 AI"。如果你后续进安克,**纯技术深度的价值有限,能落地业务、推动非技术方使用的能力才是核心**。面试和入职后都要往这个方向靠。
