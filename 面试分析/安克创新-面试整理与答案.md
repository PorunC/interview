## 二、技术问题清单 + 参考答案

### 【项目一】AI Agent 长期记忆 + 上下文压缩系统

#### Q1:长期记忆和上下文压缩是 for 你们内部自研 agent runtime,还是基于已有 runtime 二开?

**参考答案**:
> 不是从零开发完整 Agent Runtime。按当前项目口径，实际主路线是**本地插件 + SQLite**：插件接宿主的生命周期 Hook，在模型调用前 Recall，一轮提交后 Capture；Core 负责记忆和 Offload，宿主仍负责模型循环、工具调用和流式输出。
>
> Core 在设计上保持宿主无关，也有 HTTP Gateway/sidecar 这类适配能力，但要把“支持的接入形态”和“这次实际采用的部署形态”分开。新 Runtime 仍需提供模型前注入、轮次提交事件；要做 Tool Result Offload，还要提供稳定的 tool call/result ID 和可调整的消息上下文，不能说零改造接任何 Agent。

#### Q2:Copilot 自己就有上下文压缩,你们的压缩和它有什么区别?(被追问)

**参考答案**:
> 我不会猜 Copilot 未公开版本内部一定如何压缩，只比较自己能证明的能力。宿主 compact 主要解决“当前会话接近窗口后怎样继续”；我们的系统额外解决两类问题：跨会话长期记忆，以及 Coding Agent 大 Tool Result 的可追溯卸载。
>
> 长期记忆的 L0~L3 是“原始对话、原子记忆、场景 Markdown、Persona”，不是会话摘要逐层晋升。Offload 是另一套层级：完整 Tool Result 先写 refs，Prompt 留摘要、任务状态和引用，需要精确错误或行号时再下钻原文。真正降低 Token 的是原结果外移和消息替换，Mermaid 只是任务导航，不应把它本身说成压缩。
>
> 两者可以共存：宿主 compact 做整段会话兜底，Memory/Offload 提供跨会话复用和工具证据恢复。差异应落到可验证的数据链，不能靠贬低外部产品来证明。

#### Q3:现在还用千问吗?(确认当前模型)

如实回答当前用的模型(千问 / DeepSeek / 其他)。

#### Q4:对接 DeepSeek V4 Pro 的上下文压缩,策略怎么设计?到多少 k 做压缩?怎么设计?

**参考答案(当前默认值 + 设计边界)**:
> 当前不是写死某个 K，而是先读取模型 Context Window，再按比例触发。源码默认大约是 50% 进入 Mild、85% 进入 Aggressive、95% 进入 Emergency，紧急处理目标约 60%。换算到 128K，大约是 64K、109K 和 122K，但还要给 system prompt、tool schema、下一轮输出和 tokenizer 误差留余量。
>
> Mild 主要把高可替代 Tool Result 换成摘要；Aggressive 会进一步移除较老消息并补任务图；Emergency 是避免下一轮直接超窗的有损兜底。原始 Tool Result 先保存在 refs，最后一条真实用户消息有明确保护，但更早普通对话不保证逐字可恢复。
>
> 这些比例是当前默认配置，不是理论最优值。接新模型后要按任务通过率、Token 节省、原文下钻率和恢复成功率重跑，不能直接说“80% 是最佳阈值”。

### 【项目二】CodeWiki(GraphRAG / AST 代码图谱)—— 本场被挑战最狠

#### Q5:这其实就是做了个语法树(AST)解析吧?跟 Claude Code 插件的 MCP(Go/Python 等语法解析)有什么区别?

**面试官的潜台词**:这东西现成的都有,你做的有啥不一样?

**参考答案(不贬低现成工具，讲清当前边界)**:
> 不能把现成 MCP/插件统一说成只会单文件解析，成熟 Coding Agent 也可能有 Repo Map、索引、LSP 或跨文件搜索。CodeWiki 的可证明差异是把仓库持续保存成 Code Graph、Source Chunk、社区和带来源 Wiki，再通过 MCP 给人和 Agent 复用。
>
> 其中定义、包含和精确行范围属于较确定的 AST 事实；跨文件 `calls/references` 是分层名称解析的启发式结果，会带 confidence 和 provenance，有歧义时宁可不连。它能沿图补充调用方、被调用方和相关 Schema，但不能承诺“所有上下游一次性补全”或“改代码绝不漏调用方”。
>
> 所以区别不是“我们的解析一定更强”，而是**持久结构证据 + 受限图扩展 + 来源引用 + 可复用文档**。是否比宿主原生能力有净收益，要用同任务对照验证。

#### Q6:这个图谱是给人用的吗?具体起什么作用?

**参考答案**:
> 主要给**模型/agent 用**(RAG 检索底座),也附带给人看(可视化依赖关系)。核心作用:当代码 agent 需要理解或修改跨模块代码时,用图谱做检索,把相关上下文(不止相似代码,还有依赖代码)喂给模型,提升跨模块理解的准确率。

#### Q7(杀手锏问题):我直接用 Claude Code 对仓库做 init,生成一个 markdown 长期记忆,跟你这个 GraphRAG MCP 区别多大?模型自己抓重点做长期记忆,是不是比做成 GraphRAG MCP 给模型更优?

**这是全场最难的问题,Dennis 直接表达"我理解模型自己抓重点做长期记忆可能更优"。你必须有力反驳,否则 CodeWiki 的价值就塌了。**

**参考答案(先接受最简单替代方案，再证明增量价值)**:
> 小仓库、一次性问题或本地改动特别快的分支，我也会直接用成熟 Coding Agent 的原生搜索和项目说明，不强制接 CodeWiki。
>
> CodeWiki 争取的是另外三类价值：第一，把已解析的定义、包含、导入和启发式调用关系沉淀成可重复查询的结构证据；第二，回答和 Wiki 能回到文件、行范围和允许的 Source Ref 核对；第三，同一套图、Chunk 和页面可由 Web、CLI、MCP 及多个会话复用，不必每次从零形成仓库认知。
>
> 但它也有明确成本。跨文件调用会漏；当前 Git Diff/Hash 只让扫描和解析局部复用，图、社区和持久化后半段仍有全量成本；图、Chunk、Wiki 与源码还没有统一不可变 Revision，大分支或分析期间继续修改代码时可能产生陈旧证据。因此不能说“只更新变动节点、始终新鲜”。
>
> 最终我会在同一批任务上比较原生 Agent、Agent + Repo Map/Skill、Agent + CodeWiki，测任务成功率、跨模块召回、引用正确性、Token、建索引成本和陈旧率。只有净收益成立，CodeWiki 才值得接。

> 💡 核心论点应改成：**确定的语法事实交给解析器，不确定的跨文件关系显式标注；CodeWiki 的价值需要对照评测证明，不靠“AST 绝不出错”来防守。**

#### Q8(承上,可能追问):那如果模型够强,以后能自己扫准了,GraphRAG 还有意义吗?

**参考答案**:
> 模型更强以后，CodeWiki 的适用范围应该缩小，而不是继续宣称所有仓库都需要它。一次性任务优先让 Agent 实时读当前工作区；反复的跨模块问题、团队共享文档和需要来源审计的场景，再考虑持久图索引。
>
> 更强 Agent 也带来了新的轻量基线：Skill 用 `SKILL.md` 定义分析步骤，Agent 再用 `read/grep/bash/LSP` 实时取证，产物写成仓库内 Markdown/JSON，不一定需要向量库。CodeWiki 下一版应吸收这种“实时工具优先、渐进披露、文件真相源”的方式，只把高复用图能力做成按需增强。

### 【项目三】AI 周报系统 —— 被挑战"没大模型也能做" + "做不了根因分析"

#### Q9:没大模型,我配固定模板 + 自动采集 pipeline 也能做吧?

**参考答案(承认 + 补差异)**:
> 可以。当前项目本来就是一条网联运营保障周报的批处理链路，采集、完整性判断、统计和固定模板都可以不用大模型完成，所以我不会说 LLM 是系统成立的前提。
>
> 当前 LLM 的作用是接收程序已经算好的错误日志、大事务、慢 SQL、失败交易、TPS、响应时间等模块结果，做分段异常解读、趋势归纳和文字组织。最终产物仍是固定结构的表格加文本，通过内部消息接口推送。数字、状态和是否允许发送都由确定性程序负责。
>
> 当前没有自然语言追问 RAG，也不是员工 Git/Jira 周报。如果以后需要交互式查数，我会把它作为下一版独立能力评估，而不是拿未来设想证明当前必须用 LLM。

#### Q10:大模型介入后,推送的周报模板变了吗?

**参考答案**:
> 模板结构没有变，当前仍按固定板块输出表格加文本。变化的是异常说明和趋势文字的生成方式：数字由预写 SQL 和程序逻辑计算，模型只根据这些结果分模块组织文字。这样既保持运营人员原来的阅读习惯，也不会让模型决定数字或报表结构。

#### Q11:做成自动化?定时采集 + 生成 + 推送?

> 是自动化链路，但更准确地说是日终批任务按业务日期采集和回补数据；当上一周七天数据都完整时，才进入分模块统计、LLM 解读、模板组装和内部消息推送。任何关键模块最终失败时，本轮不会发送残缺周报，后续批次再补跑。

#### Q12:大模型写 SQL,如果它写了 DROP/DELETE 把表删了,怎么拦截?

**参考答案(多层防护)**:
> 我会先澄清：**当前周报系统不是 Text-to-SQL**。查询和统计 SQL 都是程序预先写好的，模型只读取整理后的结果，所以现状里不存在模型生成 DROP 或 DELETE 再直接执行的问题。
>
> 如果下一版扩展成自然语言查数，我会做多层防护：数据库使用只读账号和只读副本；服务端用 SQL parser 解析 AST，只允许单条 SELECT，并限制 schema、table、function、行列权限、执行时间和扫描量；执行前先做 EXPLAIN；所有查询保留用户、SQL、策略命中和结果审计。关键词黑名单只能辅助，不能替代数据库权限和 AST 白名单。
>
> 核心原则是：模型只能提议查询，真正能不能执行由服务端权限和策略决定。这一段是扩展设计，不是我把未来能力说成当前已经上线。

#### Q13:怎么把表名和表描述精确给到模型?(模型得知道有哪些表才能查)

**参考答案**:
> 当前周报没有让模型选表或写 SQL，表名、字段和统计逻辑都在程序里预先定义，所以我不会说已经做了 Schema 向量检索。
>
> 如果下一版做 Text-to-SQL，我会先按当前用户权限筛出允许访问的 Schema，再从经过治理的元数据目录里检索相关表和字段，把业务含义、主外键、时间口径、枚举值和示例一起给模型。生成后仍要经过 SQL AST 校验和权限注入。不能把全库 Schema 全塞进去，更不能因为模型“知道表名”就允许它访问那张表。

#### Q14(产品杀手锏问题):老板看周报发现销量下滑,问"为什么销量下滑"——根因分析,你们系统现在能解决吗?

**面试官直接说"感觉你们现在解决不了"。要诚实承认现状,再给设计方案。**

**参考答案**:
> **诚实承认**:目前做不到真正的根因分析,现在只能回答"数据是什么"(查数 + 描述),回答不了"为什么"。这是当前系统的明确边界。

#### Q15:如果让你设计,怎么让这个智能体既能回答数据问题,又能找根因?

**参考答案(分层设计:数据层→归因层→验证层)**:
> 我会把它拆成三层能力:
>
> 1. **数据层**：当前系统通过预写 SQL 和确定性统计回答“是什么”，拉出指标现状，不让模型自由写查询。如果下一版增加开放式自然语言查数，安全的 Text-to-SQL 只能作为受权限和校验约束的扩展能力。
>
> 2. **归因层(新增核心)**:不是让模型直接"猜"原因(会幻觉),而是建一套**归因分析能力**:
>    - **多维下钻**:销量下滑 → 按维度拆解(地区/品类/渠道/时段),定位下滑集中在哪个切片。
>    - **对比基线**:和历史同期、目标值对比,判断是趋势性下滑还是异常波动。
>    - **关联分析**:把可能相关的指标(库存、促销、竞品、流量、客诉)一起拉出来,看相关性。
>    - 这些用**确定性计算/规则**做,把候选原因缩小到几个,而不是让模型凭空猜。
>
> 3. **推理 + 验证层**:把"数据层拉的事实 + 归因层的候选原因"喂给大模型,让模型做**假设推理**("可能是 X 促销结束了导致 Y 品类下滑"),但要**回查数据验证假设**(真去查 X 促销期间的销量),验证通过才输出,不通过就标注"待确认"。
>
> **关键设计原则**:归因的"找候选原因"尽量用确定性方法(下钻/对比/关联),把模型用在"组织叙述 + 生成可验证假设"上,**绝不让模型直接编原因**——这跟周报"不让模型算数只让它表达"是同一个原则。

> 💡 这题 Dennis 是在考你的**产品思维 + 系统设计**,不是考你有没有做过。答出"数据/归因/验证三层 + 归因用确定性、推理用模型、结论要回查"就到位了,而且这套思路和你周报系统"不让模型算数"的原则一脉相承,可以呼应。

### 【通用技术追问】

#### Q16:平时用什么 coding agent?什么模型?AI 代码生成率多少?

如实回答工具（Claude Code / Cursor / Copilot 等）、模型和使用场景。代码生成比例只有 Git Diff、任务记录和统计窗口支持时才给区间；不要用“业界常见比例”代替个人事实。

#### Q17:Cursor / Claude Code / Codex 这种 coding agent 怎么实现对代码文件的编辑的?

**参考答案(核心:工具调用 + 文件操作协议,不是模型直接改文件)**:
> 模型本身不直接碰文件,是通过**工具调用(tool use)**实现的:
> - agent 给模型暴露一组文件操作工具(读文件 read_file、写文件 write_file、按范围编辑 edit_file/str_replace、创建文件、删除、搜索 grep/glob 等)。
> - 模型在推理后输出**结构化的工具调用指令**(指定文件路径、操作类型、内容/范围),agent runtime 执行这些指令真正改文件。
> - 关键点:编辑多采用**基于锚点的局部替换**(如指定 old_string → new_string),而不是整文件重写,减少 token、降低改错风险。
> - 执行后再读回文件验证,形成"读→改→验"循环。

#### Q18:如果是你设计这个 coding agent 工具,会设计哪几个参数?

**参考答案(给一组合理参数)**:
> 我会设计这几类参数:
> - **文件操作类**:file_path(目标文件)、operation(read/write/edit/delete/search)、
> - **编辑定位类**:old_string / new_string(锚点替换)或 line_range(行范围),edit 必须给精确定位,不能整文件覆盖。
> - **校验类**:dry_run(只预览不写)、verify_after(改完是否自动读回校验)。
> - **上下文类**:context_window(读文件时带几行上下文)、max_bytes(防读超大文件)。
> - **安全类**:allow_overwrite、backup(改前是否备份)。
> 核心设计原则:**编辑要锚点定位而非整体重写、操作要可预览可回滚、读文件要限大小防爆 token。**

> 💡 这段信息很重要:安克给 AI 工程师的环境是**顶配工具 + 充足算力 + 不卡预算**,而且明确说"没有技术困难"——意味着他们要的人是能**推动业务落地 AI**的人,不是纯做技术的。你后续面试要往"我能把 AI 能力嵌进业务流程、推动非技术方使用"上靠。

## 四、复盘:本场难点 + 改进

### Dennis 的风格特征
- **不因你做过就认可**:每个项目都先问"现成的/模型原生能不能做",逼你证明差异化。
- **产品思维重**:周报那题不问技术实现,问"老板问根因你能不能解决"——考的是你懂不懂业务。
- **诚实可加分**:Q14 你若硬说"能解决根因"反而露怯,诚实承认 + 给设计方案是更优解。

### 必须打磨的 3 个"防御性答案"
