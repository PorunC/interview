## 二、Agent 长期记忆系统架构深挖

### Q3. 你独立设计过调度器和记忆架构，详细描述一下这款产品的整个架构形态，为什么要这样设计，有什么优缺点？

> 这是本场项目部分的重点。面试官要的是**完整架构 + 设计 rationale + 诚实的优缺点**。基于你的真实实现（TdaiCore 宿主无关内核 + pipeline-manager 调度器 + L0~L3 + 混合召回 + Context Offload）来答。

**参考答案**（分架构 / rationale / 优缺点三段）：

#### 架构形态

> 整套系统是**宿主无关的内核 + 两条链路**的设计：
>
> ```
> ┌─────────────────────────────────────────────┐
> │           Agent Runtime（宿主，可替换）        │
> │   对话 / 工具调用 / 流式输出                  │
> └───────────────┬─────────────────────────────┘
>                 │  (记忆接口)
> ┌───────────────▼─────────────────────────────┐
> │           TdaiCore（宿主无关的记忆内核）       │
> │                                              │
> │  ┌────────────┐    ┌────────────────────┐   │
> │  │ 长期记忆链路 │    │  短期上下文压缩链路  │   │
> │  │            │    │                    │   │
> │  │ L0 原始证据 │    │  Context Offload   │   │
> │  │ L1 原子记忆 │    │  (工具日志卸载)     │   │
> │  │ L2 场景归纳 │    │  Mermaid 任务画布   │   │
> │  │ L3 用户画像 │    │  (任务状态可视化)   │   │
> │  └─────┬──────┘    └─────────┬──────────┘   │
> │        │                     │              │
> │  ┌─────▼─────────────────────▼──────────┐  │
> │  │   pipeline-manager（后台调度器）       │  │
> │  │   异步触发：L1 / L2 / L3 后台处理       │  │
> │  └───────────────────────────────────────┘  │
> │                                              │
> │  ┌──────────────────────────────────────┐   │
> │  │   混合召回层（Hybrid RRF）            │   │
> │  │   Vector + FTS/BM25 候选，RRF 融合   │   │
> │  └──────────────────────────────────────┘   │
> └──────────────────────────────────────────────┘
> ```
>
> **两条链路**：
> - **长期记忆链路**：L0 原始对话证据 → L1 原子记忆 → L2 场景归纳 → L3 Persona。四层逐步聚合，但不是同一条事实按置信度逐层晋升。
> - **短期上下文压缩链路**：工具日志通过 Context Offload 移出 prompt，只留摘要 + 索引（result_ref / node_id），需要时按索引找回原文；Mermaid 任务画布把任务状态结构化呈现，替代大段文本。
>
> **后台调度器**（pipeline-manager）：按不同节奏触发 L1 原子记忆抽取、L2 场景组织和 L3 Persona 更新。Context Offload 是另一条短期链路，不能把三层处理说成“摘要、事实抽取、置信度晋升”。
>
> **混合召回**：本地后端并行取 Vector 和 FTS 候选，再按同一 Record ID 用 RRF（Reciprocal Rank Fusion）合并。不同 Store 后端能力有差异，当前不是“向量 + BM25 + 实体结构索引”三路统一实现。

#### 为什么这样设计（rationale）

> 四个核心问题驱动：
>
> 1. **宿主无关**：agent runtime 会换（自研/Copilot/其他），但记忆治理逻辑是核心资产，不能和某个 runtime 绑死。所以把 TdaiCore 设计成宿主无关内核，runtime 换了记忆层不动。
> 2. **记忆必须分层**：原始证据、L1 原子记忆、L2 场景和 L3 Persona 是不同粒度的信息，生命周期、召回方式和 Token 成本不同。分层不是事实按置信度晋升，而是不同抽象职责各司其职。
> 3. **召回要稳**：只靠向量会漏关键词和专有名词，只靠全文检索又不懂语义，所以本地后端并行做 Vector + FTS，再用 RRF 合并；效果仍要靠评测，而不是假设 Hybrid 一定更准。
> 4. **压缩要可恢复**：工具日志能从 prompt 移出去，但不能真丢。上下文只留摘要 + 索引，必须能按 `node_id`/`result_ref` 找回原文——"热路径有损、冷路径可还原"。

#### 优缺点（诚实讲）

> **优点**：
> - **跨会话连续性**：L3 Persona 与 Scene Navigation 提供稳定方向，本轮相关 L1 稀疏注入，细节再按需下钻。
> - **可追溯与去重**：L1 保存 `source_message_ids`，并通过相似候选 + `store/skip/update/merge` 处理新旧记录；但来源还没有严格 span/蕴含校验。
> - **上下文压力可控**：Offload 和分级压缩能显著延缓窗口增长；85%/95% 后的删除仍然有损，不能说语义完全不丢。
> - **宿主无关**：runtime 换了记忆层可复用。
>
> **缺点**（诚实承认）：
> - **复杂度高**：四层 + 调度器 + Hybrid Recall，实现和运维成本不低，小场景可能过度设计；引入前要看是否真的需要跨会话治理和证据追溯。
> - **L3 更新有门槛，冷启动慢**：新用户前几轮 Persona 信息少，L3 通常在场景变化和新增记忆达到触发条件后更新；这不是事实置信度晋升。
> - **异步调度有延迟**：L1 抽取、L2 场景和 L3 Persona 都是后台处理，会话刚结束时抽象层可能还没更新。
> - **混合召回仍需评测**：RRF 常数和候选规模不是自动学习出来的，不同后端的分数和阈值语义也并不完全一致。

## 三、大模型使用与中转站

### Q4. 个人使用最多的是哪个大模型？遇到过模型切换和模型降级的场景吗？公司开发用什么？直接用 API 还是聚合器？多个模型怎么切换/降级？

**参考答案**：
> **个人使用最多**：[如实说，如 Claude（日常编码 + agent）/ GPT-4（推理）/ DeepSeek（特定任务）]。
>
> **公司开发**：用**聚合器 API 为主**（如 LiteLLM / 内部网关），而不是直接调单家 API。原因：
> - 多模型统一接口，切换模型只改配置不改代码。
> - 聚合器层做 fallback、限流、缓存、成本统计，比每家 API 各接一遍省事。
> - CodeWiki 里就是用 LiteLLM gateway + ModelRouter，按 task type（catalog/page/qa/embedding）路由到不同模型。
>
> **模型切换场景**：
> - **按任务路由**：摘要用便宜模型（如 DeepSeek/Haiku），复杂推理用强模型（如 Claude Sonnet/GPT-4），embedding 用专门 embedding 模型——按 task type 自动切换。
> - **按窗口切换**：短上下文用小模型省成本，超长上下文切大窗口模型。
>
> **模型降级场景**：
> - **故障降级**：主模型 API 超时/限流，自动 fallback 到备用模型（如 Claude 挂了切 GPT-4）。
> - **质量降级**：发现某模型在特定 task 上效果变差（线上信号），手动或自动切到更稳的模型。
> - **成本降级**：预算紧张时把非关键 task 从强模型降到便宜模型。
> - **降级要可观测**：每次降级记录原因、触发条件、影响范围，不能静默切。

### Q5. ⚠️ 你用 Claude Code 时用了一个中转站，用的是哪个？怎么用的？对中转站产品有什么评价？

**参考答案**：
> 用过中转站，主要是为了**用到国内官方渠道暂时不方便访问的特定模型**（比如某些 Claude / GPT 的特定版本）。具体方式：中转站提供兼容 OpenAI 格式的 API，我在 Claude Code / Cursor 里把 API endpoint 指向中转站，配 API key 就能用。
>
> **对中转站产品的评价**（诚实）：
> - **优点**：解决了特定模型的获取问题，兼容 OpenAI 格式接入方便，价格通常比官方低。
> - **风险/缺点**：
>   1. **合规风险**：很多中转站来源不透明，可能涉及账号共享、违反 ToS，企业用不安全。
>   2. **稳定性差**：中转站经常限流、排队、挂掉，生产环境不能用。
>   3. **数据安全**：请求经过第三方，敏感数据有泄露风险，不能传生产数据。
>   4. **"智能路由"大多是噱头**：很多中转站宣传智能路由，实际就是按价格/可用性简单切换，没有真正的任务级路由。

### Q6. 对于正规渠道（OpenRouter / 国内云厂商中转），有使用经验或调研吗？

**参考答案**：
> 有调研，正规渠道我会区分来看：
>
> - **OpenRouter**：用过。优点是**一个 API 接入多家模型**，统一计费，有 failover，适合原型和中小项目。缺点是比直连官方略贵、延迟多一跳。生产环境关键链路还是建议直连官方或私有部署。
> - **国内云厂商中转（如阿里云百炼、腾讯云、火山引擎）**：调研过。优点是**合规、稳定、国内访问快**，国产模型（Qwen/DeepSeek/GLM）接入方便，企业用安全。缺点是海外模型（Claude/GPT）通常没有或受限。
> - **自建聚合层**：生产环境我倾向用 **LiteLLM 自建 gateway**——既能聚合多家，又能自己控制 fallback/限流/审计/成本，不依赖第三方。CodeWiki 就是这么做的。
>
> **选择逻辑**：个人探索 / 用特定模型 → 中转站或 OpenRouter；企业生产 → 国产模型走云厂商中转 + 海外模型走官方或自建 gateway。**核心是按场景选，不是一概而论**。

## 四、三个项目的延迟优化

### Q8. 这三个项目对响应延迟敏感吗？有的话怎么优化？先讲延迟，再讲其他产品优化。

**参考答案**（分项目讲，每个给具体优化手段）：

#### 延迟优化

> **周报系统**——对延迟不敏感（异步生成，非实时交互）：
> - 当前是日终批任务：按业务日期采集和回补数据，上一周七天完整后才做确定性统计、分模块调用 LLM 解读，再组装成表格加文本推送。用户不在线等待，所以重点是数据完整、按时送达和失败可补跑，不是交互式首 Token 延迟。
> - 当前没有“用户追问周报走 RAG”的链路，也没有 Text-to-SQL。以后如果增加自然语言查数，需要单独定义交互延迟、权限、查询安全和评测，不能拿这个下一版设想当现有优化成果。
>
> **CodeWiki**——对延迟中等敏感（人在等，但能接受秒级）：
> - **检索链路可降级**：GraphRAG 第一层有符号搜索 + FTS，向量是可选增强；没有 Embedding 仍能检索，避免把模型服务变成唯一依赖。具体延迟要引用实际压测，不能直接承诺毫秒级。
> - **图扩展限制深度**：避免无限 BFS 导致子图膨胀，既控 token 又控延迟。
> - **LLM 缓存**：`llm_run` 表按 prompt version + input payload 缓存，重复查询直接命中，不调模型。
> - **Lite Mode**：项目内本地 SQLite，无 LLM 也能查图；它减少外部调用，但当前材料不足以承诺统一的毫秒级 SLA。
>
> **Agent 记忆系统**——对延迟最敏感（实时对话，用户在等）：
> - **前台少做、后台补齐**：主链路捕获 L0、做少量 Recall；Embedding、L1 抽取、L2 场景和 L3 Persona 放后台。Recall 默认 Top 5，并有整体超时，超时就不带记忆继续回答，优先保证主对话可用。
> - **稀疏注入**：L3 Persona + Scene Navigation 放稳定 system 后缀，本轮相关 L1 放 user 前缀；L2 场景正文和 L0 原话按需查询，不拉全量。
> - **Embedding 异步补齐**：元数据和 FTS 先落，Embedding 通过后台批处理补齐，向量暂时失败不阻塞证据保存。
> - **诚实边界**：稳定 system 区有利于 Prompt Cache，但当前没有完整的通用 Recall 结果缓存；流式回复属于宿主模型链路，也不能包装成记忆内核自身的优化成果。

#### 其他产品优化

> - **准确性优化**：周报"数字与叙述分离"；记忆系统有来源 ID、原始证据和四动作判断，但严格 span/事实置信度仍待补；CodeWiki 做 Allowed Source Ref 和 Citation 范围校验，不能说已经验证每个 Claim 都被证据蕴含。
> - **成本优化**：按 task type 路由到不同价位模型；LLM 缓存复用；上下文压缩降 token。
> - **可观测性**：每次 LLM 调用记录 model/token/usage/latency/缓存命中，可审计可回溯。
> - **增量与保留**：CodeWiki 扫描和解析阶段利用 Git Diff/Hash 复用，但图和社区后半段仍偏全量；记忆系统按保留期清理日期分片，不要说成已完成冷热分层归档。

## 五、架构设计实例：AI 模型路由引擎 ⭐（本场重点）

### Q9. 设计一个 AI 模型路由引擎架构，三个需求：①请求 100ms 内完成路由决策；②所选模型故障 500ms 内 failover；③所有路由决策可审计。从核心组件和数据流讲。

> 这是本场分水岭。给一套完整设计：组件分层 + 数据流 + 三个需求的落地。

**口语化回答**：

> 我先确认一下 500ms 的口径。它是指“我在发现主模型不可用后，500ms 内开始调用备用模型”，还是指“500ms 内把备用模型的完整答案返回给用户”？这两个 SLA 不是一回事。我能把前一个作为故障切换目标；如果备用模型还是远端大模型，受网络、首 token 和生成时长影响，我一般不能承诺 500ms 内拿到完整答案。真要承诺后一个口径，我就得把降级结果改成本地小模型、模板或缓存结果，或者做 hedging，并且要用压测数据证明，而不能只靠架构图承诺。
>
> 我也会先讲清现状。当前 CodeWiki 里有 LiteLLM gateway、按 task type 选模型和基础 fallback，但下面这套带 100ms 决策预算、500ms 切换目标、健康状态机和持久化审计的路由引擎，是我针对这道架构题给出的下一版设计，不是我已经上线并跑出这些 SLA 的功能。

#### 我会怎么拆组件

```text
Client / Agent
      |
API Gateway：鉴权、限流、生成 tenant_id / request_id / trace_id、接收总 deadline
      |
Router Core：特征提取 -> 候选过滤 -> 规则/轻量模型打分 -> 主模型 + fallback 列表
      |                         ^
      |                         |
      |                 本地只读快照：策略、能力、成本、健康状态
      v
Executor：按剩余 deadline 调用模型、熔断、hedging、failover、取消请求
      |
Model Providers / Local Models

Router Core / Executor
      |
本地 WAL 或事务 Outbox：先持久化最小决策事件和执行事件
      |
消息队列：异步分发
      |
ES / ClickHouse / 审计查询服务：检索、统计和复盘
```

#### 一次请求我会怎么走

> 1. 请求进来后，我先生成租户、请求和链路标识，同时接收调用方给的**总 deadline**。后面每一步都拿“还剩多少时间”做决策，而不是每层各设一个互不相关的超时，最后把总时延叠爆。
> 2. 我只做确定性的轻量特征提取，比如任务类型、语言、输入规模、是否要流式输出、是否允许工具调用、数据合规区域和预算等级。路由阶段不再调一次 LLM，也不临时查慢数据库。
> 3. 我从进程内快照读取策略、模型能力、价格和健康状态，先过滤掉能力、合规、配额或熔断状态不满足的模型，再按质量、成本、延迟和健康度打分。我不仅产出主模型，也会把当时可用的 fallback 列表和打分原因一起固定下来。
> 4. 在真正发请求前，我把最小决策事件写入本地 WAL，或者和业务记录一起写进事务 Outbox。只有这个事件持久化成功，我才把请求交给 Executor。后续详细日志可以异步展开，但“这次为什么这样选”不能只留在内存里。
> 5. Executor 按总 deadline 的剩余预算调用主模型。遇到明确可重试的网络错误、限流、服务端错误或本次尝试预算耗尽时，我才评估是否切备用模型；切换后再把尝试结果和 fallback 结果追加到同一条审计链路。

#### 100ms 路由决策我怎么保证

> 我会把 100ms 定义成从 Router Core 收到请求，到产出“主模型、fallback 列表和 decision_id”为止，并明确最小审计事件是否包含在这个口径里。要做到这一点，我的核心原则是：热路径只读本地快照，只做规则或轻量模型计算，不在决策时调用大模型，也不依赖远程数据库。
>
> 具体预算不能靠我在面试里编一个“特征几毫秒、打分几毫秒”。我会先用压测和线上 tracing 测出特征提取、候选过滤、打分、快照读取和审计持久化各自的 p95、p99，再按 100ms 总预算分配子预算，设置超时和降级路径。如果某个非关键特征来不及，我会回退到已有 metadata 或保守规则，而不是拖过总预算。配置和健康数据由后台持续刷新，本次决策读取带版本号的一致快照，事后才能复现。

#### 500ms failover 我怎么落地

> 我把 500ms 定义成“故障信号成立，到备用模型请求已经发出”的时间，而不是备用模型完整生成结束。路由阶段已经排好 fallback，所以故障时不需要重新走一遍全量决策；同时每个请求都有总 deadline，我会给 fallback 预留预算，避免主模型把时间全部耗完。
>
> 我不会固定写死“300ms 检测、50ms 切换”。连接失败、明确的 429/5xx、熔断器打开可以立即触发；无响应要根据这个模型近期的首 token 分布、任务类型和请求剩余预算动态确定尝试上限。对特别关键且允许增加成本的请求，我可以在测量过收益后做 hedged request，先后启动两个等价候选，谁先满足条件就用谁并取消另一个。
>
> failover 也不是所有请求都能直接重试。我只对**可重试、幂等**的模型调用自动切换，并给每次尝试带同一个 idempotency key。流式场景如果还没向用户发 token，我可以透明切换；如果已经发出部分内容，我就不能假装什么都没发生后从头拼接。我会由协议显式标记切换、从可验证的检查点续跑，或者结束本次流并让上层决定重试。涉及工具调用时，我会用工具执行账本记录“准备、已执行、结果”状态；已经产生外部副作用的工具绝不能因为换模型再执行一遍。

#### 所有决策我怎么做到可审计

> 我不会只把日志异步写 ES 或 ClickHouse，因为消息还没发出去进程就挂了，这次决策就丢了。我的做法是先用本地 WAL，或者用数据库事务把业务状态和 Outbox 事件一起提交，确保最小决策事件已经持久化；后台再通过消息队列把它投递到 ES、ClickHouse 或合规审计库。ES 和 ClickHouse 是查询视图，不是唯一事实源。如果业务要求“一次决策都不能漏”，WAL/Outbox 写失败时我会 fail closed，而不是继续调用模型后留下无审计请求。
>
> 我至少会记录：tenant_id、request_id、trace_id、各阶段时间戳，策略版本、模型目录版本、配置版本，候选模型、过滤原因、各项分数和最终选择，决策时使用的健康快照版本，主模型每次尝试的开始和结束时间、错误分类，是否触发 fallback、切到哪个模型、fallback 最终结果。涉及 prompt 时我会按合规要求存摘要、哈希或脱敏内容，不默认把敏感原文全部写进检索库。
>
> 这样拿一个 trace_id，我能还原“当时看到了哪些候选、基于哪版策略和健康状态做了什么决定、主模型为什么失败、备用模型最后怎样”，而不只是看到一行“请求成功”。

### Q10. ⚠️ 追问1：两个模型延迟、成本几乎一样，怎么决策用哪个？

> 面试官在追问"打分难分时怎么办"。不能只说"随便选一个"，要有产品层思考。

**参考答案**：
> 延迟成本一样时，**不能用延迟成本做 tie-breaker，要引入其他维度**，按优先级排：
>
> 1. **实时质量信号**：两个模型近期在线表现（成功率、用户反馈、人工抽样评分）。质量好的优先。这是最重要的 tie-breaker——延迟成本是静态的，质量是动态的。
> 2. **健康度 / 负载**：哪个当前负载低、p99 延迟更稳。避免往已经抖动的模型上压。
> 3. **能力匹配度**：虽然成本延迟一样，但能力侧重点不同——比如 A 擅长代码、B 擅长推理，按 task_type 细分匹配。
> 4. **成本冗余 / 灾备考虑**：故意把流量分到两个模型上，不 all-in 一个，便于一个挂了另一个能承接——**流量分散本身就是容灾策略**。
> 5. **确定性 tie-breaker**：以上都分不出，用**一致性 hash（按 user_id 或 session_id）**固定路由——同一用户固定走同一模型，保证体验一致性（不忽好忽坏），而不是随机。
>
> **产品层原则**：难分时优先保证**体验一致性 + 容灾分散**，而不是纯粹按某个静态指标选。把"两模型差不多"当机会做流量分担，而不是当麻烦。

### Q11. ⚠️ 追问2：怎么判断哪个模型效果更好？路由时任务还没执行，你怎么知道哪个效果好？

> 这是面试官的漂亮反问——路由是事前决策，效果是事后才知道。**必须答出"用历史信号 + 在线学习"**，不能说"等执行完看结果"（那时已经路由完了）。

**参考答案**：
> 这是路由引擎的核心矛盾：**决策时任务还没执行，效果是事后信号**。解决思路是用**历史信号 + 在线反馈**，不是等这次执行完才判断：
>
> 1. **离线质量基线**：每个模型在各类任务上有**预先建立的质量评分**（来自 benchmark + 人工标注 + 历史线上数据）。比如"模型 A 在代码任务上准确率 92%，模型 B 88%"。路由时用这个基线做初判——这是事前可用的。
> 2. **在线反馈信号（关键）**：
>    - **显式反馈**：用户对回答点踩/点赞、采纳/拒绝。
>    - **隐式反馈**：用户有没有重新提问（说明上次没答好）、有没有中断、停留时长、是否复制了结果（说明有用）。
>    - **下游信号**：如果是 agent 链路，看后续步骤是否成功（比如生成代码后能不能跑通）。
> 3. **反馈回流更新质量分**：在线反馈实时（或近实时）更新每个模型的"任务-质量"评分表（multi-armed bandit 思路：exploration vs exploitation）。某模型在某类任务上反馈变差，质量分下降，下次路由少选它。
> 4. **探索机制**：不能只选历史最优（会信息茧房），留小比例流量做 exploration（随机选非 top-1），收集新信号，防止评分过期。
> 5. **A/B + 影子评估**：新模型上线先影子跑（不发真实流量，只对比输出），积累足够质量信号再放量。
>
> 核心：**事前用历史基线初判，事后用在线反馈修正，exploration 持续校准**——不是单次决策追求最优，是让评分表持续逼近真实质量。

### Q12. ⚠️ 追问3：模型发生抖动，要预先替换，你怎么设计？

**参考答案**：
> 我先区分一下现状和设计。当前项目里我用 LiteLLM gateway 做基础路由和 fallback，但我没有把“趋势识别、自动降权、自动恢复”说成已经在线稳定运行的能力。下面是我会在下一版路由引擎里补的闭环。
>
> 我不会只看一次 ping，也不会拿所有请求混在一起算一个平均值。我会把**被动流量信号**和**主动探测信号**放到同一条时间线上：按模型、供应商、区域、任务类型和流式/非流式分组，观察连接失败、429/5xx、首 token 延迟、完整响应延迟、超时率、成功率和剩余配额。否则可能只是某个区域或某类长请求变慢，却被误判成整个模型故障。
>
> 判定时我会用滑动窗口或 EWMA 跟这个模型自己的历史基线比较，并要求“样本量足够、连续多个观测异常、多个信号能互相印证”。阈值要通过历史回放和压测校准，我不会在设计阶段凭空承诺固定的秒数或百分比。发布变更、供应商公告和网络故障也会作为时间线证据，帮助我判断这是模型本身、链路还是我方配置的问题。
>
> 控制面我会做成有滞回的状态机，比如 `healthy -> degraded -> open -> half-open`。进入 `degraded` 后，我先减少新流量并把请求导向已经预排、能力等价且健康的候选，同时保留受控探测流量；证据继续恶化才进入 `open`，而不是一个窗口异常就把模型全踢掉。恢复时我也不会立刻把权重拉满，而是经过半开探测和逐步放量，观察错误预算和延迟分位数稳定后再恢复，这样能避免状态来回震荡。
>
> 我说的“预先替换”也不是临时找一个名字相同的模型。我会提前校验备用模型的区域合规、能力、上下文长度、工具协议、配额和限流状态，必要时用不产生业务副作用的探测请求确认可用。对已经在执行的请求，我仍然遵守总 deadline、幂等性、流式输出和工具副作用边界；不能因为模型抖动就把一个已经扣款或已经发消息的工具调用重做一遍。
>
> 每次健康状态变化、权重调整和恢复，我都会沿用 Q9 的 WAL/事务 Outbox 记录触发证据、健康快照版本、策略版本、调整前后权重和操作者，再异步写入查询系统。这样出了误切，我能回放当时为什么降权，而不是只看到最终告警。
>
> 所以我最后会把话说准确：抖动场景我做的是**多信号识别、提前降权、受控探测和渐进恢复**；Q9 里的 500ms 目标仍然只是“故障成立后，在 500ms 内发起符合条件的 fallback”，不等于备用远端大模型能在 500ms 内生成完整答案。

### Q13. 工作中如何利用 AI 协助你提效 / 扩展职能？有事例吗？

**参考答案**（给具体事例，不空谈）：

>

>
> **扩展职能（做超出原本职责的事）**：
> - **文档撰写**：技术设计文档、周报、面试整理，用 AI 起草 + 自己改，效率高很多——比如这份面试整理就是 AI 辅助。

> - **调研对标**：让 AI 帮忙整理竞品方案（CoCo / Cursor / Mem0）的公开设计，加速调研。
>
> **认知层面**：AI 让"能写代码"贬值，让"能判断、能定义边界、能把 AI 当杠杆"升值。我的定位是做**"AI 的指挥者"**——自己定架构和边界，让 AI 干执行，这正好呼应您说的"AI first 超级个体，一个人指挥多个 agent 达到 3-5 人战斗力"。

## 八、复盘：这场的得失与风险

### 得分点（继续巩固）：
- 记忆系统架构能讲到"宿主无关内核 + 两链路 + 调度器 + 混合召回"的完整形态，并诚实给了优缺点。
- 大模型使用经验扎实：聚合器（LiteLLM）、按 task type 路由、降级场景都答到了。
- 中转站问题处理得体：诚实承认 + 区分灰产/正规 + 落到自建 gateway 的工程判断。
- AI 协助工作有事例，呼应了"AI 超级个体"的方向。

### 风险点（下来要补）：
1. **架构设计题的"质量判断"被反问住**——"路由时任务还没执行怎么判断效果"这题如果当场没答好，下来要把"离线基线 + 在线反馈 + exploration"这套背熟，这是路由引擎的标准答法。
2. **中转站话题敏感**——虽然处理得体，但提了"类灰产"风险。后续如果还有京东流程，**别主动提中转站**，直接谈 OpenRouter / 云厂商 / 自建 gateway 即可。
3. **项目"独立负责"反复被追问**——三场面试（卓誉/Abound/京东）都在确认角色。统一用"技术 end-to-end 责任在我 + 团队协作执行 + PM 管流程"的框架，别再让"独立"被误解成"单打独斗"。

### 下来必做：
1. **把路由引擎架构题练到能口述**——组件、数据流、三个需求落地、四个追问，闭眼能讲。这是架构师岗的硬通货。
