# 货拉拉 · 大数据平台开发工程师 · 面试整理与答案

> **转写说明**：本次转写包含大量双方声道回声，“你:”后面重复面试官原话的部分不应视为独立回答。`CodeWiki/Cloud Code/Q Code/Deep Wiki/OpenClaw` 等名称可能存在语音识别误差，本文只在不影响判断的地方采用规范写法；产品版本、开源状态、团队规模、上线范围和指标数字仍需本人按项目材料确认。
>
> **面试性质**：这是一场约 30 分钟的项目深挖面，岗位为 **大数据平台开发工程师**。实际问题集中在 CodeWiki、Agent Memory、代码版本更新、记忆遗忘与相对时间处理，最后进入“关闭 AI Coding 后现场写代码”的环节；转写在出具体题目前结束。因此，本场并不能证明候选人的 Kafka、Flink、Spark、Hive、SQL 或大数据平台生产能力。
>
> **一句话结论**：本场属于 **“AI 项目有匹配度，但大数据岗位核心能力尚未被验证，且记忆系统的遗忘和时间语义回答偏弱”**。CodeWiki 的图谱、源码引用和版本文档有一定工程价值；但面试官真正关心的“什么记忆保留、什么记忆衰减、相对时间怎样落库”没有被回答成确定的数据模型和生命周期策略。最后要求关闭 AI Coding，说明后续很可能用现场代码检验基础编程能力。

### 0.3 面试官真正关注的能力

1. **项目是不是实际做过。** 追问节点、关系、版本、文档审核和接入形态，都是在确认候选人能否从概念落到数据结构和流程。
2. **CodeWiki 的价值是否独立于模型。** 如果只是把几段代码交给模型生成文档，成熟 Coding Agent 很容易替代；必须说明持久索引、版本视图、团队复用、源码引用和确定性关系的价值。
3. **Memory 是否有真正的数据治理。** “四层结构 + LRU + 大模型判断 update/merge”还不是完整方案，面试官继续追问了遗忘频率、事实更新和相对时间，说明他关心生命周期和语义正确性。
4. **是否具备大数据平台基本功。** 本轮没有问到并不代表岗位不需要；最后安排关闭 AI Coding，很可能把编程基础留到后续验证。

### 0.4 本场最大失分点

#### 失分点一：岗位是大数据平台，但自我介绍没有主动对齐大数据能力

候选人讲了 Python、NumPy、FastAPI、tree-sitter、GraphRAG 和 Memory，却没有说明：

- 是否做过 Kafka、Flink、Spark、Hive、ClickHouse 或数据湖；
- 是否负责过数据采集、调度、实时计算、离线数仓、质量校验或监控；
- Java 后端经历中具体的数据链路、吞吐、延迟和故障处理是什么。

这会让面试官难以判断“AI 项目候选人”是否适合“大数据平台开发工程师”。

#### 失分点二：把记忆衰减回答成 LRU 分层

LRU 解决的是缓存淘汰，不等于人类记忆或业务记忆的遗忘策略。低访问频率的记忆可能是一次性但极其重要的安全规则；高频访问的错误事实也不能因为访问频繁就提升到 Persona。

#### 失分点三：相对时间没有在写入时明确归一化

“保存消息时间戳，模型以后看到昨天就能推断”太依赖模型；正确做法应是保存原文，同时在写入时根据参考时间和时区解析出绝对时间或时间区间，并保留解析来源和不确定性。

#### 失分点四：现场编码题没有出现在材料中

面试官最后明确要求关闭 AI Coding，但转写已经结束。不能写成“代码题做对/做错”，也不能根据未记录的题面编造现场表现。

### 0.5 结果判断

**判断：中性偏弱，关键取决于后续代码题和大数据技术面。**

- 如果岗位实际偏 AI 平台或代码知识工程，CodeWiki 和 Memory 有继续比较的价值。
- 如果岗位要求实时/离线大数据平台经验，本场没有提供足够证据，候选人处于待验证状态。
- 现场代码题若表现稳定，可以弥补“AI 项目多、传统平台少”的疑问；若基础题再失分，进入下一轮的概率会明显下降。

## 二、项目一：CodeWiki 代码智能平台

### Q3. 现在 Claude Code 等工具可以一键生成项目文档，CodeWiki 的区别是什么？

**现场原答主线：** 项目在 2024 年下半年开发，当时 Claude Code、Q Code 尚未流行；Coding Agent 主要通过 grep 逐行检索，而 CodeWiki 先用 tree-sitter 做静态分析、建函数图、生成带行号的文档，并供团队复用以节省 Token。

**现场风险：**

- 不能把现代 Coding Agent 简化成“只会 grep”；它们会组合搜索、读文件、语言服务器、Repo Map 和工具调用。
- 不能只用“更精确”作结论，没有任务集和基线就无法证明。
- 项目早期时间点可以说明立项背景，但不能成为今天仍然不可替代的充分理由。

**推荐答案：**

> 我不会把 CodeWiki 定位成“比 Claude Code 更聪明”，也不把 Coding Agent 简化成 grep。对个人、小仓库、一次性问题，直接让 Coding Agent 探索通常更快；CodeWiki 的价值在团队共享和长期维护的代码事实层。
>
> 第一，它把仓库解析成带版本的符号和关系图，调用方、实现关系和模块依赖是可复用的确定性事实；第二，Wiki 页面保留 `repository、revision、file、line range`，可以从自然语言说明回到源码证据；第三，同一仓库被多人或多个 Agent 反复查询时，索引、文档和评测结果可以复用，不需要每个人重新消耗上下文；第四，代码变更后可以按 revision 和影响范围增量更新，保留历史版本。
>
> 所以替代关系取决于场景：一次性探索用强 Agent，跨模块查询、团队知识沉淀、版本对照和可审计引用用 CodeWiki。是否值得建设，应比较正确率、耗时、Token、索引成本、更新延迟和引用新鲜度，而不是泛称“更精确”。

### Q4. 图谱节点和关系有哪些？

**现场原答：** 函数是最小节点；另有 file、class、function；关系包括调用、导入、继承、实现。

**推荐答案：**

> 节点分层设计：仓库/版本、目录、文件、类、函数或方法、接口、Endpoint、Schema、配置项都可以是节点；函数通常是最小可解释单元，但不是唯一单元。边包括 `contains、defines、imports、exports、calls、references、inherits、implements、routes_to、uses_config`。
>
> 每条边至少保存方向、类型、来源文件和行号、所属 revision、解析方式和置信度。`contains/defines/imports` 相对确定；跨文件 `calls/references` 在动态语言、重载、反射和类型信息不足时可能是启发式推断，不能包装成编译器级完整调用图。
>
> 数据库中不是只存“节点 A、节点 B、关系”三个字段，还要存稳定 ID、版本、路径、符号签名、内容 Hash 和 provenance，否则无法处理重命名、分支、删除和历史查询。

### Q5. 图谱如何检索？输入、输出和中间过程是什么？

**现场原答：** 先让模型生成粗略目录；再用向量和 BM25 融合召回前三个节点；再沿 GraphRAG 扩展相邻节点，打包给模型生成 Wiki，循环完成目录。

**推荐答案：**

> 输入有两类：一类是文档规划得到的页面目标，例如“订单模块的调用链”；另一类是用户自然语言查询，例如“谁调用这个支付函数”。系统先从符号名、路径、全文和可选向量中找到 Seed，再根据问题选择关系类型和最大跳数进行图扩展。
>
> 排序不能只固定前三个节点，要综合关键词匹配、语义相似度、图距离、节点类型、源码新鲜度和边置信度，并受最大节点数和 Token Budget 约束。输出不是裸文本，而是带 `node_id、relation、path、line range、revision` 的 Context Pack；模型据此生成 Wiki 或回答，服务端再校验引用和结构。
>
> 文档生成可以采用“先规划目录、再逐页取证、最后生成”的流程，但规划结果不是事实。每一页都应重新检索允许的源码证据，并在生成失败时重试、降级为 Draft 或要求人工审核。

### Q6. 没有代码注释时，怎么知道函数功能？

**现场原答：** 让大模型先生成说明，缺少注释时标记，再由业务人员人工审核后放到平台。

**推荐答案：**

> 先区分确定性事实和模型解释。函数签名、参数、返回类型、调用方、被调用方、读写表和路由可以由静态分析或配置直接得到；函数的业务意图、异常语义和模块职责需要结合调用链、测试、日志和源码上下文，再让模型基于证据解释。
>
> 输出必须带 Source Ref，并标注哪些内容来自源码、哪些是模型推断、哪些没有证据。若没有注释且调用关系不足，应该输出“无法确认”或低置信度，而不是生成一段看起来完整的业务描述。人工审核是质量门禁，但不能代替自动引用校验、版本校验和回归样本。

### Q7. 代码变动后，怎样更新文档？

**现场原答：** 以生产版本为单位，用 Git diff 找增量代码，重新解析并标注版本号；平台下拉列表可以查看旧文档和新文档。

**现场优点：** 具备 revision、增量更新、历史查看意识。

**现场不足：** “Git diff 精确，所以基本不会错”不成立；diff 行不能直接等价于符号变化，重命名、移动、跨文件依赖和删除边都需要重新建图与校验。

**推荐答案：**

> 每个索引和 Wiki 页面绑定不可变 `repo_id + revision`。新版本到达后先读取 parent revision 和新 revision 的 diff，再通过内容 Hash、符号签名和稳定 ID 判断新增、修改、删除、移动和可能的重命名。
>
> 修改文件需要重新解析 AST、更新受影响的符号和关系；删除符号要删除或标记其 Chunk、向量和图边；被调用方、接口实现和模块文档可能受到间接影响，需要根据反向关系生成 Dirty Set，而不是只重生成 diff 行所在页面。新图、索引和文档先在临时 revision 中构建并校验，成功后再原子切换为可见版本。
>
> 旧版本只读保留，查询必须显式带 revision；如果当前工作区有未提交改动，要标记 dirty，不能让旧索引冒充当前代码。校验包括解析失败率、引用行号、节点数量、删除边、文档结构和抽样人工审核。这样才是“可回滚、可审计、可发现错误”的增量更新。

### Q8. 现在 AI Coding 工具很强，CodeWiki 能被替代吗？

**推荐答案：**

> 部分能力会被替代，但不是所有场景。个人 Agent 已经可以很好地完成一次性仓库探索、代码问答和局部文档生成，CodeWiki 不应把这些能力包装成自己的独占价值。
>
> 仍有差异的部分是团队级持久知识、确定性依赖关系、跨版本对照、权限隔离、来源审计和增量更新。CodeWiki 可以作为 MCP/Tool 提供给 Coding Agent：Agent 负责理解任务和决定调用，CodeWiki 负责返回带 revision 和源码引用的代码事实。
>
> 如果直接使用 Coding Agent 在正确率、新鲜度和总成本上更好，就应缩小 CodeWiki 范围，而不是为了保住平台继续堆图。真正要验证的是三组基线：原生 Agent、CodeWiki 检索、CodeWiki + Agent，在同一仓库问题集上比较答案正确率、引用正确率、Token、耗时和维护成本。

### 本项目复盘

**得分项：**

- 能讲清函数、文件、类和调用/导入/继承等基本图模型。
- 能说出 GraphRAG、BM25、向量融合和源码行号追溯。
- 具备版本下拉、Git diff 和人工审核意识。
- 能说明项目立项时间与后续 MCP 演进。

**失分和改进：**

- 不要说现代 Coding Agent 只是 grep。
- 不要以“更精确”替代对照实验。
- Git diff 是变更输入，不是完整一致性保证。
- 需要补 stable ID、删除边、重命名、Dirty Workspace 和原子发布。
- 代码文档生成必须区分静态事实、模型推断和人工审核。

## 三、项目二：Agent Memory 与上下文治理

### Q9. 怎么知道哪些记忆需要保留，哪些可以忘掉？

**现场原答：** 用 LRU；高频使用的记忆提炼到更高层，低频使用的留在较底层；系统分 L0 原始对话、L1 结构化事实、L2 场景记忆、L3 用户画像。

**这是本场最重要的概念纠偏题。**

**问题：**

- LRU 是缓存淘汰算法，只按最近访问时间，不理解业务重要性。
- “高频访问就提升到 Persona”会把临时热点误固化为长期画像。
- 低频不代表不重要，例如一次性的密码变更、合规约束或用户明确偏好。
- 不能把 L0 原始证据直接遗忘后再指望 L1-L3 完全恢复原意。

**推荐答案：**

> 我会把“是否值得长期保留”和“是否当前放在热缓存”分成两个决策。L0 原始对话是可审计证据，通常追加保存或归档，不用 LRU 直接删除；L1 是带来源和作用域的原子事实；L2 是可重建的主题场景；L3 只保留跨任务稳定、对后续回答确实有帮助的 Persona。
>
> 重要性由多因素决定：用户是否明确要求记住、事实置信度、是否影响安全/权限/业务约束、跨会话复用价值、最近性、访问频率、是否仍然有效、冲突状态以及隐私保留策略。访问频率只是一个信号，不是唯一晋升条件。
>
> LRU 或 TTL 可以用于 L1/L2 的热缓存和计算资源回收；冷数据仍可在归档层按权限保留。L3 更新要有阈值、来源和可回滚版本，不能每次访问都重写 Persona。用户要求删除时，要从在线索引、缓存、派生场景、画像和备份中执行删除传播。

**可以使用的简化评分：**

```text
importance = explicitness
           + safety_or_constraint
           + confidence
           + cross_task_reuse
           + recency
           + access_signal
           - staleness
           - contradiction
```

这不是必须写成固定公式，但必须说明规则和模型共同判断、风险字段优先、证据可回查、低置信不晋升。

### Q10. L0-L3 四层分别是什么？

**推荐答案：**

> - **L0 原始证据**：按会话和消息时间保存原始对话，作为审计、回查和重建来源；不能把模型注入的 Prompt 当作用户原话重复捕获。
> - **L1 原子记忆**：从新增消息中抽取事实、偏好、约束和任务状态，保存 source id、事件时间、写入时间、scope、置信度和生命周期。
> - **L2 场景记忆**：将相关 L1 组织成项目、主题、任务或关系，提供导航和上下文摘要；它可以重建，不应成为唯一真相。
> - **L3 Persona**：只保留跨场景稳定、长期有价值的背景或偏好，更新保守，必须可追溯到 L1/L0。
>
> 召回时不应每轮把四层全部注入：L3 提供稳定背景，L1 提供当前相关事实，L2 按需下钻，L0 用于核对原话和证据。长期记忆与单任务工具结果 Offload 也要分开，后者主要解决当前窗口过大。

### Q11. 记忆条目随着时间推移需要更新，遇到 A 变 B 怎么处理？

**现场原答：** 从 L0 提炼到 L1 时让大模型看已有 L1，判断 update 或 merge。

**推荐答案：**

> 先按实体、属性、scope 和候选时间范围召回旧事实，再判断新内容是新增、修正、并存还是冲突。`update` 表示同一属性在同一作用域被明确改成新值；`merge` 表示新旧内容互补；如果时间、项目或环境不同，两个事实可以同时成立；证据不足时进入 `conflict` 并澄清。
>
> 在线视图保存当前有效版本，历史层追加保存原始证据和 `supersedes/contradicts` 关系，不能只覆盖旧 JSON。模型可以提出动作，但服务端要校验实体、时间、权限和 schema；高风险事实不能只由 Prompt 决定。
>
> 例如用户说“这个项目采用 A”，第二天说“改成 B”，如果项目和属性相同且第二句话是明确决策，就将 B 标为当前版本、A 标为 superseded；如果用户说“另一个项目采用 B”，则应建立不同 scope，而不是覆盖 A。

### Q12. “昨天、今天”这样的相对时间，最终怎样存？

**现场原答：** 保存对话时间戳，模型读取原话时结合时间戳理解；必要时可以调用 Python 工具判断。

**主要问题：** 这把时间解析推迟到模型读取阶段，容易在异步处理、时区切换和跨天检索时产生歧义。

**推荐答案：**

> 原文必须保留“昨天/今天”，因为它是用户真实表达；同时在写入 L0/L1 时，用消息的 `reference_time`、用户时区、locale 和时间解析器把它解析为绝对时间或时间区间。数据至少保存：
>
> - `raw_text`：原始相对时间表达；
> - `event_time_start/end`：解析后的时间点或范围；
> - `reference_time`：说这句话时的时间；
> - `timezone`：使用的时区；
> - `resolver_version/confidence`：解析器版本和置信度；
> - `source_id`：原话引用。
>
> 例如用户在 `2026-07-31 09:00 Asia/Shanghai` 说“昨天上线”，默认解析为 `2026-07-30` 的本地日期范围，而不是系统当前日期。若“昨天”指的是业务账期、相对某个事件或跨时区，系统要保留未决状态并追问，不能让模型自行猜。查询和冲突判断优先使用标准化时间，展示时再根据用户时区还原自然语言。

### Q13. Memory 是本地 Skill/插件，还是一个服务？

**现场原答：** 在用户本地跑服务，接入 Coding Agent 的记忆层，不是 Skill；类似 Hook，所有对话经过处理、加载、存入和提取。

**推荐答案：**

> 当前形态可以准确描述为**用户本地的 Memory Service/Daemon，通过宿主 Hook 接入 Coding Agent**，而不是把全部逻辑写成 Skill。Skill 适合描述 Agent 的使用流程；本地服务负责持久化、抽取、索引、召回和版本治理。
>
> 一轮对话进入时，Hook 先读取原始用户输入和当前 scope，按需召回记忆；对话完成后把原始输入和工具结果写入本地 outbox，再异步抽取 L1-L3。服务不可用时，主 Agent 至少要能继续执行，不应因为记忆插件挂掉而阻塞普通任务；但要记录 outbox、重试和丢失告警。系统注入的 `<relevant-memories>` 不能再次作为用户原话被 Capture，避免记忆自我污染。
>
> 如果未来要支持多 Agent 或团队平台，可以把 Core 做成网关/Sidecar 服务，但必须引入用户、项目、Agent 和权限 scope；本地部署并不自动等于没有隐私和删除风险。

### Q14. 这个记忆系统和上下文压缩有什么关系？

**推荐答案：**

> 长期 Memory 解决跨会话事实保存和召回；Context Offload 解决当前任务中工具输出过大。长期链路关注事实的生命周期、冲突、权限和删除；短期链路关注 Token 预算、任务状态和原文可恢复。
>
> 工具输出外置时，原文写入 Artifact Store，活跃上下文只保留结构化摘要、关键状态和 `result_ref`。关键错误码、决策、约束和副作用不能靠 Top K 丢弃；BM25/向量是后续取回工具结果的手段，不是压缩时的重要性判定。

### 本项目复盘

**得分项：**

- 有 L0-L3 分层、结构化事实、场景和 Persona 的完整框架。
- 能举出 A 技术改 B 技术的事实冲突例子。
- 知道本地服务通过 Hook 接入，而非简单 Skill。
- 意识到相对时间需要时间戳和 Python 工具辅助。

**失分项：**

- LRU 被当作记忆遗忘策略，缺少语义重要性和隐私保留边界。
- 让大模型直接判断 update/merge，缺少版本、scope 和服务端校验。
- 相对时间没有在写入时解析，过于依赖模型运行时理解。
- 没有讲服务故障、异步 outbox、失败重试和记忆自我污染。
- “用户本地服务”没有说明数据格式、索引、scope 和删除传播。

## 五、现场代码题：转写未记录题面

### Q17. 关闭 AI Coding/代码补全后现场写代码

**现场信息：** 面试官在约半小时处问“现在在电脑旁边吗”，要求打开 IDE，并关闭 AI Coding 或代码补全能力；转写到此结束，没有记录题目、输入输出、代码、测试和评价。

- 不能说题目是 LRU、二叉树、滑动窗口或某道具体 LeetCode；
- 不能把“准备关掉工具”写成“现场手写表现良好”。

**正确的现场答题流程：**

1. 先确认语言、函数签名、输入规模、是否允许修改输入和异常约束。
2. 用自己的话复述题目，并先给一个简单样例和边界样例。
3. 先说朴素方案，再说明瓶颈和优化方向。
4. 写代码时保持变量、循环不变量和退出条件清楚。
5. 主动测试空输入、单元素、重复值、边界数值、极端规模和非法输入。
6. 最后说明时间复杂度、空间复杂度、线程安全或数据溢出风险。

**大数据平台岗位优先准备的代码类型：**

| 题型 | 重点 |
|---|---|
| HashMap/滑动窗口 | 频次、窗口收缩、边界和 O(n) 复杂度 |
| Top K/海量数据 | 堆、分桶、分治和内存上限 |
| LRU/TTL Cache | HashMap + 双向链表；过期、并发和容量边界 |
| 区间/时间窗口 | 合并、排序、事件时间和跨天边界 |
| 二叉树/图 | DFS/BFS、visited、栈深度和复杂度 |
| 生产小题 | 幂等消费、批量聚合、重试和顺序处理的伪代码 |

**如果被问 LRU，标准口述：**

> O(1) 查询和更新需要 HashMap 定位节点，双向链表维护最近使用顺序。访问或写入时把节点移到头部，超容量时删除尾部；更新已有 key 不增加节点。若用于并发服务，还要说明锁粒度、读写并发、TTL 和过期清理，不能把算法题的单线程实现直接当生产缓存。

## 六、本场理论题与大数据岗位八股单列

> 本节分成“本场实际涉及的理论题”和“大数据平台高概率补题”。后者不是本次转写中的真实提问，不应在复盘里写成面试官已经问过。

### 6.1 本场实际涉及的理论题

#### 理论 1：LRU 能不能直接表示记忆遗忘？

> 不能。LRU 只按最近访问时间淘汰缓存；业务记忆还要考虑明确记忆指令、安全约束、置信度、scope、时效、冲突、跨任务复用和隐私政策。LRU 可以用于热缓存，不能作为唯一记忆生命周期策略。

#### 理论 2：长期 Memory 和 Context Compression 有什么区别？

> 长期 Memory 关注跨会话保存、更新、召回和删除；Context Compression 关注当前上下文超限时怎样减少活跃 Token。压缩最好保留外部原文引用，Memory 则要治理事实版本和权限。

#### 理论 3：相对时间应该怎样处理？

> 原文保留，写入时根据 reference time 和 timezone 解析为绝对时间或区间，并保存解析置信度和来源。不能每次检索时让模型临时猜“昨天”对应哪一天。

#### 理论 4：update、merge 和 conflict 有什么区别？

> 同一实体、属性、scope 的新值替代旧值是 update；新旧互补是 merge；作用域、时间或来源无法统一时是 conflict。保存历史和 supersedes/contradicts 关系，不直接覆盖原证据。

#### 理论 5：MCP、Skill、Hook 和 Service 的边界是什么？

> Skill 是流程知识，Hook 是宿主生命周期接入点，Service 是持久化和计算能力，MCP 是标准化工具/资源暴露协议。Memory 可以由 Hook 调 Service，也可以把 recall/search 暴露为 MCP；它们不是同一层概念。

#### 理论 6：GraphRAG 为什么需要版本和引用？

> 图关系会随代码变化，只有绑定 repo、revision、节点 ID、文件和行号，回答才可复核。引用不只是展示链接，还用于检测陈旧索引、更新影响范围和审计模型输出。

#### 理论 7：Git diff 能否直接保证代码文档增量正确？

> 不能。diff 是文件级变更线索；还要重新解析受影响符号、更新删除/新增/重命名节点和关系，并按反向依赖生成 Dirty Set。新索引校验通过后原子切换，旧 revision 保留回滚。

#### 理论 8：BM25 与向量检索的关系是什么？

> BM25 擅长标识符、错误码和精确关键词；向量检索擅长语义改写；可以用 RRF 或归一化分数融合。它们只负责候选召回，不能代替代码图关系、权限过滤或重要性规则。

### 6.2 大数据平台高概率八股补题

#### 八股 1：Kafka 如何保证消息不丢？

> 生产端使用 `acks=all`、幂等生产者和合理重试；Broker 配置副本与最小 ISR；消费端只有在业务处理成功并完成幂等落库后提交 offset。至少一次投递通常意味着可能重复，因此业务侧要用业务键、去重表或幂等 Upsert 消除重复。不能简单宣称端到端 exactly-once。

#### 八股 2：Kafka 分区、顺序和消费组怎样权衡？

> 同一 key 进入同一分区可以保证分区内顺序；分区数决定并行度上限；一个消费组内一个分区同一时刻主要由一个消费者处理。扩容、重平衡会影响延迟和局部状态，不能要求全 Topic 全局顺序而又保持高并行。

#### 八股 3：Flink watermark 和窗口解决什么问题？

> 事件时间按事件发生时间计算，watermark 表示系统预计某时间之前的事件基本到齐；窗口按时间范围聚合，允许迟到数据通过 allowed lateness 或侧输出处理。处理时间延迟低但不适合严格事件时间分析。状态需要 checkpoint 保证故障恢复。

#### 八股 4：Flink checkpoint 与 exactly-once 是什么关系？

> checkpoint 持久化算子状态和消费位置；恢复时从一致性快照继续。端到端 exactly-once 还要求 Sink 支持事务或幂等提交，不能只因为开启 checkpoint 就声称全链路 exactly-once。

#### 八股 5：Spark 和 Flink 怎么选？

> Spark 更适合大规模离线批处理、SQL、成熟数仓作业和微批；Flink 更适合持续流处理、事件时间、低延迟状态计算和复杂窗口。实际选择还要看团队生态、运维、数据源、延迟目标和回放方式，不能简单说“Flink 一定更快”。

#### 八股 6：大数据 ETL 怎样做到幂等？

> 为批次或事件定义稳定业务键，记录处理版本和 watermark；写入使用 Upsert、去重或分区覆盖，任务重试不会产生重复结果。外部副作用要有 outbox 或幂等请求键；不能只依赖“任务通常只执行一次”。

#### 八股 7：迟到数据和重复数据怎样处理？

> 先区分事件时间、处理时间和摄取时间；通过 watermark、allowed lateness、去重键和修正任务处理迟到。结果表需要能重算或增量修正，指标必须记录数据版本和 completeness，不能把迟到数据当零。

#### 八股 8：数据质量至少检查什么？

> 完整性、唯一性、及时性、范围、枚举、主外键关系、分区数量、总量和上下游对账。异常进入隔离区或告警，报表要显式标记缺失，不能把空值默认为 0 并让下游继续传播。

#### 八股 9：海量 Top K 怎么做？

> 单机数据可以用大小为 K 的最小堆，时间 O(n log K)、空间 O(K)；分布式场景先在各分片求局部 Top K，再合并全局候选，避免全量排序。若数据无法放内存，还要考虑外排、分桶或近似算法，并说明误差和资源上限。

#### 八股 10：如何处理数据倾斜？

> 先通过 key 分布、任务耗时和 Shuffle 指标确认倾斜；再按场景使用热点 key 加盐、两阶段聚合、广播小表、过滤异常数据或调整分区。不能盲目增加并行度，因为单个热点 key 仍会落到同一分区。

### 8.2 第二优先级：把 Memory 遗忘题改成 60 秒答案

> LRU 只用于热缓存，不定义业务记忆的价值。原始 L0 作为证据归档，L1 保存带来源、时间和 scope 的事实，L2/L3 是可重建的场景和稳定画像。晋升和衰减综合明确记忆、置信度、安全约束、跨任务复用、最近性、访问信号、过期和冲突；低频不等于不重要，高频也不等于应该写进 Persona。模型提出动作，服务端校验并保留版本；用户删除要传播到派生层和索引。

### 8.3 第三优先级：把时间语义讲成数据模型

至少能写出：

```text
raw_text = "昨天上线"
reference_time = 2026-07-31T09:00:00+08:00
timezone = Asia/Shanghai
event_time_start = 2026-07-30T00:00:00+08:00
event_time_end = 2026-07-30T23:59:59+08:00
resolver_version = v1
confidence = high
source_id = conversation:...
```

说明：原文用于展示和审计，标准化时间用于查询和冲突，解析不确定时保存区间或向用户确认。

### 8.4 第四优先级：准备现场编码

## 九、速记版结论

### 9.1 三句必须修正的回答

1. **CodeWiki 不只是“比 Coding Agent 更精确”，它提供版本化、可追溯、团队可复用的代码事实；是否更好要用基线评测。**
2. **LRU 只是缓存淘汰，记忆遗忘要综合语义重要性、置信度、scope、时效、安全和删除策略。**
3. **相对时间要保留原文，同时按 reference time 和 timezone 在写入时解析成绝对时间/区间，不能只等模型以后猜。**

### 9.2 一分钟岗位匹配答案

> 我的经历更偏 Java 后端与 AI 应用中的数据链路，而不是已经覆盖所有大数据组件。我做过采集、清洗、指标计算、源码索引、版本增量、记忆持久化和召回，这些经验可以迁移到平台的数据契约、任务状态、幂等更新和质量校验。Kafka/Flink/Spark 等组件如果是岗位核心，我会按真实使用边界说明当前差距，并通过现场编码和系统设计证明基础能力，而不是把 NumPy 或 GraphRAG 直接包装成大数据平台经验。

### 9.3 本场最终判断

> 有项目相关性，但大数据岗位能力覆盖不足；Memory 题的遗忘与时间语义是最需要立即补强的部分。转写没有记录实际代码题，因此结果保持未知，不能把面试官要求关闭 AI Coding 解读成通过或淘汰。
