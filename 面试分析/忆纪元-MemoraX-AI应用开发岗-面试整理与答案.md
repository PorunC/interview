### 0.2 面试官真正关注的能力

1. **能否从“使用框架”上升到“设计框架”。** 面试官不断把问题从 FastAPI 好不好用，推进到默认与扩展、显式依赖、构建期验证。这不是普通八股，而是在测试系统抽象能力。
2. **能否把记忆项目讲成可验证的方法，而不是四层结构。** “L0-L3”只是组织方式；公司更关心什么值得记、谁能知道、怎样更新冲突、如何评测，以及与其他方案相比是否真的更好。
3. **是否尊重证据边界。** 面试官明确追问评测机制和第三方对比。忆纪元自己公开强调基准和 Agentic RL，因此候选人的数字、版本、基线和对比方法会被严格审视。
4. **是否适合早期创业团队。** 对方使用多种 Coding Agent、内部 Provider、托管基础设施，并在搭建 AI Review。岗位需要快速交付，但不能只有“AI 帮我写代码”。

### 0.3 结果信号

**正面信号：**

- 面试持续到约定结束时间，面试官完整深挖三个项目，并花较多时间讨论框架设计，说明没有在早期快速结束。
- 对方主营记忆系统，互动小说业务又需要世界、角色和玩家的长程记忆，和候选人的第三个项目高度重合。
- 面试官在反问环节详细介绍技术工具、Skill、CI Review、托管基础设施和具体业务挑战，信息开放度较高。
- 周报项目的历史补采、状态记录和指数退避体现了一定生产工程意识。

**风险信号：**

- 没有当场约下一轮或给明确正向评价，结束语保持中性。
- 框架比较大量停留在“轻重、生态、开发快慢”，未稳定落到类型系统、运行模型、扩展机制和治理边界。
- “约定优于配置”的坏处被讲成“配置太多”，概念上有矛盾；后续错误处理方案又落到“每处 try/catch”，暴露工程方法风险。
- 编译期 DI 题中先答“懒加载”，方向与面试官要的“尽早发现缺依赖”相反。
- 记忆评测的名称和数字出现多个口径，且对 Mem0 的功能判断过于绝对。

### 0.4 综合判断

**判断：中性偏正，但不是稳过。**

- 如果岗位主要需要 **Agent Memory / AI 应用工程**，候选人的领域匹配足以支持继续比较。
- 如果岗位更看重 **框架、平台和基础设施设计**，本场设计题表现偏弱。
- 忆纪元是一家非常早期、研究导向明显的公司，下一轮大概率会继续追问 Benchmark、记忆治理和互动叙事领域设计，而不是回到普通 Java 八股。

## 二、项目一：AI 周报系统

### Q2. 周报数据从哪些系统采集？

**推荐答案：**

> 数据主要来自三类内部运维系统：第一是 Kubernetes 的工作负载和资源运行数据；第二是分布式 Trace 和调用链数据，用于统计接口执行时间和异常链路；第三是数据库性能与事务监控数据，例如慢 SQL、长 SQL 和长事务。各数据源通过获批 API 或只读接口采集，再统一成周报指标模型，保留来源、统计窗口、采集时间和状态。
>
> 我不会把原始日志直接交给 LLM。采集、清洗、聚合和指标计算都是确定性代码；LLM 只读取已经验证的指标和必要证据，负责生成易读文字。

### Q3. 数据采集遇到过什么难点？API 不稳定怎么处理？

**现场原答：** API 每分钟最多约 10 次；失败后最多重试 10 次，采用 1、2、4 秒递增等待；用 `pending/success` 状态记录采集结果。

**评价：** 已经具备“指数退避 + 持久状态”的正确方向，但还缺四个生产细节：全局限流、错误分类、随机抖动和最大耗时。每个调用自己 `try/catch` 并重试，多个任务并发时仍可能一起打爆限额。

**改进答案：**

> 这个问题要拆成限流和失败恢复两层。限流不是每个任务各自 sleep，而是在连接器级使用共享 token bucket，确保所有 worker 合计不超过每分钟 10 次。遇到 429 时优先遵守 `Retry-After`；只对超时、429 和可恢复的 5xx 重试，鉴权失败、参数错误等 4xx 直接标记永久失败。
>
> 重试采用有上限的指数退避加 full jitter，限制最大次数和总耗时，避免多个任务同步重试。每个采集窗口持久化 `source + window_start + window_end + status + attempt + next_retry_at + last_error`，worker 用租约领取任务；失败后由调度器重新投递，不在请求线程里无限等待。
>
> 超过重试阈值进入死信并告警，但不会阻塞其他数据源。最终周报要显式标注缺失数据，不能把缺失误当成零。

### Q4. 23 日数据失败后，24 日、25 日怎样继续拉 23 日的数据？如何避免重复？

**现场原答：** 每天扫描最近 15 天仍为 `pending` 的日期，逐日重拉；成功数据不再处理，插入时避免键冲突。

**改进答案：**

> 采集任务以“数据窗口”而不是“执行日期”为主键。例如 23 日窗口固定为 `[23日00:00, 24日00:00)`；任务无论在 24 日还是 25 日执行，都使用这个原始窗口，不会错拉成当天数据。
>
> 数据库对 `source_id + window_start + metric_key` 建唯一约束，写入使用事务性 upsert，因此重放同一个窗口不会产生重复。任务状态至少区分 `pending、running、success、retryable_failed、permanent_failed`，并记录 attempt 和错误原因。
>
> 最近 15 天扫描更准确地说是**对账回看窗口**，不是“最多重试 15 次”。日常失败按 `next_retry_at` 调度；每天再对最近 15 天做 completeness reconciliation，发现状态成功但明细缺失或源端迟到数据时补采。超过保留窗口仍失败要报警和人工处理。

### Q5. LLM 的智能分段分析怎样做？为什么要分段？

**现场原答：** 按不同数据源使用不同提示词，分批调用，结果存数据库，最终用 SQL 汇总。

**改进答案：**

> 分段的单位不只按数据源，还应按周报语义章节和 token 预算。比如资源运行、调用链、慢 SQL、长事务分别有独立指标 schema 和分析规则。每段输入包含经过验证的指标、同比/环比基线、异常阈值和 metric id；模型按 JSON Schema 输出 `summary、anomalies、evidence_ids`，不能自由修改数值。
>
> 各段是 map 阶段，最终 reduce 不让模型重新计算数字，而是由程序按固定章节组装；如果需要总览，再给模型读取各段摘要，但总览中的数字仍要从指标表引用。这样能控制上下文、隔离单段失败，也方便单独重试和审计。

### Q6. 研发初期如何验证周报数据准确？

**现场问题：** 原回答只说“NumPy 计算、LLM 不算数”，没有直接回答如何验证数据是否准确。这是本项目明显失分点。

**推荐答案：**

> 我把准确性拆成三层验证。
>
> 1. **采集正确性**：检查时间窗口、时区、分页完整性、记录数、唯一键和源端总量；保留 source watermark 和采集审计。
> 2. **指标正确性**：为每个指标准备固定输入与期望输出的单元测试；上线前选择 4 到 8 周历史数据，与原人工报表并行跑，逐项核对差异并记录原因。
> 3. **生成正确性**：数字由程序计算，LLM 输出中的数字和 evidence id 回查指标表；不一致就拒绝该段并回退到模板。抽样人工评估只评可读性、重点和解释，不重新靠人肉算数。
>
> 上线后还监控数据缺失率、迟到率、重复率、指标差异和 LLM 校验失败率。系统成功不是“生成了文字”，而是数字可复算、来源可追溯、缺失可见。

### 本项目复盘

**得分：** 业务收益真实，失败补采讲得具体，明确不让 LLM 计算指标。

**需要修正：**

- 不要把 `pending/success` 直接称为幂等；幂等依赖稳定业务键、唯一约束和可重放写入。
- 不要把“用了 NumPy/Python”当作准确性证明；准确性来自测试、对账和审计。
- 不要用每个调用内部 `try/catch + sleep` 代替全局限流和持久调度。

## 三、项目二：CodeWiki

### Q7. 为什么要做 CodeWiki？是团队项目还是个人项目？

**推荐答案：**

> 背景是行内要求探索 AI 应用，同时部分存量系统存在注释和详细设计缺失。开发者接手陌生需求时需要逐文件追代码并反复询问原维护者，理解慢且容易遗漏跨模块影响。
>
> 这个方向由我提出并做技术 owner，但不是未经团队确认的个人玩具。我先用一个存量仓库做 PoC，验证能否生成带源码引用的模块说明和调用链；评审通过后再明确支持语言、数据权限、验收指标和接入范围。底层解析、统一 IR、图构建和核心检索由我主导，环境、业务验收和使用反馈由团队协作。

### Q8. 2024 年为什么需要做平台？现在直接让 Coding Agent 扫仓库不可以吗？

**推荐答案：**

> 2024 年下半年成熟的仓库级 Coding Agent 还没有现在普及，所以当时建设共享代码知识平台有明确价值。即使现在有 Claude Code、Codex 等产品，大仓库里仍有三类需求：团队共享的持久知识、确定性的依赖关系、以及按代码变更增量更新。
>
> 对单人、小仓库、一次性问题，直接让 Coding Agent 扫描更简单；CodeWiki 不应宣称全面替代它。CodeWiki 更适合作为企业代码知识底座，通过 MCP 暴露符号搜索、调用方、影响范围和带引用文档，让不同 Agent 复用一次索引结果。
>
> “公司有约 5000 名开发人员”只是潜在覆盖人群，不能直接当成真实用户或节省量。实际价值要报活跃用户、查询量、任务耗时和成功率。

### Q9. 支持哪些语言？你的熟悉程度如何排序？

**现场问题：** 先遗漏 Python、被提醒后补上，会让人怀疑语言适配边界没有提前梳理。

**推荐答案：**

> 当时版本支持 Java、Go、TypeScript 和 Python。底层不是四套完全独立系统，而是每种语言一个 adapter，将函数、类、模块、import、call 等映射到统一 IR；不同语言支持深度不同，我会列清 capture matrix，不用“支持”掩盖部分语法缺口。
>
> 个人熟悉度是 Java 最强，生产业务主要用 Spring Boot；Python 主要用于 AI 应用、数据处理和 FastAPI；TypeScript 用于 React 前端及部分 Node 工具；Go 能阅读和完成适配，但生产经验少于前三者。

### Q10. tree-sitter 已经是开源库，你自己开发了什么？

**推荐答案：**

> 我不会说“AST 解析器从零自研”，那不准确。tree-sitter 负责把源码解析成 CST；我开发的是上层多语言统一引擎：语言识别与 parser registry、各语言 query/capture spec、语言特有语法 augmenter、统一 `Symbol/Relation` IR，以及跨文件图构建。
>
> 确定性较高的边包括 contains、defines、imports、inherits；calls/references 在动态派发、反射、重载等场景可能只是启发式推断，因此每条边要保留 type、direction、confidence 和 provenance。上层 GraphRAG 才能区分硬事实和推断关系。

### Q11. 多维依赖图的节点和边是什么？怎样参与检索？

**推荐答案：**

> 节点包括 repository、module、file、class、function/method、endpoint 和 schema；边包括 contains、defines、imports、calls、inherits、implements、references 等。边要有方向、类型、来源位置和置信度。
>
> 在线检索不是把整张图塞给模型：先用符号、FTS 和向量找到种子节点，再按问题选择边类型和跳数扩展，例如修改接口时关注 callers、implementations 和 schema；然后按语义相关度、图距离、节点类型和置信度重排，在 token budget 内形成 context pack，并附源码引用。

### Q12. 已经有 AST 和依赖图，能否检测模块设计或架构级代码坏味道？

**现场原答问题：** 主要讲了 SonarQube 和内部流水线，实际上没有回答“CodeWiki 能否利用图做架构级检测”。面试官问的恰恰是 Sonar/Lint 较弱的跨模块层面。

**推荐答案：**

> 当前版本主要做文档和检索，没有正式上线架构坏味道检测，这一点要先说清。但现有图可以自然扩展出一层 Architecture Linter，它与 SonarQube 互补。
>
> 可检测的规则包括：模块依赖环、分层越界、禁止方向依赖、高 fan-out 的 God Module、跨域直接访问、接口实现泄漏、稳定模块依赖不稳定模块，以及变更历史和调用图结合后的高耦合热点。每条规则要输出具体路径和源码位置，而不是让 LLM 主观评价“代码很乱”。
>
> 规则和图算法负责确定性发现，LLM 只解释风险、给重构建议；建议仍需测试和人工 review。第一版可先做依赖环和层级规则，因为准确率和可解释性最高。

### Q13. MCP 在 CodeWiki 中的作用是什么？

**推荐答案：**

> GraphRAG 是内部知识组织和检索方法，MCP 是把能力提供给外部 Agent 的协议，两者不在同一层。我会把 `search_symbol`、`get_callers`、`get_dependency_path`、`get_impact_scope` 和 `read_wiki_page` 包装成只读 MCP tools。
>
> Agent 调用这些工具时可以复用团队已有索引，不必每次用 grep 全量探索；返回结果带 revision、source refs 和置信度。MCP 层还要做项目权限、结果大小限制、超时和审计，不能因为是只读工具就忽略源码泄露。

### 本项目复盘

**得分：** 立项背景可信，能说明技术出现的时间窗口；多语言统一抽象和 MCP 演进有实际价值。

**失分：**

- 语言清单不稳定。
- “tree-sitter 自研 AST 引擎”容易夸大，应明确开源底座与自研层。
- 面对架构坏味道问题绕回 SonarQube，错过展示图算法价值的机会。
- 5000 名开发人员不能替代真实采用数据。

## 四、跨语言 Web 框架与框架设计题

### Q14. Django、FastAPI、Express/Koa、Spring Boot 分别有什么设计特点？

**现场原答问题：** 使用“Python 简洁、FastAPI 快、Express 版本多、Spring Boot 重”来比较，偏主观且维度不统一。“MVP 用 Python，用户多了再重写 Java”也不是普适结论，重写成本通常很高。

**先如实交代使用边界：**

> Spring Boot 是我的生产主栈；FastAPI 在 AI 项目中实际使用较多；Django 只在学校阶段做过小项目；Express 有基础使用经验，Koa 没有生产经验。因此我可以比较它们公开的设计思路，但不会把少量使用说成熟练。

**推荐答案：**

| 框架 | 核心定位 | 默认能力 | 主要取舍 |
|---|---|---|---|
| Django | batteries-included Web framework | ORM、Admin、Auth、模板、迁移 | 约定多、整体性强，适合内容/后台型产品 |
| FastAPI | 类型提示驱动的 ASGI API 框架 | 路由、Pydantic 校验、OpenAPI、异步接口 | API 开发快；大型工程的模块治理需团队补充 |
| Express | 极简 Node middleware/router | 很少默认能力 | 灵活、生态大；架构、校验、DI 和规范需自行选择 |
| Koa | 更小的 async middleware kernel | 洋葱模型中间件 | 控制力高；完整 Web 能力需组合生态 |
| Spring Boot | opinionated enterprise application platform | IoC、Auto Configuration、Actuator、Data/Security/Cloud 生态 | 企业能力成熟；隐式自动装配、启动和调试复杂度更高 |

> 选型应看团队语言、领域复杂度、类型安全、依赖生态、延迟模型、部署环境和维护周期，而不是简单按“用户少用 Python、用户多用 Java”。FastAPI 也可以规模化，Spring Boot 也适合快速开发；性能瓶颈往往先在数据库、网络和业务设计。

### Q14.1. 当前使用哪个 JDK 版本？怎样看 JDK 17/21 的新能力？

**推荐答案：**

> 当前生产环境主要是 JDK 8，这是公司平台和存量系统的统一版本。我的生产经验因此以 Java 8 为主；对新版本有学习和个人实践，但不会说成已经在核心系统大规模投产。
>
> 新 LTS 版本的价值不只在减少样板代码。JDK 17 可以稳定使用 record、sealed class、pattern matching for `instanceof` 等能力；JDK 21 又提供虚拟线程、record pattern 和 switch pattern matching 等。record 适合不可变数据载体，sealed class 加模式匹配适合封闭领域状态，虚拟线程适合大量阻塞 I/O，但都要结合框架、监控和依赖兼容性评估。
>
> 如果从 8 升级到 17/21，我会先做依赖与构建插件盘点、完整回归和性能基线，再处理强封装、移除模块、反射访问和 JVM 参数变化，最后灰度迁移。升级不能只为了语法更短。

### Q15. Spring Boot 的“约定优于配置”带来什么好处和坏处？

**准确答案：**

> 好处是减少重复决策：目录、Bean 生命周期、配置键、组件组合和常见集成有默认方案，新成员可以快速理解，Starter 让团队复用经过验证的能力。
>
> 代价不是“配置文件一定更多”，而是**隐式行为增多**。某个 Bean 为什么出现、哪个条件触发了 Auto Configuration、配置值来自哪个 PropertySource、为什么换依赖版本后装配改变，这些问题可能难排查；当业务偏离默认假设时，覆盖机制和兼容性也会复杂。
>
> 改进方式是：合理默认值但允许显式覆盖；使用类型化配置和启动期校验；输出配置来源与生效值；提供 Condition Evaluation Report、Actuator 和依赖图；关键模块支持显式注册；升级时锁定依赖版本并做兼容测试。

### Q16. “每个可能报错的地方都 try/catch，再包装 AppException”是否合理？

**结论：不合理，属于需要主动修正的现场表述。**

> 到处 `try/catch` 会制造重复代码，容易吞掉异常类型、堆栈和根因，也可能造成同一错误多次记录。正确做法是：只在能够恢复、补充业务语义或跨边界转换时捕获；用领域异常表达可预期失败；在 Controller/消息消费等边界统一映射错误码和响应；保留原始 `cause`，日志只在责任边界记录一次，并通过 traceId 串联。
>
> 对 Spring 启动或自动配置失败，应该依赖 fail-fast 配置校验、健康检查、Condition Report 和结构化启动诊断，而不是业务代码逐处包异常。

### Q17. 如果从零设计一个 Web 框架，它应该提供什么能力？

**推荐答题方式：先定目标，再列内核，不要直接罗列功能。**

> 我会先限定目标：这是面向类型化后端 API、支持多人协作、要求显式依赖和构建期校验的框架。核心设计原则是 **小内核、显式组合、合理默认、可替换扩展、尽早失败、全链路可观测**。
>
> 最小内核包含：
>
> 1. Router 与 Request/Response 抽象；
> 2. Middleware/Interceptor pipeline；
> 3. 类型化输入校验和序列化；
> 4. 显式模块与依赖注入；
> 5. 生命周期和资源关闭；
> 6. 类型化配置、配置来源和启动校验；
> 7. 统一错误边界；
> 8. 日志、Metrics、Trace 和健康检查；
> 9. 测试 Harness 与插件 SPI。
>
> 数据库、认证、缓存和消息队列不硬编码进内核，而是标准扩展。默认值可以降低上手成本，但每个默认都应可观察、可覆盖，扩展点有兼容性契约。

### Q18. 怎样设计依赖注入，让依赖关系显式，并在编译期发现缺失？

**现场原答问题：** “懒加载 + 注解 + 容器 + 可视化”没有命中核心。懒加载会把错误推迟到第一次使用，和编译期发现相反；检查是否写了 `@Autowired` 也不能证明目标 Bean 存在、Scope 正确或不存在循环依赖。

**推荐答案：**

> 我会采用构造器注入和构建期生成，而不是运行时反射扫描。每个模块显式声明 provider、依赖类型和 scope；构建插件读取类型签名形成依赖 DAG，检查缺失 provider、重复绑定、循环依赖和 scope 泄漏，失败就中止编译。验证通过后生成工厂代码和依赖 manifest，运行时容器只负责实例化顺序、单例/请求作用域和关闭，不再猜依赖。
>
> 这类思路可以参考 Dagger 的 annotation processor、Micronaut/Quarkus 的 build-time DI。生成的 manifest 还能输出 DOT 图供审查，但可视化是辅助，类型和图校验才是正确性保证。
>
> 对确实需要延迟创建的昂贵依赖，可以显式使用 `Provider<T>` 或 `Lazy<T>`，但它必须已经通过构建期图校验，不能用懒加载掩盖缺依赖。

### 本段复盘

这是本场最明显的能力短板。面试官并非要求背某个框架 API，而是在观察：

- 能否先澄清设计目标；
- 能否区分默认、配置和扩展点；
- 能否区分构建期验证与运行时容器；
- 能否用类型系统和 DAG 解决问题，而不是继续加注解和规范。

## 五、项目三：Agent 长期记忆与上下文压缩

### Q19. 这套系统什么时候做？和哪些 Agent 配合？

**推荐答案：**

> 项目在 2025 年下半年开始，接入对象是行内采购或封装的 Coding Agent。架构上不绑定某个产品：OpenClaw 类宿主通过 hooks 适配，其他 Agent 可通过 Gateway/sidecar 调用统一的 `capture、recall、search、session end` 接口，核心记忆逻辑由宿主无关的 Core 承担。
>
> 需要准确说出实际接入过的宿主和只做过适配验证的宿主，不把“接口兼容”说成“多个业务已正式投产”。

### Q20. 长任务中的“幻觉”到底从哪里来？

**现场原答：** 模型固有幻觉、长上下文注意力稀释、重复工具结果冲突三方面都有。

**改进答案：**

> 我会先区分三类故障，因为它们的治理不同。
>
> 1. **模型固有事实幻觉**：模型生成无证据事实，需要 RAG、引用和工具验证。
> 2. **长上下文退化**：工具日志和重复历史占满窗口，关键信息 lost in the middle，表现为遗漏约束、重复动作或错误恢复；这更准确地叫 context degradation，不应全部归为幻觉。
> 3. **状态冲突**：同一工具多次返回不同结果，旧结果和新结果同时存在，Agent 不知道哪个是当前真相；需要版本、时间、任务状态和 superseded 关系。
>
> 我们的 Context Offload 主要解决第二类，并通过时间、引用和任务图缓解第三类；它不能消除模型固有幻觉。评测也要分别看任务通过率、错误事实率、重复工具调用和恢复成功率。

### Q21. L0-L3 怎样抽取、维护和搜索？

**推荐答案：**

> - **L0 原始证据**：按会话保存原始消息和时间，作为审计与回查入口；避免把系统注入的记忆再次捕获形成自我回灌。
> - **L1 原子记忆**：只从新增消息抽取 persona、episodic 和 instruction，带 source ids、时间和作用域。写入前先召回相似候选，再由语义判断执行 `store、skip、update、merge`。
> - **L2 场景**：把相关 L1 组织成项目、习惯、任务等场景块，解决单条事实碎片化问题。
> - **L3 Persona**：只保留跨场景稳定背景，增量更新，避免把一次事件固化成人格。
>
> 查询时，L3 和场景导航提供稳定背景；当前 query 触发 L1 的 BM25 + 向量混合召回和 RRF；需要主题细节时下钻 L2，需要核验原话时回到 L0。四层不是每轮全部注入。
>
> 维护不能只“比较时间戳”。时间新不代表一定正确，两个事实也可能作用域不同。冲突判断要看语义、来源、时间、项目 scope 和用户显式纠正，并保留历史版本关系。

### Q22. 除了集成工作，你自己设计的核心亮点是什么？

**现场问题：** 回答“分成四层”仍然是在描述结构，没有回答最核心的业务流程和技术取舍。

**推荐答案：**

> 我认为核心不是层数，而是 **证据可追溯的记忆生命周期 + 可恢复的上下文卸载**。
>
> 长期链路中，原始对话先保存，再增量抽取原子记忆；新记忆和候选旧记忆做 store/skip/update/merge，保留 source id，随后再生成场景和 Persona。短期链路中，大工具结果移到 refs，只把摘要、任务状态和 result_ref 留在上下文；当模型需要精确日志时能按引用恢复原文。
>
> 这两个链路共同解决“全塞会爆、只摘要会丢证据”的矛盾。我的主要设计工作是 Core 与宿主解耦、增量游标和调度、混合召回、冲突动作、Offload 引用和任务恢复。当前不足也明确：来源 ID 还不是逐字蕴含校验，事实置信度、时序模型、多租户和删除传播仍需完善。

### Q23. 如何评测记忆系统？这些数字分别代表什么？

**本场最高风险：指标口径混乱。**

现场出现了“40% 到接近 70%”“Token 降低 91%”“任务通过率提升 52%”“48% 到 76%”等说法。根据本地项目材料，能够稳定引用的口径是：

| 能力 | 数据集 | 基线 | 使用系统后 | 正确表述 |
|---|---|---:|---:|---|
| 长任务通过率 | WideSearch | 33% | 50% | 增加 17 个百分点，相对提升 51.52% |
| 长任务 Token | WideSearch | 221.31M | 85.64M | 降低 61.38% |
| 长期记忆问答 | PersonaMem | 48% | 76% | 增加 28 个百分点 |

**推荐答案：**

> 我会把长期记忆和短期 Offload 分开评测。WideSearch 测连续长任务，基线通过率 33%，使用系统后 50%；Token 从 221.31M 降到 85.64M。PersonaMem 测长期 Persona 问答，准确率从 48% 到 76%。这些都是特定数据集、模型和配置下的离线结果，不是线上平均收益。
>
> 评测 Harness 必须固定模型、prompt、context window、重试、超时和任务集，多次运行报告均值与方差。记忆链路还应分段测 L1 抽取 Precision/Recall、冲突动作 Macro-F1、Recall@K/MRR、答案证据一致率、错误记忆注入率和用户纠错后的残留召回率。只有最终任务分数，没有分段指标，很难定位提升来自哪里。

**口径纪律：**

- 不再说“OpenClaw 数据集 40% 到 70%”，除非能指出具体仓库、commit、任务和计算脚本。
- 不把 Token 降低 61.38% 说成 91%。
- 不把“增加 17 个百分点”和“相对提升 51.52%”混为一谈。
- 不把 PersonaMem 的 76% 说成系统整体准确率。

### Q24. 和 Mem0 相比效果如何？为什么不用现成方案？

**现场风险：** 直接说 Mem0 “只有两层、没有场景和画像、Token 更多”容易被反驳，因为开源版、托管版和不同年份版本能力会变化；没有固定版本、模型和预算的对比也不公平。

**推荐答案：**

> 我不会说 Mem0 全面弱于我们的方案。Mem0 是成熟的通用记忆层，具备 scope、抽取、更新和多信号检索，接入成本和生态是它的优势。我们的项目针对 Coding Agent 的特殊问题：除跨会话长期记忆外，还有大量工具结果的可恢复卸载，因此把长期记忆和单任务 Offload 拆成两条链，并保留 L0 source ids、result refs 和任务图。
>
> 如果要比较，我会固定 Mem0 的版本与部署形态、相同底模、embedding、任务集、token budget、重试和超时，分别报告任务通过率、Token、写入/召回延迟、错误注入和删除能力。我们内部曾做过探索性对比，但如果没有保留完整版本、配置和多次运行记录，我只能把它当方向性结果，不能下“Mem0 不到 60%、我们接近 70%”的产品结论。
>
> 选型上，通用个性化记忆优先评估现成方案；需要深度处理 Coding Agent 工具日志和任务恢复时，自研 Offload 链路更贴合。

### 本项目复盘

**得分：** 领域高度匹配；能讲分层、混合召回、冲突更新和量化结果；不是简单向量库。

**失分：**

- 把“context degradation”统称为幻觉，故障分类不够精确。
- 用“分四层”回答核心创新，差异化不够强。
- 只靠时间戳描述冲突更新，忽略语义和作用域。
- Benchmark 名称、分数和百分比没有固定口径。
- 对 Mem0 的功能和效果下了超出证据的结论。

## 六、针对忆纪元互动小说业务的设计答案

> 面试官最后介绍了真正的业务：AI 生成的 AVG/文字冒险，经过数百轮对话后，需要维护世界事实、角色各自知道的事实、人格一致性、新角色/地点和剧情推进。这是本场最重要的信息。现场只回答“了解”错过了一个展示岗位匹配的机会。

### Q25. 你的 Coding Agent 记忆系统怎样迁移到多角色互动小说？

**推荐答案：**

> 我不会直接把“每个角色一个向量库”当作完整方案。互动叙事需要把 **客观世界真相** 和 **角色主观认知** 分开。
>
> 我会设计五类状态：
>
> 1. `WorldState`：世界中已经成立的客观事实和规则；
> 2. `EventLog`：不可变事件，包含时间、地点、参与者、因果和分支；
> 3. `CharacterBelief`：每个角色知道、相信或误解的内容，带来源、知情方式和置信度；
> 4. `CharacterProfile/Relationship`：稳定人格、目标、关系和情绪状态；
> 5. `StoryState`：当前场景、主线/支线、未解决冲突和叙事节奏。
>
> 角色不在场的事件不会自动写入它的 Belief。它后来可以通过他人转述知道，但要记录“听说”而不是“亲眼见到”；角色甚至可以相信错误信息，而 WorldState 仍保持真实。这种 truth/belief 分离才能同时防信息泄漏和支持戏剧冲突。

### Q26. 轮到某个角色说话时，怎样召回记忆而不泄漏世界信息？

**推荐答案：**

> 检索先做权限过滤，再做相关性，而不是先全局召回后靠 prompt 告诉模型“不要说”。请求带 `story_id、timeline_id、scene_id、speaker_id`；候选集合只包含该角色可见的 Belief、公开 World Facts、当前场景事件和允许使用的人格/关系。
>
> 在过滤后的集合内，再用近期性、语义相关度、实体关系、未解决目标、情绪强度和因果距离重排。最终上下文按预算组装：角色核心人格、当前场景、最近事件、相关长期记忆、目标和禁止泄漏项。每条记忆带 event id/provenance，生成后做 claim-to-memory 检查。
>
> 权限边界必须在数据访问层实现；仅靠 system prompt 无法防止模型引用它已经看到的秘密。

### Q27. 大模型突然编出一个新人物或地点，怎样放入原有世界？

**推荐答案：**

> 生成文本不能直接修改 canonical world。先把候选实体和事件解析成结构化 proposal，再经过四步校验：
>
> 1. **Entity Resolution**：检查同名、别名和相似实体，避免重复创建；
> 2. **Schema/Rule Validation**：时间、地点、角色属性和世界规则是否合法；
> 3. **Consistency Check**：是否与已有事实、时间线和资源约束冲突；
> 4. **Commit/Repair**：合法才分配 canonical id 并写入事件日志；不合法则让模型基于明确错误修复，必要时拒绝。
>
> 新实体写入后，再按事件参与和可见性更新相关角色 Belief，不把它广播给所有角色。若编剧希望“retcon”，必须显式产生版本或新 timeline，不能静默覆盖旧事实。

### Q28. 玩家不主动推进时，怎样让开放世界仍有剧情发展？

**推荐答案：**

> 不应让 LLM 每轮凭感觉自由续写。我会增加一个 World Tick / Narrative Director：维护角色目标、资源、未解决剧情钩子、因果前置条件、冷却时间和 tension curve。每个 tick 先由规则或规划器产生若干候选事件，再按一致性、相关性、剧情价值和重复度评分，选中后由 LLM 负责具体表现。
>
> 也就是说，**状态机/事件调度负责世界真的发生什么，LLM 负责这件事怎样被讲出来**。这样既能自动推进，也避免模型突然制造不符合设定的重大事件。关键事件可以进入人工审批或更严格的验证链。

### Q29. 如何评测互动叙事记忆系统？

**推荐答案：**

> 我会把“好不好玩”和“记忆是否正确”分开。记忆与一致性指标包括：
>
> - 角色知情范围泄漏率；
> - 世界事实矛盾率和时间线冲突率；
> - Persona/说话风格一致性；
> - 事件与实体 Recall@K；
> - 新实体重复率和错误合并率；
> - 用户纠正后错误记忆残留率；
> - 200/500 轮后的任务正确率、延迟和单位轮次成本。
>
> 叙事体验再看剧情推进率、重复情节率、选择影响度、玩家留存和主观评分。离线可构造“某角色是否应该知道某事”的金标题；线上做 A/B，但安全和泄漏类指标不能只靠用户满意度替代。

### 面试现场更好的即时回应

> 这个场景和我做的 Coding Agent Memory 有同构点，但复杂度更高，因为它不只有“记不记得”，还多了“谁有资格记得”和“主观认知是否等于世界真相”。如果我来做，我会把世界事件作为 canonical truth，把每个角色的 belief 单独维护，并在检索前做 speaker scope 过滤；新人物和地点先作为 proposal 经过实体解析与一致性校验，再写入世界。我的 L0、混合召回和 source reference 可以复用，但 Persona、时间线、角色权限和分支世界需要重新设计。这会是我最想深入的部分。

### 7.2 对 AI 多模型 Review 的专业回应

> 三模型投票可以提升覆盖率，但如果模型同源、prompt 相同，它们的错误高度相关，三票不等于独立证据。我会按风险分层：先用确定性 lint、类型检查和测试过滤，再让不同职责的 Reviewer 分别看正确性、安全和可维护性；输出必须引用 diff 行和规则，低置信或高风险改动交给人。AI Review 不能成为合并授权主体，人仍对发布负责。

### 7.3 托管基础设施的利弊

**合理性：** 早期团队购买托管 K8s、PG、Redis、ClickHouse，能减少值班和平台人力，把资源集中到产品。

**需要核验：**

- 数据区域、备份、RPO/RTO 和供应商故障降级；
- 用户对话与长期记忆的加密、删除和审计；
- 云成本、模型成本和单用户毛利；
- 是否有基础的 on-call owner，而不是把全部责任交给客服。

## 九、面试表现复盘

### 9.1 得分项

1. **项目真实性较强。** 周报失败补采、CodeWiki 语言适配、记忆维护都能讲实现细节，不像只背概念。
2. **记忆方向直接匹配。** 对方主营业务和第三个项目几乎同赛道。
3. **技术演进意识不错。** 能说明 2024 年 Coding Agent 成熟度、后续 MCP 接入和共享索引价值。
4. **反问质量高。** 工具、Skill、AI Review、基础设施和业务挑战都问到了真实工作方式。
5. **语言熟悉度回答诚实。** Java 最强、Python/TS 次之，没有把自己包装成四语言专家。

### 9.2 主要失分项

1. **公司主体表述可能不准确。** 招银网络不能直接说成招商银行信息技术部。
2. **数据准确性答非所问。** “不用 LLM 算数”不等于验证数据准确。
3. **架构坏味道问题被绕开。** 讲 SonarQube 没有回答图谱能做什么。
4. **框架比较缺少统一维度。** “快、轻、生态好”不足以支撑设计判断。
5. **约定与配置概念混淆。** Convention over Configuration 的问题是隐式魔法和扩展边界，不是简单“配置更多”。
6. **错误处理方案有反模式。** 每处 try/catch 会增加噪声并破坏异常语义。
7. **编译期 DI 设计没有命中。** 懒加载与运行期注解不能解决缺失依赖的早发现。
8. **记忆核心贡献回答过浅。** 四层结构本身不是足够强的创新说明。
9. **指标口径混乱。** 对 benchmark-heavy 的公司，这是可信度风险。
10. **竞品判断过度。** 对 Mem0 的层数、画像和效果不能不限定版本就下结论。

### 9.3 面试官风格

- 技术基础扎实，喜欢从使用体验追到设计原则。
- 不满足于名词，会给反例继续推进，观察候选人能否修正模型。
- 对框架显式性、可调试性和构建期安全有明显偏好。
- 愿意长篇解释自己的观点，可能也在判断候选人是否能进行平等技术讨论。
- 对记忆 Benchmark 和竞品有了解，下一轮不适合用未经核验的营销数字应对。

## 十、下一轮准备清单

### 10.1 第一优先级：把指标做成一张卡

只背下面三个确定口径：

1. WideSearch：通过率 `33% → 50%`，增加 17 个百分点，相对提升 51.52%。
2. WideSearch：Token `221.31M → 85.64M`，降低 61.38%。
3. PersonaMem：准确率 `48% → 76%`，增加 28 个百分点。

同时准备模型版本、prompt、context window、任务数、运行次数、重试和失败定义；没有记录的就明确说材料未完整保留，不补造。

### 10.2 第二优先级：画出互动小说记忆模型

至少能白板讲清：

```text
Canonical World State
        ↓ 产生事件
Immutable Event Log ──→ Timeline / Branch
        ↓ 按参与、观察、转述传播
Character Belief A / B / C
        ↓
Persona + Relationship + Goal
        ↓ speaker-scope retrieval
Narrative Generation
```

核心关键词：`truth vs belief、knowledge scope、provenance、timeline、entity resolution、pre-retrieval ACL、persona consistency`。

### 10.3 第三优先级：重新练框架设计

必须能用 2 分钟回答：

> 目标约束 → 小内核 → 显式模块 → 构造器注入 → 构建期 DAG 校验 → 生成工厂 → 类型化配置 → 可观察默认值 → 插件扩展 → 测试 Harness。

重点研究 Dagger、Micronaut 或 Quarkus 的 build-time DI 思路，不需要实现完整框架，但要理解为什么它比运行时反射更早发现错误。

### 10.4 第四优先级：准备 Mem0 公平对比

建立比较表：版本、OSS/托管、底模、embedding、scope、写入动作、时间语义、检索、证据、删除、Offload、延迟、Token 和部署成本。结论必须是“按场景选型”，不能是“竞品只有两层”。

### 10.5 第五优先级：准备公司核验

下一轮至少问清：产品阶段、该岗位前三个月目标、创始人/直属负责人投入、团队规模、实际工时、融资 runway、合同主体、期权比例、记忆数据删除和多租户隔离。

## 十一、速记版结论

### 本场最值得保留的三句话

1. **周报：数字由确定性代码计算，LLM 只做受证据约束的表达。**
2. **CodeWiki：tree-sitter 是解析底座，自研价值在统一 IR、依赖图、增量知识和 Agent 工具化。**
3. **Memory：核心不是四层，而是证据可追溯的记忆生命周期与可恢复的工具结果卸载。**

### 本场最需要改掉的三句话

1. 不再说“每个可能报错的地方都 try/catch”。
2. 不再说“MVP 用 Python，用户多了再重写 Java”。
3. 不再说“Mem0 只有两层，所以我们的效果更好”。

### 对结果的最终判断

> **方向匹配是这场的入场券，严谨性才是下一轮的分水岭。** 候选人已经证明自己做过记忆工程，但还需要证明能够设计更强的抽象、建立可复现评测，并把 Coding Agent 的单用户记忆升级为互动小说的多主体世界记忆。
