## 二、八股文问题单列：数据结构、操作系统与 Java

> 以下题目均在本场真实出现，和后面的 CodeWiki/Memory 项目题分开。回答优先采用“先定义，再说明关键性质，最后结合工程边界”的结构。

### 八股 1：二叉树是什么？

**现场回答问题**：把“树”和“二叉树”混在一起，先说父节点、子节点，未明确“每个节点最多两个孩子”。

**正确答案**：

> 二叉树是一种树形结构，除空树外由根节点和递归的左右子树组成；每个节点最多有两个子节点，分别称为左孩子和右孩子，允许只有一个孩子，也允许没有孩子。它不等同于二叉搜索树，二叉搜索树还要求左子树键值小于根、右子树键值大于根（重复值规则需另定）。

### 八股 2：二叉树如何遍历？

**正确伪代码**：

```text
preorder(node):
    if node == null: return
    visit(node)
    preorder(node.left)
    preorder(node.right)

inorder(node):
    if node == null: return
    inorder(node.left)
    visit(node)
    inorder(node.right)

postorder(node):
    if node == null: return
    postorder(node.left)
    postorder(node.right)
    visit(node)
```

> 三种递归遍历的时间复杂度都是 O(n)，递归栈空间为 O(h)，`h` 是树高；树很深时可以改成显式栈，避免调用栈溢出。层序遍历使用队列，时间 O(n)，额外空间取决于最大宽度。

### 八股 3：B+树是什么，为什么适合数据库索引？

**现场表现**：说到了磁盘 IO 和树深较低，但没有讲清内部节点、叶子节点、叶子链和数据存储方式。

**正确答案**：

> B+树是多路平衡搜索树。内部节点只保存有序的分隔键和子指针，真正的记录或记录指针集中在叶子节点；所有叶子在同一层，并通过链表连接。查找从根沿分隔键走到叶子，范围查询找到起点叶子后可以顺链扫描。
>
> 它适合磁盘/页式存储，是因为一个节点可以容纳很多键和指针，树高较低，减少随机 IO；叶子有序链还能高效支持范围查询。更新时可能发生叶子分裂、合并和父节点分隔键调整。数据库索引中的“聚簇/非聚簇”和叶子保存完整记录还是主键/指针，则取决于具体实现。

### 八股 4：进程和线程有什么区别？

**正确答案**：

> 进程是资源隔离和分配的基本单位，拥有独立虚拟地址空间、文件描述符等资源；线程是进程内的调度执行单元，同一进程线程共享堆、代码和大部分进程资源，但各自有程序计数器、寄存器上下文和栈。进程间隔离强、创建和切换成本通常更高；线程通信方便但共享数据会引入竞态，需要同步。一个进程可以只有一个线程，也可以有多个线程；多线程并不等于一定并行，还取决于 CPU 核数和运行时限制。

### 八股 5：线程上下文切换保存哪些状态？

**正确答案**：

> 至少包括下一条指令位置的程序计数器、通用寄存器、栈指针、处理器状态/标志寄存器，以及内核调度所需的线程状态和调度信息。地址空间、页表等通常属于进程上下文；只有发生进程切换或地址空间切换时才需要切换对应内容，不能简单说每次线程切换都完整保存一套页表。内核会把这些信息保存在 PCB/TCB 或架构相关的上下文结构中。

### 八股 6：Java 多线程访问共享变量怎样同步？

**现场不足**：提到了 `synchronized`、`Lock`、原子类和 `volatile`，但没有区分互斥、可见性和原子性。

**正确答案**：

> 先看共享操作的性质。需要互斥保护复合操作时使用 `synchronized` 或 `ReentrantLock`；需要可中断、超时、公平策略或多个条件队列时选显式 `Lock`/`Condition`。计数器等简单单变量更新可以使用 `AtomicInteger`、`AtomicLong` 或 CAS。`volatile` 主要保证可见性和有序性，不保证 `i++` 这类复合操作的原子性。读多写少可以考虑读写锁或 `StampedLock`，更推荐使用线程安全集合和不可变对象减少共享状态。无论选哪种方式，都要说明锁范围、释放方式、死锁风险和数据不变量。

### 八股 7：线程池有哪些核心参数？

**正确答案**：

> Java `ThreadPoolExecutor` 的核心参数包括 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory` 和 `RejectedExecutionHandler`，构造函数还接收时间单位。执行逻辑通常是：线程数未达到 core 时创建线程；达到 core 后先入队；队列满且未达到 max 时继续创建；队列满且达到 max 时执行拒绝策略。
>
> 选择线程数要区分 CPU 密集和 IO 密集，队列要有容量上限并结合任务耗时、内存和上游限流；生产环境必须配置线程命名、异常处理、监控、优雅关闭和拒绝策略。使用无界队列时通常不会扩容到 `maximumPoolSize`，还可能掩盖堆积和造成内存风险。

## 三、项目一：CodeWiki 深挖

### Q8. CodeWiki 解决什么业务问题？

**推荐答案**：

> 它面向老项目接手和跨模块维护。原有代码注释、详细设计和调用关系不完整，新成员需要逐文件阅读，定位一项需求的影响范围成本高。CodeWiki 先用静态分析提取可验证的符号和依赖，再让模型基于源码证据生成带文件和行号的文档；它的价值是减少重复探索、保存团队共享知识，而不是宣称替代所有 Coding Agent。

### Q9. 多语言统一 DSL 怎么定义？

**现场回答方向正确但不够具体**：说抽象类、接口、函数、方法和关系，没有给出 IR 字段和版本边界。

**推荐答案**：

> DSL 更准确地说是语言无关的代码 IR。节点至少包含 `repo_id、revision、symbol_id、kind、qualified_name、signature、file、start_line/end_line、parent_id、visibility`，按能力可扩展类型、注解、Endpoint、表和配置项；边包含 `source_id、target_id、relation_type、source_ref、revision、confidence`。Java/Python/Go/JavaScript 的 AST 解析器负责把各自语法映射到这套 IR，无法确认的动态关系要标低置信度。
>
> LLM 不负责把源代码“翻译成 DSL”；Tree-sitter 和规则/类型分析负责确定性抽取，LLM 只基于 IR、调用链和源码片段生成解释性文档。

### Q10. 为什么用 GraphRAG？用了什么技术？

> 普通向量 RAG 更容易召回语义相似的孤立片段，但代码问题常需要回答“谁调用谁、接口落到哪个实现、修改一个类会影响哪些方法”。图能表达这些确定关系，向量和关键词检索则补充自然语言描述、标识符和错误码召回。因此应采用混合检索：先按仓库、revision、权限过滤，再用 BM25/向量召回候选，沿调用/依赖边扩展，最后把带源码引用的 context pack 交给模型。
>
> 转写提到 LangGraph、Neo4j、pgvector、MCP 和早期 `Scikit` 存储；具体组件、哪些已生产、哪些只是 MVP 必须按本人事实核对。不能把“接过 MCP 接口”自动说成平台已被多个业务正式采用。

### Q11. 图数据和向量数据怎样存？

> 图数据按节点和边存储，不应把“一条边”粗糙塞进某个节点的普通字段。节点/边都要绑定 `repo_id + revision`，并保留源码位置、关系类型和解析置信度；Neo4j 适合关系遍历，关系型表也可以保存规范化边表。向量记录必须绑定 `chunk_id/symbol_id + revision + embedding_model + content_hash`，不能只存一串向量。
>
> 查询时先按 scope、权限和 revision 过滤，做关键词/向量候选召回，再用图关系扩展。删除、重命名和版本切换必须能清理或隔离旧节点、旧边和旧向量，避免把过期代码返回给模型。

### Q12. 代码变更后怎样增量更新？

**现场表现**：能说 Git diff、删除旧向量、插入新向量和人工审核，但没有回答重命名、反向依赖、原子切换和校验。

**推荐答案**：

> Git diff 只是文件级线索。流程应是：先保存新 revision；对变更文件重新做 AST/IR 解析；通过稳定 symbol ID、签名和相邻代码识别新增、删除、修改、重命名；根据定义关系和反向依赖计算 Dirty Set；重建受影响节点、边、文档 chunk 和向量；跑引用、数量、语法和代表性问答回归；校验通过后原子切换当前 revision，失败则保留旧版本并告警。
>
> 增量不是只更新“变动的函数”。类属性、基类、接口、配置或公共类型变化，可能改变包含方法和调用方的语义，需要重新计算受影响范围。文档生成可以人工审核，但不能用人工审核代替机器一致性检查。

### Q13. 类属性新增或类型改变，如何更新向量？

**这是本场最明显的项目失分点。** 现场最后回答“可能影响函数，但不更新向量”，会导致检索仍返回旧语义。

**正确答案**：

> 先定位属性节点和包含它的类节点，计算该类的规范化内容哈希；如果类摘要、字段类型、序列化结构或方法上下文发生变化，就重算类级 chunk 以及引用该属性/类的函数级 chunk 和文档。若静态依赖不足，至少把同文件相关符号加入 Dirty Set，并用回归样本确认没有陈旧引用。
>
> 新向量写入时带上 `revision` 和 `content_hash`，通过 staging namespace 或事务批量写入，校验通过后切换 revision；旧向量不直接物理删除，先标记不可检索，待保留期后清理。这样既能避免旧向量残留，也能支持回滚。

## 四、项目二：Agent Memory 深挖

### Q14. Memory 是独立服务还是嵌入式组件？

**现场回答**：称可以作为独立服务，也可以接入 Coding Agent/OpenClaw，但后面又确认当前在用户本地机器、面向单一用户。

**推荐答案**：

> 当前实现应准确说是**本地、单用户的 Memory 组件/服务**：宿主通过 Hook 在模型调用前 Recall、一次交互完成后 Capture，数据保存在用户本机。它不是已经部署的共享多租户服务。未来若做团队化 Gateway，可以暴露 HTTP/MCP，但要增加用户、项目、Agent、权限 scope、租约、审计和删除传播；“接口可兼容”不等于“已完成云化”。

### Q15. 四层记忆什么时候写入？

**现场回答**：L0 原始对话按消息数写入，L1/L2 每 5 条抽取，画像层约每小时更新，并有 5/15 分钟保底任务。

**问题**：固定“每五条”是当前实现的触发策略，但没有覆盖用户明确记忆指令、任务结束、重要事件和失败重试；直接同步抽取还会增加延迟。

**推荐答案**：

> L0 原始事件应先追加写入不可变存储，带 `conversation_id、turn_id、event_time、timezone、scope、source_ref`，这是证据而不是摘要。L1 结构化事实由会话边界、用户明确“记住”、重要事实检测或定时保底异步抽取；L2 在多个事实形成同一任务/场景或任务结束时更新；L3 只有在稳定偏好达到置信度、跨多次会话复用且未冲突时才晋升。
>
> 如果当前项目确实使用“每 5 条 + 5/15 分钟/1 小时”的规则，就说这是当前实现的成本控制策略；下一版会用事件触发、异步队列、幂等键、重试和延迟预算补足，而不是把固定轮数说成通用记忆理论。

### Q16. 新旧事实冲突怎样发现和解决？

**现场不足**：把向量/BM25 召回和 LLM 判断作为主要冲突发现方式，没有明确稳定事实键。

**推荐答案**：

> 冲突发现分两步。先把事实规范化为 `subject、attribute、value、scope、valid_time、source_ref、confidence、status`，用实体 ID、属性名和 scope 做候选定位；向量/BM25 只用于补充召回，不能单独证明两条事实是同一属性。候选事实按时间、来源可信度和有效期比较，发现不同值且时间/作用域重叠时标记 conflict。
>
> 然后由规则和服务端状态机决定：明确的“改成 B”可以把 A 标为 superseded；互补字段做 merge；时间或 scope 不清楚则保留冲突并追问。LLM 只能提出 update/merge/ask-user 动作，服务端校验版本号、权限和安全规则后落库；旧事实保留历史和引用，用户删除要同步 L0、派生事实、向量索引和备份生命周期。

### Q17. 每轮都检索吗？主要检索哪一层？

> 当前如果确实每轮检索，应说明主要检索 L1 结构化事实，必要时按场景召回 L2，L0 只作为引用回溯，L3 作为低频画像条件，不把四层原文全部塞进 Prompt。生产设计可以用意图门控：与历史无关的短问题跳过召回；命中高风险/冲突事实时扩大候选；设置数量、Token、延迟和权限预算，并记录 Retrieval Trace。每轮无条件做向量和 BM25 会增加成本和延迟，也不等于召回正确。

### Q18. 应用端怎样集成 Memory？

> Hook 适合 Agent 生命周期接入：`before_model_call -> recall`，`after_turn/after_tool -> capture`，失败时由本地队列重试；Gateway/HTTP 适合 Web 或多宿主，但接口必须有稳定协议，例如 `recall(query, scope, as_of, budget)`、`capture(events, idempotency_key)`、`delete(subject/scope)`、`health`，返回 `memory_id、source_ref、revision、confidence`。如果当前只有本地 Hook，就明确说 Gateway 是下一版设计，不能把未来接口说成已部署的共享平台。

## 五、学习情况与职业表达

### Q19. 最近在学习什么技术？

**现场回答问题**：主要讲 Codex/Vibe Coding、Three.js 魔方，以及对“Loop Engineering/Graph Engineering”概念的个人评价。

**推荐答案**：

> 最近我把学习重点放在 Data Agent 的工程化：自然语言到 SQL 的安全生成、语义层/指标口径、数据血缘、评测集、链路可观测性和失败回放。我会先把表、字段、指标定义、权限和时间口径结构化，再让模型做候选 SQL 或解释，结果通过 SQL AST/只读权限/数值对账和人工样本回归校验。与此同时，我用一个小型 Three.js 项目练习前端和 3D，但它是个人练习，不会把它作为大数据生产经验。

### 7.1 二面最需要修正的三句话

1. 不要说“二叉树就是有两个子节点”；应说“每个节点最多两个子节点”。
2. 不要说“类属性变更不更新向量”；应说“按属性、包含类和反向依赖计算 Dirty Set，重算受影响 chunk/向量并按 revision 原子切换”。
3. 不要说“向量/BM25 找到冲突”；应说“先按实体、属性、scope、时间定位候选，检索只是召回，冲突由规则、版本和证据状态机确认”。

## 八、下一轮准备清单

### 8.1 基础与 Java

- 手写二叉树前/中/后序、层序遍历，说明 O(n) 和 O(h)。
- 画出 B+树内部节点、叶子节点和叶子链，解释点查与范围查。
- 准备进程/线程、用户态/内核态、上下文切换、虚拟内存和 IO 多路复用的 60 秒答案。
- 准备 `synchronized`、`ReentrantLock`、`volatile`、CAS、原子类、线程安全集合的适用边界。
- 能写 `ThreadPoolExecutor` 的参数、执行顺序、队列选择和拒绝策略；不要只背参数名。

### 8.2 项目补强

- CodeWiki：准备属性变更、方法重命名、删除、公共接口变化、回滚和陈旧向量清理的完整流程。
- DSL：准备一张节点/边 schema 卡，写清 `repo_id/revision/symbol_id/source_ref/confidence`。
- Memory：准备事实主键、scope、有效时间、冲突状态、异步抽取、幂等 Capture 和删除传播。
- Data Agent：准备语义层、指标口径、NL2SQL、归因/下钻、权限、评测和 Trace 的端到端设计。
