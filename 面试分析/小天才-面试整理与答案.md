## 二、周报项目深挖

### Q2. AI 周报的数据源是从其他系统抽取的吗？大概多少个系统？数据量多大？

**参考答案**（给具体数字，别虚）：
> 这个项目不是从 Git、Jira、CI 里统计员工工作的周报，而是公司内部的**网联运营保障周报**。当前能确认的数据来自北斗、园方、AN1LOG、CKTRANS、CKSLOWSQL、FTCLOG 等内部运营、交易和日志系统，主要覆盖错误日志、大事务、慢 SQL、失败交易、TPS 和响应时间等指标。
>
> 程序按业务日期从内部接口或数据库记录取数，写入对应业务表，再做周维度统计。具体要算几个系统源、每天和每周多少条、单条多大，我会以内部接口文档、表统计和运行记录为准。当前材料不能证明精确量级时，我宁可说“这是多源日批运营数据”，也不会临场编一个 X 万条。
>
> 这题要把两个口径分开：能确认的数据类别和处理流程可以直接讲；系统数、记录数和字节量属于运行事实，必须有内部统计再报。

### Q3. 数据格式是 JSON 还是纯文本日志？

**参考答案**：
> 当前我能确认的是，数据通过结构化接口和数据库记录进入批处理，程序按业务日期解析后写入不同模块的数据表。现有材料不足以证明每个接口都是 JSON，也不能把“错误日志指标”直接等同于“系统读取纯文本日志文件”。
>
> 所以面试时我会先讲清输入经过接口解析、字段映射和入表，再按统一周窗口统计；如果面试官继续问某个源的具体报文格式，我会按内部接口文档回答，不根据字段用途猜它是 JSON 还是纯文本。

### Q4. 所以是数据采集 → 统一标准格式 → 大模型分析，对吧？源跟源之间有联动分析吗？

**参考答案**：
> 主线更准确地说是：按业务日期采集和入表，先检查上一周七天的数据是否完整，再按错误日志、大事务、慢 SQL、失败交易、TPS、响应时间等模块做确定性统计，最后把已经算好的结构化结果分段交给 LLM 做异常解读和文字组织。
>
> 多源数据会放在同一个周窗口里组装，模型可以提示“错误日志上升和某类失败交易同时出现”这类相关线索，但当前没有调用链、因果图或自动实验去证明根因。所以我会说它能做跨模块关联提示，不能说已经完成了真正的根因分析。Git 提交、Jira 任务和 CI 状态不属于这个项目的数据链路。

## 三、延展设计题：多系统日志根因诊断 ⭐（本场核心）

### Q5. ⚠️ 场景题：我们有多个系统的日志抽到集中地方，现在有一个异常告警/error，给你各种系统的日志源，让你排查异常的源头/根因在哪里。微服务系统，出问题的服务不一定是根因。需要：①哪些数据 ②怎么处理 ③用什么方法快速排查到根因？

> 这是本场重头戏。面试官明确说"你的经历里周报能处理各系统日志，CodeWiki 能解析代码，我需要你做延展"。**考的是能力迁移 + 系统设计**。

**参考答案**（分三部分，每部分要具体——面试官明确反感"笼统"）：

#### 第一部分：需要哪些数据

> 我不会只收 ERROR 日志，而是先准备七类可以互相验证的信号：
>
> 1. **告警与影响面**：哪条 SLO 或业务指标异常、开始时间、持续时间、受影响租户/接口和错误样本。HTTP 500 只是表象，不直接代表哪一层是根因。
> 2. **Trace 与关联标识**：完整或抽样的 Span、request_id、业务流水号、消息 ID。TraceId 很有价值，但采样、断链和 MQ 异步调用都可能让它不完整。
> 3. **指标**：各服务的请求量、错误率、延迟、饱和度，以及数据库、缓存、MQ、线程池和主机资源指标，用来识别第一个异常信号。
> 4. **日志与事件**：不只看 WARN/ERROR。关键 INFO 状态迁移、结构化业务事件、异常堆栈和上下游返回都可能是证据，要按字段和关联 ID 检索，而不是按日志级别一刀切。
> 5. **服务拓扑**：预期依赖和运行时实际调用关系，包括同步、异步和外部依赖。
> 6. **变更时间线**：代码发布、配置、Feature Flag、依赖版本、扩缩容、数据库变更和运维操作。很多故障的首个线索是“异常从某次变更后开始”。
> 7. **源码、Runbook 和历史事件**：用 CodeWiki 定位候选路径，再结合已知故障模式和修复记录核验。

#### 第二部分：怎么处理

> 我会分三步，但每一步都要留下可复核产物：
>
> **步骤 1：统一时间线和关联关系**
> - 先统一时区、时间精度和时钟偏差，把告警、Span、指标异常、日志、发布和配置变更放到一条时间线上。
> - Trace 完整时沿关键路径分析；Trace 缺失时用 request_id、业务流水号、消息 ID、时间窗口和拓扑补关联，并明确哪些链路只是推断。
>
> **步骤 2：从“第一个异常信号”缩小候选**
> - 比较异常前后的基线，找最早出现偏离的服务、依赖或资源，而不是只看最后返回 500 的服务。
> - 沿调用关键路径看每个 Span 的状态和耗时，再叠加数据库/MQ/主机指标、日志状态迁移以及同时间变更，把候选缩到几条可检查的假设。
>
> **步骤 3：生成并验证假设**
> - LLM 可以把证据组织成“假设、支持证据、反证、缺失证据和下一条查询”，但它不能直接宣布根因。
> - 系统通过日志查询、指标对照、请求回放、配置核对、回滚或关闭 Feature Flag、沙箱实验逐条验证。验证不了就输出“候选原因”，不能把相关性写成因果结论。

#### 第三部分：用什么方法快速排查根因（具体链路）

> 面试官要具体过程，我会用一个例子讲七步：
>
> 1. **确认告警和影响**：比如 10:03 开始，支付接口错误率从基线升高，部分请求返回 500。先确认范围和开始时间，不把 500 当根因分类。
> 2. **建立统一时间线**：拉同一时间段的发布、配置、指标、Trace、日志和资源事件，校正时区与时钟偏差。
> 3. **还原请求路径**：有完整 Trace 时得到“网关→A→B→C”；没有时用业务流水号或消息 ID 补齐，并给推断边标记不确定性。
> 4. **找首个异常信号**：如果 C 的延迟先升高，随后 B 线程池堆积并返回 500，C 是候选；如果 C 返回正常而 B 新版本开始出现空指针堆栈，B 的代码变更是另一候选。
> 5. **生成可证伪假设**：例如 H1“C 返回了不符合契约的空值”，H2“B 新版本缺少空值处理”。每个假设都列支持证据、反证和下一步查询。
> 6. **逐条验证**：查 C 的原始响应和 Schema 变化、比较其他调用方、在沙箱回放同一输入，或者临时回滚 B 的变更观察错误率是否恢复。只有验证闭环后才定根因；否则只报候选和缺失证据。
> 7. **给修复与防复发建议**：用 CodeWiki 找到相关函数、调用方、契约和测试，生成补丁建议，同时补监控、契约校验和回归用例。

> **关键论点**：
> - TraceId、日志级别和 HTTP 状态码都是定位信号，不是根因证明；任何一个都可能缺失或误导。
> - 真正的核心是“多信号统一时间线 → 候选假设 → 可证伪验证”，模型负责组织和提出下一步，不负责凭概率拍板。
> - 修复环节可以复用 CodeWiki 的源码定位能力，但仍要经过测试、审批、灰度和回滚。

### Q6. ⚠️ 追问1：拓扑数据这部分怎么存？最初的拓扑数据怎么产生？

**参考答案**（要具体，不能笼统）：
> **怎么存**：
> - 预期拓扑是图结构，可以用关系库的节点/边表或图数据库保存，边记录协议、接口、来源、有效版本和 owner。
> - 调用次数、错误率和 P99 是时间序列，不适合只覆盖在一条边的当前值上；我会放到 Metrics/时序库，用 service、operation、edge 等标签和拓扑关联，这样才能回看故障时刻。
>
> **怎么产生**：
> 1. **静态意图**：从服务注册、配置、代码依赖和 API 契约得到“应该有哪些调用”。
> 2. **运行时观察**：从 Trace 或服务网格聚合“实际看到了哪些调用”。它能发现动态路径，但受采样、断链和观测窗口影响，不能说一定最准或完整。
> 3. **基础设施依赖**：从 K8s、数据库、缓存、MQ 和云资源关系补齐非服务调用。
>
> 实际上我会同时保留“预期拓扑”和“观测拓扑”，对差异做告警，并给关系带来源与时间范围。这样不会用某一段抽样 Trace 覆盖掉系统真实设计。

### Q7. ⚠️ 追问2：详细描述怎么根据 trace_id 和错误码具体排查到根因？整个过程、整个链路？笼统的不行，要具体。

> 面试官明确说"刚你说的都比较笼统，我需要具体的过程"。**这是本场最关键的追问**——他要看你能不能把抽象流程落到具体步骤。

**参考答案**（必须给具体步骤，但每一步都要有证据产物）：
> 我把具体链路拆成 7 步：
>
> 1. **界定异常**：记录错误率、影响接口、开始时间和代表请求；500 只作为症状。
> 2. **统一时间线**：合并同窗口的 Trace、指标、结构化日志、部署和配置事件，并处理时钟偏差。
> 3. **关联请求**：优先用 TraceId；缺失时用 request_id、业务流水号或消息 ID，不能假装链路完整。
> 4. **找首个异常 Span 或资源**：沿关键路径比较延迟和状态，再看 DB、MQ、线程池等指标以及同期变更。
> 5. **形成候选假设**：让模型输出 H1/H2、支持证据、反证、未知项和下一条工具查询，不直接输出唯一根因。
> 6. **验证**：用日志/指标查询、请求回放、配置核对、版本对照或受控回滚验证；只有证据闭环才把候选升级成根因。
> 7. **修复与复发预防**：定位源码、提出补丁、补契约测试和告警，再走人工 Review、灰度和回滚。
>
> 这里最重要的不是步骤数量，而是每个结论都能回到证据和验证动作。周报项目能迁移多源数据处理思路，CodeWiki 能迁移源码定位能力，但这仍是一道场景设计题，不代表原项目已经有自动根因诊断。

### Q8. 追问3：找到根因后，甚至可以让大模型自己修复代码，异常就不需要人参与了？

**参考答案**：
> 我不会把“完全不需要人”设成所有故障的目标。诊断结论本身就可能不确定，测试通过也只证明覆盖到的用例通过，不代表生产风险为零。
>
> 如果根因已经有充分证据，我可以让系统用 CodeWiki 拉取相关函数、调用方、契约和测试，在隔离分支或沙箱里生成补丁，跑静态检查、单测、集成测试和安全扫描，再自动创建 MR，并附上证据、假设和验证结果。它只能提 MR，不能直接合并或上线。
>
> 只有低风险、可逆、权限边界明确的变更，才考虑审批后灰度；涉及资金、数据、权限、Schema 或跨服务契约的修改必须由 Code Owner 审核，并准备监控和回滚。也就是说，我追求的是“减少人工排查和准备修复的时间”，不是把责任交给模型。

## 四、记忆系统 vs OpenClaw 原生

### Q9. ⚠️ 从 0 设计 L0 到 L3 多层记忆架构，跟 OpenClaw 原生的 memory 机制有什么不同？为什么会选择这样做？

> 这是新角度——之前没被问过"vs OpenClaw 原生"。回答时只讲自己能证明的接入边界：在我们的实现里，OpenClaw 承担 Agent 宿主和 Hook 生命周期，L0~L3 来自外接的 TdaiCore。不要把它扩大成对 OpenClaw 所有版本和全部 Memory 能力的绝对判断。

**参考答案**：

#### 先澄清事实：L0~L3 属于 TdaiCore，不属于宿主链路

> 首先澄清我们的架构边界：**这套 L0~L3 不是 OpenClaw 生成的，而是 TdaiCore 提供的**。OpenClaw 在这里负责注册工具、上下文注入和会话事件；具体宿主版本即使还有自己的 Memory/Compact 能力，也不改变这套分层记忆由外部内核管理的事实。
>
> 我的系统是通过 OpenClaw 的 hooks 把 TdaiCore（记忆核心）注入进去的：在 `agent_end` 时 capture 对话，在下一轮注入时 recall 记忆。**OpenClaw 是宿主，TdaiCore 是记忆核心，两者分离**——这正是设计成"宿主无关"的原因。

#### 我的 L0~L3 和"如果只用 OpenClaw 原生"的区别

> 如果不接 TdaiCore，只使用宿主在当前接入中暴露给我们的会话上下文和通用压缩能力，就缺少我们定义的 L0 证据、L1 原子记忆、L2 场景和 L3 Persona 这一整套跨会话治理。这里不评价宿主未公开的内部实现，只比较我们能控制和验证的能力。
>
> 我的 L0~L3 解决这三个问题：

| 问题 | 只用当前宿主会话能力 | 接入 TdaiCore 后 |
|------|-------------------|-----------|
| 跨会话信息 | 没有使用我们这套分层资产 | L1/L2/L3 可跨 Session 组织和检索 |
| 注入量 | 依赖宿主自身策略 | Persona + Scene Navigation 稳定注入，相关 L1 稀疏注入，L2/L0 按需 |
| 证据追溯 | 取决于宿主自己的摘要和存储策略 | L0 保存来源消息，Offload refs 保存完整 Tool Result，可按不同链路回溯 |
| 记忆更新 | 不使用 TdaiCore 的更新链路 | 相似候选 + LLM 判断 `store/skip/update/merge`，保留来源 ID 和追加历史 |

#### 为什么选 L0~L3 分层（而不是单层向量库）

> 三个原因：
> 1. **信息粒度不同**：原始对话、L1 原子记忆、场景总结、用户画像，是不同粒度，生命周期、召回方式和 Token 成本都不一样，混在一起召回难解释。
> 2. **向量库不解决分层**：只做相似性搜索，原始日志和画像混在一起，且对专有名词/文件路径不稳定（BM25 更稳）。
> 3. **证据链**：L1 通过 `source_message_ids` 回到 L0 来源消息；工具结果则通过 `node_id -> result_ref` 回到 Offload 原文。当前来源还没有逐字 span/蕴含硬校验，这个边界要主动讲。
>
> 一句话：**OpenClaw 提供宿主能力，记忆治理是我的差异化价值**。把宿主和记忆核心分离（TdaiCore 宿主无关），也是为了不绑死在 OpenClaw 上，能复用到其他 agent runtime。

### Q10. 放到 OpenClaw 里能提升任务成功率，是吧？（面试官确认）

**参考答案**：
> 有离线 Benchmark 证据，但不能把不同数据集混成一个“40% 到 70% 的线上成功率”。当前材料能直接引用的是：WideSearch 长任务通过率从 **33% 到 50%**，Token 从 **221.31M 降到 85.64M**；PersonaMem 长期记忆准确率从 **48% 到 76%**。
>
> 这些只是特定数据集、特定配置下的结果，说明这套分层记忆和 Offload 在对应任务上有效；不能外推成所有 OpenClaw 任务、所有线上用户都提升接近 30 个百分点。线上收益还要结合任务类型、召回质量、原文下钻率、成本和失败恢复率评估。

## 六、复盘：这场面试的得失与风险

### 这场的特殊性

小天才这场和微众一样是**场景延展设计题**，但方向不同：微众深挖你已有项目的每个设计决策，小天才**给你一个新场景让你用已有能力组合解决**——考的是"能力迁移 + 系统设计 + 具体落地"。

### 得分点

| 环节 | 表现 | 评价 |
|------|------|------|
| 延展题框架（Q5） | 能给出"五类数据 + 三步处理 + 6 步链路"的完整框架 | ★★★★ 如果当场答到 |
| 拓扑存储 + 产生（Q6） | 三种来源（静态配置/trace 聚合/服务网格）有深度 | ★★★★ |
| 记忆系统 vs OpenClaw（Q9） | 澄清"OpenClaw 无原生分层记忆" + 四维对比表 | ★★★★ 新角度答得稳 |

### 风险点

| 环节 | 风险 | 严重度 |
|------|------|--------|
| **回答笼统被追问**（Q7） | 面试官明确说"刚你说的都比较笼统，我需要具体过程" | ★★★★★ 致命 |
| 周报数据源数字（Q2） | 系统数/数据量如果当场拿不出具体数 | ★★★ 中危 |
| 网络卡影响沟通 | 面试官多次说"听得不太清、卡顿" | ★★★ 中危（非技术） |

### 三个必须内化的点

**1. 回答必须具体到步骤，不能"分析一下、排查一下"**
- 面试官明确反感笼统。任何流程题都要落到"第 1 步做什么、第 2 步做什么、输入是什么、输出是什么"。
- 准备延展题时，把每个流程拆成可编号的步骤，每步有明确输入输出。
- 这场 Q7 被追问"具体过程"就是因为第一次答得太抽象。**第一次就要具体，别等被追问**。

**2. 延展题要显式连接两个项目能力**
- 面试官明确说"你周报能处理日志、CodeWiki 能解析代码，我需要你做延展"。
- 答案里要**显式点出**："这一步用周报的日志采集能力"、"这一步用 CodeWiki 的代码解析能力"——让面试官看到你在做能力迁移，不是凭空设计。
- 根因诊断题的修复环节（Q8）就是 CodeWiki 能力的直接延展，要点明。

**3. OpenClaw 对比要澄清接入边界**
- 在我们的实现里，OpenClaw 是宿主，L0~L3 来自 TdaiCore；这足以说明职责分离。
- 不要扩大成“OpenClaw 所有版本都没有 Memory”或“宿主记忆是空的”。先讲可验证边界，再讲分层价值。

### 下来必做

1. **把根因诊断的 6 步流程练到能口述**：每步输入输出明确，能举具体例子（trace_id=abc123 这类），不再笼统。
2. **准备周报项目的真实数据数字**：X 个系统源、每周 X 万条、清洗后 X 千条——被问不卡。
3. **准备"能力迁移"话术**：遇到延展题，主动说"这个场景用我项目 X 的 Y 能力 + 项目 Z 的 W 能力组合"，显式连接。
4. **网络问题**：下次面试前测网络，卡顿会严重影响面试官体验，可能比答错还伤。

## 七、横向对比：小天才这场和其他场的差异

| 维度 | 小天才 | 微众 | 京东 | 安克 |
|------|--------|------|------|------|
| **核心题型** | 场景延展设计（组合已有能力） | 设计决策审查（深挖已有项目） | 新系统现场设计 | 对标竞品防御 |
| **面试官关注** | 能力迁移 + 具体落地 | 设计合理性 | 架构师潜质 | 差异化价值 |
| **最大风险** | 回答笼统被追问 | Mermaid 定位 + 用户确认 | 路由引擎质量判断 | vs Claude Code init |
| **岗位方向** | AI 辅助运维/根因诊断 | 产品+项目+开发三能力 | AI first 超级个体 | 不明 |

**关键发现**：
- 小天才和京东都考"系统设计"，但**京东给全新题（路由引擎）**，**小天才要求用已有项目能力组合延展**——后者更考"你真的理解自己项目能力并能迁移"。
- 小天才和微众都考"具体性"，但**微众深挖设计合理性**，**小天才要落地步骤**——微众问"为什么这么设计"，小天才问"具体怎么做"。
- **"回答笼统"是跨场风险**：微众面试官说"问题的背景是否定义清楚"，小天才面试官说"都比较笼统，我需要具体过程"——两场都被指出过笼统。**这是你要系统性改进的表述习惯**。

## 八、总结

这场小天才面试的核心是**一道延展设计题**，考察的是"能否把周报的日志采集 + CodeWiki 的代码解析组合成新的根因诊断系统"。

**技术匹配是真实的**：他们的场景（多系统日志 + 微服务根因诊断）正好需要你的两项能力——周报的跨系统日志处理 + CodeWiki 的代码解析。这是你的主战场。

**最大风险是"笼统"**：面试官明确两次指出"笼统、要具体过程"。这是表述习惯问题，不是技术不懂。下来要把所有流程性回答拆成可编号步骤，每步有明确输入输出和具体例子。

**下来优先级**：
1. 根因诊断 6 步流程练到口述（每步具体）。
2. 周报真实数据数字备好。
3. "能力迁移"话术准备（显式连接两个项目）。
4. 网络问题下次提前测。

延展题答好了是加分项——它证明你不只是"做了三个项目"，而是"理解了项目能力并能迁移解决新问题"，这是高级工程师的标志。
