# 微众银行 · 面试整理与答案

> **说明**：微众银行面试。面试官风格非常特殊——**不接受泛泛而谈，每个回答都要具体例子和实际数据**，且会用他自己的理解框架（Claude Code compact 式压缩）来挑战你的设计。
>
> 本场核心考察主线：**长期记忆的"问题定义是否清楚" → 上下文压缩的具体机制 → L0~L3 抽取准确度 → 置信度与冲突检测 → CodeWiki 在强模型时代的价值**。
>
> 三个关键挑战点（面试官明确质疑）：
> 1. **"长上下文导致准确率下降，到底哪些层面下降？"**——要具体，不能泛泛说"抓不住重点"。
> 2. **"Mermaid 任务画布只是日志定位，不是上下文压缩"**——面试官用 Claude Code compact 框架挑战你的设计，必须讲清两者区别。
> 3. **"置信度靠用户确认？用户根本不会确认"**——面试官指出你的冲突处理依赖用户确认是不现实的。

## 二、长期记忆：问题定义（本场重点 1）

### Q2. ⚠️ 做长期记忆的原因——长上下文导致准确率下降，到底体现在哪些方面？哪些会下降，哪些不会，下降的点到底是哪些？

> **面试官明确要求**："你有实际去看过吗？还是只是……"——他要的是**具体观察到的现象**，不是"业界通用问题"的泛泛而谈。

**参考答案**（必须给具体层面 + 具体例子）：
> 我实际观察到长上下文导致准确率下降，主要体现在**三个层面**，不是所有层面都下降：

#### 层面 1：关键约束被"稀释"丢失（会下降）

> **现象**：用户在早期轮次给出的精确约束（文件路径、参数值、命名规范、错误原文），在对话拉长后，模型开始"模糊化"——把 `recall_checkpoint.json` 写成 `recall_checkpoint.jsonl`，把用户说的"不要用 X 框架"忘掉用了 X。
> **原因**：这些是**精确的、点状的信息**，在长上下文里被大量工具日志和中间推理淹没，模型注意力被稀释。
> **不下降的**：宏观的、语义层面的理解（比如"用户在做记忆系统"这种大方向）不会因上下文变长而丢——模型对主题级信息的保持力强。

#### 层面 2：工具结果之间的"串扰"（会下降）

> **现象**：第 5 轮读了文件 A 的内容，第 10 轮要改文件 B，模型把 A 的某个字段名"记成"是 B 的——跨工具结果的字段/路径混淆。
> **原因**：多个 tool result 堆在上下文里，模型分不清哪个结果属于哪次调用，尤其结构相似的工具输出。
> **具体例子**：agent loop 了 10 轮排查问题，第 3 轮读了调度器代码（含 `l2DelayAfterL1` 参数），第 11 轮要改压缩逻辑时，模型把 `l2DelayAfterL1` 当成了压缩层的参数写进去——实际上它属于 L2 调度。这就是工具结果串扰导致的偏差。

#### 层面 3：重复信息导致的"自信错误"（会下降）

> **现象**：同一个错误日志在上下文里出现多次（agent 反复尝试同类操作），模型对这条错误信息过度"自信"，在第 11、12 轮基于这个错误信息做推理，即使它其实是早期一次失败尝试的噪声。
> **原因**：重复曝光让模型误判为"重要且正确"，实际是噪声被放大。

#### 不下降的层面（主动讲，显得有观察）

> - **主题/意图理解**：模型对"用户在做什么"的大方向保持力强，不会因上下文长而跑题。
> - **近期 K 轮**：最近几轮的细节保持好（模型对近期信息注意力高）。
> - 下降集中在中期、远期的**精确点状信息**和**工具结果间的区分度**。

### Q3. 能举个具体的例子吗？比如十轮对话后，第十一轮十二轮因为前面读了什么导致偏差？

**参考答案**（给一个真实可信的例子）：
> 举一个我实际遇到的：agent 排查一个"压缩没触发"的问题。
> - 第 1-3 轮：读项目结构、定位到 `pipeline-manager.ts`，读到 L1 触发条件有 `everyNConversations=5` 和 `l1IdleTimeoutSeconds=600`。
> - 第 4-8 轮：又读了好几个其他文件（offload 状态机、L2 调度器），中间产生了大量 tool result。
> - 第 9-10 轮：agent 尝试改 L1 的触发逻辑，但这时上下文里已经有 8 轮的工具日志。
> - 第 11 轮：agent 要写新的触发条件，**把 `l1IdleTimeoutSeconds` 的值从 600 记成了 6000**——因为这个数字在第 4-8 轮的其他文件里以不同形式出现过（有个 `60000` 毫秒的配置），模型串扰了。
> - 第 12 轮：基于错误的 6000 继续推理，得出"空闲 1.6 小时才触发"的错误结论。
>
> 这就是典型的**工具结果串扰 + 精确值稀释**——不是模型不懂，是长上下文里精确点状信息被淹没了。

### Q4. 除了这个典型场景，还有其他场景吗？

**参考答案**（再给一个不同类型的）：
> 还有一类是**用户原话约束的丢失**。用户在第 2 轮说"commit message 必须用 conventional commits 格式"，到第 30 轮 agent 生成 commit 时用了自由格式——因为中间 28 轮的工具日志把这个约束"挤"出了注意力范围。这类是**指令性约束被过程信息淹没**，和上面的"值被串扰"是两种不同的下降模式。
>
> 所以长期记忆的 L1（结构化事实）和 L3（用户画像）就是针对性解决：把"用户要 conventional commits"这种稳定约束抽出来沉淀，不依赖它在原始上下文里被记住。

### Q5. 面试官总结："做功能一定要解决实际生产问题，不可能把业界功能全搬上来。"

**应对**：这正是面试官在引导——他要确认你不是"照搬业界概念"，而是"从实际问题出发设计"。上面的具体例子已经证明了这一点。可以主动呼应：
> 对，我的设计就是从这两个具体下降模式出发的：**值串扰** → 用 Context Offload 把工具日志移出上下文只留摘要+索引；**约束丢失** → 用 L1/L3 把稳定约束抽出来沉淀。不是先有"长期记忆"概念再套功能，是先有这两个实际问题再设计分层。

## 三、上下文压缩机制（本场重点 2，被挑战最狠）

### Q6. 简历提到"结构化摘要"，你是怎么做结构化摘要的？哪些重要哪些不重要，怎么提炼？

**参考答案**：
> 结构化摘要的核心是**按信息类型分优先级，不是一刀切压缩**：
>
> **高优先级保留**（重要）：
> - 用户明确指令和约束（"用 X 框架""不要 Y"）。
> - 关键决策点（"我们决定用分层而不是单库"）。
> - 错误原文、文件路径、参数值等精确证据。
> - 任务当前状态（做到哪一步、下一步是什么）。
>
> **低优先级压缩/丢弃**（不重要）：
> - 工具调用的中间过程（调了什么、返回了什么）——保留摘要+索引，丢原始内容。
> - 重复的尝试和失败过程。
> - 闲聊和确认性对话。
>
> **提炼手段**：
> - LLM 抽取时**必须带原文 span**（无依据丢弃）。
> - 按类型分桶：事实类、指令类、事件类、偏好类，不同桶不同保留策略。
> - 工具结果用 Context Offload：压缩成高密度摘要 + `result_ref` 索引，原文存 `refs/*.md`。

### Q7. ⚠️ 面试官挑战："你说的 Mermaid 流程图，是把 tool use/tool result 链路保留、实际内容剔除——但这不解决问题啊！大模型后面要用历史某轮的 tool result，不是一样要重新读，读完上下文又满了？这个功能到底解决什么问题？"

> **这是本场最关键的挑战**。面试官的质疑有道理：如果你的"压缩"只是把 tool result 移出上下文留个图，那模型真要用到那个结果时还得读回来，等于没压。必须讲清楚 Mermaid 画布解决的是**另一个问题**，不是"省 token 省到底"。

**参考答案**（先承认面试官说的对，再讲清定位差异）：
> 您说得对，我先承认这一点：**Mermaid 任务画布确实不是"把 50 轮对话压成更短"那种意义上的上下文压缩**，它和 Claude Code 的 compact 解决的是不同问题。我讲清楚两者的定位：

#### Mermaid 任务画布解决的是"长任务的问题定位与跳转"，不是"对话历史的压缩"

> 在 coding agent 的长任务里，真正的问题不是"50 轮对话记不住"，而是**agent 在 loop 模式里不停调工具，上下文被 tool result 撑爆，但根因还没找到**。这时如果粗暴 compact（摘要），会把关键证据（错误日志、文件路径）摘要掉，agent 失去追溯能力。
>
> Mermaid 画布的思路是：把"调了哪些工具、形成什么链路"结构化成一张图（node_id 映射到工具调用摘要），**原文存 refs/*.md 只留索引**。这样：
> - **上下文里只放图 + 摘要**，token 大幅下降。
> - **agent 不需要从头 loop**，而是看图判断"最可能出问题的节点在哪"，**有跳转地**去读那个节点的原文（按 node_id → result_ref 找回），而不是一层层重查。
> - 这是**把"线性重放"变成"图上跳转定位"**，解决的是长任务根因排查的效率问题。

#### 和 Claude Code compact 的区别（正面回答面试官的对比）

> | 维度 | Claude Code compact | 我的 Context Offload + Mermaid |
> |------|---------------------|-------------------------------|
> | 解决问题 | 50 轮对话后摘要压短，继续对话 | 长任务 loop 里 tool result 撑爆 + 根因难定位 |
> | 压缩方式 | 暴力摘要（有损） | 工具日志移出 + 留索引（可恢复） |
> | 证据保留 | 摘要可能丢细节 | 原文不丢，按索引找回 |
> | 定位能力 | 无（摘要后是连续文本） | 图结构支持跳转定位 |
>
> **诚实承认**：如果用户的需求是"50 轮闲聊后还能接着聊"，那 Claude Code compact 式的摘要更直接，我的 Mermaid 画布不是为这个设计的。我的设计是**针对 coding agent 长任务**——工具调用多、证据不能丢、需要跳转定位。

#### 面试官进一步确认："所以这是日志定位/问题排查的优化，不是上下文压缩？"

> **诚实回答**：您这么总结有道理。更准确的说法是：**Context Offload 是上下文压缩（把 tool result 移出 + 留索引，确实降 token），Mermaid 画布是任务状态的结构化呈现（解决定位跳转）**，两者配合使用。如果严格按"上下文压缩 = 把长对话压短继续对话"这个定义，那我的 Offload 部分是压缩，Mermaid 画布更偏任务管理。我之前把两者放一起讲，确实容易让人误解，这是表述上的问题。

> ⚠️ **关键**：这里要**诚实承认面试官的区分有道理**，不要硬辩。面试官明显懂行，硬辩会失分。承认表述问题 + 讲清两部分各自定位，是更稳的策略。

## 四、L0~L3 抽取与准确度（本场重点 3）

### Q8. L0 到 L3 的多层记忆架构具体体现在哪？给什么用？

**参考答案**（基于真实实现）：
> 四层各有明确职责，不是为分层而分层：
> - **L0 原始对话证据**：完整原始对话 + 工具日志，不加工。**给系统兜底**——所有摘要都可能丢细节，L0 保证可回溯。不直接进 prompt。
> - **L1 结构化事实**：从 L0 抽取干净的记忆单元（偏好/指令/事件/项目事实）。**给检索用**——把长对话变成可检索、可去重、可评分的事实。
> - **L2 场景归纳**：把 L1 点状事实按主题/场景聚合。**给宏观上下文**——单条 L1 只能答局部，L2 让 agent 理解"这个场景整体在做什么"。
> - **L3 长期画像**：跨会话沉淀的稳定偏好/风格/SOP。**给常驻注入**——每轮直接注入，不用临时检索推理。
>
> 加载策略：L3/L2 常驻，L1 按需召回，L0 兜底下钻。

### Q9. 这些都是直接通过大模型从历史对话抽取出来的，对吧？

**参考答案**：
> 对，L1/L2/L3 的抽取都走 LLM，但**不是无约束抽取**——有约束保证准确度（见 Q10）。L0 是直接落库不经过 LLM。

### Q10. ⚠️ 抽取过程中有没有方法/手段尽可能提升 L0→L3 的准确度？

**参考答案**（五层防护，这是记忆系统的核心）：
> 有，这是记忆系统的命门——一次幻觉被固化成长期错误事实，后面反复召回放大。几层防护：
>
> 1. **抽取阶段加 span 约束**：LLM 抽事实必须给原文出处（span），找不到依据直接丢弃——减少凭空捏造。
> 2. **置信度打分**：每条记忆带置信度。低置信度/单次出现的进"候选区"，**多次出现/被确认后才晋升** L2/L3。
> 3. **冲突检测**：入库前和已有记忆做一致性校验（见 Q11）。
> 4. **可溯源 + 可失效**：每条记忆追溯到 L0 原始对话，发现错误能定位撤销。
> 5. **召回时二次校验**：关键场景召回后让主模型结合上下文判断记忆是否仍适用。
>
> 核心：**不追求单次 100% 准确，通过"多次确认晋升 + 溯源 + 置信度 + 冲突检测"让错误记忆难固化、可回滚。**

### Q11. ⚠️ 置信度怎么制定？冲突怎么检测？通过语义匹配/向量相似度检索历史的，让大模型识别有没有冲突？

**参考答案**：
> 冲突检测的流程基本是您说的这样，但补充细节：
>
> **冲突检测流程**：
> 1. 新事实入库前，**先按实体 + 属性检索已有记忆**（向量召回 + 结构召回——按实体索引拉同实体的所有记忆，不只靠向量）。
> 2. 拿到候选历史记忆后，**让 LLM 判断是否冲突**（同实体同属性值不同 = 冲突）。
> 3. 检测到冲突：
>    - **可变属性**（当前项目/状态）：新值覆盖，旧值标过期保留。
>    - **不可变属性**（姓名）：**降置信度 + 标记冲突**。
>
> **置信度计算**：
> - 基础分来自抽取时的 LLM 自评（带 span 的给高分，没 span 的低分）。
> - **频次加权**：同一事实多次出现/跨会话稳定，置信度累积上升。
> - **冲突惩罚**：出现冲突降分。
> - 晋升阈值：L2→L3 要达到一定置信度 + 频次才晋升。

### Q12. ⚠️ 面试官挑战："你为什么会确认呢？让用户确认其实很难，他为什么要确认？领导强制？还是工具特别好？有什么手段让用户确实来确认？"

> **面试官指出核心问题**：依赖用户确认是不现实的——像元宝/豆包，如果回答不满意还反过来问用户"确认对不对"，用户觉得慢就不用了。**你的冲突处理如果靠用户确认，等于回避了最大问题。**

**参考答案**（必须诚实承认 + 给出不依赖用户确认的方案）：
> 您这个挑战非常对，我承认**依赖用户确认是不现实的**——这是我在设计上的一个短板。实际情况是当时是内部工具、用户是同事，可以约定要确认，但这不能作为通用方案。
>
> **更通用的、不依赖用户确认的冲突处理**应该是：
>
> 1. **可变属性直接覆盖**（不确认）：当前项目、当前状态这类本就该变的，新值生效，旧值标过期保留可溯源。不需要用户参与。
>
> 2. **不可变属性冲突——降置信度而非求确认**：姓名这类不该变的属性出现冲突，**不弹给用户确认，而是降置信度 + 标记冲突**。召回时这条记忆带"冲突"标记，主模型结合当前上下文判断用哪个，而不是中断对话问用户。
>
> 3. **多源交叉验证**：同一条事实如果在多次对话里被独立提到（不是同一次的重复），置信度自动上升；只出现一次的冲突值，自动降权。
>
> 4. **隐式反馈修正**：如果模型用了某条记忆后用户直接改掉（"不对，我叫 B 不是 A"），这个修正信号回流，自动更新记忆——不需要专门问"确认对不对"。
>
> **核心修正**：把"主动问用户确认"改成"降置信度 + 召回时让模型判断 + 隐式反馈修正"。用户无感，记忆质量仍能维护。这是我下来要改进的方向。

### Q13. 面试官总结："所以现在置信度只是冲突会降，没冲突就认为很高？"

**参考答案**（确认 + 补充频次）：
> 不只是冲突。没冲突的情况下，**频次也是置信度计算的标准**——同一事实多次出现/跨会话稳定，置信度累积上升；只出现一次的即使没冲突，置信度也不会很高，留在候选区不直接晋升 L3。所以置信度 = 基础分（span 有无）+ 频次加权 - 冲突惩罚。

## 五、其他项目

### Q14. AI 周报系统应该是个很老以前的系统吧？后面没变化了吧？

**参考答案**：
> 对，是 2023 年早期做的，比较早的探索。核心设计原则（数字与叙述分离）到现在没变，但系统本身已经稳定运行，没大改动。我后来的精力主要转到 CodeWiki 和记忆系统了。
>
> 诚实说：这是个早期项目，技术深度不如后面两个，但它的"不让 LLM 算数只让它表达"原则我后来一直沿用。

### Q15. ⚠️ 你提到"prompt 中间注意力最低、前后最高"，有探究过为什么吗？

**参考答案**（这是 lost-in-the-middle 现象）：
> 这是 **"lost in the middle"** 现象，有研究论文专门研究过。原因要从注意力机制讲：
> - **位置编码的衰减**：Transformer 的注意力对相对位置敏感，长序列中间位置离 query（通常在末尾）的相对距离远，注意力权重被稀释。
> - **首尾的"锚定效应"**：开头有全局上下文（模型从这里开始读，建立全局 frame），结尾离生成位置最近（直接决定下一个 token），这两段注意力天然强。中间既没有开头的全局锚定，又没有结尾的生成邻近，容易被"跳过"。
> - **信息冗余**：中间往往是重复的过程信息，模型学会了对中间冗余降权。
>
> 实际应用：组装上下文时把**最重要的放结尾**（离生成最近）、**次重要放开头**、**补充放中间**。

> 面试官说"没关系，顺便问一下"——说明这题是加分题，答出来显深度，答不出也不扣分。但答出"位置编码衰减 + 首尾锚定"会比只说"有这个现象"强。

### Q16. ⚠️ CodeWiki 是什么时候做的？今年大模型能力飞跃、agentic 能力很强后，这个项目存在的价值在哪？

> **这是 CodeWiki 的生死线问题**，和安克那场"vs Claude Code init"同性质。面试官在问：模型够强了，你的图还有意义吗？

**参考答案**（基于真实时间 + 两个根本约束）：
> CodeWiki 是 2024 年做的。今年模型确实飞跃，agentic 能力很强，但**这个项目仍然有价值**，基于两个不随模型变强的根本约束：
>
> 1. **确定性 vs 概率性**：模型再强，让它"自己读仓库总结依赖"仍是概率性的——可能漏关键调用、可能总结错。代码这种"错一个调用链就跑不通"的场景，**AST 静态解析的调用关系是确定性的、精确的**。工程场景里"可能对"和"一定对"是两种东西，生产级代码理解要后者。
>
> 2. **成本**：每次让强模型重新扫描大仓库的 token 成本远高于查一次图。即使模型能扫准，成本也不可接受——大仓库几十万行，每次 init 的 token 消耗巨大，而图是离线建好在线按需检索，成本低几个数量级。
>
> **价值定位**：GraphRAG 把**确定性的部分（调用关系、依赖结构）交给工程**，把**需要语义理解的部分（组织表达、解释）交给模型**，是更稳的分工。模型变强只是让"语义理解"那部分更好，不改变"确定性部分该用确定性方法"这个结论。
>
> 诚实边界：模型变强确实压缩了 GraphRAG 的优势区间——小仓库、不需要精确依赖的场景，强模型 + Claude Code init 已经够用。GraphRAG 的价值集中在**大仓库 + 跨模块精确依赖 + 企业定制**这个细分场景，不是全面替代。

## 七、复盘：这场面试的得失与风险

### 这场面试的特殊性

微众这场和前几场**性质不同**：前几场是"你被评估技术够不够"，这场面试官**用他的理解框架持续挑战你的设计合理性**——他不接受"业界都这么做"，要你证明"你的设计解决了什么实际问题、为什么这么设计"。这是**架构师级审查**的风格。

### 得分点

| 环节 | 表现 | 评价 |
|------|------|------|
| 问题定义（Q2-Q4） | 能给出"值串扰/约束丢失/重复噪声"三个具体下降层面 + 真实例子 | ★★★★ 如果当场答到这个度 |
| L0~L3 职责（Q8） | 能讲清每层给什么用，不是为分层而分层 | ★★★★ |
| 抽取准确度（Q10） | 五层防护（span/置信度/冲突/溯源/召回校验）有深度 | ★★★★ |
| CodeWiki 价值（Q16） | 确定性 vs 概率性 + 成本，两个根本约束 | ★★★★ |

### 风险点（下来必须补）

| 环节 | 风险 | 严重度 |
|------|------|--------|
| **Mermaid 画布定位（Q7）** | 被面试官成功挑战"这不是上下文压缩"——表述上把 Offload 和 Mermaid 混在一起讲，导致误解 | ★★★★★ 致命 |
| **用户确认不现实（Q12）** | 依赖用户确认被指出不现实，当场没给出不依赖确认的方案 | ★★★★★ 致命 |
| 上下文压缩定义 | 面试官用 Claude Code compact 框架来套，你的设计思路不同但没讲清差异 | ★★★★ 高危 |
| 置信度机制 | 当场被追问细节，频次加权可能没讲清 | ★★★ 中危 |

### 三个必须内化的校正

**校正 1：Context Offload 和 Mermaid 画布要分开讲，别混**
- 之前把两者放一起讲成"上下文压缩"，导致面试官合理质疑"Mermaid 不是压缩"。
- 正确表述：**Context Offload = 上下文压缩**（tool result 移出 + 留索引，降 token，可恢复）；**Mermaid 画布 = 任务状态结构化**（解决长任务定位跳转）。两者配合但职责不同。
- 以后讲项目时先讲 Offload（这是压缩），再讲 Mermaid（这是任务管理），不要让面试官把它们混为一谈。

**校正 2：冲突处理不能依赖用户确认**
- 之前的"不可变属性冲突 → 向用户确认"是不现实的设计，被面试官精准击中。
- 正确方案：**可变属性直接覆盖不确认；不可变属性降置信度 + 标冲突，召回时让模型判断，不中断对话；隐式反馈修正（用户改掉 = 修正信号回流）**。用户无感。
- 这是下来要改进的核心设计点，下次被问必须这么答。

**校正 3：用面试官的框架讲，不要用你的框架讲**
- 面试官用"compact 式压缩"理解上下文压缩，你的设计是"可恢复 offload + 分层记忆"，两者不同。
- 策略：**先对齐定义**（"您说的压缩是指 compact 那种把对话压短继续聊，我的设计侧重点不同，我讲清楚"），再讲差异。不要假设面试官会自动理解你的框架。

### 下来必做

1. **重写"上下文压缩"的表述**：明确区分 Offload（压缩）和 Mermaid（任务管理），准备一段 3 分钟的清晰表述，不再让面试官混淆。
2. **重写"冲突处理"方案**：去掉"用户确认"，改成"降置信度 + 模型判断 + 隐式反馈"，准备成标准答法。
3. **准备"长上下文准确率下降"的 2-3 个真实例子**：值串扰、约束丢失、重复噪声，每个能讲出具体轮次和具体偏差。
4. **对齐微众岗位的"三能力"要求**：产品思维 + 项目管理 + 开发，后续沟通要体现前两者，不能只讲技术。

## 八、横向对比：微众这场和其他场的差异

| 维度 | 微众 | 京东 | 安克 | 码云 |
|------|------|------|------|------|
| **面试官风格** | 架构师审查（挑战设计合理性） | 架构师定级（设计题） | 产品+技术（对标竞品） | 概念+项目（广度） |
| **核心挑战** | "你设计为什么这么定" | "现场设计新系统" | "你的价值 vs 竞品" | "概念懂不懂" |
| **最大风险** | Mermaid 定位 + 用户确认 | 路由引擎质量判断 | vs Claude Code init | 幻觉机制答错 |
| **岗位要求** | 产品+项目+开发三能力 | AI first 超级个体 | 不明 | CodeWiki 岗 |

**关键发现**：微众和京东都是"架构师级深挖"，但**京东给你新题现场设计**，**微众深挖你自己项目的每个设计决策**。微众这种更难防——因为你的设计如果有不合理处，会被精准击中。Mermaid 定位和用户确认就是被这样击中的。

**应对策略**：对自己项目的每个设计决策，都要能回答"**为什么这么设计、解决了什么实际问题、有什么替代方案、为什么没用替代方案**"。这是微众这类面试的核心准备方向。
