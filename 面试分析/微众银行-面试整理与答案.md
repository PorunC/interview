> **问题来源与当前事实口径**：保留本场真实追问和面试官质疑；项目实现以 [CodeWiki 全链路源码级深入分析](../问题/02-CodeWiki/CodeWiki-全链路源码级深入分析.md) 和 [Agent Memory 全链路源码级深入分析](../问题/03-Agent-Memory/Agent-Memory-全链路源码级深入分析.md) 为准。答案会把当前能力、真实缺口和下一版方案分开，不用理想设计替代源码事实。

> **说明**：微众银行面试。面试官风格非常特殊——**不接受泛泛而谈，每个回答都要具体例子和实际数据**，且会用他自己的理解框架（Claude Code compact 式压缩）来挑战你的设计。
>
> 本场核心考察主线：**长期记忆的"问题定义是否清楚" → 上下文压缩的具体机制 → L0~L3 抽取准确度 → 置信度与冲突检测 → CodeWiki 在强模型时代的价值**。

> 2. **"Mermaid 任务画布只是日志定位，不是上下文压缩"**——面试官用 Claude Code compact 框架挑战你的设计，必须讲清两者区别。
> 3. **"置信度靠用户确认？用户根本不会确认"**——面试官指出你的冲突处理依赖用户确认是不现实的。

## 二、长期记忆：问题定义（本场重点 1）

### Q2. ⚠️ 做长期记忆的原因——长上下文导致准确率下降，到底体现在哪些方面？哪些会下降，哪些不会，下降的点到底是哪些？

> **面试官明确要求**："你有实际去看过吗？还是只是……"——他要的是**具体观察到的现象**，不是"业界通用问题"的泛泛而谈。

**参考答案**（先把证据口径说清楚）：
> 我先说清楚证据边界：下面这些是我根据公开研究和系统结构设计的**受控风险样例**，不是我已经拿线上 Trace 复盘过的生产事故。我不会把一个能解释风险的例子，说成自己真实观察到的故障。对我这个项目来说，动机来自已知的长上下文风险、公开基准结果，以及 coding agent 里工具结果会持续膨胀这个客观结构；要证明某个模型在我的任务上具体下降多少，还得用固定实验去测。
>
> 我会把要测的风险拆成三个层面，而不是笼统地说“上下文一长，所有能力都会下降”。

#### 层面 1：精确约束召回风险

> 我会在上下文前部埋一个精确约束，比如文件名必须是 `recall_checkpoint.json`、禁止使用某个框架，再在后面加入不同长度的工具输出和相似文件名，最后要求模型执行任务。我测的是它能不能**原样召回并遵守约束**，而不是凭感觉判断它有没有“抓住重点”。

#### 层面 2：工具来源归属风险

> 我会准备 A、B 两个结构相似的工具结果，只让 A 包含 `l2DelayAfterL1`，然后问“这个字段来自哪个文件、能不能用于 B”。这里测的是**值是否正确、来源是否归对、最终操作是否成功**。如果只看最终回答像不像，很容易漏掉模型拿对了值但引错了证据。

#### 层面 3：旧证据和重复噪声干扰风险

> 我会把一条已经失效的错误日志重复放几次，再在后面放一次修复后的最新结果，看模型最终引用旧证据还是新证据。这个实验验证的是**时间状态和证据选择**，不能直接把失败归因成“重复一次就让模型更自信”，除非 Trace 和对照实验真的支持这个解释。

#### 哪些能力“不下降”

> 这部分我不会做绝对承诺。主题理解、近期轮次或者简单问答在某个模型上**可能更稳**，但不代表永远不下降；效果会受模型、任务、上下文布局、噪声类型和问题位置影响。我的结论只能落到具体指标上，比如这组实验里精确约束召回是否变化，不能外推成“宏观理解一定不受影响”。
>
> 真要验证，我会固定模型版本、Prompt、采样参数和工具集合，只改变四个变量：上下文长度、噪声比例、目标信息所在位置、是否存在相似干扰项。每组重复运行，记录**精确约束召回率、工具来源归属准确率和端到端任务成功率**，并保留完整输入、Tool Call、Tool Result 和最终回答 Trace。这样我才能回答“哪项能力从什么条件开始下降”，而不是只讲一个听起来合理的故事。

### Q3. 能举个具体的例子吗？比如十轮对话后，第十一轮十二轮因为前面读了什么导致偏差？

**参考答案**（把它说成实验样例，不冒充事故）：
> 可以。我会构造一个“压缩为什么没触发”的受控任务：前面让 Agent 读到 `pipeline-manager.ts` 里的 `l1IdleTimeoutSeconds=600`，中间加入 offload、L2 调度器等结构相似的工具结果，其中故意出现 `6000`、`60000` 这些干扰值，最后要求它说明 L1 的触发条件并给出修改方案。
>
> 我不是预设它第十一轮一定会把 600 说成 6000，而是看三件事：最终值对不对、引用的文件对不对、补丁有没有改到正确模块。然后把同一个目标信息分别放在前、中、后位置，把干扰长度逐级增加，和短上下文基线对比。只有 Trace 真出现了混淆，我才会说“这次实验观察到了串扰”；在那之前，它只是一个用来暴露风险的测试用例。

### Q4. 除了这个典型场景，还有其他场景吗？

**参考答案**（再给一个不同类型的受控样例）：
> 还有一类是指令约束。我可以在早期消息写“commit message 必须符合 Conventional Commits”，后面加入不同数量的代码和工具日志，最后让 Agent 生成提交信息。我会检查格式是否严格满足，而不是先写死“到第三十轮一定会忘”。
>
> 这个样例对应我的设计思路：把明确、稳定、跨任务还要复用的用户约束抽到 L1/L3，需要时召回；把一次任务里的大块工具结果做 Context Offload。但这只是合理的风险到设计的映射，不能替代 A/B 实验。下一版我会把上面那套固定评测加入回归集，验证抽取和卸载到底提升了哪项指标、有没有引入摘要失真。

### Q5. 面试官总结："做功能一定要解决实际生产问题，不可能把业界功能全搬上来。"

**应对**：不要把测试样例说成已经证明了生产问题，可以这样回应：
> 对，所以我会把项目动机分成“已知风险”和“我已经验证的收益”。公开研究和长 Agent 的输入结构说明长上下文存在位置、干扰和成本风险；我的当前实现针对这些风险，把大块工具结果外移、把稳定约束结构化。至于它在我的业务任务上到底提升多少，必须跑固定基线、消融实验并保留 Trace。没有这组证据之前，我不会说自己已经解决了一个线上事故，更不会把业界所有记忆功能都搬进来。

## 三、上下文压缩机制（本场重点 2，被挑战最狠）

### Q6. 简历提到"结构化摘要"，你是怎么做结构化摘要的？哪些重要哪些不重要，怎么提炼？

**参考答案**：
> 结构化摘要的核心是**按信息类型分优先级，不是一刀切压缩**：
>
> **高优先级保留**（重要）：
> - 用户明确指令和约束（"用 X 框架""不要 Y"）。
> - 关键决策点（"我们决定用分层而不是单库"）。
> - 错误原文、文件路径、参数值等精确证据。
> - 任务当前状态（做到哪一步、下一步是什么）。
>
> **低优先级压缩/丢弃**（不重要）：
> - 工具调用的中间过程——从热 Prompt 移出，只留摘要和索引；完整结果仍保存在 refs，不是物理丢弃。
> - 重复的尝试和失败过程。
> - 闲聊和确认性对话。
>
> **提炼手段**：
> - L1 抽取要求返回 `source_message_ids`，用于从记忆回到 L0 来源消息；当前还没有逐字 span 和内容蕴含硬校验，不能说成“无依据自动丢弃”。
> - 长期记忆只抽 `persona / episodic / instruction` 三类，临时任务、寒暄和模型推测不进入 L1。
> - 工具结果用 Context Offload：压缩成高密度摘要 + `result_ref` 索引，原文存 `refs/*.md`。

### Q7. ⚠️ 面试官挑战："你说的 Mermaid 流程图，是把 tool use/tool result 链路保留、实际内容剔除——但这不解决问题啊！大模型后面要用历史某轮的 tool result，不是一样要重新读，读完上下文又满了？这个功能到底解决什么问题？"

> **这是本场最关键的挑战**。面试官的质疑有道理：如果你的"压缩"只是把 tool result 移出上下文留个图，那模型真要用到那个结果时还得读回来，等于没压。必须讲清楚 Mermaid 画布解决的是**另一个问题**，不是"省 token 省到底"。

**参考答案**（先承认面试官说的对，再讲清定位差异）：
> 您说得对，我先承认这一点：**Mermaid 任务画布确实不是"把 50 轮对话压成更短"那种意义上的上下文压缩**，它和 Claude Code 的 compact 解决的是不同问题。我讲清楚两者的定位：

#### Mermaid 任务画布解决的是"长任务的问题定位与跳转"，不是"对话历史的压缩"

> 在 coding agent 的长任务里，真正的问题不是"50 轮对话记不住"，而是**agent 在 loop 模式里不停调工具，上下文被 tool result 撑爆，但根因还没找到**。通用摘要如果省略了错误日志、文件路径等精确证据，agent 后续就很难核对，所以我额外保留 refs 和引用链。
>
> Mermaid 画布的思路是：把"调了哪些工具、形成什么链路"结构化成一张图（node_id 映射到工具调用摘要），**原文存 refs/*.md 只留索引**。这样：
> - **上下文里只放图 + 摘要**，token 大幅下降。
> - **agent 不需要从头 loop**，而是看图判断"最可能出问题的节点在哪"，**有跳转地**去读那个节点的原文（按 node_id → result_ref 找回），而不是一层层重查。
> - 这是**把"线性重放"变成"图上跳转定位"**，解决的是长任务根因排查的效率问题。

#### 和 Claude Code compact 的区别（正面回答面试官的对比）

> | 维度 | Claude Code compact | 我的 Context Offload + Mermaid |
> |------|---------------------|-------------------------------|
> | 解决问题 | 当前会话接近窗口上限后继续运行 | 长任务里 Tool Result 撑大 Prompt + 证据难定位 |
> | 压缩方式 | 随宿主版本和策略变化，不猜未公开实现 | 完整结果外移到 refs，热 Prompt 留摘要和索引 |
> | 证据保留 | 取决于宿主自身的存储与恢复机制 | `node_id -> result_ref` 可回到完整结果 |
> | 定位能力 | 不作绝对判断 | MMD 提供任务状态和证据导航 |
>
> **诚实承认**：如果用户的需求是"50 轮闲聊后还能接着聊"，那 Claude Code compact 式的摘要更直接，我的 Mermaid 画布不是为这个设计的。我的设计是**针对 coding agent 长任务**——工具调用多、证据不能丢、需要跳转定位。

#### 面试官进一步确认："所以这是日志定位/问题排查的优化，不是上下文压缩？"

> **诚实回答**：您这么总结有道理。更准确的说法是：**Context Offload 是上下文压缩（把 tool result 移出 + 留索引，确实降 token），Mermaid 画布是任务状态的结构化呈现（解决定位跳转）**，两者配合使用。如果严格按"上下文压缩 = 把长对话压短继续对话"这个定义，那我的 Offload 部分是压缩，Mermaid 画布更偏任务管理。我之前把两者放一起讲，确实容易让人误解，这是表述上的问题。

> ⚠️ **关键**：这里要**诚实承认面试官的区分有道理**，不要硬辩。面试官明显懂行，硬辩会失分。承认表述问题 + 讲清两部分各自定位，是更稳的策略。

## 四、L0~L3 抽取与准确度（本场重点 3）

### Q8. L0 到 L3 的多层记忆架构具体体现在哪？给什么用？

**参考答案**（基于真实实现）：
> 四层各有明确职责，不是为分层而分层：
> - **L0 原始对话证据**：保存原始用户和助手消息、消息 ID、会话和时间信息。**给系统兜底**——抽象层可能丢细节，L0 用于审计和原话检索；工具结果卸载属于另一条短期链路。
> - **L1 原子记忆**：只抽取 `persona / episodic / instruction` 三类记忆。**给检索用**——把增量消息变成可检索、可去重、可更新的原子记录；它不是会话摘要。
> - **L2 场景归纳**：把 L1 点状事实按主题/场景聚合。**给宏观上下文**——单条 L1 只能答局部，L2 让 agent 理解"这个场景整体在做什么"。
> - **L3 长期画像**：生成紧凑的 `persona.md`，沉淀相对稳定的偏好、能力和协作方式。
>
> 当前加载策略更准确地说是：L3 Persona 正文和完整 Scene Navigation 放 system 后缀；本轮相关的少量 L1 放 user 前缀；L2 场景正文沿导航按需读取；需要原话时再主动搜索 L0。不是把完整 L2/L3 正文每轮全部塞进去。

### Q9. 这些都是直接通过大模型从历史对话抽取出来的，对吧？

**参考答案**：
> 对，L1 抽取、L2 场景组织和 L3 Persona 生成都用了 LLM，但三层任务不同，不是把同一份摘要逐级晋升。L0 是原始证据落库，不经过这些抽象生成步骤；Prompt 约束能降低风险，但不能等同于确定性正确性保证。

### Q10. ⚠️ 抽取过程中有没有方法/手段尽可能提升 L0→L3 的准确度？

**参考答案**（当前能力和缺口分开讲）：
> 有约束，但我不会说已经有“五层准确度保险”。当前做了这些：只从本批新增消息抽取；L1 保存 `source_message_ids`，可以回到 L0；新记忆先召回相似旧记录，再由 LLM 判断 `store / skip / update / merge`；L0 和 L1 JSONL 保留追加证据，在线 Store 保留当前规范记录。
>
> 边界也要讲清：来源 ID 还没有逐条验证存在性和内容蕴含，不等于严格 span；`priority` 是重要度，不是事实置信度；当前没有低置信候选区、按出现频次自动晋升、隐式反馈闭环或一键恢复旧版本。下一版我会先补来源校验和 Claim-Evidence 判断，再单独增加 evidence confidence、冲突状态和纠错事件。

### Q11. ⚠️ 置信度怎么制定？冲突怎么检测？通过语义匹配/向量相似度检索历史的，让大模型识别有没有冲突？

**参考答案**：
> 您说的“先召回候选，再让模型判断”接近当前实现。新 L1 会优先用向量召回相似旧记忆，向量不可用时退到 FTS；然后一次批量 LLM 判断返回 `store / skip / update / merge`。这解决的是语义去重和新旧记录处理，不是完整的实体属性冲突引擎。
>
> 当前**没有事实置信度公式**。L1 的 `priority` 只表示重要程度，不能解释成“基础分 + 频次 - 冲突惩罚”；L2 也不是事实层，L3 更不是达到阈值后的事实晋升区。可变/不可变属性 Schema、冲突并存与降权、evidence confidence 都是下一版要补的治理能力。

### Q12. ⚠️ 面试官挑战："你为什么会确认呢？让用户确认其实很难，他为什么要确认？领导强制？还是工具特别好？有什么手段让用户确实来确认？"

> **面试官指出核心问题**：依赖用户确认是不现实的——像元宝/豆包，如果回答不满意还反过来问用户"确认对不对"，用户觉得慢就不用了。**你的冲突处理如果靠用户确认，等于回避了最大问题。**

**参考答案**（先澄清现状，再给改进方案）：
> 您这个挑战是对的，但我先把现状说准：当前流水线**没有“遇到冲突就弹窗让用户确认”**，所以系统正确性也不依赖用户主动确认。当前仍然是相似候选召回后做 `store/skip/update/merge` 判断。
>
> 真正的短板是：没有完整的实体属性模型和纠错闭环。下一版普通冲突不打断用户；先识别属性是否允许随时间变化，判断不了就并存并降权。只有付款、身份等高风险事实才选择性确认；用户明确说“不对”时，再把它记录成纠错事件，驱动重抽取和索引更新。隐式反馈目前还不是已实现闭环，不能提前当成果讲。

### Q13. 面试官总结："所以现在置信度只是冲突会降，没冲突就认为很高？"

**参考答案**（直接纠正前提）：
> 当前不能这样概括，因为系统还没有事实置信度字段和公式。已有的 `priority` 是“这条记忆有多重要”，Offload `score` 是“摘要能多大程度替代原文”，都不是事实可信度。冲突处理靠相似候选加 LLM 四动作判断，不靠分数晋升。频次、来源质量和冲突惩罚可以进入下一版 evidence confidence，但现在不能说已经在算。

### Q13A. 这个系统实际是什么部署形态？同一主题每天都聊，是否每次要捞全部历史？

**美狮物流面试新增追问：**
> 先回答物理形态：按当前现场口径，主路线是**本地插件 + SQLite**。插件在模型调用前 Recall，一轮提交后 Capture；JSONL 保存原始证据，L2/L3 使用 Markdown，Tool Result 原文放 refs。`TdaiCore` 也支持 Hook 或 HTTP Gateway 适配，但那是架构能力，不能和实际部署混为一谈。
>
> 在线也不会把同一主题的全部历史取回再总结。L0 保留原话，L1 保存可检索原子记忆，L2 后台合并主题场景，L3 保持紧凑 Persona；每轮只做有界 Top-K Hybrid Recall，先返回当前规范记录或摘要，争议时才下钻来源。查询成本因此不与全部历史线性增长，但后台聚合、Embedding 欠账、热点用户和 SQLite 写竞争仍需监控，不能说分层后容量问题自动消失。

## 五、其他项目

### Q14. AI 周报系统应该是个很老以前的系统吧？后面没变化了吧？

**参考答案**：
> 对，是 2023 年早期做的，比较早的探索。核心设计原则（数字与叙述分离）到现在没变，但系统本身已经稳定运行，没大改动。我后来的精力主要转到 CodeWiki 和记忆系统了。
>
> 诚实说：这是个早期项目，技术深度不如后面两个，但它的"不让 LLM 算数只让它表达"原则我后来一直沿用。

### Q15. ⚠️ 你提到"prompt 中间注意力最低、前后最高"，有探究过为什么吗？

**参考答案**（先说现象，再说因果边界）：
> Lost-in-the-Middle 是一个经验现象：在一些模型、任务和上下文布局里，同一条相关信息放在长上下文中间时，利用效果会比放在其他位置差。但它不是所有模型都固定呈 U 形，也不是“中间注意力最低”这句话能覆盖的定律，具体结果会随模型版本、任务类型、上下文长度、干扰内容和提问方式变化。
>
> 至于为什么，我会说目前有多种可能贡献因素，包括位置表示方式、训练数据里的长度和布局分布、长上下文里的信息竞争，以及生成时的近因偏好。它们可能共同作用，但我不能把“位置编码衰减 + 首尾锚定”说成已经证明的唯一机制。看一张 Attention Heatmap 也只能说明模型在某次前向里把权重放在哪里，注意力权重本身不是因果证明。
>
> 工程上我也不会机械地说“重要信息永远放头尾”。我会在实际模型和评测集上对比目标证据放前、中、后，以及重排、摘要、检索后置等布局，测精确召回、引用正确率和任务成功率。哪种布局在这套模型上稳定，我才采用哪种；模型升级后还要回归。

### Q16. ⚠️ CodeWiki 是什么时候做的？今年大模型能力飞跃、agentic 能力很强后，这个项目存在的价值在哪？

> **这是 CodeWiki 的生死线问题**，和安克那场"vs Claude Code init"同性质。面试官在问：模型够强了，你的图还有意义吗？

**参考答案**（把当前能力和边界一起说）：
> CodeWiki 是 2024 年做的。现在模型的代码理解和 Agent 能力确实强了，所以我不会说 CodeWiki 对所有仓库都有必要；它的价值主要在需要**可复用结构索引、可追溯证据和增量维护**的企业代码库。
>
> 1. **结构提取可以复用**：当前实现对 Python 用标准库 `ast`，其他已支持语言用 tree-sitter，把选定的类、函数、导入和语法关系归一成 `AstSymbol`。这些已抽到的语法事实比每次让模型重新猜更稳定，也能链接回源码证据。但我要讲清楚：跨文件 `calls/references` 仍有启发式成分，动态分派、反射、重载和完整类型解析达不到编译器或 LSP 的精度，我不会把它说成“调用图绝对正确”。
>
> 2. **离线计算可以摊销**：解析、切块、关系抽取和页面生成可以预先完成，在线问题只取相关符号、关系和页面，不必每次把整个仓库重新送进模型。实际能省多少 Token、延迟和费用要用同一仓库、同一问题集做基线测试，我不会在没有测量记录时说“低几个数量级”。
>
> **价值定位**：我把能静态提取并验证的结构交给解析器，把跨模块语义解释和页面组织交给模型，并让生成结果保留到源码符号的引用。下一版如果要追求更准的跨文件关系，我会接类型信息、编译器前端或 LSP，而不是继续把启发式边当成确定事实。
>
> 诚实边界：模型和 Harness 变强确实压缩了 GraphRAG 的优势区间。小仓库、一次性任务或本地变化特别快的分支，原生 Agent 或 Agent + Repo Map/Skill 更直接；Skill 可以指导 `read/grep/bash/LSP` 实时取证，产物写成 Markdown/JSON，也不一定需要向量库。CodeWiki 只在反复跨模块问题、可追溯引用和团队复用上争取增量价值。
>
> 当前还要正视陈旧索引：Git Diff/Hash 能发现变化，但图、Chunk、Wiki 和实际文件读取没有统一不可变 Revision。大分支未提交改动时，旧证据可能短暂可见。最终应比较原生 Agent、Repo Map/Skill 和 CodeWiki 的任务成功率、引用、Token、索引成本和陈旧率，而不是预设“大仓库一定需要图”。

## 七、复盘：这场面试的得失与风险

### 这场面试的特殊性

微众这场和前几场**性质不同**：前几场是"你被评估技术够不够"，这场面试官**用他的理解框架持续挑战你的设计合理性**——他不接受"业界都这么做"，要你证明"你的设计解决了什么实际问题、为什么这么设计"。这是**架构师级审查**的风格。

### 得分点

| 环节 | 表现 | 评价 |
|------|------|------|
| 问题定义（Q2-Q4） | 能给出"值串扰/约束丢失/重复噪声"三个具体下降层面 + 真实例子 | ★★★★ 如果当场答到这个度 |
| L0~L3 职责（Q8） | 能讲清每层给什么用，不是为分层而分层 | ★★★★ |
| 抽取准确度（Q10） | 能讲清来源 ID、四动作判断、可追溯，以及严格 span/置信度仍是缺口 | ★★★★ |
| CodeWiki 价值（Q16） | 承认原生 Agent/Skill 基线，再用结构证据、引用和复用价值做可验证对照 | ★★★★ |

### 风险点（下来必须补）

| 环节 | 风险 | 严重度 |
|------|------|--------|
| **Mermaid 画布定位（Q7）** | 被面试官成功挑战"这不是上下文压缩"——表述上把 Offload 和 Mermaid 混在一起讲，导致误解 | ★★★★★ 致命 |
| **用户确认不现实（Q12）** | 依赖用户确认被指出不现实，当场没给出不依赖确认的方案 | ★★★★★ 致命 |
| 上下文压缩定义 | 面试官用 Claude Code compact 框架来套，你的设计思路不同但没讲清差异 | ★★★★ 高危 |
| 置信度机制 | 旧答案把 priority、频次和候选区说成现状；当前其实没有事实置信度公式 | ★★★★ 高危 |
| 部署形态与容量 | 如果先讲 Hook/Gateway 能力而不说“实际本地插件 + SQLite”，容易再次被连续澄清 | ★★★★ 高危 |

### 三个必须内化的校正

**校正 1：Context Offload 和 Mermaid 画布要分开讲，别混**
- 之前把两者放一起讲成"上下文压缩"，导致面试官合理质疑"Mermaid 不是压缩"。
- 正确表述：**Context Offload = 上下文压缩**（tool result 移出 + 留索引，降 token，可恢复）；**Mermaid 画布 = 任务状态结构化**（解决长任务定位跳转）。两者配合但职责不同。
- 以后讲项目时先讲 Offload（这是压缩），再讲 Mermaid（这是任务管理），不要让面试官把它们混为一谈。

**校正 2：冲突处理不能依赖用户确认**
- 之前的"不可变属性冲突 → 向用户确认"是不现实的设计，被面试官精准击中。
- 当前事实：流水线并没有冲突即弹窗；现有能力是候选召回 + LLM 判断 `store/skip/update/merge`，但还没有可变/不可变属性状态机。
- 下一版方向：普通冲突不打断用户，先识别属性和作用域，无法判定时并存降权；高风险事实才选择性确认，明确纠正再形成审计事件。

**校正 3：用面试官的框架讲，不要用你的框架讲**
- 面试官用"compact 式压缩"理解上下文压缩，你的设计是"可恢复 offload + 分层记忆"，两者不同。
- 策略：**先对齐定义**（"您说的压缩是指 compact 那种把对话压短继续聊，我的设计侧重点不同，我讲清楚"），再讲差异。不要假设面试官会自动理解你的框架。

### 下来必做

1. **重写"上下文压缩"的表述**：明确区分 Offload（压缩）和 Mermaid（任务管理），准备一段 3 分钟的清晰表述，不再让面试官混淆。
2. **重写"冲突处理"方案**：先讲当前四动作判断和真实缺口，再讲属性 Schema、并存降权和纠错事件，不能把下一版说成已经上线。
3. **准备"长上下文准确率下降"的 2-3 个可核验例子**：有 Trace 就讲真实 Bad Case；没有就明确说是可复现示例，不能包装成生产事故。
4. **对齐微众岗位的"三能力"要求**：产品思维 + 项目管理 + 开发，后续沟通要体现前两者，不能只讲技术。
5. **补当前竞争基线**：实际运行一个代码分析 Skill，并为 CodeWiki 增加 dirty worktree 陈旧索引测试；不要只与普通向量 RAG 比较。

## 八、横向对比：微众这场和其他场的差异

| 维度 | 微众 | 京东 | 安克 | 码云 |
|------|------|------|------|------|
| **面试官风格** | 架构师审查（挑战设计合理性） | 架构师定级（设计题） | 产品+技术（对标竞品） | 概念+项目（广度） |
| **核心挑战** | "你设计为什么这么定" | "现场设计新系统" | "你的价值 vs 竞品" | "概念懂不懂" |
| **最大风险** | Mermaid 定位 + 用户确认 | 路由引擎质量判断 | vs Claude Code init | 幻觉机制答错 |
| **岗位要求** | 产品+项目+开发三能力 | AI first 超级个体 | 不明 | CodeWiki 岗 |

**关键发现**：微众和京东都是"架构师级深挖"，但**京东给你新题现场设计**，**微众深挖你自己项目的每个设计决策**。微众这种更难防——因为你的设计如果有不合理处，会被精准击中。Mermaid 定位和用户确认就是被这样击中的。

**应对策略**：对自己项目的每个设计决策，都要能回答"**为什么这么设计、解决了什么实际问题、有什么替代方案、为什么没用替代方案**"。这是微众这类面试的核心准备方向。
