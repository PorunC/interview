# 金融 AI 与自动授信高频面试题

> **使用边界**：本题库面向美股投研 Agent、Open Banking、自动授信和金融 Agent 岗位。当前材料能够证明的是三个公司内部 AI 项目的工程设计；本人是否做过美股投研或信贷生产系统、是否接触过真实金融数据与审批链路，仍需本人核实。未确认前，我统一按“基于现有 AI 工程能力给出的迁移设计”回答，不把方案题说成生产经历。
>
> **合规边界**：这里讨论的是数据授权、模型治理、解释、审计和人工复核等技术控制，不下具体法规适用结论。司法辖区、产品类型、客户类型和数据角色不同，要求会变化，最终必须由目标公司的法务、合规和模型风险团队确认。
>
> **回答规则**：全部使用第一人口语表达。简历里的投产范围、用户、团队、模型和指标只有在内部证据核实后才引用；不虚构数据终端、投资收益、授信效果、审批权限或监管结论。

## 一、美股投研 Agent：数据、时点、证据与评测

### Q001：你做过美股投研生产系统吗？为什么你觉得自己能做这个岗位？

> **口语化回答：** 我先把边界说清楚：目前材料还不能证明我做过真实的美股投研生产系统，所以我不会说自己跑过实盘、接过某个行情终端，或者创造过投资收益。我能迁移过来的是 CodeWiki 的结构化解析、图检索、证据引用，以及 Agent Memory 的分层存储和可追溯召回。放到投研场景，我会把它做成“按时点冻结数据、结构化提取财务事实、检索原始披露、生成带引用结论”的研究助手，最终判断仍由研究员负责。
>
> **原理追问：** 我认为投研 Agent 的难点不只是模型会不会总结，而是同一家公司、同一个指标在不同披露时间、财年口径、币种、单位和修订版本下是否可比。系统必须同时保留业务有效时间、系统观测时间和原始证据，才能回答“当时能知道什么”。
>
> **容易踩坑：** 我不会把“会做 RAG”直接等同于“懂投研”，也不会用今天修订后的数据回答过去的决策问题；更不会把生成内容包装成投资建议或收益承诺。
>
> **岗位或项目连接：** CodeWiki 已有 AST、图谱、检索和引用边界，Agent Memory 有原始证据与摘要分层；把代码符号换成公司、报告期、指标和公告关系是可迁移思路，但美股数据接入、授权和线上效果都属于待验证的新领域。

### Q002：如果让你设计一个美股投研 Agent，端到端架构怎么拆？

> **口语化回答：** 我会拆成六层：数据源接入、原始文件留存、标准化与实体解析、时点化事实库、检索与工具层、研究工作流层。公告和财报先原样落对象存储，生成内容哈希和来源元数据；XBRL、表格和正文分别解析，再统一关联到公司、证券、报告期和披露事件。Agent 只能通过受控工具查事实、取证据、做计算，最后输出“结论、依据、假设、冲突和缺口”，而不是直接给买卖动作。
>
> **原理追问：** 我会把确定性计算和语言生成分开：财务比率、同比环比、复权和币种转换由代码完成，LLM 负责查询规划、证据归纳和表达。每一步产生可复现的输入快照、工具结果和版本号，方便回放。
>
> **容易踩坑：** 我会避免把所有内容直接塞进向量库，让模型自己“算”；也不会让 Agent 无限制抓网页、调用交易或写数据库。数据许可、时点和工具权限必须在架构第一层解决。
>
> **岗位或项目连接：** 这个拆法继承 AI 周报“数字由程序算、LLM 只解释”的原则，也借鉴 CodeWiki 的结构化索引加 GraphRAG；它是金融迁移设计，不是当前项目已有的投研架构。

### Q003：什么是 point-in-time 数据？为什么投研系统必须做？

> **口语化回答：** 我理解的 point-in-time 不是给每行加一个日期就结束，而是能还原“在某个决策时刻，系统实际上已经看到哪些信息”。我至少保存 `valid_time`，表示事实对应哪个业务期间；再保存 `known_at` 或 `system_time`，表示这条披露什么时候被市场和系统知道。回测查数时只能取 `known_at <= as_of_time` 的版本，后续修订不能穿越回去。
>
> **原理追问：** 财报的报告期结束日、正式提交或接收时间、系统抓取时间是三件事。一个 12 月 31 日的年度数字可能到次年才披露，所以不能按报告期结束日提前给模型使用；时点模型本质上是双时态或版本化数据模型。
>
> **容易踩坑：** 我会特别防止用最新的标准化财务库覆盖历史、用当天收盘价响应盘后公告、忽略时区和修订文件。这些都会造成 look-ahead bias。
>
> **岗位或项目连接：** Agent Memory 已经强调原始记录和摘要版本不能混为一层；迁移到投研后，我会进一步增加业务有效时间和系统观测时间，这是当前记忆项目没有证明已实现的金融能力。

### Q004：你会怎么接入 SEC EDGAR？

> **口语化回答：** 我会优先走 SEC 官方 EDGAR 页面和 `data.sec.gov` 提供的 submissions、company facts 等接口，按 CIK 建公司主索引，再按 accession number 唯一标识一次 filing。采集器带清晰的 User-Agent 联系信息，遵守 SEC 当前 Fair Access 要求，做全局限速、退避、缓存和增量同步；原始文档、索引 JSON 和抓取响应都保留哈希与时间戳。
>
> **原理追问：** submissions 更适合拿申报历史和元数据，company facts 适合查询标准化 taxonomy 下的事实，但 filing 内的自定义扩展、脚注和上下文仍可能需要解析原始 Inline XBRL。不同接口不能互相替代。
>
> **容易踩坑：** 我不会暴力并发爬 SEC、只存解析结果不存原文，也不会把 ticker 当永远不变的公司主键。接口字段和访问政策可能更新，所以限速与解析规则要配置化并监控失败率。
>
> **岗位或项目连接：** AI 周报的数据采集链路有重试、补跑和完整性校验思路；在 SEC 场景需要再补 Fair Access、accession 幂等和 filing 版本治理，不能说现有采集器已接过 EDGAR。

### Q005：10-K、10-Q、8-K、20-F、6-K 这些文件怎么处理？

> **口语化回答：** 我不会只按表单类型贴标签。我会先识别发行人类型和报告语义：10-K、10-Q通常承载美国发行人的年度和季度披露，8-K是重大事项的及时披露；20-F和6-K常见于外国私人发行人。系统按 form、item、fiscal period、accepted timestamp 和 amendment 关联，再让检索根据问题选择正文、结构化事实或附件。
>
> **原理追问：** 同一个事件可能先出 8-K 附件或新闻稿，后进入 10-Q；不同文件的审计程度、覆盖范围和披露时点不同。我会保留来源层级和事件关系，而不是简单让“最新文档覆盖旧文档”。
>
> **容易踩坑：** 我不会假设所有公司都按同一种表单和季度节奏披露，也不会把附件里的非 GAAP 指标当成 XBRL 标准事实。具体表单含义和适用要求要以 SEC 当前说明及专业人员判断为准。
>
> **岗位或项目连接：** CodeWiki 会区分代码、符号、文件和调用关系；投研迁移中类似地把 form、item、附件、事实和事件建成不同实体，仍需金融领域 Schema 与测试集验证。

### Q006：XBRL 到底解决什么问题？你会怎么解析？

> **口语化回答：** 我把 XBRL 理解成“带业务语义和上下文的财务事实”，不是普通 HTML 表格。解析一条 fact 时，我会同时保留 concept、value、unit、period、entity、dimensions、decimals、taxonomy、filing 和原始定位。只有这些上下文一致或经过明确映射，数字才有资格比较。
>
> **原理追问：** 同一个 concept 可能是 instant 或 duration；同一期间还可能按业务分部、地区等维度拆分。Inline XBRL 把人读的 HTML 与机器读标签结合，但机器可读不代表语义天然统一，仍要做上下文和维度校验。
>
> **容易踩坑：** 我不会只按标签名抓数、丢掉单位和维度，也不会把 `decimals` 当成真实精度保证。重复 fact、nil 值、缩放、负号、上下文冲突和自定义扩展都需要显式处理。
>
> **岗位或项目连接：** CodeWiki 的 AST 经验能迁移到“先结构化解析、再让 LLM 理解”，但 XBRL taxonomy 和财务口径是新的领域知识，必须用官方样本和会计专家反馈校验。

### Q007：不同公司大量使用自定义 XBRL Extension，怎么做横向对比？

> **口语化回答：** 我会把标准概念和公司扩展概念分开保存。只有数据源确实提供显式 Anchoring 时才把它作为证据；否则主要结合标签、定义、Presentation/Calculation 关系、Context、历史用法和数值行为生成候选映射，再通过规则与人工审核确认。映射结果带版本、置信度和适用范围；没有可靠映射时，我宁可展示原概念并标“不可直接比较”，也不硬归一。
>
> **原理追问：** 公司可能因为业务特殊而扩展，也可能只是标签差异。映射不只是语义相似，还要检查 period type、balance、unit、dimensions 和 calculation network；一个概念也可能只在特定分部上下文下对应标准项。
>
> **容易踩坑：** 我不会用 embedding 最相近就自动合并，也不会永久锁死第一次映射。taxonomy 演进和公司披露习惯变化后，需要重新验证并保留历史版本。
>
> **岗位或项目连接：** 这和 CodeWiki 的多语言符号归一有相似性，但财务映射的错误成本更高。我会复用候选检索和证据展示，不会声称现有代码图谱已经解决财务概念标准化。

### Q008：财报修订、10-K/A 或数据源回填怎么处理？

> **口语化回答：** 我不会原地覆盖。每次 filing 和每条事实都建不可变版本，记录 accession、accepted_at、ingested_at、supersedes 关系和变更原因。在线查询默认可看最新已知版本；做历史回放时按 as-of 截断，只能看到当时已经披露的版本，并把“后来被修订”作为单独事件展示。
>
> **原理追问：** 业务有效时间告诉我数字属于哪个期间，系统时间告诉我哪个版本何时进入系统。采用 append-only 加有效区间，能同时支持当前视图和历史视图，也便于审计修订影响。
>
> **容易踩坑：** 我会防止供应商静默回填、同一事实多个 context 被错误去重、修订后缓存不失效。历史回测和当前研究必须使用不同的查询模式。
>
> **岗位或项目连接：** Agent Memory 对更新和 merge 已保留来源，但还不是完整双时态事实系统；这里是对其可追溯思想的金融化增强，需要单独实现。

### Q009：CIK、ticker、公司名和证券之间怎么做实体对齐？

> **口语化回答：** 我会把发行主体和可交易证券拆开。公司主体用稳定的官方标识和内部 entity_id 管，ticker、交易所、share class、ISIN 等作为带生效区间的证券标识；名称只是别名。一次更名、换代码、换交易所或并购都产生映射事件，不能改掉历史。
>
> **原理追问：** 一个发行人可能有多类证券，一个 ticker 也可能在不同时期被不同主体使用。实体解析需要时间维度、来源优先级和人工处理队列，不能只做字符串模糊匹配。
>
> **容易踩坑：** 我不会把 ticker 作为数据库主键，也不会仅靠公司简称合并实体。ADR、外国发行人、退市重组和 share class 都可能让一对一假设失效。
>
> **岗位或项目连接：** CodeWiki 图里符号 ID 不能只靠显示名，金融实体也一样；可迁移的是稳定 ID、别名和关系建模，真实证券主数据仍要来自获授权且可验证的数据源。

### Q010：股票拆分、分红、并购、退市这些公司行动怎么处理？

> **口语化回答：** 我会建立独立的 corporate action 事件表，保存事件类型、公告日、除权日、生效日、比例或金额、来源和版本。价格、股数、EPS 与市值的分析都明确使用原始值还是复权值；做跨期比较时展示调整因子链，让结果可以从复权值追回原值。
>
> **原理追问：** 拆分会同时影响股价和股数，现金分红影响 total return 但不等于价格回报，并购换股还会改变证券连续性。不同数据商对 adjusted close 的定义可能不同，所以必须保存供应商和算法版本。
>
> **容易踩坑：** 我不会把复权价与原始财报每股指标混算，也不会只按公告日处理事件。忽略退市股票和合并前证券会制造 survivorship bias。
>
> **岗位或项目连接：** 这属于投研专有的数据工程，不是三个现有项目已经做过的能力；我能迁移的是版本化、事件溯源和确定性计算方法。

### Q011：时区、交易日和盘前盘后披露怎么处理？

> **口语化回答：** 我会把所有原始时间保留其来源时区并统一存 UTC，同时单独保存交易所日历和本地展示时区。判断一条消息能否用于某根行情 Bar 时，不只看日期，而要看精确披露时间、市场是否开盘、下一个可交易时点以及数据进入系统的时间。
>
> **原理追问：** 盘后 16:05 发布的财报不能影响当天 16:00 已收盘的策略；夏令时、半日市、临时休市和跨市场证券都会改变边界。事件时间和处理时间也要分开。
>
> **容易踩坑：** 我不会把所有日期按北京时间零点处理，也不会用自然日代替交易日。只保存 `date` 会让盘前盘后和夏令时问题无法回放。
>
> **岗位或项目连接：** AI 周报按业务日处理数据的经验可以迁移，但交易所日历和可交易时点是新增的金融规则，需要专门日历源与边界测试。

### Q012：行情和基本面怎么做 point-in-time Join？

> **口语化回答：** 我会先定义研究问题的 as-of 时间，再对每个基本面事实取该时点前最后一个可用版本，对行情取对应市场可交易时点的原始或明确复权序列。Join 结果保存事实版本、价格版本、汇率版本和日历版本，确保同一查询可以重放。
>
> **原理追问：** 这是 as-of join，不是简单按季度末等值连接。基本面代表业务期间，但可用时间是披露时间；行情有交易时间，汇率也有自己的定价时间，三者要按研究规则对齐。
>
> **容易踩坑：** 我会避免用季度末价格配后来才发布的财报、把不同币种直接相除，以及用今日最新复权因子重算过去却不留版本。
>
> **岗位或项目连接：** AI 周报的多源数据完整性检查能提供方法论，但金融 as-of join 和回测隔离需要全新的数据模型与测试证据。

### Q013：公开披露数据不是都能随便用吗？数据授权怎么设计？

> **口语化回答：** 我不会把“网页上能看到”理解成“可以任意抓取、再分发或用于所有模型训练”。我会为每个数据源建数据合同，记录来源、允许用途、用户范围、缓存期限、再分发限制、模型训练权限、删除要求和责任人；查询结果沿 lineage 继承这些限制。SEC 官方访问也要遵守当前访问政策，商业行情、研报和新闻更要按合同确认。
>
> **原理追问：** 数据授权既是入口控制也是派生数据控制。原文、embedding、摘要、特征和模型样本都可能属于衍生资产，所以不能只在下载时检查一次。
>
> **容易踩坑：** 我不会引用一个不存在的“公开数据免责规则”，也不会默认买了终端就能让 Agent 批量导出给全公司。具体版权、许可和跨境要求必须由法务和供应商合同确认。
>
> **岗位或项目连接：** CodeWiki 当前适合内部代码，但集中化后同样需要仓库 ACL 和派生索引授权；金融场景会把这套授权扩展到 source、dataset、feature 和 answer 全链路。

### Q014：财报、新闻稿、电话会和第三方新闻互相冲突怎么办？

> **口语化回答：** 我不会让模型静默挑一个喜欢的答案。我会按事实类型定义来源优先级，但同时保留时效和语境：监管披露适合作为正式财务事实依据，管理层新闻稿和电话会可补充解释，第三方新闻可提供事件线索。出现冲突时，我输出各自主张、时间、口径差异和未解决状态，让研究员判断。
>
> **原理追问：** 冲突可能来自 GAAP 与 non-GAAP、合并与分部、报告期不同、币种不同、估计值与最终值不同，并不一定是谁“错了”。先做结构化对齐，再谈来源可信度。
>
> **容易踩坑：** 我不会简单规定“最新的永远对”或“官方的每个字段都能覆盖其他来源”，也不会让摘要丢掉限定词、预测区间和管理层措辞。
>
> **岗位或项目连接：** Agent Memory 当前有 store、skip、update、merge 的候选冲突处理，但还没有财务属性级状态机；这里会增加口径、时点和来源类型，不夸大现状。

### Q015：投研答案怎么做到可引用、可追溯？

> **口语化回答：** 我要求每个关键 claim 都带 evidence id，而不是只在文末放几个链接。证据对象保存 accession 或文档 ID、章节或表格定位、原始片段、抓取时间、内容哈希和授权标签；数字结论还保存计算公式及输入 fact id。输出前做引用存在性、范围和数值一致性检查，失败就降级成“不足以确认”。
>
> **原理追问：** 链接只能证明来源页面存在，不能证明句子被来源支持。更强的可追溯链是 claim 到 evidence span，再到原始不可变文档和解析版本；计算结果则要有 lineage DAG。
>
> **容易踩坑：** 我不会把模型生成的引用当真，也不会只验证引用 ID 合法却不验证支持关系。网页内容变化和授权过期也会让历史引用失效，所以要保留合规允许的快照与哈希。
>
> **岗位或项目连接：** CodeWiki 已有 Allowed Source Ref 和 citation 范围控制，但还不能说每个 claim 都经过蕴含验证；投研版本需要再加数字 lineage 和 claim-evidence 评测。

### Q016：财务指标应该让 LLM 提取和计算吗？

> **口语化回答：** 我会把 LLM 放在候选识别和解释层，不让它成为唯一计算器。XBRL 或表格有可靠结构时由解析器取数；同比、毛利率、自由现金流等公式由版本化代码计算，并检查单位、期间和缺失值。LLM 可以解释变化原因，但必须引用管理层披露，不能从数字相关性直接编因果。
>
> **原理追问：** 结构化事实适合确定性程序，非结构化脚注可用模型抽取，但要输出 schema、置信度和证据 span。计算与叙述分离后，模型升级不会改变历史数字。
>
> **容易踩坑：** 我会防止把百万和千混算、duration 与 instant 混用、负号和括号丢失，以及让模型对缺失值做“合理补全”。non-GAAP 指标也要保留公司自己的定义。
>
> **岗位或项目连接：** 这直接沿用 AI 周报“数字和状态由 SQL/代码确定，LLM 只做分段解读”的现有原则；金融字段与公式是下一步领域适配。

### Q017：长财报怎么 Chunk，普通向量切块为什么不够？

> **口语化回答：** 我会先按 filing 结构切：form、item、章节、表格、脚注和 XBRL fact 是不同单元，再为长文本做有重叠的语义片段。检索先根据公司、时点、报告期和文档类型过滤，再做关键词、向量和结构关系扩展；表格行和脚注不能被随意拆散。
>
> **原理追问：** 投研问题经常要跨正文、财务表和脚注组合证据。纯向量 Chunk 不理解章节层级、报告期和数值上下文，容易找到相似措辞却用错公司或季度。
>
> **容易踩坑：** 我不会把整份 10-K 一次塞给模型，也不会只按固定字符数切。Chunk 必须继承 entity、form、period、accepted_at、section 和许可标签，否则召回后无法正确过滤。
>
> **岗位或项目连接：** CodeWiki 的符号级切分和图扩展思路能迁移成“章节加事实关系检索”；当前项目没有金融 filing parser，所以只把检索框架视为可复用。

### Q018：怎么防止投研 Agent 出现数字幻觉？

> **口语化回答：** 我会让模型尽量引用工具返回的 typed facts，而不是从长文本记数字。生成后做三类校验：引用中的数值是否存在，单位和期间是否一致，派生指标能否按公式复算。关键结论校验失败就删除或标不确定，不能靠再问模型一遍自我确认。
>
> **原理追问：** 结构化输出只保证 JSON 形状，不保证事实正确。真正的约束来自受控数据源、类型系统、确定性计算、claim-evidence 对齐和失败关闭策略。
>
> **容易踩坑：** 我不会用“温度设为 0”当防幻觉方案，也不会认为引用链接存在就代表数字正确。近似值、币种换算、每股与总额尤其容易被模型混淆。
>
> **岗位或项目连接：** CodeWiki 的引用白名单和 AI 周报的确定性统计能组合成这套校验；当前没有投研准确率数据，所以不会报虚构指标。

### Q019：怎么评测一个美股投研 Agent？

> **口语化回答：** 我会先按任务拆评测：实体与期间识别、事实取数、数值计算、证据召回、冲突识别、综合回答和拒答。测试样本冻结 query 的 as-of 时间，语料库只能包含当时可见数据；答案除了正确性，还看引用支持率、时点泄漏率、单位错误率、缺证据拒答率、延迟和成本。
>
> **原理追问：** 端到端分数不能告诉我问题出在数据、检索、计算还是生成，所以要同时有组件评测和工作流评测。涉及开放问题时，我会用有 rubric 的专家双评，并校准 LLM judge，不让 judge 看到候选系统身份。
>
> **容易踩坑：** 我不会用最新网页构造历史题、把同一 filing 的相邻片段分到训练和测试两边，也不会只看“回答像不像专业研报”。收益回测更不是问答质量的唯一代理。
>
> **岗位或项目连接：** 三个现有项目的评测证据仍有待补齐，尤其不能把记忆 Benchmark 的数字迁移成投研效果；这里给的是岗位落地时的评测设计。

### Q020：投研回测最常见的偏差有哪些？你怎么控制？

> **口语化回答：** 我重点防 look-ahead、survivorship、selection、data-snooping 和 transaction-cost omission。样本必须包含当时仍存在和后来退市的证券，特征按当时可见版本生成，模型与策略只在训练窗里调参，再走时间顺序的 walk-forward 验证；交易成本、延迟和可成交性要显式建模。
>
> **原理追问：** 同一数据集上反复试策略会把测试集变成训练集；公司成分表用今天的名单回看过去会产生幸存者偏差。即使统计显著，也要检查经济意义、稳定性和多重比较。
>
> **容易踩坑：** 我不会展示最好的一条收益曲线就声称有效，也不会把离线回测收益当真实投产成果。投资表现还受容量、市场冲击和制度约束影响。
>
> **岗位或项目连接：** 当前简历没有投资收益或实盘系统证据，所以我只讲控制方法；面试时会明确自己需要与量化研究、风控和合规共同验证。

## 二、Open Banking 与自动授信：数据、特征与决策平台

### Q021：你做过信贷生产系统吗？Open Banking 自动授信你怎么理解？

> **口语化回答：** 我先如实说，目前材料还不能证明我做过真实信贷生产系统，也不能证明我有授信审批权限，所以我会按迁移设计回答。我理解 Open Banking 自动授信，是在客户明确授权的范围内取得账户和交易数据，把原始流水标准化成可解释的现金流与负担特征，再由经过验证的风险模型、规则和策略引擎作出或辅助决策。LLM 可以帮助分类、整理材料和生成受约束说明，但不能把一段自然语言输出直接当授信结论。
>
> **原理追问：** 这条链路至少包含 Consent、数据接入、交易清洗、特征快照、模型评分、政策规则、理由码、人工复核、通知和审计。任何一层都要能版本化和重放，不能只讨论一个“AI 模型”。
>
> **容易踩坑：** 我不会把“不用传统 credit score”说成“不做风险评估”，也不会假设拿到账户数据就可无限使用。具体产品、地区和监管义务必须由法务、合规和模型风险团队确认。
>
> **岗位或项目连接：** AI 周报的多源采集、确定性统计和异常补跑可以迁移到流水处理；CodeWiki 和 Agent Memory 的证据追溯可以迁移到决策解释，但真实授信效果和合规性都不能由现有项目证明。

### Q022：Open Banking 的 Consent 应该怎么建模？

> **口语化回答：** 我会把 Consent 当一等业务实体，不只是一个布尔值。至少记录 consent_id、客户或主体、授权目的、数据范围、账户范围、授权时间、有效期、当前状态、撤回时间、上游 Provider 引用和政策版本。每次数据访问都校验当前授权，并把 consent_id 写入 lineage，后面才能知道某个特征和决定来自哪次授权。
>
> **原理追问：** 授权范围、访问 Token 和数据处理依据是相关但不同的概念；Token 仍有效不代表业务授权一定仍有效。Consent 有创建、授权、过期、撤回和失败等状态，需要状态机和不可变事件日志。
>
> **容易踩坑：** 我不会把一次授权理解成永久授权，也不会在客户撤回后只停止新拉取却继续无边界使用派生特征。撤回后哪些数据必须删除、哪些因审计或法定义务保留，要由合规确认并落实成策略。
>
> **岗位或项目连接：** Agent Memory 有生命周期和删除思路，但 Open Banking Consent 是更严格的业务授权状态；这是下一版迁移设计，不是现有记忆系统已经具备的合规能力。

### Q023：OAuth、Token、重定向和重新授权怎么设计？

> **口语化回答：** 我会让客户在受信任的银行或授权 Provider 页面完成身份确认，不在自己的系统收集网银密码。回调时校验 state、nonce、redirect URI 和签名，Token 放密钥管理系统加密保存，业务库只留引用；刷新、过期、撤销和重新授权都有明确状态。调用失败先分类，不能把需要客户重新授权的问题无限重试。
>
> **原理追问：** OAuth 授权码流程解决委托访问，OpenID Connect 解决身份层，具体 Open Banking Profile 还可能规定更强的客户端认证、签名和报文要求。我会按 Provider 认证资料和目标标准实现，不凭印象自创协议。
>
> **容易踩坑：** 我不会在日志打印 access token、把 Token 发到前端长期保存，或把 redirect 参数当可信身份。时钟漂移、Key rotation、重复回调和客户中途退出都要测试。
>
> **岗位或项目连接：** 当前三个项目没有 Open Banking OAuth 生产证据；我能迁移的是 Gateway 鉴权、Secret 管理和状态机方法，具体 Profile 必须重新实现并做安全评审。

### Q024：接多家银行或聚合商，数据 Schema 不一致怎么办？

> **口语化回答：** 我会保留三层数据：上游原始响应、Provider 适配层、内部 canonical model。原始层不可变，适配层只负责字段和状态翻译，内部模型统一账户、余额、交易、币种、状态和时间语义；每次转换记录 adapter version 和字段级 lineage。新 Provider 先通过契约测试，再进入相同的质量门禁。
>
> **原理追问：** Canonical model 能降低下游耦合，但不能把所有差异硬抹平。比如 pending 与 booked、余额类型、交易时间精度和 merchant 信息缺失，都要保留 Provider 特性与 `unknown` 状态。
>
> **容易踩坑：** 我不会用空字符串代替未知、把 pending 当最终交易，也不会修改适配规则后静默重算全部历史特征。Schema 演进需要版本、回放和影响评估。
>
> **岗位或项目连接：** AI 周报已有多源异构采集思路；迁移时需要更强的原始快照、canonical schema 和授权 lineage，不能把普通内部数据采集直接等同于银行数据接入。

### Q025：银行交易流水为什么要清洗？怎么清洗？

> **口语化回答：** 原始流水里会有 pending 与 booked 重复、撤销、退款、冲正、卡验证、小额测试、内部转账、现金提取和描述变化。我会先按 Provider transaction id、账户、金额、币种、时间和状态做状态合并，再识别内部转账和退款链；所有清洗都保留原始记录、规则版本和置信度，不直接覆盖。
>
> **原理追问：** 去重不是简单按金额加日期，因为真实交易可能同额同日发生多次。更合理的是事件状态机加多字段匹配，并在无法确定时保留候选关系，不把猜测变成事实。
>
> **容易踩坑：** 我不会把现金取款当普通消费、把账户间转账同时算收入和支出，也不会为了让特征好看删除异常值。清洗规则改变会影响历史评分，必须可回放。
>
> **岗位或项目连接：** AI 周报的完整性检查和幂等采集能迁移，但交易清洗需要领域规则、带标签样本和业务专家验收，当前项目没有证明这部分经验。

### Q026：Merchant 和交易分类怎么做？LLM 能直接分类吗？

> **口语化回答：** 我会做分层分类：先用银行提供的 code、商户 ID、字典和确定性规则，再用经过验证的分类模型处理长尾，最后把低置信或高影响样本送人工或保守归到 unknown。LLM 可以帮助解释模糊描述或生成候选标签，但输出必须受固定 taxonomy 约束，并经过脱敏、置信度和一致性检查。
>
> **原理追问：** 商户描述存在别名、支付聚合商和地理噪声，分类标签还会随产品策略变化。需要 taxonomy version、训练样本时点、模型版本和 override 记录。
>
> **容易踩坑：** 我不会把模型每次给出的自由文本当类别，也不会把“餐饮”直接解释成不良风险。分类误差会传导到 affordability 和理由码，所以高影响类别要单独评测。
>
> **岗位或项目连接：** CodeWiki 的结构化输出和模型路由可迁移到受约束分类，但金融流水、标签体系和准确率属于新数据，面试时不会虚构结果。

### Q027：怎么识别工资、稳定收入和一次性入账？

> **口语化回答：** 我会综合付款方、金额区间、周期、日期漂移、描述模式和连续出现次数识别 recurring income，并区分工资、福利、经营收入、退款、借款和账户内转账。结果输出收入事件、稳定性、置信度和缺失月份，不把单笔大额入账自动当月收入。
>
> **原理追问：** 工资可能因周末提前、奖金变化或多雇主而不固定；自由职业收入更不规则。可以用周期检测和实体归一生成候选，但最终特征要对观测窗口和不确定性敏感。
>
> **容易踩坑：** 我不会用简单正则看到 `salary` 就确认，也不会把 overdraft、朋友转账或贷款放款算收入。数据窗口太短时应降低置信度或要求补充材料。
>
> **岗位或项目连接：** 这和 AI 周报里“程序先确定事实、LLM 后解释”一致；但工资识别规则与模型必须用真实授权数据验证，现有项目无法证明。

### Q028：固定支出、债务和生活成本怎么识别？

> **口语化回答：** 我会识别房租或房贷、贷款还款、水电通信、保险、税费、赡养等 recurring commitments，同时把日常必要支出与可选消费分开。算法输出金额区间、频率、最近一次、变动和置信度；低置信条目不能直接变成拒贷原因，应进入规则确认或人工复核。
>
> **原理追问：** 周期交易可能按周、月或年度发生，付款日期会漂移，direct debit 也可能金额变化。需要 recurrence 模型、merchant/entity 归一和政策定义共同决定，而不是纯聚类。
>
> **容易踩坑：** 我不会把所有订阅都当必要支出，也不会把漏识别的现金支出视为不存在。跨账户和共同账户还可能重复计算，必须看授权账户覆盖度。
>
> **岗位或项目连接：** 当前项目没有个人财务分类生产数据；我会把可追溯规则、置信度和人工确认机制作为迁移方案，不报虚构准确率。

### Q029：Affordability 和 Credit Risk 有什么区别？

> **口语化回答：** 我会把两者分开理解。Affordability 更关心客户在合理生活和既有承诺之后，是否有能力承担新增还款；Credit Risk 更关心贷款发生违约和损失的风险。它们相关但不是一个分数，我不会因为预测违约率低就自动说产品对客户可负担。
>
> **原理追问：** Affordability 通常需要可持续收入、必要支出、现有债务、还款计划、缓冲和压力情景；风险模型还会考虑违约概率与损失。具体评估标准和证据必须由产品、风控、合规按司法辖区确定。
>
> **容易踩坑：** 我不会把“月均流入大于流出”当完整 affordability，也不会用 LLM 的主观评价替代政策计算。一次性余额和稳定现金流也不能混为一谈。
>
> **岗位或项目连接：** AI 周报的确定性指标框架适合承载 affordability 计算，但当前系统是运维周报，不是信贷决策；面试时必须明确迁移性质。

### Q030：怎么量化现金流波动和抗风险能力？

> **口语化回答：** 我会在多个观察窗口计算收入与净现金流的中位数、分位数、波动、最低余额、透支频率、支付失败和固定支出覆盖率，再做收入下降、利率或支出上升的压力情景。特征不仅给一个均值，还要带观测覆盖度、趋势和缺失标志。
>
> **原理追问：** 均值很容易被一笔大额收入扭曲，中位数和分位数更稳健；但季节性收入需要按业务模式建模。压力参数属于风险政策，不应该由工程师随便拍数字。
>
> **容易踩坑：** 我不会把透支一次直接等同高风险，也不会把账户数据不足视为零波动。异常、季节性和数据断档要分别处理。
>
> **岗位或项目连接：** 现有 AI 周报有趋势与异常统计思路；金融压力情景和阈值必须由风险团队定义并通过历史数据验证。

### Q031：特征平台怎么保证线上线下一致和 point-in-time 正确？

> **口语化回答：** 我会让特征定义代码化并版本化，训练和在线决策尽量复用同一套转换逻辑。每次决策冻结 input snapshot，记录 feature view version、event-time cutoff、数据覆盖度和每个特征的 lineage；离线训练按申请时点做 point-in-time join，不能从后来发生的还款或更新流水里偷信息。
>
> **原理追问：** 线上线下偏差可能来自代码不同、窗口边界不同、晚到数据、默认值不同或时区不同。Feature Store 只是工具，真正保证一致的是统一定义、时点回放、契约测试和监控。
>
> **容易踩坑：** 我不会用今日全量表重建历史训练样本，也不会把缺失默认成 0 而不加 missing indicator。特征回填和定义升级都要生成新版本。
>
> **岗位或项目连接：** CodeWiki 的缓存键和版本化输入、Agent Memory 的来源 ID 可迁移为 snapshot 和 lineage；当前没有信贷 Feature Store 生产证据。

### Q032：PD、LGD、EAD 分别是什么？

> **口语化回答：** 我会这样解释：PD 是在定义时间范围和违约口径下发生违约的概率；LGD 是发生违约后，考虑回收和成本仍损失的比例；EAD 是违约时预计暴露金额。三者的定义、期限、分群和校准必须一致，不能只背缩写。
>
> **原理追问：** PD 是概率预测，LGD 和 EAD 是条件损失与暴露估计，它们可能受到经济周期、产品、额度使用和回收流程影响。监管资本、会计减值和业务定价可能使用不同口径，具体采用哪套要由风险和财务确认。
>
> **容易踩坑：** 我不会把模型分数直接叫 PD，也不会说 LGD 永远在 0 到 1 的简单范围而忽略特殊口径。训练标签、观察窗和默认定义不清，任何指标都没有意义。
>
> **岗位或项目连接：** 这是岗位领域知识，不是我现有项目产出的模型；我会在面试中讲清定义和工程落地，但不声称做过其生产校准。

### Q033：Expected Loss 是不是直接等于 PD × LGD × EAD？

> **口语化回答：** 这个乘积是常见的直观近似，我会用它解释三个风险分量怎么组合，但不会说任何场景都只需相乘。实际还要看期限、条件依赖、折现、宏观情景、生命周期、违约定义和所采用的监管或会计框架，最后口径要由风险与财务团队确认。
>
> **原理追问：** 如果 PD、LGD、EAD 相互依赖，简单使用各自均值相乘可能偏差很大；多期贷款还涉及时间分布和现金流。系统应保存每个组件、版本和情景，不只落一个最终数。
>
> **容易踩坑：** 我不会把 expected loss 当审批的唯一标准，也不会把定价、资本和客户 affordability 混成一个公式。公式看起来确定，不代表输入已经可靠。
>
> **岗位或项目连接：** AI 周报“指标计算可复现”的原则可用于实现公式，但具体风险口径不是现有项目经验，必须由金融专业团队定义。

### Q034：规则、传统模型、机器学习和 LLM 在授信里怎么分工？

> **口语化回答：** 我会把硬性资格、产品边界和合规策略放在可审计规则层；经过验证的统计或机器学习模型输出风险估计；Decision Engine 结合模型、政策、affordability 和人工复核状态给出确定性结果。LLM 更适合非结构化材料整理、低风险分类、分析员助手和受约束的客户说明，不直接生成有约束力的额度或批准结果。
>
> **原理追问：** 分层后每一层有不同的验证方式：规则做边界和变更测试，模型做区分度、校准、稳定性和公平评测，LLM 做 groundedness、提示攻击和输出约束评测。最终决策要能重放到具体版本。
>
> **容易踩坑：** 我不会用“Agent 更智能”作为绕过已有决策控制的理由，也不会让 LLM 生成一个无法映射到正式理由码的拒绝原因。
>
> **岗位或项目连接：** AI 周报已经实践确定性计算与 LLM 表达分离；将这个原则迁移到授信是合理设计，但不能说周报系统等同于 Decision Engine。

### Q035：Reject Inference 是什么？为什么危险？

> **口语化回答：** 我理解的 Reject Inference 是：历史上只有获批客户才会产生完整还款标签，被拒客户的真实违约结果看不到，所以训练样本存在选择偏差。常见推断或加权方法都带强假设，我不会把补出来的标签当真值；我会先分析旧政策的选择机制、覆盖重叠和敏感性，再让模型风险团队决定是否、如何使用。
>
> **原理追问：** 这是 selective labels 和 missing-not-at-random 问题。接受概率建模、重新加权、parceling 等方法只有在假设成立时才可能改善，政策变化还会让历史选择机制失效。
>
> **容易踩坑：** 我不会为了拿标签随意批准高风险申请，也不会用合成拒绝标签后只报 AUC 提升。任何探索策略都要有风险限额、客户保护、合规批准和独立评估。
>
> **岗位或项目连接：** 当前简历没有 Reject Inference 项目，我只会把它作为信贷建模风险回答，不编造实施结果。

### Q036：自动授信 Decision Platform 的核心架构是什么？

> **口语化回答：** 我会把入口、编排和决定分开：Application API 接申请并生成 application_id；Consent/Data Service 拉取并冻结数据；Feature Service 生成版本化特征；Model Service 评分；Policy Engine 执行资格、affordability 和策略；Decision Orchestrator 汇总结果并触发人工复核或通知；Audit Store 保存输入快照、版本、理由和状态事件。
>
> **原理追问：** Orchestrator 用显式状态机管理 `received / data_pending / scored / review_required / decided / notified`，外部调用采用超时、幂等和补偿。决策记录应不可变，新决定通过 supersede 关联，不能原地改历史。
>
> **容易踩坑：** 我不会把所有逻辑写进一个同步接口，也不会因为模型超时就默认批准或拒绝。降级策略属于产品和风险政策，必须事先审批。
>
> **岗位或项目连接：** Agent Memory 的 pipeline-manager 和京东面试中的可审计路由设计可迁移为编排思路；这是下一版金融架构，不是当前已投产系统。

### Q037：授信接口怎么做幂等？

> **口语化回答：** 我会让调用方传稳定的 idempotency key，并把它绑定到租户、业务动作和规范化请求哈希。首次请求占位后执行，重复且请求一致就返回同一结果；同一个 key 但 payload 不同直接报冲突。模型评分、规则执行、发通知和写审计各自也要有业务唯一键，不能只在 API 入口去重。
>
> **原理追问：** 分布式系统很难靠网络获得严格 exactly-once，我会按 at-least-once delivery 加幂等副作用设计。状态写入和 Outbox 事件要在同一事务边界，消费者按 event_id 去重。
>
> **容易踩坑：** 我不会只用 application_id 去重所有阶段，也不会在请求超时后让客户端创建新申请。幂等记录过早过期、失败状态不可恢复、重试重复发送通知都要测试。
>
> **岗位或项目连接：** AI 周报已有任务补跑和事务保障思路；授信幂等需要更细的状态与副作用边界，不能直接宣称现有实现满足金融要求。

### Q038：银行回调、异步拉数和重复事件怎么处理？

> **口语化回答：** 我会先校验回调来源、签名、时间窗和事件 ID，再把原始事件不可变落库并快速 ACK，后续由 Worker 异步处理。消费者按 Provider、consent_id 和 event_id 幂等；乱序事件通过状态版本或序列号判断，定时 reconciliation 主动对账，不能完全相信回调一定到达。
>
> **原理追问：** Webhook 通常是至少一次、可能重复和乱序的通知，不是事实库本身。事件驱动能降低同步等待，但最终一致性需要 Outbox/Inbox、重试、死信和对账任务共同保证。
>
> **容易踩坑：** 我不会在回调线程里完成整条授信、也不会只按时间戳丢弃旧事件。签名验证前解析业务、无限重试坏消息和死信无人处理都是风险。
>
> **岗位或项目连接：** AI 周报的补跑机制和后端事件处理经验能迁移；当前材料没有银行 Webhook 生产事实，因此只按设计回答。

### Q039：为什么决策必须版本化？怎么做到可重放？

> **口语化回答：** 同一个申请未来可能因为数据修订、模型升级或政策调整得到不同结果，所以我会冻结原始数据快照、标准化版本、特征版本、模型 artifact、阈值、规则包、配置和代码版本。重放时在隔离环境加载这些版本，先复现历史结果，再比较新版本的 counterfactual；历史决定本身不改写。
>
> **原理追问：** 可重放不只是保存模型名，还要保存输入转换、外部依赖返回和随机性。对于无法永久保存的受限数据，要至少保留合规允许的哈希、摘要和访问引用，并和法务确认留存策略。
>
> **容易踩坑：** 我不会只有 Git commit 没有数据快照，也不会让动态配置和特征字典在回放时读取“当前最新”。模型可加载不等于决策可复现。
>
> **岗位或项目连接：** CodeWiki 的 prompt/input 缓存和 Agent Memory 的来源追溯提供基础思路；金融决策还需模型注册表、政策版本和不可变审计，这是新增能力。

### Q040：数据缺失、银行接口失败或模型不可用时怎么降级？

> **口语化回答：** 我不会默认批准，也不会用一个便宜模型随便顶上。先区分临时技术失败、客户未授权、数据窗口不足和真实缺失，再按已审批策略选择重试、延后决定、请求补充材料、走人工复核或明确无法判断。任何 fallback 都记录原因、使用的数据和对客户结果的影响。
>
> **原理追问：** Missingness 本身可能带信息，但把技术故障当风险特征会伤害客户。降级策略要保证模型输入分布仍在验证范围内；换模型或少用一类数据通常构成新的决策路径，需要独立验证。
>
> **容易踩坑：** 我不会把 `null` 默认为 0，也不会把 Provider 故障写成“客户风险高”。静默 fallback 会让理由码和审计对不上。
>
> **岗位或项目连接：** 京东面试里的模型 failover 设计可迁移可用性机制，但在授信场景切换必须服从风险策略，不能把普通 LLM fallback 原样照搬。

## 三、公平合规与模型风险：指标、理由、PII 与审计

### Q041：信贷模型的“公平”到底是什么？

> **口语化回答：** 我不会把公平说成一个万能分数。技术上可以比较不同群体的批准率、真正例率、假正例率、校准和误差分布，但选哪个指标、按什么群体和阈值判断，必须结合产品、伤害类型、数据可用性和目标司法辖区要求。我的责任是把指标、样本不确定性和 trade-off 透明呈现，法律结论由法务与合规确认。
>
> **原理追问：** 不同公平定义经常无法同时满足，尤其当群体基础率不同。公平评估还需要交叉群体、时间维度和拒绝样本偏差，不能只看总体平均。
>
> **容易踩坑：** 我不会说“去掉敏感字段模型就公平”，也不会看到指标接近就宣布合规。样本量小、标签偏差和阈值选择都可能掩盖问题。
>
> **岗位或项目连接：** 当前三个项目没有信贷公平性生产评估，所以我只按治理方案回答，不虚构群体数据或合规结论。

### Q042：Demographic Parity、Equal Opportunity、Equalized Odds 有什么区别？

> **口语化回答：** 我会这样讲：Demographic Parity 看不同群体获得正向结果的比例是否接近；Equal Opportunity 主要看真实正类中的通过率是否接近；Equalized Odds 同时关注真正例率和假正例率。它们回答的伤害问题不同，我不会脱离标签含义和业务后果机械选一个。
>
> **原理追问：** 在信贷里“正类”到底定义为会按时还款还是获批，要先说清；标签本身也只在历史获批样本上可见。群体基础率不同时，校准和某些错误率公平指标可能互相冲突。
>
> **容易踩坑：** 我不会只报比例不报分母、置信区间和阈值，也不会把相关性差异直接解释成歧视原因。任何法定测试方法要由合规确认。
>
> **岗位或项目连接：** 这属于拟进入岗位的模型评测能力，与现有 AI 项目没有直接生产结果；可以迁移的是评测分层和可观察性方法。

### Q043：为什么还要检查不同群体的 Calibration？

> **口语化回答：** 如果模型给两个群体都打 10% PD，我希望在各自可比样本里实际违约率也接近 10%，这就是我关注 calibration 的原因。区分度高但校准差，会让定价、额度或阈值失真；我会按群体、分数区间和时间窗口画 reliability curve，并给出样本不确定性。
>
> **原理追问：** AUC 衡量排序，不保证概率准确；整体校准也可能掩盖子群偏差。校准方法本身要在独立验证集上拟合并版本化，不能在测试集上调到最好。
>
> **容易踩坑：** 我不会用小群体的几个样本下结论，也不会为了让一项公平指标好看而破坏全局风险校准却不说明 trade-off。
>
> **岗位或项目连接：** 当前简历里的记忆准确率不能类比信贷校准；这是全新评测体系，必须用真实标签和独立验证建立。

### Q044：不使用敏感属性，为什么模型仍可能不公平？什么是 Proxy？

> **口语化回答：** 因为邮编、消费地点、教育、设备或收入模式等非敏感字段，可能和受保护属性高度相关，模型会通过它们间接重建群体差异。我会做业务审查、相关与互信息分析、特征贡献分布、可预测性测试和反事实敏感性分析，但不会仅凭一个统计量就断言某字段一定是非法 Proxy。
>
> **原理追问：** Proxy 风险既来自单个字段，也可能来自多个弱信号组合。删除明显字段后，模型可能从剩余变量恢复同样信息，所以要评估完整 pipeline 和决策影响。
>
> **容易踩坑：** 我不会擅自推断或补全客户的敏感属性，也不会把所有相关变量一刀切删除。敏感数据能否为公平监测而收集、如何隔离，必须先由法务合规确认。
>
> **岗位或项目连接：** CodeWiki 的图关系分析只能提供技术思路，不能当成公平性证明；金融 Proxy 审查需要专门数据权限和治理流程。

### Q045：信贷特征怎么做准入和治理？

> **口语化回答：** 我会为每个特征建 Feature Card，说明业务含义、来源授权、计算公式、窗口、缺失策略、稳定性、潜在 Proxy 风险、允许用途和 owner。上线前经过数据、风险、合规和模型验证门禁；修改定义就产生新版本，不能在原名字下静默变化。
>
> **原理追问：** 特征治理连接数据合同、训练 lineage、在线服务和理由码。一个统计效果很强的特征，如果来源不可解释、容易操纵或与产品目的无关，也不一定应该使用。
>
> **容易踩坑：** 我不会因为 SHAP 排名高就批准特征，也不会使用事后结果、未经授权数据或含泄漏的聚合字段。删除特征后还要检查其衍生字段和缓存。
>
> **岗位或项目连接：** Agent Memory 的元数据和来源可追溯可迁移成 Feature Card 基础，但特征审批流程是金融岗位新增要求。

### Q046：Reason Code 和 Adverse Action 是什么关系？

> **口语化回答：** 我把 Reason Code 设计成决策链内部的稳定、具体原因标识，例如“验证后的可支配现金流不足以覆盖拟议还款”，再由受控模板映射成客户可理解的通知内容。是否构成 Adverse Action、要给哪些原因、时限和格式是什么，取决于司法辖区和产品，我不会现场下法律结论；我会确保系统能保存实际起决定作用的原因并交由法务合规确认通知。
>
> **原理追问：** 理由不能在决定后让 LLM猜，而应由规则和模型决策过程同步产生。模型因素、政策规则和数据缺失都要映射到版本化 reason taxonomy，并能重放。
>
> **容易踩坑：** 我不会用“内部政策”“模型评分不足”这种空泛文本，也不会为了文案好听而给出与真实决定不一致的原因。
>
> **岗位或项目连接：** CodeWiki 的证据引用与 AI 周报的模板化表达可迁移，但当前项目没有消费者信贷通知经验；这里严格按技术控制回答。

### Q047：直接把 SHAP Top 3 当拒绝理由可以吗？

> **口语化回答：** 我不会直接这么做。SHAP 解释的是模型输出相对某个背景分布的局部贡献，不一定等于政策上实际触发拒绝的原因，也可能受相关特征、基线和变换影响。我会先确定最终决定路径，再把经过验证、稳定且可操作的模型因素映射到 reason code，并用反事实和回放测试确认原因忠实。
>
> **原理追问：** 同一申请可能先被硬规则拒绝，模型贡献就不该成为主因；高度相关特征会分摊或互换贡献。解释算法是证据之一，不是法律充分性的自动证明。
>
> **容易踩坑：** 我不会让 LLM把 SHAP 值润色成不存在的业务原因，也不会因为特征贡献为负就说客户行为“导致”拒绝。具体通知要求仍需法务确认。
>
> **岗位或项目连接：** 现有三个项目没有 SHAP 或授信理由码生产链路；可迁移的是引用真实中间结果而不是让模型事后编理由。

### Q048：复杂模型能不能用于信贷？“黑盒”是不是一定不能用？

> **口语化回答：** 我不会简单回答能或不能。复杂模型要看它是否带来稳定、可验证的增益，以及能否满足数据治理、独立验证、原因说明、监控和回滚要求。如果一个模型只提升很小，却让原因不稳定、边界难测试，我会倾向更简单方案；最终可否用于某产品由模型风险、合规和业务共同批准。
>
> **原理追问：** 可解释性不只有模型结构，还包括全局行为、局部原因、输入 lineage、场景测试和决策回放。复杂度越高，验证样本、压力测试和变更治理成本越大。
>
> **容易踩坑：** 我不会说“用了 SHAP 就可解释”，也不会为了可解释性牺牲明显的风险控制却不量化。模型供应商声称合规也不能替代机构自己的验证。
>
> **岗位或项目连接：** CodeWiki 的模型路由强调按任务和证据选择，而不是追求最大模型；这个取舍思路可迁移，信贷准入仍是新治理流程。

### Q049：什么是 Model Risk？模型清单和分级怎么做？

> **口语化回答：** 我把 Model Risk 理解为模型本身有错误、被错误使用，或者在环境变化后仍被信任而造成损失和客户伤害。首先我会建立统一 Inventory，记录用途、owner、输入、输出、依赖、用户、限制、验证状态和下游决定；再按影响、自动化程度、暴露规模、复杂度和可替代性分级，决定验证与审批强度。
>
> **原理追问：** 不只统计模型算模型，规则、评分卡、第三方模型、LLM 和关键后处理也可能进入模型风险范围，具体边界由公司的模型风险政策定义。一个低风险组件进入高影响决策链后，整体风险可能上升。
>
> **容易踩坑：** 我不会只登记主模型而漏掉 embedding、分类器、阈值和人工 override，也不会让“实验”模型长期在线绕过 Inventory。
>
> **岗位或项目连接：** 当前项目有模型调用和路由，但没有证据证明已按银行 Model Risk Framework 管理；面试时我会明确这是拟建立的治理能力。

### Q050：独立模型验证要验证什么？

> **口语化回答：** 我会让独立于开发的一方检查概念是否合理、数据和标签是否可信、实现是否与文档一致、性能与校准是否稳定、限制条件是否明确，以及公平、压力、敏感性和变更测试是否充分。验证不是复跑开发者的 notebook，而是能挑战假设、复现结果并提出限制或拒绝上线。
>
> **原理追问：** 有效验证通常覆盖 conceptual soundness、ongoing monitoring 和 outcomes analysis；第三方模型即使拿不到全部源码，也要通过文档、基准、黑盒测试、使用限制和供应商风险控制建立足够证据。
>
> **容易踩坑：** 我不会把代码 Review 当独立验证，也不会让同一人开发、挑测试集、审批和签字。验证结论要有 issue、责任人、截止时间和风险接受记录。
>
> **岗位或项目连接：** 事实清单尚未证明现有项目的独立验证流程，因此我不会反推已有银行级治理；这是岗位落地方法。

### Q051：Data Drift、Concept Drift、Policy Drift 有什么区别？

> **口语化回答：** Data Drift 是输入分布变了，比如收入或交易模式变化；Concept Drift 是相同特征与违约结果的关系变了；Policy Drift 是审批阈值、营销渠道或人工策略改变，导致观察到的人群和标签变化。我会分别监控，不能看到 PSI 上升就笼统说模型坏了。
>
> **原理追问：** 特征分布可以较快看到，但标签往往延迟数月；因此要结合输入稳定性、分数分布、批准率、早期行为和成熟 cohort 表现。政策变更要作为事件进入监控解释。
>
> **容易踩坑：** 我不会把所有漂移都触发自动重训，也不会在没有成熟标签时用短期代理指标宣布风险下降。重训本身是模型变更，需要重新验证。
>
> **岗位或项目连接：** Agent Memory 有指标上报思路，CodeWiki 有版本化调用记录；金融漂移监控需要新增 cohort、标签成熟度和政策事件体系。

### Q052：线上要监控哪些信贷模型指标？

> **口语化回答：** 我会分四层：数据层看缺失、延迟、覆盖和 Schema；模型层看分数分布、区分度、校准和稳定性；决策层看批准、拒绝、人工复核、理由码和 override；结果层看成熟 cohort 的还款、违约、损失与群体差异。所有指标按模型、策略、渠道、时间和关键群体切片，并设置有 owner 的响应流程。
>
> **原理追问：** AUC 不会告诉我概率是否可用于定价，整体坏账率也可能被政策和客群结构影响。需要基准、阈值、置信区间、数据延迟和根因 drill-down。
>
> **容易踩坑：** 我不会堆一块 Dashboard 就叫治理，也不会对小样本群体设置噪声很大的硬报警。监控必须能关联到冻结版本和具体申请。
>
> **岗位或项目连接：** 当前简历只提“指标上报和性能计时”，不能证明有信贷 outcome monitoring；这里是面向岗位的扩展设计。

### Q053：Champion/Challenger 怎么上线才安全？

> **口语化回答：** 我会先让 Challenger 做离线回放和 shadow scoring，只记录如果使用它会怎样，不影响客户结果。通过独立验证后，再按审批方案做小流量或受控试验，设置客群边界、风险限额、停止条件和回滚；比较时使用同一输入快照，并区分模型差异与政策差异。
>
> **原理追问：** Shadow 能比较分数和决策差异，但拿不到 Challenger 真正改变客群后的长期反事实结果。任何线上试验都要考虑标签延迟、选择偏差和客户公平，而不是普通推荐系统 A/B 测试。
>
> **容易踩坑：** 我不会自动把短期批准率更高的模型升为 Champion，也不会让两个版本使用不同清洗逻辑后直接比较。回滚还要恢复规则、特征和通知模板的兼容版本。
>
> **岗位或项目连接：** CodeWiki 的模型路由与 fallback 提供运行时基础，但信贷 Challenger 需要风险审批和长期 outcome，不是现有路由功能的直接等价物。

### Q054：人工复核和 Override 怎么设计？

> **口语化回答：** 我会明确哪些情况必须进入人工复核，比如数据冲突、模型超出适用域、高影响边界案例或客户申诉。复核页面展示原始证据、特征计算、模型和规则版本、理由建议与不确定性；Reviewer 的 override 必须选结构化原因、写备注并保留原决定，不能直接改数据库结果。
>
> **原理追问：** Human-in-the-loop 不等于把风险甩给人。要监控 Reviewer 一致性、处理时长、override 率、群体差异和后续 outcome，并避免自动化偏见让人只点确认。
>
> **容易踩坑：** 我不会只给人工看模型结论不看证据，也不会允许无理由 override。人工队列过载时不能静默自动放行或拒绝。
>
> **岗位或项目连接：** CodeWiki 的证据展示和 Agent 工作流状态可迁移为 Reviewer UI 基础；现有项目没有信贷审批人员和 override 数据，不能夸大。

### Q055：PII 在采集、训练、推理和日志里怎么保护？

> **口语化回答：** 我会先做数据最小化和字段分级，再按环境与职责隔离。传输和静态数据加密，Token、账户标识和身份信息做 vault 化或 tokenization；训练集使用受控快照，开发人员默认只见脱敏或合成数据；模型请求、Trace 和日志在写入前做字段级过滤，访问都有审计和到期回收。
>
> **原理追问：** 去掉姓名不代表匿名，交易序列很容易重新识别。密钥、映射表和业务数据要分离，备份、缓存、embedding、导出和第三方模型 Provider 也必须纳入数据流图。
>
> **容易踩坑：** 我不会在 Prompt、异常堆栈或 APM 中打印完整流水，也不会把 hash 当匿名化万能方案。是否允许把哪些数据发给哪家模型，要按合同、地域和合规批准。
>
> **岗位或项目连接：** 当前内部项目有日志和模型调用，但材料不足以证明金融级 PII 控制；题库把它定义为必须新增的架构门禁。

### Q056：数据最小化、保留、删除和 Consent 撤回怎么落地？

> **口语化回答：** 我会建立数据目录和 purpose binding：每类原始数据、特征、模型样本、日志和审计记录都说明用途、保留期、合法依据或合同要求、删除方式和例外审批。撤回 Consent 后先停止新访问，再由策略引擎生成删除或限制处理任务，沿 lineage 找到派生资产；依法或因审计需要保留的部分隔离并限制用途，具体范围由法务确认。
>
> **原理追问：** 删除不是一条 SQL，数据可能存在对象存储、特征库、缓存、搜索索引、备份和训练快照。需要 tombstone、异步任务、完成证明和备份自然过期策略。
>
> **容易踩坑：** 我不会承诺“立即从所有备份物理抹除”而没有架构证据，也不会把模型参数中的影响简单等同可定位个人记录。是否需要重训或做机器遗忘要按风险评估。
>
> **岗位或项目连接：** Agent Memory 有日期分片清理能力，但不能证明具备金融全链路删除传播；这里会把 source-to-derived lineage 补齐。

### Q057：金融决策审计日志应该记录什么？

> **口语化回答：** 我会记录谁在什么时间、基于哪次 Consent 和输入快照、调用了哪个特征/模型/规则版本、得到哪些中间结果、触发什么理由、是否人工 override、最终通知是什么。日志采用 append-only 事件，敏感值最小化或引用化，带 trace_id、event_id、前后状态和完整性校验；查询审计本身也要审计。
>
> **原理追问：** 业务数据库保存当前状态，审计日志保存如何到达当前状态，两者用途不同。不可篡改不必夸成“绝对不能改”，可以通过 WORM、权限隔离、哈希链、签名和定期校验提高篡改可发现性。
>
> **容易踩坑：** 我不会把完整 PII 复制到日志，也不会只记最终 approved/declined。日志若没有统一时钟、版本和 actor 身份，事后仍无法重放。
>
> **岗位或项目连接：** 京东模型路由题里的决策审计和 Agent Memory 的来源引用可迁移；金融审计的留存、访问和完整性要求需由公司政策与法务确认。

### Q058：纯自动化决策和人工介入有什么监管风险？

> **口语化回答：** 我不会泛化说任何地区都禁止或允许纯自动决策。我的技术方案会把自动化程度、决定影响和人工介入点配置化，支持客户获得说明、提出异议、补充信息和进入真正有权限改变结果的人工复核。哪些场景必须提供这些权利，最终按目标地区的法律与产品类型确认。
>
> **原理追问：** “有人看过 Dashboard”不等于有意义的人工介入；Reviewer 需要理解证据、有时间判断、能推翻结果，并留下独立理由。系统还要防止人工只机械确认模型。
>
> **容易踩坑：** 我不会用客服转人工冒充决策复核，也不会让 LLM 模拟人工审批。跨国扩张时更不能拿一个地区的流程套所有市场。
>
> **岗位或项目连接：** 现有 Agent 工作流可表达暂停和审批节点，但没有金融消费者权利流程；这里是迁移设计，必须联合法务和运营落地。

### Q059：发现模型事故或群体伤害信号，怎么响应？

> **口语化回答：** 我会先按预案止损：冻结版本或切到已批准的保守路径，停止自动决定并转人工，而不是现场换个模型。随后固定受影响时间窗、申请、版本和数据，保护证据，通知风险、合规、安全和业务负责人；完成根因、影响评估、客户补救和变更验证后才恢复。
>
> **原理追问：** 事故可能来自数据映射、特征缺失、模型漂移、阈值配置或通知错误，所以回滚单位不只模型 artifact。恢复标准和风险接受人必须事先定义。
>
> **容易踩坑：** 我不会先删日志或重跑覆盖历史，也不会未经批准给客户发模型猜测的解释。是否需要监管或客户通知由法务合规决定。
>
> **岗位或项目连接：** 当前项目有重试和模型 fallback 思路，但没有已证实的信贷事故经验；我只讲可执行 Runbook，不编造真实事故故事。

### Q060：一个模型上线审批包应该包含什么？

> **口语化回答：** 我会准备业务用途和禁用场景、数据与标签说明、特征卡、模型方法、性能与校准、公平与敏感性测试、压力与边界测试、解释和理由码验证、依赖与供应商风险、监控阈值、回滚方案、独立验证意见和未关闭风险。最后由有权限的风险、合规和业务角色签批，工程师不能自己证明自己合规。
>
> **原理追问：** Model Card 是摘要，不等于完整审批证据；数据、代码、配置、artifact、测试报告和决策记录要互相可追溯。重大变更还要定义何时必须重新验证。
>
> **容易踩坑：** 我不会只交一份漂亮 PPT，也不会漏掉局限性和失败样本。第三方模型更新版本时，同样要触发影响分析，不能默认兼容。
>
> **岗位或项目连接：** 事实清单显示现有项目的 RACI、投产和测试证据仍待补齐；这份审批包结构也提醒我先把自己的项目证据补实，再谈金融级治理。

## 四、金融 Agent 安全与系统设计

### Q061：为什么不能让 LLM 直接做授信或投资决定？

> **口语化回答：** 因为 LLM 的自然语言输出有随机性、会受提示和上下文影响，也很难单独承担稳定校准、理由一致和决策重放。我会让它做查询规划、材料整理、证据归纳和受约束说明；真正有约束力的风险分数、政策判断、额度或交易动作，必须经过版本化的确定性服务、审批策略和必要的人工确认。
>
> **原理追问：** 工具调用或结构化输出只能约束格式，不能证明决策正确。金融决定还需要输入时点、模型适用域、规则版本、授权、解释、审计和申诉路径，不能由一次生成覆盖。
>
> **容易踩坑：** 我不会把 temperature 设为 0 就称为确定性，也不会让 LLM 生成理由后反过来驱动决定。模型升级也不能绕过变更审批。
>
> **岗位或项目连接：** AI 周报已经把确定性数字与 LLM 叙述分开；金融场景会把这条边界做得更严格，但现有周报不等于授信或投顾系统。

### Q062：金融 Agent 的 Threat Model 怎么做？

> **口语化回答：** 我会先列资产、信任边界和攻击者。资产包括客户 PII、账户流水、研究数据、模型与策略、API 凭证和决策记录；边界包括用户输入、外部网页或财报、模型 Provider、MCP/工具、内部数据源和人工审批。然后按泄密、越权、篡改、欺骗、拒绝服务和供应链风险逐条映射控制与监控。
>
> **原理追问：** Agent 风险不是只防 Prompt Injection，因为模型同时连接了数据和动作。最危险的是不可信内容改变控制流，再借高权限工具产生真实副作用，所以要把数据平面与控制平面分离。
>
> **容易踩坑：** 我不会只做一份静态 STRIDE 表就结束，也不会把“内部用户”当天然可信。每次新增工具、数据源或模型都要更新威胁模型。
>
> **岗位或项目连接：** CodeWiki 读取仓库、Memory 读取历史工具结果，都有不可信内容边界；金融迁移会额外引入 PII、决策和资金相关资产，风险级别更高。

### Q063：财报或网页里藏了 Prompt Injection，Agent 怎么防？

> **口语化回答：** 我会把外部文件明确标成数据，不让其中的“忽略之前指令、调用某工具”进入系统控制层。解析后只提取允许的字段和证据片段，Prompt 中使用清晰的数据边界；工具权限由独立 Policy Engine 判断，不由文档内容授予。高风险动作还需要参数校验和人工批准。
>
> **原理追问：** Indirect Prompt Injection 利用模型同时解释指令和数据的弱点，单靠一句“不要听文档”并不可靠。更有效的是能力隔离、最小权限、允许列表、污点传播和输出到动作之间的确定性闸门。
>
> **容易踩坑：** 我不会指望一次模型分类器识别所有攻击，也不会把网页全文连同隐藏文本直接送入有写权限的 Agent。编码、图片和多语言内容也可能携带注入。
>
> **岗位或项目连接：** CodeWiki 的源码和 README 都应视为不可信数据；当前材料没有证明已完成完整 Prompt Injection 防御，因此这是需要补强的金融安全设计。

### Q064：金融 Agent 的工具权限怎么设计？

> **口语化回答：** 我会按任务、租户和用户签发短时能力令牌，只允许调用指定工具和资源范围。读 SEC、读客户账户、跑模型、写备注、发通知和提交决定是不同权限；工具参数在服务端重新校验，Agent 不能靠自己生成一个 tenant_id 或 account_id 就越权。涉及副作用的工具默认需要更高门槛和审批。
>
> **原理追问：** 最小权限要同时限制“能调用什么”和“能访问哪条数据”，还要限制次数、金额、时间和环境。Capability 可以绑定 trace、purpose 和 expiration，调用后写不可变审计。
>
> **容易踩坑：** 我不会给 Agent 一个万能数据库账号，也不会只在 Prompt 里写“不要越权”。工具描述和参数 Schema 不是授权系统。
>
> **岗位或项目连接：** CodeWiki 集中部署还缺完整 Repo ACL 证据；金融场景必须先补服务端 ABAC/RBAC 和短时凭证，不能沿用本地工具的信任假设。

### Q065：允许 Agent 执行 SQL 或 Python，怎么做沙箱？

> **口语化回答：** 我会优先提供高层只读工具，不直接开放任意 SQL 或 Shell。确实需要计算时，把任务放到无网络或受限网络的临时沙箱，使用只读数据快照、最小文件系统、CPU/内存/时间限制、固定依赖和输出大小上限；SQL 走只读副本、语法解析和表列白名单，并由服务端强制租户条件。
>
> **原理追问：** 容器不是天然安全边界，还需要内核隔离、seccomp、非 root、只读挂载、Secret 零注入和任务后销毁。对查询要同时控制扫描量、行数和执行时间，防止数据外泄与资源耗尽。
>
> **容易踩坑：** 我不会只靠正则过滤 `DROP`，也不会让 Agent 自己拼接 ACL 条件。只读 SQL 仍可以批量导出 PII或做时间侧信道。
>
> **岗位或项目连接：** 现有项目没有证据证明金融级代码沙箱；CodeWiki 的查询工具可以作为高层 API 示例，但不能包装成完整隔离方案。

### Q066：两个单独安全的工具为什么组合后会泄密？

> **口语化回答：** 比如“读取客户流水”和“发送邮件”单独都有合理用途，但 Agent 把前者结果传给后者，就形成数据外泄路径。我会对工具输出打数据分类和租户标签，对输入声明允许接收的数据等级，再由 Policy Engine 检查 source-to-sink 流；敏感数据只能流向批准的内部目的，高风险组合需要人工授权。
>
> **原理追问：** 这是组合权限和信息流控制问题。单次 ACL 只能判断某个动作是否允许，无法判断一串动作是否把数据带到不允许的目的地，所以要保留污点标签和调用图。
>
> **容易踩坑：** 我不会认为每个工具都通过安全评审就代表任意组合安全，也不会让摘要自动降级数据敏感性。模型改写后的内容仍可能包含可识别信息。
>
> **岗位或项目连接：** Agent Memory 的工具结果引用可以承载 lineage；下一步需要把 sensitivity 和 allowed sinks 加入引用元数据，当前实现不能说已经具备。

### Q067：Prompt、Trace 和模型日志怎样避免泄露金融数据？

> **口语化回答：** 我会在调用模型前做字段级最小化和 tokenization，只发送完成任务必需的数据；Trace 默认记录 ID、类型、耗时、Token 和哈希，而不是完整流水。需要保留内容做调试时进入受控采样库，设置用途、访问审批、保留期和导出审计；第三方 Provider 是否留存或训练必须按合同与配置确认。
>
> **原理追问：** 可观测性与隐私是 trade-off，不是“全不记”或“全量记”。可以把敏感 payload 存在权限更严的证据库，普通 Trace 只保存 reference，并用 break-glass 流程访问。
>
> **容易踩坑：** 我不会在错误日志里直接 dump 请求，也不会假设关闭 Provider training 就解决地域、分包商和保留问题。Prompt Cache 同样可能跨请求泄露，缓存键要含租户和权限上下文。
>
> **岗位或项目连接：** Agent Memory 的 Offload 正适合“Trace 留引用、原文进受控存储”的模式；但现有存储是否达到金融 PII 要求尚未核实，不能直接宣称合规。

### Q068：怎么防 Memory Poisoning 和跨客户记忆串用？

> **口语化回答：** 我会把记忆按 tenant、user、purpose 和授权范围强隔离，存储主键、查询过滤和加密上下文都带租户。写入前校验来源和可信等级，把用户陈述、外部文档、系统事实和人工确认分层；高影响事实不能仅凭一轮对话写成长期真相，冲突时保留证据并要求确认。
>
> **原理追问：** Memory Poisoning 是攻击者把恶意或错误内容变成后续高权重上下文。除了 ACL，还要有 provenance、TTL、置信或状态、写入策略和召回时的 purpose filter。
>
> **容易踩坑：** 我不会只在查询层加 tenant filter，却让向量索引或缓存跨租户共享未隔离结果；也不会把模型摘要当比原始证据更可信。
>
> **岗位或项目连接：** Agent Memory 当前有 L0-L3、来源 ID 和冲突动作，但完整属性级置信状态和金融租户隔离尚未被材料证明；题库明确把它列为下一版要求。

### Q069：金融 RAG 怎么做行级权限和删除传播？

> **口语化回答：** 我会让每个文档、Chunk、Fact 和 embedding 都继承 owner、tenant、purpose、许可和有效期。检索时先用服务端授权上下文做候选过滤，再排序和图扩展；不能先召回后让模型“别看”。源数据权限变化或删除时，通过 lineage manifest 找到索引、缓存、摘要和评测副本，执行失效或删除并留下完成记录。
>
> **原理追问：** ACL 必须贯穿 ingestion、index、retrieval、generation 和 cache。向量数据库如果不支持可靠过滤，可以按租户物理隔离或在可信服务层做候选交集，但要验证不会侧漏。
>
> **容易踩坑：** 我不会把 tenant_id 只写在 metadata 却允许客户端覆盖，也不会忽略图扩展从授权节点跳到未授权邻居。缓存命中也必须重新验证权限。
>
> **岗位或项目连接：** CodeWiki 的 Allowed Source Ref 是引用范围控制，不等于完整 Repo ACL；金融版本必须增加入口权限与派生资产删除，明确现状边界。

### Q070：如何让金融 Agent 的回答真正 Grounded？

> **口语化回答：** 我会先让 Agent 生成结构化 claim，再为每个 claim 绑定可访问的 evidence span 或 typed fact。生成后做引用存在、时点、单位、数值复算和基本支持关系检查；来源冲突时展示冲突，不让模型投票。没有足够证据就明确拒答或请求补充，不靠语言自信填空。
>
> **原理追问：** Groundedness 包括来源正确、引用支持、时点正确和推导合法四层。检索召回率高不等于最终 claim 被支持，LLM judge 也要防候选答案中的提示注入和偏好偏差。
>
> **容易踩坑：** 我不会把“带了三个链接”当 grounded，也不会让模型引用自己上一轮生成的摘要作为唯一证据。派生指标必须能追到原始 fact。
>
> **岗位或项目连接：** CodeWiki 已有 Citation 白名单但缺严格 claim entailment；金融迁移会增加 claim-evidence verifier 和数值验证，当前不能说已完成。

### Q071：Policy Engine 为什么要独立于 Agent？

> **口语化回答：** 我会把 Policy Engine 独立出来，因为授权、额度、数据用途、模型准入和人工审批条件必须稳定、可测试、可审计，不能随着 Prompt 改写。Agent 只提出 action proposal，Policy Engine 根据身份、状态、风险、数据标签和版本化规则返回 allow、deny 或 require_approval；真正的工具服务还会再次校验，不能只信 Agent 或上游结果。
>
> **原理追问：** 这是把非确定性的规划层和确定性的执行控制层分开。Policy decision 也要保存规则版本、输入属性和原因，支持 dry-run 与回放。
>
> **容易踩坑：** 我不会只在 Agent System Prompt 写公司政策，也不会让 Agent 自己判断是否需要审批。Policy Engine 不是业务风险模型，两者职责仍要区分。
>
> **岗位或项目连接：** 京东模型路由题里的候选过滤和审计可迁移为策略执行框架；当前三个项目没有统一金融 Policy Engine 证据。

### Q072：金融 Agent 工作流为什么要用显式状态机？

> **口语化回答：** 我会把“收集数据、验证授权、生成特征、评分、策略判断、待复核、已决定、已通知”写成有限状态和允许转移，而不是让模型用自然语言决定下一步。每次转移带 event_id、前置条件、版本和副作用状态；中断后从持久化 checkpoint 恢复，重复执行仍保持幂等。
>
> **原理追问：** 显式状态机能约束不允许的跳转，把长任务的控制权放回系统。LLM 只在某些节点生成建议，下一节点由代码和策略决定；Saga/补偿用于跨服务副作用，但不能假装能撤销所有外部事实。
>
> **容易踩坑：** 我不会把 LangGraph 节点图本身当合规保证，也不会只保存最后一个节点名。工具结果、审批人和副作用提交状态都要可恢复。
>
> **岗位或项目连接：** Agent Memory 的调度器和 Mermaid 任务画布可以帮助展示状态，但不是金融 Decision State Machine；这里是对现有编排经验的强化。

### Q073：金融场景怎样做模型路由和 Failover？

> **口语化回答：** 我会先按任务风险分级。低风险摘要可在通过评测的模型池里按成本和延迟路由；涉及客户决定、理由或 PII 的任务只允许批准清单中的特定模型与区域。故障时只有语义和控制等价、已经验证的备用路径才能自动切换，否则转人工或延迟处理，并记录切换原因和输出差异。
>
> **原理追问：** 模型可用不代表可互换，不同 tokenizer、上下文、工具调用和安全策略会改变行为。路由决策要基于静态元数据与实时健康，但不能让未经审批的新模型因为“效果好”自动进入高风险链路。
>
> **容易踩坑：** 我不会把 500ms failover 理解成 500ms 内生成完整答案，也不会在授信模型不可用时切到通用 LLM。静默降级会破坏理由与审计。
>
> **岗位或项目连接：** 京东面试已经深挖 100ms 路由、500ms 切换和审计；这里补上金融风险分级，仍然是架构设计，不冒充已跑出 SLA。

### Q074：怎么防 Agent 无限循环、成本失控和 Provider 雪崩？

> **口语化回答：** 我会给一次 Run 设置总 deadline、最大步骤、Token、费用、工具次数和每类资源预算，并在每个子任务扣减同一个全局 budget。Provider 侧有并发隔离、限流、熔断和带 jitter 的退避；达到预算就输出已有证据、缺口和可恢复 checkpoint，而不是继续自我反思。
>
> **原理追问：** 多 Agent 如果各自只管局部预算，总扇出会指数增长。重试要受端到端 deadline 和幂等约束，熔断按 Provider/模型/租户隔离，避免一个故障拖垮全部路径。
>
> **容易踩坑：** 我不会每层都重试三次，也不会只限制 Token 不限制工具扫描和数据库成本。预算耗尽不能自动绕过审批或降低安全检查。
>
> **岗位或项目连接：** Agent Memory 的前台超时和 CodeWiki 的模型调用记录可作为基础；完整全局预算和金融级熔断需要新增实现与压测。

### Q075：金融 Agent 的 Human-in-the-loop 应该放在哪些点？

> **口语化回答：** 我会按风险放点：数据授权异常、证据冲突、超出模型适用域、高影响决定、外部通知、资金或账户动作、客户申诉都可触发人工。审批人看到的是 action diff、来源、模型/规则版本、风险提示和回滚能力，而不是一句“AI 建议通过”；批准 Token 绑定具体参数，修改参数后必须重新审批。
>
> **原理追问：** 人工审批要防 TOCTOU，也就是人看的是 A，执行时变成 B。可以对规范化 action payload 做哈希并写入审批记录，执行服务校验哈希、身份、有效期和一次性使用。
>
> **容易踩坑：** 我不会每一步都弹窗造成审批疲劳，也不会只在流程末尾让人背书。低风险自动化和高风险动作要分级。
>
> **岗位或项目连接：** 当前 Agent 项目有任务编排能力，但没有证据证明实现参数绑定的金融审批；这是需要补的系统设计。

### Q076：怎么做一次 Agent Run 的端到端审计和回放？

> **口语化回答：** 我会给 Run 生成 trace_id，并记录用户与授权上下文、输入快照、Planner 版本、模型和 Prompt 版本、每次工具参数与结果引用、Policy decision、人工批准、状态转移、Token/成本以及最终输出。回放分两种：历史复现使用冻结版本；新版本对比在隔离环境重跑，绝不覆盖原记录或触发真实副作用。
>
> **原理追问：** 模型服务可能不完全确定，所以回放要区分“字节级相同”和“决策证据等价”。必要时保存合规允许的原始响应或其哈希与 Provider request id，并把非确定性标出来。
>
> **容易踩坑：** 我不会为了回放再次发送邮件、提交决定或访问已撤回数据，也不会把完整 PII 复制进普通 Trace。审计访问也要有 purpose 和记录。
>
> **岗位或项目连接：** Agent Memory 的 result_ref 和 CodeWiki 的 llm_run 记录是可迁移基础；金融回放还要补授权、策略、审批和副作用隔离。

### Q077：金融 Agent 怎么做 Eval 和 Red Team？

> **口语化回答：** 我会建立四套测试：正常任务的事实与完成率，金融领域的时点、数值和理由正确性，安全攻击的提示注入、越权、泄密与工具组合，以及运营故障的超时、重复、乱序和降级。每个样本定义允许动作和禁止动作；高风险失败按最坏结果计分，不用平均准确率掩盖。
>
> **原理追问：** 离线测试要固定语料、模型和策略版本，防止评测泄漏；LLM judge 需要人工校准、成对比较和注入防护。上线前做 shadow/canary，上线后把真实失败匿名化回灌测试集。
>
> **容易踩坑：** 我不会只测试“回答得好不好”，也不会让测试 Agent 使用生产写权限。攻击样本要覆盖多语言、文件、图片、编码和跨回合记忆。
>
> **岗位或项目连接：** 当前项目已有一些 Benchmark 表述，但实验元数据仍需事实核实；金融题库只给完整评测框架，不捏造通过率。

### Q078：现场让你设计美股投研 Agent，你会怎么在十分钟内讲清？

> **口语化回答：** 我先澄清用户、数据授权、是否做历史回测、输出是不是投资建议和延迟目标。然后画主链路：官方披露/获授权数据进入不可变 Raw Zone，解析成 XBRL Facts、文档 Chunk、实体和公司行动，写双时态事实库与检索索引；Query Planner 只能调用时点检索、确定性计算和证据工具，Answer Builder 输出 claim、citation、冲突与不确定性，研究员最终确认。
>
> **原理追问：** 我会重点展开三个非功能点：as-of 查询防未来数据泄漏，source-to-claim lineage 保证可追溯，数据合同和 ACL 控制授权。评测按事实、时点、引用、数值、拒答、延迟和成本分层。
>
> **容易踩坑：** 我不会一上来画十个 Agent，也不会用向量库替代事实库。没有明确业务边界前谈模型品牌没有意义。
>
> **岗位或项目连接：** 我会说明这是基于 CodeWiki 结构化解析、GraphRAG 和引用能力的迁移方案；本人是否做过真实美股生产系统仍待核实，不把设计题说成履历。

### Q079：现场让你设计 Open Banking 自动授信平台，你会怎么讲？

> **口语化回答：** 我先问司法辖区、产品、是否全自动、决定 SLA、人工复核和上游 Provider。主链路是：Application 创建幂等申请，Consent Service 管授权，Data Gateway 拉取并保存原始快照，Normalization/Feature Service 生成 point-in-time 特征，经过验证的 Model Service 和 Policy Engine 分别评分与执行规则，Decision Orchestrator 汇总到批准、拒绝、补件或人工复核，Notice Service 用真实 reason code 出通知，Audit Store 保存全链路版本。
>
> **原理追问：** 我会强调 LLM 只做非结构化整理和受控表达，不能替代风险模型、政策或法务。系统用状态机、Outbox、幂等键和对账处理长流程；异常时 fail closed 到人工或延迟路径，具体策略预先审批。
>
> **容易踩坑：** 我不会承诺“AI 自动批贷更公平”，也不会编造 PD、坏账率或审批效果。Consent、Adverse Action 和自动决策规则必须按目标市场确认。
>
> **岗位或项目连接：** 我会把 AI 周报的确定性计算、Memory 的可追溯证据和京东路由题的审计编排组合起来，同时明确它们只证明工程迁移能力，不证明信贷投产经验。

### Q080：入职后 30/60/90 天，你会怎么推进金融 AI 项目？

> **口语化回答：** 前 30 天我先跟业务、风险、合规、数据和运营把决策边界、数据流、现有模型、事故与审批流程摸清，建立资产和风险清单；60 天选一个低风险、高反馈场景，比如分析员证据助手或交易分类 Shadow，补齐离线 Eval、权限、审计和回滚；90 天只在门禁通过后做受控试点，用真实反馈决定扩展，不急着让 LLM 进入有约束力的决定。
>
> **原理追问：** 我会用阶段退出条件，而不是只按日期：数据授权清楚、基线可复现、安全威胁关闭、模型风险审批通过、运行 Runbook 完整，才进入下一阶段。指标包含质量、风险、人工负担、延迟和成本，不只看自动化率。
>
