# 项目一:AI 周报系统

## 第一层:实战已问(回顾)

### 【实战·卓誉】基于什么模型?一人天工时怎么审出来的?

**参考答案**:
> 周报系统模型为 [实际模型]。工时核算是关键设计:不让模型凭空"算"工时——工时由**确定性逻辑**得出(从提交记录、任务关联、代码量等多源数据,按预设规则折算),LLM 只把算好的工时数据组织进周报叙述。面试官质疑"不用 LLM 也能做",这里的边界是:**算数用规则,表达用 LLM**,这正是周报系统的设计原则。

### 【实战·卓誉】这东西不用 LLM 也能做吧?听起来就是个 workflow。

**参考答案**:
> 纯数据采集 + 模板填充确实能做出基础周报,大模型不是必需的。LLM 的价值在两点:
> 1. **自然语言交互**:周报推出来后,用户能直接追问("这周 A 模块提交为什么少了"),不用翻系统。
> 2. **数据解读**:把数字组织成有重点的叙述(亮点/异常),降低阅读成本。
> 但诚实说:**只定时推数字周报,确实不需要大模型**,LLM 价值在交互和解读层。

### 【实战·Ashley】数据收集清洗是不是从人工找各数据源 → 脚本收集 → 大模型分析?数据分析是大模型做的吗?

**参考答案**:
> 前半段是工程活:把人工去 Git/Jira/CI 多数据源找数据的过程,用脚本自动收集、清洗、结构化。后半段才用 LLM,它不做统计分析(统计用规则算准数),LLM 只负责把结构化数据**组织成自然语言周报**。分工原则:**数字必须准用规则算,表达要自然用 LLM 生成**,避免让 LLM 算数产生幻觉。

### 【实战·安克】没大模型,我配固定模板 + 自动采集 pipeline 也能做吧?模板变了吗?自动化定时?

**参考答案**:
> 纯模板确实能做基础周报。大模型介入后**模板结构没变**(固定板块,稳定用户习惯),变的是**内容生成方式**:数字仍由脚本统计(保证准),文字描述和重点提炼由 LLM 生成。是自动化定时触发:每周采集→生成→推送。

### 【实战·安克】大模型写 SQL,如果它写了 DROP/DELETE 把表删了,怎么拦截?

**参考答案**(多层防护):
> 1. **SQL 权限隔离**:给大模型的数据库连接用**只读账号**,DDL/DML(删改)在数据库层直接拒绝——最硬的兜底。
> 2. **SQL 预校验**:执行前用 SQL parser 解析,白名单只允许 SELECT,出现 DROP/DELETE/UPDATE/ALTER 直接拦截。
> 3. **关键词黑名单**:对生成 SQL 做关键词检查。
> 4. **沙箱库**:复杂场景查的是只读副本或脱敏副本,动不到生产。
> 核心原则:**永远不信任模型生成的 SQL 直接打生产,权限 + 解析双保险。**

### 【实战·安克】怎么把表名和表描述精确给到模型?

**参考答案**:
> 维护一份**表元数据(schema 字典)**:表名、字段、字段含义、业务说明,做向量化。用户提问时先检索相关表 schema,把"表名 + 字段说明"作为上下文喂给模型,模型基于精确 schema 生成 SQL。不是把全库 schema 灌进去(太大),而是按 query 相关性召回相关表。

### 【实战·安克】(杀手锏)老板看周报发现销量下滑,问"为什么下滑"——根因分析,你们现在能解决吗?如果让你设计怎么做?

**参考答案**(诚实承认 + 分层设计):
> **诚实承认**:目前做不到真正的根因分析,只能回答"数据是什么",回答不了"为什么"。这是明确边界。
>
> 若要设计,拆三层:
> 1. **数据层(现有)**:Text-to-SQL,回答"是什么",拉指标现状。
> 2. **归因层(新增核心)**:不让模型直接"猜"原因(会幻觉),建**归因分析能力**:
>    - **多维下钻**:按地区/品类/渠道/时段拆解,定位下滑集中切片。
>    - **对比基线**:和历史同期、目标值对比,判断趋势性 vs 异常波动。
>    - **关联分析**:把相关指标(库存/促销/竞品/流量/客诉)一起拉出看相关性。
>    - 用**确定性计算/规则**缩小候选原因,不靠模型凭空猜。
> 3. **推理 + 验证层**:把"数据事实 + 候选原因"喂模型做**假设推理**("可能是 X 促销结束导致 Y 品类下滑"),再**回查数据验证假设**,验证通过才输出,不通过标注"待确认"。
>
> 关键原则:**归因的"找候选原因"用确定性方法,模型只做"组织叙述 + 生成可验证假设",绝不让模型直接编原因**——跟"不让模型算数"同一原则。

## 第二层:深挖——数据与可靠性

### 【深挖 1】数据源具体有哪些?数据质量怎么保证?脏数据怎么处理?

**参考答案**:
> 数据源主要是几类:代码提交记录(Git)、任务/缺陷管理(Jira 类)、CI/CD 构建记录、Code Review 数据。质量保证分三道关:
> 1. **采集层校验**:每个数据源定义 schema,采集时做字段完整性 + 类型校验,不合规记录进死信队列待人工排查,不污染主流程。
> 2. **清洗层**:去重(同一提交多平台同步)、补全(缺失字段用关联数据回填)、归一化(时间戳统一、人员 ID 跨系统映射)。
> 3. **统计层兜底**:最终进入周报的数字由脚本算,不让 LLM 碰数字——即使前面数据有问题,也是"数据问题"而非"生成问题",可追溯可修。

### 【深挖 2】某个数据源挂了怎么办?增量采集还是全量?

**参考答案**:
> 设计成**增量为主、全量为兜底**:
> - 平时按时间增量拉(只取上次同步后的新增),降低负载。
> - 每个数据源有**健康检查 + 重试 + 降级**:拉取失败重试 N 次,仍失败则该数据源本周报缺失字段标注"数据获取异常",其余正常出,不整体阻塞。
> - 定期(如每月)跑一次全量对账,修复增量可能漏的。
> 核心原则:**单数据源故障不阻断周报产出,但要显式标注异常**,不能默默缺失让数字失真。

### 【深挖 3】LLM 生成周报,怎么保证数字准确?周报数字错了是事故。

**参考答案**:
> 这是周报系统的命门,用**"数字与叙述分离"**原则:
> 1. **所有数字由脚本统计**,从结构化数据算出,绝不交给 LLM 生成。LLM 看到的是已经算好的数字。
> 2. **LLM 只做叙述组织**:把数字串成自然语言、提炼重点、生成解读,但不能改数字。
> 3. **生成后校验**:LLM 输出里出现的数字,回比对统计结果,不一致就重生成或回退模板。
> 4. **关键指标双人/双算**:重要数字用两种方式算,交叉验证。
> 本质思路和 SQL 那题一样:**模型负责表达,确定性逻辑负责准确**。

## 第三层:深挖——Text-to-SQL 深水区

### 【深挖 4】Text-to-SQL 准确率多少?怎么评估?bad case 怎么收集?

**参考答案**:
> 这个必须能报出数,否则显得没做评估。
> - **评估**:建一个 query-SQL 的**评测集**(人工标注的正确 SQL),用**执行结果正确率**(而非文本相似度)作为指标——同一查询有多条正确 SQL,文本对比会误判。关注两个数:**执行成功率**(SQL 能跑)和**结果正确率**(跑出来对)。
> - **bad case 收集**:线上用户对结果点"不对/重新生成"时记录该 case,定期人工分析归类(表选错/字段错/聚合错/条件错),针对性补 schema 描述或加 few-shot 示例。
> - **持续优化**:把高频 bad case 转成 few-shot 示例放进 prompt,或修正表 schema 描述。

### 【深挖 5】模型生成的 SQL 性能很差(全表扫描、多表笛卡尔积)怎么办?

**参考答案**:
> 这是 Text-to-SQL 的隐藏坑,很多人忽略。做法:
> 1. **执行前预估**:拿到 SQL 先 EXPLAIN,检查全表扫描、笛卡尔积、缺索引命中,命中告警规则就拦截重生成。
> 2. **Schema 描述里带索引信息**:告诉模型哪些字段有索引、表多大,引导走索引字段过滤。
> 3. **大表加保护**:对大表强制要求 WHERE 条件,无条件的大表查询直接拒。
> 4. **超时熔断**:执行设超时,慢查询熔断返回"查询超时,请缩小范围"。
> 核心思路:**不仅要 SQL 对,还要 SQL 快**,生产环境慢查询会拖垮库。

### 【深挖 6】多用户/多部门并发查询,数据权限怎么隔离?A 部门不能看 B 部门数据。

**参考答案**:
> 权限不能交给模型(模型可能生成越权 SQL),要在**工程层硬隔离**:
> 1. **数据源级隔离**:每个用户/部门的查询连接的是**已做行级权限过滤的视图或库**,即使模型生成"查全表"的 SQL,数据库层也只返回他有权限的行。
> 2. **Schema 范围隔离**:给模型注入的表 schema 本身就按权限过滤——A 部门用户只能看到 A 部门相关的表/字段描述,模型根本不知道 B 部门的表存在。
> 3. **审计**:所有生成 SQL + 执行结果落审计日志,可追溯谁查了什么。
> 原则:**模型不可信,权限必须在它之下的数据库/工程层兜死**。这和"只读账号拦截 DROP"是同一套防御思路。

## 第四层:深挖——产品与评估

### 【深挖 7】不同角色(老板/员工/PM)看的周报一样吗?怎么做个性化?

**参考答案**:
> 不一样。不同角色关注点不同:老板看全局指标和异常,员工看自己贡献和待办,PM 看模块进度和风险。做法:
> - **同一份数据底座,不同视角模板**:数据层统一,呈现层按角色配不同模板(指标选型、重点维度、详略程度)。
> - **大模型在个性化上的作用**:按角色调整叙述口吻和重点提炼,但底层数据一致。
> 注意陷阱:**个性化不能让数字打架**——老板和员工看到的同一指标必须一致,差异只在视角和详略,否则会失信。

### 【深挖 8】怎么评估周报质量?有没有反馈闭环?

**参考答案**:
> 周报这种"软产出"评估比 SQL 难,但必须做,否则没法迭代:
> 1. **显式反馈**:周报上配"有用/无用""有误"按钮,收点对点反馈。
> 2. **隐式信号**:用户有没有打开周报、停留多久、是否追问(追问说明周报引起了兴趣或没讲清)。
> 3. **抽样人工评**:定期抽样,人工按维度打分(数字准确、重点突出、无幻觉、可读性)。
> 4. **A/B**:改 prompt/模板时小流量 A/B 对比反馈率。
> 闭环:反馈 → 归类 → 改 prompt/模板/数据源 → 再评估。

# 项目二:CodeWiki / 代码图谱(GraphRAG + AST)

## 第一层:实战已问(回顾)

### 【实战·Ashley】讲一下 GraphRAG 在代码生成平台里的流程。

**参考答案**:
> 整体分四步:**离线建图 → 在线检索 → 子图扩展 → 上下文组装**。
> 1. **离线建图**:对代码库做静态解析(AST),以函数为基本单元切成 chunk,每个函数是一个节点,把节点向量化存向量库,同时把调用关系、依赖关系存成图。
> 2. **在线检索**:用户 query 先做向量召回,找到最相关的种子节点。
> 3. **子图扩展**:从种子节点沿图的边扩展(调用它的、它调用的、同文件/同类的),把有结构关联的相关代码一起拉出来——这是 GraphRAG 相比普通 RAG 的核心价值:**普通 RAG 只按相似度召回孤立片段,GraphRAG 能把有依赖关系的上下文补全**。
> 4. **上下文组装**:对召回 + 扩展的节点做重要性排序,组装进 prompt 交给大模型生成。

### 【实战·Ashley】chunk 怎么切分?函数级吗?节点和边怎么设计?边是什么?

**参考答案**:
> - **节点**:一个函数 = 一个节点,带元数据(所属文件、类、函数签名、注释)。
> - **边**表示函数间关系,主要几类:
>   - **调用边**(A 调用 B)—— 最重要
>   - **归属边**(函数属于某个类/模块)
>   - **依赖边**(共享同一数据结构/import)
>   - (可选)**继承/实现边**(面向对象场景)
> 边带方向和类型,检索扩展时按边类型给不同权重。
> 选函数级是因为:函数是代码里语义最完整、边界最清晰的最小单元,既不会像按行/按 token 切那样切碎语义,也不会像按文件切那样粒度太粗。

### 【实战·Ashley】(陷阱题)同一个大函数被切成两个节点,边怎么定义?

**参考答案**:
> 当一个大函数被迫切成两个 chunk 节点时,给它们之间加一条特殊的 **"同源顺序边"(intra-function / sequential 边)**,标记它们本属于同一个函数、保留先后顺序。检索时如果命中其中一个片段,能通过这条边把同一函数的另一半也一起召回,**保证函数语义不被割裂**。同时两个子节点共享同一个父函数 ID,组装上下文时按原顺序拼回去。
> 这题考的是有没有想过"切分带来的语义断裂"问题。答"加同源顺序边 + 共享父 ID 拼接"就到位了。

### 【实战·Ashley】(反复追问)检索到代码后,按什么优先级组装上下文?prompt 前面和后面信息特别重要,你怎么排?

**参考答案**(你当场只答了"按相关性",这里补完整):
> 组装上下文分两个维度:
> 1. **筛选/排序维度**——综合打分,不只看向量相似度,还加权:
>    - 向量相关性(与 query 的语义相似度)
>    - 图距离(离种子节点几跳,越近越重要)
>    - 节点类型权重(直接被调用的核心函数 > 工具函数)
> 2. **位置摆放维度(利用 LLM 的 "lost in the middle" 特性)**——大模型对 prompt **开头和结尾**最敏感,中间容易忽略。所以:
>    - **最重要的信息(用户直接要改的目标函数、明确指令)放在结尾**(离生成位置最近,注意力最高)
>    - **次重要的背景/依赖代码放在开头**
>    - **相关性最低的补充上下文放在中间**
> 这样既保证信息全,又让模型注意力落在最关键的代码上。
> 💡 关键词:**"lost in the middle"**。面试官在暗示的知识点,答出来会直接扭转印象。

### 【实战·安克】这其实就是做了个语法树(AST)解析吧?跟 Claude Code 插件的 MCP(Go/Python 等语法解析)有什么区别?

**参考答案**:
> 表面都是语法解析,区别在**输出的结构和使用方式**:
> - 现成 MCP/插件做的是**单文件/单语言的语法解析**,给模型提供"这个文件的符号表/定义位置",本质是**定位工具**。
> - 我们做的是**跨文件、跨模块的代码知识图谱**:不只解析单个文件,而是把整个仓库的**函数调用关系、模块依赖关系、数据流**建成一张图(GraphRAG)。模型检索时不是"找一个定义",而是"找到一段代码 + 它的所有上下游依赖",把**完整的调用链上下文**一次性补全。
> 价值差异:模型改一个函数时,现成工具可能只给函数本体,我们能把"谁调用它、它调用谁、共享什么数据结构"一起喂进去,改起来不会漏掉调用方。**单点解析 vs 全局图谱**,这是核心区别。

### 【实战·安克】这个图谱是给人用的吗?具体起什么作用?

**参考答案**:
> 主要给**模型/agent 用**(RAG 检索底座),也附带给人看(可视化依赖关系)。核心作用:当代码 agent 需要理解或修改跨模块代码时,用图谱做检索,把相关上下文(不止相似代码,还有依赖代码)喂给模型,提升跨模块理解的准确率。

### 【实战·安克】(生死线)我直接用 Claude Code 对仓库做 init,生成 markdown 长期记忆,跟你这个 GraphRAG MCP 区别多大?模型自己抓重点做长期记忆,是不是比做成 GraphRAG 给模型更优?

**参考答案**(Dennis 明确表达"我理解模型自己抓重点做长期记忆可能更优",必须有力反驳):
> 这两种是不同思路,各有场景,但 GraphRAG 有几个 markdown 记忆替代不了的优势:
>
> 1. **确定性 vs 概率性**:Claude Code init 让模型自己读仓库、自己总结重点存 markdown——这是**概率性**的,模型可能漏关键依赖、可能总结错。GraphRAG 基于 **AST 静态解析**,调用关系、依赖关系是**确定性、精确**的,不会漏调、不会幻觉。代码这种"错一个调用链就跑不通"的场景,精确性比"聪明总结"更重要。
>
> 2. **增量更新 vs 全量重扫**:仓库每天在变,Claude Code 的 markdown 记忆**怎么增量更新**?要么过期失效,要么重新 init 全扫(成本高)。GraphRAG 的图可以**基于 git diff 增量更新**只变动节点,维护成本低、始终新鲜。
>
> 3. **检索精度**:markdown 是自由文本,模型从一大段文本里"自己找"相关部分,召回靠语义相似度,容易漏。GraphRAG 是**结构化检索**,按图结构精确扩展(调用它的、它调用的),召回准、可解释。
>
> 4. **规模**:大仓库(几十万行)Claude Code init 一次性扫成本极高,且 markdown 膨胀后检索质量下降;GraphRAG 离线建图、在线按需检索,规模可扩展。
>
> **公平地说**:Claude Code init 适合**小仓库、快速上手、不需要精确依赖**的场景;GraphRAG 适合**大仓库、跨模块、需要精确依赖关系**的工程化场景。两者不是替代关系,是分层互补。
> 💡 核心论点就一句:**代码的调用关系是确定性的,该用确定性方法(AST 图)而不是概率性方法(模型总结)来保证精确。**

### 【实战·卓誉】自研多种编程语言的 SC 解析引擎,对标 Codex / Cursor,核心竞争力在哪里?

**参考答案**:
> 诚实定位——**不是全面超越,是特定场景的补强**。对标 Codex/Cursor 这种成熟产品,我们的差异化集中在:
> 1. **跨模块依赖的精确召回**:Codex/Cursor 的 codebase indexing 在相似度检索上很强,但跨模块依赖召回靠模型自己摸索,可能漏。我们用图结构精确扩展,不漏调用方。
> 2. **企业内定制**:Codex/Cursor 是通用产品,企业内部代码规范、私有依赖、特定业务模块的语义,通用产品不懂,我们可以定制建图规则。
> 3. **大仓库 + 增量更新**:git diff 局部更新,成本可控。
> 不假装全面替代:**通用场景打不过 Codex/Cursor,但在"超大仓库 + 跨模块精确依赖 + 企业定制"这个细分场景有差异化**。

## 第二层:深挖——建图工程化

### 【深挖 9】支持哪些语言?跨语言调用怎么建边?

**参考答案**:
> 支持主流语言(Java/Python/Go/TS 等)。跨语言调用的边是难点:
> - **语言内**:用对应语言的 AST 解析,调用关系精确(如 Java 的 method invocation、Python 的 call)。
> - **跨语言**:通过**接口契约**建边——比如服务间 RPC/HTTP 调用、FFI、protobuf 定义。这类边基于接口描述文件(IDL/swagger)匹配,而非源码级直接解析。边类型标记为"跨语言调用",权重低于语言内调用。
> - 跨语言边本质是**协议级**而非**源码级**,要诚实标注其确定性低于语言内边,检索时区别对待。

### 【深挖 10】AST 解析用什么工具?各语言差异大怎么统一成一张图?

**参考答案**:
> 用 **tree-sitter**(支持多语言、增量解析、容错)。统一思路:
> 1. 各语言用 tree-sitter 解析得到 CST,再抽取**统一的中间表示**:节点统一抽象为 Function/Class/Module,边统一抽象为 Calls/BelongsTo/DependsOn 等类型,屏蔽各语言语法差异。
> 2. 设计一层**语言适配器**:每种语言一个 adapter,负责把该语言的 AST 特定结构映射到统一 IR。
> 3. 图存储用统一 schema,语言只作为节点属性。
> 好处:上层检索逻辑与语言无关,新增语言只需加 adapter。

### 【深挖 11】图存储用什么?向量库和图怎么结合?

**参考答案**:
> 分两套存:
> - **图存储**:存节点 + 边的关系结构(可用 Neo4j,或轻量场景用关系表 + 邻接表)。负责"结构检索"——找调用链、依赖链。
> - **向量库**:存节点的向量(函数代码/签名的 embedding)。负责"语义检索"——按 query 找最相关节点。
> - **结合**:节点 ID 双向关联。检索时先向量召回种子节点 → 拿节点 ID 去图里扩展子图 → 子图节点再回向量库取内容。两库分工:向量库找"相关",图找"关联"。

### 【深挖 12】大仓库(百万行)建图要多久?增量更新机制?

**参考答案**(安克没问但很可能追的工程问题):
> - **首次全量**:按模块并行解析,百万行级别可控在分钟到十几分钟级(取决于语言和机器),瓶颈在 AST 解析和向量化,可并行。
> - **增量更新(关键)**:基于 **git diff**——只对变更文件重新解析,定位受影响的节点和边,**局部重建**。函数签名没变只改实现,只更新节点内容向量不动边;签名变了或调用关系变了,才重算相关边。
> - **版本一致性**:图绑定 commit 版本,不同分支/版本可并存,避免脏读。
> 这是 GraphRAG 对比 Claude Code init markdown 的核心优势之一:**markdown 记忆没法增量更新,图可以**。

## 第三层:深挖——检索与效果

### 【深挖 13】GraphRAG vs 普通 RAG 效果对比,有量化数据吗?

**参考答案**:
> 这是面试官最想听但最该提前准备的数。建议按你实际测过的报:
> - 评测场景:跨模块代码理解/修改任务(如"修改 X 功能需要改哪些地方")。
> - 对比维度:**召回完整度**(有没有漏掉相关调用方/依赖)、**修改正确率**(基于召回上下文,模型给出的修改是否完整正确)。
> - 典型结论方向:普通 RAG 在"找相似代码"上够用,但在"找相关依赖"上明显漏召回(只召回语义相似的,漏掉调用关系关联的);GraphRAG 在跨模块任务上召回完整度显著高。
> - 诚实补充:单文件内简单任务两者差不多,GraphRAG 的增益集中在跨模块场景——不要夸大成"全面碾压"。
> 如果还没有量化数据,坦诚说"目前定性验证为主,正在建评测集"——比编数据强。

### 【深挖 14】节点向量化用什么模型?代码 embedding 怎么选?

**参考答案**:
> 代码 embedding 不能用通用文本模型,要用**代码专用模型**(如 CodeT5/Salesforce 的 code embedding、或开源 code embedding 模型)。要点:
> - 向量化内容不只是函数体,**带签名 + 注释 + 所属类上下文**一起编码,信息更全。
> - 代码和自然语言 query 的语义对齐:用户问的是自然语言,检索的是代码,要确保 embedding 模型对"自然语言→代码"的跨模态检索效果好(选支持 code-text 对齐的模型)。

### 【深挖 15】如果代码没注释没文档,图节点上有什么信息?

**参考答案**:
> 没注释时节点信息来自**代码本身的结构语义**:函数名、参数名、返回类型、调用的其他函数名、被谁调用、所属类/模块。这些结构信息往往已能反映函数职责。必要时可以**用 LLM 给无注释函数生成摘要**作为节点补充信息(离线一次性生成,缓存),但标注为"模型生成的摘要",与确定性结构信息区分置信度。

### 【深挖 16】这套东西最终有没有提升 agent 效果?怎么证明?

**参考答案**:
> 必须能证明,否则就是"自嗨"。证明方式:
> - **端到端评测**:同一批代码修改任务,分别用"无图谱 RAG"和"GraphRAG"给 agent,对比修改完整性和正确率。
> - **真实使用信号**:接入后 agent 的修改返工率/用户人工修正次数是否下降。
> - **案例**:举一两个具体例子,说明没有图谱时模型漏改了某个调用方,有了图谱后能补全。
> 如果还没有量化数据,坦诚说"目前定性验证为主,正在建评测集"——比编数据强。

# 项目三:AI Agent 长期记忆 + 上下文压缩系统

## 第一层:实战已问(回顾)

### 【实战·Ashley】是你一个人做的吗?

**参考答案**:坦诚说明独立负责 / 主导的部分即可。

### 【实战·Ashley】四层设计分别是什么?(L0/L1/L2/L3)

**参考答案**:
> 从"原始"到"抽象"分四层:
> - **L0 — 原始对话层(Raw)**:完整原始对话记录,不加工,兜底和溯源。
> - **L1 — 会话摘要层(Session Summary)**:对单次会话做压缩摘要,去冗余保留关键。
> - **L2 — 结构化事实层(Facts / Entities)**:从对话抽取结构化用户事实、偏好、实体,可检索可更新。
> - **L3 — 长期画像层(Profile / Semantic)**:跨会话沉淀的稳定用户画像、长期偏好,最抽象最稳定。
> 越往上层越抽象、越稳定、体积越小;越往下层越原始、越大。压缩就是把 L0 逐层蒸馏到 L1/L2/L3。

### 【实战·Ashley】记忆系统是跨会话的吗?

**参考答案**:是**单用户、多会话**的记忆系统。同一用户跨多个会话的记忆沉淀到 L2/L3,新会话能召回历史记忆。

### 【实战·Ashley】什么时候存?怎么存?

**参考答案**:
> 分两个时机:
> - **实时/增量存**:会话进行中,L0 原始记录实时落库。
> - **异步/触发式抽取**:会话结束(或达一定轮次/token 阈值)时,异步触发抽取任务,用 LLM 把对话蒸馏成 L1 摘要,并抽取 L2 结构化事实,再更新 L3 画像。用异步是为了**不阻塞主链路响应速度**。

### 【实战·Ashley】存的时候出现事实冲突 / 反事实怎么办?(今天叫 A,明天叫 B)

**参考答案**(你当场答"覆盖",这里升级):
> 用**带时间戳的覆盖 + 版本保留**策略:
> - 检测到新事实与旧事实冲突时(同一实体、同一属性、值不同),**不直接硬删**,而是打时间戳/版本,**新值生效、旧值标记过期但保留**(可溯源)。
> - 对于"可变属性"(如当前项目、当前状态)——**用新值覆盖**(以最新为准)。
> - 对于"本不应变的属性"(如姓名)出现冲突——**标记为冲突,降低置信度**,必要时下次交互向用户确认,而不是盲目覆盖。
> 简单说:**可变信息按时间覆盖,不可变信息按冲突处理**,避免被一次幻觉/口误污染长期记忆。

### 【实战·Ashley】(核心追问)大模型抽取判断错误(幻觉)怎么办?怎么保证长期记忆准确?

**参考答案**:
> 长期记忆最大风险是**一次幻觉被固化成长期错误事实**,后面反复召回污染 agent。几层防护:
> 1. **抽取阶段加约束**:让 LLM 抽取事实时**必须给出原文出处(span)**,找不到依据的直接丢弃——减少凭空捏造。
> 2. **置信度打分**:每条记忆带置信度,LLM 不确定的、单次出现的低置信度事实,不直接进 L2/L3,先放"候选区",**多次出现/被确认后才晋升**。
> 3. **冲突检测**:入库前和已有记忆做一致性校验(见上)。
> 4. **可溯源 + 可失效**:每条记忆能追溯到原始对话,发现错误能定位和撤销。
> 5. **召回时二次校验**:关键场景召回记忆后,让主模型结合当前上下文判断记忆是否仍适用,而非无脑信任。
> 核心思路:**不追求单次 100% 准确(做不到),而是通过"多次确认晋升 + 溯源 + 置信度 + 冲突检测"让错误记忆难以固化、且可回滚。**

### 【实战·Ashley】怎么取?什么时候加载 L0/L1/L2/L3?

**参考答案**:
> 按"由抽象到具体、按需下钻"加载,平衡 token 成本和信息量:
> - **默认每次都加载 L3(长期画像)+ L2(相关结构化事实)**:体积小、价值密度高,几乎每次调用都带上。
> - **L1(会话摘要)按相关性召回**:当前 query 和某历史会话相关时,召回对应 L1 摘要。
> - **L0(原始对话)只在需要精确溯源/细节时才加载**:比如用户追问某次具体对话细节,或需核对原文,才下钻到 L0。
> 简单说:**L3/L2 常驻,L1 按需召回,L0 兜底下钻**。

### 【实战·安克】长期记忆和上下文压缩是 for 内部自研 agent runtime,还是基于已有 runtime 二开?

**参考答案**:
> 基于已有 runtime 二开。我们没有从零造 agent runtime,而是在现有 runtime 之上,把**记忆层和上下文压缩层**作为独立模块接入。原因:runtime 本身的调度、工具调用、流式输出造轮子性价比低;我们的差异化价值在**记忆治理和上下文管理**,集中精力做深。

### 【实战·安克】(被追问)Copilot 自己就有上下文压缩,你们的压缩和它有什么区别?

**参考答案**:
> Copilot 的压缩是**通用的、被动的、黑盒的**——它对超长上下文做截断/摘要,但不理解业务语义,也无法定制。我们做的是**可定制、分层的主动压缩**:
> - **分层压缩**:不一刀切摘要,而是分 L0~L3 不同层不同压缩策略、不同保留优先级。
> - **业务感知**:哪些信息留、哪些丢,可按业务场景配置(比如代码 agent 保留函数签名和依赖,丢掉闲聊)。
> - **可控可观测**:压缩了什么、丢了什么可追溯,而不是 Copilot 黑盒一截了之。
> 简单说:Copilot 的压缩是"被动省 token",我们的是"主动管理记忆质量"。

### 【实战·安克】现在还用千问吗?对接 DeepSeek V4 Pro 的上下文压缩,策略怎么设计?到多少 k 做压缩?怎么设计?

**参考答案**(分阈值 + 分层触发):
> 不是无脑到某个阈值才压,而是**多触发点 + 分层**:
> 1. **阈值触发**:设定上下文用到模型窗口的一定比例(比如 DeepSeek V4 Pro 128k 窗口,用到 ~80% 即 ~100k 时)启动压缩,留余量避免溢出。阈值不是固定值,结合单轮增量预留动态算。
> 2. **轮次触发**:每 N 轮对话做一次轻量摘要增量更新,避免堆积。
> 3. **分层处理**:
>    - 近期上下文(最近 K 轮)**原样保留**(模型对近期信息注意力高,不该压)。
>    - 中期上下文做**摘要压缩**(L1)。
>    - 远期上下文抽**结构化事实**(L2)和**画像**(L3)。
> 4. **保留锚点**:压缩时保留关键实体/函数签名/决策点作为"锚点",便于回溯到 L0。
> 核心思路:**近期不压、中期摘要、远期蒸馏**,按时间衰减决定压缩力度。

## 第二层:深挖——四层流转与生命周期

### 【深挖 19】四层之间怎么流转?L0→L1→L2→L3 的触发机制?

**参考答案**:
> 流转不是定时全量跑,而是**事件驱动 + 阈值触发**:
> - **L0→L1(会话摘要)**:会话结束,或单会话 token 达阈值,触发异步摘要。
> - **L1→L2(抽取事实)**:摘要生成后,触发事实抽取,从 L0/L1 抽结构化事实(实体、属性、偏好)。
> - **L2→L3(画像沉淀)**:不是单次触发,而是**累积晋升**——L2 里某事实多次出现/高置信度/跨会话稳定,才晋升为 L3 长期画像。单次出现的低置信度事实留在 L2 候选区,不进 L3。
> 关键设计:**越往上层,晋升门槛越高**——L3 是最稳定的,不能被一次对话污染。

### 【深挖 20】记忆不能无限存,有"遗忘"机制吗?怎么淘汰?

**参考答案**(Ashley 没问但很可能追):
> 有,长期记忆不淘汰会膨胀 + 过期信息污染。淘汰策略:
> 1. **时效衰减**:每条记忆带时间戳和"有效期"(有些事实天生有保质期,如"当前负责 X 项目")。超有效期且未刷新的记忆,降置信度,逐步归档。
> 2. **访问频次**:长期未被召回的记忆降权(类似 LRU),优先保留高频被召回的。
> 3. **冲突替换**:被新事实覆盖的旧值,标记过期但不立即删(可溯源),归档到冷存储。
> 4. **L0 冷归档**:原始对话保留一段时间后转冷存储,L1 摘要替代其位置,L0 只在需要溯源时才回查。
> 原则:**遗忘不是删除,是降权 + 归档**,保证可回溯同时控制热数据规模。

### 【深挖 21】记忆检索怎么和当前 query 相关?纯向量召回够吗?

**参考答案**:
> 不够,纯向量召回有局限。检索是**向量 + 结构 + 时间**三路:
> 1. **向量召回**:query 向量化,找语义相关的 L2 事实/L1 摘要。
> 2. **结构召回**:query 里涉及的实体(如"某个项目/模块"),直接按实体索引拉出该实体相关的所有记忆(不依赖语义相似度,避免漏召回)。
> 3. **时间加权**:近期记忆权重高,久远的降权(除非是稳定 L3 画像)。
> 三路结果合并去重 + 重排,再喂模型。向量召回"相关",结构召回"完整",时间加权"时效"。

## 第三层:深挖——安全与隐私

### 【深挖 22】记忆里存了用户敏感数据怎么办?隐私怎么处理?

**参考答案**(企业场景必问):
> 1. **入库前脱敏**:抽取事实时,对敏感字段(身份证、手机、密码、密钥)脱敏/掩码,只存脱敏值或不存。
> 2. **分级存储**:高敏感记忆单独加密存储,访问需鉴权。
> 3. **可擦除**:用户/合规要求删除某条记忆时,能按用户 ID 全链路删除(包括 L0~L3 和向量索引),满足"被遗忘权"。
> 4. **不出域**:记忆数据不进外部模型训练,本地/私有化部署抽取逻辑,敏感数据不外流。
> 核心原则:**记忆系统是用户数据的托管者,合规和可擦除是底线**。

### 【深挖 23】多用户记忆怎么隔离?A 的记忆绝不能给 B。

**参考答案**:
> 隔离要在**存储层硬隔离**,不能靠检索时过滤(一旦 bug 就泄漏):
> 1. **用户 ID 作为分区键**:记忆存储按用户 ID 强制分区,检索时 query 必带用户 ID,只在用户自己的分区里检索。
> 2. **向量库命名空间隔离**:不同用户用不同 namespace/collection,物理隔离。
> 3. **接入层校验**:从 session 拿用户身份,不允许前端传 user_id(防伪造)。
> 4. **审计**:跨用户记忆访问打告警。
> 原则和 SQL 权限隔离一样:**隔离在工程层兜死,不信任上层逻辑**。

## 第四层:深挖——压缩的深水区

### 【深挖 24】上下文压缩是有损还是无损?信息丢失怎么衡量?

**参考答案**:
> **有损**,这是本质——压缩就是取舍。衡量和应对:
> 1. **保留优先级**:近期 > 关键事实 > 摘要 > 细节。近期对话原样保留(模型对近期注意力高),远期才压缩。
> 2. **信息损失衡量**:用"压缩后回溯能力"评估——能否从压缩后的记忆回答原本在 L0 里能回答的问题。建一个回溯评测集,压缩前后对比回答正确率。
> 3. **兜底**:L0 原始数据不删,只是不常加载。需要精确细节时下钻 L0,所以"有损"是"热路径有损、冷路径可还原",不是永久丢失。

### 【深挖 25】(最深)压缩错了会不会"幻觉放大"——压缩层一错,后面全错?

**参考答案**(这是记忆系统最深的坑):
> 会,这是最大风险。压缩层(尤其 LLM 做摘要/抽取)一旦引入错误,会被当作"事实"反复召回,比单轮幻觉危害大得多——**单轮幻觉一次性,记忆幻觉被反复放大**。应对:
> 1. **压缩层加约束**:抽取事实必须带原文 span(无依据丢弃),和单轮幻觉治理同源。
> 2. **压缩结果置信度**:低置信度的压缩产物不进 L2/L3,留候选区。
> 3. **可回滚**:每次压缩生成新版本,L0 保留,发现压缩错误能回滚到上一版。
> 4. **定期对账**:抽样把 L2 事实回比对 L0 原文,发现不一致就标记修正。
> 核心认知:**压缩层是记忆系统的"污染入口",治理力度要大于单轮生成**。这恰恰是这套系统的核心价值——不治理这层的记忆系统是有毒的。

### 【深挖 26】分层加载 L0 下钻会不会很慢?延迟怎么控?

**参考答案**:
> L0 下钻确实慢(原始数据大),所以设计上**尽量避免热路径下钻**:
> 1. **L3+L2 常驻预加载**:会话开始就把用户画像和关键事实加载好(体积小),热路径基本不下钻。
> 2. **L1 按需召回**:毫秒级,可接受。
> 3. **L0 下钻异步化**:用户追问细节需要 L0 时,先返回"正在查询历史记录...",异步查完再补,不阻塞主响应。
> 4. **L0 索引优化**:原始对话按时间/主题建索引,下钻时按索引定位片段而非全扫。
> 原则:**热路径只碰 L2/L3/L1,L0 是冷路径异步兜底**。

## 第五层:深挖——效果评估与范式

### 【深挖 27】怎么评估记忆系统的效果?有没有指标?

**参考答案**(记忆系统最难评估,能答出显得专业):
> 记忆系统效果难评,但要有框架:
> 1. **召回质量**:有记忆 vs 无记忆,回答涉及历史信息的问题的正确率提升。
> 2. **一致性**:同一事实跨会话是否稳定(不该忽 A 忽 B)。
> 3. **污染率**:压缩/抽取引入的错误事实占比(抽样人工审)。
> 4. **时效性**:过期信息是否被正确降权/失效。
> 5. **token 效率**:有记忆后,达到同等回答质量,上下文 token 是否下降。
> 诚实说:记忆系统评估业界尚无成熟标准,我是在实践中建了一套内部指标,不完美但能指导迭代。

### 【深挖 28】记忆和 RAG 是什么关系?记忆本身是不是一种特殊 RAG?

**参考答案**(体现对范式的理解):
> 记忆可以看作**"写入 + 时间累积 + 个人化"的 RAG**:
> - 相同:都是"存起来 → 检索 → 喂上下文"。
> - 区别:
>   ① RAG 检索的是**外部静态知识库**,记忆检索的是**该用户自己历史产生的、动态演化的信息**。
>   ② RAG 一般只读,记忆要**写入、更新、冲突处理、遗忘**——维护成本高得多。
>   ③ 记忆有**时间维度和所有权**,RAG 通常没有。
> 所以记忆系统 ≈ 个人化的、可写的、带生命周期的 RAG。把记忆当 RAG 做(只存只读)会漏掉"冲突/时效/遗忘"这些核心难题——这正是我们系统要解决的。

# 横向:通用追问(三个项目都会被问)

### 【实战·安克】平时用什么 coding agent?什么模型?AI 代码生成率多少?

**参考答案**:如实回答工具(Claude Code / Cursor / Copilot 等)、模型、生成率(业界常见 30%~60%,给真实数)。

### 【实战·安克】Cursor / Claude Code / Codex 这种 coding agent 怎么实现对代码文件编辑的?

**参考答案**:
> 模型本身不直接碰文件,是通过**工具调用(tool use)**实现:
> - agent 给模型暴露一组文件操作工具(读 read_file、写 write_file、按范围编辑 edit_file/str_replace、创建/删除/搜索 grep/glob 等)。
> - 模型推理后输出**结构化的工具调用指令**(指定文件路径、操作类型、内容/范围),agent runtime 执行这些指令真正改文件。
> - 关键点:编辑多采用**基于锚点的局部替换**(指定 old_string → new_string),而非整文件重写,减少 token、降低改错风险。
> - 执行后再读回文件验证,形成"读→改→验"循环。

### 【实战·安克】如果是你设计这个 coding agent 工具,会设计哪几个参数?

**参考答案**:
> - **文件操作类**:file_path、operation(read/write/edit/delete/search)
> - **编辑定位类**:old_string / new_string(锚点替换)或 line_range,edit 必须给精确定位
> - **校验类**:dry_run(只预览不写)、verify_after(改完自动读回校验)
> - **上下文类**:context_window(读文件带几行上下文)、max_bytes(防读超大文件)
> - **安全类**:allow_overwrite、backup(改前是否备份)
> 核心设计原则:**编辑要锚点定位而非整体重写、操作要可预览可回滚、读文件要限大小防爆 token**。

### 【实战·Ashley·HR】技术方向是什么?为什么看新机会?match 岗位的地方在哪?哪些需提升?三个词形容自己?

**参考答案**:
> - **技术方向**:想往 AI / 大模型应用开发(agent 方向)走。
> - **看机会原因**:招行 agent 需求归独立算法团队,后端转 agent 机会少,外部找 AI 应用岗。
> - **能胜任的**:后端工程能力扎实(高并发/系统设计/部署)——AI 应用落地的地基;已有真实 AI 应用项目经验(GraphRAG、长期记忆),做过检索/记忆/幻觉治理这些应用层核心难题。
> - **需提升的**:agent 框架(LangGraph)深度实战;大规模生产环境的 agent 部署/评测/可观测性;算法/模型层理解(定位是应用工程,不训模型)。
> - **三个词**(可选):务实落地 / 深挖 / 快速学习。

### 【实战·卓誉·HR】多需求都紧急、人力不够、有 DELAY 风险,怎么处理?

**参考答案**:
> 1. **不闷头扛**:第一时间向上 + 向需求方同步风险,别等到 deadline 才说做不到。
> 2. **重新排序**:拉需求方对齐"紧急"的真实定义——是真紧急还是"想要快"。按**业务影响 × 时间紧迫度**重新排优先级,而非谁催得凶谁先。
> 3. **砍范围而非赶工**:与其压缩所有需求的质量,不如协商砍掉非核心范围(先上 MVP),或分期交付。
> 4. **争取资源**:若确实是资源问题,带着排好的优先级和影响评估去争取加人或调期。
> 核心:**透明同步 + 重新对齐优先级 + 砍范围而非压质量**。

### 【实战·卓誉·HR】与同事技术文档分歧大,怎么推进达成共识?

**参考答案**:
> 1. **先把分歧点列清楚**,不是各自讲完整方案,而是对齐"我们到底在哪几点上不一致"——很多分歧是误解而非真分歧。
> 2. **用事实而非立场讨论**:每方给出方案的依据(性能要求/可维护性/成本/团队现状),用约束条件说话,不拼嗓门。
> 3. **找共同目标**:回到"这个系统要解决什么问题",用目标倒推方案,容易达成一致。
> 4. **设决策机制**:实在谈不拢,明确决策权归属(谁 owner 谁拍板),并记录 dissenting opinion,事后可复盘。**不追求全员认同,追求有依据的决策 + 记录分歧**。

### 【实战·卓誉·HR】AI agent 时代,程序员的 coding 能力还是核心竞争力吗?

**参考答案**(开放题,给一个有判断的答案):
> coding 能力的**形式**在变,但**核心价值**没变。AI 能写代码,但程序员的核心竞争力从来不是"打字打代码",而是**把模糊需求转化为确定系统**的能力——拆解问题、定义边界、设计架构、权衡取舍、保证可靠性。这些 AI 替代不了。
> 变化的是:**纯实现型的 coding 价值在下降,系统设计 + 工程判断 + 把 AI 用好的能力在上升**。所以核心竞争力的内涵在扩大,不是消失。能把 AI 当杠杆放大自己产出的程序员,会比不用 AI 的更有竞争力。
