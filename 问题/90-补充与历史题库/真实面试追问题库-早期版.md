# 项目一：AI 周报系统

## 第一层：实战已问

### Q1.【卓誉】基于什么模型？一周一人天工时怎么审出来的？怎么计算？

**答案要点**：
- 这是运营保障周报，不是根据 Git、Jira、代码量或 CI 统计员工工时。
- 简历里的 8-10 小时、20 分钟和年省约 50 人天都要先用原始工时、运行记录和观察窗口核验；输入成立后才能做工时估算。
- 错误量、慢 SQL、TPS 等业务指标由确定性 SQL/程序计算，LLM 只组织叙述。具体模型和本人贡献按模型记录与 RACI 填写。

### Q2.【卓誉/安克】这东西不用 LLM 也能做吧？听起来就是个 workflow / 固定模板也行。

**答案要点**：
- 诚实承认：纯数据采集 + 模板填充能做基础周报，**大模型不是必需的**。
- 当前 LLM 价值主要是把已验证的模块结果组织成有重点的叙述。
- 当前没有围绕周报自由追问的对话式 RAG 或 Text-to-SQL；自然语言查数只能作为下一版设计。固定模板确实可以完成基础交付。

### Q3.【Ashley】数据收集清洗是不是 人工→脚本→大模型？数据分析是大模型做的吗？

**答案要点**：
- 前半段工程链路：按业务日期采集运营保障数据，做完整性检查、字段处理和确定性统计；不是采集 Git/Jira/CI 员工活动。
- 后半段 LLM：**不做统计分析**（统计用规则算准数），只把结构化数据**组织成自然语言周报**。
- 分工：**数字必须准用规则算，表达要自然用 LLM 生成**。

### Q4.【安克】大模型介入后模板变了吗？自动化定时？

**答案要点**：
- 模板结构没变（固定板块，稳定习惯），变的是**内容生成方式**——数字仍由脚本统计，文字由 LLM 生成。
- 自动化：每周定时触发，采集→生成→推送。

### Q5.【安克】大模型写 SQL，写了 DROP/DELETE 把表删了怎么拦截？

**答案要点**（多层防护）：
> 当前周报不是 Text-to-SQL。下面是面试官要求扩展设计时的答法，不能说成现有项目能力。

1. **SQL 权限隔离**：给 LLM 的数据库连接用**只读账号**，DDL/DML 在 DB 层拒绝——最硬兜底。
2. **SQL 预校验**：执行前用 SQL parser 解析，白名单只允许 SELECT，DROP/DELETE/UPDATE/ALTER 直接拦。
3. **关键词黑名单**。
4. **沙箱库**：查只读副本或脱敏副本，动不到生产。
- 原则：**永远不信任模型生成的 SQL 直接打生产，权限 + 解析双保险。**

### Q6.【安克】怎么把表名和表描述精确给到模型？

**答案要点**：
- 维护**表元数据（schema 字典）**：表名、字段、字段含义、业务说明，做向量化。
- 用户提问时先检索相关表 schema，把"表名 + 字段说明"作为上下文喂模型，基于精确 schema 生成 SQL。
- **不灌全库 schema**（太大），按 query 相关性召回相关表。

## 第二层：深挖

### Q7.【深挖】某个数据源挂了怎么办？增量采集还是全量？

**答案要点**：
- **增量为主、全量兜底**：平时按时间增量拉，定期（如每月）全量对账。
- 每个数据源有**健康检查 + 重试 + 降级**：失败重试 N 次，仍失败则该数据源本周报缺失字段标注"数据获取异常"，其余正常出，不整体阻塞。
- 原则：**单数据源故障不阻断周报产出，但要显式标注异常**。

### Q8.【深挖】LLM 生成周报，怎么保证数字准确？数字错了是事故。

**答案要点**（"数字与叙述分离"原则）：
1. **所有数字由脚本统计**，LLM 看到的是算好的数字。
2. **LLM 只做叙述组织**，不能改数字。
3. **当前缺口**：现有材料不能证明已自动回比、自动重生成、模板回退或关键指标双算，关键数字仍需人工复核。
4. **下一版**：结构化回填关键值、允许值与单位校验，失败后有限重试和模板回退。

### Q9.【深挖】Text-to-SQL 准确率多少？怎么评估？bad case 怎么收集？

**答案要点**：
- 当前周报没有 Text-to-SQL，因此没有本项目的 Text-to-SQL 准确率、线上用户点踩或生产 Bad Case，不能补百分比。
- 如果下一版建设，评测集应包含 query、授权 Schema、期望结果和安全属性，指标拆成可执行率、结果正确率、越权率和资源预算违规率。
- Bad Case 可从受控测试、灰度反馈和真实 Trace 回流；没有灰度记录时只讲设计，不冒充已有闭环。

### Q10.【深挖】不同角色（老板/员工/PM）看的周报一样吗？

**答案要点**：
- 当前材料只证明统一结构的表格加文字运营保障周报，没有老板、员工、PM 三套模板，也不包含员工任务进度。
- 如果下一版做角色化展示，应由服务端按授权范围选择指标，LLM 只调整叙述详略；同一指标值不能因角色不同而变化。

### Q11.【深挖】怎么评估周报质量？有没有反馈闭环？

**答案要点**：
1. 当前没有按钮、打开率、追问率或完整 Gold Set 已上线的证据，不能用过去式回答。
2. 下一版可用固定历史周回放，评事实正确性、异常覆盖、可读性和人工修改量。
3. 若增加反馈入口，要先定义用户、采样和隐私边界，再把有证据的 Bad Case 纳入回归集。

## 第三层：杀手锏

### Q12.【安克·杀手锏】老板看周报发现销量下滑，问"为什么下滑"——根因分析，能解决吗？让你设计怎么做？

**答案要点**（诚实承认 + 三层设计）：
- **诚实承认**：目前做不到根因分析，只能回答"数据是什么"，回答不了"为什么"。
- 设计三层：
  1. **数据层（现有）**：预定义 SQL 与确定性统计回答“发生了什么”，当前不是 Text-to-SQL。
  2. **归因层（新增核心）**：不让模型猜，用确定性方法——**多维下钻**（地区/品类/渠道/时段）、**对比基线**（历史同期/目标值）、**关联分析**（库存/促销/竞品/流量），缩小候选原因。
  3. **推理 + 验证层**：把"数据事实 + 候选原因"喂模型做**假设推理**，再**回查数据验证假设**，通过才输出，不通过标"待确认"。
- 原则：**归因用确定性方法，模型只做"组织叙述 + 生成可验证假设"，绝不让模型直接编原因**——和"不让模型算数"同一原则。

# 项目二：CodeWiki（AST + GraphRAG 代码图谱）

## 第一层：实战已问

### Q13.【码云】先讲一讲 CodeWiki 的项目架构

**答案要点**（七层）：
1. **仓库接入**：RepoScanner，本地路径/Git URL，文件打 sha256/mtime/git commit time。
2. **AST 结构化**：tree-sitter 多语言，统一产出到 AstSymbol（type/name/signature/imports/calls/references/bases/implements/decorators）。
3. **Code Graph**：GraphBuilder，节点（class/function/method/endpoint/schema）+ 边（contains/defines/imports/calls/references/inherits），边带 confidence/provenance。
4. **社区检测**：Louvain/Leiden 模块度分区，level 0/1/2 层级社区 + 社区摘要。
5. **GraphRAG 检索**：符号 seed → FTS/vector chunk → 图扩展 → context pack（受 token budget 约束）。
6. **Wiki & Ask**：Ask 用 GraphRAG 回答；Wiki 先目录再逐页生成，必须引用 allowed source refs。
7. **产品入口**：FastAPI + React、CLI、MCP server、Lite Mode（项目内本地 sqlite）。
- 一句话：**普通 RAG 以 chunk 为中心，CodeWiki 以 graph 为中心**。

### Q14.【码云】向量库是如何选型的？

**答案要点**：
- **跟随主存储**：SQLite（FTS5 + sqlite-vec）/ PostgreSQL（tsvector + pgvector），不引入独立向量服务（Milvus/Qdrant）。
- **向量是可选**：第一层召回靠符号搜索 + FTS，vector 是语义增强。embedding 需 LLM provider，成本高，做成 `include_embeddings` 可选。
- 理由：本地优先、零外部依赖、FTS 和 vector 同库避免跨库一致性。
- 边界：适合单仓库本地中小规模；多租户 SaaS 该上独立向量库。

### Q15.【码云】涉不涉及向量库的更新和删除？怎么增删改？有没有随机改？

**答案要点**：
- 涉及，但不是"随机改单条向量"，是**跟着代码变更走的批量增量**。
- 更新触发：`IncrementalUpdater` 优先 git diff 找候选文件，兜底 sha256 对比（size+mtime 没变复用旧 hash）。只对 changed/new 重算 embedding。
- 删除：deleted 文件 → 删对应 chunks/graph 节点边/embedding 行。
- **怎么定位原始向量**：靠稳定主键 `chunk_id`（repo_id + file_path + 行范围/hash），不靠向量相似度反查。embedding 行用同 `chunk_id` 做外键，upsert/删按 `chunk_id` 精确。
- 没有手动改单条向量接口——向量无业务语义，单独改只破坏一致性，要改源头（代码/chunk）向量跟着重算。

### Q16.【码云】这样操作有没有遗留问题？

**答案要点**（诚实）：
1. **chunk_id 稳定性 vs 内容变化权衡**：内容 hash 派生则小改全重算（浪费）；行范围派生则插入错位。无完美解。
2. **embedding 模型升级要全量重算**：不同模型向量空间不兼容，按 model 分区但切换是重活。
3. **retrieval trace 未持久化**：`/graphrag/traces/{trace_id}` 还是 `not_persisted_yet`。
4. **启发式解析边可能误**：跨文件 call/reference 是启发式 + 置信度，重名/动态调用会错。

### Q17.【Ashley】讲一下 GraphRAG 在代码生成平台里的流程

**答案要点**（四步）：
1. **离线建图**：AST 解析，函数级切 chunk，节点向量化存向量库，调用/依赖关系存图。
2. **在线检索**：query 向量召回找种子节点。
3. **子图扩展**：从种子沿边扩展（调用它的、它调用的、同文件/同类的）——GraphRAG 核心价值：**补全依赖上下文**。
4. **上下文组装**：召回 + 扩展节点排序，组装进 prompt。

### Q18.【Ashley】chunk 怎么切分？函数级吗？同一个大函数切成两个节点，边怎么定义？

**答案要点**：
- 当前 `ChunkBuilder` 一般按源码节点的起止行生成 Chunk，一个函数节点对应一个 Chunk；没有“超大函数自动二次切分”和顺序边。
- 如果下一版增加二次切块，图上仍保留一个函数 Symbol，多个检索块共享父 `node_id`，顺序只放 Chunk 元数据，调用边仍指向函数。

### Q19.【Ashley】节点和边怎么设计？

**答案要点**：
- **节点**：函数 = 节点，带元数据（所属文件/类/签名/注释）。
- **边**：调用边（最重要）、归属边（属于类/模块）、依赖边（共享数据结构/import）、继承/实现边。边带方向和类型，扩展时按类型给不同权重。

### Q20.【Ashley】⚠️ 检索到代码后，按什么优先级组装上下文？

> 现场答得不够好，面试官提示"prompt 排在前面和最后面的信息特别重要"。

**答案要点**（两维度）：
1. **筛选/排序维度**：向量相关性 + 图距离（离种子几跳）+ 节点类型权重（核心函数 > 工具函数）。
2. **位置摆放维度（利用 "lost in the middle"）**：LLM 对 prompt 开头和结尾最敏感。
   - **最重要信息（目标函数、明确指令）放结尾**（离生成位置最近，注意力最高）。
   - 次重要背景/依赖放开头。
   - 相关性最低的补充放中间。
- 关键词：**"lost in the middle"**——面试官在暗示的知识点。

### Q21.【码云】AST 解析自研的，讲一讲这个自研 AST 解析引擎

**答案要点**（基于真实实现）：
- **底层**：tree-sitter 的 Language/Parser/Query，支持 Python/Java/Go/Rust/C/C++/C#/TS/JS。
- **capture_engine（自研核心）**：`TreeSitterCaptureParser` 用统一语义 capture name 驱动查询，每语言有 `capture_spec`（tree-sitter query + capture name 映射），跑 query 拿 capture 转 `DefinitionRecord`。
- **统一产物 AstSymbol**：所有语言归一化到同一结构，下游 GraphBuilder 不关心语言。
- **augmenter**：每语言一个（python/java/go...），处理语言特有信息（装饰器/implements/export）。
- **并发 + 容错**：ThreadPoolExecutor（默认 min(file,cpu,4)），捕获 SyntaxError 记录到 parse_errors 继续跑。
- 设计哲学：**统一性比单语言精确性重要**。

### Q22.【码云】变量、函数、全局变量、class 类，是在 AST 里存还是在数据库里存？

**答案要点**：
- **两层都存，职责不同**：
  - **AST 层（瞬时）**：解析产生 AstSymbol 列表，中间产物，不持久化原始 AST。
  - **数据库层（持久化）**：GraphBuilder 把 AstSymbol 转图节点存库。`code_node`（file/config/class/function/method/endpoint/schema）+ `code_edge`（contains/defines/imports/calls/...）+ `code_chunk`（源码片段，FTS + 可选 embedding）+ `ast_cache`（缓存解析结果，增量复用）。
- **全局变量**：没有显式 def 节点的，通过 reference/assignment 捕获，作 reference 边或 file-level symbol 存，不单独建节点（避免图膨胀）。
- **成员变量**归 class 节点，**局部变量**不持久化（作用域太局部）。

### Q23.【码云】为什么会选择 GraphRAG？

**答案要点**（三个痛点）：
1. **代码含义依赖结构上下文**：普通 RAG 按文本相似度召回孤立 chunk，漏掉依赖关系。GraphRAG 沿图扩展补全依赖。
2. **代码大量专有名词**：需关键词精确命中（FTS）+ 结构扩展（图）。纯向量不稳，纯 FTS 不懂结构。
3. **Wiki 生成需系统化组织**：社区摘要 + 图边提供模块级视图，普通 RAG 给不了。
- 诚实边界：单文件内简单任务两者差不多，增益集中在跨模块。

### Q24.【码云】⚠️ GraphRAG 存在 token 爆炸问题，怎么解决？

> 现场说"没了解过"，必须补。

**答案要点**：
- 根因：图扩展不加约束，沿 calls/references 多跳扩展子图指数膨胀。
- 控制机制：
  1. **token budget 硬约束**：`graphrag_context_token_budget`（默认 8000）+ `graphrag_max_source_chunks`，超预算丢。
  2. **扩展深度限制**：最大跳数控制，避免无限 BFS。
  3. **社区摘要代替全量子图**：用 `community_summaries` 代表模块，token 远小于原始节点。
  4. **噪声过滤**：低置信度边、external 节点不扩展。
  5. **分层检索**：先社区级（粗）定位，再模块内符号级（细）。
  6. **context pack 结构化**：source chunks + nodes/edges + community summaries，每类独立预算。

### Q25.【码云】怎么解决代码多版本问题？多个分支、提交、tag？查一个月前的代码版本有解决吗？

**答案要点**（诚实承认 + 方案）：
- **当前没解决**：图是"当前工作区快照"，查历史版本要 checkout 重新 analyze。repo_id 用路径 SHA1 隔离，commit_hash 记录当前 HEAD，增量走 git diff。
- 设计方向（未实现）：① 按 commit 存多快照，节点带 commit_hash 维度；② git blame/history 集成；③ 时间旅行查询，保留关键 tag 快照图做图 diff。
- 诚实：当前聚焦"理解当前代码"，历史版本是明确待补。

### Q26.【卓誉】跨模块代码理解现在还有人在用吗？

**答案要点**：如实说使用情况。覆盖了哪些场景、谁在用、用了多久；没继续用就说"验证完核心能力后转入下一阶段"——比硬撑"在用"强。

### Q27.【卓誉】⚠️ 自研 AST 解析引擎，对标 Codex/Cursor，核心竞争力在哪？

**答案要点**（诚实 + 差异化矩阵）：
- 诚实：**通用场景打不过 Codex/Cursor**——它们 codebase indexing 强、开箱即用。
- 差异化：

| 维度 | Codex/Cursor | CodeWiki |
|------|-------------|----------|
| 相似度检索 | 强 | 持平 |
| **跨模块依赖召回** | 依赖运行时探索，可能漏 | 图结构扩展，可追溯但受静态解析边界限制 |
| 大仓库成本 | 每次重扫，贵 | 离线建图，在线检索，省 |
| 增量更新 | 按具体产品版本核对 | 扫描/解析复用；图与社区后段仍可能重建 |
| 通用易用性 | 极强 | 需建图，有门槛 |

- 核心论点：**代码调用关系是确定性的，用 AST 静态解析建图比让模型猜依赖更准更省**。定位是"超大仓库 + 跨模块精确依赖 + 企业定制"细分场景补强，不是替代。

## 第二层：深挖

### Q28.【深挖】GraphRAG vs 普通 RAG，有量化数据吗？

**答案要点**：
- 诚实：如果没数据，说"定性验证为主，正在建评测集"。
- 评测方式：同一批跨模块任务，对比"无图谱 RAG"vs"GraphRAG"，看召回完整度/修改正确率。
- 结论只能由固定任务集给出。当前性能 Benchmark 不能证明 GraphRAG 质量显著提升；没有对照实验时只讲机制假设。

### Q29.【深挖】没注释时节点信息哪来的？

**答案要点**：
- 来自**代码本身的结构语义**：函数名、参数名、返回类型、调用的函数、被谁调用、所属类/模块。
- 必要时**用 LLM 给无注释函数生成摘要**作为补充（离线一次性生成 + 缓存），但标注为"模型生成摘要"，与确定性结构信息区分置信度。

### Q30.【深挖】图存储用什么？向量库和图怎么结合？

**答案要点**：
- 图存关系库（SQLite/PG 的 code_node/code_edge 表），不一定要图数据库（Neo4j）——节点边规模在关系库够用，且和 chunks/FTS 同库事务一致。
- 向量库存节点向量（函数代码/signature 的 embedding）。
- 结合：节点 ID 双向关联。检索先向量召回种子 → 拿节点 ID 去图扩展子图 → 子图节点回向量库取内容。**向量库找"相关"，图找"关联"**。

### Q31.【深挖】增量更新怎么做？和 Claude Code init markdown 比优势？

**答案要点**：
- 增量：优先 git diff 找候选文件，兜底 sha256 对比 changed/new/deleted/unchanged。只解析 changed/new，unchanged 复用缓存 symbols；合并后图和社区仍会重建，更新 chunks 后标记受影响 Wiki 页面 stale。
- vs Claude Code init markdown：① **确定性 vs 概率性**（AST 精确 vs 模型总结可能漏/错）；② **增量更新 vs 全量重扫**（markdown 怎么增量？要么过期要么重 init）；③ **检索精度**（结构化检索 vs 自由文本语义搜）；④ **规模**（大仓库 init 成本极高）。
- 诚实：Claude Code init 适合小仓库快速上手，GraphRAG 适合大仓库跨模块工程化，分层互补。

### Q32.【深挖】如果模型够强，以后能自己扫准了，GraphRAG 还有意义吗？

**答案要点**：
- 即使模型再强，两个根本约束不变：① **成本**——每次重扫大仓库 token 成本远高于查一次图；② **确定性**——工程场景"可能对"和"一定对"是两种东西。GraphRAG 把确定性交给工程，语义理解交给模型，是更稳的分工。

### Q33.【深挖】这其实就是做了个 AST 解析吧？跟 Claude Code 插件的 MCP（语法解析）有什么区别？

**答案要点**：
- 现成 MCP/插件做**单文件/单语言语法解析**，给模型"这个文件的符号表/定义位置"，本质是**定位工具**。
- CodeWiki 做的是**跨文件、跨模块代码知识图谱**：整个仓库的调用关系、依赖关系、数据流建成图。检索时不是"找一个定义"而是"找到一段代码 + 所有上下游依赖"。
- **单点解析 vs 全局图谱**。

## 第三层：杀手锏

### Q34.【安克·生死线】⚠️ 我直接用 Claude Code 对仓库做 init，生成 markdown 长期记忆，跟你 GraphRAG MCP 区别多大？模型自己抓重点做长期记忆，是不是比做成 GraphRAG 更优？

> Dennis 明确表达"我理解模型自己抓重点做长期记忆可能更优"，必须有力反驳。

**答案要点**（四个优势 + 诚实定位）：
1. **结构事实 vs 模型总结**：AST 能确定性提取符号、导入和继承等事实；调用/引用边仍有启发式误差，不能说完全精确不漏。
2. **复用边界**：CodeWiki 能复用未变化文件的扫描/解析结果，并重生成脏页面；图和社区后段仍可能重建。
3. **检索精度**：markdown 自由文本，模型从大段文本"自己找"靠语义相似度容易漏。GraphRAG 结构化检索，按图精确扩展，召回准可解释。
4. **规模**：大仓库 init 一次性扫成本极高，markdown 膨胀后检索质量下降；GraphRAG 离线建图在线检索，规模可扩展。
- 公平地说：Claude Code init 适合**小仓库、快速上手、不需要精确依赖**；GraphRAG 适合**大仓库、跨模块、需要精确依赖**。分层互补，不是替代。

### Q35.【深挖】这套东西最终有没有提升 agent 效果？怎么证明？

**答案要点**：
- **端到端评测**：同一批代码修改任务，分别用"无图谱 RAG"和"GraphRAG"给 agent，对比修改完整性和正确率。
- **真实使用信号**：只有存在接入记录和统计时，才谈返工率或人工修正次数。
- **案例**：使用有 Trace 的真实任务；没有案例就说评测设计，不编“模型漏改后被图补全”的故事。
- 诚实：如果还没量化数据，说"定性验证为主，正在建评测集"——比编数据强。

# 项目三：Agent 长期记忆 + 上下文压缩系统

## 第一层：实战已问

### Q36.【Ashley/京东】是你一个人做的吗？/ 独立负责具体代表什么？end-to-end 还是有带人？

**答案要点**（统一框架，别再让"独立"被误解）：
- 不能先把“独立负责”定义成技术 end-to-end。按需求、设计、编码、联调、测试、发布和维护逐段填写 RACI。
- 我亲自负责 **[填可由代码、评审或工单证明的模块]**；同事协作 **[填写]**；最终决策、排期、测试和发布分别由 **[填写真实角色]** 负责。

### Q37.【Ashley】四层设计分别是什么？

**答案要点**（基于真实实现，注意 L1/L2 命名可能和你文档略有差异，按实际）：
- **L0 — 原始对话层**：完整原始对话记录，不加工，兜底溯源。
- **L1 — 原子记忆层**：从增量消息抽取 `persona / episodic / instruction` 三类记录，保留 `source_message_ids`；它不是完整属性事实库。
- **L2 — 场景归纳层**：把零散事实按主题/场景串联组织。
- **L3 — 长期画像层**：跨会话沉淀的稳定偏好/风格/SOP，最抽象最稳定。
- 越往上抽象粒度越高，但不是同一条事实按置信度逐层晋升；长期记忆和 Tool Result Offload 也是两条独立链路。
- ⚠️ 注意：你的真实实现里 L1 是"结构化事实"、L2 是"场景层"，和某些通用设计（L1=会话摘要）不同，**按你实际讲**。

### Q38.【Ashley】记忆系统是跨会话的吗？什么时候存？怎么存？

**答案要点**：
- 当前是 local-first、单用户口径；L0 保存对话，L1/L2/L3 由各自队列、游标、会话计数和时间/事件条件异步处理，不是简单“达到 token 阈值就逐层晋升”。
- 新会话稳定加载 Persona 与 Scene Navigation，相关 L1 按 Query 召回；L2 正文沿导航按需读取，需要原话时再查 L0。

### Q39.【Ashley】⚠️ 存的时候事实冲突/反事实怎么办？覆盖还是纠错？

> 你当场答"覆盖"，要升级。

**答案要点**（当前能力与下一版分开）：
- 当前入库前会召回相似 L1 候选，再由模型选择 `store / skip / update / merge`，并保留 L0 与 `source_message_ids` 作为来源入口。
- 当前没有实体-属性 Schema、可变/不可变分类、事实置信度、旧值自动过期或 Supersede 状态机，不能说已经按时间安全覆盖。
- 下一版才会显式建模实体、属性、作用域、有效时间和版本关系；无法判断时并存或请求用户确认。

### Q40.【Ashley·核心】⚠️ 大模型抽取判断错误（幻觉）怎么办？怎么保证长期记忆准确？

**答案要点**：
1. 当前先保留 L0 原始消息，L1 带 `source_message_ids`，写入时结合相似候选做四动作判断；当前用户明确表达优先于召回记忆。
2. `source_message_ids` 不是逐字 Span，当前也没有事实置信度、候选区、多次确认晋升、完整失效或用户纠错闭环。
3. 下一版才补来源存在性与蕴含校验、独立 evidence confidence、版本关系、用户纠错和错误召回评测。当前只能说“有追查入口”，不能说“已保证准确”。

### Q41.【Ashley】怎么取？什么时候加载 L0/L1/L2/L3？

**答案要点**（由导航到证据、按需下钻）：
- 稳定上下文放 L3 Persona 与 Scene Navigation，不是把全部 L2 正文常驻。
- 当前 Query 相关的少量 L1 通过关键词、向量或 Hybrid Recall 注入。
- 需要场景细节时沿导航读取 L2 正文，核验原话时再查 L0。

### Q42.【安克】长期记忆和上下文压缩是 for 内部自研 agent runtime，还是基于已有 runtime 二开？

**答案要点**：
- 设计是 host-neutral core 加 Adapter：OpenClaw 可走进程内 Hook，Hermes 类宿主走 HTTP Gateway/Sidecar，也有 Standalone 入口。
- 这证明多 Host 技术适配能力，不等于任意 Runtime 零改动接入，也不证明多个业务渠道已经投产。

### Q43.【安克】Copilot 自己就有上下文压缩，你们的压缩和它有什么区别？

**答案要点**：
- 不猜 Copilot 某个版本内部一定怎样实现，只比较可验证能力。
- 当前项目把长期记忆与短期 Tool Result Offload 分开；大工具结果外移到 refs，Prompt 保留摘要、`node_id` 和 `result_ref`，需要时可下钻原文。
- Mermaid 画布负责任务状态与证据导航，真正释放窗口的是 Tool Result 外移和消息替换；不能把两者都叫“压缩”。

### Q44.【安克】对接一个长上下文模型时，压缩策略怎么设计？到多少比例触发？

**答案要点**（多触发点 + 分层）：
1. 先从真实模型 Metadata/Gateway 获取输入上限，扣除 System、Tools、MMD 和最大输出预留；不能把某个模型名和窗口按印象写死。
2. 当前 Offload 有 mild/aggressive/emergency 工程阈值，但必须随模型窗口重算；接近阈值时用精确 Tokenizer，远离阈值才用快速估算。
3. 优先外移低价值大 Tool Result，保护最近用户消息、System 和 Tool Pair；更激进删除是有损降级，仍保留 refs 下钻路径。

### Q45.【卓誉】系统是否投产覆盖多个业务渠道？以什么形式接入？

**答案要点**：
- 技术上已有 Hook、HTTP Gateway/Sidecar 和 Standalone 等 Host 形态；真实业务入口、用户、请求量和维护人必须从接入记录填写。
- 当前总体仍是 local-first、单用户口径，`X-User-Id` 等路由键不是认证凭证，不能说已经完成多租户隔离或多个渠道投产。

### Q46.【卓誉】做这个时有没有参考业界方案？看过 CoCo / 淘宝编码源码吗？跟 CoCo 比有哪些亮点？

**答案要点**：
- 本人实际读过的论文、文档和源码是 **[填写来源、版本和深度]**；没读过 CoCo/淘宝编码源码就直接说没有。
- 当前可证明的项目特点是长期记忆与 Tool Result Offload 分成两条链，并通过 L0、source IDs、result refs 和任务图保留证据路径。
- 事实置信度、时序冲突、多租户和硬删除仍不完整，不能把下一版治理包装成领先亮点。

### Q47.【码云】结构化记忆和非结构化记忆，都怎么更新删除？有没有删除？

**答案要点**：
- 当前有记录级存取、相似候选四动作和部分保留期清理，但没有属性级冲突状态、自动降权归档、冷热存储或全链路“被遗忘权”闭环。
- 删除 L0 不会自动证明所有派生 L1/L2/L3、向量、缓存、备份和日志都已级联删除。
- 下一版才设计幂等删除任务、停止召回、派生资产清理、Persona/Scene 重建和审计结果；不能说已经投产。

### Q48.【京东】详细描述这款产品的整个架构形态，为什么这样设计，有什么优缺点？

**答案要点**（基于真实实现）：
- **架构**：宿主无关内核（TdaiCore）+ 两条链路：
  - **长期记忆链路**：L0 原始消息、L1 原子记忆、L2 Scene、L3 Persona 各有不同抽象职责，不是按事实置信度逐层晋升。
  - **短期上下文压缩链路**：Context Offload（工具日志卸载，留摘要+索引）+ Mermaid 任务画布（任务状态结构化）。
  - **后台调度器**（pipeline-manager）：按各层队列、游标和触发条件异步处理。
  - **混合召回**（Hybrid RRF）：本地后端组合 FTS/BM25 与可选向量候选；不同 Store 能力不同，不存在统一的“向量+BM25+实体结构”三路实现。
- **rationale**：① 宿主无关；② 不同抽象粒度分层；③ 关键词与语义候选互补；④ Offload 保留 refs，热路径有损但证据可下钻。
- **优缺点**（诚实）：
  - 优点：跨会话连续性、证据下钻、上下文压力可控、宿主无关。
  - 缺点：复杂度高、异步更新有窗口、混合召回仍需评测，事实置信度/时序冲突/多租户/删除传播不完整。

## 第二层：深挖

### Q49.【深挖】四层怎样调度？是不是事实按 L0→L1→L2→L3 晋升？

**答案要点**（事件驱动 + 阈值触发）：
- L0 持久化原始消息；L1 从增量消息抽原子记忆；L2 按主题组织 L1；L3 基于更高层输入更新 Persona。
- 各层通过会话计数、时间/事件条件、串行队列、Cursor 和 Checkpoint 调度，不是同一事实按置信度自动晋升。
- 当前没有低置信候选区或多次出现自动晋升规则。

### Q50.【深挖】记忆不能无限存，有"遗忘"机制吗？怎么淘汰？

**答案要点**：
- 当前没有基于有效期、访问频次、冲突状态的完整自动降权和冷热归档机制，也没有派生记忆级联删除闭环。
- Offload refs 有保留期清理，不等于长期记忆已经实现“遗忘”。
- 下一版才按事实类型、有效时间、访问证据和合规删除要求设计降权、归档与重建。

### Q51.【深挖】记忆检索怎么和当前 query 相关？纯向量召回够吗？

**答案要点**：
- 当前本地后端主要用 FTS/BM25 与可选向量候选，再按同一 Record ID 用 RRF 融合；Embedding 不可用时可以降级 FTS。
- 当前没有统一实体结构索引和时间衰减加权，L2 正文也不是每轮随 L1 一起 Top-K 注入。
- Persona 与 Scene Navigation 放稳定上下文，相关 L1 按 Query 召回，L2/L0 按需下钻。

### Q52.【深挖】多用户记忆怎么隔离？A 的记忆绝不能给 B。

**答案要点**（存储层硬隔离）：
1. **用户 ID 作为分区键**：记忆按 user_id 强制分区，检索必带 user_id。
2. **向量库命名空间隔离**：不同用户不同 namespace/collection，物理隔离。
3. **接入层校验**：从 session 拿身份，不允许前端传 user_id（防伪造）。
4. **审计**：跨用户记忆访问打告警。
- 原则和 SQL 权限隔离一样：**隔离在工程层兜死，不信任上层逻辑**。

### Q53.【深挖】记忆里存了用户敏感数据怎么办？隐私怎么处理？

**答案要点**：
1. **入库前脱敏**：敏感字段（身份证/手机/密码/密钥）脱敏/掩码。
2. **分级存储**：高敏感单独加密，访问需鉴权。
3. **可擦除**：合规要求删除时按 user_id 全链路删（L0~L3 + 向量索引），满足"被遗忘权"。
4. **不出域**：记忆数据不进外部模型训练，本地/私有化抽取。
- 原则：**记忆系统是用户数据托管者，合规和可擦除是底线**。

### Q54.【深挖】上下文压缩是有损还是无损？信息丢失怎么衡量？

**答案要点**：
- **有损**，压缩就是取舍。
- 应对：①**保留优先级**（近期 > 关键事实 > 摘要 > 细节）；②**信息损失衡量**——用"压缩后回溯能力"评估，建回溯评测集，压缩前后对比回答正确率；③**兜底**——L0 原始不删只不常加载，需要时下钻，"热路径有损、冷路径可还原"。

## 第三层：杀手锏

### Q55.【深挖·最深】⚠️ 压缩错了会不会"幻觉放大"——压缩层一错，后面全错？

**答案要点**（记忆系统最深的坑）：
- 会，这是最大风险。压缩层（尤其 LLM 做摘要/抽取）一旦引入错误，会被当"事实"反复召回，比单轮幻觉危害大得多——**单轮幻觉一次性，记忆幻觉被反复放大**。
- 当前防线是保留 L0、让 L1 带 `source_message_ids`、写入前结合相似候选做四动作判断；这只提供追查入口，不能保证摘要正确。
- 当前没有逐字 Span、事实置信度、候选区、定期蕴含校验或多模型交叉验证。
- 下一版才补来源存在性与蕴含校验、独立 evidence confidence、用户纠错和错误召回评测；不能写成当前五层防护。

### Q58.【码云】聊一聊你理解的提示词工程

**答案要点**：
- 不是"写漂亮咒语"，是**用结构化方式固定任务约束、上下文、输出格式，让模型输出可控可复现**。
- 五层：①角色与任务定义；②上下文注入（检索到的事实，非凭记忆）；③输出格式约束（JSON/source ref/Mermaid placeholder）；④few-shot 示例；⑤校验与修复回路（不合法回灌 errors 让模型修）。
- CodeWiki 体现：Wiki 页面生成必须返回 JSON、引用 allowed source refs、过 Markdown/citation/diagram 校验，失败进 repair。
- 核心：**用约束把概率模型变成工程上可控的组件**。

### Q59.【码云】⚠️ 大模型的幻觉问题是怎么产生的？

> 码云面试被指出"理解不准确"，必须从机制层讲。

**答案要点**（从模型机制讲）：
- 幻觉本质：**大模型是概率生成模型，不是检索系统**——生成"当前上下文下概率最高的 token 序列"，不是"事实正确的 token 序列"。
- 产生原因：
  1. **训练目标决定它是"流畅"而非"正确"**：next-token prediction，优化"像人话、连贯"不优化"符合事实"。
  2. **知识存储是参数化的、隐式的**：知识压缩进权重，没有"知识库+检索"边界，问事实是从权重"回忆"概率分布，回忆不准就是幻觉。
  3. **训练数据噪声**：语料有错误/过时/虚构内容，模型分不清事实还是虚构陈述。
  4. **上下文冲突/知识截止**：训练有截止日期，问训练后的事实没有，但生成本能驱使它"编一个看起来合理"的答案，不说"我不知道"。强上下文里用户暗示错误前提，模型会顺从（sycophancy）。
  5. **长尾知识采样不足**：高频知识记得准，长尾/冷门权重表示模糊，容易张冠李戴。
  6. **解码策略**：高 temperature/top-p 增加随机性放大幻觉。
- 一句话：**幻觉不是 bug，是概率生成模型的固有特性——它优化"说得像"不优化"说得对"**。消除不可能，靠外部约束（RAG/引用校验/工具验证）压到可控。

### Q60.【码云】如何防治模型编造不存在的信息/幻觉？

**答案要点**（结合 CodeWiki 真实防幻觉）：
1. **RAG 提供事实**：Ask/Wiki 先走 GraphRAG，source chunks/graph facts/community summaries 作事实输入。
2. **source refs 硬约束**：Wiki 页面必须引用 allowed refs 范围内的 source_refs，校验失败进 repair。
3. **citation 校验**：Markdown citation marker 必须对应合法 source ref。
4. **Mermaid 服务端生成**：不让 LLM 画图（画图极易幻觉），LLM 只放 placeholder，Mermaid 基于图事实服务端生成 + 校验。
5. **LLM 缓存 + prompt version**：`llm_run` 表记录 prompt version/model/token/response，既缓存又审计。
6. **校验修复回路**：目录生成最多重试 3 次，errors 回灌修复。
7. **诚实边界标注**：不确定的标置信度，不强行编。
- 通用：降低 temperature、system prompt 显式约束"无依据回答未找到"、工具验证、多路交叉验证。
- 原则：**把模型当"表达引擎"不当"知识库"——事实从外部给，输出被外部校验**。

### Q61.【码云】了解不了解 harness 和 loop engineer？

**答案要点**（概念开放，给工程化解读）：
- **Harness**：包裹模型的外层工程框架——模型只会输入输出，harness 提供工具调用循环、上下文管理、状态持久化、错误重试、结果校验。Claude Code/Codex CLI 本身是 coding harness。
- **Loop / Loop Engineer**：社区概念无定论。理解为**让 agent 任务闭环**——执行→观察→反馈→修正→再执行，直到收敛或满足终止条件。Loop engineer 设计闭环：每轮喂什么上下文、何时终止、失败怎么回退、怎么压缩历史。
- 诚实：Claude Code 当前 loop 是"tool call 驱动的隐式循环"（有 tool call 就继续，没有就结束），深度闭环设计还在早期。概念在演进，跟进不下死定义。

### Q62.【码云】项目有没有了解 LangGraph？图中状态怎么设计？

**答案要点**：
- 当前没用 LangGraph，也没有等价的 Durable Graph Runtime。Wiki 生成由服务层显式编排，保存 Job、Page 状态和已有产物，可为页面级重试与复用提供依据；不能说 `plan→evidence→generate→validate→repair→save_page` 每个任意节点都落了 Checkpoint、进程中断后能精确续跑。
- 如果用 LangGraph 重实现：任务、页面队列、当前页、Allowed Source Refs、Validation Errors、Retry Count 和审批结果才会成为 State，各阶段成为 Node，`validate→repair` 是条件回环，并补持久 Checkpointer、幂等和副作用账本。当前/下一版边界见 [框架专项 Q73-Q75](../04-AI-Agent通用/LangChain-LangGraph与主流AI框架-面试题.md)。

### Q63.【京东】设计一个 AI 模型路由引擎架构，三个需求：①100ms 内路由决策；②故障 500ms 内 failover；③可审计。

**答案要点**（完整设计，见京东面试整理，核心）：
- **架构**：Router Core（Feature Extractor→Decision Engine→Model Selector）+ Executor（Model Caller + Health Monitor + Failover Controller）+ Audit Log。决策上下文常驻 Redis。
- **数据流**：请求→Gateway→特征提取（缓存）→决策引擎（规则+轻量ML打分，纯内存<1ms）→选模型+预排 fallback list→Executor 调用→故障触发 Failover→审计异步写。
- **100ms 决策**：决策不调 LLM 不查 DB，规则+GBDT 打分纯内存+Redis，整链路<10ms。
- **500ms failover**：预排 fallback list（不重新决策）+ 熔断器（内存查<1ms）+ 硬超时（300ms 无响应判故障）+ 健康信号预热。检测<300ms + 切换<50ms ≈ <500ms。
- **可审计**：每次路由落审计日志（task特征/候选/选中/原因/版本/时间/user_id）+ failover 单独记 + 异步写 ES/ClickHouse 不阻塞 + trace_id 用户可见 + append-only 不可篡改。

### Q64.【京东·追问】两个模型延迟成本几乎一样，怎么决策？

**答案要点**：
- 不能用延迟成本做 tie-breaker，引入其他维度按优先级：
  1. **实时质量信号**（最重要）：在线表现/用户反馈/抽样评分。
  2. **健康度/负载**：当前负载低、p99 稳的优先。
  3. **能力匹配度**：按 task_type 细分（A 擅长代码 B 擅长推理）。
  4. **流量分散/容灾**：故意分流到两个模型，一个挂了另一个能承接。
  5. **一致性 hash**：以上都分不出，按 user_id/session_id 固定路由保证体验一致。
- 原则：难分时优先**体验一致性 + 容灾分散**，把"两模型差不多"当机会做流量分担。

### Q65.【京东·追问·分水岭】⚠️ 怎么判断哪个模型效果更好？路由时任务还没执行，你怎么知道效果？

**答案要点**（事前决策 vs 事后信号的悖论）：
- 用**历史信号 + 在线反馈**，不等这次执行完：
  1. **离线质量基线**：每模型在各类任务的预先评分（benchmark+人工标注+历史线上）。
  2. **在线反馈信号**：①显式（点踩/点赞、采纳/拒绝）；②隐式（重新提问/中断/停留/复制）；③下游（agent 后续步骤是否成功）。
  3. **反馈回流更新质量分**：multi-armed bandit 思路（exploration vs exploitation），某模型某类任务反馈变差则降分。
  4. **探索机制**：留小比例流量 exploration 随机选非 top-1，防评分过期。
  5. **A/B + 影子评估**：新模型先影子跑对比输出，积累信号再放量。
- 核心：**事前用历史基线初判，事后用在线反馈修正，exploration 持续校准**。

### Q66.【京东·追问】模型抖动，要预先替换，怎么设计？

**答案要点**（抖动 ≠ 硬故障，要提前识别趋势）：
1. **实时健康指标采集**：成功率/p50/p99 延迟/错误率/超时率，滑动窗口算。
2. **抖动判定**：p99 连续 N 窗口超阈值 / 成功率滑动下降 / 错误率突增超 baseline+3σ。满足即判"抖动中"，不等完全失败。
3. **主动降权而非立即熔断**：抖动期把路由权重降（100%→20%），流量优先导健康模型，保留小流量探测——避免误判踢掉好模型。
4. **预热备用**：检测到抖动提前把 fallback list 下一个预热（发探测请求确认健康），主模型恶化秒级切过去。
5. **半开探测恢复**：降权后每隔一段时间放少量流量探测，连续成功 N 次才恢复权重。
6. **告警 + 人工兜底**：持续抖动超阈值告警。
- 原则：**抖动靠趋势预判 + 降权缓冲，不是等硬故障才 failover**。

# 开放题 / 趋势 / 软素质

### Q68.【码云】从 LLM → workflow → OpenCloud/Claude Code 这些工具，谈谈发展趋势

**答案要点**：
- 演进线：**单次推理 → 编排 → 自主智能体**，每层把更多"人的判断"交给工程框架。
  1. LLM 层：单次 prompt-response，无状态无工具无记忆。
  2. Workflow 层：多 LLM 调用+工具+规则编排成确定性流程，人定义流程模型填空。
  3. Agent 层：把"决定下一步做什么"也交给模型，harness 提供工具协议/上下文/状态。
  4. 平台化：agent+记忆+知识库+评测+权限打包服务团队。
- 趋势：①从模型为中心转向工程框架为中心（差异化在 harness/记忆/工具/上下文管理）；②从给人看的代码转向给 AI 看的表示；③记忆与长期上下文成核心；④评测与可信（SWE-bench）。
- 诚实：还在早期，Claude Code 也是老编辑器跑新引擎，终局形态未定。

### Q69.【码云】下一个风口模型/框架朝什么发展？

**答案要点**（带不确定性）：
1. 长上下文 + 持久记忆原生支持（hot/cold 分离）。
2. 多模态 agent（视觉/操作/语音，coding agent 看截图调试）。
3. Agent 协议标准化（MCP 之于 agent 如 HTTP 之于 web）。
4. 从"生成代码"到"维护系统"（长期维护 codebase，需记忆和图谱）。
5. 小模型 + 强框架（够用小模型 + 精强工程框架完成大部分任务）。
6. 可验证性（输出能被自动验证）。
- 自己押注：**记忆治理 + 上下文工程**（模型同质化后这层是差异化）。

### Q70.【卓誉·HR】多需求都紧急、人力不够、有 DELAY 风险，怎么处理？

**答案要点**：
1. **不闷头扛**：第一时间向上+需求方同步风险，别等 deadline 才说。
2. **重新排序**：拉需求方对齐"紧急"真实定义，按**业务影响 × 时间紧迫度**排，不是谁催得凶谁先。
3. **砍范围而非赶工**：协商砍非核心先上 MVP 或分期。
4. **争取资源**：带排好的优先级和影响评估去谈加人/调期。
- 核心：**透明同步 + 重新对齐优先级 + 砍范围而非压质量**。

### Q71.【卓誉·HR】和同事技术文档分歧大，怎么推进达成共识？

**答案要点**：
1. **先把分歧点列清楚**，对齐"到底在哪几点不一致"——很多是误解。
2. **用事实而非立场**：每方给方案依据（性能/可维护性/成本/现状），用约束说话。
3. **找共同目标**：回到"系统要解决什么问题"，用目标倒推。
4. **设决策机制**：谈不拢明确决策权归属（谁 owner 谁拍板），记录 dissenting opinion 可复盘。
- 原则：**不追求全员认同，追求有依据的决策 + 记录分歧**。民主讨论集中决策。

### Q72.【卓誉·HR】AI agent 时代，程序员 coding 能力还是核心竞争力吗？

**答案要点**：
- coding 形式在变，核心价值没变。程序员核心竞争力从来不是"打字打代码"，而是**把模糊需求转化为确定系统**——拆解问题、定义边界、设计架构、权衡取舍、保证可靠性。
- 变化：**纯实现型 coding 价值下降，系统设计 + 工程判断 + 把 AI 用好的能力上升**。内涵扩大不是消失。
- 体感：vibe coding 让"能写代码"贬值，让"能判断代码好坏、能定义边界"升值。

# 横向复盘：7 场面试暴露的共性问题

1. **"独立负责"表述被 4 场追问**（卓誉/Abound/京东/Ashley）——按项目和阶段回答真实 RACI，不能统一套"技术 end-to-end + PM 管流程"模板。
2. **对标竞品拿不出量化数据**（卓誉/安克）——CodeWiki 必须建 benchmark，哪怕小规模也要有数。
3. **幻觉机制理解不准**（码云）——从概率生成 + 参数化知识存储机制层重学。
4. **生产级稳定性回答不足**（京东路由引擎抖动题）——有真实故障就带工单、日志和复盘；没有就明确按故障演练或设计题回答。
5. **项目"使用情况"答得虚**（卓誉/趣搭）——只准备有口径、窗口和来源的脱敏数字；没有记录就不报。
6. **CoCo/淘宝编码源码没看**（卓誉）——至少读公开设计，能讲对标差异。
7. **英文需练**（Abound）——2 分钟自我介绍练到自然流畅。

这些问题是**跨场复现**的，说明不是偶发，是系统性短板。下来按优先级逐个补，能显著提升后续面试通过率。
