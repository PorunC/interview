## W01：项目解决什么问题，价值和模型是什么？

这是网联运营保障周报，不是统计员工 Git/Jira 进度。原流程每周从多个系统取错误日志、慢 SQL、大事务、失败交易、TPS 和响应时间，再人工核对、分析和组装。系统把它改成自动日批，价值首先来自自动采集、校验和确定性统计；LLM 只减少逐模块阅读与写说明的成本。

“约 50 人天”必须说明是改造前后年度人工投入差值的估算，不是财务审计。具体模型、上线时间、当前是否仍使用均为 **[待本人确认]**，不要用模型名字代替系统设计。

## W02：数据源、格式和完整链路是什么？

当前材料确认的数据源包括北斗、园方、AN1LOG、CKTRANS、CKSLOWSQL、FTCLOG 等业务、交易和日志系统。外部响应可以是 JSON、表格或日志，但进入分析前必须归一成带 `source、business_date、metric、value、status` 的内部结构。

链路是：按业务日期采集 -> 清洗落表 -> 七天完整性 Gate -> 各模块确定性统计 -> LLM 分段解读 -> 固定模板组装表格加文本 -> 内部消息推送。不同来源可以给出相关性线索，但当前没有因果图和自动实验，不能说成已经证明根因。

## W03：API 不稳定、历史补拉和幂等怎么做？

限流应放在连接器级共享 token bucket；只对超时、429 和可恢复 5xx 重试，遵守 `Retry-After`，使用有上限的指数退避加 jitter。采集任务以原始数据窗口为主键，不以补跑日期为主键。

幂等依赖稳定业务键和唯一约束，例如 `source_id + window_start + metric_key`，写入用事务性 upsert。`pending/success` 只是状态，不等于幂等。当前实现每天回看近 15 天 Pending 数据；“租约、`next_retry_at`、死信、输入版本和自动失效重算”是更完整的下一版设计。

## W04：如何验证数据准确？

准确性分三层：采集层核对时区、分页、行数、唯一键和源端总量；指标层用固定输入/期望输出做单测，并与历史人工报表并行核对；生成层把模型输出中的数字和 `evidence_id` 回查事实表，不一致就拒绝该段并回退模板。

上线后持续看缺失率、迟到率、重复率、指标差异和 LLM 校验失败率。使用 NumPy、Python 或“不让 LLM 算数”本身都不是准确性证明。

## W05：LLM 如何分段，模板是否变化？

按周报语义章节和 Token Budget 分段，例如资源、调用链、慢 SQL和长事务。每段输入是已验证指标、基线、阈值和证据 ID，模型按固定 Schema 输出摘要、异常和引用。程序负责聚合数字与最终章节，模型不能在 Reduce 阶段重新计算指标。

大模型加入后可以让异常说明随数据变化，但最终表格和章节骨架仍是确定性模板。分段的价值是控制上下文、隔离失败、单独重试和审计，不是简单把文本平均切块。

## W06：没有 LLM 能不能做，项目现在还有没有价值？

可以。固定采集、规则统计和模板足以完成基础周报。LLM 的增量价值是对每周变化的异常做受证据约束的解释和归纳，避免把所有说明规则都人工穷举。若业务只要数字表格，应优先不用 LLM。

当前维护状态、使用人群和最后更新时间是 **[待本人确认]**。回答应承认工作流底座的价值，不声称 LLM 不可替代。

## W07：Text-to-SQL 如何防删库、越权和 Schema 错误？

先纠正前提：当前周报不是 Text-to-SQL，查询和统计 SQL 由程序预先编写。若下一版支持自然语言查数，应使用只读账号/只读副本、授权后的 Schema 子集、SQL AST 白名单、行列权限、超时与扫描量限制、执行前 `EXPLAIN`、结果限行和完整审计；禁止多语句、DDL/DML 和危险函数。

Schema 通过结构化 catalog 提供表、字段、类型、业务含义、关联、敏感级别和更新时间，而不是把整个库 DDL 无差别塞进 Prompt。

## W08：多系统日志如何做根因诊断？

这属于从周报能力迁移出的 **下一版设计**。先收业务影响、Trace/请求 ID、RED 指标、数据库/MQ、结构化日志、发布配置变更、预期/观测拓扑和 Runbook；统一时间、时区和实体标识后，寻找“第一个异常信号”，而不是最后一个报 500 的服务。

模型只整理“候选假设、支持证据、反证、缺失证据和下一条查询”。必须通过原始日志、请求回放、配置对照、Feature Flag 或受控回滚验证后，才能称为根因。

## W09：拓扑、Trace 断链和自动修复怎么处理？

预期拓扑来自注册中心、RPC 配置、API 契约、静态代码和基础设施；观测拓扑来自 Trace、Service Mesh、网关和消息系统，两者都要带版本与时间窗口。关联优先使用 W3C Trace Context，再用 message ID、业务流水号，最后才用拓扑、实例、时间窗和错误码做不确定推断。

自动修复只能分级：低风险、可回滚、验证充分的 Runbook 动作可自动执行；改代码应在隔离分支生成补丁、跑测试/静态扫描/回归并人工审批，绝不能由模型直接改生产。

## W10：两个来源的数据冲突、时间标签不一致，怎样处理？

先把来源、指标、单位、时区和窗口统一，再分别保留 `event_time`、`ingest_time`、来源版本和质量状态。来源权威度、完整性、新鲜度和时间对齐只能用于排序，不能把不确定的数字静默覆盖；无法裁决时保留冲突、标记待核验并在周报中显式提示。这个答案适用于 Suunto 追问的“多源运动/运营指标”，也适用于周报，不代表当前项目已经有自动因果裁决器。

## W11：429、超时和历史补采怎样重试，如何避免重复？

连接器级共享限流器先尊重 `Retry-After`，只对超时、429 和可恢复 5xx 做有上限的指数退避与 jitter，并受单次运行 Deadline 约束。任务以 `source_id + window + metric_key + input_version` 形成幂等键，落库用唯一约束和事务性 upsert；重试状态、死信、租约和回放游标要可观测。API 重试解决“没拿到/暂时失败”，来源冲突解决“拿到了但口径不同”，不能混成一个问题。

## W12：周报数字怎样和模型叙述、对账结果闭环？

数字、汇总、排序和同比由程序确定性计算；LLM 只消费已验证指标、阈值和 `evidence_id`，输出摘要、异常和引用。生成后校验引用存在、数字与事实表一致、时间范围匹配，失败就回退到模板或进入人工核对。若把周报能力迁移到运动或数据平台，仍要保留源端总量、落库行数、迟到/重复率和最终产物的对账记录。当前尚无证据时，不把“准确率”说成模型指标。

## 附录：AI 周报系统口语化串讲

### 30 秒开场版

> 这个项目做的不是员工工作周报，而是网联运营保障周报。以前每周要人工从多个系统收集错误日志、慢 SQL、大事务、失败交易、TPS 和响应时间，再做统计、分析和排版。我把它改成了一条自动化批处理链路：每天采集和校验数据，确认上一周七天数据完整后，由程序计算确定性指标，再让大模型解释异常、组织文字，最后按固定模板组装并推送。这个项目最难的不是调一次模型，而是多源数据口径、补数幂等、数据准确性和整个任务的状态一致性。

### 一、为什么要做这个项目

面试官问项目背景时，我会先把问题说清楚：

> 原来的痛点是每周都要重复做一遍采集、核对、统计、分析和排版。它不只是耗时，还容易因为数据源多、格式不同、人工复制而出现漏项或口径不一致。所以我没有一上来先找大模型，而是先把固定流程自动化，再把确实需要语言理解的异常解释交给模型。

材料中的效率口径是人工一轮约 8 到 10 小时，自动流程约 20 分钟。这个数字在面试时要说清统计范围和样本数；“一年节省约 50 人天”只是按工作周估算的毛投入差值，还要扣掉人工复核、系统维护和异常处理，不能说成财务审计后的净收益。

### 二、整条链路怎么跑

我一般按真实执行顺序来讲：

> 日终任务启动后，系统先创建当天的控制记录，然后扫描近 15 天仍然没有下载成功的业务日期。这样上游某一天临时失败，不会因为错过一次调度就永久缺数据。接着各个连接器调用北斗、园方、AN1LOG、CKTRANS、CKSLOWSQL、FTCLOG 等数据源，把 JSON、表格或日志归一成统一内部结构，再幂等写入对应数据表。
>
> 数据采集成功只是第一关。系统还会检查上一周七天的 `PROC_STATUS` 是否全部成功，七天不齐就不生成周报。通过这个完整性 Gate 后，各分析模块先用程序计算 TPS、响应时间、错误量、慢 SQL 和大事务等确定性结果，再把已经算好的指标、基线和异常证据分段交给大模型。模型负责解释趋势和组织文字，不负责重新计算核心数字。
>
> 最后程序把各模块结果按固定章节组装成“表格加文本”，只有所有必选模块都成功才更新分析状态并调用内部消息接口发送。也就是说，模型只是链路中的一个分析节点，采集、状态判断、数字计算和最终发布仍然由程序控制。

主链路可以压缩成一句：

```text
按业务日期采集 -> 清洗落表 -> 七天完整性 Gate -> 确定性统计
-> LLM 分段解读 -> 模板组装 -> 内部消息推送
```

### 三、失败重试和幂等怎么讲

> 这个项目里我把“任务执行成功”和“数据不会重复”分开处理。状态字段只能告诉我这一步走到哪里，真正的幂等要靠稳定业务键和数据库唯一约束，例如 `source_id + window_start + metric_key`，补跑时用 upsert 或忽略重复写入。上游失败后，当前系统会在后续日终继续扫描近 15 天的 Pending 日期，并按配置做有限重试。

当前边界也要主动说明：固定间隔重试和 15 天回看能解决常见短期故障，但还不是完整任务中台。超过窗口的历史缺口、上游已经成功后又修正数据、发送失败后的可靠重发，都需要独立 Backfill、输入版本、报告 Revision、Outbox 和送达对账，这是下一版设计，不能说当前已经全部实现。

### 四、怎么保证数据和模型输出准确

> 准确性我分三层。第一层是采集准确，核对业务日期、时区、分页、记录数和唯一键；第二层是指标准确，用固定样本给统计逻辑做单测，并和历史人工周报并行核对；第三层是生成准确，模型输入只给已经验证的指标和证据，输出按固定 Schema 返回，数字和证据 ID 还能回查事实表。

当前系统能够证明的是“确定性统计先算、七天不完整不分析”，但现有材料不能证明所有模型输出都已经完成逐字段事实校验。因此面试时不能只说“数字不用模型算，所以绝对准确”；更完整的生产方案还要增加事实引用、输出校验和失败回退模板。

### 五、大模型在里面到底有什么价值

> 没有大模型，这套系统仍然能完成采集、统计和固定模板周报，所以项目价值不能建立在“必须用 LLM”上。模型真正增加的能力是：面对每周不同的异常组合，它可以根据已经算好的指标解释趋势、归纳重点并组织自然语言，避免为每一种情况都手写说明规则。

我也会强调边界：当前多源数据只能提供相关性线索，没有运行时 Trace、因果图和自动实验，不能把模型生成的解释直接说成已确认根因。真正做根因诊断时，还要结合 Trace、业务流水号、发布变更和受控验证。

### 六、项目难点和收尾表达

> 这个项目真正有工程含量的地方，是让一条跨多个数据源、数据库、模型和消息接口的批处理链路可以重复运行、失败后补回来，并且不会在数据不完整时生成一份看起来正常的周报。模型调用本身反而只是其中一小段。

一句话收尾可以这样说：

> 我先用确定性程序把数据采准、数字算准、状态管住，再让大模型做受证据约束的解释，最后由程序完成组装和发布。这样即使模型不可用，基础周报仍能运行；即使上游暂时失败，后续任务也能补数恢复。
