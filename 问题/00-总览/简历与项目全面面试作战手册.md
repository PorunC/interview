## 0. 先读结论：面试官会怎样给你定级

### 0.1 一句话判断

现有源码和设计材料能够证明三个内部项目覆盖确定性数据处理、LLM 生成、AST/图检索、Agent 记忆和上下文卸载等完整技术链路；货拉拉二面进一步证明，面试官会用二叉树、B+树、进程线程、Java 并发和线程池检验基础底盘，再追问增量索引和 Memory 事实治理。但这些材料不能自动证明本人对需求、全栈实现、测试、部署和结果都最终负责。真正限制通过率的是**个人 RACI、指标证据、基础知识表达精度、对照实验和生产工程细节**。

### 0.2 可能得到的面试评价

| 维度 | 当前判断 | 面试官可能的评价 | 提升动作 |
|---|---:|---|---|
| AI 应用广度 | A- | 周报、代码理解、Agent Memory 三类场景完整 | 保持，不再堆新项目 |
| 独立交付能力 | 待核实 | 项目技术链完整，但本人负责范围尚未由 RACI 关闭 | 填写三个项目的分阶段 RACI，并用代码、评审和发布记录证明 |
| 项目技术深度 | B+ | 有 AST、GraphRAG、Hybrid RRF、Offload | 把源码细节和设计取舍讲具体 |
| 生产工程能力 | B | 有重试、事务、状态机、检查点、监控意识 | 补并发锁、幂等、发送一致性、故障演练 |
| 评测能力 | B- | Memory 有内部 benchmark，CodeWiki 有性能压测 | 补质量评测、基线和置信区间 |
| 指标表达 | B- | 指标亮眼，但定义和实验口径容易被深挖 | 准备样本、基线、公式和局限 |
| 后端基础 | 未充分证明 | 简历没有技能栏，也没有传统后端成果 | 补 Java/Python、DB、缓存、并发、网络题 |
| 大数据平台匹配 | 待验证 | AI 数据链路可迁移，但 Hadoop/Spark/Data Agent 生产边界未关闭 | 准备数据契约、补数、幂等、质量、语义层和评测答案 |
| 表达 | B | 能讲框架，曾多次被指出“笼统” | 每个答案按输入→步骤→状态→输出→指标讲 |
| 英文 | B- | CET-6，但英文简历和口述仍需校正 | 练 2 分钟介绍和 5 个项目追问 |

### 0.3 最适合和不适合的岗位

**优先投递**：

1. AI 应用开发工程师 / Agent Engineer。
2. RAG / 企业知识库 / Coding Agent 工程师。
3. AI 平台后端工程师，尤其是强调全链路落地而非训练大模型的岗位。
4. 需要 Python/FastAPI + TypeScript/React 全栈原型交付的初创公司或创新团队。
5. 大数据与 AI 结合、强调语义层/评测/平台工程的岗位；面试时必须主动说明 Hadoop/Spark 等传统组件的真实边界。

**谨慎投递**：

1. 纯算法岗：如果要求预训练、SFT、RL、CUDA、分布式训练，你的简历证据不足。
2. 纯高并发基础架构岗：目前缺少百万 QPS、消息中间件、缓存一致性等工作证据。
3. 资深架构师岗：3 年经验和项目治理证据不足，现场系统设计可以加分，但不要主动包装成架构师。
4. 强金融算法岗：银行工作背景不等于信贷/量化/风控模型经验。
5. 纯大数据平台岗：如果核心要求是 Hadoop/Spark/Flink/Hive 生产数仓，而你没有相应交付证据，应把它作为补齐项而不是把 AI 项目直接等同于大数据经验。

### 1.2 个人概述

原表述：

> 3 年后端开发经验，专注将大模型落地为生产级业务工具。主导过 AI 周报系统及代码智能平台三个从 0 到 1 的项目，具备独立完成系统设计、全链路开发及持续交付的能力。

**问题 1：“AI 周报系统及代码智能平台三个”有语病。**“及”前后只列出两个名字，却说三个项目。英文版的 “including” 虽然语法成立，仍让人疑惑第三个项目是什么。

**问题 2：“3 年后端”与正文技术栈不匹配。**正文更像 AI 应用全栈工程师，却没有 Java/Python、数据库、中间件、容器、测试等技能栏来支撑“后端”。

**问题 3：“生产级、主导、独立、从 0 到 1”叠加。**每个词都可以用，但同时出现会让面试官默认进行证据审计：谁立项、谁设计、谁编码、谁评审、谁部署、谁运维、谁对指标负责。

**RACI 完成前的安全版本**：

> 3 年后端与 AI 应用开发经验，聚焦将 LLM、RAG 和 Agent 能力落地到企业场景。参与 AI 周报、CodeWiki 和 Agent Memory 三个内部项目，负责范围包括 **[按 RACI 填写真实阶段和模块]**；能够从确定性数据处理、检索、模型调用、校验和可观测性角度完成 AI 应用工程设计与实现。

只有证据能证明本人对项目技术设计和核心开发最终负责时，才把“参与”升级为“主导”；只有前端、部署和评测责任都能逐项证明时，才使用“全栈实现到部署评测”。

### 1.4 AI 周报项目审计

**能够被现有材料支持的内容**：

- 多源采集：北斗指标、AN1LOG、FTCLOG、CKTRANS、CKSLOWSQL 等。
- 控制表状态：`PROC_STATUS`、`ANA_STATUS`。
- 15 天回溯、模块级重试、分模块分析、周报组装和群组推送。
- 确定性 SQL 统计与 LLM 叙述可以明确分工。
- 简历中的“8-10 小时到 20 分钟、约 50 人天/年”在输入成立时数学自洽，但原始工时、运行记录和观察窗口仍待本人核验，不能列为已被源码证明的事实。

**当前表述过强或待补证的内容**：

- “事务保障”只能证明数据库局部事务，不能证明外部 API、LLM 调用和消息发送之间存在分布式事务。
- “稳定运行”必须准备运行时长、成功率、故障次数、SLA、告警方式。
- “LLM 智能分段分析”需要准备具体 token 预算、分段键、聚合方法和超长输入 bad case。

**源码级高风险设计**：详设先提交 `ANA_STATUS='S'`，再组装并发送消息。如果状态提交后发送失败，下一次调度可能因全部为 S 而跳过，造成周报永久漏发。正确设计应把“分析完成”和“发送完成”拆成独立状态，或使用 outbox 事件表。

### 1.5 CodeWiki 项目审计

**内部实现证据**：

- 项目覆盖 FastAPI、React、AST、GraphRAG、MCP、CLI、Wiki、增量更新。
- 支持 Python、Java、Go、Rust、C、C++、C#、JavaScript/JSX、TypeScript/TSX。
- Python 与多语言 tree-sitter 解析、统一 `AstSymbol`、调用/导入/继承/路由/配置关系建图有源码证据。
- 有 React、VS Code、Superset、Rust 的冷启动/增量性能压测。

**必须校正的说法**：

1. “自研 AST 解析引擎”不能让人理解为你从零实现 parser。准确说法是：**基于 Python AST 和 tree-sitter grammar，自研多语言统一符号抽取、capture spec、关系解析与图构建层**。
2. “GraphRAG 语义检索”不是所有请求都走向量。源码中 embeddings 是可选的，默认路径包括符号 seed、FTS、可选 vector、图扩展和上下文预算。
3. “日均查询 50+”和“团队使用”要准备内部埋点口径，说明是请求数、用户数还是自动调用次数。
4. 现有 benchmark 证明的是规模与性能，不是 GraphRAG 对普通 RAG 的质量提升。不能拿 30 万节点、88 万边证明召回更准。
5. “新人上手数周”“日均 50+”“日常评审采用”要准备内部试用范围、观察周期和用户反馈。
6. Git diff/Hash 增量只能定位变更候选，不能保证属性、公共类型、重命名和反向依赖的语义更新；面试时必须补 Dirty Set、stale 标记、revision 绑定、回归校验和原子切换。

### 1.6 Agent Memory 项目审计

简历中的三组数字对应公司内部离线评测：

- WideSearch：Token 221.31M→85.64M，下降 61.38%。
- 通过率 33%→50%，相对提升 51.52%。
- PersonaMem：48%→76%。

面试重点是你能否把架构、个人职责和指标测量讲清楚。建议删掉“共 97 个 TypeScript 模块”这种容易随版本变化、又不能证明业务价值的数字，改成你真正负责的子系统：L0-L3 Pipeline、Hybrid RRF、Context Offloading、scheduler、checkpoint、GC 和可观测性。

“覆盖多个业务渠道”要准备内部接入方式：是 SDK、插件、Gateway 还是服务接口；接了几个渠道；如何隔离用户和配置；出现故障怎么回滚。

货拉拉二面进一步暴露：当前实现更准确的口径是本地单用户组件/服务，通过宿主 Hook 接入；不能把未来 Gateway 或 MCP 适配写成已经完成的共享多租户平台。

### 1.7 量化指标的证据模板

任何数字都按下面 8 个字段准备；缺一项，面试官就可能把它判为宣传数字：

| 字段 | 示例 |
|---|---|
| 指标定义 | 通过率是 task pass，不是单元测试通过率 |
| 基线 | OpenClaw 原生、普通 RAG、人工流程 |
| 样本 | 多少任务、多少用户、多少周、什么仓库 |
| 实验变量 | 只开启插件，模型、温度、工具和数据保持一致 |
| 运行次数 | 每个任务是否重复，如何处理随机性 |
| 统计口径 | 相对提升还是绝对百分点，均值还是 P50/P95 |
| 数据来源 | 埋点、评测脚本、人工标注、日志查询 |
| 局限 | 样本偏差、外部模型版本变化、置信区间 |

### 2.2 明确失分点

1. 码云：LLM 幻觉成因回答不准确；harness/loop 概念答偏；GraphRAG token 爆炸不了解。
2. Ashley：上下文组装只说相关性；事实冲突只说覆盖；工程部署和并发数字不足。
3. 卓誉：没有 GraphRAG vs 普通 RAG 的质量 benchmark；使用情况回答偏虚。
4. 京东：模型路由在执行前如何预估质量，被追问后缺少离线基线、在线反馈和探索机制。
5. 微众：把 Mermaid 画布和上下文压缩混讲；依赖用户确认冲突不现实。
6. 小天才：根因诊断流程第一次回答太笼统；数据规模拿不出具体数。
7. Abound：独立负责、排期和项目管理机制表达不清；编码题和英文仍是硬门槛。
8. 丰泊国际：Java 基础从 Spring 注入、ConcurrentHashMap、AQS、事务传播一路到 GC 连续失分；三个项目没有先讲清用户、原流程和业务价值；离职理由过度绑定 Claude/Codex；AI 生成代码后的本人责任链和公司调研证据不够清楚。
9. 货拉拉二面：二叉树定义不够严谨；B+树没有讲清叶子链和内部/叶子节点分工；上下文切换把页表混入每次线程切换；`volatile` 语义不完整；类属性变化时承认不更新向量；用向量/BM25 召回代替事实主键和冲突状态机；最近学习回答偏工具兴趣，没有对齐 Data Agent 语义层。

### 2.3 你的统一答题协议

以后所有项目题都按同一骨架回答：

1. **问题**：谁遇到什么损失，为什么值得做。
2. **边界**：哪些由确定性代码做，哪些交给模型。
3. **链路**：输入→关键步骤→状态/存储→输出。
4. **取舍**：为什么选 A，替代方案 B/C 为什么暂不选。
5. **可靠性**：超时、重试、幂等、并发、回滚、权限、观测。
6. **指标**：定义、基线、样本、结果、局限。
7. **个人贡献**：我决定什么、实现什么、与谁协作、谁最终负责。
8. **反思**：一个真实缺陷和下一版改法。

禁止只说“做了分析”“做了优化”“用了 GraphRAG”。每一步都要有输入、输出、状态变化或可观测结果。

丰泊这场还补了一条现场纪律：**先用一句话直接回答面试官问的核心，再展开原因和链路。**如果面试官问“主要解决什么”，第一句就说用户、痛点和被替代的人工步骤，不要先讲技术名词。

### 2.4 “独立负责”的统一答案

> 我不会用一句“技术主线由我 owner”给三个项目统一定责。源码和设计材料能证明项目有哪些技术链路，但不能单独证明这些链路由我设计、实现或上线。现场我会按项目和阶段回答：我直接负责的是 **[按 RACI 填写]**，与同事协作的是 **[填写]**，最终评审、发布和指标负责人是 **[填写]**。RACI 还没核实时，我只讲能从材料确认的系统机制，不把团队成果算成个人贡献。三个项目都按公司内部项目口径回答，不讨论源码日期、远端地址或公开提交身份。

### 2.5 当前面试题趋势（联网交叉验证）

近期公开题单与官方资料和你的真实面试高度重合，说明下面不是偶然：

- RAG 已从“解释流程”升级到切块、混合检索、rerank、Lost in the Middle、检索/生成分层评测、权限和间接提示注入。
- Agent 已从“会 LangChain”升级到 harness、tool loop、context engineering、compaction、long-term memory、durable execution、trace grading。
- MCP 已从“知道协议”升级到 host/client/server、capability negotiation、OAuth、token passthrough、SSRF、session hijacking、scope minimization。
- 项目面越来越关注基线、bad case、评测集、成本、P95、故障恢复和人机权限，而不是只看 demo。
- Coding Agent 岗会继续追问 AST 的确定性价值、repo map、增量索引、编辑工具协议、验证闭环和代码安全。
- 大数据与 AI 结合岗位会继续追问语义层、指标口径、NL2SQL、归因/下钻、权限、数据血缘和 Agent 轨迹评测；“能调模型”不等于“能回答正确数据问题”。

### 2.6 丰泊国际新增结论：岗位是五条证据链同时验真

丰泊不是把 Java、AI Coding 和 AI 项目分开打分，而是在确认五条证据链能否同时成立：

1. **Java 后端证据链**：简历写三年 Java，就要能连续回答 Spring 注入与事务代理、JUC/AQS、并发集合、幂等、分布式一致性和 JVM/GC；不能只靠 AI 项目深度抵消基础空档。
2. **AI Coding 证据链**：不要纠结“人工和 AI 各写百分之多少”。应拿一个真实变更说明 AI 生成了什么、遗漏了什么、本人实际修改和验证了什么，并给出 Commit、Review 或测试证据。谁决定架构、谁批准合并、谁负责发布和线上结果都是事实题；只能对 RACI 中自己真实承担的环节负责，不能默认全部归到本人。
3. **AI 项目证据链**：每个项目先说 `谁在什么场景遇到什么问题 → 原流程哪里慢 → 系统具体替代哪一步 → LLM 为什么有必要 → 当前边界`。CodeWiki 必须能回答“为什么不用 Claude/Codex 直接扫仓库”，Memory 必须区分“扩大窗口”“长期记忆”和“上下文卸载”。
4. **职业选择证据链**：离职不能说成“公司不让用先进工具”。更稳的表达是工作内容、正式业务目标和可落地空间与长期方向不匹配，工具限制只是表象，并明确认可金融机构的安全约束。
5. **公司调研证据链**：不能只说“问了 AI”。至少要交叉核验业务模式、监管/持牌主体、收入或资金口径、公开正负面信息，再说明它和自己的金融后端、研发提效经历为什么匹配。

针对丰泊透露的“需求增长快、文档缺失”场景，CodeWiki 的落地答案按三段讲：前 30 天访谈并建文档缺口和任务基线；31-60 天选一个低风险高频仓库上线带源码引用的增量 Wiki/问答 MVP；61-90 天用理解耗时、引用正确率、文档新鲜度和需求 cycle time 验证，再决定扩仓库、扩语言或接入 SDD。不要承诺一上来自动生成全部文档。

完整单场证据见 [丰泊国际 Java 后端 / AI 应用岗面试整理](../../面试分析/丰泊国际-Java后端-AI应用岗-面试整理与答案.md)，公司业务与风险核验见 [丰泊国际 FundPark 公司深度分析](../../公司/丰泊国际FundPark_公司深度分析报告.md)。

### 2.7 货拉拉二面新增结论：基础底盘和语义数据平台同时验真

货拉拉二面不是单纯的 AI 项目面。面试官先用二叉树、B+树、进程/线程、上下文切换、Java 同步和线程池确认后端基本功，再追问 CodeWiki 的统一 DSL、图/向量存储、属性变更和 Memory 的写入/冲突/集成，最后介绍团队正在做 Hadoop/Spark 基础设施、Data Agent、NL2SQL、语义层、本体、归因下钻和多模态数据处理。

这场之后，岗位匹配答案必须从“我做过 AI 项目”改成：

> 我的项目更偏 AI 应用和知识工程，但可以迁移的是数据契约、采集清洗、任务触发、幂等写入、增量索引、质量校验、Trace 和故障回放。对 Hadoop、Spark 或团队内部 Data Agent 语义层，我会区分已经使用过的能力和需要补齐的组件；我不会把 NumPy、GraphRAG 或本地 Memory 直接包装成完整的大数据平台生产经验。

二面暴露的最高优先级不是继续堆新的 AI 名词，而是把以下三条链路讲成可验证实现：

1. **基础链路**：树遍历、B+树、进程/线程、上下文切换、Java 内存可见性/原子性/互斥、线程池队列与拒绝策略。
2. **版本链路**：`repo_id + revision + symbol_id + source_ref`，由 diff 找候选、由依赖算 Dirty Set、由校验和原子切换保证新旧索引一致。
3. **语义链路**：业务指标/表/字段/权限/时间口径先进入结构化语义层，模型只生成候选 SQL 或解释，结果经 AST、权限、数值对账和评测平台校验。

## 3. 第一优先级：25 个决定通过率的问题

下面 25 题必须先练；每题都在真实面试中出现过，或由源码审计直接触发。

### Q1. 三个项目在公司内部是什么关系？为什么会先后做这三个？

**面试官意图**：先做真实性校验。

**口语化回答**：

> 这三个都是公司内部项目，但解决的问题不一样。AI 周报解决运维数据人工汇总；CodeWiki 解决大仓库和跨模块代码理解；Agent Memory 解决跨会话记忆和长任务工具结果膨胀。从能力关系看，它们分别对应业务自动化、代码知识基础设施和 Agent 运行时能力。具体业务阶段与维护状态我会按内部记录回答，不使用源码日期推断项目先后。

### Q2. 为什么简历上三个项目都写“独立负责”？

**口语化回答**：

> 简历里的“独立负责”需要按项目和阶段拆开，不能预先解释成“技术主线都由我 owner”。我会分别说明需求、设计、编码、联调、测试、发布和维护中，我直接负责的是 **[填写]**，共同完成的是 **[填写]**，最终负责人是 **[填写]**。源码只能证明实现存在，不能证明作者和责任人；没有内部记录支持的环节，我不会算到自己头上。

### Q3. Agent Memory 里你个人到底负责了什么？

**口语化回答**：

> 从当前源码能确认，项目分成 L0-L3 长期记忆和工具结果 Context Offload 两条链路，包含分层 Pipeline、双后端存储、Hybrid RRF、调度与 checkpoint，以及 offload、Mermaid 和原文引用机制。这是项目架构事实，不等于这些模块都由我设计或实现。我的真实贡献要按 RACI 补成：我直接负责 **[模块/阶段/证据]**，参与 **[填写]**，没有负责 **[填写]**，最终评审和上线责任人为 **[填写]**。在这些记录补齐前，我不会声称整体方案、核心实现和最终落地都由我负责。

### Q4. 61.38%、51.52%、48%→76% 是怎么测的？

**口语化回答**：

> 这三组数都是我们内部离线评测出来的，不是拿线上所有业务直接平均。WideSearch 里，总 token 从 2.2131 亿降到 8564 万，所以降幅是 61.38%；成功率是从 33% 到 50%，绝对是多了 17 个百分点，相对提升是 51.52%；PersonaMem 是从 48% 到 76%，绝对提升 28 个百分点。我面试时会把相对提升和百分点分开讲，也会说明评测任务、模型版本、运行次数和基线，避免让人误以为这是所有线上场景都能稳定达到的数字。

### Q5. CodeWiki 的日均 50+ 是怎么统计的？

**口语化回答**：

> 这道题必须回到真实统计。我要先说明 50+ 是 Ask、API、MCP 还是页面操作，是否排除健康检查、重试和自动任务，统计窗口和去重口径是什么，再给出日志或报表来源。当前仓库材料不能证明这些埋点细节；如果拿不到内部查询，我会把简历降级成“已有内部使用和反馈”，不继续报一个无法复核的精确日均数字。即使 50+ 有证据，它也只是请求量，不等于 50 个用户或已经证明业务效果。

### Q6. 周报系统不用 LLM，脚本和模板不能做吗？

**口语化回答**：

> 这题我会先把边界说清楚：能做采集、统计和固定模板，所以我没有让 LLM 计算数字。LLM 的增量价值只在异常叙述、跨指标解释和自然语言追问。如果业务只需要固定表格，我会选择脚本而不是 LLM；只有可读性和非固定问题带来的收益高于成本时才接入模型。

### Q7. 周报的事务保障具体保障了什么？

**口语化回答**：

> 这题我会先把边界说清楚：当前保障的是单次数据库写入与状态更新的本地原子性，不是外部 API、LLM 和消息平台之间的分布式事务。下载与分析用业务键和 `INSERT IGNORE` 做幂等，失败保持 Pending 供下次回溯。发送链路要进一步用 outbox：同一事务写 `REPORT_READY` 事件，独立 sender 以 `report_id` 幂等发送，成功后置 `SEND_STATUS=S`。

### Q8. 状态已成功但消息发送失败怎么办？

**口语化回答**：

> 这题我会先把边界说清楚：现有详设这里有缺口：`ANA_STATUS=S` 先提交，发送后置，失败会漏发。我会拆 `ANALYSE_STATUS` 和 `SEND_STATUS`，并用 outbox + 唯一 `report_id` + 重试退避；消费者至少一次投递，消息端用幂等键去重。监控 Pending age 和连续失败次数，超过阈值告警人工补发。

### Q9. 两个调度实例同时运行，会不会重复生成或重复发送？

**口语化回答**：

> 这题我会先把边界说清楚：单靠 `INSERT IGNORE` 不够。应在控制表加 owner/lease/version，使用条件更新 `P→R` 抢占：`UPDATE ... SET status='R', owner=?, lease_until=? WHERE status='P' AND lease_until<now()`，受影响行数为 1 才执行。实例崩溃后 lease 到期可恢复；发送仍以唯一业务键去重。

### Q10. CodeWiki 的 AST 是你从零写的吗？

**口语化回答**：

> 从当前 CodeWiki 源码看，它不是从零实现语法解析算法：Python 使用标准 AST，多语言使用 tree-sitter grammar；项目自研部分是统一解析层，包括语言注册、capture query/spec、`AstSymbol` 标准模型、关系抽取、跨文件解析、缓存、并行解析和后续图构建。这个结论描述的是项目实现；我本人负责其中哪些模块，要用 RACI、代码变更和评审记录单独证明。

### Q11. CodeWiki 的 GraphRAG 完整检索链路是什么？

**口语化回答**：

> 在 CodeWiki 里，我会这么回答：先用符号名和节点级全文检索得到 seed；再做 code chunk FTS，可选向量召回；把 chunk 命中合并回节点 seed；无命中时回退 overview seed；按最多 0-4 hop 在代码边上扩展；然后按 token budget、hop、seed/FTS/vector 信号筛 source chunks，同时取 community summaries；最后输出带 stable trace id 的 context pack。LLM 只消费经过预算和来源约束的上下文。

### Q12. embeddings 默认可选，为什么简历写“语义级检索”？

**口语化回答**：

> 在 CodeWiki 里，我会这么回答：“语义级”不等于每次都必须走向量。我们的系统一共有符号语义、FTS、可选 embedding 和代码图关系四类信号，更准确的说法是“多路检索加代码图扩展”。部署开启 embedding profile 时会加入向量语义召回；没有开启时，符号、全文检索和图关系仍然能完成检索链路。

### Q13. GraphRAG 比普通 RAG 好多少？

**口语化回答**：

> 在 CodeWiki 里，我会这么回答：目前我们内部已经有规模和性能压测，但质量对照还需要继续补，所以我不会直接说 GraphRAG 全面提升了多少。我会准备一批跨模块问题，标出正确文件、符号和依赖边，再对比 BM25、纯向量、混合检索和加图扩展四种方案。检索看 Recall@K、MRR 和依赖覆盖，最终任务再看回答正确率、引用准确率、修改通过率、token 和延迟。现阶段我更准确的说法是：图结构在多跳依赖和影响分析上有明显价值，但不是所有问题都一定优于普通 RAG。

### Q14. 大仓库增量更新为什么复用 99% 文件仍然不快？

**口语化回答**：

> 在 CodeWiki 里，我会这么回答：解析复用不等于端到端增量。Rust warm 只重解析 6 个文件，但仍要处理 30 万节点、70 万级边、社区检测和 SQLite 持久化，所以耗时 247 秒；VS Code 边密度近 380 万，warm 仍 514 秒。下一步要做差量图更新、受影响社区局部重算、批量写入和延迟索引，而不是继续优化 parser。

### Q15. Claude Code 已能搜索仓库，CodeWiki 还有什么价值？

**口语化回答**：

> 在 CodeWiki 里，我会这么回答：Claude Code 的优势是模型主动探索和即时推理，CodeWiki 不应宣称替代它。差异在于确定性、复用和审计：AST 图把调用/导入/继承关系一次计算，多次查询复用；可返回稳定 source refs 和影响分析；大仓库可以在 token 进入模型前做结构化剪枝。正确产品形态是把 CodeWiki 作为 MCP/索引工具供 Coding Agent 调用，而不是另造一个封闭聊天框。

### Q16. L0-L3 分别是什么，为什么四层？

**口语化回答**：

> 从当前 Agent Memory 源码和设计材料看，L0 是可追溯原始对话，L1 是原子记忆，L2 是场景聚合，L3 是跨场景 Persona。四层对应 evidence→memory→scene→profile 的不同生命周期和检索粒度，不是为了层数好看。这个回答说明项目机制，不代表四层都由我本人设计；个人贡献仍按 RACI 单独回答。

### Q17. Memory 和 context offload 是同一个问题吗？

**口语化回答**：

> 从当前 Agent Memory 源码看，不是同一个问题。长期记忆解决跨会话保留什么、怎么检索和治理；Context Offload 解决单次长任务的 working context 膨胀。Mermaid Canvas 主要是任务状态和证据索引，不等于 compact；真正降低上下文的是把原始 tool result 移到外部 refs，只保留可恢复引用和高密度摘要。

### Q18. 记忆抽取错了，如何避免错误长期放大？

**口语化回答**：

> 从当前 Agent Memory 源码看，L0 原始对话单独保留，L1 保存 `source_message_ids`；新记忆会召回相似候选，再由模型决定 `store/skip/update/merge`；召回结果只是历史参考，当前用户输入优先，需要时可以继续下钻原文。当前缺口是 `source_message_ids` 还不是逐字 span，也没有事实置信度、候选区、自动晋升和完整 tombstone/硬删除闭环。来源存在性与蕴含校验、时序版本和用户纠错属于下一版，不能倒灌成现状。

### Q19. 为什么用 RRF，不直接把 BM25 和 cosine 加权？

**口语化回答**：

> 从当前 Agent Memory 源码看，两路原始分数尺度不同，BM25、cosine 和不同后端的 score 不可直接比较；当前使用 RRF 按名次融合，`score=Σ1/(k+rank)`，默认 `k=60`。它的代价是丢失分数幅度且不理解业务；是否加 reranker、怎样调参都属于需要离线评测验证的下一步，不能说成已取得效果。

### Q20. 长上下文为什么仍需要压缩？

**口语化回答**：

> 从当前 Agent Memory 的问题定义和公开资料看，上下文窗口变长只消除硬容量限制，不消除注意力预算、无关信息污染、延迟和成本。工程目标不是“塞得下”，而是用更少的高信号上下文提高任务成功率；是否真的提升，仍要回到项目自己的对照评测。

### Q21. 模型路由在请求执行前怎么知道哪个模型效果好？

**口语化回答**：

> 这题我一般会这么说：不可能知道单次请求的真实结果，只能估计条件期望。先按任务类型、长度、工具需求、SLA 建离线质量/成本/延迟矩阵；在线用历史同类反馈更新；留小比例 exploration 或 shadow traffic 避免永远选旧赢家；关键请求可先小模型分类再路由。执行后信号回流，持续校准路由器。

### Q22. LLM 幻觉的机制是什么？

**口语化回答**：

> 这题我一般会这么说：模型优化的是条件 token 概率，不是真值查询；参数化知识是压缩分布，不是可校验数据库。训练分布缺口、冲突、解码随机性、上下文噪声和错误检索会增加幻觉，但不是根本定义。工程上不能承诺消灭，只能通过证据约束、工具验证、结构化输出、权限隔离和评测降低概率与影响。

### Q23. MCP 是什么，不是什么？

**口语化回答**：

> 这题我一般会这么说：MCP 是基于 JSON-RPC 2.0 的上下文与工具连接协议，角色是 host、host 内 client、提供能力的 server；server 可暴露 resources、prompts、tools，双方初始化时协商 capabilities。它标准化连接，不替你实现 Agent 的 planner、memory、权限策略和业务 workflow，也不会自动让工具安全。

### Q24. Agent 应该怎样评测？

**口语化回答**：

> 这题我一般会这么说：分三层：最终结果看 task success、正确性和约束满足；过程看 tool selection、参数、步骤、恢复和越权；系统看 token、成本、P50/P95、错误率。建立版本化数据集和 deterministic grader，主观项用 rubric+多评审；保存完整 trace 做 trace grading，定位是检索、规划、工具还是生成失败；上线后持续回放高风险和真实 bad cases。

### Q25. 你最需要诚实承认的项目缺陷是什么？

**口语化回答**：

> 我不会说这三个项目没有问题。周报里，分析状态和发送状态没有完全拆开，存在状态成功但消息没发出去的窗口；CodeWiki 目前性能压测比较完整，但质量基线还要继续补，而且增量更新仍然有全图成本；Memory 最大的风险是压缩时可能把当下看起来不重要、后面却有用的细节丢掉。我的做法不是回避这些问题，而是把它们变成下一版的明确优化项。

## 4. 项目一：AI 周报系统深挖题（Q26-Q50）

### Q26. 用三分钟讲清完整架构。

**口语化回答**：

> 这题我会先说结论：系统由调度、采集、控制、分析、生成、发送六部分组成。日终先为 T-1 初始化控制记录；采集器回溯 15 天 Pending 日期，从北斗和 AN1LOG 等数据源拉取并按业务键入库；周级分析器只有在上周七天全部下载成功时才运行。错误日志、大/长事务、慢 SQL、异步入账、失败交易、TPS/响应时间/交易量分别由确定性逻辑统计，LLM 只做分段解读；所有模块成功才生成统一周报。可靠性依赖控制表、模块重试、幂等键、事务和链路 ID；下一版会把发送做成 outbox，拆分分析态和发送态。

面试时应画出数据流，不要先念 7 个表名。先讲六个组件，再按追问下钻。

### Q27. 详设一处写 T-1，一处又把 `PROC_DATE` 赋成 T，到底哪个正确？

**口语化回答**：

> 这个项目里，我是这么做的：我们的日终批次是运行日 T 处理自然日 T-1 的业务数据，所以控制记录里的业务日期用 T-1，T 只作为技术运行日期。我后面把两个概念拆成 `business_date` 和 `batch_date`，这样月末、年末、闰日和跨时区时不会混。对应的边界用例也会单独覆盖，不让一个字段同时承担两个日期含义。

这类问题不要硬解释文档“没错”。承认并给出领域建模修复更加分。

### Q28. `PROC_STATUS` 和 `ANA_STATUS` 两个状态够吗？

**口语化回答**：

> 我当时的考虑是这样的：不够表达完整生命周期。P/S 无法区分运行中、可重试失败、永久失败和发送结果。建议至少 `PENDING/RUNNING/SUCCEEDED/RETRYABLE_FAILED/DEAD`，并分别记录 `DOWNLOAD_STATUS`、`ANALYSE_STATUS`、`SEND_STATUS`、attempt、last_error、next_retry_at、owner、lease_until。状态迁移必须由条件更新约束，不能任意从 S 改回 P。

### Q29. 为什么固定 sleep 重试不好？应该怎样重试？

**口语化回答**：

> 这题我会先说结论：固定间隔会在上游恢复时形成惊群，且对限流不友好。只对超时、5xx、限流等瞬时错误重试；4xx 参数错误和数据校验错误直接进入人工处理。采用指数退避加 full jitter，尊重 `Retry-After`，设置单次超时、总时间预算和最大尝试次数；连续失败触发 circuit breaker，避免把故障上游压垮。

### Q30. 为什么一个模块失败后还继续跑其他模块？

**口语化回答**：

> 当前一轮中，某个模块失败后会继续执行后续模块，已经成功写入的结果不会主动删除；但每个模块只有进程内成功标志，没有持久化模块状态。所以下一次不是精准只补失败模块，而是重新进入整套分析，主要靠 `INSERT IGNORE` 降低重复。模块 Run 表、独立状态和 DAG 精确续跑是下一版方案。

### Q31. `INSERT IGNORE` 就等于幂等吗？

**口语化回答**：

> 我当时的考虑是这样的：不是。它只在唯一约束正确时避免重复插入，还可能静默吞掉数据问题。真正幂等需要稳定业务键，例如 `report_week + module + dimension`，并定义重复请求是忽略、覆盖还是版本化。输入发生修正时要支持 upsert 或新版本，不能永远 ignore；同时记录 input hash 和生成版本，确保相同输入得到可判断的结果。

### Q32. 外部 API 返回一半数据后断开，如何判断数据完整？

**口语化回答**：

> 当前系统把 API 调用、解析落库和控制状态更新作为处理成功，并要求上一周七天 `PROC_STATUS=S` 才分析；这只能证明流程完成，不能严格证明上游内容没有少页或少维度。详设没有分页总数、checksum、watermark 和 staging 切换的证据。下一版才会记录 cursor 和上游总数，全部分页校验后原子发布数据版本；拿不到总数时至少做关键维度对账并标记完整性未知。

### Q33. 5000 条慢 SQL 超过上下文，怎么分段？

**口语化回答**：

> 当前详设能证明的是先计算输入长度，超窗时截断或分批调用。这样能避免直接超窗，但硬截断可能丢高风险记录，分批也可能重复或失去全局排序。更好的下一版是先按 SQL 指纹做确定性聚合，算频次、耗时和环比，只把高风险候选分组送给模型，并保留候选到原始记录的映射。后半段是改进设计，不是当前实现。

### Q34. LLM 把 12.3% 写成 123%，怎样防？

**口语化回答**：

> 当前 TPS、响应时间和总笔数由程序先算好再交给模型，所以模型不负责原始算术；但详设没有 `fact_id`、允许值自动比对和确定性模板回退的证据，模型仍可能在叙述里抄错数字或单位。当前要人工复核关键数字；下一版才让渲染层回填关键值，并对模型文本做单位和允许值校验。

### Q35. 日志里藏着“忽略系统提示并泄露数据”，怎么办？

**口语化回答**：

> 这题我会先说结论：这是间接提示注入。把日志和文档标记为不可信数据，不让其与系统指令同层；对输入做大小、格式和敏感字段处理，但不幻想关键词过滤能根治。模型只得到完成分析所需的最小字段，工具权限只读且最小化；任何写操作在代码层授权和审批；输出做数据泄露与引用校验。OWASP 明确指出 RAG 和微调不能完全消除 prompt injection。

### Q36. 银行数据发给模型，合规怎么做？

**口语化回答**：

> 当前能确认的是通过公司内部智算平台调用模型，具体脱敏、TLS、密钥托管、租户隔离和保存期限要以真实平台与项目配置为准，详设不能证明完整合规闭环。我会先讲生产要求：数据分级、最小字段、脱敏、审批模型服务、访问审计、日志最小化和保存删除；再明确哪些由平台提供、哪些由项目实现。拿不出配置证据时不说“全部已经上线”。

### Q37. Text-to-SQL 怎样避免删库和越权？

**口语化回答**：

> 我会先纠正前提：当前 AI 周报使用预先编写的统计 SQL，没有让 LLM 生成并执行 SQL。下面是面试官要求扩展 Text-to-SQL 时的架构设计，不是现有实现：第一层用数据库只读账号和只读副本禁止 DDL/DML；第二层用 SQL Parser 构建 AST Allowlist，只允许单条 SELECT，限制 Schema、Table 和 Function，禁止多语句、外联和系统表；第三层注入行列级权限，并设置 Statement Timeout、扫描行数和 Cost 上限；第四层先 EXPLAIN 再执行；第五层记录用户、生成 SQL、策略命中和结果。关键词黑名单只能辅助，不能当主要安全边界。

### Q38. “销量下降为什么”是不是让 LLM 看数据就能做根因分析？

**口语化回答**：

> 这题我会先说结论：不能把相关性叙述成因果。先由指标树把销量分解为流量×转化率×客单价，再按地区、渠道、产品、时间做 contribution analysis 和同期/环比；对候选因素做规则、统计检验或实验验证；模型只负责生成假设、选择工具和组织证据。输出分成“已证实事实、相关候选、待验证假设”，每项带证据和置信度。

### Q39. `val/60` 为什么就是 TPS？

**口语化回答**：

> 当前公式只有在 `val` 明确定义为连续 60 秒窗口内请求总量时，除以 60 才表示该窗口的平均 TPS，不是瞬时峰值。还要确认窗口是否滑动、是否缺采样，以及时区和重叠问题。若要做容量规划，应关注更细粒度的 Peak TPS 和 P95/P99，不能把“每日最大的一分钟平均值”冒充瞬时峰值；本人是否负责这段统计逻辑仍按代码和 RACI 回答。

### Q40. 响应时间分布计算有哪些边界 bug？

**口语化回答**：

> 我当时的考虑是这样的：总笔数为 0 时要避免除零；各 bucket 是否互斥、是否覆盖全部范围要验证；原始值可能缺失、重复或晚到；百分比四舍五入后和不一定 100%；“>1s”如果由多个指标相加要避免重叠。建议用整数 count 作为真值，百分比仅展示，并做 `sum(bucket_count)==total` 的不变量校验。

### Q41. 按月份分区清理有什么风险？

**口语化回答**：

> 这题我会先说结论：只用 `01-12` 作为分区键容易跨年份混淆；`SUCCESS_RECORDS==TOTAL_RECORDS` 在两者都为 0 时会错误判完整；`TRUNCATE PARTITION` 往往是 DDL，不一定受普通事务回滚保护；并发任务可能仍在读写该分区。修复是使用年月或明确轮转策略，要求 `TOTAL_RECORDS>0` 且日期覆盖完整，清理前获取维护锁/检查 watermark，保留审计并验证数据库 DDL 事务语义。

### Q42. 怎样评估周报“写得好”？

**口语化回答**：

> 当前材料能证明的是业务工时口径，不能证明已经有 8-12 周 Gold Set、自动数字引用检查和盲评。完整评测应该分事实正确性、异常覆盖、可读性和行动价值：固定历史周输入，和人工结论对照，关键数字确定性校验，文字用统一 rubric 盲评，再看人工修改量和异常处理价值。这是下一版评测方案，不是现有上线事实。

### Q43. 系统要监控什么？

**口语化回答**：

> 当前能确认的是控制状态、技术链路 ID、维护时间和模块失败日志，可以定位某天是否下载、哪一模块失败。完整生产监控还应覆盖按时送达、数据新鲜度和对账、Pending age、重试积压、模型超时与成本、发送成功率和人工驳回。当前没有完整 Dashboard 和 P95/P99 数字时，我只讲应该监控什么，不声称看板已经全部存在。

### Q44. 线上发布和回滚怎么做？

**口语化回答**：

> 这是一道发布设计题，当前材料没有完整 CI/CD、Shadow、灰度和模板回退记录。我会把代码、Prompt、模型、Schema 一起版本化；用固定历史周回放，再灰度到测试群；数据库迁移保持前向兼容；出现回归时切回上一制品和配置。面试中会明确这是我建议的发布门槛，真实项目流水线和发布责任按内部记录回答。

### Q45. 如果数据量增长 100 倍，先优化哪里？

**口语化回答**：

> 这是一道容量设计题，不是当前已经做过的一百倍实测。我会先量数据库扫描、上游 API、模型等待和发送耗时，再针对瓶颈优化：采集分页增量，统计下推数据库，弱依赖模块受控并行，模型前先聚合筛选，大结果异步化。当前能证明的是按模块处理以及超长截断或分批，watermark、缓存和完整异步队列属于扩展方案。

### Q46. 成本怎么估？

**口语化回答**：

> 我当时的考虑是这样的：每周成本 = 各模块输入 token×输入单价 + 输出 token×输出单价 + embedding/重试 + 基础设施。记录每个 prompt version、model、module 的 token 和缓存命中；用规则/小模型处理分类和抽取，大模型只处理高价值解释；稳定前缀利用 prompt cache，重复输入做内容 hash 缓存。成本优化必须同时看质量门槛，不能只报 token 降低。

### Q47. 上游连续三天故障，15 天回溯队列会怎样？

**口语化回答**：

> 当前恢复方式是下一次日终继续扫描最近 15 天的 Pending 日期，并按固定次数和间隔重试。连续故障后确实可能集中形成 backlog，详设没有 `next_retry_at`、优先级队列和数据源级 QPS 治理。下一版才会让当前周优先、历史补数分批、每个上游独立限流，并确保恢复吞吐大于新增任务速率。

### Q48. 设计复盘里发现过什么最危险的一致性问题？有真实事故证据吗？

**口语化回答**：

> 当前材料能证明的是一个设计风险，不是一次有工单和时间线的真实线上事故：详设先更新 `ANA_STATUS=S`，再组装并调用发送接口。如果发送超时，就可能出现数据库显示分析成功但用户没收到。材料也不能证明已经用 Outbox 修复，所以我会把它说成设计审计发现的缺口。下一版拆分析态和发送态，同事务写 Outbox，Sender 按稳定 `report_id` 幂等发送。如果面试官要求真实事故，我必须换成自己有日志和修复记录的案例，不能把这个风险编成事故。

### Q49. 如果重做周报系统，你会怎么改？

**口语化回答**：

> 如果重做，我会分阶段补：先拆分析态和发送态，用 Outbox 解决送达窗口；再把模块状态持久化，支持精确续跑；然后补租约抢占、数据完整性对账、结构化事实引用、历史回放评测和敏感数据治理。Lease、Outbox、`fact_id`、Gold Set 和 DAG 都是下一版方案，不能说成当前已经实现。

### Q50. 这个项目最有技术含量的是什么？

**口语化回答**：

> 这题我会先说结论：不是“调用了大模型”，而是把不确定模型嵌入确定性运维流程：数字不交给模型、数据不完整不生成、模块可重试、结果可追溯、失败可回补。再往深一层，真正的难点是跨系统数据口径和状态一致性。模型只是链路中的一个能力，不是系统中心。

## 5. 项目二：CodeWiki 源码级深挖题（Q51-Q80）

> 本节的架构、数据流和边界来自当前源码与项目文档。它们能证明项目怎样工作，不能单独证明由本人设计或实现。面试时先讲“当前实现”，再按 CodeWiki 分阶段 RACI 补充“我直接负责 **[填写]**、协作 **[填写]**、最终评审/发布 **[填写]**”；未核实前不把源码作者、测试执行者或上线负责人默认成自己。

### Q51. CodeWiki 的分层架构是什么？

**口语化回答**：

> 从当前 CodeWiki 源码看，输入层接受本地路径或 Git URL；scanner 负责 ignore、语言、hash 和 Git metadata；parser registry 把 Python AST 与多语言 tree-sitter 统一为 `AstSymbol`；graph builder 生成 file/symbol 节点和多类关系边；持久层支持 SQLite/PostgreSQL；GraphRAG 负责 FTS、可选 vector、graph expansion 和 context packing；Wiki/Q&A 通过 LiteLLM 生成并做 source/citation 校验；HTTP、CLI、MCP、React UI 是不同交互边界。增量更新通过 git diff 与 SHA256 识别变化并标记 Wiki stale。这是当前实现链路，不代表每一层都由我本人开发。

### Q52. 为什么 Python 不统一用 tree-sitter？

**口语化回答**：

> 当前源码的取舍是：Python 使用标准 AST，多语言使用 tree-sitter，统一发生在 `AstSymbol` 之后，而不是强迫底层 Parser 一致。Python AST 对 Python 语义节点更直接，tree-sitter 的优势是多语言和容错；代价是两条抽取路径需要一致性测试。这个选型理由可以从实现解释，但由谁提出和落地仍按 RACI 回答。

### Q53. `AstSymbol` 至少要包含什么？

**口语化回答**：

> 这题我会先把结论说清楚：稳定 id、type、name、file_path、language、start/end line、parent_id、signature、bases/implements、imports/calls/references、file hash 和 metadata。稳定 id 用于数据库 upsert、图边、source refs 和增量更新；行号与 hash 用于溯源和判断旧引用是否失效。不要把完整 AST 树原样塞数据库，数据库存面向检索的标准化事实。

### Q54. 图里有哪些边？边的置信度怎么来？

**口语化回答**：

> 当前源码中的关系主要有 file containment、symbol containment、import、definition/reference、call、inherit/implement、route 和配置使用等；边可保留 source location、解析策略和 confidence。完全限定名和明确 import 的解析置信度高，同文件唯一名称次之，仅靠短名启发式匹配较低。当前实现能证明边和置信信息存在；“按置信度精排到什么程度、效果如何”还要按查询代码和评测证据回答，不能把目标方案说成线上效果。

### Q55. `foo()` 怎么解析到另一个文件的具体函数？

**口语化回答**：

> 当前源码体现的静态解析思路是：先记录 call name 和当前作用域，再结合当前文件的 import/alias 形成候选模块，在符号索引中按 fully-qualified name、模块导出和作用域查找；唯一候选可建高置信边，多候选只能保留低置信候选或不建边。动态分派、反射、monkey patch 和运行时依赖是当前静态分析边界；融合 LSP 或 runtime trace 属于下一版选项。

### Q56. 代码 chunk 为什么不按固定 500 token？

**口语化回答**：

> 当前 `ChunkBuilder` 按代码图里的源码节点生成 Chunk，使用节点的起止行和 `node_id`，所以函数、类等语义边界优先；它没有实现“超大函数再按语句块或固定 token 切成多块”。优点是引用简单、不会切断普通函数，缺点是超大函数可能形成大 Chunk 并挤占预算。二次切块、父 Symbol 关联和相邻块补召回是下一版方案。

### Q57. 一个超大函数被切成两块，图上怎样表示？

**口语化回答**：

> 当前不会出现“一个超大函数自动切成两块”的情况，一般一个源码节点对应一个 Chunk，所以不能拿 `chunk_index/total` 和顺序边当现状。如果下一版增加二次切块，我会保持图上仍只有一个函数 Symbol，多个检索块共享父 `node_id`，顺序只存在于 Chunk 元数据，调用边仍指向函数，避免制造假的代码拓扑。

### Q58. 多路检索结果怎样排序？

**口语化回答**：

> 当前链路先形成 symbol、FTS 和可选 vector seeds，再按图 hop 扩展；上下文选择综合 seed、文本、向量、hop 距离和 source chunk 预算，目前没有复杂的学习排序。这是源码事实。信号归一化、扩大候选集、增加代码 reranker 或按任务类型精排，都是下一版方案，只有在内部离线集验证后才能谈权重和收益。

### Q59. 怎样控制 GraphRAG token 爆炸和 Lost in the Middle？

**口语化回答**：

> 当前用 Seed 上限、最大 Hop、最大扩展节点/关系/社区数和 Source Chunk Budget 控制规模；扩图按边类型和 confidence 降权，但不是把所有低置信边硬过滤。还要主动说明：默认 8000 主要约束 Source Chunk，后面仍会追加 Community Summary 和 Graph Facts，所以不是最终 Prompt 的硬上限。下一版应按模型 Tokenizer 给 System、源码、图、社区和输出分别留预算，打包后再精算和按证据优先级降级。

### Q60. 当前社区检测到底用 Louvain 还是 Leiden？为什么还要做社区检测？

**口语化回答**：

> 我先纠正一个容易说错的点：当前代码不是 Leiden 优先，而是优先跑 NetworkX Louvain，固定 seed；Louvain 异常后才尝试 graspologic Leiden，再失败就退到 greedy modularity，没有边时按 connected components。部分旧设计稿把顺序写反了，面试要按当前实现讲。
>
> 为什么还要做社区检测？因为几十万代码节点直接展示没有阅读价值，我们要根据 calls、routes_to、imports、inherits 等加权关系，把耦合紧密的符号组织成模块视图，辅助 overview、Wiki 目录和远端摘要。它只是辅助信号，不能覆盖目录、包、模块这些确定性边界。社区结果受边权、confidence 和 resolution 影响，所以还限制社区规模和总数，并用确定性规则生成基础名称，LLM 只做可选重命名。

### Q61. 为什么不用 Neo4j，而用 SQLite/PostgreSQL 存图？

**口语化回答**：

> 当前目标是单用户、本地优先，关系表便于和 Repo、Wiki、Chunk 共用一套存储与运维。代价是在线 GraphRAG、Callers/Trace 等路径目前会先读取全量 Graph，GraphRAG 还读取全量 Chunk，再在内存扩展；大仓多人查询会成为瓶颈。Neo4j 更擅长复杂路径，但会增加部署和双存储一致性。下一版先把邻接查询下推数据库、按 Frontier 取边并测 P95，再决定是否需要专用图数据库。

### Q62. 增量更新完整流程是什么？

**口语化回答**：

> 这题我会先把结论说清楚：读取上次 repo metadata 和 commit；能做 git diff 时拿候选路径，再用 SHA256 兜底判断 add/modify/delete/unchanged；仅重新解析变化文件，删除旧 symbols，恢复未变符号；重建受影响图并更新 metadata；根据 source refs 和变更路径标记 wiki missing/stale/dirty，再选择性再生成。当前性能报告表明解析增量做到了，但图和社区仍较接近全量。

### Q63. 如何支持多个 branch、tag 和历史 commit？

**口语化回答**：

> 当前 CodeWiki 主要索引工作树或当前 Commit，不能说已经完整支持历史查询。把索引身份扩为 `repo_id + revision`、共享 content-addressed AST/chunks、保存 snapshot 或 base+delta，并增加显式 revision 查询与历史 GC，都是下一版设计，不是当前能力。

### Q64. 一条代码修改后，向量怎样更新和删除？

**口语化回答**：

> 当前 Chunk ID 由 repo、node、文件、起止行和内容 hash 生成；内容变化会产生新 ID，`sync_code_chunks` 删除旧项并写新项，Embedding 记录再按 Chunk 变化同步。这里不能说 FTS、主表和所有向量物理表总在同一个事务里原子切换；异常顺序下仍要考虑孤儿向量。主 Chunk 表应是重建依据，生产化再补 Manifest、状态和对账。

### Q65. 更换 embedding 模型或维度怎么办？

**口语化回答**：

> 这题我会先把结论说清楚：embedding 记录必须带 provider/model/dimension/normalization/version。维度或模型变化不能混在同一索引中比较；新建 versioned index，后台双写/回填，抽样验证质量后原子切 alias，最后删除旧版本。迁移期间查询按 index version 路由，失败可回切。

### Q66. Wiki 如何保证源码引用不是模型编造的？

**口语化回答**：

> 当前源码会在生成前计算 `allowed_source_refs`，Prompt 只提供允许引用；模型返回结构化 content/source refs，服务端再验证引用 ID、Repo、行号和 Markdown Citation。Mermaid 尽量由 Graph Facts 生成，校验失败会 Repair Retry 或拒绝保存。这是项目机制，个人负责了哪一段仍需 RACI 和变更记录证明。

### Q67. 有引用就代表答案正确吗？

**口语化回答**：

> 不代表。当前引用校验主要证明引用可解析和可追溯，不能证明它支持结论，也不能排除断章取义和漏掉反例。Citation entailment/precision、source coverage、answer correctness 和逐条 claim→evidence 验证属于需要补齐的质量评测，不能说成已经实现。

### Q68. LiteLLM 在项目里解决什么？

**口语化回答**：

> 这题我会先把结论说清楚：统一不同模型供应商接口、profile、超时和调用记录，便于 catalog/wiki/QA 使用不同模型。它不自动解决质量路由；模型选择仍要依据任务、离线评测、成本和 SLA。生产还需限制重试、并发、速率、熔断和 fallback，记录 model/prompt/version/token/latency。

### Q69. LLM cache 应缓存什么？有哪些失效条件？

**口语化回答**：

> 当前 Cache Key 会结合任务、输入哈希、模型和 Prompt Version 复用已经成功的 LLM Run。它是“查缓存、调用模型、写结果”的 read-through 流程，没有同 Key singleflight 或 in-flight lease，所以两个相同请求同时首次进入仍可能重复调用模型。下一版单机按 Key 合并请求，多实例用数据库唯一租约；代码 Revision、Schema 和保留归档也要纳入失效治理。

### Q70. CodeWiki 的 MCP server 应暴露哪些工具？

**口语化回答**：

> 当前 MCP 入口复用项目已有的分析、检索、图查询、Ask 和 Wiki 能力。面试时我会按实际 Tool Schema 说明现有工具，不凭设计稿补造。更细的 symbol search、call trace、affected files 拆分，以及 revision、权限、写操作确认和 bounded evidence 契约，属于下一版治理方向。

### Q71. MCP 接入后最大的安全风险是什么？

**口语化回答**：

> 仓库内容本身可能包含间接提示注入。当前页面生成由服务端预读文件，引用范围也会校验，这减少了任意工具调用和伪造路径；但 Prompt 没有完整的不可信仓库隔离策略，系统也不是成熟多租户服务。生产化要把仓库文本明确标成数据，限制模型工具与出网，按用户授权过滤 Repo，并补 Secret/DLP 和恶意仓库回归集。合法引用只能证明位置存在，不能证明没有服从恶意指令。

### Q72. VS Code 为什么有 379 万条边？会有什么问题？

**口语化回答**：

> 大量 reference/call/import 候选和高 Fan-out 会拖慢持久化、社区检测和在线查询，也增加噪声。当前可以按边类型、confidence、最大 Hop 和节点数限制扩展，但低置信边主要是降权，并没有完整分层图和按需弱边索引。分类型统计、限制高出度、确定性边常驻和弱边按需计算，是我根据压测提出的下一版方向。

### Q73. 性能报告能得出哪些结论，不能得出哪些？

**口语化回答**：

> 现有性能报告只能说明指定机器和版本下，Rust、VS Code、Superset 的扫描、解析、节点边规模、耗时与增量复用率。它不能证明线上 P95、并发、内存峰值、检索准确率、文档质量或跨机器复现；部分运行的 SQLite 归档也不完整。报告是谁执行、我是否参与分析，要按实验记录回答。

### Q74. 多用户同时分析仓库，怎样调度？

**口语化回答**：

> 当前 Analyze API 创建 Run 后把任务放进 FastAPI `BackgroundTasks`，同进程 Repo Lock 能串行写入；但 active-run 的“先查再创建”不是原子操作，服务重启也不会自动接管任务。现在不能说已有持久队列、lease、heartbeat、取消和阶段 checkpoint。团队服务化时才把 Analyze/Wiki/Embedding 统一成持久 Job，Web 只入队，Worker 用租约和心跳执行，并按租户、Repo 和 Provider 做并发配额。

### Q75. 索引私有仓库时如何保护 secret？

**口语化回答**：

> 当前 Scanner 会跳过符号链接、二进制和超大文件，但接口允许本地路径以及 http/https/ssh/git/file 等 URL，没有完整认证、Host Allowlist、私网阻断、Clone Timeout、仓库总大小和租户隔离。`git clone` 用参数数组避免了常见 Shell 拼接注入，但不等于私有仓已经安全。服务化时要禁任意本地/file URL，限制 Git Host 与私网访问，把 Clone 放低权限沙箱，并用短期凭证、Secret Scanner、磁盘和时间配额治理。

### Q76. 恶意仓库能怎样攻击解析服务？

**口语化回答**：

> 风险包括超大仓库耗尽磁盘/CPU、恶意编码和 Parser Crash、路径与 URL 访问、Markdown/Mermaid XSS、提示注入。当前有部分文件大小、二进制和 symlink 保护，但没有完整 Clone 超时、总字节、CPU/内存沙箱和服务模式 URL 治理。因此我会先说现状，再把低权限工作区、网络默认关闭、资源预算、渲染 sanitize 和逐文件隔离作为生产化补项。

### Q77. React 前端不是“花活”，它解决什么核心工作流？

**口语化回答**：

> 这题我会先把结论说清楚：仓库注册和分析状态、图谱从 overview 到文件/符号下钻、问答结果与节点高亮联动、Wiki 目录/文章/source navigation、设置模型 profile。面试中强调前端用于验证可用工作流和可追溯性，而不是把“全栈”理解成写了几个页面。

### Q78. 测试策略怎样覆盖这个项目？

**口语化回答**：

> 当前仓库能看到 Parser、Graph Resolver、Incremental、Retrieval、Wiki、API/CLI/MCP 和存储集成等测试，约 196 个后端 test function 只是数量信号，质量仍看风险覆盖和实际执行结果。源码存在测试不等于这些测试由我编写或每次发布都运行；我的测试贡献和真实门禁要用 Commit、CI 或发布记录说明。

### Q79. 项目用了多少 AI 生成代码？

**口语化回答**：

> 我不会为了显得代码都是手写的去报一个假比例，也不会把一套理想流程冒充成自己每次都做过。现场我会拿一个真实变更回答：AI 生成了 **[填写]**，我实际修改了 **[填写]**，执行过的验证是 **[填写真实命令/结果]**，Review、合并和发布分别由 **[填写]** 负责。源码里存在 lint、typecheck、test 或 build，不等于这些门禁都由我运行。对我在 RACI 中真实负责的代码，我可以解释数据流、失败模式和验证证据；线上责任仍按实际发布与运维分工回答。

### Q80. 下一版最值得做什么？

**口语化回答**：

> 这题我会先把结论说清楚：下一版第一优先级是质量 benchmark，先证明图在什么任务上真正有价值；第二是差量图和社区更新，解决文件复用 99% 但整体仍然慢的问题；第三是 revision-aware index；第四是 MCP 安全和多租户；第五是把 CodeWiki 做成 Coding Agent 的结构化工具层。当前最大的未知是质量和性能，所以我不会优先继续堆语言和 UI。

## 6. 项目三：Agent Memory 与上下文卸载（Q81-Q115）

> 本节先按当前源码说明 Agent Memory 的机制，再单独回答个人贡献。源码能证明两条链路、数据结构和调度行为，不能证明这些模块都由本人设计、实现或上线。个人部分统一按分阶段 RACI 填写：直接负责 **[填写]**、协作 **[填写]**、最终评审/发布 **[填写]**；未核实前只讲项目事实。

### Q81. 整体架构分哪两条链路？

**口语化回答**：

> 从当前源码看，长期记忆链路是：host adapter 捕获对话→L0 recorder 保存原文→L1 extractor 抽原子记忆并去重→L2 scene 聚合场景→L3 persona 生成画像→auto-recall 检索并注入。短期链路是：hook 捕获 tool call/result→原文写 refs/JSONL→生成或更新 Mermaid 状态→token tracker 判断 mild/aggressive/emergency→主上下文保留引用和 MMD，需要时下钻原文。SQLite/TCVDB 是可替换存储，OpenClaw/Hermes/standalone 是不同 Host 适配。这是项目架构，不等于整条链路都由我实现。

### Q82. L0 为什么不能只存模型摘要？

**口语化回答**：

> 当前源码把 L0 作为偏追加式原始证据，保留 session、message、role、时间和来源等信息，因为摘要有损且可能出错，没有原文就难以重抽取和纠错。源码能证明原文保留与上层抽取关系；完整 retention、加密、用户隔离和删除传播仍是生产化治理项，不能说成当前已经闭环。

### Q83. L1 原子记忆应该长什么样？

**口语化回答**：

> 当前一条 `MemoryRecord` 只表达一个原子记忆，核心字段包括 id、content、`persona/episodic/instruction` 类型、priority、scene name、`source_message_ids`、metadata、timestamps、创建更新时间和 session 标识。`priority` 表示重要程度，不是事实置信度；`source_message_ids` 也不是逐字 span。Embedding 模型信息属于存储 Manifest，不是每条 L1 都带一套可信度和模型版本字段。

### Q84. 去重和冲突为什么不是一回事？

**口语化回答**：

> 去重是判断新原子记忆和已有候选是否应该 store、skip、update 或 merge；当前先用关键词或向量找相似候选，再让 LLM 做决策。冲突治理还需要知道实体、属性、作用域和时间，例如“当前城市改变”与“出生地矛盾”不是同一种情况。当前源码没有这套结构化属性 Schema、conflict 状态和事实置信度，所以只能说已有候选决策，完整时序冲突仍是下一版。

### Q85. L2 Scene 与普通 summary 有什么区别？

**口语化回答**：

> 从当前实现看，Scene 按任务或主题聚合多条 L1，形成可导航的场景 Markdown；Pipeline 通过增量输入和 checkpoint 避免每次从头处理。它和普通一段式 summary 的差别是保留场景结构与导航。Scene 命名稳定性和防碎片化属于需要持续验证的质量问题，不是已经证明的个人设计成果。

### Q86. L3 Persona 为什么低频更新？

**口语化回答**：

> 这题我会先说结论：Persona 是跨场景的稳定偏好、身份和习惯，单次对话不应轻易改写，所以更新频率低于 L1/L2。当前实现通过较高触发阈值、场景聚合和已有 persona 输入控制更新频率；还没有一套完整的时间衰减硬逻辑。召回时也不能把 persona 当系统真理，当前明确指令永远优先。

### Q87. 为什么需要 Warm-up 调度？

**口语化回答**：

> 当前调度实现包含 warm-up：早期从较低阈值开始，触发后逐步增加，达到正常 `everyNConversations` 后进入稳定阶段；相关进度进入 checkpoint。它解决的是早期可用性与后期调用成本的平衡。这个机制可从源码说明，但由谁提出、实现和验证仍按 RACI 回答。

### Q88. L2 为什么同时有最小间隔和最大间隔？

**口语化回答**：

> 当前 L2 调度同时设置最小与最大间隔：最小间隔限制高频重复调用，最大间隔避免低频会话长期不聚合；源码默认值约为 900 秒和 3600 秒。这只是工程默认，不是生产最优参数，实际值需要根据真实流量、成本和质量评测调整。

### Q89. 为什么 L1/L2/L3 各用串行队列？

**口语化回答**：

> 这题我会先说结论：同一层并发执行会重复消费 cursor、互相覆盖 persona/scene 或制造乱序。SerialQueue 保证层内顺序，running 时新触发只标 pending，当前完成后合并再跑，避免无限排重复任务。跨层仍需依赖关系：L2 只消费已持久化 L1，L3 只基于稳定 L2。

### Q90. checkpoint 要保存什么，怎样恢复？

**口语化回答**：

> 从当前源码看，checkpoint 保存 Session 级 cursor、conversation count、warm-up threshold、last run/next timer、Pipeline 状态和版本等调度进度，并通过临时文件与 rename 降低半写风险。恢复时仍要校验 cursor 和底层数据；运行中状态不能直接当成功。Checkpoint 记录的是调度水位，不替代 L0/L1/L2/L3 业务数据本身。

### Q91. 为什么定义 Store capability，而不是到处判断 SQLite/TCVDB？

**口语化回答**：

> 当前 Store 抽象让上层面向 put/list/search/delete 和 supportsVector/FTS/nativeHybrid 等能力，factory 再按配置实例化后端。SQLite 可以走本地 FTS、vector 与 RRF，TCVDB 可以走服务端 hybridSearch；核心 Recall 因而不需要到处判断后端名称。这是源码结构，个人是否负责接口定义或某个后端实现要单独举证。

### Q92. SQLite 本地后端怎样做混合检索？

**口语化回答**：

> 这题我会先说结论：L1/L0 主记录存在 SQLite；FTS5 提供关键词/BM25 排名，sqlite-vec 存 embedding 做相似度；中文关键词用 jieba 分词；两路并行取 candidate K，按 record id 用 RRF 合并，取 top K。embedding 不可用时降级 FTS，FTS 不可用时可只走 vector，必须在 trace 中标明降级。

### Q93. TCVDB 后端的差异是什么？

**口语化回答**：

> 从当前源码看，云后端支持 collection、dense/sparse 向量、native hybridSearch 和 RRFRerank；它在能力上更适合共享存储与更大数据量，但源码支持不等于已经完成多实例生产部署。Collection Schema、网络超时、批量 upsert、幂等、租户过滤和服务降级仍要结合真实环境验证，不能把“可配置”说成“已投产”。

### Q94. RRF 的 `k=60` 有什么意义？

**口语化回答**：

> 当前实现的 RRF 默认 `k=60`，它用于平滑头部名次差异；k 越小，第一名优势越大，k 越大，共同出现在多路结果中的价值相对更明显。60 是经典默认，不是项目已经调优出的最优值；在自有 labeled queries 上比较 Recall/NDCG 才是下一步验证方式。

### Q95. 中文 BM25 用 jieba 有什么问题？

**口语化回答**：

> 这题我会先说结论：用户名、产品名、代码标识符和中英混写可能切错；新词词典不全；文档和 query 分词必须一致。应支持业务词典、保留英文/数字/下划线 token、观察零召回 query；对于精确实体，可增加原串/n-gram 字段。BM25 sparse vector 的 IDF 还依赖语料统计，更新语料时要考虑重算。

### Q96. 召回结果怎样注入，避免反而污染上下文？

**口语化回答**：

> 当前自动 Recall 根据 Query 做关键词、向量或 Hybrid 检索并取 Top K，再把相关 L1 作为历史参考注入；Persona 和 Scene Navigation 走稳定上下文。当前用户明确表达优先于旧记忆。我要主动说明，当前不是完整多租户系统，也没有事实置信度和冲突状态可供“低置信硬过滤”；生产化才会增加可信 tenant/user 作用域、独立 evidence confidence、时间过滤、冲突展示和完整 Retrieval Trace。

### Q97. context offload 的数据流是什么？

**口语化回答**：

> 从当前 Context Offload 源码看，after-tool-call 捕获 tool use/result，完整结果先写入 `refs/*.md`，随后把工具调用、摘要、`result_ref` 和 `tool_call_id` 写成 OffloadEntry；同一任务的多条 Entry 再聚合成 MMD，并把 node_id 回填 JSONL。进入模型前计算 Token，必要时把旧 tool result 替换成带 summary、node_id 和 result_ref 的 stub，再注入 active MMD。当前机制是外移但可恢复，不是不可逆删除。

### Q98. mild/aggressive/emergency 三档是什么？

**口语化回答**：

> 这题我会先说结论：当前默认 context window 200k；mild 在 50% 左右开始优先卸载低价值 tool result；aggressive 在 85% 附近删除更大范围旧消息，目标删除比例约 40%，并用历史 MMD 补状态；emergency 在 95% 附近触发，压到约 60% 以避免 overflow。阈值是工程默认，必须按模型真实窗口、系统 prompt 和输出预留动态计算，不能背数字后当通用真理。

### Q99. 压缩为什么要保护 tool call/result 配对？

**口语化回答**：

> 当前压缩逻辑会保护 assistant tool_use 与后续 tool_result 的配对，避免只删一半导致请求 Schema 非法或模型误解；同时保护最近用户消息、System、MMD Marker 和最小尾部消息。多工具并行、失败、重试和跨边界场景属于必须核对的测试范围；只有真实测试记录能证明覆盖到什么程度。

### Q100. Mermaid MMD 应插在上下文哪个位置？

**口语化回答**：

> 当前实现把 MMD 放在最近 User Message 之后、ongoing tool loop 之前，并避免切开 Tool Pair；历史 MMD 位于 active MMD 前，形成 history→active→recent loop。这是源码中的位置策略，不代表已经证明最优，仍需通过长任务评测比较下钻成功率和任务完成率。

### Q101. MMD 会不会只是“看起来结构化”，但模型仍找不到原文？

**口语化回答**：

> 这题我会先说结论：会，所以任务导航和证据恢复必须分开。节点不是按一次调用切一个，而是同一意图的多条 OffloadEntry 聚合成宏观节点；每个 `tool_call_id` 又必须通过 `node_mapping` 回填到一个 node_id。MMD 只负责告诉模型“做过什么、结论和状态是什么”，真正的证据链是 `node_id -> offload JSONL -> result_ref -> refs 原文`。还要单独评测下钻成功率和额外延迟，不能只看图是否生成。

### Q102. 被卸载内容后来突然重要，怎样找回？

**口语化回答**：

> 当前源码中，压缩后的 tool result stub 带 summary、node_id 和 `result_ref`；需要精确错误、行号或参数时，可以直接读取 ref。若只拿到 MMD 的 node_id，则先查 Offload JSONL 找到对应记录，再读取目标 `result_ref`。当前没有独立分类器自动判断哪条原文会再次重要；“早期细节很久后重新重要”仍需专门评测。

### Q103. 为什么同时有 tiktoken 和 fast estimate？

**口语化回答**：

> 当前实现同时有快速估算和较精确的 Token 计算：远离阈值时用字符、CJK 和 Latin 近似做快速判断，接近 50/85/95% 决策边界时再精算。缓存要在消息变更后失效，模型切换时也要匹配 Tokenizer。近似值用于决策短路，不等于可直接作为精确成本指标。

### Q104. 模型真实上下文不是 200k，默认值会怎样？

**口语化回答**：

> 这题我会先说结论：错配会过早压缩或直接 overflow。优先从模型 metadata/gateway 获取输入上限，并扣除 system/tools、MMD 和最大输出预留；路由换模型时重新计算，不能沿用 session 旧阈值。未知模型使用保守配置并打 warning，生产禁止静默假设 200k。

### Q105. Offload 的 L1.5 有什么价值？它是场景检索吗？

**口语化回答**：

> 不是场景检索。Offload 的 L1.5 负责判断当前长任务边界、目标和是否已经结束，给后续 L2 Mermaid 聚合确定 active task。它没有稳定前，系统避免用错误边界生成或注入新的任务图。长期记忆里的 Scene Navigation 是另一条链路，帮助 Agent 决定要不要读取某个 L2 场景正文；两套层级名字相似，但数据结构和调度完全独立。

### Q106. Session GC 怎样避免删掉仍在使用的 ref？

**口语化回答**：

> 当前 GC 会根据存活 JSONL 构建 referenced refs 集合，再清理过期且无引用的文件；active MMD 受保护，并按配置保留一定数量历史 MMD。源码能证明已有引用扫描和清理策略；更严格的跨进程锁、删除对账和完整可观测性属于生产化补项，不能说成已经上线。

### Q107. 记忆系统怎样实现“被遗忘权”？

**口语化回答**：

> 当前还没有完整“被遗忘权”闭环。删除某个 L0 Session 不会自动级联删除已抽取 L1，来源还可能变成无法下钻；远端 Store、向量、Persona、Scene、Backup、Cache 和日志也没有统一删除任务。生产化才会由可信 tenant/user 定位全部派生资产，先停止召回，再用幂等 Job 逐项物理删除、重建 Persona/Scene 并生成审计结果。不能把这套目标方案说成现状。

### Q108. 记忆系统最严重的提示注入是什么？

**口语化回答**：

> 最危险的风险是攻击者把恶意指令写进对话，系统又把它抽成 instruction 或长期内容，后续每轮反复注入。当前抽取 Prompt 有数据与指令边界，L1 也保留来源消息 ID，但没有证据证明已经有完整内容安全分类、actor 鉴别和对抗评测。生产化要把历史记忆明确标成不可信数据，限制它改变 System Policy，写入前做风险分类，工具权限在执行层硬控制，并建立“持久化提示注入”回归集。

### Q109. 多租户隔离应该在哪几层实现？

**口语化回答**：

> 当前项目是 local-first，Offload 的 user ID 还可能退到主机 IP 或 `unknown-host`，它只是路由键，不是可信认证主体。生产化时才由网关签发不可伪造的 tenant/subject，所有主键、查询、Collection、FTS、Cache、Backup 和 Trace 强制带作用域，返回前再做权限校验。不能相信模型、客户端参数或 IP fallback 作为授权依据。

### Q110. 怎样做可观测性？

**口语化回答**：

> 当前有日志、Checkpoint、部分 Trace ID 和 Benchmark 报告，但没有证据证明完整线上看板和每项指标都已落地。目标 Trace 应串联 capture、extract、dedup、persist、recall、inject 和 offload；指标看队列、Checkpoint Lag、召回候选与注入、各层延迟、Token、压缩、下钻和失败。内容必须脱敏并设置采样与保留期。面试中要把“当前可查日志”和“下一版可观测体系”分开。

### Q111. 内部 benchmark 的三组结果能合成一个“准确率提升”吗？

**口语化回答**：

> 不能。WideSearch pass rate、SWE-bench task pass、AA-LCR long-context reasoning 和 PersonaMem persona QA 衡量的不是一件事，样本与基线也不同。我只会按现有报告分别说明离线指标，不把它们揉成一个“准确率提升”，更不会反推线上业务效果；本人是否参与实验也要按运行记录回答。

### Q112. 怎样严格复现 61.38% token 降低？

**口语化回答**：

> 要严格复现 61.38%，下一次实验应固定 Host、插件、模型、工具、Prompt 和 Dataset 版本，对同一任务序列分别运行 Baseline 与 Plugin，记录 Cache、Token、重复次数、方差和失败，并把 Token 与 Pass Rate 联合报告。这是复现实验协议；现有材料缺少的元数据仍要补，不能说成我已经完整执行过。

### Q113. 如何评估长期记忆准确率？

**口语化回答**：

> 这题我会先说结论：数据集包含写入、更新、冲突、遗忘、跨会话、多用户和时效问题；分解为 extraction precision/recall、retrieval Recall@K/MRR、answer accuracy、conflict handling、deletion completeness。避免只问“用户喜欢什么”这种静态题，要测旧偏好被新偏好覆盖、错误记忆是否拒答和来源下钻。

### Q114. 和 Mem0、Letta、Zep 的差异怎么讲？

**口语化回答**：

> 比较 Mem0、Letta、Zep 时，我会按宿主集成、记忆模型、原文保留、结构化层级、检索、冲突/遗忘、Context Offload、部署后端、评测和运维逐项核对。当前源码可证明的辨识点是 L0-L3、短期 Tool Result Offload 和 SQLite/TCVDB 双后端；复杂度、误差传播和 Host Hook 依赖是代价。竞品结论来自公开版本，不是我做过生产对比的经历。

### Q115. 如果上千万用户，怎么扩展？

**口语化回答**：

> 当前源码不能证明已经服务上千万用户。若设计集中式下一版，我会让 Capture 先写耐久事件流，再按 tenant/user/session 分区，分层处理 L1 与 L2/L3，补租户过滤、分片、Persona 并发控制和冷热分层。容量必须从消息量、Embedding 数、写放大、召回 QPS 和 LLM 调用率推导；这整段是扩展方案，不是现状或本人线上经验。

## 7. 2026 AI 应用与 Agent 高频知识（Q116-Q150）

### Q116. Prompt engineering 和 context engineering 有什么区别？

**口语化回答**：

> 如果让我现场回答，我会这么说：Prompt engineering 主要优化指令文本和组织方式；context engineering 管理一次推理实际进入窗口的全部信息：system、tools/MCP、检索数据、历史、memory、示例和中间结果。Agent 多轮循环中，问题从“怎样写一句好 prompt”变成“每一轮选择哪些最小高信号 token”。因此检索、压缩、工具返回设计和记忆治理都属于 context engineering。

### Q117. Workflow 和 Agent 怎样区分？

**口语化回答**：

> 我一般是这么理解的：Workflow 的路径由代码预定义，模型只在节点内完成分类/生成；Agent 由模型根据观察自主选择下一步工具并循环。稳定、可审计、低变化流程优先 workflow；任务步骤不可预知且工具探索价值高时才用 Agent。生产常是混合：外层确定性状态机，局部节点允许 Agent 探索。

### Q118. ReAct loop 的最小闭环是什么？

**口语化回答**：

> 这题我会先说结论：接收目标和当前 state→模型选择 action/tool+args→代码校验并执行→把 observation 写回 state→判断完成/失败/继续。必须有 max steps、总时间/token/cost budget、取消、重复检测和错误分类；终止条件由系统验证，不能仅相信模型说“完成了”。

### Q119. Harness/loop engineer 是什么？

**口语化回答**：

> 如果让我现场回答，我会这么说：Harness 是包围模型的工程运行时：prompt/context、tool contract、loop、state、memory、权限、重试、预算、trace、eval。Loop engineering 关注怎样让“执行→观察→纠错”稳定闭环。它不是社会化协作术语，也不是又一个模型训练方法；模型能力相近时，harness 往往决定任务完成率。

### Q120. 怎样设计一个模型容易用对的工具？

**口语化回答**：

> 我一般是这么理解的：工具单一职责、名称和描述明确、重叠少；参数用强 schema、枚举和清晰单位，避免一个 `options:any`；返回 bounded structured result、stable id、错误码和下一步提示；读写能力分离，高风险操作显式确认；提供幂等键和 dry-run。Anthropic 的 context engineering 指南也强调最小可用工具集和 token-efficient 返回。

### Q121. Function calling 能保证模型参数正确吗？

**口语化回答**：

> 这题我会先说结论：Schema 只能保证一定程度的结构，不保证语义、权限和业务有效性。服务端仍要验证范围、资源归属、路径、金额、SQL、幂等和授权；未知字段拒绝，错误返回机器可理解但不泄密。模型是非可信调用方，和公网客户端采用同一零信任原则。

### Q122. Structured output 为什么仍会失败？

**口语化回答**：

> 如果让我现场回答，我会这么说：模型/provider 不完全支持、流式中断、schema 太复杂、枚举外值、长度截断、语义自相矛盾。使用原生 constrained decoding 时仍做 Pydantic/Zod 校验；失败区分可修复语法和业务错误，有限 repair retry；关键字段由确定性工具填充。不要用正则从自由文本“抢救”高风险动作。

### Q123. MCP 的 host、client、server 分别是什么？

**口语化回答**：

> 我一般是这么理解的：Host 是用户运行的 LLM 应用，控制安全和用户体验；client 是 host 内针对某个 server 的连接器；server 提供 resources/prompts/tools。一个 host 可有多个 client/server 连接。server 不应默认看到 host 的全部上下文，host 决定暴露什么。

### Q124. Resources、Prompts、Tools 的差别？

**口语化回答**：

> 这题我会先说结论：三者最重要的区别是交互控制方，不是简单按读写分。Resource 是应用选择读取的 URI 化上下文；Prompt 是用户选择的模板化消息；Tool 是模型决定调用的能力，既可以是只读查询，也可以有副作用。高风险 Tool 要确认和审计，Resource 同样要鉴权；不能因为名字叫 Resource 就默认安全，也不能说所有只读能力都必须做成 Resource。

### Q125. MCP 初始化时为什么要 capability negotiation？

**口语化回答**：

> 如果让我现场回答，我会这么说：不同版本/实现支持的 resources、tools、sampling、roots、elicitation 等不同。双方初始化协商能力和协议版本，之后只能使用已声明能力；未知能力要优雅降级。不能仅凭工具名字猜 server 支持什么，也不能忽略版本兼容。

### Q126. 什么是 token passthrough，为什么 MCP 明确禁止？

**口语化回答**：

> 我一般是这么理解的：server 接收一个不是为自己签发的上游 token，再直接转给下游 API，就是 passthrough。它绕过 audience、限流、审计和服务边界，泄露后可横向使用。MCP server 必须验证 token 是为本 server 签发，并用自己的下游凭证或 token exchange，最小 scope 调用第三方。

### Q127. 什么是 confused deputy？

**口语化回答**：

> 这题我会先说结论：MCP proxy 作为第三方 API 的合法 client，却被恶意 MCP client 借其身份完成未授权操作。典型是共享 static client id 和已有 consent cookie 导致用户授权被跳过。防护是每 client 显式 consent、严格 redirect URI/state/CSRF、服务端保存授权绑定和最小 scope。

### Q128. MCP 还要防哪些新风险？

**口语化回答**：

> 如果让我现场回答，我会这么说：OAuth metadata/endpoint 引发 SSRF；session id 被窃取后注入事件或冒充；恶意 authorization URL 导致 XSS/RCE；本地 stdio server 执行任意二进制；scope 过宽；tool description 不可信。措施包括 HTTPS/egress allowlist、随机且绑定用户的 session、每请求鉴权、CSP/URL 校验、本地 server 安装确认、sandbox 和渐进授权。

### Q129. Durable execution 是什么？

**口语化回答**：

> 我一般是这么理解的：把 Agent/workflow 的状态和每步结果持久化，进程崩溃、等待人工或长时间暂停后从 checkpoint 恢复，而不是从头重跑。恢复通常会 replay，因此节点必须 deterministic，副作用封装成幂等 task；随机数、当前时间、外部调用结果要被记录，不能在 replay 时重新产生不同结果。

### Q130. Thread checkpoint 和 long-term store 有何不同？

**口语化回答**：

> 这题我会先说结论：checkpoint 保存某次 thread/run 的短期 state 和执行位置，服务于恢复和多轮；store 保存跨 thread 的用户/应用记忆。删除一个 thread 不一定删除长期记忆，二者 retention/权限也不同。把全部历史都塞 checkpoint 会膨胀，把 workflow 游标塞长期向量库则难以一致恢复。

### Q131. 语义、情景、程序性记忆怎样理解？

**口语化回答**：

> 如果让我现场回答，我会这么说：Semantic 是事实和概念，如偏好；episodic 是发生过的事件/成功轨迹；procedural 是怎样做事的规则、prompt、policy。三类写入、更新和召回时机不同：事实可按 query 检索，事件用于相似任务示例，程序性规则应高权限版本化，不能由普通用户对话随意改写。

### Q132. Compaction 的核心评测目标是什么？

**口语化回答**：

> 我一般是这么理解的：不是压缩率最大，而是给定 token budget 下保持任务成功。先追求关键约束/决策/未完成项/证据引用的 recall，再减少冗余提高 precision；测 token、pass rate、恢复下钻率和延迟。最安全的第一步通常是清理陈旧 tool result，而不是把全历史总结成一段不可恢复文本。

### Q133. 一个完整 RAG 链路有哪些步骤？

**口语化回答**：

> 这题我会先说结论：离线：采集→解析/OCR→清洗/权限 metadata→结构化切块→embedding/FTS index→版本与删除。在线：query 分类/改写→权限过滤→多路召回→融合/rerank→上下文选择与引用→生成→groundedness/格式校验→trace/feedback。线上还需增量更新、回滚、评测和数据删除，不是“向量库+prompt”两步。

### Q134. Chunk size 怎样选？

**口语化回答**：

> 如果让我现场回答，我会这么说：先按文档/代码结构边界，再把 token 上限作为约束。小块检索精但上下文不足，大块完整但噪声大；可用 parent-child：小块命中，返回父块。用领域 query-gold evidence 数据对不同 chunk/overlap 做 Recall@K、MRR、context precision 和端到端答案评测，不能只背 256-512 token。

### Q135. Embedding 模型怎样选？

**口语化回答**：

> 我一般是这么理解的：看领域语言、query/document 非对称性、最大长度、维度、吞吐、部署/隐私和许可；MTEB 只做初筛，最终在自有数据测 Recall@K/MRR/NDCG、延迟和成本。还要明确 similarity、归一化、是否有 instruction prefix；模型升级需要版本索引和迁移。

### Q136. Hybrid retrieval 和 rerank 各解决什么？

**口语化回答**：

> 这题我会先说结论：BM25 擅长精确词/编号，dense 擅长语义同义；RRF 合并两路 rank，提升候选 recall。Reranker 对 query-document 对做更贵的联合打分，提升前几名 precision。典型是各路 top 50→RRF 50-100→cross-encoder top 5-10；参数由 latency/quality curve 选择。

### Q137. HyDE/Multi-query/Query decomposition 什么时候用？

**口语化回答**：

> 如果让我现场回答，我会这么说：HyDE 对短而抽象 query 先生成假设文本再 embedding，但可能把错误假设带入；multi-query 用多种表述提高 recall，但成本和重复上升；decomposition 适合多条件/多跳问题，把子问题分别检索再合并。先做失败分类再启用，不应所有查询固定多次调用模型。

### Q138. 回答错了，怎样定位是检索还是生成？

**口语化回答**：

> 我一般是这么理解的：保存 trace：query rewrite、各路候选/分数、rerank、最终 context、prompt、output。先看 gold evidence 是否在 top K：不在是 retrieval/index/chunk 问题；在候选但未入 context 是 rerank/budget；在 context 但答案不忠实是 generation/prompt；答案忠实但文档错是数据问题。分层指标避免盲目换模型。

### Q139. RAG 评测至少有哪些指标？

**口语化回答**：

> 这题我会先说结论：检索：Recall@K、Precision@K、MRR、NDCG；上下文：relevance、coverage；生成：faithfulness/groundedness、answer correctness/relevance、citation precision/recall；系统：任务成功、拒答、延迟、成本。LLM-as-judge 需 rubric、校准集和人工抽检，不能把 judge 分数当绝对真值。

### Q140. Microsoft GraphRAG 的 Local/Global/DRIFT/Basic 有何差异？

**口语化回答**：

> 如果让我现场回答，我会这么说：Local 用实体图+原文回答具体实体问题；Global 对 community reports map-reduce，适合全局主题但成本高；DRIFT 用社区信息拓宽 local 起点并生成后续问题；Basic 是普通 vector RAG baseline。CodeWiki 的实现借鉴图扩展和社区摘要，但不是 Microsoft GraphRAG 的逐项复制，不能混称。

### Q141. Prompt injection 与 jailbreak 有何关系？

**口语化回答**：

> 我一般是这么理解的：Prompt injection 是非可信输入改变模型行为，既可直接来自用户，也可间接来自网页/文件/RAG；jailbreak 通常指使模型绕过安全策略的一类 injection。核心风险取决于 Agent 有多少数据和工具权限。没有万能检测器，目标是最小权限、数据/指令隔离、审批、输出检查和持续红队降低影响。

### Q142. RAG 怎样实现文档级权限？

**口语化回答**：

> 这题我会先说结论：ACL 在索引 metadata 中与 chunk 绑定，检索请求由服务端身份生成 tenant/user/group filter，在 ANN/FTS 查询阶段就过滤；rerank/context 再校验。不能先全库召回再让模型“不要回答”，分数/标题本身也可能泄露。权限变化要及时更新索引或查询时联表。

### Q143. Hallucination 和 nondeterminism 有什么区别？

**口语化回答**：

> 如果让我现场回答，我会这么说：Nondeterminism 是同输入输出可能变化，变化不一定错误；hallucination 是输出缺乏事实/上下文支持或与真值冲突。temperature=0 也不能保证无幻觉，provider/kernel/模型仍可能变化。分别用稳定性重复测试和 grounded correctness 评测。

### Q144. RAG、fine-tuning、long context 怎样选？

**口语化回答**：

> 我一般是这么理解的：需要更新知识、私有数据和引用时优先 RAG；要改变风格、格式、任务策略或让小模型学行为时 fine-tune；一次性文档且规模可控可直接 long context。常见组合是 fine-tune 行为+RAG 事实+context engineering 控制预算。选择依据是错误类型、更新频率、成本和审计，不是潮流。

### Q145. 设计模型路由器需要哪些特征？

**口语化回答**：

> 这题我会先说结论：静态：任务类型、语言、模态、长度、结构输出、工具和安全等级；动态：供应商健康、P95、限流、价格、剩余额度；历史：同类任务 quality posterior。决策输出 model/profile/reason/version，可审计；特征不可包含敏感原文时用派生分类。100ms 路由通常依赖本地规则/轻模型和缓存，而非再调用大模型。

### Q146. Fallback 怎样避免级联故障？

**口语化回答**：

> 如果让我现场回答，我会这么说：健康状态来自滑动窗口错误率/延迟和主动探测；只对可重试错误切换，限制每请求总尝试和总 deadline；备用模型预热并验证 schema/tool compatibility；用 circuit breaker+half-open，带 jitter；避免所有流量瞬间涌向一个备份。降级模型能力不足时应降功能或返回可解释失败，不假装等价。

### Q147. Prompt cache 和 semantic cache 有何区别？

**口语化回答**：

> 我一般是这么理解的：Prompt/provider prefix cache 复用相同前缀的 KV/计费，要求稳定 system/tools 前缀；semantic cache 在应用层把相似 query 映射到旧结果。前者一般不改变语义，后者可能返回错误上下文，必须带 tenant、数据版本、模型/prompt version、TTL 和高阈值。含权限或实时数据的回答慎用 semantic cache。

### Q148. Trace grading 比只评最终答案多了什么？

**口语化回答**：

> 这题我会先说结论：它给完整 Agent trace 的工具选择、参数、步骤、权限和恢复行为打结构化标签，可定位“答案碰巧对但过程危险”或“最终错在某一步”。OpenAI 当前文档强调 trace grading 用于规模化找 orchestration 错误和回归。过程指标不能替代最终结果，两者联合。

### Q149. 怎样建立能持续使用的 eval 数据集？

**口语化回答**：

> 如果让我现场回答，我会这么说：从真实日志按失败类型采样，去敏后由领域专家标 gold evidence/answer/allowed tools；覆盖正常、边界、对抗、拒答和历史回归；按 train/dev/test 防止调参泄漏，版本化数据、grader、模型和环境。每次发布跑核心集，线上新 bad case 经过审核再加入，避免只收简单成功样本。

### Q150. AI 系统如何同时优化质量、延迟和成本？

**口语化回答**：

> 我一般是这么理解的：先设质量/SLA 硬约束，再看 Pareto frontier。减少无用上下文和工具返回；简单任务小模型/规则，复杂任务升级；并行独立检索/工具但控制 fanout；缓存稳定前缀/embedding；设置 early exit、timeout 和 budget；批量离线工作。每项优化用相同 eval 对比 quality、P50/P95、token 和实际费用，不能只看一个维度。

## 8. 后端与系统设计基本功（丰泊 Java 补充 + Q151-Q185）

### 8.0 丰泊国际新增：Java / React 硬门槛速答（J1-J22）

这组题不是为了把总览扩成完整八股文，而是修复丰泊场暴露的连续失分。详细版本见 [丰泊国际完整面试整理](../../面试分析/丰泊国际-Java后端-AI应用岗-面试整理与答案.md) 的第二章，这里保留现场必须能直接说出的口语化主干。

**J1. `@Autowired` 和 `@Resource` 有什么区别？**

> `@Autowired` 是 Spring 注解，默认按类型找 Bean，有多个候选时再配合 `@Qualifier` 或 `@Primary`；`@Resource` 是 Jakarta/JSR-250 注解，语义上优先按名称匹配。底层分别主要由 `AutowiredAnnotationBeanPostProcessor` 和 `CommonAnnotationBeanPostProcessor` 处理。实际业务里我更推荐构造器注入，依赖显式、方便测试，字段也可以保持 `final`。

**J2. `ThreadLocal` 是什么，在线程池里有什么坑？**

> `ThreadLocal` 是给同一个线程保存一份独立上下文，常见是 traceId、租户或请求信息，它不是让共享对象自动线程安全。线程池会复用线程，所以必须在 `finally` 里 `remove()`；否则除了内存泄漏，还可能把上一个请求的用户上下文带到下一个请求。异步切线程时也不能假设它会自动传播。

**J3. Java 8 的 `ConcurrentHashMap` 怎么保证并发安全？**

> Java 8 已经不是 Segment 方案。空桶插入主要靠 CAS，发生哈希冲突后对桶头做细粒度 `synchronized`，读取依赖 volatile 可见性，链表达到阈值后可能树化，扩容时多个线程可以协助迁移。容器线程安全不代表多步业务操作原子，`containsKey` 再 `put` 仍有竞态，要用 `putIfAbsent` 或 `computeIfAbsent`。

**J4. `ReentrantLock`、可重入和 AQS 是什么关系？**

> 可重入就是同一个线程拿到锁后可以再次获取，内部记录持有线程和重入次数；释放几次才真正解锁。`ReentrantLock` 是具体锁，AQS 是它底层的同步器骨架，用一个 `state`、CAS 和 FIFO 等待队列管理获取与释放。它比 `synchronized` 多了可中断、超时、公平锁和多个 Condition，但也必须在 `finally` 里主动 unlock。

**J5. Spring 事务传播主要解决什么？**

> 它解决的是一个带事务的方法调用另一个事务方法时，到底加入当前事务、创建新事务、挂起旧事务还是禁止事务。最常用的是 `REQUIRED`，有就加入、没有就新建；`REQUIRES_NEW` 会挂起外层并新开事务；`NESTED` 通常基于保存点。还要补一句：同类内部 `this.method()` 可能绕过代理，事务注解不生效。

**J6. 幂等怎么保证？**

> 幂等不是保证请求只来一次，而是同一个业务请求重复执行，最终只产生一次业务效果。我会用业务幂等键和数据库唯一索引做最终兜底，再配合状态机和结果复用；消息消费用 eventId 去重。分布式锁只能减少并发，不能替代唯一约束，也不能单独证明端到端幂等。

**J7. 微服务分布式一致性怎么做？**

> 先看业务不变量，能放进同一个数据库强一致边界就不要拆。跨服务大多数场景我会用本地事务写业务表和 outbox，后台可靠发 MQ，消费者按 eventId 幂等，失败重试、死信、补偿和对账，保证最终一致。长流程再按场景考虑 Saga 或 TCC，不能一句“上分布式事务”就结束。

**J8. Minor GC 和 Full GC 有什么区别？**

> Minor 或 Young GC 主要回收年轻代，频率高、一般停顿短；Full GC 通常处理整个堆，很多情况下还会涉及元空间，停顿明显更长。常见诱因是老年代压力、晋升失败、元空间不足、显式 `System.gc()` 或收集器退化。面试时最好结合具体收集器讲，比如 G1 还有 Young、Mixed 和 Full，Mixed 不等于 Full。

**J9. MyBatis-Plus 怎么统计年龄大于 20 的男性学生？**

```java
Long count = studentMapper.selectCount(
    Wrappers.<Student>lambdaQuery()
        .gt(Student::getAge, 20)
        .eq(Student::getGender, Gender.MALE)
);
```

> 关键是让数据库做 `COUNT`，不要先 `selectList()` 再在 Java 里 `size()`；性别值按真实字段类型传枚举或编码。

**J10. 箭头函数的 `this` 和 Hooks 怎么回答？**

> 箭头函数没有自己的 `this`，而是在定义时词法捕获外层 `this`，`call/apply/bind` 也改不了。React 函数组件通常不用 `this`。Hooks 也不是把类生命周期机械改名，`useEffect` 是按副作用和依赖组织 setup/cleanup；`useMemo`、`useCallback` 只有在昂贵计算或引用稳定确实有价值时才用。

**J11. JVM 运行时内存区有哪些，常见 OOM 怎么定位？**

> 线程私有的是程序计数器、Java 虚拟机栈和本地方法栈；线程共享的主要是堆和方法区，HotSpot 里类元数据主要在 Metaspace，直接内存也可能耗尽但不属于 Java 堆。定位 OOM 我先看错误类型，再保留 heap dump、GC log、线程和 native memory 信息：`Java heap space` 看对象增长与引用链，`Metaspace` 看类加载泄漏，`Direct buffer memory` 看堆外缓冲，`unable to create native thread` 看线程数和系统限制。先证据定位，不能一上来只调大 `-Xmx`。

**J12. 类加载过程和双亲委派是什么？什么时候会被打破？**

> 类生命周期通常讲加载、验证、准备、解析、初始化；使用和卸载在后面。双亲委派是 ClassLoader 先让父加载器尝试，父加载不到自己再加载，能避免核心类被重复或恶意替换。SPI、Tomcat 多 WebApp 隔离、OSGi 或热部署会使用线程上下文加载器、子优先或自定义加载规则。打破委派不是目的，必须同时考虑类隔离、版本冲突和卸载泄漏。

**J13. `volatile` 保证什么，为什么不能代替锁？**

> `volatile` 主要保证可见性和一定的有序性：一个线程写入后，其他线程能看到；对该变量的读写还建立 happens-before。它不保证复合操作原子，`count++` 仍是读、改、写三步，会丢更新。状态标志和单写多读配置适合 volatile；计数用 Atomic，多个变量共同维护不变量时用锁或串行化。DCL 单例里的实例引用要 volatile，是为了防止对象初始化重排序后被其他线程看到半初始化状态。

**J14. Java 线程池七个参数怎么讲？队列和拒绝策略怎么选？**

> 核心是 corePoolSize、maximumPoolSize、keepAliveTime、TimeUnit、workQueue、ThreadFactory 和 RejectedExecutionHandler。执行顺序不是先扩到 max：先用核心线程，核心满后入队，队列也满才扩到 max，最后拒绝。生产不直接用无界队列，因为流量高时延迟和内存会无限积累；我会按任务耗时、允许并发和下游容量设有界队列。拒绝可以快速失败、调用方执行、丢弃或自定义降级，但不能静默丢关键任务；同时监控 active、queue、reject、耗时和任务年龄。

**J15. `CompletableFuture` 最容易踩哪些坑？**

> 第一，不显式传 Executor 时很多异步阶段会落到 common pool，阻塞 I/O 可能拖累全局任务；第二，`thenApply` 是同步变换，`thenCompose` 用于串联另一个 Future，选错会出现嵌套；第三，异常会沿链传播，要用 `handle/exceptionally/whenComplete` 明确处理；第四，`allOf` 只表示全部结束，不自动返回结果列表。生产还要加超时、取消、并发上限和 trace 传播，外部副作用不能因为 Future 重试而重复执行。

**J16. Spring Bean 生命周期怎么口述？**

> 容器实例化 Bean，填充依赖，执行 Aware 回调，然后经过 `BeanPostProcessor` 的初始化前处理，调用 `@PostConstruct`、`InitializingBean` 或自定义 init，再做初始化后处理；AOP 代理通常在后处理阶段产生。容器关闭时调用 `@PreDestroy`、`DisposableBean` 或 destroy method。循环依赖、代理和作用域会让细节变化，面试里重点说清后处理器是 Spring 扩展和 AOP 的关键入口，Prototype Bean 的销毁也不由容器完整托管。

**J17. `@Transactional` 哪些情况下会失效？**

> 常见是同类 `this` 自调用绕过代理、方法不是可代理入口、对象不是 Spring 管理、异常被吞掉、抛的是默认不回滚的受检异常但没配置 `rollbackFor`，或者新线程里执行导致事务上下文不传播。还要注意数据库引擎和传播级别。定位时先确认调用是否经过代理、事务是否真正开启、异常是否到达拦截器，而不是只看注解写没写。

**J18. MySQL 联合索引、最左前缀和回表怎么解释？**

> 联合 B+Tree 先按第一列排序，再在相同第一列下按第二列排序，所以查询能否有效利用后续列取决于前导列和范围条件。InnoDB 二级索引叶子保存主键，查询非覆盖字段时还要按主键回聚簇索引，这就是回表；覆盖索引可以减少回表。优化时用 `EXPLAIN` 看 access type、key、rows、Extra，再结合真实基数和慢日志，不能看到“用了索引”就认定性能好。

**J19. InnoDB 的 MVCC 和隔离级别怎么讲？**

> MVCC 通过事务 ID、undo log 和 Read View 让普通快照读看到一致版本。Read Committed 通常每次语句创建新的 Read View，Repeatable Read 通常在事务首次一致性读时建立并复用，所以能重复读到同一快照。当前读如 `SELECT ... FOR UPDATE` 读最新版本并加锁；RR 下还会用 next-key lock 处理范围并发。MVCC 主要解决读写并发，不代表写写冲突消失，也不能替代业务幂等。

**J20. Redis 缓存一致性、穿透、击穿和雪崩怎么处理？**

> 常见读缓存模式是更新数据库后删除缓存，并用重试或消息保证删除最终成功；不能宣称数据库和 Redis 天然强一致。穿透是查不存在的数据，可用参数校验、空值短缓存和 Bloom Filter；击穿是热点 Key 失效时大量回源，可用互斥重建、逻辑过期或提前刷新；雪崩是大量 Key 同时过期或 Redis 故障，要随机 TTL、多级缓存、限流降级和高可用。热点 Key 还要做拆分、只读副本或本地缓存，并明确一致性代价。

**J21. MQ 怎么保证不丢、幂等、顺序和失败处理？**

> 生产者确认只证明 Broker 接收，持久化和副本策略决定 Broker 故障下是否保留；消费者要处理成功后再提交位点或 ACK。端到端通常是 at-least-once，所以消费者按 eventId 或业务键做幂等，数据库唯一约束兜底。顺序只能在同一分区或同一业务键范围内保证，不能同时要求无限并发和全局严格顺序。失败按可重试、业务拒绝和永久错误分类，指数退避后进入死信，配套告警、人工处理和对账。

**J22. 数据库连接池和 N+1 问题怎么排查？**

> 连接池不是越大越好，大小要结合数据库可承受连接、应用实例数、查询耗时和目标并发；连接泄漏、长事务和慢 SQL 会让池看起来“不够”。我会监控 active、idle、wait、timeout、连接持有时间和数据库线程。N+1 是先查一批主记录，再为每条各查一次关联数据；通过 SQL 日志和 trace 很容易看到。解决可以 join、批量 `IN`、预取或 DataLoader，但要防大结果集和笛卡尔积。

### Q151. Python `async` 适合什么，不适合什么？

**口语化回答**：

> 这题我会先说结论：适合大量等待网络/DB的 I/O 并发，同一线程 event loop 在 await 时切换任务；不让 CPU 代码自动并行。AST 解析、压缩、重排序等 CPU 重任务会阻塞 loop，应进 thread/process pool 或独立 worker。调用的 DB/HTTP SDK 也必须真正异步，否则写了 `async def` 仍阻塞。

### Q152. 在 async 路径里调用 `time.sleep` 会怎样？

**口语化回答**：

> 如果放到实际系统里，我会这么做：阻塞整个 event loop，该 worker 上其他请求都无法推进。用 `await asyncio.sleep`；同步阻塞库用 `asyncio.to_thread`/executor，但还要限制线程数和取消语义。用 event-loop lag、P95 和 blocking profiler 发现问题。

### Q153. FastAPI 的 dependency injection 能解决什么？

**口语化回答**：

> 我一般会这么处理：统一解析/验证请求、鉴权、tenant context、DB session 和服务依赖，并支持测试 override。依赖要按生命周期管理，DB session 请求结束 rollback/close；重资源在 lifespan 初始化，不要每请求创建模型/连接池。业务逻辑放 service，不堆 route function。

### Q154. Python GIL 是什么影响？

**口语化回答**：

> 这题我会先说结论：CPython 同一进程通常只有一个线程执行 Python bytecode，所以 CPU-bound 的纯 Python 线程很难线性加速；但 I/O 等待会释放 GIL，部分 C 扩展也会释放。我的选择一般是 CPU 解析用多进程，I/O 用 async 或线程，同时考虑进程的序列化和内存成本。所以更准确的说法不是“Python 不能多线程”，而是要看任务是否受 GIL 限制。

### Q155. Thread、process、async 怎样选？

**口语化回答**：

> 如果放到实际系统里，我会这么做：async：高并发可等待 I/O，前提库支持；thread：同步 I/O 或释放 GIL 的 C 扩展，开发简单但线程开销/共享状态；process：CPU-bound 隔离和并行，代价是 IPC/启动/内存。生产常是 API async + 任务队列多进程 + 局部 thread pool。

### Q156. TypeScript 类型能否防止运行时错误？

**口语化回答**：

> 我一般会这么解释：TypeScript 的类型编译以后会被擦掉，所以外部 JSON、LLM 输出和配置到了运行时，还是要用 Zod 或 JSON Schema 做校验。`any` 很容易把约束全部绕过去，我会更倾向用 `unknown` 再做 narrowing。前后端 API 最好共享 schema 或自动生成类型，而不是两边各写一套看起来差不多的 interface。

### Q157. React 大图谱怎样避免渲染卡顿？

**口语化回答**：

> 这题我会先说结论：后端/前端先按层级聚合，不一次渲染 30 万节点；viewport culling、分页/按需下钻、memoized selectors、Web Worker 做布局，稳定 node/edge identity 避免全量重渲染。大图 UI 的目标是回答任务问题，不是展示所有节点。

### Q158. ACID 分别是什么？

**口语化回答**：

> 我一般会这么解释 ACID：Atomicity 是一个事务要么全成功、要么全失败；Consistency 是事务执行前后都满足业务和数据库不变量，不是分布式一致性的同义词；Isolation 是控制并发事务彼此能看到什么；Durability 是提交以后即使故障也能保留下来。这里还有一个边界，外部 HTTP 和消息发送不会自动进入数据库事务。

### Q159. 常见隔离级别和异常？

**口语化回答**：

> 这题我会从隔离级别和并发异常两部分讲。Read Uncommitted 可能脏读；Read Committed 能防脏读，但仍可能不可重复读或幻读；Repeatable Read 保证同一事务内重复读取一致，具体怎么处理幻读要看数据库实现；Serializable 最强，但冲突和开销也最大。Lost update 还要结合条件更新、锁或者 Serializable 处理，不能只背一张隔离级别表。

### Q160. MVCC 怎样工作？

**口语化回答**：

> 这题我会先说结论：记录保留版本和事务可见性信息，读按 snapshot 判断可见版本，普通读写减少互斥；旧版本由 undo/tuple chain 和 vacuum/purge 清理。长事务会阻碍回收、造成膨胀；MVCC 不等于所有写冲突消失，更新同一行仍需锁/冲突检测。

### Q161. 联合索引怎样设计？

**口语化回答**：

> 如果放到实际系统里，我会这么做：从真实 query/filter/order/group 和选择性出发；常见顺序是等值列在前、范围/排序结合，考虑覆盖索引和写放大。`(tenant_id,status,next_retry_at)` 可支持按租户找可重试任务。用 EXPLAIN 验证实际扫描和排序，不能机械背“最高选择性放最前”。

### Q162. 一条 SQL 慢，怎样排查？

**口语化回答**：

> 我一般会这么处理：先确认慢在 DB 而非连接池/网络/锁；看慢查询日志和 EXPLAIN ANALYZE：访问路径、估算与实际行数、join 顺序、sort/hash spill、回表、分区剪枝；检查锁等待、统计信息、参数偏斜和缓存冷热。优化 SQL/索引/schema 后用相同数据回归，并观察写入成本。

### Q163. 为什么深分页慢？

**口语化回答**：

> 这题我会先说结论：`OFFSET N` 仍需扫描/排序并丢弃前 N 行，且并发插入下页可能重复/遗漏。用 keyset/cursor pagination：`WHERE (created_at,id)<(?,?) ORDER BY ... LIMIT`，排序键唯一稳定并有匹配索引。随机跳页才考虑预计算或限制深度。

### Q164. 乐观锁和悲观锁怎样选？

**口语化回答**：

> 如果放到实际系统里，我会这么做：乐观锁用 version/CAS，冲突少、持锁短，失败由调用方重试；悲观锁 `FOR UPDATE` 适合冲突高且重试代价大，但要短事务、固定加锁顺序防死锁。分布式外部调用不要持数据库锁等待数秒。

### Q165. 为什么事务里不宜调用 LLM/API？

**口语化回答**：

> 我一般会这么处理：外部调用慢且不可控，长事务占连接、持锁、增加死锁和 MVCC 膨胀；回滚也撤不回外部副作用。先提交状态/outbox，再异步调用；结果用幂等条件更新。确需读取一致快照时，把必要数据复制成 immutable job payload。

### Q166. `UPSERT` 有哪些坑？

**口语化回答**：

> 这题我会先说结论：唯一键必须对应业务幂等语义；并发 upsert 仍可能锁冲突；更新可能覆盖更新更晚的数据；不同 DB 的 affected rows/returning 语义不同。加 version/event_time 条件避免旧事件覆盖新值，并记录输入 hash；不要把所有错误用 `ON CONFLICT DO NOTHING` 静默吞掉。

### Q167. 幂等和去重有什么区别？

**口语化回答**：

> 如果放到实际系统里，我会这么做：去重检测重复请求；幂等保证重复执行结果等价。去重表只是实现之一，还要定义 key、作用域、TTL、并发原子性和返回旧结果。支付/发送等用业务幂等键+唯一约束，处理状态和结果持久化；同 key 不同 payload 应报冲突。

### Q168. “Exactly once” 为什么通常是端到端语义？

**口语化回答**：

> 我一般会这么理解 Exactly once：网络或者进程故障时，发送方经常不知道接收方到底处理了没有，所以基础设施通常只能给 at-least-once，或者只在自己的边界里保证 exactly-once。业务上我会用幂等消费、唯一键、事务性 offset 或 outbox，做到效果上只生效一次。即使消息系统内部说 exactly-once，也不代表外部数据库和 API 自动只执行一次。

### Q169. Transactional Outbox 怎样工作？

**口语化回答**：

> 这题我会先说结论：同一个 DB 事务写业务状态和 outbox event；relay/CDC 在提交后读取事件发消息；发送成功标记/保留 offset。relay 可能重复发送，消费者按 event_id 幂等。它消除“DB 成功但消息没发”的双写窗口，但增加表清理、顺序和延迟治理。

### Q170. 重试的三个前提是什么？

**口语化回答**：

> 如果放到实际系统里，我会这么做：错误是暂时的、操作幂等/可安全重复、总 deadline 允许。再配 exponential backoff+jitter、max attempts、retry budget。参数错误、权限错误、数据不变量失败不重试；多层 SDK/服务同时重试会放大流量，要确定唯一重试层。

### Q171. Circuit breaker 的状态是什么？

**口语化回答**：

> Circuit breaker 我会分三个状态来讲。Closed 时正常请求并统计失败；失败达到阈值以后进入 Open，直接快速失败；冷却一段时间后进入 Half-open，只放少量探测请求，成功就恢复，失败就重新打开。我会按 endpoint 或模型分别隔离，并结合最小样本和滑动窗口判断。它的作用是保护系统，业务结果还要靠 fallback 或队列恢复。

### Q172. Rate limit 常见算法？

**口语化回答**：

> 常见限流算法我会这样区分：Fixed window 最简单，但窗口边界容易突发；sliding log 精确但成本高；sliding counter 是折中；token bucket 可以允许受控突发；leaky bucket 更适合把输出流量抹平。AI API 往往同时限制每分钟请求数和 token 数，所以我会先按估算 token 预占，用完再按实际结算，并按租户和模型保证队列公平。

### Q173. 消息队列何时有价值？

**口语化回答**：

> 如果放到实际系统里，我会这么做：解耦、削峰、异步长任务、重试和事件传播。不是为了“架构高级”；若任务量小且 DB job table 足够，先用简单方案。使用队列要回答投递语义、幂等、顺序、重试/DLQ、背压、schema evolution 和监控。

### Q174. 怎样保证同一 session 消息有序？

**口语化回答**：

> 我一般会这么处理：以 session/user 为 partition key，使同一 key 进同一分区/单消费者；消息带 sequence/version，消费者检测 gap/duplicate；跨分区不承诺全局顺序。重试不能把旧消息放到新消息后直接覆盖状态，状态更新用 version 条件。

### Q175. 分布式锁为什么需要 lease 和 fencing token？

**口语化回答**：

> 这题我会先说结论：客户端暂停超过 lease 后锁已被别人获得，旧客户端恢复仍可能写入。每次获取返回单调递增 fencing token，下游只接受不小于已见 token 的操作，才能挡住过期 owner。只有 Redis `SET NX PX` 而下游不校验，不能完全防 stale writer。

### Q176. 强一致和最终一致怎样选？

**口语化回答**：

> 如果放到实际系统里，我会这么做：看业务不变量和错误成本。权限、余额、唯一所有权通常需要强约束；搜索索引、统计、推荐可最终一致。最终一致必须定义收敛时间、冲突策略、读己之写和补偿，不是“暂时不一致没关系”。

### Q177. Cache-aside 的典型故障？

**口语化回答**：

> 我一般会这么处理：读 miss→DB→cache；写 DB→删 cache。并发会短暂读旧值，可用延迟双删/版本/短 TTL，按业务容忍度处理。穿透用参数校验/negative cache/Bloom；击穿用 singleflight/互斥更新；雪崩用 TTL jitter、多级缓存、限流和降级。缓存 key 必须带 tenant 和数据版本。

### Q178. API 怎样做版本和兼容？

**口语化回答**：

> 这题我会先说结论：优先 additive change，新字段可选、旧字段语义不变；破坏性变化用路径/header/schema version，设置迁移期和 telemetry。错误码和幂等语义也是契约。LLM tool/MCP schema 同样要版本化，因为旧 Agent 可能缓存工具描述。

### Q179. Timeout 和 deadline 有何区别？

**口语化回答**：

> 如果放到实际系统里，我会这么做：timeout 常是单次操作上限；deadline 是整个请求剩余总时间，应跨服务传播。每层 timeout 要小于上层剩余时间并预留返回；重试共享总 budget，不能每次重新获得完整 timeout。客户端取消要向下游/worker传播，避免幽灵任务继续烧 token。

### Q180. Authentication 和 authorization 怎样区分？

**口语化回答**：

> 我一般会这么区分：Authentication 解决“你是谁”，Authorization 解决“你能对哪个资源做什么”。验证 JWT 时，我会检查签名、issuer、audience、过期时间和密钥轮换；真正授权要在服务端按 tenant、resource 和 action 判断，不能只靠前端把按钮藏起来。服务自己的凭证和代表用户发起的委托身份也要分开。

### Q181. 日志、指标、trace 各解决什么？

**口语化回答**：

> 我会把它们理解成三个层次：Metrics 适合看整体趋势和告警，log 适合查具体事件和细节，trace 用来串起一次请求跨组件的完整时序。三者通过 trace_id、job_id 或 report_id 关联。高基数值我不会随便做 metric label，日志要结构化和脱敏，trace 可以采样，但错误和高延迟请求优先保留。AI 链路还会额外记录 model、prompt、tool、token 和 finish reason。

### Q182. SLI、SLO、SLA 是什么？

**口语化回答**：

> 我一般会这么区分：SLI 是实际测量值，比如周报按时送达率、Agent task success 或 P95；SLO 是团队内部希望达到的目标，比如 99.5%；SLA 是对外承诺，以及达不到后的责任。团队可以根据 error budget 决定继续发布还是优先做稳定性。对 AI 系统来说，LLM API 调用成功率不能直接当业务 SLI，因为 HTTP 200 但答案错误，业务上还是失败。

### Q183. 单元、集成、端到端、评测怎样分工？

**口语化回答**：

> 我一般会这么处理：单元测纯逻辑和边界；集成测 DB/vector/queue/provider contract；E2E 测关键工作流与部署；LLM eval 测概率输出质量和回归。能用 deterministic assertion 就不要全交给 LLM judge；外部模型测试固定版本并隔离 flaky，核心安全/数字不变量必须确定性验证。

### Q184. 一个可靠 CI/CD pipeline 包含什么？

**口语化回答**：

> 这题我会先说结论：lint/typecheck/unit→integration/contract→security/dependency/secret scan→build immutable artifact/SBOM→staging migration和 smoke/eval→灰度/canary→指标门禁→自动/一键回滚。Prompt、模型 profile、eval dataset 和 DB migration 与代码一起版本化。生产密钥不进入 CI 日志。

### Q185. 现场系统设计怎样组织前 10 分钟？

**口语化回答**：

> 如果放到实际系统里，我会这么做：先问功能、用户/QPS/数据量/SLA/一致性/安全；定义核心 API 和数据模型；画一条正常请求链路；再算容量并定位瓶颈；最后讲故障、扩展、观测和取舍。不要一上来就列 Kafka/Redis/K8s。所有数字是推导依据，不是装饰。

### Q186. 做一个 90 秒中文自我介绍。

### Q207. 你做完设计以后，怎么交付给同事，怎么评审和拆任务？

### Q208. 一个任务要做多久，你是怎么估出来的？

**题型**：项目管理方法题。

### Q209. 什么叫任务完成？代码写完算不算 Done？

**题型**：项目管理方法题。

**口语化回答**：

> 代码写完只叫开发完成，不一定叫任务完成。我的 DoD 会跟任务风险匹配，但基本包括：实现已经合并，单元或集成测试通过，PR review 的问题关闭，接口和文档同步更新，监控和错误处理能覆盖关键链路，具备发布和回滚条件，并且业务验收用例通过。像只读查询接口，DoD 可以轻一些；涉及记忆写入、权限或数据迁移，就必须再加兼容、灰度、审计和回滚验证。

> 最关键的是在拆任务时就把 DoD 写清楚，不能到最后一刻才争论“到底算没算做完”。

### Q210. 你平时怎么监控项目进度？

**题型**：项目管理方法题。

**口语化回答**：

> 我看进度不会只问“完成了百分之多少”，因为这个数字很容易失真。我更关注可验收交付物、关键路径和阻塞。任务在看板里有明确状态，里程碑对应一组可以演示或验收的结果；站会或固定同步里重点讲已经完成什么、下一步是什么、卡在哪里，而不是逐个人汇报忙不忙。

> 我还会看几个趋势：关键路径任务有没有滑动、阻塞持续多久、剩余工作量和当前吞吐是否还匹配 deadline、缺陷和返工是否突然增加。风险项单独登记 owner 和处理时点。这样进度不是靠感觉，而是能从任务流转、可验收产物和风险变化看出来。

### Q211. 你怎么提前知道项目会不会延期？发现风险后怎么办？

**题型**：项目管理方法题。

**口语化回答**：

> 我一般看五类信号：关键路径任务是否晚于计划；按当前吞吐能不能在剩余时间做完剩余范围；上游接口或决策阻塞了多久；需求范围是否持续增加；测试阶段的缺陷和返工是否超过预期。如果时间已经过半但关键产物还没有形成，或者预留空间被未知问题提前吃完，就不能再把它当成正常波动。

> 确认有风险后，我会尽早把影响说成具体范围，比如“按当前速度，A 能按期，B 大概率晚三到五天”，同时给选择：砍掉非核心范围、调整依赖顺序、增加合适资源，或者调整 deadline。加人不是万能解，临近交付时还可能增加沟通成本。最后由业务和项目 owner 做取舍并书面记录。我负责的是尽早暴露风险和给出可执行选项，不是到最后一天才宣布做不完。

### Q212. 简历写年省约 50 人天，这个数字到底怎么算的？

**口语化回答**：

### Q213. 用三个词形容你自己。

**题型**：行为面。

**口语化回答**：

### Q214. 如果把本地 Agent Memory 做成多用户记忆中台，怎样控制回库吞吐和召回延迟？

**题型**：场景设计题，不代表当前本地插件已经按中台架构投产。

**口语化回答**：

> 这题我会先把边界说清楚：我现在的项目核心是宿主无关的记忆层和本地/云双存储，不会把它包装成已经验证过的大规模记忆中台。如果让我中台化，我会先定召回的 P95、并发、记忆规模和一致性要求，再把在线热路径和离线记忆加工彻底分开。

> 在线热路径只做“身份和租户校验、候选召回、轻量排序、预算内组装”。稳定的小体积画像和近期高频记忆可以按用户和版本做内存或 Redis 缓存；L1 原子记忆走带 tenant/user/time 过滤的关键词加向量召回，只取 bounded top K，不把整个用户历史拉上来。关键词、向量和必要的结构查询可以并行，统一设 deadline；缓存 key 必须带用户、记忆版本、模型和检索策略，写入后用版本号失效，不能只靠 TTL 赌一致性。

> L1 抽取、L2 聚合、embedding、去重和冲突检测全部放异步队列，不阻塞当前对话；写入按用户或 session 保序，并用幂等键防重复。存储侧按 tenant/user 分区，热点用户可以单独限流，读压力大时用副本或独立检索服务。依赖超时就降级到近期上下文、缓存画像或 keyword-only，并明确标记结果可能不完整。最后按阶段记录 cache hit、候选数、检索/排序/组装耗时和 P50/P95，先从 trace 找真实瓶颈，不是先堆 Redis、MQ 和向量库。

### Q215. 智能眼镜要求对方说完后快速给提示，你会怎样设计实时链路？

**题型**：场景设计题，不代表本人已交付智能眼镜系统。

**口语化回答**：

> 我不会先承诺一个拍脑袋的毫秒数，而是先跟产品确认首个提示和完整建议各自能接受多大延迟。架构上我会做快慢两条路径。端侧先做 VAD、降噪、流式 ASR，以及在明确授权前提下的必要视觉特征提取；能在端侧完成的就不上传原始音视频。云端收到增量文本或最小化特征后，快路径用规则或小模型先给一句短提示，慢路径再结合会话状态和相关记忆，用更强模型补充完整建议。

> 记忆召回不能每次全量回库，稳定画像和当前会话状态放热缓存，远期记忆只按当前意图取 top K。ASR、特征处理和允许并行的召回并行执行，每一段都有 deadline；新一轮说话开始后，上一轮已经过时的生成要能取消，避免提示排队。网络差、云模型超时或权限不足时，降级成端侧基础提示或者明确不输出，不能拿过时建议冒充实时结果。

> 可观测上要把采集、ASR、上传、召回、首 Token 和最终输出分别计时，才能知道七八秒到底慢在什么地方。质量上还要测建议正确性、过时提示率和打断率，不能只追求快。隐私和对方是否知情是产品能不能做的前置条件，不是性能优化完成后再补的一层。

### Q216. 用户上传第三方聊天截图、语音或微表情数据，隐私合规怎么做？

**题型**：合规与系统设计题。

**口语化回答**：

> 这类场景最关键的一点是：用户同意上传，不等于截图、语音和面部数据里的第三方也同意被分析。尤其语音、面部和所谓微表情可能涉及生物识别或敏感个人信息，我不会只加一段隐私协议就说合规了。上线前必须让法务和隐私负责人确认处理目的、合法基础、适用地区和是否需要第三方明确同意；如果拿不到合法基础，就应该砍掉这项能力，而不是靠技术绕过去。

> 工程上我会按目的最小化：能端侧即时处理就不上传，能上传结构化特征就不存原始音视频；默认不用于训练，不跨目的复用。传输和存储加密，租户与用户隔离，权限最小化，访问有审计；设置明确保存期限、删除和导出机制，日志里也不能落原始敏感内容。模型输出要避免把不确定的表情推断包装成心理事实，并且要评估误判和群体偏差。

> 对“让对方不知道眼镜在分析”这种产品要求，我的结论会很直接：隐蔽采集和分析本身就是高风险信号。没有清晰告知、同意和合法依据，我不会把它当成一个普通功能继续设计。

### Q217. 面试官追问情感经历、家庭、征信等私人问题，你怎么回应？

**题型**：行为面与个人边界。

**口语化回答**：

> 我会保持礼貌，但把问题拉回岗位。比如我会说：“这部分比较私人。如果您是想确认稳定性、入职时间或者是否能接受岗位安排，我可以直接回答这些和工作相关的信息；情感经历和家庭细节我希望保留隐私，我们可以继续聊岗位要求和协作方式。”

### Q218. 简历说 Memory 覆盖多个业务渠道，具体是怎么接入的？

**题型**：真实架构与组织口径，不能用设计方案代替实际渠道数量。

**口语化回答**：

> 这里要先区分“技术宿主接入”和“业务渠道采用”。技术上，同一套 TdaiCore 通过 HostAdapter 做了几种接入形态：OpenClaw 可以进程内通过 Hook 调用；Hermes 这类 Python 宿主通过 Sidecar HTTP Gateway 接入；Standalone CLI 或 Docker 复用同一个 Core。核心的 capture、recall、offload 和 session 生命周期逻辑不跟具体宿主绑死，所以换入口不需要重写记忆内核。

> 但这些 Host 形态不能自动证明“多个业务团队已经采用”。如果面试官问业务渠道，我会按真实情况说清接了哪些内部入口、各自多少用户或请求、由谁维护、怎么鉴权和回滚；没有可核验证据的渠道不报数量。更准确的表达是：架构具备多 Host 接入能力，实际投产范围以内部接入记录为准。这样既能说明设计价值，也不会把技术兼容能力夸成业务规模。

### Q219. 和 Copilot、Claude Code 自带的 Compact 相比，你的 Context Offload 多解决了什么？

**口语化回答**：

> 我不会先猜某个商业产品当前版本的内部算法，只比较可观察的能力边界。普通 Compact 的核心目标是把已有对话压成更短的继续上下文；我的 Offload 重点处理 Coding Agent 的大 Tool Result：原文先外移到 `refs`，上下文保留 summary、`node_id` 和 `result_ref`，Mermaid 再提供任务状态导航。它的价值是摘要不够时还能定向回查证据。
>
> 代价也很明确：链路、存储和恢复协议更复杂，摘要和任务图本身也可能错；短会话或宿主已经提供足够好的可恢复压缩时，没有必要重复建设。真正比较要固定同一任务、模型和预算，看成功率、Token、延迟、原文下钻成功率和错误恢复，而不是只比功能名字。

### Q220. AST 代码图和现成的语言解析 MCP、LSP 插件有什么区别？

**口语化回答**：

> MCP 是能力接入协议，不等于解析算法；一个 MCP Server 背后仍然可能用 tree-sitter、LSP、编译器或简单文本搜索。LSP 在支持良好的语言和完整构建环境里，类型、定义跳转和调用层次通常更准；CodeWiki 用 Python AST 和 tree-sitter 做离线多语言基线，不要求每个仓库先恢复依赖，但跨文件调用有启发式误差。
>
> 所以不是谁替代谁。我的选型是 tree-sitter 做广覆盖和可批处理底座，高价值语言再让 LSP 或编译结果补歧义边；通过 MCP 把最终检索和图查询能力暴露给 Agent。比较时要看语言覆盖、环境成本、边 Precision/Recall、索引延迟和可部署性。

### Q221. 周报接入 LLM 以后，最终模板到底变没变？

**口语化回答**：

> 当前交付形态仍是统一模板的表格加文字，并通过消息接口推送到内部招乎群。确定性程序负责取数、统计和表格，LLM 主要生成各模块的分析叙述，所以变化的是叙述生成方式和自动化程度，不是让模型每周自由设计一种版式。具体上线前后的模板字段差异要以历史样例为准；没有样例证据时，我不会编“模板改了多少版”。

### Q222. Agent Memory 和 ClaudeCode 有什么差异？

**口语化回答**：

> 我会先请面试官确认 ClaudeCode 指的是哪一个产品或具体版本，因为同名项目很多。没有固定版本的官方文档和同条件测试时，我不会直接说它没有分层、不能压缩或者我们更强。我会统一按写入策略、冲突和时间语义、召回、证据下钻、上下文管理、宿主集成、租户删除和运维成本比较。

> 我们当前能证明的特点，是长期 L0-L3 与单任务 Tool Result Offload 分开，并用 `source_message_ids`、`result_ref` 和任务图保留下钻入口；事实置信度、多租户和完整删除则仍是短板。对方方案的结论必须在确认产品和版本后再给。

### Q223. CodeWiki 真的用于评审和新人上手了吗？怎样证明？

**口语化回答**：

> 这是使用事实题，不能只从系统有 Wiki 和图谱功能推出业务已经采用。我会准备真实入口、参与团队、观察周期、查询或页面访问日志，以及至少一个评审或新人任务的前后对比。指标可以看定位模块耗时、需要请教次数、引用点击和重复使用，但必须说明样本。
>
> 当前拿不到内部采用记录时，我会说“产品设计支持评审和新人上手场景，已有内部使用反馈的范围是[本人填写]”，不会把预期使用场景写成已验证成效。对应证据统一在《面试前个人事实核对清单》中补齐。

### Q224. 为什么 Agent Memory 本地存储选 SQLite，而不是 PostgreSQL？

**口语化回答**：

> 当前项目首先服务 Local-first 接入，SQLite 单文件、零服务依赖，WAL 支持读写并行，FTS5 和 sqlite-vec 又能在同一存储里完成关键词与向量检索，最适合先把插件和 Gateway 链路跑通。直接要求每个开发者部署 PostgreSQL、扩展和连接池，会把本地接入成本放到核心价值前面。
>
> 这不是说 SQLite 更适合所有生产环境。多实例共享、租户隔离、在线迁移、容量和高可用要求上来后，应通过存储接口切换到云向量库或 PostgreSQL。选型原则是按部署形态和故障目标决定，不是“先写 SQLite，用户多了再无成本替换”。

### Q225. 为什么 CodeWiki 用 Tree-sitter，而不是所有语言都接 LSP？

**口语化回答**：

> CodeWiki 需要批量扫描整个仓库并统一抽取符号、Import、调用候选和源码位置。Tree-sitter 启动快、语言覆盖广、适合离线批处理，也能把各语言语法先归一成统一 Contract；LSP 的完整语义更精确，但每种语言都要维护 Language Server，大仓启动、内存和工程集成成本更高，而且它主要为编辑器交互设计。
>
> 取舍是速度和覆盖换掉一部分类型语义，所以跨文件调用必须带推断层级和置信度，不能说成编译器级真相。下一版可以对高价值语言或歧义边按需接 LSP 做二次解析，而不是让两者互斥。

### Q226. 为什么通过 LiteLLM 统一模型，而不是业务直接调用各家 SDK？

**口语化回答**：

> 统一 Gateway 可以把 Provider 差异、超时、重试、模型目录、任务路由、缓存和审计从业务服务中拿出来。业务只声明 Task Type 与输入契约，不需要在 Catalog、Wiki、Recall 等每条链路里分别适配 OpenAI、Anthropic 或云厂商接口，切模型也更容易做受控配置变更。
>
> LiteLLM 只是 Provider 适配层，不会自动解决质量路由、数据合规、缓存污染和故障切换。外层仍要固定模型与 Prompt 版本、记录 Run、限制数据出域，并用同一评测集决定路由，不能把“API 能调通”当成“模型可替换”。

### Q227. 为什么 Agent Memory 用 Mermaid 表示任务图，而不是只存 JSON？

**口语化回答**：

> Mermaid 用较少 Token 同时表达节点、状态和依赖，人和模型都能快速浏览，也能直接渲染用于排障；每个节点再通过 `node_id` 和 `result_ref` 回到 JSONL 与原始 Tool Result。它适合做上下文里的任务索引，而不是事实数据库。
>
> JSON 更适合确定性解析、Schema 校验、并发更新和稳定 ID，所以生产上不该二选一：结构化 Store 保存规范状态，Mermaid 由状态派生并进入上下文。当前项目里 Mermaid 仍有 LLM 参与，不能因为可渲染就说节点划分完全可靠。

### Q228. 为什么 Hybrid Recall 先用 RRF，而不是直接加 Reranker？

**口语化回答**：

> RRF 只依赖各路排序名次，不要求 BM25 和向量分数同量纲，也不需要额外模型服务，适合 Local-first 的第一版稳定融合。它把关键词精确匹配与语义召回组合起来，链路短、可解释、故障点少。
>
> RRF 不理解当前任务的细粒度意图，也不会自动解决时间、权限和冲突。是否加 Cross-Encoder、第三方 Rerank API 或 LLM Reranker，要在同一候选集上比较 Recall@K、NDCG、最终答案质量、p95 延迟和单位请求成本；没有消融数据时不能说 RRF 已经最优，也不能笼统说 Reranker 一定让成本翻倍。

### Q229. 为什么 AI 周报用控制表，而不是消息队列？

**口语化回答**：

> 当前周报是按业务日期运行的批任务，核心需求是知道哪一天、哪个模块、哪个阶段成功或失败，并能重跑和对账。数据库控制表能把业务数据与批次状态放在可查询、可事务更新的模型里，运维人员也容易按日期定位；为低频日终任务先引入 Kafka 或 RabbitMQ，会额外带来消费确认、死信、顺序和消息数据一致性问题。
>
> 控制表不代表永远不用队列。任务量、并行度、跨系统事件和削峰需求上来后，可以用 Outbox 把确定性状态变化发布到队列，由 Worker 消费；数据库仍保存权威 Run 状态。选型关键是当前负载与恢复语义，不是把消息队列简单归类为过度设计。

### Q230. LRU 能不能直接表示 Agent Memory 的遗忘？（货拉拉、颂拓）

> 不能。LRU 只按最近访问淘汰热缓存，无法表达低频但重要、事实置信度、有效期、安全约束、scope 和用户删除。我的做法是保留 L0 原始证据，L1 保存带来源/时间/作用域的事实，L2/L3 保存可重建的场景和画像；遗忘或降级综合语义重要性、跨任务复用、时效、冲突和合规策略。模型可以提出 `skip/update/archive`，服务端必须校验、留版本并执行删除传播。

### Q231. “昨天”“今天”这种相对时间怎样落库？（货拉拉、颂拓）

> 写入时就结合 reference time 和用户时区解析，而不是只保存字符串等模型以后猜。记录 `raw_text`、`reference_time`、`timezone`、`event_time_start/end`、解析器版本、来源 ID 和置信度；“昨天跑了十公里”应变成该时区前一天的日期区间，同时保留原文。无法确定时保存区间并澄清。查询和冲突使用标准化时间，展示和审计使用原文。

### Q232. 单用户本地 Memory 怎样扩展成 ToC 多租户服务？（颂拓）

> 我会先承认当前项目是 Local-first、本地 SQLite 和宿主适配，不把它说成成熟 ToC 平台。中台化先建立服务端注入的 `tenant/user/device/agent/session` scope，原始事件走 outbox，抽取、Embedding、去重和冲突治理异步化；在线 Recall 做权限前置过滤、分片、热缓存、并发预算、超时和降级。版本号和幂等键保证乱序与重复不污染记忆，删除事件要传播到 L0-L3、索引、缓存、refs、备份和外部 Trace。QPS/P95/用户量只能引用真实监控。

### Q233. 健康、运动和 GPS 数据应不应该全部放进向量 Memory？（颂拓）

> 不应该。距离、配速、心率、睡眠、HRV、GPS 路线和潜水记录等权威事实应放结构化或时序存储，带设备、采集时间、单位、数据新鲜度和授权范围；Memory 更适合保存用户偏好、训练目标和可追溯摘要。向量用于找相关背景，不替代精确的时间、数值、设备和权限查询。Agent 输出还要区分训练建议、设备说明和医疗诊断，后者应拒答或转官方/人工渠道。

### Q234. Git diff 能否保证 CodeWiki 的知识图谱增量更新正确？（货拉拉、颂拓）

> 不能。diff 只是受影响候选的线索，函数重命名、移动、删除、动态调用和跨文件类型变化可能留下旧边、旧向量、Wiki 和引用。增量流程应基于 `repo_id + revision + symbol_id`、内容 Hash、反向依赖和删除 tombstone 重算受影响子图，并在同一 Revision 下原子发布；无法证明一致时标记 stale，回退读取当前源码。当前有 Diff/Hash 增量思路，但没有完整的统一 Revision 强一致承诺。

### Q235. 大 Tool Result 压缩前怎样保证关键内容不丢？（Autel）

> 先把原文作为不可变 Artifact 保存，再按 Tool Schema 和业务规则定义 must-keep 字段，例如 ID、状态、数字、时间、错误码、权限和引用。结构化字段由程序抽取，模型只摘要非结构化内容；输出必须通过 Schema、数字/状态一致性、引用存在性和 Citation 校验。摘要不可信就回退抽取片段或原文。BM25/向量是之后怎样取回，不是压缩时不丢信息的保证。

### Q236. 无人机调度 Agent 中 LLM、约束引擎、优化器和飞控分别做什么？（Autel）

> LLM 负责把自然语言转成结构化任务意图、解释候选方案和处理非结构化信息；约束引擎校验禁飞区、电量、载荷、时间窗、通信和权限；优化器在合法解空间内做多机分配和动态重规划；飞控负责实时姿态、避障、返航和最终安全闭环。任何 LLM 输出都必须经过 Schema、权限和硬约束验证，不能直接发飞控指令。

### Q237. 复杂 Agent 怎样证明不是 Demo？（Autel）

> 我会同时测最终结果和执行轨迹：任务成功率、约束违规率、危险动作拦截率、工具选择/参数正确率、状态恢复率、动态重规划耗时、人工介入率、成本和 P95。离线用固定任务集和仿真做回归，线上先 shadow mode，再小范围灰度；注入模型超时、遥测断链、工具重复和调度冲突，验证降级、回滚和审计。满意度不能替代安全指标。

### Q238. 早期 Demo 怎样走向稳定环境和 App 云化？（颂拓）

> 先把开发、临时测试和稳定环境的配置、数据、模型和版本隔离，并给每次运行可追踪的 Run/Revision。质量门禁从 Schema/契约测试、关键场景回放、Trace、成本和安全检查开始；上线用灰度、shadow、可回滚制品和明确的 Drain/告警。App 云化从低风险只读、低敏数据开始，和 App 团队先定 API/事件契约、数据新鲜度和删除责任，再逐步同步运动数据，不能因为团队买了云服务额度就声称已经完成生产云化。

### Q239. 大数据平台岗位中，AI 项目经验怎样如实对齐？（货拉拉）

> 我能迁移的是数据契约、采集与补数、幂等更新、质量校验、任务状态、回放和故障治理；Kafka、Flink、Spark、Hive、ClickHouse 等组件是否实际使用必须逐项说明。若没有完整生产数仓经历，我会把它说成当前差距，并用现场编码、系统设计和一条可核验的 Java/数据交付证明基础能力。转写没有记录货拉拉的实际编码题面和结果，所以不能杜撰题目或通过结论。

### Q240. 二叉树是什么？（货拉拉二面）

**口语化回答：**

> 二叉树由根节点和递归的左右子树组成，每个节点最多有两个子节点，分别称为左孩子和右孩子，可以只有一个孩子或没有孩子。它不等同于二叉搜索树；二叉搜索树还要满足左子树键值小于根、右子树键值大于根，重复值策略要单独定义。

### Q241. 二叉树怎样做前序、中序、后序遍历？（货拉拉二面）

**口语化回答：**

```text
preorder(node):
    if node == null: return
    visit(node)
    preorder(node.left)
    preorder(node.right)

inorder(node):
    if node == null: return
    inorder(node.left)
    visit(node)
    inorder(node.right)

postorder(node):
    if node == null: return
    postorder(node.left)
    postorder(node.right)
    visit(node)
```

> 三种遍历时间复杂度都是 O(n)，递归栈空间 O(h)；树很深时改用显式栈，层序遍历使用队列。

### Q242. B+树的结构和用途是什么？（货拉拉二面）

**口语化回答：**

> B+树是多路平衡搜索树。内部节点存有序分隔键和子指针，记录或记录指针集中在同层叶子节点，叶子按键排序并通过链表相连。高扇出让树高较低、减少磁盘页 IO；查到范围起点后可以沿叶子链顺序扫描，所以点查和范围查都适合数据库索引。插入、删除可能触发叶子分裂/合并和父节点分隔键调整。

### Q243. 进程和线程有什么区别？（货拉拉二面）

**口语化回答：**

> 进程是资源隔离和分配单位，拥有独立的虚拟地址空间；线程是进程内的调度执行单位，同一进程线程共享代码、堆、文件等资源，但各自有栈、程序计数器和寄存器上下文。进程隔离强、创建和切换成本通常更高；线程共享方便但必须处理竞态。线程可以并发执行，不代表一定并行。

### Q244. 线程上下文切换需要保存什么？（货拉拉二面）

**口语化回答：**

> 至少保存程序计数器、通用寄存器、栈指针、处理器状态/标志寄存器和内核调度需要的线程状态。页表和地址空间主要属于进程上下文，不应说每次线程切换都完整切换页表；这些状态由 PCB/TCB 等内核结构管理。切换本身有保存、恢复和缓存失效成本，所以线程数不是越多越好。

### Q245. Java 多线程访问共享变量怎样同步？（货拉拉二面）

**口语化回答：**

> 复合操作需要互斥时用 `synchronized` 或 `ReentrantLock`；需要超时、公平、可中断或多个条件队列时用 `Lock/Condition`。单变量 CAS 更新可以使用原子类。`volatile` 保证可见性和有序性，但不保证 `i++` 的原子性；读多写少可以考虑读写锁。选择方案时我还会说明锁粒度、释放方式、死锁风险、线程安全集合和不可变对象。

### Q246. 线程池有哪些核心参数，任务怎样进入线程池？（货拉拉二面）

**口语化回答：**

> `ThreadPoolExecutor` 的核心参数是 `corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`workQueue`、`threadFactory` 和 `RejectedExecutionHandler`。任务到达时先创建核心线程；核心线程满后进入队列；队列满且未到最大线程数才创建非核心线程；队列仍满则执行拒绝策略。生产环境要有界队列、线程命名、异常处理、监控、优雅关闭和明确的 CallerRuns/Abort 等拒绝策略；无界队列可能使最大线程数失效并掩盖堆积。

### Q247. CodeWiki 的多语言 DSL 怎样定义，AST 和 LLM 各做什么？（货拉拉二面）

**口语化回答：**

> 我把 DSL 当作语言无关的代码 IR。节点包含 `repo_id、revision、symbol_id、kind、qualified_name、signature、file、line range、parent_id`，边包含 `calls/imports/inherits/implements/defines`、来源和置信度。不同语言的 Tree-sitter/AST 解析器负责映射到 IR，无法确定的动态关系标出推断层级。
>
> LLM 不负责把源代码猜译成 DSL；它只消费 IR、调用链和带 Source Ref 的源码片段，生成解释性文档。这样可以把确定性事实、模型推断和无法确认的内容分开审计。

### Q248. GraphRAG 的图和向量数据怎样存？（货拉拉二面）

**口语化回答：**

> 图节点和边都绑定 `repo_id + revision`，边保存关系类型、来源行号和解析置信度；向量记录绑定 `symbol_id/chunk_id + revision + content_hash + embedding_model`。查询先做版本、仓库和权限过滤，再用符号/FTS/BM25/向量取得候选，沿调用和依赖边扩展，最后输出带引用的 context pack。
>
> Neo4j、PostgreSQL/pgvector 或早期原型存储的实际使用范围要按事实说明；不能把“做过适配”说成多业务正式生产，也不能让旧 revision 的向量在新版本中继续可检索。

### Q249. Git diff 怎样驱动 CodeWiki 增量更新？（货拉拉二面）

**口语化回答：**

> Git diff 只是文件级变更线索。我会保存新 revision，重新解析变更文件，通过稳定符号 ID、签名和内容哈希识别新增/删除/修改/重命名，再按反向依赖计算 Dirty Set，重建节点、边、文档 chunk 和向量。引用、数量、语法和固定问答回归通过后原子切换 revision，失败则保留旧版本回滚。

### Q250. 类属性新增或类型变化，如何更新向量？（货拉拉二面）

**口语化回答：**

> 先定位属性、包含类和引用该类/属性的函数，重算类级摘要、受影响函数级 chunk 以及相关文档和向量。属性变化不能因为“最小节点是函数”就跳过；它可能改变序列化、方法语义和调用方。新向量用 revision/content hash 写入 staging，校验后切换，旧向量先标 stale，避免返回陈旧语义。

### Q251. Memory 当前是共享服务还是本地组件？（货拉拉二面）

**口语化回答：**

> 当前实现是本地、单用户的 Memory 组件/服务，宿主通过 Hook 在模型调用前 Recall、回合结束后 Capture，数据在用户本机；它不是已经完成的共享多租户服务。未来做 Gateway 要增加用户、项目、Agent、权限 scope、审计、重试和删除传播，接口兼容不等于云化完成。

### Q252. L0-L3 记忆什么时候写入？（货拉拉二面）

**口语化回答：**

> L0 先追加保存不可变原始对话和事件引用；L1 在用户明确要求记住、会话边界、重要事实检测或异步保底任务时抽取；L2 在多个事实组成同一场景或任务结束时聚合；L3 只有稳定、可复用、无冲突且达到置信度的偏好才晋升。固定“每五条”和定时任务可以是当前实现的成本策略，但不是通用语义规则。

### Q253. 新旧 Memory 事实冲突怎样定位和解决？（货拉拉二面）

**口语化回答：**

> 先按 `subject/entity、attribute、scope、valid_time` 建事实候选键，再用 BM25/向量召回相关条目；召回只找候选，不能独立证明冲突。同一属性的新值明确替代旧值时标记 supersedes，互补信息才 merge，时间或作用域不清时保留 conflict 并追问。LLM 只能提出动作，服务端校验版本、来源、权限和安全规则后落库，旧证据保留历史和引用。

### Q254. Memory 怎样给应用端提供集成接口？（货拉拉二面）

**口语化回答：**

> 当前用 Agent Hook 做轻量接入：`before_model_call` 调 Recall，`after_turn/after_tool` 调 Capture，失败写本地队列重试。通用 Gateway 可以提供 `recall(query, scope, as_of, budget)`、`capture(events, idempotency_key)`、`delete` 和 `health`，返回 memory ID、Source Ref、revision 和 confidence；如果 Gateway 还没部署，就明确说它是下一版设计。

### Q255. 最近在学什么，怎样和 Data Agent 岗位匹配？（货拉拉二面）

**口语化回答：**

> 最近重点学习 Data Agent 的工程化，包括语义层/指标口径、NL2SQL 安全校验、血缘、评测集、链路可观测性和失败回放。我会先把表、字段、业务定义、权限和时间口径结构化，再让模型生成候选 SQL 或解释，经过 AST、只读权限、数值对账和固定样本回归；Three.js 只是个人练习，不作为生产数据平台经验。针对货拉拉团队，我还会重点补 Hadoop/Spark 的任务、数据质量和回放基础。

### 货拉拉二面反问：团队和岗位应确认什么？

> 我会优先问：“这个岗位在 Hadoop/Spark 基础设施、Data Agent、语义层和多模态数据之间的工作占比如何？”、“前三个月最希望我交付什么，验收指标是什么？”、“语义层的指标口径和 Owner 如何确定，NL2SQL/归因/下钻怎样评测？”以及“线上值班、发布和故障复盘如何安排？”

> 面试官已经透露团队拥有相对成熟的 CI/CD 和 Kubernetes 基础设施，但语义层、链路可观测性和评测能力仍处于初期到中期建设阶段。这个信息适合用来判断岗位是否有平台建设空间，不应写成候选人已经做过这些公司的内部平台。

## 11. 推荐简历证据模板

## 16. 最终备战优先级

### P0：先修复可信度底盘

1. 三个项目统一按公司内部项目介绍，但个人角色按各项目 RACI 分别回答，不统一套“技术 Owner”。

3. 所有量化指标准备定义、基线、样本和来源。
4. 把“独立负责”拆成需求、设计、实现、测试、发布和维护的真实责任，不预设本人是端到端 Owner。
5. 补齐丰泊暴露的 Java 硬基础，至少能连续答完 J1-J22，不再出现一串 `pass`。
6. 每个项目练 30 秒版和 2 分钟版，第一句讲用户和业务问题，不用 GraphRAG、L0-L3 等名词代替产品解释。
7. 补齐货拉拉二面暴露的二叉树、B+树、进程/线程、上下文切换、Java 同步和线程池基础；定义必须准确，不能靠模糊术语蒙混。

### P1：真实面试已多次失分

1. 具体回答而不是抽象框架。
2. CodeWiki vs Claude Code/Cursor 的定位与质量 benchmark。
3. Memory 的 offload/MMD/long-term memory 概念分离。
4. 幻觉机制、冲突治理、RAG 分层评测。
5. 项目部署、并发、CICD、故障和 SLA。
6. AI Coding 责任链：准备一个真实变更，讲清 AI 草稿、人工修改、测试发现和最终责任。
7. 离职动机与公司调研：职业方向是根因，工具限制是表象；公司结论必须来自多源核验。
8. 针对目标团队痛点准备 30/60/90 天落地方案，不泛讲“入职后先熟悉业务”。
9. CodeWiki 增量要覆盖属性变化、反向依赖、重命名、旧向量清理和 revision 原子发布；Memory 冲突要用事实键和服务端状态机，不把召回当判定。
10. Data Agent 方向要能讲语义层、指标口径、NL2SQL 只读权限、SQL AST 校验、数值对账、血缘和评测闭环。

### P2：决定能否拿更高职级

1. MCP 安全、durable execution、trace grading。
2. 分布式锁、outbox、deadline、可观测和容量推导。
3. 系统设计迁移能力：模型路由、根因诊断、多租户 RAG。
4. 英文和中等难度编码稳定性。

**最后原则**：不追求把 255 道答案逐字背下来。先保证事实可信，再把每个核心项目练成“3 分钟全貌 + 10 分钟深挖 + 1 个缺陷 + 1 个指标证据”。面试官真正想看到的是你能否在追问下保持口径一致、知道系统边界，并对自己写在简历上的每个动词和数字负责。
