# 项目一：AI 周报系统

## 第一层：项目全貌与动机

### Q1. 一句话讲清这个项目，以及你为什么选 LLM 而不是纯规则脚本？

**【面试官意图】** 考察你能不能区分「LLM 真正创造价值的地方」vs「为用而用」。资深面试官最反感简历硬塞 LLM。

**【参考答案】**：
> AI 周报系统把银行运维数据周报从「人工多源采集汇总 8-10 小时」自动化到「20 分钟全链路闭环」。核心设计原则是**「数字与叙述分离」**：所有数字（错误日志量、大事务、慢 SQL、TPS、响应时间分布、交易量异常）由确定性 SQL 统计算出，LLM 只负责把这些结构化数字**组织成有重点的自然语言叙述**，绝不碰数字计算。
>
> 选 LLM 而非纯规则脚本的价值在两点：①**数据解读**——把一堆数字串成「本周亮点 / 异常 / 风险」的可读叙述，降低阅读成本；②**自然语言交互**——周报推出后用户能直接追问「这周 A 模块错误为什么多了」，不用翻系统。
>
> 诚实边界：**如果只做定时推数字周报，纯模板 + 脚本确实够了，LLM 不是必需的**。LLM 的价值在交互和解读层，不在采集和统计层。

**【口语化回答】**：

> 嗯，这个项目说白了就是把银行运维周报从「人工凑数据 8 到 10 小时」压到「20 分钟自动跑完」。
>
> 我最核心的一个设计原则是「数字和叙述分离」--什么意思呢，就是所有的数字，错误日志量啊、慢 SQL 啊、TPS 啊，全都是 SQL 算出来的，确定性逻辑，不交给大模型。大模型只干一件事：把这些已经算好的数字，组织成一段人能读的自然语言，比如「本周 X 模块错误量上涨了 Y%」。
>
> 那为什么还要用大模型呢？纯脚本其实也能出周报。但大模型的价值有两个：一是解读，把一堆冷冰冰的数字串成有重点的叙述，告诉运维哪里要关注；二是交互，周报推出来用户能直接追问「这周 A 模块怎么错了」，不用再去翻系统。
>
> 不过我也得诚实说，如果只是定时推个数字周报，那确实不需要大模型，纯模板加脚本就够。大模型的价值在交互和解读这层，不在采集和统计这层。

**【连环追问】**：
- 「那为什么不让 LLM 也算数？它能读数啊」→ 见 Q8（数字准确性治理）
- 「这东西听起来就是个 Airflow + 模板，技术深度在哪」→ 见 Q3（重试容错与事务保障）

### Q2. ⚠️ 周报的完整链路是什么？数据源有哪些？数据量多大？

**【面试官意图】** 微众/小天才两场都因「回答笼统」被追问。面试官要的是**具体到表名、字段、步骤**，不是「采集-清洗-分析」三段论。

**【参考答案】**（基于详设.md 真实实现）：
> 完整链路分四大阶段，每阶段都有控制表 `AN1_REPORT_DATA_CTRL_T` 记录状态（`PROC_STATUS` 下载态 P/S、`ANA_STATUS` 分析态 P/S）：
>
> **阶段 1·初始化下载控制**：日终触发，取 T-1 为待处理日期，`INSERT IGNORE` 插入控制记录（PTN_KEY 取该日期所属周周一的月份分区，PROC_STATUS='P'，ANA_STATUS='P'，TECH_TRACE_ID 链路 ID）。
>
> **阶段 2·回溯下载 15 天未成功数据**：查 `PROC_STATUS='P'` 且 PROC_DATE 在过去 `TRACEBACK_DAYS=15` 天内的记录，循环调外部 API（按 `API_DEPLOY_UNIT` + PROC_DATE 封装请求），成功则解析数据 `INSERT IGNORE` 批量入对应数据源表并置 `PROC_STATUS='S'`，失败重试 `MAX_RETRIES=10` 次、每次间隔 `RETRY_DELAY_SECONDS` 秒。
>
> **阶段 3·周报分析（7 个子模块）**：分析前先检查上周七天数据是否全部 `PROC_STATUS='S'`，有 P 则终止；再检查 `ANA_STATUS` 避免重复生成。然后串行执行 7 个模块（错误日志量 / 大事务长事务 / SQL 性能 / 异步入账 / 失败交易 / 北斗数据 TPS+RESP+TRANS / 周报组装发送），每模块独立重试循环 + `IS_ALL_ANALYSIS_SUCCESS` 全局 Flag。
>
> **阶段 4·北斗临时数据清理**：按分区键 PTN_KEY 计算上月分区，检查上月数据完整性（下载+分析全 S）和分区是否已清空，再 `ALTER TABLE ... TRUNCATE PARTITION`。
>
> 数据源：主要是北斗指标平台（TPS/响应时间/交易量）、AN1LOG 数据库（付款申请/退款/失败交易）、CKTRANS（大事务长事务）、CKSLOWSQL（慢 SQL）、FTCLOG（错误日志）。每周采集量级在 [备真实数，如 X 万条原始记录]，清洗结构化后 [X 千条] 进分析。

**【口语化回答】**：

> 嗯，完整链路分四个阶段，我讲具体点。
>
> 第一阶段是初始化下载控制。日终触发，取 T-1 作为待处理日期，往控制表 `AN1_REPORT_DATA_CTRL_T` 里插一条记录，状态都置成 P 也就是 Pending，同时记一个链路 ID 方便排查。
>
> 第二阶段是回溯下载。查过去 15 天里状态还是 P 的记录，循环调外部 API 拉数据，成功就解析入库、状态置成 S，失败就重试，最多重试 10 次。
>
> 第三阶段是周报分析，这是重点。先检查上周 7 天数据是不是都下载成功了，有没成功的就终止不发残缺周报。然后串行跑 7 个模块--错误日志量、大事务长事务、SQL 性能、异步入账、失败交易、北斗数据、最后是周报组装发送。每个模块独立重试，有个全局 Flag，全成功才发周报。
>
> 第四阶段是清理，把上个月的北斗临时分区数据 TRUNCATE 掉。
>
> 数据源主要是北斗指标平台、AN1LOG 数据库、还有几个 CK 开头的表。每周采集量大概 X 万条原始记录，清洗后 X 千条进分析。

**【连环追问】**：
- 「数据源挂了怎么办」→ 见 Q4（降级与容错）
- 「分区为什么要按周一的月份」→ 跨月时上周数据可能落在两个分区，取周一所在月保证一周数据在一个分区，便于 TRUNCATE 清理和按周聚合查询
- 「LLM 分析的 Prompt 怎么组装，超长怎么办」→ 见 Q5（Prompt 长度控制）

## 第二层：核心机制深挖

### Q3. 重试容错和事务保障具体怎么做？为什么每模块独立重试而不是整体重试？

**【面试官意图】** 简历写了「内置重试容错与事务保障」，面试官要验证你是不是真做了，还是抄的词。

**【参考答案】**：
> 每个分析子模块（3.2-3.8）都有独立的重试循环：
> ```
> for (attemptCount = 1; attemptCount <= MAX_RETRIES + 1; attemptCount++):
>   try:
>     1. 数据统计与入库（开事务 -> INSERT IGNORE -> 提交）
>     2. LLM 智能分析（组装 Prompt -> 调智算平台 -> 存 AN1_REPORT_LLM_ANALYSE_T）
>     isModuleSuccess = true; break
>   catch:
>     记录「模块 X 第 N 次尝试失败」
>     if attemptCount > MAX_RETRIES: break
>     else: 休眠 RETRY_DELAY_SECONDS 秒
> if (!isModuleSuccess): IS_ALL_ANALYSIS_SUCCESS = FALSE
> 程序继续执行下一模块（不终止）
> ```
>
> **为什么模块独立重试而非整体重试**：
> 1. **故障隔离**：7 个模块互相独立，错误日志量分析失败不该拖垮大事务分析。整体重试会把成功的模块白跑一遍，浪费 LLM 调用成本。
> 2. **部分产出优于全无**：即使某模块彻底失败（重试耗尽），其余模块仍能产出，周报只是缺这一块（标注「数据获取异常」），而不是完全不发。
> 3. **IS_ALL_ANALYSIS_SUCCESS 全局 Flag**：只有 7 个模块全成功才更新 `ANA_STATUS='S'` 并发送周报；任一失败则不发送、不更新状态，等明天重试——避免发出残缺周报误导决策。
>
> **事务保障**：每个数据库写操作都包在「开事务 -> 操作 -> 提交」里，`INSERT IGNORE` 防重复插入。LLM 分析结果单独存 `AN1_REPORT_LLM_ANALYSE_T`，与统计数据分表存储，互不污染。

**【口语化回答】**：

> 每个分析模块都有自己独立的重试循环。简单说就是 for 循环跑 MAX_RETRIES+1 次，try 里面先统计入库再调 LLM 分析，成功就 break，失败就记日志、休眠 RETRY_DELAY_SECONDS 秒重试。重试耗尽了就把全局 Flag 置成 FALSE，然后继续跑下一个模块，不终止。
>
> 为什么独立重试而不是整体重试呢？三个原因。第一是故障隔离，7 个模块互相独立，错误日志量分析失败了不能拖垮大事务分析，整体重试会把成功的模块白白再跑一遍，浪费 LLM 调用钱。第二是部分产出优于全无，某模块彻底失败了，其他模块照样能出结果，周报顶多缺一块标注「数据异常」，而不是完全不发。第三是那个全局 Flag IS_ALL_ANALYSIS_SUCCESS，全成功才更新状态发周报，任一失败就不发不更新，等明天重试，避免发出残缺周报误导决策。
>
> 事务保障就是每个写操作都包在开事务、操作、提交里，用 INSERT IGNORE 防重复插入。LLM 分析结果单独存一张表，和统计数据物理隔离，互不污染。

**【连环追问】**：
- 「重试间隔固定还是指数退避」→ 详设里是固定 `RETRY_DELAY_SECONDS`，生产里对 LLM 调用应该用指数退避 + 抖动，避免雪崩。这是可优化的点。
- 「LLM 分析失败但统计成功，数据会丢吗」→ 不会。统计已入 `..._ANALYSE_T` 表（如 `AN1_REPORT_LOGCOUNT_ANALYSE_T`），LLM 失败只是 `AN1_REPORT_LLM_ANALYSE_T` 缺这模块的解读。明天重试时统计表 `INSERT IGNORE` 不会重复，只补 LLM 解读。

### Q4. ⚠️ 某个数据源挂了怎么办？增量采集还是全量？北斗数据清理会不会误删？

**【面试官意图】** 生产可靠性思维。面试官要看你有没有想过「失败不是异常是常态」。

**【参考答案】**：
> **数据源故障处理**：
> - **回溯机制**：阶段 2 每天回溯过去 15 天 `PROC_STATUS='P'` 的记录重试，所以某天 API 挂了，第二天起连续 15 天都会自动重试补下载，不丢数据。
> - **不阻断周报**：分析前检查上周七天是否全 `PROC_STATUS='S'`，有 P 则**终止本次分析**（不发残缺周报），等明天数据补齐再跑。这是「宁可延迟一天发完整周报，不发残缺周报」的策略。
> - **增量为主**：每天只处理 T-1 一天的新数据（增量），15 天回溯窗口兜底补漏。不做每天全量重拉（数据源扛不住）。
>
> **北斗清理防误删**（详设阶段 4 有四道防线）：
> 1. **分区键计算**：只清理「上个月」分区（PREV_PTN_KEY），绝碰当月。
> 2. **完整性检查**：`SUCCESS_RECORDS == TOTAL_RECORDS`（上月所有记录下载+分析全 S）才允许清理，`CAN_CLEAN=TRUE`。
> 3. **已清空检查**：逐表 `SELECT COUNT(*) FROM ... PARTITION (p_ptnkey_XX)`，已为 0 则跳过（`ALREADY_CLEAN=TRUE`）。
> 4. **异常回滚**：整个清理过程 try-catch，失败回滚事务记日志。
> - **兜底**：`retentionDays < 3` 直接 skip（防误删近 3 天数据），要清 1-2 天必须显式开 `allowAggressiveCleanup`。

**【口语化回答】**：

> 数据源挂了这块我们有两层保障。一层是回溯机制，每天都会回溯过去 15 天里状态还是 P 的记录重试，所以某天 API 挂了，从第二天起连续 15 天都会自动补下载，不丢数据。另一层是不阻断周报，分析前检查上周 7 天是不是全 S，有 P 就终止这次分析，等数据补齐再跑。宁可延迟一天发完整周报，也不发残缺的。
>
> 增量为主，每天只处理 T-1 一天的数据，不做全量重拉，数据源扛不住。
>
> 北斗清理防误删这块我特别小心，做了四道防线。第一，只清上个月分区，绝不碰当月。第二，完整性检查，上月所有记录必须下载加分析全 S 才允许清。第三，已清空检查，逐表 COUNT 一下，已经是 0 就跳过。第四，异常回滚。还有个兜底，保留天数小于 3 天直接 skip，要清 1 到 2 天必须显式开 allowAggressiveCleanup。
>
> 其实 TRUNCATE 是 DDL 隐式提交不能事务回滚的，所以前面那两道前置检查很关键，确保只在确认安全时才执行。

**【连环追问】**：
- 「15 天回溯还不够怎么办」→ 极端情况（数据源长期宕机），需要人工介入。系统会持续告警，运维拉数据补录后手动置 `PROC_STATUS='S'`。
- 「分区 TRUNCATE 是 DDL，事务能回滚吗」→ MySQL 里 TRUNCATE 是隐式提交，不能事务回滚。所以前面做了完整性检查和已清空检查两道前置校验，确保只在确认安全时才执行。这是详设里有意识的设计。

### Q5. ⚠️ LLM 分析的 Prompt 怎么组装？数据超长（如 5000 条慢 SQL）怎么办？

**【面试官意图】** 详设里反复出现「长度控制：若超过大模型限制则截断或分批」，面试官会追「具体怎么截断、怎么分批、分批结果怎么合并」。

**【参考答案】**：
> **Prompt 组装**：每个模块的数据按「产品 / 模块」分组，组装成结构化文本（表格 + 关键指标），配上分析指令（「请分析上周错误日志量趋势，指出异常模块和可能原因」）。
>
> **超长处理——分批 + 合并**：
> 1. **token 预估**：组装后先计算文本长度（按字符数 × 系数估算 token），与模型限制对比。
> 2. **分批**：超长则按产品/模块维度分批，每批控制在模型窗口安全范围内（留出输出空间）。比如 5000 条慢 SQL 按 DeployUnit 分成 5 批，每批 1000 条。
> 3. **分批分析**：每批独立调 LLM 分析，得到分批结论。
> 4. **合并**：把分批结论作为新输入，再调一次 LLM 做跨批汇总（「以下是 5 个 DeployUnit 各自的慢 SQL 分析，请汇总出全局结论和 Top 风险」）。
> - **替代方案**：如果数据本身就是聚合后的统计值（如 TPS 取每组最大值），先在 SQL 层聚合降量再喂 LLM，避免分批。详设里 TPS 是「按 (API, DeployUnit, 日期) 分组取最大 TPS」后才送 LLM，已经是预聚合。
>
> **交易量异常检测**（模块 3.7 TRANS）：参考智能工场脚本的异常检测算法做**确定性异常点检测**，把检测结果（而不是原始数据）送 LLM 解读——这也是「先确定性计算缩小范围，再 LLM 组织叙述」原则的体现。

**【口语化回答】**：

> Prompt 组装就是把每个模块的数据按产品、模块分组，拼成结构化文本，表格加关键指标，再配一句分析指令，比如「请分析上周错误日志量趋势，指出异常模块」。
>
> 超长的话我们是分批加合并。先估算 token，超了就按产品或者 DeployUnit 维度分批，比如 5000 条慢 SQL 按 DeployUnit 分成 5 批，每批 1000 条。每批独立调 LLM 分析拿到分批结论，再把分批结论作为新输入，再调一次 LLM 做跨批汇总。
>
> 其实有个更优的做法是先在 SQL 层预聚合降量，避免分批。比如 TPS 我们是按 API、DeployUnit、日期分组取最大值之后才送 LLM，已经是预聚合过的了。
>
> 交易量异常检测这块我们是参考智能工场的脚本做确定性异常点检测，把检测结果而不是原始数据送 LLM 解读。这也是「先确定性计算缩小范围，再 LLM 组织叙述」这个原则的体现。

**【连环追问】**：
- 「分批合并会不会丢信息」→ 会，分批是「有损降级」。应对：分批时按业务维度（DeployUnit）而非随机切，保证每批内部完整；合并时让 LLM 显式列出「各批结论 + 跨批共性 + 冲突点」。
- 「LLM 分析结果质量怎么保证」→ 见 Q6（数字校验）

### Q6. ⚠️ LLM 生成的周报数字错了怎么办？这是事故。

**【面试官意图】** 周报系统的命门。安克/卓誉都问了。面试官要看你有没有「数字准确性治理」的工程思维。

**【参考答案】**（「数字与叙述分离」原则的四层防护）：
> 1. **数字不交给 LLM 算**：所有数字（TPS、错误量、慢 SQL 数、交易量）由 SQL `GROUP BY` 聚合算出，存入 `..._ANALYSE_T` 统计表。LLM 看到的是**已经算好的数字**，只做叙述组织。
> 2. **LLM 只做叙述**：LLM 的任务是「把这些数字组织成『本周错误日志量趋势，X 模块异常增长 Y%』这样的句子」，不能改数字。
> 3. **生成后校验**：LLM 输出里出现的数字，回比对统计表里的值，不一致就重生成或回退到模板填充。这一步在组装阶段 3.8 做。
> 4. **统计与解读分表存储**：统计数据在 `..._ANALYSE_T`，LLM 解读在 `AN1_REPORT_LLM_ANALYSE_T`，物理隔离。即使 LLM 解读错了，统计原始数据仍在，可追溯可修正。
>
> **本质思路**：和 Text-to-SQL 那题同一原则——**模型负责表达，确定性逻辑负责准确**。让 LLM 算数是幻觉重灾区，绝不让它碰数字计算。

**【口语化回答】**：

> 这个我特别在意，数字错了就是事故。我们有个核心原则叫「数字与叙述分离」，四层防护。
>
> 第一，数字绝对不交给 LLM 算。所有数字都是 SQL GROUP BY 聚合算出来的，存统计表。LLM 看到的是已经算好的数字，它只负责组织叙述，不能改数字。
>
> 第二，LLM 只做叙述。它的任务就是把这些数字串成「本周错误日志量趋势，X 模块异常增长 Y%」这样的句子。
>
> 第三，生成后校验。LLM 输出里出现的数字，我们会回比对统计表里的值，不一致就重新生成或者回退到模板填充。
>
> 第四，统计和解读分表存储。统计数据在 `_ANALYSE_T` 表，LLM 解读在 `AN1_REPORT_LLM_ANALYSE_T` 表，物理隔离。即使 LLM 解读错了，统计原始数据还在，能追溯能修正。
>
> 说白了就是和 Text-to-SQL 一个原则：模型负责表达，确定性逻辑负责准确。让 LLM 算数是幻觉重灾区，绝不能让它碰数字计算。

**【连环追问】**：
- 「LLM 把 95.23% 写成 95.32% 这种小错怎么防」→ 生成后做数字正则提取 + 比对统计表，不一致拦截。关键指标（如成功率）做双算交叉验证。
- 「用户反馈周报数字错了，怎么定位是哪一步」→ `TECH_TRACE_ID` 链路 ID 贯穿，统计表有原始值，LLM 表有解读值，一比就知道是统计错还是解读错。

### Q7. ⚠️ 如果让 LLM 写 SQL 查数据（Text-to-SQL），它写了 DROP/DELETE 怎么拦截？SQL 性能差怎么办？

**【面试官意图】** 安克面试原题 + 深挖 SQL 性能。两道题考的是「不信任模型 + 工程层兜底」的防御性思维。

**【参考答案·安全防护】**（四层）：
> 1. **SQL 权限隔离**（最硬兜底）：给 LLM 的数据库连接用**只读账号**，DDL/DML 在数据库层直接拒绝。即使 LLM 生成 DROP，DB 层报错。
> 2. **SQL 预校验**：执行前用 SQL parser（如 sqlglot）解析 AST，白名单只允许 SELECT，出现 DROP/DELETE/UPDATE/ALTER/TRUNCATE 直接拦截。
> 3. **关键词黑名单**：兜底检查。
> 4. **沙箱库**：复杂场景查只读副本或脱敏副本，动不到生产。
> - **原则**：永远不信任模型生成的 SQL 直接打生产，权限 + 解析双保险。

**【参考答案·性能防护】**（多数人只想到安全想不到性能，答出来显工程深度）：
> 1. **执行前 EXPLAIN 预估**：拿到 SQL 先 EXPLAIN，检查全表扫描（type=ALL）、笛卡尔积（无 JOIN 条件）、缺索引命中（key=NULL），命中告警规则就拦截重生成。
> 2. **Schema 描述带索引信息**：告诉模型哪些字段有索引、表多大（行数），引导走索引字段过滤。
> 3. **大表保护**：对大表强制要求 WHERE 条件（时间范围），无条件的大表查询直接拒。
> 4. **超时熔断**：执行设超时（如 30s），慢查询熔断返回「查询超时，请缩小范围」。
> - **核心**：不仅要 SQL 对，还要 SQL 快。生产环境慢查询会拖垮库。

**【口语化回答】**：

> 安全这块是四层防护。最硬的兜底是 SQL 权限隔离，给大模型的数据库连接用只读账号，DDL、DML 在数据库层直接拒绝，就算它生成 DROP 也跑不了。然后是 SQL 预校验，执行前用 sqlglot 解析 AST，白名单只允许 SELECT，出现 DROP、DELETE、UPDATE、ALTER 直接拦。再加关键词黑名单兜底。复杂场景就查只读副本或者脱敏副本，动不到生产。原则就是永远不信任模型生成的 SQL 直接打生产。
>
> 性能这块其实多数人只想到安全想不到性能，但生产里慢查询会拖垮库。我们会执行前先 EXPLAIN，检查全表扫描、笛卡尔积、缺索引命中，命中告警就拦截重生成。Schema 描述里会带上索引信息和表行数，引导模型走索引字段过滤。大表强制要求 WHERE 条件，无条件的大表查询直接拒。再设个超时熔断，慢查询直接返回「请缩小范围」。
>
> 核心就是不仅要 SQL 对，还要 SQL 快。

**【连环追问】**：
- 「怎么把表名和字段描述精确给模型」→ 维护表元数据 schema 字典（表名/字段/含义/业务说明），做向量化。用户提问时先检索相关表 schema，把「表名 + 字段说明」作为上下文喂模型。**不灌全库 schema**（太大），按 query 相关性召回相关表。
- 「Text-to-SQL 准确率多少？怎么评估」→ 见 Q9
- 「多部门数据权限怎么隔离」→ 见横向 Q（数据权限隔离）

### Q8. TPS 是怎么算的？为什么 val/60？

**【面试官意图】** 详设里写了「TPS = val/60」，面试官追具体计算逻辑，看你是不是真懂业务。

**【参考答案】**：
> 北斗数据里 `val` 字段是「60 秒内的请求数」。TPS = Transactions Per Second = 每秒请求数，所以 `val / 60` 得到每秒平均请求数。
>
> 处理流程：①把 ISO 时间转 datetime 提取日期；②按 `(API, DeployUnit, 日期)` 分组；③每组取所有时间点 TPS 的**最大值**（同一 API+DeployUnit+日期，一天有多个 60 秒采样点，取峰值 TPS 代表当天最高负载）；④结果存 `AN1_REPORT_TPS_ANALYSE_T` 并送 LLM 分析。
>
> **响应时间分析（RESP）**类似：解析 `kpiList` 里 `resp`（总笔数）、`resp0ms`/`resp50ms`/`resp100ms` 等分桶笔数，算百分比（某段笔数/总笔数×100%），总笔数转「万」单位。这些都是**确定性 SQL/代码计算**，LLM 只解读趋势。

**【口语化回答】**：

> 北斗数据里那个 `val` 字段是「60 秒内的请求数」，TPS 是每秒请求数，所以 val 除以 60 就得到每秒平均请求数。
>
> 处理流程是先把 ISO 时间转 datetime 提取日期，然后按 API、DeployUnit、日期三个维度分组，每组取所有时间点 TPS 的最大值。因为同一个 API 加 DeployUnit 加日期，一天有很多个 60 秒采样点，取峰值 TPS 代表当天最高负载。结果存 TPS 分析表再送 LLM。
>
> 响应时间分析 RESP 类似，解析 kpiList 里总笔数、各个分桶的笔数，算百分比，总笔数转成「万」单位。这些全都是确定性 SQL 或者代码算的，LLM 只解读趋势。

### Q9. Text-to-SQL 准确率多少？怎么评估？bad case 怎么收集？怎么持续优化？

**【面试官意图】** 卓誉/安克都问了准确率。面试官要看你有没有评测体系，不是「感觉还行」。

**【参考答案】**：
> **准确率**：[备真实数，如执行成功率 X%、结果正确率 Y%]。⚠️ 必须能报出数，否则显得没做评估。
>
> **评估方法**：
> - 建 **query-SQL 评测集**（人工标注的正确 SQL + 期望结果）。
> - 用**执行结果正确率**（而非文本相似度）作指标——同一查询有多条正确 SQL（子查询 vs JOIN），文本对比会误判。关注两个数：**执行成功率**（SQL 能跑）和**结果正确率**（跑出来对）。
> - 测试集需覆盖：多表 JOIN、聚合、窗口函数、嵌套子查询、时间范围、方言差异。
>
> **bad case 收集**：线上用户对结果点「不对/重新生成」时记录该 case，定期人工分析归类（表选错/字段错/聚合错/条件错/时间算错），针对性补 schema 描述或加 few-shot 示例。
>
> **持续优化**：把高频 bad case 转成 few-shot 示例放进 prompt，或修正表 schema 描述。建立「bad case → 评测集 → prompt/schema 优化 → 回归测试」闭环。
>
> **诚实**：如果早期没建评测集，说「后补的，应该从第一天就建」——比硬编数据强。

**【口语化回答】**：

> 准确率这块我得先说，[备真实数，比如执行成功率 X%、结果正确率 Y%]，这个数必须能报出来。
>
> 评估方法是建一个 query-SQL 评测集，人工标注正确 SQL 和期望结果。指标用执行结果正确率而不是文本相似度，因为同一个查询有多条正确 SQL，子查询和 JOIN 写法不同但结果一样，文本对比会误判。重点看两个数：执行成功率，也就是 SQL 能不能跑；和结果正确率，跑出来对不对。测试集要覆盖多表 JOIN、聚合、窗口函数、嵌套子查询、时间范围这些。
>
> bad case 收集就是线上用户点「不对、重新生成」的时候记下来，定期人工归类，是表选错了还是字段错了还是聚合错了，针对性地补 schema 描述或者加 few-shot 示例。然后把高频 bad case 转成 few-shot 放进 prompt，建立「bad case 到评测集到优化到回归测试」的闭环。
>
> 诚实说，如果早期没建评测集，就说后补的，应该从第一天就建，比硬编数据强。

**【连环追问】**：
- 「执行结果正确率怎么判断，结果集比对吗」→ 对比结果集行数 + 排序后逐行比对（处理排序差异）；浮点用容差；NULL 单独处理；空集要区分「真没数据」vs「SQL 错了」。
- 「Spider/BIRD 这些公开 benchmark 能反映生产吗」→ 不能完全反映。Spider 是干净 schema + 单轮，生产是多轮对话 + 脏 schema + 业务术语。公开 benchmark 验证模型基础能力，生产要建自己的领域评测集。

## 第四层：杀手锏追问

### Q11. ⚠️【安克·杀手锏】老板看周报发现销量下滑，问「为什么下滑」——根因分析，你们现在能解决吗？让你设计怎么做？

**【面试官意图】** 产品思维考题。安克面试原题。面试官要看你「诚实承认边界 + 有设计思路」。

**【参考答案】**（诚实承认 + 三层设计）：
> **诚实承认**：目前做不到真正的根因分析，只能回答「数据是什么」，回答不了「为什么」。这是明确边界。
>
> 若要设计，拆三层：
>
> **1. 数据层（现有）**：Text-to-SQL，回答「是什么」，拉指标现状。
>
> **2. 归因层（新增核心）**：不让模型直接「猜」原因（会幻觉），建归因分析能力：
> - **多维下钻**：按地区/品类/渠道/时段拆解，定位下滑集中切片（如「华东区 3C 品类下滑最严重」）。
> - **对比基线**：和历史同期、目标值对比，判断趋势性下滑 vs 异常波动。
> - **关联分析**：把相关指标（库存/促销/竞品/流量/客诉）一起拉出看相关性。
> - 用**确定性计算/规则**缩小候选原因，不靠模型凭空猜。
>
> **3. 推理 + 验证层**：把「数据事实 + 候选原因」喂模型做**假设推理**（「可能是 X 促销结束导致 Y 品类下滑」），再**回查数据验证假设**（X 促销确实上周结束？Y 品类下滑时间吻合？），验证通过才输出，不通过标注「待确认」。
>
> **关键原则**：归因的「找候选原因」用确定性方法，模型只做「组织叙述 + 生成可验证假设」，绝不让模型直接编原因——跟「不让模型算数」同一原则。

**【口语化回答】**：

> 这个我得诚实承认，目前做不到真正的根因分析，只能回答「数据是什么」，回答不了「为什么」。这是明确的边界。
>
> 如果要设计，我会拆三层。第一层是数据层，就是现有的 Text-to-SQL，回答「是什么」，拉指标现状。
>
> 第二层是归因层，这是新增的核心。关键是不能让模型直接猜原因，会幻觉。要建归因能力：多维下钻，按地区、品类、渠道、时段拆解，定位下滑集中在哪个切片；对比基线，和历史同期、目标值比，判断是趋势性还是异常波动；关联分析，把库存、促销、竞品、流量、客诉这些相关指标一起拉出来看。用确定性计算缩小候选原因，不靠模型凭空猜。
>
> 第三层是推理加验证层。把数据事实加候选原因喂模型做假设推理，比如「可能是 X 促销结束导致 Y 品类下滑」，再回查数据验证这个假设，促销是不是真结束了、下滑时间对不对得上，验证通过才输出，不通过标「待确认」。
>
> 核心原则就是，归因的找候选原因用确定性方法，模型只做组织叙述加生成可验证假设，绝不让模型直接编原因，跟不让模型算数是一个道理。

### Q13. 讲一讲 CodeWiki 的整体架构。为什么要做这个？

**【面试官意图】** 码云面试原题。面试官要的是「七层架构 + 一句话定位」，不是流水账。

**【参考答案】**（七层 + 核心定位）：
> CodeWiki 是单用户、本地优先的代码理解平台，把一个仓库转成可检索、可视化、可生成文档的代码知识库。**一句话定位：普通 RAG 以 chunk 为中心，CodeWiki 以 graph 为中心**。
>
> 七层架构：
> 1. **仓库接入**：`RepoScanner`（FileSystemWalker + IgnoreMatcher + GitOperations + LanguageDetector），文件打 sha256/mtime/git commit time。
> 2. **AST 结构化**：tree-sitter 多语言（Python/Java/Go/Rust/C/C++/C#/TS/JS），统一产出到 `AstSymbol`（type/name/signature/imports/calls/references/bases/implements/metadata）。
> 3. **Code Graph**：`GraphBuilder` 分五阶段建图——file nodes → symbol nodes → import edges → structure edges（contains/defines/exports/inherits/implements/routes_to）→ call/reference edges。边带 confidence（deterministic/inferred）+ provenance。
> 4. **社区检测**：`CommunityDetector` 用 graspologic Leiden，fallback 到 NetworkX Louvain/greedy。`CommunityRecordBuilder` 生成 deterministic community records，可选 `CommunityNamer` LLM 命名。
> 5. **GraphRAG 检索**：`GraphRAGRetriever`——symbol seed → FTS chunk → optional vector → graph expansion（max_hops 0..4）→ related edges → select source chunks（token budget）→ community summaries → context pack + trace_id。
> 6. **Wiki & Ask**：Ask 用 GraphRAG 回答；Wiki 先 catalog 再逐页生成，必须引用 allowed source refs，服务端生成 Mermaid 图（不让 LLM 画图）。
> 7. **产品入口**：FastAPI + React（Graph/Wiki/Ask/Settings）、CLI（Click）、MCP server、Lite Mode（项目内本地 sqlite，给 AI agent 用）。
>
> 核心设计原则：**AST 和扫描器提供事实，LLM 只负责组织和解释**。所有 Wiki 页面必须通过源码引用校验后才能成为 `generated`。

### Q14. ⚠️ 为什么选 GraphRAG 而不是普通向量 RAG？普通 RAG 哪里不行？

**【面试官意图】** 码云/Ashley 都问了。核心考「GraphRAG 解决了普通 RAG 解决不了的什么问题」。

**【参考答案】**（三个痛点 + 诚实边界）：
> 三个痛点：
>
> 1. **代码含义依赖结构上下文，普通 RAG 召回孤立片段**：用户问「修改 `generate_pages` 会影响哪些地方」，普通 RAG 按文本相似度召回 `generate_pages` 函数本身的 chunk，但**漏掉所有调用方**。GraphRAG 沿 calls 边反向扩展，把「谁调用了它」一起拉出来。这是 GraphRAG 相比普通 RAG 的核心价值：**补全依赖上下文**。
>
> 2. **代码大量专有名词，纯向量不稳定**：函数名、类名、文件路径这些是精确标识符，向量检索容易被语义近邻稀释（`AuthService` 和 `UserService` embedding 很近但完全不同）。需要 FTS 关键词精确命中 + 结构扩展（图）。**纯向量不稳，纯 FTS 不懂结构**。
>
> 3. **Wiki 生成需系统化组织**：社区摘要 + 图边提供模块级视图，普通 RAG 给不了。Wiki catalog 不是文件树直译，而是面向阅读的模块树，需要社区检测提供「哪些符号属于一个功能模块」的信号。
>
> **诚实边界**：单文件内简单任务（「这个函数做什么」）两者差不多，GraphRAG 增益集中在**跨模块**场景——不要夸大成「全面碾压」。

## 第二层：核心机制深挖

### Q15. ⚠️ AST 解析引擎是自研的，讲一讲。用了什么工具？怎么统一多语言？

**【面试官意图】** 码云面试原题。面试官要看你是不是真懂 tree-sitter，还是只是调了个库。

**【参考答案】**（基于 CodeWiki 真实实现）：
> **底层**：tree-sitter 的 Language/Parser/Query，支持 Python/Java/Go/Rust/C/C++/C#/TS/JS 九种语言。
>
> **capture_engine（自研核心）**：`TreeSitterCaptureParser` 用**统一语义 capture name** 驱动查询。每语言有一个 `capture_spec`（tree-sitter query S-expression + capture name 映射），跑 query 拿 capture 结果转成 `DefinitionRecord`。这样上层逻辑与具体语言语法解耦。
>
> **统一产物 AstSymbol**：所有语言归一化到同一结构——`id`（`file_path::name`）、`type`（function/class/method/endpoint...）、`name`、`signature`、`imports[]`、`calls[]`、`references[]`、`bases[]`、`implements[]`、`metadata{}`。下游 `GraphBuilder` 不关心语言。
>
> **augmenter（语言增强器）**：每语言一个（python/java/go...），处理语言特有信息——Python 的装饰器、Java 的 implements、Go 的 export（首字母大写）、TS 的 endpoint（Express/Koa 路由）等。
>
> **并发 + 容错**：ThreadPoolExecutor（默认 min(file, cpu, 4)），捕获 SyntaxError 记录到 `parse_errors` 继续跑（不因一个文件语法错中断全量）。
>
> **AstCache**：按内容 hash 缓存解析结果，增量更新时 unchanged 文件直接复用，减少重复解析成本。
>
> **设计哲学**：**统一性比单语言精确性重要**——宁可每语言都 80% 准确，也要保证跨语言一致的图结构，因为上层检索逻辑与语言无关。

**【口语化回答】**：

> 底层用的是 tree-sitter 的 Language、Parser、Query，支持 Python、Java、Go、Rust、C、C++、C#、TS、JS 九种语言。
>
> 自研的核心是 capture_engine。TreeSitterCaptureParser 用统一语义 capture name 驱动查询，每种语言有一个 capture_spec，就是 tree-sitter query 加 capture name 映射，跑 query 拿 capture 结果转成 DefinitionRecord。这样上层逻辑就和具体语言语法解耦了。
>
> 然后所有语言归一化到同一个 AstSymbol 结构，id 是文件路径加函数名，type 是 function、class 这些，还有 imports、calls、references、bases、implements 这些字段。下游 GraphBuilder 完全不关心是哪种语言。
>
> 每种语言还有一个 augmenter 做语言特有增强，比如 Python 的装饰器、Java 的 implements、Go 的首字母大写导出、TS 的 Express 路由。
>
> 并发用 ThreadPoolExecutor，默认取文件数、CPU、4 的最小值。容错是捕获 SyntaxError 记录到 parse_errors 继续跑，不因一个文件语法错就中断全量。还有个 AstCache 按内容 hash 缓存解析结果，增量更新时没改动的文件直接复用。
>
> 设计哲学就是统一性比单语言精确性重要，宁可每种语言都 80% 准确，也要保证跨语言一致的图结构。

**【连环追问】**：
- 「tree-sitter 产出的是 CST 还是 AST」→ CST（具体语法树，含括号/关键字/空白），保留完整位置信息。CodeWiki 在 CST 之上用 query 抽取所需节点转成更轻的 AstSymbol。
- 「tree-sitter 怎么处理语法错误」→ error recovery 机制，遇到错误插入 ERROR/MISSING 节点继续解析，对半成品代码仍产出可用 CST。这对分析 work-in-progress 代码是刚需。
- 「tree-sitter 增量解析怎么用」→ 单文件内编辑后复用未受影响子树。但 CodeWiki 跨文件增量靠 git diff + sha256 检测脏文件，单文件内复用 AstCache，不是每次全解析。见 Q23。
- 「变量、全局变量、class 在 AST 还是数据库」→ 见 Q22

### Q16. ⚠️ chunk 怎么切分？函数级吗？同一个大函数被切成两个节点，边怎么定义？

**【面试官意图】** Ashley 面试原题。考「切分带来的语义断裂」问题。

**【参考答案】**：
> **函数级为主要粒度**：函数是代码里语义最完整、边界最清晰的最小单元，既不会像按行/token 切那样切碎语义，也不会像按文件切那样粒度太粗。
>
> **超大函数二次切分**：超过 chunk token 上限的函数会被切。这时给两个 chunk 之间加一条特殊的**「同源顺序边」（intra-function / sequential 边）**：
> - 标记它们**本属于同一个函数**，保留先后顺序。
> - 两个子节点共享同一个父函数 ID。
> - 检索时命中其中一个片段，能通过这条边把同一函数的另一半一起召回，**保证函数语义不被割裂**。
> - 组装上下文时按原顺序拼回去。
>
> 这题考的是有没有想过「切分带来的语义断裂」。答「加同源顺序边 + 共享父 ID 拼接」就到位了。

**【口语化回答】**：

> 函数级是主要粒度。因为函数是代码里语义最完整、边界最清晰的最小单元，既不会像按行切那样切碎语义，也不会像按文件切那样粒度太粗。
>
> 超大函数会二次切分。这时候给两个 chunk 之间加一条特殊的「同源顺序边」，标记它们本来属于同一个函数、保留先后顺序，两个子节点共享同一个父函数 ID。检索时命中其中一个片段，能通过这条边把同一函数的另一半一起召回，保证函数语义不被割裂。组装上下文时按原顺序拼回去。
>
> 这题考的就是有没有想过切分带来的语义断裂问题，答「加同源顺序边加共享父 ID 拼接」就到位了。

### Q17. 节点和边具体怎么设计？边带什么属性？

> **节点类型**：repository / directory / file / config / module / class / interface / schema / function / method / endpoint。

> |---|---|---|
> | contains | 包含下级节点 | deterministic |

> | inherits | class 继承 | deterministic 或 inferred |
> | implements | class 实现接口 | deterministic 或 inferred |
> | routes_to | endpoint 指向 handler | inferred（框架检测） |
> | uses_config | 使用配置 | inferred |

> **跨文件 call/reference 是启发式**：不做完整类型推导，重名/动态调用会错。所以要标 inferred + confidence，检索时区别对待。

> 节点类型有 repository、directory、file、config、module、class、interface、schema、function、method、endpoint 这些。

### Q18. ⚠️ GraphRAG 检索的完整流程？检索到代码后，按什么优先级组装上下文？

**【面试官意图】** Ashley 面试原题，现场答得不够好，面试官提示「prompt 排在前面和最后面的信息特别重要」。考「lost in the middle」。

**【参考答案】**（检索流程 + 组装两维度）：
> **检索流程**（design.md 8.2）：
> ```
> query
>   -> seed_from_symbols(query, graph nodes)    # 符号 seed
>   -> search_fts(SQLite FTS5 或 PG tsvector)    # 全文检索
>   -> optional search_vectors(sqlite-vec/pgvector)  # 可选向量
>   -> merge chunk hits into seed nodes
>   -> fallback overview seeds if empty
>   -> graph expansion, max_hops 0..4            # 图扩展
>   -> related_edges(selected nodes)
>   -> select_source_chunks(token budget, proximity, FTS/vector hits)
>   -> community_summaries(selected nodes)
>   -> context_pack + trace_id
> ```
> 输出 `RetrievalTrace`：seed nodes + expanded nodes + related edges + source chunks + community summaries + structured context pack + stable trace id。
>
> **上下文组装——两个维度**：
>
> 1. **筛选/排序维度**（综合打分，不只看向量相似度）：
>    - 向量相关性（与 query 语义相似度）
>    - 图距离（离种子节点几跳，越近越重要）
>    - 节点类型权重（直接被调用的核心函数 > 工具函数）
>
> 2. **位置摆放维度（利用 LLM 的 "lost in the middle" 特性）**——LLM 对 prompt 开头和结尾最敏感，中间容易忽略：
>    - **最重要的信息（用户直接要改的目标函数、明确指令）放在结尾**（离生成位置最近，注意力最高）
>    - **次重要的背景/依赖代码放在开头**
>    - **相关性最低的补充上下文放在中间**
>
> 💡 关键词：**"lost in the middle"**。面试官在暗示的知识点，答出来直接扭转印象。

**【口语化回答】**：

> 检索流程是：query 先 seed_from_symbols 找符号 seed，然后 search_fts 做全文检索，可选 search_vectors 做向量，merge 之后做 graph expansion，max_hops 0 到 4，再 related_edges，select_source_chunks 受 token budget 约束，最后 community_summaries，输出 context pack 加 trace_id。
>
> 组装上下文分两个维度。第一个是筛选排序，综合打分，不只看向量相似度，还加权图距离，就是离种子节点几跳，以及节点类型权重，核心函数比工具函数重要。
>
> 第二个是位置摆放，利用 LLM 的「lost in the middle」特性。大模型对 prompt 开头和结尾最敏感，中间容易忽略。所以最重要的信息，比如用户直接要改的目标函数、明确指令，放在结尾，离生成位置最近注意力最高；次重要的背景依赖代码放在开头；相关性最低的补充上下文放在中间。
>
> 这个词「lost in the middle」是面试官在暗示的知识点，答出来直接扭转印象。

**【连环追问】**：
- 「lost in the middle 为什么会产生」→ Transformer 注意力机制：①位置编码衰减，中间位置离 query（通常在末尾）相对距离远，注意力权重被稀释；②首尾有锚定效应（开头建全局 frame，结尾离生成最近）；③中间往往是冗余过程信息，模型学会降权。
- 「token budget 怎么分配」→ source chunks / nodes+edges / community summaries 各类独立预算，超预算按相关性丢。默认 `graphrag_context_token_budget=8000`。

### Q19. ⚠️ GraphRAG 存在 token 爆炸问题，怎么解决？

**【面试官意图】** 码云面试被问住（现场说「没了解过」），必须会答。

**【参考答案】**：
> **根因**：图扩展不加约束，沿 calls/references 多跳扩展子图指数膨胀。
>
> **控制机制**（六层）：
> 1. **token budget 硬约束**：`graphrag_context_token_budget`（默认 8000）+ `graphrag_max_source_chunks`，超预算丢。
> 2. **扩展深度限制**：`max_hops` 0..4 控制，避免无限 BFS。
> 3. **社区摘要代替全量子图**：用 `community_summaries` 代表模块，token 远小于原始节点。检索时先社区级（粗）定位，再模块内符号级（细）。
> 4. **噪声过滤**：低置信度边、external 节点不扩展。
> 5. **分层检索**：先社区级（粗）定位，再模块内符号级（细）。
> 6. **context pack 结构化**：source chunks + nodes/edges + community summaries，每类独立预算，不混在一起算。
>
> **本质**：GraphRAG 的 token 控制是「用结构化摘要替代原始子图」——不是把整张子图塞进去，而是用社区摘要 + 精选 source chunks + 关键边，在有限 token 里表达最多信息。

**【口语化回答】**：

> 根因是图扩展不加约束，沿 calls、references 多跳扩展子图会指数膨胀。
>
> 我们用六层控制。第一，token budget 硬约束，默认 8000，加 max_source_chunks，超预算丢。第二，扩展深度限制，max_hops 0 到 4，避免无限 BFS。第三，社区摘要代替全量子图，用 community_summaries 代表模块，token 远小于原始节点。第四，噪声过滤，低置信度边、external 节点不扩展。第五，分层检索，先社区级粗定位，再模块内符号级细查。第六，context pack 结构化，source chunks、nodes 和 edges、community summaries 各类独立预算，不混在一起算。
>
> 本质就是用结构化摘要替代原始子图，不是把整张子图塞进去，而是用社区摘要加精选 source chunks 加关键边，在有限 token 里表达最多信息。

### Q20. ⚠️ 向量库怎么选型？涉不涉及向量更新删除？有没有随机改单条向量？

**【面试官意图】** 码云面试原题（三连问）。

**【参考答案】**：
> **选型**：**跟随主存储**，不引入独立向量服务：
> - SQLite（FTS5 + sqlite-vec）/ PostgreSQL（tsvector + pgvector）。
> - 理由：①本地优先、零外部依赖；②FTS 和 vector 同库避免跨库一致性；③单用户中小规模够用。
> - 边界：多租户 SaaS 该上独立向量库（Milvus/Qdrant）。
>
> **向量是可选路径**：第一层召回靠符号搜索 + FTS，vector 是语义增强。embedding 需 LLM provider，成本高，做成 `include_embeddings` 可选。pgvector 不可用时 GraphRAG 降级到 symbol + FTS + graph expansion。
>
> **更新删除**：涉及，但不是「随机改单条向量」，是**跟着代码变更走的批量增量**：
> - **更新触发**：`IncrementalUpdater` 优先 git diff 找候选文件，兜底 sha256 对比。只对 changed/new 重算 embedding。
> - **删除**：deleted 文件 → 删对应 chunks / graph 节点边 / embedding 行。
> - **怎么定位原始向量**：靠稳定主键 `chunk_id`（repo_id + file_path + 行范围/hash），不靠向量相似度反查。embedding 行用同 `chunk_id` 做外键，upsert/删按 `chunk_id` 精确。
>
> **没有手动改单条向量接口**——向量无业务语义，单独改只破坏一致性，要改源头（代码/chunk）向量跟着重算。

**【口语化回答】**：

> 选型上我们跟随主存储，不引入独立向量服务。SQLite 配 FTS5 加 sqlite-vec，PostgreSQL 配 tsvector 加 pgvector。理由是本地优先、零外部依赖，FTS 和 vector 同库避免跨库一致性，单用户中小规模够用。边界是多租户 SaaS 该上 Milvus、Qdrant 这种独立向量库。
>
> 向量是可选路径，第一层召回靠符号搜索加 FTS，vector 是语义增强。pgvector 不可用时 GraphRAG 降级到 symbol 加 FTS 加 graph expansion。
>
> 更新删除是涉及的，但不是随机改单条向量，是跟着代码变更走的批量增量。IncrementalUpdater 优先 git diff 找候选文件，兜底 sha256 对比，只对 changed 和 new 重算 embedding。删除是 deleted 文件就删对应 chunks、graph 节点边、embedding 行。定位原始向量靠稳定主键 chunk_id，不靠向量相似度反查。
>
> 没有手动改单条向量接口，因为向量无业务语义，单独改只破坏一致性，要改就改源头代码或 chunk，向量跟着重算。

**【连环追问·遗留问题】**（码云追问，诚实回答）：
1. **chunk_id 稳定性 vs 内容变化权衡**：内容 hash 派生则小改全重算（浪费）；行范围派生则插入错位。无完美解。
2. **embedding 模型升级要全量重算**：不同模型向量空间不兼容，按 model 分区但切换是重活。Agent 记忆系统里有 `manifest.ts` 检测 + `reindexAll` 的方案，CodeWiki 这里是明确待补。
3. **retrieval trace 未持久化**：`/graphrag/traces/{trace_id}` 还是 `not_persisted_yet`。
4. **启发式解析边可能误**：跨文件 call/reference 是启发式 + 置信度，重名/动态调用会错。

### Q21. ⚠️ 增量更新怎么做？和 Claude Code init markdown 比优势在哪？

**【面试官意图】** 增量更新是 GraphRAG 对比 markdown 记忆的核心优势，必须讲清。

**【参考答案】**：
> **增量更新两层**：
> 1. `IncrementalUpdater`（图层）：
>    - 优先 git diff 找候选文件，兜底 sha256 对比 changed/new/deleted/unchanged。
>    - **复用 unchanged 文件的旧 symbols**（从 AstCache 恢复），只解析 changed/new。
>    - 刷新 changed/new 文件 chunks。
>    - 根据 changed files、deleted files、affected graph refs 标记 doc pages stale。
> 2. `WikiIncrementalStrategy`（文档层）：
>    - 对 catalog nodes 和 existing pages 做 dirty planning。
>    - missing、draft、stale、metadata changed 页面需要重新生成。
>    - translated language 页面如果缺失/draft/base slug 刚生成，需要重新翻译。
>
> **vs Claude Code init markdown 四个优势**：
> 1. **确定性 vs 概率性**：Claude Code init 让模型自己读仓库总结存 markdown——**概率性**，可能漏关键依赖、可能总结错。GraphRAG 基于 **AST 静态解析**，调用关系是**确定性、精确**的。
> 2. **增量更新 vs 全量重扫**：markdown 记忆怎么增量更新？要么过期失效，要么重新 init 全扫。GraphRAG 基于 git diff 增量更新只变动节点。
> 3. **检索精度**：markdown 是自由文本，模型从大段文本「自己找」靠语义相似度容易漏。GraphRAG 结构化检索，按图精确扩展，召回准可解释。
> 4. **规模**：大仓库 init 一次性扫成本极高，markdown 膨胀后检索质量下降；GraphRAG 离线建图在线按需检索，规模可扩展。
>
> **诚实**：Claude Code init 适合**小仓库、快速上手、不需要精确依赖**；GraphRAG 适合**大仓库、跨模块、需要精确依赖**。分层互补，不是替代。

**【口语化回答】**：

> 增量更新有两层。图层是 IncrementalUpdater，优先 git diff 找候选文件，兜底 sha256 对比，复用 unchanged 文件的旧 symbols，只解析 changed 和 new，刷新对应 chunks，然后根据变更标记受影响的 Wiki 页面 stale。文档层是 WikiIncrementalStrategy，对 catalog 和 existing pages 做 dirty planning，missing、draft、stale、metadata changed 的页面要重新生成。
>
> 和 Claude Code init markdown 比有四个优势。第一，确定性 vs 概率性，init 让模型自己读仓库总结，是概率性的可能漏可能错；GraphRAG 基于 AST 静态解析，调用关系是确定性的精确的。第二，增量更新 vs 全量重扫，markdown 怎么增量？要么过期要么重新 init 全扫；图基于 git diff 只动变更节点。第三，检索精度，markdown 是自由文本模型自己找容易漏；GraphRAG 结构化检索按图精确扩展。第四，规模，大仓库 init 成本极高，GraphRAG 离线建图在线检索可扩展。
>
> 诚实说，Claude Code init 适合小仓库快速上手，GraphRAG 适合大仓库跨模块工程化，是分层互补不是替代。

### Q22. ⚠️ 变量、函数、全局变量、class 类，是在 AST 里存还是在数据库里存？社区检测为什么用 Leiden？

**【面试官意图】** 码云面试原题（两连问）。

**【参考答案·存储】**：
> **两层都存，职责不同**：
> - **AST 层（瞬时）**：解析产生 AstSymbol 列表，中间产物，**不持久化原始 AST**。
> - **数据库层（持久化）**：GraphBuilder 把 AstSymbol 转图节点存库。`code_node`（file/config/class/function/method/endpoint/schema）+ `code_edge`（contains/defines/imports/calls/...）+ `code_chunk`（源码片段，FTS + 可选 embedding）+ `ast_cache`（缓存解析结果，增量复用）。
>
> **全局变量**：没有显式 def 节点的，通过 reference/assignment 捕获，作 reference 边或 file-level symbol 存，**不单独建节点**（避免图膨胀）。
> **成员变量**归 class 节点，**局部变量**不持久化（作用域太局部）。

**【参考答案·Leiden 社区检测】**：
> **为什么做社区检测**：Wiki catalog 不是文件树直译，而是面向阅读的模块树。社区检测提供「哪些符号属于一个功能模块」的信号——把调用关系密集的符号聚成一个社区，对应一个 Wiki 页面主题。
>
> **为什么 Leiden 而非 Louvain**：
> - Louvain 有个核心缺陷：**社区内部不连通**——模块度优化时起桥接作用的节点被移走，旧社区可能变成内部不连通（某部分仅通过社区外节点路径与社区其余部分相连）。
> - Leiden 增加了**分区细化（refinement）阶段**，允许把社区再拆分，保证子集最优性和社区间良好连通。
> - Leiden 用「快速局部移动（fast local move）」只访问邻居发生变化的节点，比 Louvain 遍历所有节点更高效。
>
> **CodeWiki 实现**：graspologic Leiden → fallback NetworkX Louvain → greedy。`CommunityDetector` 只做图分区，`CommunityRecordBuilder` 从 partitions + graph facts 生成 deterministic community records，`CommunityNamer` 可选 LLM 命名。**Detector 不生成名称**，避免算法和 presentation 耦合。
>
> **层次化**：Leiden 产生 level 0/1/2 层级社区，对应从微观到宏观的摘要。Global Search 在某层（通常顶层）遍历所有社区报告做 MapReduce。

**【口语化回答】**：

> 两层都存，职责不同。AST 层是瞬时的，解析产生 AstSymbol 列表，中间产物，不持久化原始 AST。数据库层是持久化的，GraphBuilder 把 AstSymbol 转图节点存库，有 code_node、code_edge、code_chunk、ast_cache 这些表。全局变量没有显式 def 节点的，通过 reference 捕获，作 reference 边或 file-level symbol 存，不单独建节点避免图膨胀。成员变量归 class 节点，局部变量不持久化。
>
> 社区检测为什么用 Leiden。首先是为什么做--Wiki catalog 不是文件树直译，是面向阅读的模块树，社区检测提供「哪些符号属于一个功能模块」的信号。
>
> 为什么 Leiden 不用 Louvain 呢，Louvain 有个核心缺陷是社区内部可能不连通，模块度优化时桥接节点被移走，旧社区可能变成内部不连通。Leiden 增加了分区细化阶段，允许把社区再拆分，保证子集最优性和社区间良好连通，而且用快速局部移动只访问邻居变化的节点，比 Louvain 更高效。
>
> 我们用 graspologic Leiden，fallback 到 Louvain 再 fallback 到 greedy。Detector 只做图分区不生成名称，避免算法和 presentation 耦合。

### Q23. 大仓库（百万行）建图要多久？增量更新机制？

### Q24. Wiki 页面生成流程？怎么保证 LLM 不编造源码引用（source refs）？

**【面试官意图】** 考防幻觉工程化。CodeWiki 的核心设计是「LLM 只负责组织，事实由 AST 提供」。

**【参考答案】**（design.md 9.3）：
> **单页生成流程**：
> ```
> catalog item
>   -> GraphRAG retrieve(topic, max_hops=3)
>   -> add source_hints chunks
>   -> compute allowed_source_refs        # 关键：只允许引用这些文件
>   -> ReadFile evidence from repo path
>   -> diagram plan from graph facts
>   -> PageGenerationPayloadBuilder.build
>   -> page.md system prompt
>   -> stable page generation contract message
>   -> dynamic Page payload message
>   -> LLM JSON response
>   -> JSON repair retry if needed
>   -> PageResponseValidator
>        source_refs exist and are allowed  # 校验引用合法
>        citations match returned refs      # citation 校验
>        markdown has required sections
>        diagram placeholders are known
>   -> replace citations
>   -> compose relevant source files + diagrams + source list
>   -> validate Mermaid blocks
>   -> upsert DocPageRecord
> ```
>
> **防幻觉四层**：
> 1. **allowed_source_refs 硬约束**：LLM 只能引用 `allowed_source_refs` 范围内的 source_refs，超出即校验失败。
> 2. **citation 校验**：Markdown 里 `[[S1]]` 类 citation marker 必须对应合法 source ref。服务端自动补齐 markdown 使用到但 response 未列出的 source refs，过滤未使用的。
> 3. **Mermaid 服务端生成**：**不让 LLM 画图**（画图极易幻觉），LLM 只放 `[[DIAGRAM:...]]` placeholder，Mermaid 基于图事实服务端生成 + 校验。
> 4. **状态规则**：校验全过 = `generated`；LLM 调用失败/JSON 修复失败/source_refs 失败 = `draft`。Mermaid 失败不导致 draft（移除图表保留正文）。
>
> **repair retry**：校验失败时把 validation errors + previous response 放进动态 payload（不改变稳定 contract 前缀），让 LLM 修，最多重试 N 次。

**【口语化回答】**：

> 单页生成流程是：catalog item 先 GraphRAG retrieve，加 source_hints chunks，然后 compute allowed_source_refs 这个很关键，只允许引用这些文件，再 ReadFile evidence，diagram plan，PageGenerationPayloadBuilder build，然后 system prompt 加 stable contract message 加 dynamic payload message 喂 LLM，拿到 JSON response，需要的话 JSON repair retry，再过 PageResponseValidator，校验 source_refs 存在且 allowed、citations 匹配、markdown 有必需 section、diagram placeholder 合法，然后 replace citations、compose 源文件加图表、validate Mermaid、最后 upsert。
>
> 防幻觉四层。第一，allowed_source_refs 硬约束，LLM 只能引用这个范围内的，超出就校验失败。第二，citation 校验，Markdown 里 [[S1]] 这种 marker 必须对应合法 source ref，服务端自动补齐和过滤。第三，Mermaid 服务端生成，不让 LLM 画图，画图极易幻觉，LLM 只放 placeholder，图基于图事实服务端生成加校验。第四，状态规则，校验全过才是 generated，失败就是 draft。
>
> repair retry 是把 validation errors 加 previous response 放进动态 payload，不改变稳定 contract 前缀，让 LLM 修，最多重试 N 次。

**【连环追问】**：
- 「为什么 message 形状要稳定（system + stable contract + dynamic payload）」→ 优化 provider prefix cache。稳定前缀让 DeepSeek 等 OpenAI-compatible provider 复用 `prompt_cache_hit_tokens`。批量执行时第一个 page 预热前缀缓存，后续并发 page 命中。

### Q25. 多语言支持怎么统一？跨语言调用怎么建边？

**【参考答案】**：
> **语言内**：用对应语言的 tree-sitter grammar + capture_spec，调用关系精确（Java 的 method invocation、Python 的 call、Go 的 function call）。
>
> **跨语言**：通过**接口契约**建边——服务间 RPC/HTTP 调用、FFI、protobuf 定义。这类边基于接口描述文件（IDL/swagger）匹配，而非源码级直接解析。边类型标记为「跨语言调用」，权重低于语言内调用。
>
> **统一 IR**：设计统一抽象图 schema（Function/Class/Module 通用节点类型 + 语言特定属性）。tree-sitter 的统一 query S-expression 有助于跨语言抽取。新增语言只需加 capture_spec + augmenter，上层检索逻辑不变。
>
> **诚实**：跨语言边本质是**协议级**而非**源码级**，要诚实标注其确定性低于语言内边，检索时区别对待。

**【口语化回答】**：

> 语言内用对应语言的 tree-sitter grammar 加 capture_spec，调用关系是精确的，Java 的 method invocation、Python 的 call、Go 的 function call 都能精确解析。

### Q26. ⚠️【安克·生死线】我直接用 Claude Code 对仓库做 init，生成 markdown 长期记忆，跟你 GraphRAG MCP 区别多大？模型自己抓重点做长期记忆，是不是比做成 GraphRAG 给模型更优？

> 这两种是不同思路，GraphRAG 有几个 markdown 记忆替代不了的优势：
>
> 1. **确定性 vs 概率性**：Claude Code init 让模型自己读仓库、自己总结重点存 markdown——这是**概率性**的，模型可能漏关键依赖、可能总结错。GraphRAG 基于 **AST 静态解析**，调用关系、依赖关系是**确定性、精确**的，不会漏调、不会幻觉。**代码这种「错一个调用链就跑不通」的场景，精确性比「聪明总结」更重要**。
>

### Q31. ⚠️ 整体架构形态？为什么这样设计？有什么优缺点？

**【面试官意图】** 京东面试原题。考架构师视角的全局思考。

**【参考答案】**（基于真实实现）：
> **架构**：宿主无关内核（TdaiCore）+ 两条链路 + 后台调度器 + 混合召回：
>
> 1. **Host 层**：OpenClaw（in-process）/ Hermes（Python provider via HTTP）/ Standalone CLI / Docker。
> 2. **Adapter 层**：`HostAdapter + LLMRunnerFactory + RuntimeContext` 让 Core host-neutral。
> 3. **TDAI Core Facade**：`tdai-core.ts`，对外 6 个方法（handleBeforeRecall / handleTurnCommitted / searchMemories / searchConversations / handleSessionEnd / destroy）。
> 4. **长期 Pipeline**：L0 recorder → L1 extractor → L2 SceneExtractor → L3 PersonaGenerator，由 `MemoryPipelineManager` 调度。
> 5. **短期 Offload**：StateManager + Hooks（after_tool_call / llm_input_l3 / before_prompt_build）+ L2 Mermaid pipeline。
> 6. **存储**：`IMemoryStore` 抽象 + SQLite / TCVDB 两个实现 + Embedding + BM25 + RRF。
> 7. **Gateway**：`node:http` HTTP sidecar，端口 8420。
>
> **rationale（为什么这样设计）**：
> 1. **宿主无关**（HostAdapter）：同一份 TdaiCore 既能 OpenClaw 里 new 出来直调，也能被 gateway/server.ts 包装成 HTTP 服务，零代码改动。runtime 换记忆层不动。
> 2. **记忆分层**：生命周期/召回/可信度/token 成本不同，混在一起召回难解释。
> 3. **召回要稳**：向量 + BM25 + 结构三路 RRF 融合，单一检索不稳。
> 4. **压缩要可恢复**：offload 留索引，热路径有损冷路径可还原。
>
> **优缺点（诚实）**：
> - **优点**：跨会话连续性、幻觉治理深（span + 置信度 + 冲突检测）、token 可控（WideSearch 实测 ↓61.38%）、宿主无关。
> - **缺点**：①复杂度高（四层 + 调度器 + 三路召回，小场景过度设计，重做会合并 L1/L2）；②L2→L3 晋升靠累积冷启动慢；③异步调度有延迟窗口；④混合召回权重需调参；⑤SQLite 单进程写，多 Agent 并发要上 TCVDB。

**【口语化回答】**：

> 架构是宿主无关内核 TdaiCore 加两条链路加后台调度器加混合召回。Host 层支持 OpenClaw、Hermes、Standalone CLI、Docker。Adapter 层用 HostAdapter 加 LLMRunnerFactory 让 Core host-neutral。TDAI Core Facade 对外 6 个方法。长期 Pipeline 是 L0 到 L1 到 L2 到 L3 逐层蒸馏。短期 Offload 是 StateManager 加 Hooks 加 Mermaid pipeline。存储是 IMemoryStore 抽象加 SQLite 或 TCVDB 加 Embedding 加 BM25 加 RRF。Gateway 是 node:http 的 sidecar 端口 8420。
>
> 为什么这么设计。宿主无关是因为同一份 TdaiCore 既能 OpenClaw 里 new 出来直调，也能被 gateway 包成 HTTP 服务零代码改动。记忆分层是因为生命周期、召回、可信度、token 成本都不同混在一起难解释。召回要稳是因为向量加 BM25 加结构三路 RRF 融合，单一检索不稳。压缩要可恢复是因为 offload 留索引，热路径有损冷路径可还原。
>
> 优缺点诚实说。优点是跨会话连续性、幻觉治理深、token 可控、宿主无关。缺点是复杂度高，四层加调度器加三路召回小场景过度设计重做会合并 L1 L2；L2 到 L3 晋升靠累积冷启动慢；异步调度有延迟窗口；混合召回权重需调参；SQLite 单进程写多 Agent 并发要上 TCVDB。

### Q32. ⚠️ 做长期记忆的原因——长上下文导致准确率下降，到底体现在哪些方面？

**【面试官意图】** 微众面试重点 1。面试官明确要求「具体观察到的现象，不是业界通用问题的泛泛而谈」。

**【参考答案】**（三个层面 + 主动讲不下降的）：
> 我实际观察到长上下文导致准确率下降，主要体现在**三个层面**，不是所有层面都下降：
>
> **层面 1·关键约束被「稀释」丢失（会下降）**：
> 现象：用户早期轮次给的精确约束（文件路径、参数值、命名规范、错误原文），在对话拉长后模型开始「模糊化」——把 `recall_checkpoint.json` 写成 `recall_checkpoint.jsonl`，把「不要用 X 框架」忘掉用了 X。这些是**精确的、点状的信息**，被大量工具日志和中间推理淹没，注意力被稀释。
>
> **层面 2·工具结果之间的「串扰」（会下降）**：
> 现象：第 5 轮读了文件 A 的内容，第 10 轮要改文件 B，模型把 A 的某个字段名「记成」是 B 的——跨工具结果的字段/路径混淆。具体例子：agent loop 了 10 轮排查问题，第 3 轮读了调度器代码（含 `l2DelayAfterL1` 参数），第 11 轮要改压缩逻辑时，模型把 `l2DelayAfterL1` 当成了压缩层的参数写进去——实际上它属于 L2 调度。这是工具结果串扰导致的偏差。
>
> **层面 3·重复信息导致的「自信错误」（会下降）**：
> 现象：同一个错误日志在上下文里出现多次（agent 反复尝试同类操作），模型对这条错误信息过度「自信」，在第 11、12 轮基于这个错误信息做推理，即使它其实是早期一次失败尝试的噪声。重复曝光让模型误判为「重要且正确」，实际是噪声被放大。
>
> **不下降的层面（主动讲，显得有观察）**：
> - **主题/意图理解**：模型对「用户在做什么」的大方向保持力强，不会因上下文长而跑题。
> - **近期 K 轮**：最近几轮的细节保持好（模型对近期信息注意力高）。
> - 下降集中在中期、远期的**精确点状信息**和**工具结果间的区分度**。
>
> **设计对应**：值串扰 → Context Offload 把工具日志移出上下文只留摘要+索引；约束丢失 → L1/L3 把稳定约束抽出来沉淀。**不是先有「长期记忆」概念再套功能，是先有这两个实际问题再设计分层**。

**【口语化回答】**：

> 我实际观察到长上下文导致准确率下降主要体现在三个层面，不是所有层面都下降。
>
> 第一个，关键约束被「稀释」丢失。用户早期轮次给的精确约束，文件路径、参数值、命名规范、错误原文，在对话拉长后模型开始模糊化，把 recall_checkpoint.json 写成 jsonl，把「不要用 X 框架」忘掉用了 X。这些是精确的点状信息，被大量工具日志淹没注意力被稀释。

> 第二个，工具结果之间的「串扰」。第 5 轮读了文件 A 的内容，第 10 轮要改文件 B，模型把 A 的字段名记成是 B 的。具体例子，agent loop 了 10 轮排查问题，第 3 轮读了调度器代码含 l2DelayAfterL1 参数，第 11 轮要改压缩逻辑时，模型把 l2DelayAfterL1 当成压缩层的参数写进去，实际上它属于 L2 调度。

### Q33. ⚠️ L1 抽取怎么避免重复/冲突？冲突检测具体流程？

**【面试官意图】** Ashley/微众都问了。记忆系统的命门。

**【参考答案】**（基于 `l1-dedup.ts` + `l1-extractor.ts`）：
> 1. LLM 一次 JSON 输出 scene 切分 + 候选 atoms。
> 2. 对每个候选 atom embed 后调 `searchL1Vector(topK=5, conflictRecallTopK)` 拉相似旧记忆。
> 3. 让 LLM 做一轮 **conflict detection**（`prompts/l1-dedup.ts`）：返回 `MERGE / OVERWRITE / KEEP_BOTH / DROP`。
> 4. 按决策写入 `records/<session>.jsonl` 并 `upsertL1`。
>
> **为什么用 LLM 判断而不是 cosine 阈值**：LLM 在判断「这两条事实是同一件事吗 / 有冲突吗」时比 cosine 相似度准——cosine 只能说「语义像」，但「我用 Vue3」和「我用 React」语义像但事实冲突。
>
> **冲突处理**：
> - **可变属性**（当前项目/状态）：**新值覆盖**，旧值标过期保留（可溯源）。
> - **不可变属性**（姓名）：**降置信度 + 标记冲突**，下次让主模型结合上下文判断用哪个，而不是盲目覆盖。
>
> **置信度计算**：基础分来自抽取时 LLM 自评（带 span 的给高分）+ **频次加权**（同一事实多次出现/跨会话稳定，置信度累积上升）+ **冲突惩罚**（出现冲突降分）。晋升阈值：L2→L3 要达到一定置信度 + 频次才晋升。

**【口语化回答】**：

> 流程是：LLM 一次 JSON 输出 scene 切分加候选 atoms，对每个候选 atom embed 后调 searchL1Vector 拉 topK 5 的相似旧记忆，然后让 LLM 做一轮 conflict detection，返回 MERGE、OVERWRITE、KEEP_BOTH、DROP 四种决策，按决策写入 jsonl 并 upsertL1。
>
> 为什么用 LLM 判断而不是 cosine 阈值呢？因为 LLM 在判断「这两条事实是不是同一件事、有没有冲突」时比 cosine 准。cosine 只能说语义像，但「我用 Vue3」和「我用 React」语义像但事实冲突。
>
> 冲突处理分情况。可变属性比如当前项目状态，新值覆盖旧值标过期保留可溯源；不可变属性比如姓名，降置信度加标记冲突，下次让主模型结合上下文判断用哪个，不盲目覆盖。
>
> 置信度计算是基础分来自抽取时 LLM 自评带 span 的给高分，加频次加权同一事实多次出现累积上升，减冲突惩罚。晋升阈值 L2 到 L3 要达到置信度加频次双阈值。

**【连环追问·微众挑战】**「你为什么会确认呢？让用户确认其实很难，他为什么要确认？」
> **诚实承认**：依赖用户确认是不现实的——这是设计短板。当时是内部工具、用户是同事可以约定确认，但不能作为通用方案。
> **更通用的不依赖用户确认方案**：
> 1. **可变属性直接覆盖**（不确认）：新值生效，旧值标过期保留。
> 2. **不可变属性冲突——降置信度而非求确认**：不弹给用户，召回时这条记忆带「冲突」标记，主模型结合当前上下文判断用哪个。
> 3. **多源交叉验证**：同一事实多次独立提到（不是同一次重复），置信度自动上升；只出现一次的冲突值自动降权。
> 4. **隐式反馈修正**：模型用了某条记忆后用户直接改掉（「不对，我叫 B 不是 A」），修正信号回流自动更新记忆。
> **核心修正**：把「主动问用户确认」改成「降置信度 + 召回时让模型判断 + 隐式反馈修正」。用户无感，记忆质量仍能维护。

### Q35. ⚠️ PipelineManager 里 L1/L2 timer 为什么要不一样？Warmup 是什么？

**【面试官意图】** 考调度器设计的精细度。这是项目最有工程含量的部分之一。

**【参考答案】**（基于 `managed-timer.ts`）：
> **L1 = idle debounce（resettable timer）**：只要还在聊就推迟提取。用**可重置 timer**——每来一条对话，倒计时重置。语义：用户还在输入，等他说完再提取，避免频繁打断。
>
> **L2 = SLA 保证（downward-only timer）**：必须有上限频率，不能因为 L1 不停就一直推迟。用 **`tryAdvanceTo`（只能往前提，不能延后）**——`max(now+delay, lastL2+min)` 是「响应需求」，`now+maxInterval` 是「保活兜底」，取较早者。语义：L1 可以等，但 L2 有 SLA 上限必须跑。
>
> 两种语义共享 `ManagedTimer`（`utils/managed-timer.ts`）：
> - `schedule(delayMs, cb)`：cancel + set new（L1 resettable 用）。
> - `tryAdvanceTo(epochMs, cb)`：只在更早时 reschedule（L2 downward-only 用）。
> - `flush()`：shutdown 时立即触发（不检查 isDestroyed，by design）。
>
> **Warmup 模式**：新 session 的 L1 阈值从 1 开始指数翻倍：1 → 2 → 4 → … → `everyN=5`。原因：新会话最初几轮用户会一次性给很多偏好（「我用 Vue3 + TS」），尽快把它们沉淀到 L1，召回时立即生效。阈值翻倍后稳态频率回归，避免一直 L1 浪费 LLM。`enableWarmup` 在 PipelineSessionState 里维护 `warmup_threshold`，每次 L1 跑完翻倍。

**【口语化回答】**：

> L1 是 idle debounce 用的 resettable timer，只要还在聊就推迟提取，每来一条对话倒计时重置。语义是用户还在输入等他说完再提取，避免频繁打断。
>
> L2 是 SLA 保证用的 downward-only timer，必须有上限频率不能因为 L1 不停就一直推迟。用 tryAdvanceTo，只能往前提不能延后，取响应需求和保活兜底的较早者。语义是 L1 可以等但 L2 有 SLA 上限必须跑。
>
> 两种语义共享 ManagedTimer。schedule 是 cancel 加 set new 给 L1 用；tryAdvanceTo 是只在更早时 reschedule 给 L2 用；flush 是 shutdown 时立即触发。
>
> Warmup 模式是新 session 的 L1 阈值从 1 开始指数翻倍，1、2、4 到 everyN 5。原因是新会话最初几轮用户会一次性给很多偏好，比如「我用 Vue3 加 TS」，尽快沉淀到 L1 召回时立即生效。阈值翻倍后稳态频率回归，避免一直 L1 浪费 LLM。

### Q36. ⚠️ Checkpoint 怎么做？crash 后怎么恢复？schedulerStartPromise 那段注释在防什么 bug？

**【面试官意图】** 考并发竞态处理。这是项目最难的 bug 之一。

**【参考答案】**（基于 `tdai-core.ts:88-105` 源码注释）：
> **Checkpoint**：`utils/checkpoint.ts` 维护 `~/.openclaw/memory-tdai/checkpoint.json`，对每个 sessionKey 持久化 `PipelineSessionState`（conversation_count、warmup_threshold、lastL1At、lastL2At、scene_block_signatures…）。启动时 `TdaiCore.ensureSchedulerStarted()` 读 checkpoint → `scheduler.start(restoredStates)`。
>
> **schedulerStartPromise 防的 bug**（直接搬源码注释）：
> > Under the Gateway, several HTTP requests can reach `handleTurnCommitted` concurrently and all race into `ensureSchedulerStarted`. Using a plain boolean flag is unsafe: the first caller flips the flag to true *before* the await completes, so subsequent callers slip past the check and touch the scheduler before `start()` has actually run - which makes `start()`'s `sessionStates.set(key, restored)` later clobber the state that those concurrent captures already incremented.
>
> 简单说：boolean flag 在 `await` 之前置 true，后续请求误以为初始化已完成，绕过去直接给 scheduler 写状态；之后 start() 又用 checkpoint 覆盖回去 → 计数丢失。
>
> **修复**：改用**共享 in-flight Promise**——所有并发请求 `await` 同一个 promise。start 失败再清掉 promise 让下个请求重试；成功后保留 resolved promise 作 sentinel，后续调用 collapse 成 cheap already-resolved await。

**【口语化回答】**：

> Checkpoint 是 utils 下的 checkpoint.ts 维护一个 checkpoint.json，对每个 sessionKey 持久化 PipelineSessionState，包括 conversation_count、warmup_threshold、lastL1At、lastL2At、scene_block_signatures 这些。启动时 ensureSchedulerStarted 读 checkpoint 再 scheduler.start 传 restoredStates。
>
> schedulerStartPromise 那段注释防的 bug 是这样的：Gateway 下多个 HTTP 请求并发进 handleTurnCommitted，都 race 进 ensureSchedulerStarted。如果用普通 boolean flag，第一个 caller 在 await 之前就把 flag 置 true，后续 caller 误以为初始化已完成绕过去直接给 scheduler 写状态；然后 start 又用 checkpoint 覆盖回去，计数就丢了。
>
> 修复是改用共享 in-flight Promise，所有并发请求 await 同一个 promise。start 失败清掉 promise 让下个请求重试，成功后保留 resolved promise 作 sentinel，后续调用 collapse 成 cheap 的 already-resolved await。

**【连环追问】**：
- 「`bgTasks` 是什么？destroy 为什么要等它」→ 后台异步任务集合（Set<Promise>），目前只装 SQLite 的 deferred L0 embedding 写入。destroy 时要先 close DB，但如果 background task 还在跑会撞上「database is not open」。解决：`destroy()` 里 `await Promise.allSettled(pending)`（5s 硬超时兜底）再 `vectorStore.close()`。
- 「`handleSessionEnd` 为什么不能复用 destroy」→ 两个语义完全不同：`gateway_stop`（进程退出）→ 整个 host 都要走，全部销毁，调 `destroy()`；`on_session_end`（Hermes 单会话结束）→ 只有这一个 session 结束，其它 session 还在用同一个 process，**绝不能**销毁 scheduler。历史 bug 就是把这两个混了：旧代码做 `scheduler.destroy() + recreate`，导致每次 `/session/end` 把所有并发 session 的 in-memory 状态清掉。修复：`handleSessionEnd` 只做 `scheduler.flushSession(sessionKey)`，并被测试 `P0-1: handleSessionEnd must be scoped to its session` 锁死。

### Q37. ⚠️ 大模型抽取判断错误（幻觉）怎么办？怎么保证长期记忆准确？

**【面试官意图】** Ashley 面试核心题。记忆系统最深的坑。

**【参考答案】**（五层防护）：
> 长期记忆最大风险是**一次幻觉被固化成长期错误事实**，后面反复召回污染 agent。几层防护：
>
> 1. **抽取阶段加 span 约束**：LLM 抽事实**必须给原文出处（span）**，找不到依据直接丢弃——减少凭空捏造。`shouldExtractL1` 还会拒绝明显的 prompt-injection-like 内容。
> 2. **置信度打分**：每条记忆带置信度。低置信度/单次出现的进「候选区」，**多次出现/被确认后才晋升** L2/L3。L2→L3 要达到置信度 + 频次双阈值。
> 3. **冲突检测**：入库前和已有记忆做一致性校验（见 Q33）。
> 4. **可溯源 + 可失效**：每条记忆能追溯到 L0 原始对话，发现错误能定位和撤销。
> 5. **召回时二次校验**：关键场景召回记忆后，让主模型结合当前上下文判断记忆是否仍适用，而非无脑信任。
>
> **核心思路**：**不追求单次 100% 准确（做不到），而是通过「多次确认晋升 + 溯源 + 置信度 + 冲突检测」让错误记忆难以固化、且可回滚**。

**【口语化回答】**：

> 长期记忆最大风险是一次幻觉被固化成长期错误事实，后面反复召回污染 agent。我们五层防护。
>
> 第一，抽取阶段加 span 约束，LLM 抽事实必须给原文出处，找不到依据直接丢弃，减少凭空捏造。shouldExtractL1 还会拒绝明显的 prompt-injection 内容。
>
> 第二，置信度打分，每条记忆带置信度，低置信度单次出现的进候选区，多次出现被确认后才晋升 L2 L3，L2 到 L3 要置信度加频次双阈值。
>
> 第三，冲突检测，入库前和已有记忆做一致性校验。
>
> 第四，可溯源加可失效，每条记忆能追溯到 L0 原始对话，发现错误能定位撤销。
>
> 第五，召回时二次校验，关键场景召回后让主模型结合当前上下文判断记忆是否仍适用，而非无脑信任。
>
> 核心思路是不追求单次 100% 准确做不到，而是通过多次确认晋升、溯源、置信度、冲突检测让错误记忆难以固化且可回滚。

### Q38. ⚠️【微众挑战】Mermaid 任务画布只是日志定位，不是上下文压缩？这个功能到底解决什么问题？

**【面试官意图】** 微众面试最关键的挑战。面试官用 Claude Code compact 框架挑战你的设计。

**【参考答案】**（先承认 + 讲清定位差异）：

>
> **Mermaid 画布解决的是「长任务的问题定位与跳转」，不是「对话历史的压缩」**：
> 在 coding agent 的长任务里，真正的问题不是「50 轮对话记不住」，而是**agent 在 loop 模式里不停调工具，上下文被 tool result 撑爆，但根因还没找到**。这时如果粗暴 compact（摘要），会把关键证据（错误日志、文件路径）摘要掉，agent 失去追溯能力。
>

> - **上下文里只放图 + 摘要**，token 大幅下降（WideSearch 实测 ↓61.38%）。
> - **agent 不需要从头 loop**，而是看图判断「最可能出问题的节点在哪」，**有跳转地**去读那个节点的原文（按 node_id → result_ref 找回），而不是一层层重查。
> - 这是**把「线性重放」变成「图上跳转定位」**，解决的是长任务根因排查的效率问题。
>
> **和 Claude Code compact 的区别**：
> | 维度 | Claude Code compact | 我的 Context Offload + Mermaid |
> |---|---|---|
> | 解决问题 | 50 轮对话后摘要压短，继续对话 | 长任务 loop 里 tool result 撑爆 + 根因难定位 |
> | 压缩方式 | 暴力摘要（有损） | 工具日志移出 + 留索引（可恢复） |
> | 证据保留 | 摘要可能丢细节 | 原文不丢，按索引找回 |
> | 定位能力 | 无（摘要后是连续文本） | 图结构支持跳转定位 |
>
> **诚实承认**：如果严格按「上下文压缩 = 把长对话压短继续对话」这个定义，那我的 Offload 部分是压缩，Mermaid 画布更偏任务管理。我之前把两者放一起讲，确实容易让人误解，这是表述上的问题。

### Q39. ⚠️ L3 三级压缩（cascade / aggressive / emergency）怎么决策？

**【参考答案】**（基于 `hooks/llm-input-l3.ts`）：
> 在 `after_tool_call` 和 `before_prompt_build` 拿到当前 message snapshot，用 tiktoken 计算 totalTokens，与 contextWindow 对比：
>
> | 级别 | 触发条件 | 操作 |
> |---|---|---|
> | **Mild cascade** | totalTokens > `mildOffloadRatio × contextWindow`（默认 0.5）| 按相关性排序，把分数低的 tool result 替换为 `<offloaded id=t1 summary=...>` 占位符。原文还在 `refs/<node_id>.md`，需要时 read_file 拿回（`confirmedOffloadIds`）|
> | **Aggressive** | > `aggressiveCompressRatio × contextWindow`（默认 0.85）| 直接删除最旧 messages，并 `buildHistoryMmdInjection` 把 history MMD 注入删除位作语义补偿；记录 `_lastAggressiveBoundary`。原始 tool result 仍在 refs/ 但 LLM 看不到（`deletedOffloadIds`）|
> | **Emergency** | LLM 抛 token-overflow 异常（`isTokenOverflowError`）| 强制保留至少 `EMERGENCY_MIN_MESSAGES_TO_KEEP` 条最近消息，其它全删 |
>
> **`_mmdContextMessage` 标记的作用**：
> - `mmd-injector.injectMmdIntoMessages` **整体重写**而不是 append——先 `removeMmdMessages` 把所有带标记的旧注入删掉，再插入新版本，避免重复。
> - L3 三级压缩 **必须跳过** 带 marker 的消息，否则会把刚注入的 MMD 删掉。
> - 这种 marker 模式比「按消息内容前缀识别」更稳，因为 LLM 不会自己生成这个 JS 私有属性。
>
> **`waitForL15`**：L1.5 还没 settle 之前，无法确定 active task 边界，此时注入 MMD 会用错误的 active MMD 误导 Agent。所以 assemble 路径 `injectMmdIntoMessages({ waitForL15: true })` 会跳过注入保留旧 MMD，等 L1.5 settle 后下一轮再注入。
>
> **token 估算策略**：`consecutiveQuickSkips` 计数器允许连续 N 次用 fast estimate（启发式，5-10% 误差），到阈值或命中关键判断（aggressive 阈值附近）就跑一次精确 tiktoken。`lastKnownTotalTokens` 缓存上次精确值作快速估算基线。常态不付 tiktoken 成本。

**【口语化回答】**：

> 在 after_tool_call 和 before_prompt_build 拿到当前 message snapshot，用 tiktoken 算 totalTokens 和 contextWindow 比。
>
> Mild cascade 是 totalTokens 超过 0.5 倍窗口，按相关性排序把分数低的 tool result 替换成占位符，原文还在 refs 目录需要时 read_file 拿回，记到 confirmedOffloadIds。
>
> Aggressive 是超过 0.85 倍窗口，直接删最旧 messages，并 buildHistoryMmdInjection 把 history MMD 注入删除位作语义补偿，记 _lastAggressiveBoundary。原始 tool result 还在 refs 但 LLM 看不到了，记 deletedOffloadIds。
>
> Emergency 是 LLM 抛 token-overflow 异常，强制保留至少 EMERGENCY_MIN_MESSAGES_TO_KEEP 条最近消息其它全删。
>
> _mmdContextMessage 标记的作用：injectMmdIntoMessages 是整体重写不是 append，先 removeMmdMessages 删旧注入再插新版本避免重复；L3 三级压缩必须跳过带 marker 的消息否则会把刚注入的 MMD 删掉；这种 marker 模式比按消息内容前缀识别更稳，因为 LLM 不会自己生成这个 JS 私有属性。

### Q41. ⚠️ SQLite + sqlite-vec 是怎么做向量搜索的？为什么不用 FAISS？

**【参考答案】**（基于真实实现）：
> `sqlite-vec` 是 vec0 虚拟表，支持 `MATCH`/`distance` 子句的 cosine similarity。
>
> **选它原因**：
> 1. **零依赖**：随 plugin 装，无需用户再装 redis/qdrant；
> 2. **事务一致性**：metadata 表与 vec 表在同一个 SQLite BEGIN/COMMIT 里，避免半成品；
> 3. **WAL 足够**：单进程读写，性能完全够 Agent 单用户使用。
>
> **FAISS 不行**：纯内存，没事务，crash 丢数据；C++ 依赖在 Win/macOS 上构建噩梦。
>
> **vec0 不支持 ON CONFLICT，upsert 怎么做**：`delete + insert`，包在事务里：
> ```sql
> BEGIN;
> DELETE FROM l1_vec WHERE record_id=?;
> INSERT INTO l1_vec(...) VALUES (...);
> INSERT OR REPLACE INTO l1_records(...) VALUES (...);
> COMMIT;
> ```
> 事务保证：metadata 写成功但向量挂了，整体 rollback，不会出现「有元数据没向量」的脏状态。
>
> **SQLite 多进程安全**：WAL 模式，多进程读 + 单进程写安全；写竞争靠文件锁。单 OpenClaw 实例 = 一个 plugin process = 一个 DatabaseSync 连接；多实例真同时跑写不在 supported topology。

**【口语化回答】**：

> sqlite-vec 是 vec0 虚拟表，支持 MATCH 和 distance 子句做 cosine similarity。
>
> 选它三个原因。零依赖，随 plugin 装不用用户再装 redis、qdrant。事务一致性，metadata 表和 vec 表在同一个 BEGIN COMMIT 里避免半成品。WAL 足够，单进程读写性能完全够 Agent 单用户用。
>
> FAISS 不行，纯内存没事务 crash 丢数据，C++ 依赖在 Win、macOS 上构建噩梦。
>
> vec0 不支持 ON CONFLICT，upsert 是 delete 加 insert 包在事务里，保证 metadata 写成功但向量挂了整体 rollback，不会出现有元数据没向量的脏状态。
>
> SQLite 多进程安全是 WAL 模式多进程读加单进程写安全，写竞争靠文件锁。单 OpenClaw 实例就是一个 plugin process 一个 DatabaseSync 连接，多实例真同时跑写不在 supported topology。

**【连环追问】**：
- 「sqlite-vec vs sqlite-vss」→ sqlite-vec 是 vss 的继任者。vss 依赖 FAISS 体积大跨平台编译难；sqlite-vec 纯 C 零依赖，可跑浏览器(WASM)/树莓派/移动端，面向「本地 AI」。
- 「大规模（百万级）性能」→ sqlite-vec 早期版本是暴力线性扫描或基础 ANN，无 HNSW/IVF，大规模召回延迟高。CodeWiki 是单用户中小规模够用；多租户大规模该上独立向量库。sqlite-vec 优势是能和关系数据 JOIN 做混合过滤。
- 「Node 22 的 node:sqlite 同步 API 不阻塞 event loop 吗」→ 会短暂阻塞。策略：Auto-capture 的 L0 写入是 metadata-only（轻），事务毫秒级；嵌入这种大计算开 bgTasks 后台跑；L1/L2/L3 是 LLM 主导本身 IO-bound，DB 时间忽略。真要无阻塞可包 worker_threads，但实测 P99 远低于 LLM 调用，没必要。

### Q42. ⚠️ 混合检索（Hybrid）怎么融合？为什么用 RRF 不用加权？

**【面试官意图】** 考检索算法理解。RRF 是项目核心。

**【参考答案】**（基于 `search-utils.ts`）：
> 用 **RRF（Reciprocal Rank Fusion）**：
> ```
> score(d) = Σ_i  1 / (k + rank_i(d))    # k 通常 60
> ```
>
> **为什么 RRF 不用加权（`α·vec + β·fts`）**：
> - 加权的问题是两类分数**尺度差异大**，FTS 的 BM25 可能 1.5，cosine 是 0.78，权重根本调不准；
> - 要加权得先归一化（min-max/z-score），但归一化对分布敏感、不稳定；
> - RRF **只看排名不看分数**，完全消除尺度差，对未知数据集更鲁棒，且**零调参**（k=60 是 Cormack 2009 论文经验值）。
>
> **RRF 的代价**：丢弃了分数蕴含的「置信度」信息——两个检索器都把某文档排第 1，但一个置信度极高、一个勉强，RRF 一视同仁；也无法按检索器质量做加权。但生产里这个代价可接受，鲁棒性更重要。
>
> **BM25 为什么自己用 jieba-wasm 在 Node 端跑而不是 Python sidecar**：
> 早期版本是 Python sidecar，问题：①用户必须装 Python3 + jieba 安装链路长；②JSON-RPC over stdin 容错差，Python crash 整个 plugin 卡住；③跨平台（Windows）行为差异大。现在用 `@tencentdb-agent-memory/tcvdb-text`（jieba-wasm）纯 TS，跟 Node 同进程，零外部依赖。
>
> **encodeTexts vs encodeQueries**：TF-only vs IDF。`encodeTexts(docs)` 写入用按 TF 编码；`encodeQueries(query)` 检索用按 IDF 加权（稀有词权重高）。这是 BM25 在 BGE-M3 论文里同样的做法。

**【口语化回答】**：

> 用 RRF，就是 Reciprocal Rank Fusion，公式是 score 等于对每路检索器求 1 除以 k 加 rank，k 通常 60。
>
> 为什么 RRF 不用加权呢？加权的问题是两类分数尺度差异大，BM25 可能 1.5，cosine 是 0.78，权重根本调不准。要加权得先归一化但归一化对分布敏感不稳定。RRF 只看排名不看分数，完全消除尺度差，对未知数据集更鲁棒，而且零调参，k 等于 60 是 Cormack 2009 论文经验值。
>
> RRF 的代价是丢弃了分数蕴含的置信度信息，两个检索器都把某文档排第 1 但一个置信度高一个勉强，RRF 一视同仁。但生产里这个代价可接受，鲁棒性更重要。
>
> BM25 为什么自己用 jieba-wasm 在 Node 端跑而不是 Python sidecar？早期是 Python sidecar，问题是要装 Python3 加 jieba 安装链路长，JSON-RPC over stdin 容错差 Python crash 整个 plugin 卡住，跨平台 Windows 行为差异大。现在用 jieba-wasm 纯 TS 跟 Node 同进程零外部依赖。
>
> encodeTexts 和 encodeQueries 的区别是 TF-only vs IDF，写入用 TF 编码保留文档里 token 频率，检索用 IDF 加权稀有词权重高，这是 BM25 在 BGE-M3 论文里同样的做法。

**【连环追问】**：
- 「RRF 之后还要接 Reranker 吗」→ 互补不重复。RRF 是排序融合（只看多路排名意见），Reranker 是语义精排（cross-encoder 对每对 query-passage 联合编码打分）。典型两阶段：多路召回 top-100 → RRF 融合 → cross-encoder 精排 top-10 → LLM。RRF 快但粗，Reranker 精但慢。
- 「BM25 相比 TF-IDF 的改进」①词频饱和（k1 参数亚线性增长，防高频词堆砌霸榜）；②文档长度归一化（b 参数惩罚过长文档）。代码场景重要：函数名/错误码/文件路径这些精确标识符，向量检索易被语义近邻稀释，BM25 补这块。
- 「向量检索擅长什么、BM25 擅长什么」→ 向量擅长语义相似（同义/paraphrase）；BM25 擅长词面精确匹配（专有名词/错误码/人名/代码标识符）。失败例子：查 `ERROR_ECONNRESET_10054`，向量可能返回语义相近但不匹配的错误码，BM25 精确定位。所以生产 RAG 几乎都用混合。

### Q43. Embedding 模型换了怎么办？BGE-M3 不支持 dimensions 参数怎么兼容？

**【参考答案】**：
> **Embedding 模型切换**：`manifest.ts` 把 provider+model+dimensions 持久化为 `manifest.json`。下一次 init 检测到 `EmbeddingProviderInfo` 变化 → `StoreInitResult.needsReindex=true`。Pipeline factory 触发 `vectorStore.reindexAll(embedFn, onProgress)`，按 batch 重新 embed L0 + L1 全量数据，期间召回降级到 keyword-only。
>
> **BGE-M3 兼容**：加了 `embedding.sendDimensions: false` 配置。OpenAI text-embedding-3-* 的 Matryoshka 表示需要发 `dimensions`，但 BGE-M3 / 自部署模型见到这个字段会 HTTP 400 `does not support matryoshka representation`。在 `parseConfig` 里默认 true 保持向后兼容，BGE 用户显式置 false。
>
> **Embedding 服务三档超时**：
> - `recallTimeoutMs`：用户路径，必须短，超时直接跳过召回（`Promise.race`）。
> - `captureTimeoutMs`：后台路径（dedup），可以容忍长一点。
> - `timeoutMs`：兜底默认值。
> 真实场景里，5s 召回超时就跳过；后台 dedup 跑 30s 也无所谓。

**【口语化回答】**：

> Embedding 模型切换是 manifest.ts 把 provider、model、dimensions 持久化成 manifest.json。下一次 init 检测到 EmbeddingProviderInfo 变化就 needsReindex 等于 true，Pipeline factory 触发 reindexAll 按 batch 重新 embed L0 加 L1 全量数据，期间召回降级到 keyword-only。
>
> BGE-M3 兼容是加了 sendDimensions false 配置。OpenAI text-embedding-3 系列的 Matryoshka 表示需要发 dimensions，但 BGE-M3 见到这个字段会 HTTP 400 does not support matryoshka representation。parseConfig 里默认 true 保持向后兼容，BGE 用户显式置 false。
>
> Embedding 服务三档超时：recallTimeoutMs 是用户路径必须短超时直接跳过召回用 Promise.race；captureTimeoutMs 是后台路径 dedup 可以容忍长一点；timeoutMs 是兜底默认值。真实场景 5 秒召回超时就跳过，后台 dedup 跑 30 秒也无所谓。

**【连环追问】**：
- 「`Promise.race` + setTimeout 在 Node 里有内存泄漏风险吗」→ 有——如果 `setTimeout` 不 clear，就算 race 已经赢，timer 仍然挂在 event loop 直到 fire。源码里 `auto-recall.ts` 的写法：`inner.finally(() => { if (timer) clearTimeout(timer); })`，关键：inner 先 resolve 时也能 clear。这是 Node 编程常错点。
- 「SQLite → TCVDB 怎么迁移」→ `scripts/migrate-sqlite-to-tcvdb/` 脚本，靠 `IMemoryStore` 抽象走 TCVDB 的 `upsertL1 / upsertL0`，迁移逻辑只关心 record 不关心目标类型。

### Q44. ⚠️【微众】怎么取？什么时候加载 L0/L1/L2/L3？L0 下钻会不会很慢？

**【参考答案】**（由抽象到具体、按需下钻）：
> **加载策略**：
> - **L3（画像）+ L2（相关事实）默认每次加载**：体积小、价值密度高，几乎每次调用都带上。`appendSystemContext` 做成稳定 prompt 段落（Persona + Scene Nav + tools-guide）→ 上层（OpenAI/Anthropic）能命中 prompt cache，复用已计费 token。
> - **L1（场景/摘要）按相关性召回**：当前 query 和某历史场景相关时召回。`prependContext` 是动态 per-turn 内容（recalled L1 atoms）。
> - **L0（原始对话）只在精确溯源/细节时加载**：用户追问具体对话细节或核对原文才下钻。
>
> 简单说：**L3/L2 常驻，L1 按需召回，L0 兜底下钻**。
>
> **L0 下钻延迟控制**：
> 1. **L3+L2 常驻预加载**：会话开始就加载好，热路径基本不下钻。
> 2. **L1 按需召回**：毫秒级，可接受。`auto-recall.ts` 用 `Promise.race` 套 `recall.timeoutMs=5000`，超时直接跳过注入，绝不阻塞用户。
> 3. **L0 下钻异步化**：用户追问细节需要 L0 时，先返回「正在查询历史记录...」，异步查完再补，不阻塞主响应。
> 4. **L0 索引优化**：原始对话按时间/主题建索引，下钻时按索引定位片段而非全扫。
> 原则：**热路径只碰 L2/L3/L1，L0 是冷路径异步兜底**。

**【口语化回答】**：

> 加载策略是：L3 画像加 L2 相关事实默认每次加载，体积小价值密度高几乎每次都带上，appendSystemContext 做成稳定 prompt 段落让 OpenAI、Anthropic 能命中 prompt cache 复用已计费 token。L1 场景摘要按相关性召回，当前 query 和某历史场景相关时召回，prependContext 是动态 per-turn 内容。L0 原始对话只在精确溯源或细节时加载，用户追问具体对话细节或核对原文才下钻。
>
> 简单说就是 L3 L2 常驻，L1 按需召回，L0 兜底下钻。
>
> L0 下钻延迟控制：L3 加 L2 常驻预加载会话开始就加载好热路径基本不下钻；L1 按需召回毫秒级可接受，用 Promise.race 套 recall timeout 5 秒超时直接跳过注入绝不阻塞用户；L0 下钻异步化用户追问细节先返回「正在查询历史记录」异步查完再补不阻塞主响应；L0 索引优化原始对话按时间主题建索引下钻时按索引定位片段而非全扫。原则是热路径只碰 L2 L3 L1，L0 是冷路径异步兜底。

### Q45. ⚠️【最深】压缩错了会不会「幻觉放大」——压缩层一错，后面全错？

### Q50. ⚠️【小天才·延展题】基于周报（日志采集）+ CodeWiki（代码解析）两个项目能力，设计一个「多系统日志根因诊断」系统

**【参考答案】**（分三部分，每部分具体到步骤）：

#### 第一部分：需要哪些数据（五类）
> 1. **告警/异常本身**：错误码、错误消息、堆栈、发生时间、发生服务。
> 2. **各服务日志**：出问题服务 + 上下游服务日志，按时间窗口拉取（告警前后 X 分钟）。
> 3. **链路追踪数据（trace）**：请求在微服务间的调用链——微服务根因诊断的关键，没 trace 就不知道请求经过哪些服务、在哪段出错。
> 4. **服务拓扑关系**：服务间依赖关系（A 调 B，B 调 C）——静态拓扑，判断上下游是谁。
> 5. **代码本身**：相关服务源码（定位到具体代码行，甚至让模型生成修复建议）。

#### 第二部分：怎么处理（三步）
> **步骤 1·按 trace 串起调用链**：拿到告警的 trace_id，从 trace 数据还原完整调用链：请求经过哪些服务、每段耗时、哪段返回错误码。**确定性**的（按 trace_id 关联），不靠模型猜。
>
> **步骤 2·按服务拓扑 + 时间窗口拉日志**：从调用链确定「涉事服务集合」（出错的 + 它调用的 + 调用它的）。按拓扑拉这些服务时间窗口内日志。**过滤**：只留 ERROR/WARN + 含 trace_id 的，去掉无关 INFO——避免日志洪流淹没模型。
>
> **步骤 3·结构化 + 喂模型**：把「调用链 + 过滤后日志 + 错误码」结构化成统一诊断上下文，喂大模型做根因推理。

#### 第三部分：具体排查链路（6 步，必须具体）
> ```
> 1. 告警触发 -> 拿到 (错误码=500, trace_id=abc123, 时间=10:03, 出错服务=服务B)
>
> 2. 按 trace_id 查 trace 系统 -> 还原调用链
>    例: 网关 -> 服务A -> 服务B(返回 500) -> 服务C
>    确定: 服务B 直接报错, 但根因可能在它调用的服务C, 或它自己的代码
>
> 3. 按"出错服务B + 它的下游服务C"拉日志(时间窗口 ±5min)
>    按错误码 + trace_id 过滤, 去掉无关日志
>
> 4. 错误码映射 -> 缩小问题范围
>    错误码字典: 500_xxx -> "下游超时" / "数据格式错" / "空指针" 等
>    这一步用确定性规则, 不靠模型
>
> 5. 模型根因推理(关键步骤):
>    输入: 调用链 + 过滤后日志 + 错误码语义 + 服务B/C 相关源码(CodeWiki 提供)
>    模型判断: 根因在服务B 自己的代码, 还是服务C 返回的异常数据
>    例: 模型发现服务C 在 10:03:12 返回了 null 字段,
>        服务B 没做 null 检查直接用 -> 空指针 500
>        根因: 服务C 的数据问题(或服务B 缺防御)
>
> 6. (延展) 生成修复建议:
>    定位到服务B 的具体代码行 -> 模型生成补丁建议(加 null 检查)
>    用 CodeWiki 图谱拉取"出问题函数 + 调用方 + 依赖"作上下文(不只单文件)
>    跑测试验证 -> 通过自动提 MR, 失败回退人工
> ```
>
> **关键论点**：
> - **trace 串链 + 拓扑拉日志 + 错误码缩小范围**——这三步确定性的，不靠模型猜，把候选范围缩小。
> - **模型只在第 5 步做根因推理**，输入是已结构化、过滤好的上下文，不是把一堆原始日志糊给模型。
> - **第 6 步修复**结合 CodeWiki 的代码解析能力——这是面试官明确要的「两个项目延展」。

**【口语化回答】**：

> 需要五类数据。第一，告警异常本身，错误码、错误消息、堆栈、发生时间、发生服务。第二，各服务日志，出问题服务加上下游日志按时间窗口拉。第三，链路追踪 trace，请求在微服务间的调用链，没 trace 就不知道请求经过哪些服务在哪段出错。第四，服务拓扑关系，A 调 B、B 调 C 这种静态拓扑判断上下游。第五，代码本身，相关服务源码定位到代码行甚至让模型生成修复。
>
> 处理三步。第一步按 trace 串调用链，拿 trace_id 还原完整链路确定性关联不靠模型猜。第二步按拓扑加时间窗口拉日志，从调用链确定涉事服务集合，过滤只留 ERROR WARN 加含 trace_id 的去掉无关 INFO。第三步结构化加喂模型，把调用链、过滤后日志、错误码结构化喂大模型做根因推理。
>
> 具体排查链路 6 步：告警触发拿到错误码 500、trace_id abc123、时间 10:03、出错服务 B；按 trace_id 查 trace 还原调用链网关到 A 到 B 返回 500 到 C，B 直接报错但根因可能在 C 或 B 自己代码；按 B 加下游 C 拉日志时间窗口正负 5 分钟，用错误码加 trace_id 过滤；错误码字典把 500 映射到下游超时或数据格式错或空指针缩小范围；模型根因推理输入调用链加过滤日志加错误码语义加 B C 源码，模型判断根因在 B 代码还是 C 返回异常数据，比如发现 C 返回 null B 没做 null 检查空指针 500；最后生成修复建议定位到 B 代码行模型生成补丁。
>
> 关键论点是 trace 串链加拓扑拉日志加错误码缩小范围这三步确定性的不靠模型猜，模型只在第 5 步做根因推理输入是结构化过滤好的上下文不是糊原始日志，第 6 步修复结合 CodeWiki 代码解析能力。

### Q51. ⚠️【京东】设计一个 AI 模型路由引擎架构：①100ms 内路由决策；②故障 500ms 内 failover；③可审计

**【面试官意图】** 京东面试核心系统设计题。考架构师潜质。

**【参考答案】**：
> **架构**：Router Core（Feature Extractor → Decision Engine → Model Selector）+ Executor（Model Caller + Health Monitor + Failover Controller）+ Audit Log。决策上下文常驻 Redis。
>
> **数据流**：请求 → Gateway → 特征提取（缓存）→ 决策引擎（规则 + 轻量 ML 打分，纯内存 <1ms）→ 选模型 + 预排 fallback list → Executor 调用 → 故障触发 Failover → 审计异步写。
>
> **100ms 决策**：决策不调 LLM 不查 DB，规则 + GBDT 打分纯内存 + Redis，整链路 <10ms。
>
> **500ms failover**：预排 fallback list（不重新决策）+ 熔断器（内存查 <1ms）+ 硬超时（300ms 无响应判故障）+ 健康信号预热。检测 <300ms + 切换 <50ms ≈ <500ms。
>
> **可审计**：每次路由落审计日志（task 特征/候选/选中/原因/版本/时间/user_id）+ failover 单独记 + 异步写 ES/ClickHouse 不阻塞 + trace_id 用户可见 + append-only 不可篡改。

**【口语化回答】**：

> 架构是 Router Core 加 Executor 加 Audit Log。Router Core 有 Feature Extractor、Decision Engine、Model Selector，Executor 有 Model Caller、Health Monitor、Failover Controller，决策上下文常驻 Redis。
>
> 数据流是请求进 Gateway，特征提取带缓存，决策引擎用规则加轻量 ML 打分纯内存小于 1 毫秒，选模型加预排 fallback list，Executor 调用，故障触发 Failover，审计异步写。
>
> 100ms 决策是决策不调 LLM 不查 DB，规则加 GBDT 打分纯内存加 Redis 整链路小于 10 毫秒。500ms failover 是预排 fallback list 不重新决策加熔断器内存查小于 1 毫秒加硬超时 300ms 无响应判故障加健康信号预热，检测小于 300 加切换小于 50 大约小于 500。可审计是每次路由落审计日志加 failover 单独记加异步写 ES 不阻塞加 trace_id 用户可见加 append-only 不可篡改。

**【连环追问 1·分水岭】**「两个模型延迟成本几乎一样，怎么决策？」
> 不能用延迟成本做 tie-breaker，引入其他维度：①**实时质量信号**（在线表现/用户反馈/抽样评分）；②**健康度/负载**；③**能力匹配度**（按 task_type 细分）；④**流量分散/容灾**（故意分流，一个挂了另一个承接）；⑤**一致性 hash**（都分不出按 user_id/session_id 固定路由保证体验一致）。

**【连环追问 2·最难】**「怎么判断哪个模型效果更好？路由时任务还没执行，你怎么知道效果？」（事前决策 vs 事后信号悖论）
> 用**历史信号 + 在线反馈**，不等这次执行完：
> 1. **离线质量基线**：每模型在各类任务的预先评分（benchmark + 人工标注 + 历史线上）。
> 2. **在线反馈信号**：①显式（点踩/点赞、采纳/拒绝）；②隐式（重新提问/中断/停留/复制）；③下游（agent 后续步骤是否成功）。
> 3. **反馈回流更新质量分**：multi-armed bandit 思路（exploration vs exploitation），某模型某类任务反馈变差则降分。
> 4. **探索机制**：留小比例流量 exploration 随机选非 top-1，防评分过期。
> 5. **A/B + 影子评估**：新模型先影子跑对比输出，积累信号再放量。
> 核心：**事前用历史基线初判，事后用在线反馈修正，exploration 持续校准**。

**【连环追问 3】**「模型抖动，要预先替换，怎么设计？」（抖动 ≠ 硬故障，要提前识别趋势）
> 1. **实时健康指标采集**：成功率/p50/p99 延迟/错误率/超时率，滑动窗口算。
> 2. **抖动判定**：p99 连续 N 窗口超阈值 / 成功率滑动下降 / 错误率突增超 baseline+3σ。满足即判「抖动中」，不等完全失败。
> 3. **主动降权而非立即熔断**：抖动期把路由权重降（100%→20%），流量优先导健康模型，保留小流量探测——避免误判踢掉好模型。
> 4. **预热备用**：检测到抖动提前把 fallback list 下一个预热（发探测请求确认健康）。
> 5. **半开探测恢复**：降权后每隔一段时间放少量流量探测，连续成功 N 次才恢复权重。
> 6. **告警 + 人工兜底**。
> 原则：**抖动靠趋势预判 + 降权缓冲，不是等硬故障才 failover**。

### Q52. ⚠️【码云】大模型的幻觉问题是怎么产生的？从机制层讲。

**【面试官意图】** 码云面试被指出「理解不准确」，必须从机制层重学。

**【参考答案】**：
> **幻觉本质**：**大模型是概率生成模型，不是检索系统**——生成「当前上下文下概率最高的 token 序列」，不是「事实正确的 token 序列」。
>
> **产生原因**：
> 1. **训练目标决定它是「流畅」而非「正确」**：next-token prediction，优化「像人话、连贯」不优化「符合事实」。
> 2. **知识存储是参数化的、隐式的**：知识压缩进权重，没有「知识库 + 检索」边界，问事实是从权重「回忆」概率分布，回忆不准就是幻觉。
> 3. **训练数据噪声**：语料有错误/过时/虚构内容，模型分不清事实还是虚构陈述。
> 4. **上下文冲突/知识截止**：训练有截止日期，问训练后的事实没有，但生成本能驱使它「编一个看起来合理」的答案，不说「我不知道」。强上下文里用户暗示错误前提，模型会顺从（sycophancy）。
> 5. **长尾知识采样不足**：高频知识记得准，长尾/冷门权重表示模糊，容易张冠李戴。
> 6. **解码策略**：高 temperature/top-p 增加随机性放大幻觉。
>
> 一句话：**幻觉不是 bug，是概率生成模型的固有特性——它优化「说得像」不优化「说得对」**。消除不可能，靠外部约束（RAG/引用校验/工具验证）压到可控。

**【口语化回答】**：

> 幻觉本质是，大模型是概率生成模型不是检索系统，它生成的是「当前上下文下概率最高的 token 序列」不是「事实正确的 token 序列」。
>
> 产生原因几个。第一，训练目标决定它是流畅而非正确，next-token prediction 优化像人话连贯不优化符合事实。第二，知识存储是参数化的隐式的，知识压缩进权重没有知识库加检索边界，问事实是从权重回忆概率分布回忆不准就是幻觉。第三，训练数据噪声，语料有错误过时虚构内容模型分不清事实还是虚构。第四，上下文冲突或知识截止，训练有截止日期问训练后的事实没有但生成本能驱使它编一个看起来合理的答案不说我不知道，强上下文里用户暗示错误前提模型会顺从。第五，长尾知识采样不足高频记得准长尾模糊容易张冠李戴。第六，解码策略高 temperature top-p 增加随机性放大幻觉。
>
> 一句话，幻觉不是 bug 是概率生成模型的固有特性，它优化说得像不优化说得对。消除不可能靠外部约束 RAG、引用校验、工具验证压到可控。

> **CodeWiki 的两层缓存**：
> 1. **本地 response cache**：`complete_with_cache` 通过 `input_payload` 的稳定 hash 命中已成功的 `llm_run`，命中后不再调 provider。
> 2. **Provider prefix cache**：请求 message 采用稳定前缀形状（system prompt + stable contract message + dynamic payload message），让 DeepSeek 等 OpenAI-compatible provider 复用 `prompt_cache_hit_tokens`。
>
> **prefix cache 原理**：Transformer 自回归解码，前缀 token 的 K/V 可复用免重算 prefill。不命中——前缀不完全匹配（system prompt 插入动态内容破坏公共前缀）、多副本路由到不同实例。最大化命中：固定 system prompt 放最前、动态内容放最后、批量请求共享 prompt、session affinity 路由。
>
> **批量执行配合 prefix cache**：Wiki page generation 先生成第一个 leaf page 预热前缀缓存，再并发生成后续；translation 同理。repair retry 把 errors 放动态 payload 不改稳定 contract 前缀。
>
> **semantic cache 失败模式**（线上事故风险）：
> - 语义近但意图/约束不同（「A 的价格」vs「B 的价格」embedding 极近）；
> - 时间敏感命中过期答案；
> - 否定句。
> **安全策略**：高相似度阈值 + 额外校验（entity/关键词匹配、时间戳新鲜度、显式 cache key 字段）、命中后小模型二次判等价、监控 hit rate vs 投诉率并 A/B。对确定性场景用 exact/prefix cache 更安全。

### Q58. ⚠️【安克】Cursor / Claude Code / Codex 这种 coding agent 怎么实现对代码文件编辑的？如果是你设计这个工具，会设计哪几个参数？

**【参考答案】**：
> 模型本身不直接碰文件，通过**工具调用（tool use）**实现：
> - agent 给模型暴露一组文件操作工具（read_file、write_file、edit_file/str_replace、create/delete/search grep/glob）。
> - 模型推理后输出**结构化的工具调用指令**（指定文件路径、操作类型、内容/范围），agent runtime 执行。
> - 关键：编辑多采用**基于锚点的局部替换**（old_string → new_string），而非整文件重写，减少 token、降低改错风险。
> - 执行后再读回文件验证，形成「读→改→验」循环。
>
> **如果设计这个工具，参数**：
> - **文件操作类**：file_path、operation（read/write/edit/delete/search）；
> - **编辑定位类**：old_string / new_string（锚点替换）或 line_range，edit 必须给精确定位；
> - **校验类**：dry_run（只预览不写）、verify_after（改完自动读回校验）；
> - **上下文类**：context_window（读文件带几行上下文）、max_bytes（防读超大文件）；
> - **安全类**：allow_overwrite、backup（改前是否备份）。
> 核心设计原则：**编辑要锚点定位而非整体重写、操作要可预览可回滚、读文件要限大小防爆 token**。

### Q59. ⚠️【安克】大模型写 SQL，多用户/多部门并发查询，数据权限怎么隔离？

**【参考答案】**（工程层硬隔离）：
> 权限不能交给模型（模型可能生成越权 SQL），要在**工程层硬隔离**：
> 1. **数据源级隔离**：每个用户/部门的查询连接的是**已做行级权限过滤的视图或库**，即使模型生成「查全表」的 SQL，数据库层也只返回有权限的行。
> 2. **Schema 范围隔离**：给模型注入的表 schema 本身就按权限过滤——A 部门用户只能看到 A 部门相关的表/字段描述，模型根本不知道 B 部门的表存在。
> 3. **审计**：所有生成 SQL + 执行结果落审计日志，可追溯谁查了什么。
> 原则：**模型不可信，权限必须在它之下的数据库/工程层兜死**。这和「只读账号拦截 DROP」是同一套防御思路。

**【口语化回答】**：

> 权限不能交给模型，模型可能生成越权 SQL，要在工程层硬隔离。
>
> 第一，数据源级隔离，每个用户部门的查询连接的是已做行级权限过滤的视图或库，即使模型生成查全表的 SQL 数据库层也只返回有权限的行。第二，Schema 范围隔离，给模型注入的表 schema 本身就按权限过滤，A 部门用户只能看到 A 部门相关的表字段描述，模型根本不知道 B 部门的表存在。第三，审计，所有生成 SQL 加执行结果落审计日志可追溯谁查了什么。

### Q64. 【卓誉·HR】多需求都紧急、人力不够、有 DELAY 风险，怎么处理？

### Q65. 【卓誉·HR】与同事技术文档分歧大，怎么推进达成共识？

### Q67. 从 LLM → workflow → Claude Code 这些工具，谈谈发展趋势？下一个风口？

**【参考答案】**：
> **演进线**：**单次推理 → 编排 → 自主智能体**，每层把更多「人的判断」交给工程框架。
> 1. LLM 层：单次 prompt-response，无状态无工具无记忆。
> 2. Workflow 层：多 LLM 调用 + 工具 + 规则编排成确定性流程，人定义流程模型填空。
> 3. Agent 层：把「决定下一步做什么」也交给模型，harness 提供工具协议/上下文/状态。
> 4. 平台化：agent + 记忆 + 知识库 + 评测 + 权限打包服务团队。
>
> **趋势**：①从模型为中心转向工程框架为中心（差异化在 harness/记忆/工具/上下文管理）；②从给人看的代码转向给 AI 看的表示；③记忆与长期上下文成核心；④评测与可信（SWE-bench）。
>
> **下一个风口**（带不确定性）：
> 1. 长上下文 + 持久记忆原生支持（hot/cold 分离）；
> 2. 多模态 agent（视觉/操作/语音，coding agent 看截图调试）；
> 3. Agent 协议标准化（MCP 之于 agent 如 HTTP 之于 web）；
> 4. 从「生成代码」到「维护系统」（长期维护 codebase，需记忆和图谱）；
> 5. 小模型 + 强框架（够用小模型 + 精强工程框架完成大部分任务）；
> 6. 可验证性（输出能被自动验证）。
> 自己押注：**记忆治理 + 上下文工程**（模型同质化后这层是差异化）。

**【口语化回答】**：

> 演进线是单次推理到编排到自主智能体，每层把更多人的判断交给工程框架。LLM 层是单次 prompt response 无状态无工具无记忆。Workflow 层是多 LLM 调用加工具加规则编排成确定性流程人定义流程模型填空。Agent 层是把决定下一步做什么也交给模型 harness 提供工具协议上下文状态。平台化是 agent 加记忆加知识库加评测加权限打包服务团队。
>
> 趋势是从模型为中心转向工程框架为中心差异化在 harness 记忆工具上下文管理，从给人看的代码转向给 AI 看的表示，记忆与长期上下文成核心，评测与可信 SWE-bench。
>
> 下一个风口带不确定性说：长上下文加持久记忆原生支持 hot cold 分离；多模态 agent 视觉操作语音 coding agent 看截图调试；Agent 协议标准化 MCP 之于 agent 如 HTTP 之于 web；从生成代码到维护系统长期维护 codebase 需记忆和图谱；小模型加强框架够用小模型加精强工程框架完成大部分任务；可验证性输出能被自动验证。自己押注是记忆治理加上下文工程，模型同质化后这层是差异化。

## 最后：面试官思维的关键原则（贯穿全场）

1. **数字与叙述分离**——模型负责表达，确定性逻辑负责准确。不让模型算数、不让模型编原因、不让模型直接打生产。
2. **不信任模型，工程层兜底**——权限隔离、SQL 预校验、source refs 硬约束、citation 校验、Mermaid 服务端生成。
3. **确定性优先**——能由 AST/SQL/规则得出的不用模型猜。代码调用关系是确定性的，该用 AST 而非模型总结。
4. **失败可恢复**——L0 原文不丢、offload 留索引、压缩可回滚、backup 支持回滚。热路径有损冷路径可还原。
5. **诚实边界**——不夸大（GraphRAG 不全面碾压）、不硬编数据（没数据说「正在建评测集」）、不假装全知（CoCo 没看就说没看）。
6. **回答具体**——任何流程题落到「第 1 步做什么、输入是什么、输出是什么」，不「分析一下、排查一下」。

把握这六条原则，三小时面试里任何追问都能接住。祝面试顺利。
