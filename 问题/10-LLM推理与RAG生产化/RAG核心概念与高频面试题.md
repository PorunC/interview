# RAG 核心概念与高频面试题

> 资料口径：本文根据 JavaGuide `ai/rag` 目录下 6 篇核心文章二次整理，于 2026-07-27 获取和核对。不是上游原文的逐字转载，而是面向面试复习的概念表和第一人称口语化答案。项目经历、数据量、效果指标和线上架构只能按真实情况补充，不得把文献或示例参数说成自己的生产结果。

## 一、核心概念速查

### 1. RAG 的定位

RAG（Retrieval-Augmented Generation，检索增强生成）在生成之前从外部知识源检索证据，再将“问题 + 证据 + 指令”交给 LLM。它主要解决知识过时、私有数据接入、证据溯源和部分幻觉问题，但不会天然消除幻觉。

```text
离线：数据源 -> 解析/清洗 -> Chunk -> Metadata -> Embedding -> 向量/全文/图索引
在线：Query -> 理解/改写 -> 权限预过滤 -> 多路召回 -> 融合/去重 -> Rerank -> 上下文构建 -> 生成/引用/拒答
闭环：失败样本 -> 分层评测 -> 定位 -> 改动 -> 回放 -> 灰度 -> 监控
```

### 2. 六个核心层次

| 层次 | 核心对象 | 主要取舍 | 典型问题 |
| --- | --- | --- | --- |
| 文档处理 | 解析、清洗、结构、表格、OCR | 解析成本 vs. 证据完整性 | 多栏 PDF 乱序、表格列错位、页眉污染 |
| Chunk | 子块、父块、重叠、章节边界 | 召回粒度 vs. 上下文完整性 | 太小丢语义，太大引入噪声 |
| 表示与索引 | Embedding、BM25、HNSW、IVFFLAT | 质量、延迟、存储、更新与运维成本 | 模型/距离度量不匹配，参数选择不合理 |
| 召回与重排 | Query Rewrite、Hybrid Search、RRF、Rerank | Recall vs. Precision，质量 vs. 延迟 | 正确证据未进候选池或排名太后 |
| 生成与评测 | 压缩、排序、引用、拒答、回归集 | 答案完整性 vs. 证据边界 | 证据正确但模型未使用，或引用错配 |
| 更新与治理 | 版本、幂等、删除、ACL、灰度、回滚 | 新鲜度 vs. 一致性与可用性 | 旧版本残留、模型混用、权限滞后、部分成功 |

### 3. 关键方法对照

| 方法 | 适合什么 | 不擅长什么 |
| --- | --- | --- |
| BM25/全文检索 | 错误码、SKU、人名、版本号、精确词 | 同义改写和深层语义 |
| 向量检索 | 同义表达、概念问答、语义相似 | 精确编号、强布尔条件、多跳关系 |
| Hybrid Search | 同时存在语义问题和精确词的生产知识库 | 无法修复原始数据错误和切分丢失 |
| Rerank | 对粗召回候选做 query-document 精排 | 候选池里没有正确证据时无能为力 |
| Parent-Child Chunk | 小块精准召回，大块补足语境 | 会增加存储和关联查询成本 |
| GraphRAG | 实体关系、多跳推理、跨文档归纳、全局主题 | 简单局部问答；建图和更新成本较高 |

### 4. 向量索引算法速查

| 算法 | 核心思路 | 优势 | 代价/适用边界 |
| --- | --- | --- | --- |
| Flat/ENN | 对全部向量做精确比较 | 结果精确，可作召回基准 | 数据大时延迟高，适合小数据或离线评测 |
| HNSW | 在分层小世界图上导航 | 通常具有较好的高召回和低延迟 | 建索引慢，内存/存储开销高，关注删改维护 |
| IVFFLAT | 先聚类，查询时只扫部分倒排单元 | 索引相对简单，存储和构建成本较低 | 对训练数据、列表数和 probes 敏感 |
| IVF-PQ | 倒排候选加乘积量化压缩 | 适合超大规模且内存受限的场景 | 量化会带来额外召回损失，调优更复杂 |

### 5. 核心评测指标

| 层次 | 指标示例 | 要回答的问题 |
| --- | --- | --- |
| 检索 | Recall@K、Hit Rate@K、Precision@K、MRR、NDCG | 正确证据是否进入候选池，排名是否足够靠前？ |
| 上下文 | Context Recall、Context Precision、去重率、有效 Token 占比 | 进入 Prompt 的证据是否少而准？ |
| 生成 | Faithfulness、Answer Correctness、Answer Relevancy、Citation Accuracy | 回答是否正确、相关、忠于证据且引用匹配？ |
| 安全/拒答 | ACL 泄漏率、无答案集的拒答准确率 | 无权或无证据时是否能停下？ |
| 工程 | P95/P99 延迟、成功率、单请求 Token/费用、索引新鲜度 | 质量改善是否以可接受的成本实现？ |

## 二、RAG 基础与架构（Q001-Q009）

### Q001. 什么是 RAG？

**口语化回答：**

> 我会把 RAG 概括成“先找证据，再基于证据生成”。系统先从企业文档、数据库或其他外部知识源中找到与问题相关的片段，再将原问题、检索证据和回答约束一起交给 LLM。它的价值不是让模型无条件地更聪明，而是让答案更新、可引用、可审计。

**追问要点：** RAG 仍会因检索错误、噪声上下文、引用错配或模型不遵循证据而出错。

### Q002. 为什么需要 RAG？

**口语化回答：**

> 我认为核心原因是，预训练模型有知识截止时间，也天然访问不到企业私有数据。RAG 把知识留在可更新、可授权的外部系统里，请求时只取必要证据。这样可以降低知识更新成本，给回答提供引用和权限边界，并降低纯凭参数记忆作答时的幻觉风险。

**容易踩坑：** “降低幻觉”不等于“消除幻觉”，私有数据接入也不等于天然安全。

### Q003. RAG 的完整工作流程是什么？

**口语化回答：**

> 我会分成离线索引和在线问答两段。离线阶段做文档校验、解析、清洗、切分、元数据标注、Embedding 和建索引。在线阶段先理解或改写 Query，带着租户、权限、版本等条件做多路召回，再融合、去重、重排和压缩上下文，最后让 LLM 基于证据生成、引用或拒答。生产系统还要有反馈、评测和更新闭环。

**追问要点：** 检索只是一环，数据处理、权限、生成和更新都可能决定最终质量。

### Q004. 传统搜索和 RAG 有什么区别？

**口语化回答：**

> 我会先区分产物：传统搜索主要返回排好序的文档列表，用户自己点开阅读；RAG 会把多个检索片段交给 LLM，直接给出归纳、对比或结论。搜索链路短、延迟和成本低、可控性强；RAG 可读性更好，但多了生成偏差、Token 成本、延迟和引用校验。我在实际系统中会保留两个入口：找原文走搜索，需要读完材料再回答时走 RAG。

### Q005. RAG 和微调怎么选？

**口语化回答：**

> 我会先看问题是“模型不知道什么”，还是“模型不会按我的方式做”。知识变化快、属于私域、需要引用时优先 RAG；需要固定风格、格式、领域表达或任务行为时考虑微调。两者可以组合：微调稳定行为，RAG 提供实时且可溯源的知识。但组合也意味着两套系统的评测和版本成本。

### Q006. 长上下文会取代 RAG 吗？

**口语化回答：**

> 我的判断是不会完全取代。长上下文适合少量长文档的完整分析，但不适合每次都加载海量企业知识。上下文越长，输入成本、TTFT 和噪声通常越高，还会有 Lost in the Middle。RAG 能在检索阶段做权限和版本过滤，并给出精确引用。实际更常见的是组合：RAG 筛证据，长上下文用于读取筛选后的完整材料。

### Q007. Naive RAG、Advanced RAG 和 Modular RAG 有什么区别？

**口语化回答：**

> 我会按链路复杂度区分：Naive RAG 是“切块、Embedding、Top-K、生成”的最小链路，适合验证可行性。Advanced RAG 会加 Query Rewrite、混合召回、Rerank 和上下文压缩，重点解决召回和噪声。Modular RAG 则把检索器、重排器、压缩器、路由器和生成器做成可组合模块，按问题类型选择链路。演进不是功能越多越好，而是评测证明哪个环节值得增加。

### Q008. 什么场景适合 RAG，什么场景不适合？

**口语化回答：**

> 我会在答案依赖外部材料，且材料长、变化快或需要引用时优先 RAG，例如客服、制度库、研发文档和合规问答。如果用户只是找文件或精确字段，传统搜索或 SQL 更直接。如果答案主要来自模型的通识、没有可靠知识源，或延迟和成本极端敏感，也不应该为了技术形式强上 RAG。

### Q009. RAG 的核心优势和局限是什么？

**口语化回答：**

> 我认为它的优势是知识可快速更新，可以接入私有数据、按 ACL 过滤、附引用并与模型版本解耦。局限是检索质量决定上限，上下文噪声会影响生成，完整链路会增加延迟、Token 和运维成本。它还需要持续处理更新、删除、权限、引用和评测，所以 Demo 跑通不等于生产可用。

## 三、文档处理与 Chunking（Q010-Q017）

### Q010. 文档从上传到入库要经过哪些环节？

**口语化回答：**

> 我会按上传校验、MIME/编码识别、布局解析、清洗去噪、结构化、Chunking、Metadata 标注、分层质检、Embedding 和多索引写入来设计。质量校验不能只放在最后，解析和切分完成后就要抽样检查，避免把乱序 PDF、错位表格或 OCR 错误大批量写入索引。

**容易踩坑：** 只换 Embedding 模型，但没检查输入文档是否已被解析错。

### Q011. Chunk 切大还是切小？

**口语化回答：**

> 没有通用答案。小块粒度精准，但容易把条件、结论和上下文切开；大块保留完整语境，但可能因一句相关而带入大量噪声。我会先按业务语义单元切，再将几组块大小、重叠和父子方案建成对照索引，用同一评测集比较召回、精度、答案正确率、平均 Token 和延迟。

### Q012. 固定、递归、语义和结构切分怎么选？

**口语化回答：**

> 我会把固定 Token 切分作为实现简单、行为稳定的基线；递归切分按章节、段落、句子逐层拆分，适合技术文档和产品手册；语义切分按语义边界分组，但要防止超小块且建库成本更高；结构切分直接利用 Markdown 标题、法规条款、代码函数或表格行，如果原文有稳定的业务边界，它通常比纯语义聚类更可控。

### Q013. Parent-Child Chunk 和 Overlap 分别解决什么？

**口语化回答：**

> 我会用 Parent-Child 让小子块负责精准召回，命中后取回对应的大父块给模型，解决召回粒度和语境完整性的矛盾。我会用 Overlap 让相邻块共享一小段边界内容，减少语义被硬切开。重叠不是越多越好，过大会造成重复向量、检索噪声和 Token 浪费；父子方案也会增加存储与一次关联查询。

### Q014. 什么是语义丢失，怎么缓解？

**口语化回答：**

> 语义丢失是指文档经过解析、清洗和切分后，原来的上下文依赖被破坏了，例如条件和例外分在两块、只留“过去三年”却丢了主体、表格列关系消失。我会优先按结构边界切、保留 `section_path` 和父子关系，再考虑 Overlap、Chunk 摘要、假设问题、Parent-Child，对少量高价值长文档再评估 Late/Contextual Chunking。

### Q015. PDF、Word、Excel 和扫描件的结构丢失怎么处理？

**口语化回答：**

> 我不会把它们都当纯文本。多栏 PDF 用布局感知解析恢复阅读顺序、页码和表格；Word 保留标题样式并重建章节树；Excel 按行、数据区或表头-字段对转成结构化记录；扫描件走 OCR，对编号和数值密集文档做交叉校验和一致性检查。关键文档解析结果差异过大时应降级或转人工，不能静默入库。

### Q016. 多模态内容怎么进入 RAG？

**口语化回答：**

> 我会按内容类型分路处理。图片可用 OCR 提文字、用多模态模型生成可检索描述，或用多模态 Embedding 直接索引；表格要保留表头、行列和单位，必要时转 JSON 或 Markdown；图表除了视觉描述，还要保留 Caption、所在章节和原始文件。检索时可用摘要向量找到对象，生成时再取原图、原表或高保真结构。

### Q017. 文档处理如何做分层质检和降级？

**口语化回答：**

> 我会做三层校验：先检查格式、MIME、大小和安全性；再检查解析后的页数、文字量、乱码率、标题/表格结构；最后检查 Chunk 的长度分布、超小块、超限块、重复率和 Metadata 完整性。永久性错误直接拒绝或人工审核，瞬时错误可重试，低质量文档可降级到纯文本搜索或标记低置信度，而不是和正常证据混在一起。

## 四、Embedding、向量索引与数据库（Q018-Q025）

### Q018. Embedding 是什么，怎么选模型？

**口语化回答：**

> Embedding 把文本映射到高维稠密向量空间，让语义相近的文本距离更近。选模型时我会看业务语言、领域术语、输入长度、向量维度、延迟、成本、私有化要求和数据是否能出域。公开榜单只用于缩小候选，最终要用自己的 query-document 金标评测 Recall、MRR、延迟和索引成本。

### Q019. 余弦相似度、内积和 L2 距离怎么选？

**口语化回答：**

> 我会先区分度量语义：余弦看向量方向，对长度不敏感；内积保留向量幅度影响，向量做过 L2 归一化时，它和余弦在排序上通常等价；L2 是空间中的绝对距离，对幅度更敏感。工程上不是凭习惯选，而是遵循 Embedding 模型的训练和推荐度量，并保证建索引和查询时使用同一度量。

### Q020. RAG 为什么需要向量数据库？

**口语化回答：**

> 我的判断是，RAG 不一定需要“专用向量数据库”，但需要一个能高效存储、过滤和查询高维向量的索引系统。向量数据库通常将 ANN、Metadata Filter、持久化、分布式扩展和更新维护整合起来。数量小可用 Faiss 或内存索引，已有 PostgreSQL 且规模中等可用 pgvector，搜索为主可用 Elasticsearch/OpenSearch，数据量、吞吐和多租户较高时再评估专用系统。

### Q021. ENN 和 ANN 有什么区别？

**口语化回答：**

> ENN 会与所有向量比较，结果准确，但数据量大时延迟和计算成本过高。ANN 用索引结构只搜索有希望的一部分候选，用少量召回损失换更低延迟和更高吞吐。我会用精确搜索在抽样数据上作为召回上限和基准，再调 ANN 的建索引和查询参数，比较 Recall@K、P95 延迟、内存和更新成本。

### Q022. HNSW 和 IVFFLAT 有什么区别？

**口语化回答：**

> 我会这样区分：HNSW 构建分层小世界图，查询时逐层导航，通常有较好的召回-延迟平衡，但建索引慢、内存和存储开销较高，高频删改还要关注产品的维护机制。IVFFLAT 先把向量聚类到多个倒排单元，查询时只探测一部分中心，索引相对简单、存储低，但对训练数据、列表数和 probes 更敏感。选择要看数据规模、更新模式、内存和 SLA，不能只背“HNSW 更快”。

**追问要点：** HNSW 的 `ef_search` 和 IVF 的 `probes/nprobe` 通常越大召回越好，但查询计算和延迟也越高；参数必须在真实数据的召回-延迟曲线上选。项目里使用了哪种索引只能按真实配置回答。

### Q023. 向量数据库怎么选型？

**口语化回答：**

> 我会先把条件量化：向量数量和维度、QPS 与 P95/P99、更新/删除频率、Metadata 过滤复杂度、混合检索、多租户、备份恢复、云或内网部署、团队运维能力和总成本。然后用真实数据和过滤条件压测召回、延迟、吞吐、索引构建时间和更新抖动。不会只因为某个产品“专用”就选它。

### Q024. 什么时候选 PostgreSQL + pgvector？

**口语化回答：**

> 当业务已经使用 PostgreSQL，向量规模和并发中等，需要把向量、文本、Metadata 和关系数据放在同一个事务与运维体系里时，pgvector 是很实用的选择。它的优势是 SQL、过滤、备份、权限和现有技术栈整合。如果是超大规模、极高吞吐、独立扩容或复杂分布式多租户，我会再比较专用向量系统。

### Q025. 向量检索、关键词检索和混合检索怎么选？

**口语化回答：**

> 我会按 Query 类型选：语义改写和概念问题适合向量检索；错误码、SKU、版本号和专有名词适合 BM25 或精确过滤；企业知识库往往两类 Query 都有，所以混合召回通常更稳。常见链路是向量和 BM25 并行召回，用 RRF 按名次融合，再去重和 Rerank。如果数据高度结构化，也可以路由到 SQL 或图查询，不必所有问题都走向量。

## 五、检索、重排与评测（Q026-Q036）

### Q026. RAG 为什么还会幻觉？

**口语化回答：**

> RAG 只是增加证据来源，没有保证证据或生成一定正确。文档可能解析错或过期，正确证据可能没召回或排名太后，上下文可能混入冲突版本，模型也可能忽略证据、错做归纳或伪造引用。我会分层记录候选、重排、最终上下文和引用，并加入证据冲突检查、引用校验和低置信度拒答。

### Q027. Hybrid Search 和 RRF 是什么？

**口语化回答：**

> 我会把 Hybrid Search 解释为向量语义召回与 BM25/稀疏检索精确词召回的组合。两路原始分数不在同一标尺上，RRF 不强行比分数，而是按候选在各路列表的名次累加分数，对分数校准的依赖较小。融合后还要按文档、Chunk 和版本去重，再进入精排。

### Q028. Query Rewrite 有哪些方法，风险是什么？

**口语化回答：**

> 我会按目标选改写：规范化改写把口语和缩写变成可检索表达；Multi-Query 用多个同义视角召回；Decomposition 拆解多子问题；Step-back 先找上位概念；HyDE 先生成假设答案再用其向量检索；Self-Query 从问题提取年份、产品等结构化过滤。最大风险是改写偏离意图，所以原 Query 要保留并参与召回或审计，不能让一次 LLM 改写成为唯一真相。

### Q029. Top-K 是不是越大越好？

**口语化回答：**

> 不是。增大 Top-K 可能提高粗召回，但会同时增加重排延迟、Prompt Token 和上下文噪声。我会分三层管理：粗召回保留较大候选池，Rerank 后只留更少的 Top-N，最终进上下文的数量更少。具体值按问题类型、Chunk 大小、上下文预算和评测结果定，不用一个魔法数字管到底。

### Q030. Rerank 的作用是什么，为什么不直接用向量分数？

**口语化回答：**

> 我会把两个阶段分开：向量检索将 query 和 document 分开编码，适合大规模粗召回，但不一定能判断候选是否真正回答了某个条件。Reranker 将 query 和候选文本联合打分，能做更细的交互建模，用于把“看起来相关”重排为“能支持回答”。它应放在较小的候选池上，否则质量增益可能抵不过延迟和费用。

### Q031. 专用 Reranker 和 LLM Rerank 怎么选？

**口语化回答：**

> Cross-Encoder 或专用 Reranker 通常延迟更稳定、成本更低，适合高频在线排序；LLM Rerank 能理解复杂条件、输出理由或同时做去冲突，但更慢、更贵且稳定性更难控。我会用专用模型做默认精排，只对低频、高价值、需要复杂逻辑判断的问题评估 LLM，并用相同金标同时比较质量、P95 和费用。

### Q032. 上下文压缩和排序为什么会影响答案？

**口语化回答：**

> 我会先处理 Rerank 后仍然重复、过长或带无关部分的候选。上下文压缩要保留能支持答案的原文和必要条件，删掉导航、重复和无关句；高风险场景不应该只留不可溯源的生成摘要。排序时要考虑 Lost in the Middle，可把最强证据放在容易被模型利用的位置，同时保留章节、版本和引用 ID。

### Q033. 怎么让模型严格基于证据回答？

**口语化回答：**

> 我会在 Prompt 中明确证据边界，要求每个可验证事实关联引用 ID，证据不足、过期或互相冲突时输出拒答或请求澄清。输出后再做引用存在性、用户权限、句子-证据支持和版本校验。Prompt 只是一层约束，不能替代确定性验证、检索阈值和拒答策略。

### Q034. RAG 应该如何评测？

**口语化回答：**

> 我会把检索和生成分开。检索看 Recall@K 或 Hit Rate@K、Precision@K、MRR 和 NDCG，判断正确证据是否进来且排名靠前；上下文看 Context Recall/Precision 和有效 Token；生成看 Faithfulness、答案正确性、相关性和引用准确性；业务层再看任务成功、用户反馈、拒答、延迟和成本。评测集至少覆盖高频、失败、精确匹配、多跳、时间/版本、权限和无答案问题。

### Q035. RAG 效果差时怎么系统排查？

**口语化回答：**

> 我先将失败样本分为未入库或解析错、正确证据未进粗召回、已召回但排名靠后、进了上下文但模型未使用、理解错、引用错和应拒未拒。如果粗召回候选池里没有正确证据，查数据、Chunk、Metadata、Query Rewrite 和召回通道；候选里有但未进上下文，查融合、去重、Rerank 和预算；证据正确但答案错，再查 Prompt、模型、证据冲突和引用。

### Q036. 怎么建立可信的 RAG 优化闭环？

**口语化回答：**

> 我会固定一套可版本化的问题、金标证据和预期答案，对文档解析器、Chunk 策略、Embedding、召回参数、Reranker、Prompt 和模型分别记版本。每次只做可归因的变更，用同一数据集回放，联合比较质量、延迟和成本，然后小流量灰度。线上失败样本经过人工审核后回流到评测集，但要保留独立 Holdout，防止只对已知 badcase 过拟合。

## 六、GraphRAG（Q037-Q042）

### Q037. 什么是 GraphRAG？

**口语化回答：**

> 我把 GraphRAG 理解为：在文本检索之外，将文档中的实体、关系和主题结构显式建模成图。查询时不只找相似 Chunk，还可以找节点、边、路径、社区摘要和对应原文。关键不是是否用了图数据库，而是检索对象和问题求解方式从“文本相似”扩展到“关系与全局结构”。

### Q038. 传统向量 RAG 为什么不擅长多跳和全局问题？

**口语化回答：**

> 我认为根因是，向量 RAG 将文档切成彼此独立的 Chunk，它擅长找“哪段话和问题像”，但不天然知道几段话是否属于同一个业务对象，也不知道它们之间是依赖、影响还是因果。多跳问题需要沿“系统 -> 负责人 -> 事故 -> 链路”类似关系找证据，全局问题需要对整个语料聚合主题，单纯增大 Top-K 只会同时放大噪声和成本。

### Q039. GraphRAG 的核心概念有哪些？

**口语化回答：**

> 我会从四类对象讲：节点表示系统、人、组织、事件或条款等实体；边表示依赖、负责、影响、导致等关系；属性保留时间、版本、置信度、ACL 和来源。实体消歧用于合并别名和重复节点，社区发现用于将关系密集的节点聚成主题群，社区摘要帮助回答跨语料的全局问题。每个实体和关系都应保留原文 span 作为证据。

### Q040. GraphRAG 的 Local Search 和 Global Search 有什么区别？

**口语化回答：**

> 我会按问题范围区分：Local Search 从一个明确实体出发，沿邻居和关系路径扩展，同时回取关联原文，适合“订单中心依赖哪些服务”这类实体问题。Global Search 从社区或主题摘要出发，对多个主题的局部结论再汇总，适合“这批报告的共性风险是什么”。成熟系统会先做 Query Routing，简单事实仍用向量或全文检索，而不是全部走图。

### Q041. 什么时候应该用 GraphRAG，什么时候不用？

**口语化回答：**

> 我会先做好向量 + BM25 + Rerank 基线，再分析 badcase。如果失败集中在实体关系、上下游路径、多跳推理、跨文档冲突或全局主题，GraphRAG 才有明确价值。如果主要是 FAQ、单文档事实和数据量较小，传统 RAG 更快、更便宜也更稳。GraphRAG 的代价包括实体消歧、关系抽取、社区摘要、增量更新、图级权限和更复杂的评测。

### Q042. 你会如何分阶段落地 GraphRAG？

**口语化回答：**

> 我会分阶段降低风险：第一阶段建立可测的传统 RAG 基线；第二阶段标注关系型失败样本；第三阶段只抽取少量高价值实体和强类型关系，每条边保留来源和置信度；第四阶段为明确实体问题加局部图检索和原文补证；只有全局问题的评测收益能覆盖成本时，才加社区发现和全局检索。最后由路由器在全文、向量、SQL 和图检索间选链路。

## 七、知识库更新与治理（Q043-Q050）

### Q043. 为什么索引和查询必须使用兼容的 Embedding 模型？

**口语化回答：**

> 不同 Embedding 模型的向量空间不兼容。维度不同时向量库通常会直接拒绝；即使维度相同，不同模型的坐标语义也不同，相似度排名没有可信基础。所以我会将模型名、版本、维度、归一化和距离度量绑定到索引版本。升级时建新索引全量重编码，双读评测和灰度，不在原索引里混写新老向量。

### Q044. 支持增量更新的 Metadata 至少有哪些？

**口语化回答：**

> 我会保留 `doc_id`、`chunk_id`、`source_id`、`content_hash`、`version_id/revision`、`is_deleted`、创建/更新时间、标题和 `section_path`、`tenant_id/acl`、解析器与 Chunk 策略版本、Embedding 模型/版本/维度，以及各索引的写入状态。`content_hash` 用来跳过未变内容，`revision` 用来拒绝乱序旧事件，策略和模型版本决定是否必须全量重建。Metadata 既是过滤约束，也是审计和回滚证据。

### Q045. 文档新增、修改和删除怎么同步？

**口语化回答：**

> 我会按变更类型处理：新增要解析、切分、算哈希，然后幂等写入元数据、向量和全文索引。修改要按 `doc_id` 找到旧版本，只有内容未变时才跳过；重新切分后 Chunk ID 可能变化，所以不能只 upsert 新主键，还要隔离或清理旧版本。删除先标记软删除并立即停止检索，再延迟清理向量库、全文索引、元数据和旁路缓存。三类操作都要有审计事件和 reconciliation。

### Q046. 增量更新和全量重建怎么选？

**口语化回答：**

> 我会用增量处理日常文档增删改，事件驱动保时效，定时对账防漏更。Embedding 模型、向量维度、解析器语义、Chunk 策略或核心 Metadata Schema 改变时通常要全量重建，严重不一致或索引退化也可触发重建。稳态方案是实时增量 + 周期性对账/健康重建 + 策略升级时的紧急重建，而不是二选一。

### Q047. 全量重建怎么做到不停服和可回滚？

**口语化回答：**

> 我会用蓝绿索引或索引别名。在线查询继续读旧索引，后台基于一致的源数据快照构建新索引；构建期间的增量变更要按 revision 双写或回放到新索引。新索引通过完整性、ACL、召回、答案、延迟和灰度验证后原子切别名。旧索引保留一个回滚窗口，而不是切换后立即删除。

### Q048. 如何处理重复事件、乱序和部分成功？

**口语化回答：**

> 我会用 `doc_id + version/content_hash` 的确定性主键或唯一约束幂等处理重复事件，不依赖“先查再写”。同一 `doc_id` 尽量固定消息分区，事件携带单调 `revision`，旧事件拒绝或记审计。元数据库、向量库和全文索引不在同一事务里，所以用元数据库记 source of truth 和每个 sink 的状态，outbox 发事件，补偿任务重试，reconciliation 修复差异。

### Q049. 知识库更新最常见的坑有哪些？

**口语化回答：**

> 我重点防六类问题：修改时只写新向量却不清旧版；索引和查询混用 Embedding 模型；Chunk 策略改了但历史数据不重建；删除只传播到某一个索引；ACL 已收紧但检索元数据和缓存未失效；Webhook/CDC 漏事件却没有定期对账。这些问题的共性是系统外观仍可用，但会静默地返回过期或越权证据，所以要主动对账而不能只看错误率。

### Q050. 知识库更新链路应该监控什么？

**口语化回答：**

> 我会监控源系统到事件入队延迟、队列到索引完成延迟、索引成功率、重试和 DLQ 积压、部分成功数、陈旧文档数、源/元数据/向量/全文数量差异、ACL 不一致、删除传播滞后，还要监控更新后的 Hit Rate、引用准确性、负反馈和延迟是否回归。每次操作记录 `doc_id`、变更类型、revision、操作者、结果和错误阶段，阈值根据业务新鲜度 SLO 和历史基线设定，不直接照搬示例数字。

## 八、面试前最小自检清单

1. 能在 60 秒内说清离线索引、在线检索生成和评测更新闭环。
2. 能说清 Chunk 大小、Overlap、Parent-Child 的取舍，而不是只报一个 Token 数。
3. 能用错误码/SKU 和同义改写两类例子解释 BM25 与向量的互补。
4. 能区分“没召回”“没排上来”“没进上下文”“进了但没用对”四类问题。
5. 能说清检索、上下文、生成、拒答和工程指标的分层评测。
6. 能说清 GraphRAG 的检索对象、Local/Global Search 和不该使用它的场景。
7. 能说清为什么 Embedding 升级和 Chunk 策略变更要全量重建。
8. 能说清新增、修改、删除如何跨元数据库、向量库、全文索引和缓存传播。
9. 能用双索引、别名切换、增量追平和回滚窗口解释不停服重建。
10. 所有项目数据量、参数、模型、部署、人力和收益都能说出真实证据与适用边界。
