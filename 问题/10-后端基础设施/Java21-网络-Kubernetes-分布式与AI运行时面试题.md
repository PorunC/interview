# Java 21、网络、Kubernetes、分布式与 AI 运行时面试题

> 定位：补齐 Java 后端与 AI 应用岗位经常继续追问、但现有 Java 120 题没有展开的生产基础设施能力。本文中的项目连接严格区分两类口径：能从当前材料确认的实现直接说“当前已实现”；Virtual Threads、WebFlux、Kubernetes 集群、数据库分片、可恢复 SSE、分布式 Agent Runtime 等没有现成证据的能力，只作为迁移或下一版设计回答，不能包装成线上经验。
>
> 回答顺序统一为“先给结论，再讲机制，然后说坑，最后连回项目”。面试现场不需要逐字背诵，但必须保留边界、取舍和故障语义。

## 1. Java 21、Virtual Threads 与 WebFlux

### Q001：Virtual Thread 到底解决什么问题？它会让程序自动变快吗？

> **口语化回答：** 我会先说，Virtual Thread 解决的是“阻塞式并发的线程成本”，不是让一段 CPU 计算自动变快。传统平台线程通常对应一个比较重的操作系统线程，高并发 I/O 场景会被线程栈、调度和上下文切换成本卡住；虚拟线程由 JVM 管理，等待网络或数据库时可以让出 Carrier Thread，所以可以继续用一请求一线程这种直观写法承载更多并发。但数据库连接、模型 Provider 配额和 CPU 都没有凭空增加，真正的吞吐上限仍然由最稀缺的下游决定。
>
> **原理追问：** Virtual Thread 是 Java Thread 的轻量实现，通常由 JVM 调度到少量 Platform Thread，也就是 Carrier Thread 上执行。它适合等待占比高、任务彼此独立的阻塞 I/O；CPU 密集型任务仍受核心数限制。判断收益要同时看吞吐、P95/P99、Carrier 利用率、数据库连接池和下游限额。
>
> **容易踩坑：** 把“能创建很多虚拟线程”理解成“可以无限并发”；在每个虚拟线程里做重 CPU 解析；为了追求新技术，把成熟异步链路无收益地重写；只看入口吞吐，不看数据库和模型服务已经被压垮。
>
> **项目连接：** 当前三个项目没有可证明的 Java 21 Virtual Thread 实现。我会把它作为以后把同步 Java 接入层迁移到高并发服务时的选项，并通过同负载压测和下游容量验证，而不会说当前项目已经靠它获得了性能提升。

### Q002：Virtual Thread、Platform Thread 和 Carrier Thread 是什么关系？什么叫 Pinning？

> **口语化回答：** 我会把三者分开讲：Platform Thread 是 JVM 对操作系统线程的传统映射；Virtual Thread 是轻量任务载体；Carrier Thread 是实际承载虚拟线程运行的平台线程。虚拟线程遇到大多数可感知的阻塞时，JVM 可以把它从 Carrier 上卸载，让 Carrier 去跑别的虚拟线程。Pinning 就是虚拟线程在阻塞期间没有卸载，Carrier 也一起被占住，虚拟线程的并发优势就会下降。
>
> **原理追问：** 长时间处于某些 synchronized 临界区、Native 或 Foreign Function 阻塞路径时，可能出现 Pinning。排查时我会用 JFR 的虚拟线程相关事件、线程转储和压测指标确认是否真的发生，而不是看到 synchronized 就要求全部改锁。核心是缩短“持有 Monitor 又做慢阻塞”的范围。
>
> **容易踩坑：** 把所有 synchronized 都说成一定 Pin；为了规避 Pinning 把正确的互斥逻辑删掉；只增加 Carrier 数量掩盖锁内慢 I/O；把普通锁竞争、下游变慢和 Pinning 混成一个问题。
>
> **项目连接：** 当前材料没有 Virtual Thread 或 Pinning 诊断记录。如果未来用 Java 21 承载 LLM Gateway，我会重点检查模型调用、数据库驱动和锁内日志/网络操作，并把 JFR 证据作为是否改造的依据。

### Q003：用了 Virtual Thread 以后，线程池、连接池和限流是不是都可以删掉？

> **口语化回答：** 不能。虚拟线程可以很多，但稀缺资源还是有限。我不会再为了复用“线程本身”建一个很小的固定池，但仍然会用 Semaphore、数据库连接池、Provider 并发配额和租户级限流控制真正昂贵的资源。比如模型只允许 100 个并发，我就算能启动十万个虚拟线程，也只能让受控数量进入远程调用，其余请求要有界等待、降级或拒绝。
>
> **原理追问：** 传统线程池经常同时承担“复用线程”和“限制并发”两个职责；Virtual Thread 降低了前者的必要性，但后者必须显式保留。容量设计要把入口并发、连接池、每请求扇出、超时和重试放在一起计算，避免隐藏队列。
>
> **容易踩坑：** 每个请求无界创建子任务；虚拟线程在连接池前无限排队导致内存和尾延迟上升；多层都重试，把 Provider 故障放大；把 CallerRuns 这类平台线程池经验机械套到虚拟线程。
>
> **项目连接：** 当前 CodeWiki 和 Agent Memory 都有外部模型、存储或宿主边界。若迁移到 Java Virtual Thread 服务，我会保留模型并发、Token 预算、数据库 Pool 和租户配额；这是迁移设计，不是当前实现。

### Q004：Virtual Thread 下 ThreadLocal、MDC 和取消机制要注意什么？

> **口语化回答：** ThreadLocal 的隔离语义还在，但我不会因为虚拟线程便宜就往每个线程塞很重的对象。Trace、租户和请求上下文要小、只读、可清理；数据库连接、Session 和大缓存不能长期挂在线程变量上。取消仍然是协作式的，interrupt 只是在通知任务停止，底层 HTTP、数据库或模型请求是否真停下来，还要看驱动和远端协议。
>
> **原理追问：** 海量虚拟线程会放大每线程状态的总内存成本。结构化传递只读上下文时可以评估 ScopedValue；并发子任务的生命周期可以用 Structured Concurrency 思路约束，但要说明所用 JDK 版本和 API 状态。无论使用什么 API，外部副作用都要靠 Deadline、幂等键和状态机收口。
>
> **容易踩坑：** 认为虚拟线程之间会自动继承正确租户；捕获中断后不恢复标记也不退出；请求取消就把远端状态记成失败；把事务 Session 放 ThreadLocal 后跨异步边界复用。
>
> **项目连接：** 当前项目没有采用 ScopedValue 或 Structured Concurrency 的证据。我会把现有 traceId、runId、tenantId 设计成显式上下文字段；未来迁移 Java 21 时再评估这些 API，而不是先把规划说成现状。

### Q005：Spring MVC 加 Virtual Threads 和 Spring WebFlux 应该怎么选？

> **口语化回答：** 我的选择不会只看哪个更新。现有依赖以 JDBC、阻塞式 SDK 为主，业务团队也更熟悉命令式代码时，我会优先评估 Spring MVC 加 Virtual Threads，改造成本低、调用栈直观。如果链路从入口到数据库和下游都能真正非阻塞，而且需要大量长连接、流式处理和背压，WebFlux 才更有价值。最差的组合是在 WebFlux Event Loop 里继续跑阻塞 JDBC 或同步模型 SDK，看起来 Reactive，实际把少量事件线程卡死。
>
> **原理追问：** MVC 默认是一请求一执行线程；WebFlux 基于 Reactive Streams 和少量 Event Loop；Virtual Thread 保留阻塞编程模型但降低线程等待成本。比较时要看依赖生态、调试难度、上下文传播、连接池、CPU 工作和团队维护能力，不只看压测峰值。
>
> **容易踩坑：** 把 WebFlux 等同于“天然更快”；为一个普通 CRUD 服务全量 Reactor 化；在 Reactive 链尾部到处 block；MVC 开启 Virtual Thread 后就取消所有并发隔离。
>
> **项目连接：** 当前 CodeWiki Web API 是 FastAPI，不是 Spring MVC 或 WebFlux；三个项目也没有 WebFlux 生产证据。面试中我会把这题作为 Java 化迁移选型回答，明确不是当前技术栈。

### Q006：Mono、Flux、Cold Publisher 和 Hot Publisher 分别是什么？

> **口语化回答：** 我会这样讲：Mono 表示零个或一个结果，Flux 表示零到多个结果，它们描述的是一条异步数据流，不代表创建后马上执行。Cold Publisher 通常每个订阅者都会从头触发一份独立数据源；Hot Publisher 则可能不等订阅者，后来的订阅者只能看到后续事件。选错语义会直接影响远程调用是否重复、流事件是否丢失。
>
> **原理追问：** Reactor 是惰性组装，真正订阅后才沿链路执行；map 处理同步转换，flatMap 处理异步 Publisher，并发和顺序语义不同。共享、缓存、重放操作会把订阅行为改变，必须定义事件是否允许重复和保留多久。
>
> **容易踩坑：** 对一个会扣费的 Cold Publisher 订阅两次，导致副作用重复；用 flatMap 后误以为仍严格有序；把 cache 当普通内存优化，忽略错误和敏感结果也被缓存；没人订阅却问为什么代码没执行。
>
> **项目连接：** 当前项目没有 Reactor 实现。若以后用 WebFlux 转发模型流，我会先定义 Provider 流是单次消费还是可重放，并把副作用调用放进幂等边界，不能靠 Publisher 类型自动保证可靠性。

### Q007：Reactive Streams 的 Backpressure 是什么？它等于接口限流吗？

> **口语化回答：** Backpressure 是下游告诉上游“我现在能处理多少”，避免生产速度长期高于消费速度后无限堆内存。它解决的是一条流内部的供需协调，不等于整个系统的业务限流。接口限流还要按用户、租户、Token、成本和 Provider 配额决定谁能进来；就算 Reactor 能按需请求，远端模型也未必支持真正暂停产出。
>
> **原理追问：** Reactive Streams 通过 request 数量表达需求；缓冲、丢弃、取最新或报错都是不同过载策略。跨网络边界时，TCP 流控、应用 Queue 和 Provider API 的取消能力也各不相同，所以要逐层确认背压能传播到哪里。
>
> **容易踩坑：** 使用无界 buffer 把问题延后到 OOM；把慢客户端拖住模型连接却不设上限；认为 onBackpressureDrop 可以用于任何业务事件；用背压代替租户公平和成本预算。
>
> **项目连接：** 当前 CodeWiki 的 Ask API 返回完整响应，不是可恢复的 Reactor 流；Pi 和通用题里有流式概念，但不等于 Java Reactive 已实现。迁移设计里我会同时做流内背压和入口配额。

### Q008：WebFlux 中遇到阻塞调用、超时、重试、取消和上下文传播怎么处理？

> **口语化回答：** 我会先定位阻塞边界。短期无法替换的同步 SDK，可以放到受控的 boundedElastic 调度器，但它只是隔离，不是把阻塞变成非阻塞；长期要换真正的 Reactive Client。超时要服从端到端 Deadline，重试只针对可重试且幂等的操作，并限制总尝试。客户端取消后，我会继续确认远端是否收到取消、Usage 怎么记、最终状态怎么落，不能直接当成什么都没发生。
>
> **原理追问：** subscribeOn 主要影响订阅和上游执行位置，publishOn 改变后续算子的执行线程；Reactor Context 用于跨异步边界传递少量上下文，比 ThreadLocal 更符合模型。Retry、timeout 和 circuit breaker 的组合顺序会改变行为，必须用集成测试确认。
>
> **容易踩坑：** 在 Event Loop 上调用 block；每层各重试三次；把 429、参数错误和权限错误都重试；MDC 在线程切换后丢失；取消只停止下游消费，远端仍持续计费。
>
> **项目连接：** 当前 CodeWiki 用 FastAPI 和异步 HTTP，不是 Reactor。这里可迁移的是 Deadline、错误分类、取消状态和 Trace Context 的工程原则，不会声称当前用过 WebFlux 运维这套链路。

## 2. TCP、TLS 与 HTTP

### Q009：TCP 为什么需要三次握手？两次为什么不够？

> **口语化回答：** 我会说三次握手的核心不是背一个流程，而是让双方确认双向收发能力，并同步各自的初始序列号。客户端发 SYN，服务端回 SYN+ACK，客户端再 ACK。只有两次时，服务端无法确认自己的响应和序列号已经被客户端收到，也更难排除网络里迟到的旧连接请求，可能白白分配连接状态。
>
> **原理追问：** 序列号用于字节流确认、重传和去重；握手还会协商 MSS、窗口扩大、SACK 等能力。SYN Flood 利用服务端半连接状态消耗资源，常见缓解包括 SYN Cookie、队列和边界限速，但应用仍要保护接受后的连接资源。
>
> **容易踩坑：** 把三次握手说成“因为三次比较安全”；认为 TCP 建连成功就代表 HTTP 服务健康；忽略代理、NAT 和负载均衡各自还有连接；只调大 backlog 不处理慢处理和攻击。
>
> **项目连接：** 当前项目没有自研 TCP 协议。这个知识主要用于解释模型 API 连接建立、网关连接池和网络故障，我不会包装成项目里的自研网络能力。

### Q010：TCP 为什么通常四次挥手？TIME_WAIT 有什么作用？

> **口语化回答：** TCP 是全双工，两边的发送方向可以分别关闭，所以一方发 FIN 后，另一方先 ACK，等自己的数据发完再发 FIN，最后由前一方 ACK，常见就是四步。TIME_WAIT 主要做两件事：确保最后一个 ACK 丢失时还能重发；让旧连接的迟到报文在网络里消失，避免污染同一个四元组的新连接。
>
> **原理追问：** 主动关闭方通常进入 TIME_WAIT，持续时间与报文最大生存时间有关。大量短连接会消耗临时端口和连接跟踪状态，根治方向是连接复用、合理 Keep-Alive 和客户端池，而不是随便缩短内核安全窗口。
>
> **容易踩坑：** 看到 TIME_WAIT 多就当成内存泄漏；通过危险内核参数强行复用导致旧报文串入；每次模型请求都新建 Client；把 CLOSE_WAIT 和 TIME_WAIT 混淆，前者往往表示应用没有及时 close。
>
> **项目连接：** 当前项目通过 SDK 或 HTTP Client 调模型。排查连接耗尽时，我会先看是否复用 Client、谁主动关闭、TIME_WAIT/CLOSE_WAIT 分布和代理超时；材料没有这类真实事故就只讲方法。

### Q011：TCP 怎么保证可靠传输？流量控制和拥塞控制有什么区别？

> **口语化回答：** TCP 的可靠性来自序列号、ACK、校验、超时或快速重传、乱序重组和重复去除。流量控制保护接收端，接收窗口告诉发送方“我还能收多少”；拥塞控制保护整个网络，拥塞窗口根据丢包、时延等信号调整发送速度。真正能发送的数据量受两者较小值限制。
>
> **原理追问：** 慢启动、拥塞避免、快速重传和快速恢复是经典思路，具体算法可能是 CUBIC、BBR 等。TCP 只保证字节有序可靠，不理解业务消息边界，也不保证应用处理成功；HTTP 请求超时和业务幂等仍然要自己设计。
>
> **容易踩坑：** 说“用了 TCP 就不会丢业务消息”；把接收窗口和拥塞窗口混成一个；应用层没有长度或事件边界导致粘包解析错误；网络超时后直接重发非幂等请求。
>
> **项目连接：** Pi 的 JSONL 和模型 SSE 都需要应用层事件边界。即使底层 TCP 可靠，进程崩溃、代理断开和业务处理失败仍需 runId、eventId、状态持久化和幂等收口。

### Q012：Connect Timeout、Read Timeout、Idle Timeout、Keepalive 和 Deadline 有什么区别？

> **口语化回答：** 我不会只说“统一设 30 秒”。Connect Timeout 限制建立连接要等多久；Read Timeout 限制一段时间没有读到数据；Idle Timeout 是连接空闲多久被代理或服务端回收；TCP Keepalive 用低频探测发现死连接；Deadline 则是这次业务从入口到结束的总预算。下游每一跳都应该拿到剩余预算，而不是重新获得完整超时。
>
> **原理追问：** 流式模型可能总时长很长但分片持续到达，所以 Read Timeout 和总 Deadline 要分开。连接池中的陈旧连接还会受服务端 Idle Timeout、NAT 和负载均衡影响；健康探测不能替代真实请求超时。
>
> **容易踩坑：** 每一层都设 30 秒，三层串联后用户等 90 秒；只停止本地等待，远端仍执行；流式只看总时长误杀正常长回复；没有 jitter 的 Keepalive 或重连造成惊群。
>
> **项目连接：** CodeWiki 当前 LLM Gateway 有调用级 Timeout 和重试，但没有证据证明完整端到端 Deadline 传播。迁移设计中我会把连接、首 Token、Idle 和总 Deadline 分开观测。

### Q013：TLS 1.3 握手大致做了什么？证书校验到底在校验什么？

> **口语化回答：** 我会先讲目的：TLS 要让客户端确认对端身份、协商会话密钥，并保证后续数据的机密性和完整性。TLS 1.3 把握手轮次压缩了，客户端先给出支持的参数和密钥份额，服务端选择算法、返回证书和证明，双方派生对称密钥后传业务数据。证书校验不是只看“有证书”，还要验证信任链、域名、有效期、用途和吊销策略。
>
> **原理追问：** 非对称密码主要用于身份和密钥协商，批量数据用高效的对称加密；前向保密避免长期私钥泄露后直接解开过去会话。会话恢复和 0-RTT 可以降延迟，但 0-RTT 有重放风险，不适合直接承载不可重放写操作。
>
> **容易踩坑：** 关闭证书校验解决测试问题后带到生产；只校验证书链不校验主机名；把 TLS 当授权系统；在日志打印私钥、Token 或完整请求；对 0-RTT 的副作用请求不做重放保护。
>
> **项目连接：** 当前材料只表明系统会调用内部模型或网关，不能证明完整 TLS 配置和证书轮换。我会按真实平台事实回答；这里讲的是生产要求，不反推当前已经配置 mTLS。

### Q014：SNI、ALPN 和 mTLS 分别解决什么问题？

> **口语化回答：** SNI 是客户端在 TLS 握手时告诉服务端自己要访问哪个主机，方便同一个入口选择正确证书；ALPN 用来协商上层协议，比如 HTTP/2 还是 HTTP/1.1；mTLS 则让服务端也校验客户端证书，建立双向服务身份。mTLS 能证明“是谁接入”，但它不自动证明这个身份有权访问某个租户或仓库，授权仍要在应用层做。
>
> **原理追问：** 服务网格常用 mTLS 做工作负载身份和传输加密，证书要有签发、短周期轮换、吊销和信任域治理。跨代理时要明确 TLS 在哪里终止、下游身份如何继续传递，不能盲信用户可控 Header。
>
> **容易踩坑：** 把 mTLS 当完整零信任；证书过期导致全链路同时故障；TLS 在网关终止后内部明文却对外宣称端到端；SNI 与 HTTP Host 混淆；任意透传身份 Header。
>
> **项目连接：** CodeWiki 当前没有完整 Auth、Repo ACL 或 mTLS 证据。若做集中部署，我会把入口 TLS、服务身份和应用层用户/仓库授权分开设计，并明确这是下一版。

### Q015：HTTP/1.1、HTTP/2 和 HTTP/3 的核心区别是什么？

> **口语化回答：** HTTP/1.1 常靠多个 TCP 连接并发，请求在一个连接上按顺序处理容易受队头阻塞影响；HTTP/2 在一个 TCP 连接里把请求拆成多个 Stream 多路复用，还提供头部压缩，但底层 TCP 丢包时整个连接上的 Stream 都可能等待；HTTP/3 基于 QUIC，把可靠性做到独立 Stream 上，减少跨流队头阻塞，并整合 TLS 1.3。它不是无条件更快，还要看网络、代理、UDP 可达性和运维能力。
>
> **原理追问：** HTTP/2 的 Stream 有自己的 ID 和流控，但共享一个 TCP 拥塞控制；QUIC 基于 UDP 在用户态实现传输、加密和连接迁移。协议选择通常由 ALPN 协商，应用语义仍然是 HTTP。
>
> **容易踩坑：** 说 HTTP/2 完全没有队头阻塞；认为 HTTP/3 不可靠；为了协议升级忽略负载均衡和观测工具不支持；单连接多路复用后不设每连接 Stream 上限。
>
> **项目连接：** 当前项目没有自研 HTTP/2 或 QUIC。我会用这题解释 Provider 网关、长流和移动网络下的协议取舍，实际采用哪个版本必须看内部入口和 Client 配置。

### Q016：HTTP 连接池为什么会出现陈旧连接、端口耗尽或负载不均？

> **口语化回答：** 连接池省掉 DNS、TCP 和 TLS 重建成本，但它也会保留状态。服务端或负载均衡已经按 Idle Timeout 关了连接，客户端池还以为能用，就会拿到陈旧连接；每次请求新建 Client 会产生大量短连接和临时端口；连接活得太久，又可能一直粘在旧 IP 或少数实例上。我的做法是让连接寿命、空闲回收、DNS 刷新和服务端策略对齐，并监控建连失败、复用率和 Pool Wait。
>
> **原理追问：** DNS TTL 不会强制所有语言 Client 立即重建连接；HTTP/2 一个连接可承载大量 Stream，减少连接数但可能形成单连接热点。连接上限还要和线程/协程并发、下游实例数及代理容量一起设置。
>
> **容易踩坑：** 全局 Client 混用不同租户凭证；只调大连接池掩盖慢下游；不关闭流式 Response 导致连接永远不归还；忽略代理比应用更早关闭连接；连接池翻倍导致下游雪崩。
>
> **项目连接：** 当前 FastAPI 题库已经强调复用 Async Client，但项目材料没有完整连接池指标。若建设 LLM Gateway，我会增加 Pool Wait、DNS/TLS 建连、连接复用和每 Provider 隔离指标。

### Q017：LLM 流式输出应该选 SSE、WebSocket 还是 gRPC Streaming？

> **口语化回答：** 我会按交互方向和客户端生态选。浏览器里主要是服务端持续推 Token，SSE 基于 HTTP、实现简单、支持事件 ID 和自动重连，通常够用；需要客户端随时发送语音、控制或协同事件时，WebSocket 的全双工更合适；内部服务间要求强类型、高吞吐和双向流时可以考虑 gRPC Streaming。协议只解决传输，断线续传、最终状态和副作用幂等仍要单独设计。
>
> **原理追问：** SSE 是文本事件流，代理可能缓冲；WebSocket 建连后有自己的消息帧和心跳；gRPC 基于 HTTP/2 并有 Deadline、状态码和流控。选择还要考虑网关支持、鉴权刷新、负载均衡、移动网络和调试能力。
>
> **容易踩坑：** 因为要“实时”就默认 WebSocket；SSE 没禁代理缓冲，前端最后一次性收到；把每个 Token 当必须耐久化的业务事件；连接断开后没有 runId，只能从头生成；内部 gRPC 直接暴露浏览器。
>
> **项目连接：** 通用 AI 题和 Pi 文档已有流式协议概念，但当前 CodeWiki Ask API 不是可恢复 SSE。若下一版增加流式，我会先做 Run 状态和事件日志，再选传输协议，不能只把 SDK Iterator 透传出去。

## 3. Kubernetes 部署与运行治理

### Q018：Startup、Readiness 和 Liveness Probe 分别应该检查什么？

> **口语化回答：** 我会把三种探针的控制效果先讲清楚。Startup Probe 解决慢启动，在它成功前不让 Liveness 误杀进程；Readiness 决定这个 Pod 能不能接新流量，初始化未完成、正在 Drain 或关键依赖不可用时应该失败；Liveness 只回答进程是否已经卡死到需要重启，不能因为数据库短暂抖动就失败，否则会把一个下游故障放大成重启风暴。
>
> **原理追问：** 探针应轻量、有明确超时，并避免每次深查全部依赖。Readiness 从 Service Endpoint 摘流量不是瞬时完成，代理和客户端还可能保留连接；Liveness 失败会触发容器重启，无法修复外部数据库故障。启动预热和迁移步骤也要有独立状态。
>
> **容易踩坑：** 三个探针都指向同一个只返回 200 的接口；Liveness 查数据库；探针本身执行慢 SQL；Readiness 成功太早，缓存和模型客户端还没准备好；故障时所有 Pod 同时不 Ready 导致完全无服务。
>
> **项目连接：** 当前 CodeWiki 只有简单 Health，不能证明完整分层探针；其他项目的真实 K8s 部署也没有足够材料。集中部署时我会增加 Startup、Readiness、Liveness 状态机，这属于下一版设计。

### Q019：RollingUpdate 的 maxSurge、maxUnavailable、Readiness 和 PDB 怎么配合？

> **口语化回答：** 我会先保证新旧版本能共存，再谈滚动参数。maxSurge 控制更新时最多额外启动多少 Pod，maxUnavailable 控制最多允许多少副本暂时不可用；新 Pod 只有 Readiness 成功后才应该接流量，旧 Pod 摘流量并完成 Drain 后再退出。PDB 约束的是节点维护等自愿中断期间最少保留多少可用副本，不会替我保证应用版本兼容，也不会阻止所有故障。
>
> **原理追问：** 发布期间数据库 Schema、消息格式、缓存 Key 和 API 契约必须采用 Expand-and-Contract。终止时 Endpoint 更新、负载均衡传播、preStop 和 terminationGracePeriodSeconds 存在时间关系，要通过真实集成测试校准，而不是背固定秒数。
>
> **容易踩坑：** 新版本进程启动就标 Ready；回滚应用却无法回滚已经写入的新数据；PDB 设置过严导致节点无法维护，过松又同时中断太多；只配 preStop sleep，没有真正停止接任务和 Drain。
>
> **项目连接：** 当前材料没有可核验的 Kubernetes RollingUpdate 配置。我会把这套方案用于未来集中化部署，并明确数据库和任务状态兼容是前提，不声称三个项目已按此发布。

### Q020：Java 服务或 AI Worker 在 Kubernetes 中怎么优雅停机？

> **口语化回答：** 收到 SIGTERM 后，我会先把 Readiness 置失败并停止领取新任务，再给在途 HTTP、模型流和已经登记的 Worker 任务一个有界 Drain 时间。可完成的任务正常落最终状态；来不及完成的写 Checkpoint、释放 Lease 或标记为可重试，之后再关闭 HTTP Client、数据库 Pool、线程池和遥测。超过总关停 Deadline 就退出，由幂等恢复机制收口，不能无限阻塞发布。
>
> **原理追问：** Kubernetes 先执行 preStop，再向容器主进程发终止信号，最终受 terminationGracePeriodSeconds 限制。Spring 的 Graceful Shutdown 只能处理框架知道的请求，自己创建的线程、队列、虚拟线程和远端调用还要登记与取消。PID 1 必须正确接收并转发信号。
>
> **容易踩坑：** 先关数据库再等任务；把 Cancelled 标成 Success；只处理 HTTP，不处理 MQ 和模型流；Liveness 先失败导致立刻重启；任务无法恢复却在每次发布时强杀。
>
> **项目连接：** 当前 CodeWiki 的长分析依赖 Web 进程 BackgroundTasks 和进程内锁，没有可证明的完整 Drain/恢复协议。下一版应先拆可靠 Worker 和 Run 状态，再配 Kubernetes 关停，不能倒过来声称容器化就可靠。

### Q021：Kubernetes 的 Resource Request、Limit、CPU Throttling 和 OOMKilled 怎么理解？

> **口语化回答：** Request 是调度器用来放置 Pod、也是资源保障计算的重要依据；Limit 是容器可使用的上限。CPU 超过 Limit 常表现为 Throttling，不一定直接被杀；内存超过容器上限可能被 OOMKilled。对 JVM 来说，Xmx 只覆盖 Java Heap，RSS 还包括 Metaspace、Direct Memory、Code Cache、线程栈和 Native 库，所以我不会把 Xmx 直接设成容器内存上限。
>
> **原理追问：** CPU 是可压缩资源，内存通常不可压缩。资源配置要结合并发、GC、线程数、Native Parser 和模型 SDK；QoS 等级、节点压力和 Eviction 也会影响稳定性。JDK 版本需要正确识别容器限制，仍要通过 NMT、JFR 和 cgroup 指标验证。
>
> **容易踩坑：** Request 设太低导致节点过度承诺；CPU Limit 太小引发延迟毛刺却误判成代码慢；只看 Heap 使用解释 OOMKilled；大幅增加线程栈或 Direct Buffer 后不留余量；资源改动没有压测。
>
> **项目连接：** CodeWiki 含 Tree-sitter 和 sqlite-vec 等 Native 依赖，容器 RSS 不只有 Python Heap；Java 化迁移还要考虑 JVM Native 内存。当前没有真实资源参数证据，面试时只讲计算方法。

### Q022：HPA 给普通 API 和 LLM/Agent Worker 分别应该看什么指标？

> **口语化回答：** 普通无状态 API 可以先看 CPU，再补请求并发、队列等待和 P95；但 LLM 或 Agent Worker 经常大部分时间在等远端，CPU 不高也可能已经把 Provider 并发、连接池或任务队列打满。我会根据瓶颈选指标，比如 Ready Queue Age、Active Runs、Token Throughput、Provider In-flight、Pool Wait 和处理时长，并设置稳定窗口和扩缩速度，避免抖动。
>
> **原理追问：** HPA 增加副本不等于下游容量增加。每个副本都会带来数据库连接、模型并发和缓存预热，扩容前要算总量；缩容时还要和 Drain、Lease 及长任务安全点配合。事件驱动 Worker 也可以按队列 Lag 伸缩。
>
> **容易踩坑：** 只按 CPU 扩 LLM Worker；扩副本后数据库连接数成倍超限；队列已经堆积才扩，冷启动又很慢；缩容直接杀最长任务；指标高基数或延迟太大导致控制失真。
>
> **项目连接：** 当前项目没有 HPA 配置或生产负载数据。我会把队列、Run 状态和 Provider 配额先做成可观测信号，再谈自动扩缩，不能先报拍脑袋阈值。

### Q023：PDB、Pod Anti-Affinity 和 Topology Spread Constraints 分别解决什么？

> **口语化回答：** PDB 主要约束自愿中断时至少保留多少可用副本；Pod Anti-Affinity 用规则避免副本都落在同一节点或故障域；Topology Spread 更直接地控制副本在 Zone、Node 等拓扑上的分布。它们都不能替代多副本、数据备份和应用级容错，只是减少同一故障一次打掉全部副本的概率。
>
> **原理追问：** 强制 Anti-Affinity 可能在资源不足时让 Pod 无法调度；软约束可用性更高但分布不一定完美。PDB 不保护节点宕机这类非自愿中断，也不保证 Ready Pod 业务真的正确。跨 Zone 分布还要考虑数据库、网络成本和数据一致性。
>
> **容易踩坑：** 只有一个副本却配置 PDB 自我安慰；PDB 过严阻塞集群升级；副本看似分散但共享同一个单点数据库；跨区部署却没有考虑流量和依赖位置；把调度约束当灾备。
>
> **项目连接：** 三个项目没有可证明的多 Zone Kubernetes 拓扑。若 Memory 或 Gateway 做集中式高可用，我会先识别状态单点和恢复目标，再选择分布策略，仍属于目标架构。

### Q024：Deployment、StatefulSet、Job、CronJob 应该怎么选？长 Agent 任务适合放哪？

> **口语化回答：** Deployment 适合可替换的无状态常驻服务；StatefulSet 适合需要稳定网络身份或独立持久卷的有状态副本；Job 负责跑到完成的一次性任务，CronJob 定时创建 Job。长 Agent 任务本身不应该靠一个 HTTP Pod 一直不死来保证可靠，我更倾向把任务元数据和步骤状态落到耐久存储，由 Deployment 形式的 Worker 领取；确实是有限批次且退出语义明确时再用 Job。
>
> **原理追问：** Kubernetes 只能重启容器，不理解业务步骤是否已经产生副作用。Job 也可能因重试重复执行，所以任务仍需稳定 ID、幂等、Checkpoint 和完成条件。CronJob 要配置并发策略、补跑窗口和历史清理。
>
> **容易踩坑：** 把 StatefulSet 当成“更可靠的 Deployment”；用 Pod 本地文件做唯一任务状态；CronJob 上一轮没结束下一轮又启动；Job 重试导致邮件、扣费或工具调用重复；HTTP 202 返回后任务仍依赖 Web 进程。
>
> **项目连接：** 当前 CodeWiki 使用 BackgroundTasks，不是可靠 Job/Worker；AI 周报有调度和控制记录，但具体 Kubernetes 形态没有证据。迁移时我会复用业务状态机，而不是直接把现有进程套成 Job 就宣称可靠。

### Q025：ConfigMap、Secret、ServiceAccount 和 NetworkPolicy 各自管什么？

> **口语化回答：** ConfigMap 放非敏感配置，Secret 承载敏感数据的分发对象，ServiceAccount 代表工作负载身份，NetworkPolicy 限制 Pod 间和外部网络访问。它们解决的是不同层次的问题。Secret 只是 Kubernetes 对象，不代表默认就安全加密或不会出现在环境、日志和转储里；真正生产化还要接密钥管理、最小 RBAC、轮换和审计。
>
> **原理追问：** 配置更新不一定自动让进程重新加载，环境变量通常需要重启；挂载文件和外部 Secret CSI 有不同刷新语义。NetworkPolicy 需要网络插件支持，并且只管网络可达性，不理解 Repo、Tenant 或 Tool 权限。
>
> **容易踩坑：** 把 API Key 放 ConfigMap；给默认 ServiceAccount 集群管理员权限；Secret 烤进镜像或打印到异常日志；只限制入口不限制 Egress，Prompt Injection 可调用任意外网；配置热更新没有版本和回滚。
>
> **项目连接：** 当前材料不能证明内部模型 Key、Kubernetes RBAC 或 NetworkPolicy 的真实配置。我会把源码访问、模型 Egress 和 Secret 轮换列为集中部署的 P0 安全项，并按实际平台核验后再说已实现。

## 4. 数据库分片、复制延迟与 CDC

### Q026：什么时候才应该考虑分库分表？

> **口语化回答：** 我不会因为表大就直接分片。先用正确索引、查询改写、归档、冷热分层、读副本、批处理和垂直拆分确认单节点还能不能满足容量、吞吐、延迟和故障隔离目标。只有监控和容量推导证明单库的存储、写吞吐、维护窗口或租户隔离已经成为硬瓶颈，我才引入分片，因为它会把 Join、事务、分页、唯一约束、迁移和排障都变复杂。
>
> **原理追问：** 评估要有数据增长率、峰值读写、单行大小、索引放大、备份恢复时间和未来余量。分片解决横向容量，不会自动解决慢 SQL、热点键或错误数据模型；很多本地工具甚至根本不需要它。
>
> **容易踩坑：** 为简历架构感提前分库；没有基准就说“千万级必须分”；把读压力问题用写分片解决；分片后仍按非分片键全表扫描；没有跨片运维和恢复方案。
>
> **项目连接：** 当前 CodeWiki 是 Local-first SQLite/PostgreSQL，Agent Memory 当前也不能说已经做分布式分片。只有迁移到多租户中台并拿到真实规模后，我才会按 tenant/user/repo 的访问模式评估。

### Q027：分片键怎么选？热点租户和热点 Key 怎么处理？

> **口语化回答：** 我会从最常见查询、数据归属、写入分布和迁移成本一起选分片键。好的键能让大部分事务和查询落在单片，同时分布相对均匀。按 tenantId 分片隔离清楚，但大租户可能形成热点；纯随机哈希均匀，却会破坏范围查询和数据局部性。热点不能只靠“再加机器”，可以把超大租户单独拆片、对热点子键加盐，或者把读模型和写模型分开。
>
> **原理追问：** 取模简单但扩容迁移大；一致性哈希或虚拟槽减少搬迁量，但数据库事务、索引和运维仍要有路由层。全局二级索引、路由表和目录服务可以支持非分片键查询，但会引入一致性和可用性问题。
>
> **容易踩坑：** 用时间作唯一分片键导致最新分片最热；按用户分片却经常做跨用户统计；热点加盐后忘了读时聚合；路由缓存没有版本，迁移期间写错片；宣称哈希后绝对均匀。
>
> **项目连接：** 若 Agent Memory 做多租户服务，我会优先让 tenant/user 成为归属边界，再对超大租户做隔离；这是容量设计，不是当前已经验证的分片方案。

### Q028：分片后跨片事务、全局唯一 ID、分页和聚合怎么做？

> **口语化回答：** 我的第一原则是通过业务边界让一次写尽量落单片，而不是先上分布式事务。跨片流程通常用状态机、Outbox、幂等和补偿做最终一致；确实不可拆的核心账务要重新审视数据归属或使用能提供所需一致性的数据库。全局 ID 可以用 UUID/ULID、号段或 Snowflake 类方案，但要讲清排序、时钟和位数。分页尽量用分片键加游标，跨片 Top N 要各片取候选再归并。
>
> **原理追问：** Offset 深分页在每片都扫描并丢弃，成本会被分片数放大；跨片 count 和聚合可用异步汇总表或分析系统。全局唯一约束如果不含分片键，通常需要全局索引或独立占位服务，会增加写路径。
>
> **容易踩坑：** 把 XA 默认用于所有跨片写；Snowflake Worker ID 冲突或时钟回拨；跨片分页结果在并发写下重复/漏项；每个请求广播全部分片；把异步汇总说成实时强一致。
>
> **项目连接：** 当前项目没有跨分片事务。我可以把 Memory 的 tenant/user、CodeWiki 的 repo/revision 作为设计分区候选，但只有真实访问模式和一致性要求出来后才能定，不能从字段名直接宣布架构。

### Q029：数据库分片扩容和 Rebalance 怎么做到不停服？

> **口语化回答：** 我会把迁移做成有状态、可回放、可校验的流程。先给路由配置加版本，确定源片和目标片；做历史数据的幂等复制，再通过 CDC 或双写追平增量；进入短暂切换窗口后把读写路由切到目标，持续对账，稳定后才回收源数据。每一步都要能暂停和重试，不能用一次大事务搬完。
>
> **原理追问：** 双写存在一边成功一边失败窗口，所以需要以一个事实源加增量日志为主，或者写入带版本并对账。读路径可以先影子读比对，再灰度切换。路由版本要随请求传播，避免缓存旧拓扑后写回源片。
>
> **容易踩坑：** 全表复制期间没有捕获增量；切换后立刻删源数据无法回滚；搬迁脚本重复执行产生覆盖；只比记录数不比 Hash 和业务不变量；热点迁移把目标片打满。
>
> **项目连接：** 当前项目没有在线 Rebalance 实现。若未来云端 Memory Store 需要分片，我会先做 Asset Manifest、路由版本和迁移状态机，这完全属于下一版系统设计。

### Q030：读写分离遇到 Replica Lag，怎么保证 Read-your-writes？

> **口语化回答：** 异步副本一定可能延迟，所以我会先问业务到底需要哪种一致性。用户刚写完马上读必须看到时，可以在一个短窗口内读主库、把写入位置的 GTID/LSN 带到读请求并等待副本追上，或者让会话粘到主库；允许稍旧的数据才直接读副本。不能一边用异步副本，一边口头承诺所有读取强一致。
>
> **原理追问：** Lag 不只看秒数，还要看具体日志位点和目标事务是否已重放。复制可能因大事务、DDL、网络或副本负载变慢；故障切换时还要判断候选副本是否缺数据。缓存层也可能比副本更旧，必须统一版本语义。
>
> **容易踩坑：** 写后立即随机读副本；只看平均 Lag；支付状态等关键数据也无条件读副本；主库故障时提升落后的副本却不核对丢失窗口；为等副本无限阻塞请求。
>
> **项目连接：** 当前本地 SQLite 场景没有主从复制；PostgreSQL 集中部署和多租户 Memory 才可能遇到。面试时我会明确这是扩展方案，不把读写分离描述成现有架构。

### Q031：CDC 和 Transactional Outbox 是什么关系？能不能互相替代？

> **口语化回答：** CDC 是从数据库已提交的变更日志里读取变化的机制；Outbox 是业务在同一个本地事务里同时写业务状态和一条明确的业务事件。两者经常配合：CDC 读取 Outbox 表并投递消息。只抓业务表 CDC 虽然少写一张表，但数据库行变化不一定等于稳定业务事件，字段和事务细节会泄漏给下游；Outbox 把事件契约、eventId 和发生时机说清楚。
>
> **原理追问：** Outbox 消除了“业务提交成功但消息没发”的双写窗口，但 Relay 仍可能重复发送，消费者必须幂等。CDC 也可以用于缓存同步、搜索索引和数据仓库，但每种下游的重放、删除和 Schema 语义不同。
>
> **容易踩坑：** 把 Binlog 当成业务 MQ 契约；认为 CDC 天然 Exactly-once；Outbox 发成功但状态未标记后重复投递；没有表清理和保留；事件 Payload 带入敏感字段。
>
> **项目连接：** AI 周报的发送链路当前材料暴露了状态成功但发送可能失败的设计缺口；Outbox/CDC 是下一版修复方向。不能把建议方案说成当前已落地。

### Q032：CDC 的 Initial Snapshot、增量衔接、顺序、Schema Evolution 和故障恢复怎么设计？

> **口语化回答：** 我会把 CDC 当成一条可以重放的数据管道，而不是“开个 Debezium 就结束”。首次同步先在一致水位做 Snapshot，同时记录对应 Binlog/LSN；Snapshot 完成后从这个位置继续增量，避免丢和重叠。每条事件带源位置、主键、事务和 Schema 版本；下游按稳定 eventId 或源位置幂等。DDL 和字段演进先做兼容，再升级消费者，不能让一列改名直接把整条链打断。
>
> **原理追问：** 同一分区内可以保序，跨表、跨分片和跨事务的全局顺序通常成本很高；要先定义业务需要的顺序范围。消费端 Checkpoint、日志保留和复制 Slot 要监控，Lag 超过保留窗口后可能需要重新 Snapshot 并对账。
>
> **容易踩坑：** Snapshot 时不记录水位；消费者失败后从最新位置继续导致静默缺口；长期不推进 Slot 把主库日志撑满；把 Delete 丢掉造成下游幽灵数据；Schema 不兼容后无限重试一条毒事件。
>
> **项目连接：** 当前三个项目没有可证明的 Debezium 或完整 CDC Pipeline。若以后用 CDC 驱动索引或 Outbox，我会先定义水位、幂等、删除、Schema 和重建合同，仍是迁移设计。

## 5. LLM Gateway、Agent Runtime 与可靠流式

### Q033：设计一个生产级 LLM Gateway，控制面和数据面怎么拆？

> **口语化回答：** 我会把高频请求路径和低频管理路径拆开。数据面负责鉴权后的请求规范化、任务分类、模型路由、配额、调用、流式转发和最小审计，热路径只读本地或近端配置快照，不能临时查慢数据库或再调一次 LLM。控制面负责模型目录、Provider 凭证、路由策略、价格、健康、租户配额、灰度和策略发布。策略有版本，数据面每次决策记录版本和 decisionId，才能回放当时为什么这样选。
>
> **原理追问：** Gateway 需要统一 Provider 差异，但不能抹平能力差异。上下文长度、Tool Schema、Structured Output、区域合规、流协议和错误码都要进入 Capability Model。配置发布采用不可变快照、校验、灰度和回滚，数据面在控制面短暂不可用时继续使用 Last-known-good。
>
> **容易踩坑：** 把所有业务 Prompt 逻辑塞进网关；路由时同步查多个远端健康服务；把不同 Provider 错误一律转成 500；配置更新无版本导致审计无法重放；控制面挂了数据面也完全停摆。
>
> **项目连接：** 当前 CodeWiki 有 LiteLLM Gateway 和按 Task Type 选择 Profile 的 ModelRouter，但没有可证明的动态健康路由、完整租户配额和独立控制面。上述是从现有抽象迁移到平台级 Gateway 的设计。

### Q034：LLM Gateway 里的 Deadline、Retry、Circuit Breaker、Rate Limit 和 Budget 怎么配合？

> **口语化回答：** 我会先设一条端到端 Deadline，每次模型尝试只能使用剩余预算。Retry 只处理连接失败、部分 429/5xx 等暂时错误，而且请求必须可安全重复；指数退避加 Jitter，并限制总尝试。Circuit Breaker 按 Provider、模型、区域和能力隔离，持续异常时快速失败，Half-open 只放少量探测。Rate Limit 保护请求和 Token 速率，Budget 再按租户、任务和成本控制可花多少钱。
>
> **原理追问：** 限并发和限速不是一回事；Token 数在请求前只能估算，结束后要用 Provider Usage 对账。多层 SDK、Gateway、业务服务不能都独立重试，否则尝试次数相乘。Hedged Request 只适合少量高价值、幂等且成本可接受的请求，还要取消输掉的一路。
>
> **容易踩坑：** 对 400、401 和业务校验失败重试；流式已经发 Token 后自动整段重试；所有模型共享一个熔断器；只限请求数不看超长 Prompt；超时后远端继续生成却不记成本。
>
> **项目连接：** 当前 CodeWiki Gateway 有 Timeout 和同调用重试，但没有证据证明完整 Circuit Breaker、租户 Token Budget 或 Hedging。我会先补阶段指标和错误分类，再逐项引入，不能描述成已有平台能力。

### Q035：模型路由和 Failover 怎样做到可审计，又不让审计拖慢热路径？

> **口语化回答：** 我会先定义“可审计”不是事后尽力写一条日志，而是关键决策不能丢。路由前生成 decisionId，把租户、任务类型、输入特征摘要、候选集、健康快照版本、策略版本、选择结果和总 Deadline 写入本地 WAL 或事务 Outbox；最小事件持久化成功后再发请求。详细 Trace、Token 和响应结果可以异步写查询系统。Failover 每次生成 attemptId，沿用同一个业务请求 ID，才能看到完整尝试链。
>
> **原理追问：** ES 或 ClickHouse 适合查询，不应作为唯一事实源；写入失败时，强审计业务可以 Fail Closed，低风险业务也要明确降级策略。敏感 Prompt/Response 不应默认全量写审计，通常保存 Hash、版本、受控摘要和授权后的内容引用。
>
> **容易踩坑：** 先调用模型再异步打日志，进程崩溃后决策消失；Failover 换新请求 ID 无法串联；审计写完整源码和个人数据；健康快照没有版本；为了审计同步写多个远端库，反而打穿延迟目标。
>
> **项目连接：** 京东面试里的模型路由题已经提出 WAL/Outbox 设计，但这属于系统设计答案，不是当前三个项目已上线的路由平台。CodeWiki 当前 llm_run 记录也不能等同于完整路由审计。

### Q036：SSE 聊天怎样实现断线重连和从上次位置续传？

> **口语化回答：** 我不会把 TCP 连接当任务本身。服务先创建稳定 runId，生成过程写入带单调 seq 和 eventId 的事件日志，SSE 只是订阅这个 Run 的一种视图。客户端断线重连时带 runId 和 Last-Event-ID，服务从已确认位置重放；如果任务已经完成，就直接返回最终快照。Token Delta 可能重复，所以前端按事件 ID 去重，最终消息再用 messageVersion 或内容 Hash 收口。
>
> **原理追问：** 事件日志需要定义保留期、压缩和授权；不能永久保存每个 Token。可以把高频 Delta 批量持久化，把 Tool 开始/结束、状态转换和最终消息作为强事件。代理要关闭缓冲并设置合理 Idle 心跳；Run 的执行不应依赖某条订阅连接存在。
>
> **容易踩坑：** 重连后重新调一次模型；只在内存保存 seq，Pod 重启就丢；Last-Event-ID 不绑定用户和 Run，造成越权读取；按字符串长度定位导致 Unicode 或合并分片错位；断线就把任务取消。
>
> **项目连接：** 当前 CodeWiki Ask API 返回完整结果，没有可恢复 SSE；Pi 的流式事件也不能自动证明服务端耐久重放。下一版要先增加 Run/Event Store 和授权，再实现 SSE。

### Q037：模型流已经发出一半时失败，能不能透明切到备用模型继续？

> **口语化回答：** 我会明确说，通常不能“无痕透明拼接”。如果还没向用户发任何 Token，可以在总 Deadline 内切备用模型；一旦已经发出半段文字，另一个模型拿同样 Prompt 也不保证从同一位置、同一语义继续。我的选择是显式结束当前 attempt，标记可重试原因，再由上层决定重新生成、从已验证的结构化检查点续跑，或保留已输出内容并提示后续是新 attempt。任何已经执行的 Tool 副作用都绝不能随模型切换自动重做。
>
> **原理追问：** 可恢复点应该是业务状态或已持久化消息，不是模型隐藏状态。若 Provider 支持稳定 Resume Token，也要验证其一致性和保留语义。结构化生成可以按段落、节点或 Tool Step Checkpoint，降低失败重做范围，但会增加延迟和实现复杂度。
>
> **容易踩坑：** 把两个模型的文本直接拼起来；只按字符串前缀去重；模型超时后认为 Tool 一定没执行；重试时换 Prompt/模型却沿用相同结果版本；为了所谓无感切换隐藏事实，导致审计无法解释。
>
> **项目连接：** 当前 CodeWiki 没有流式 Failover，Memory 也不负责宿主模型输出。京东复盘中的规则是设计边界，不是现成功能；面试时我会主动区分。

### Q038：Webhook 接收端和发送端怎样做到可靠、幂等和可追溯？

> **口语化回答：** 接收端我会先验签、校验时间戳和重放窗口，再把原始事件或受控 Payload 以稳定 eventId 落到耐久 Inbox，然后尽快返回 2xx；真正业务处理由 Worker 异步执行，同一 eventId 重复到达只复用已有状态。发送端使用 Outbox，把业务提交和待发送事件放同一事务，按明确重试策略投递；超过阈值进入 DLQ 和人工对账。2xx 只表示接收成功，不等于对方业务已经完成。
>
> **原理追问：** 验签通常对原始字节做，解析或重排 JSON 后再验可能失败。Secret 要轮换并支持一段双 Key 窗口；重试使用指数退避和 Jitter。对方超时后发送方无法判断是否已处理，所以幂等键必须跨重试保持不变。
>
> **容易踩坑：** 先做慢业务再返回导致对方反复重试；验签后不做授权和 Schema 校验；每次重试生成新 ID；只记录发送日志，不记录对方响应和最终业务状态；DLQ 永久无人处理。
>
> **项目连接：** AI 周报的消息发送可借鉴 Outbox，模型 Provider 的异步回调可借鉴 Inbox；当前材料没有完整 Webhook 平台，回答时只作为迁移设计。

### Q039：Agent Runtime 进程崩溃后，怎样恢复任务又不重复 Tool 副作用？

> **口语化回答：** 我会把 Agent 的 Run、Step、Attempt 和 Tool Execution 都做成显式状态，不把唯一进度藏在内存或对话文本里。Worker 用 Lease 和 Heartbeat 领取 Run；每一步先持久化输入和状态，再执行；完成后原子写结果和下一状态。崩溃后新 Worker 从最后一个已确认 Checkpoint 恢复。Tool 调用使用稳定 idempotencyKey 和执行账本，区分 Prepared、Started、Succeeded、Failed、Unknown；Unknown 先向外部系统查询，不能直接重做。
>
> **原理追问：** Checkpoint 恢复通常意味着 Replay，所以确定性计算可以重放，当前时间、随机数、模型输出和外部结果必须记录。Exactly-once 很难跨越数据库、模型和外部 API，工程目标是耐久状态加 At-least-once 调度，再通过幂等和补偿做到 Effectively-once。
>
> **容易踩坑：** 每个节点结束后才第一次落状态；超时一律标失败并重试；Tool 参数相同就认为业务幂等；补偿动作本身不幂等；多个 Worker 没有 Lease 版本，旧 Worker 复活后继续写。
>
> **项目连接：** 当前 Agent Memory 是记忆与上下文能力，不是完整分布式 Agent Runtime；Pi 当前 Agent Session 也不等同于跨进程耐久执行。以上是平台化扩展设计，不能反推已实现。

### Q040：多租户 Agent/LLM 系统怎样做公平调度、发布 Drain 和故障测试？

> **口语化回答：** 我会把公平、可恢复和可验证放在一起设计。入口按租户设置请求、并发、Token 和成本预算，队列用分层或加权公平调度，不能让一个超长 Agent 占满全部 Worker；Provider、数据库和 Tool 再各有独立并发上限。发布时 Worker 停止领新 Run，短步骤完成，长步骤在 Checkpoint 释放 Lease，SSE 客户端按 runId 重连。验证时不仅压正常吞吐，还要杀进程、断 Provider、重复事件、制造慢客户端和滚动发布，最后检查任务状态与外部副作用。
>
> **原理追问：** Queue Lag、Oldest Age、Active Run、Step Duration、Provider In-flight、Token Spend 和租户拒绝率共同反映容量。公平调度要防止 Head-of-line Blocking；故障注入要用可控 Fake Provider 和少量真实协议 Smoke Test，两者覆盖不同边界。
>
> **容易踩坑：** 所有租户共用一个 FIFO；只限请求数不限制 Token 和 Tool 扇出；发布时强杀长任务；测试只看前端收到 Token，不核对最终数据库状态；重放故障事件时更换 eventId，掩盖幂等缺陷。
>
> **项目连接：** 当前三个项目没有可证明的多租户分布式调度、Kubernetes Drain 或 Chaos 测试闭环。我会把这套内容作为集中化 Agent Runtime 的验收方案，并要求真实容量数据后再设置阈值。

## 6. JVM 生产排障实战

### Q041：jstack、jcmd、JFR、async-profiler、jmap 和 NMT 分别什么时候用？

> **口语化回答：** 我会先按问题和风险选工具。线程卡住、死锁或线程池耗尽先抓多次 jstack 或 jcmd Thread.print；想低开销持续观察 CPU、分配、锁、GC 和虚拟线程事件用 JFR；需要更细的 CPU、Wall-clock、Lock 或 Allocation 火焰图可以评估 async-profiler；堆对象和引用关系用 Histogram 或 Heap Dump；怀疑 Direct、线程栈、Metaspace 等 Native 内存则看 NMT 和进程 RSS。不会一上来就在线上大堆执行完整 jmap dump。
>
> **原理追问：** CPU Profile 看正在消耗 CPU 的栈，Wall-clock Profile 能看到阻塞和等待；Allocation Profile 找分配热点，不等于保留对象；Heap Dump 看某个时点的存活图。NMT 需要合适的启动配置，并且它本身也有开销和覆盖边界。
>
> **容易踩坑：** 只抓一次线程栈；把分配最多的类直接判成泄漏；在线上磁盘不足时 Dump；Profiler 参数过激造成额外负载；容器内找错 PID 或忽略宿主 cgroup。
>
> **项目连接：** Java 题库已有 CPU、内存和 GC 排查框架，但当前项目没有可核验的真实 JFR 事故记录。面试时我会讲工具链和风险控制，真实案例必须换成有日志证据的经历。

### Q042：Safepoint 和 Stop-the-world 是什么？STW 是否都由 GC 引起？

> **口语化回答：** Safepoint 是 JVM 能安全检查和修改线程状态的协作点；某些全局操作需要所有相关 Java 线程到达安全状态，这段暂停就是 STW。GC 是常见原因，但不是唯一原因，撤销优化、类重定义、部分偏向锁或线程转储相关操作也可能需要停顿。排查“应用突然卡住”时，我不会只看 GC Pause，还会对齐 Safepoint、系统调度和容器 CPU Throttling。
>
> **原理追问：** 总停顿可以拆成“等待线程到达 Safepoint”和“Safepoint 操作本身”两部分；如果某个线程长期无法到达，Time to Safepoint 也可能很长。现代 JDK 可通过统一日志和 JFR 观察相关事件，具体参数按版本确认。
>
> **容易踩坑：** 看到所有请求同时停顿就断言 Full GC；只看 GC 回收耗时，不看进入 Safepoint 的等待；用旧 JDK 结论解释新版本；忽略宿主机抢占、Swap 和 CPU Limit。
>
> **项目连接：** 当前没有项目级 Safepoint 证据。这题用于完善 JVM 排障链：先把 JVM 停顿、系统资源和下游等待分开，再下结论，不虚构一次生产故障。

### Q043：Heap 没涨但容器 RSS 一直涨，应该怎么排查？

> **口语化回答：** 我会先承认 JVM 进程内存不等于 Java Heap。Heap Full GC 后基线稳定，但 RSS 继续涨时，我会分别看 Metaspace 和类加载器、Direct Buffer、线程数量与栈、Code Cache、JNI/Native 库、内存映射文件和系统 Page Cache。用容器指标确认是真正 Resident 增长，再结合 NMT、jcmd、线程数、类加载统计和 Native Profile 缩小范围。
>
> **原理追问：** 类加载器泄漏会让整批 Class Metadata 和静态对象不能卸载；DirectByteBuffer 的释放依赖引用可达性和 Cleaner，池化库也可能保留；每个平台线程都有 Native Stack，线程暴涨会在 Heap 很空时 OOM。NMT 未必覆盖所有第三方 Native 分配。
>
> **容易踩坑：** 只调大 Xmx；把容器内存全部分给 Heap；看到 Direct Memory 高就主动频繁 System.gc；忽略短时间内 Dump 和日志也会占磁盘/缓存；用一个时间点判断泄漏。
>
> **项目连接：** CodeWiki 的 Native Parser 更偏 Python 进程；若迁移 Java 或接 JNI，同样要把 Heap 与 Native 分开。当前没有对应事故数据，我只讲可迁移的诊断方法。

### Q044：怎样从 GC Log 和 JFR 区分分配过快、晋升压力、Humongous Object 和真实泄漏？

> **口语化回答：** 我会看一段时间趋势，而不是看一次 GC。Young GC 很频繁但每次回收后老年代稳定，通常更像分配率高；老年代和 Full GC 后存活基线持续上升，再结合 GC Root 路径才像泄漏；Survivor 放不下、对象年龄和老年代快速增长提示晋升压力；G1 中超过 Region 一定比例的大对象会走 Humongous 路径，要看对应 Region、回收和碎片信号。JFR 的 Allocation Sample 和对象统计能帮我定位谁在大量创建。
>
> **原理追问：** 指标至少包括 Allocation Rate、Promotion Rate、Live Set、Pause Cause、并发标记是否及时、To-space Exhaustion 和 Humongous Region。Heap 太小、批量请求、缓存策略和 GC 参数都会产生类似表象，要结合发布和流量时间线。
>
> **容易踩坑：** 年轻代 GC 多就直接调大堆；把分配热点当保留泄漏；只看平均 Pause 不看 P99；一次改很多参数无法归因；忽略超大 JSON、Embedding Batch 和缓存值生命周期。
>
> **项目连接：** Java 120 题已有 G1、ZGC 和 Full GC 基础，本题补的是证据串联。项目若没有真实 GC 记录，就用受控压测示例回答，不能说“线上观察到”。

### Q045：线上 Java 服务出现 CPU 100% 或 OOM，怎样既保留证据又控制诊断风险？

> **口语化回答：** 我会先止损和分级，不会为了抓全量证据把服务彻底打死。先确认影响面、保留时间线，把流量摘除或限流；抓进程、容器、GC、线程和系统指标，再做多次低风险线程快照或短 JFR。只有内存、磁盘和停顿预算允许时才做 Heap Dump；必要时先复制流量到隔离实例复现。所有命令、时间和制品都记录，敏感数据受控存放，修复后用同负载回归。
>
> **原理追问：** CPU 100% 要区分业务热点、GC、锁自旋、正则、序列化和系统 Steal；OOM 要先看错误类型与容器 OOM 事件。诊断动作本身可能触发 Safepoint、磁盘打满或增加 CPU，所以需要预案、权限和自动化采集。
>
> **容易踩坑：** 第一时间重启导致现场全丢；反过来为了 Dump 长时间不止损；在所有副本同时 Profile；把用户 Prompt、源码或 Token 留进诊断文件后随意传播；修复只加资源，没有根因和回归。
>
> **项目连接：** 当前材料没有足够证据让我编一个真实 Java 线上事故。我会把这套流程作为标准排障答案；如果面试官要真实案例，只讲本人能提供日志、变更和验证记录的那一条。

## 8. 货拉拉大数据平台补题（八股单列）

> 这些是针对大数据平台岗位的补充知识题，不代表候选人已经在生产环境独立使用过全部组件。现场经历和知识迁移必须分开说。

### D01. Kafka 分区、offset、重复消费和幂等怎样回答？

> 分区提供并行度和分区内有序，offset 是消费者在分区中的进度；消费组通过分区分配实现水平扩展。至少一次投递下，提交 offset 和业务写入不是天然一个事务，重平衡、超时和重试都可能重复。因此业务侧用事件 ID/窗口键、唯一约束、状态机或 Inbox/Outbox 做幂等；只有真正需要时才使用 Kafka 事务，不能把“提交 offset”说成业务 exactly-once。

### D02. Kafka 怎样避免消息丢失？

> 先明确目标是“生产端不丢、Broker 不丢、消费端不丢”。生产端开启幂等生产与合适的 `acks`，Broker 配置副本、ISR 和最小同步副本，消费者处理成功后再提交 offset；监控 lag、Under-replicated Partitions 和发送/落库失败。跨系统副作用仍需要幂等或事务性 Outbox，Kafka 本身不能替业务保证最终结果。

### D03. Flink watermark、窗口和迟到数据怎么处理？

> Watermark 是对事件时间进度的估计，用来触发窗口计算；允许乱序时间决定窗口何时关闭，迟到数据可进入 side output、更新窗口结果或补偿任务。要区分 event time、processing time 和 ingest time，并定义迟到上限、结果版本和下游是否接受更新。Watermark 不是“消息到了就按时间排序”，也不能修复源端时间戳错误。

### D04. Flink checkpoint 和 exactly-once 的关系是什么？

> Checkpoint 保存算子状态和输入进度，用于故障恢复；端到端 exactly-once 还要求 Source 可重放、状态一致快照以及 Sink 支持事务或幂等提交。Barrier 对齐可能造成反压和延迟，非对齐 checkpoint 是取舍而不是免费优化。没有幂等 Sink 时，恢复后仍可能重复写出，不能只背“开 checkpoint 就 exactly-once”。

### D05. Spark、Flink 和 Hive 怎样选？

> Spark 更适合批处理、离线 ETL 和大规模 SQL；Flink 更适合持续流处理、有状态计算和低延迟事件；Hive 主要是离线数仓 SQL/表格式生态。选型看数据时效、状态、回放、成本和团队运维能力，很多平台会用 Kafka/Flink 做实时链路、对象存储/Hive/Spark 做离线与回溯。没有真实使用过的组件按设计题回答，不把学习经验写成生产交付。

### D06. ETL 补数、回放和数据质量怎样做？

> 每个任务要有可重放的输入窗口、版本、Manifest 和幂等输出键；补数不直接覆盖未知结果，而是产生新的 run/version，经对账和质量门禁后发布。质量至少检查完整性、唯一性、合法范围、跨表一致、及时性和源端总量；失败要能定位到 source/window/partition，并保留原始输入和处理状态。

### D07. 海量 Top K、数据倾斜和小文件怎么答？

> Top K 先做分区内 Top K，再合并全局堆，避免把全部数据拉到单点；数据倾斜通过热点识别、拆分热点 Key、随机前缀/两阶段聚合和合理并行度处理；小文件通过批量写、Compaction、合理分区和文件大小目标治理。优化前先用 Stage、Shuffle、输入分布和文件统计确认瓶颈，不能只调并行度。

### D08. 大数据平台和 AI 项目经验怎样对齐？

> 可迁移的是采集、清洗、窗口、幂等、重试、补数、对账、质量和任务状态；Kafka/Flink/Spark/Hive/ClickHouse 的实际使用、吞吐和延迟必须有代码或监控证据。没有完整生产平台经历时，我会坦诚差距，再用一条真实 Java/数据交付、现场编码和系统设计证明基础能力。
