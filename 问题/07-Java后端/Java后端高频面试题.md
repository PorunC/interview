# Java 后端高频面试题

> 定位：面向简历中“三年左右 Java 后端经验”的面试准备材料。丰泊国际真实追问用“丰泊实问”标记，其余问题按同等年限常见后端面试继续展开。
>
> 回答原则：全部使用面试现场能直接说出口的表达。每题都包含结论、机制、容易踩坑和适用场景；场景只说明技术该怎么选，不虚构本人做过的生产事故、流量规模、团队人数或性能指标。

## 1. Java 语言与集合

### Q001：`==`、`equals()` 和 `hashCode()` 到底是什么关系？

> **结论：** 我会先说，基本类型用 `==` 比值，引用类型的 `==` 比是不是同一个对象；`equals()` 表达业务上的相等，`hashCode()` 是哈希容器定位桶的依据。
>
> **机制：** 如果两个对象 `equals()` 为 true，它们的 `hashCode()` 必须相同；反过来不成立，因为不同对象可以发生哈希冲突。`HashMap` 先看 hash 和桶，再用 `equals()` 找具体键。
>
> **容易踩坑：** 只重写 `equals()` 不重写 `hashCode()`，对象放进 `HashSet` 或作为 `HashMap` key 后就可能查不到；参与相等判断的字段可变，也会让 key 放进去以后失联。
>
> **适用场景：** 实体去重、值对象、缓存 key 和集合成员判断都要先定义清楚“业务相等”是什么。

### Q002：为什么 `String` 要设计成不可变？字符串常量池怎么工作？

> **结论：** `String` 不可变主要是为了安全、可共享、可缓存 hash，也让它天然适合做 Map key；修改字符串实际上会产生新对象。
>
> **机制：** 字面量通常进入字符串常量池，相同字面量可以复用；`new String("a")` 会显式创建堆对象。`intern()` 返回池中的规范引用，但不能把它当成普通业务优化手段乱用。
>
> **容易踩坑：** 用 `==` 比字符串内容、在循环中反复 `+` 拼接、把大量动态字符串随意 `intern()`，都会带来错误或内存压力。
>
> **适用场景：** 少量固定拼接可以直接用 `+`；循环或复杂拼接用 `StringBuilder`，跨线程共享但需要可变时再评估同步方案。

### Q003：自动装箱、拆箱和 Integer 缓存有什么坑？

> **结论：** 包装类型比较内容要用 `equals()`，不要依赖 `==`；自动拆箱还可能抛 `NullPointerException`。
>
> **机制：** 常见实现会缓存 `Integer` 的 -128 到 127，所以这个范围内 `Integer.valueOf()` 可能返回同一个对象，范围外通常不是同一引用。这只是实现优化，不是业务语义。
>
> **容易踩坑：** `Integer a = null; int b = a;` 会在拆箱时 NPE；包装类型和基本类型混算也可能在不明显的位置触发拆箱。
>
> **适用场景：** DTO、数据库可空字段和泛型集合必须使用包装类型；真正参与高频数值计算时优先基本类型，减少对象和拆装箱成本。

### Q004：`final`、`finally` 和 `finalize()` 分别是什么？

> **结论：** `final` 是语言约束，`finally` 是异常清理块，`finalize()` 是已经不应依赖的对象回收回调，三者没有一条统一机制。
>
> **机制：** `final` 变量只能赋值一次，但引用指向的对象仍可能可变；`finally` 通常会执行，适合释放资源；`finalize()` 的执行时机不确定并已被弃用方向替代。
>
> **容易踩坑：** 在 `finally` 里 `return` 会覆盖原返回值或异常；以为 `final List` 就是不可变集合；依赖 `finalize()` 释放连接或文件都会造成资源泄漏。
>
> **适用场景：** 依赖和状态尽量用 `final`；资源释放优先 `try-with-resources`，不要等待 GC 帮业务收尾。

### Q005：Checked Exception 和 RuntimeException 怎么选？

> **结论：** 可由调用方合理恢复、且希望编译期强制处理的异常可以是 checked；编程错误、参数非法和大多数业务运行异常通常用 unchecked。
>
> **机制：** checked 异常必须捕获或声明；RuntimeException 不强制。服务层一般会把底层异常翻译成稳定的领域异常，再由统一异常处理器映射响应。
>
> **容易踩坑：** `catch (Exception)` 后只打日志不再抛会把事务和失败状态吞掉；把数据库、HTTP 客户端的实现异常原样暴露给接口也会泄漏内部细节。
>
> **适用场景：** 业务校验给明确错误码；不可恢复的系统异常向上抛并保留 cause；批处理则要区分单条可跳过和整批必须终止。

### Q006：Java 泛型为什么说是类型擦除？有什么影响？

> **结论：** Java 泛型主要在编译期提供类型检查，运行时大部分类型参数被擦除，所以 `List<String>` 和 `List<Integer>` 运行时通常是同一个原始类型。
>
> **机制：** 编译器会插入必要的强转，并用上界替换类型变量；为了保持多态，某些场景还会生成桥接方法。
>
> **容易踩坑：** 不能直接 `new T()`、不能创建泛型数组、不能用 `instanceof List<String>`；原始类型和不受控强转会把错误推迟到运行时。
>
> **适用场景：** 通用仓储、工具库和结果包装适合泛型；需要运行时类型信息时显式传 `Class<T>`、`TypeReference<T>` 或类型令牌。

### Q007：反射和注解的底层用途是什么？为什么框架大量使用它们？

> **结论：** 注解负责声明元数据，反射让运行时读取类、方法、字段并动态调用；Spring、MyBatis 等框架用它们降低配置和业务代码的耦合。
>
> **机制：** 运行时注解必须使用 `RUNTIME` 保留策略；框架扫描 class 后读取注解，构造 Bean 定义、映射 SQL 或创建代理。反射元数据通常会缓存，不是每次都全量扫描。
>
> **容易踩坑：** 反射绕过编译期约束，错误更晚暴露；强行访问私有成员会破坏封装并受模块系统限制；把所有逻辑都做成注解会让执行路径难追踪。
>
> **适用场景：** 框架扩展、序列化、ORM 和插件机制适合反射；核心业务优先显式接口和普通方法，便于测试和重构。

### Q008：`ArrayList` 和 `LinkedList` 怎么选？

> **结论：** 大多数业务默认选 `ArrayList`；`LinkedList` 只有在已经拿到节点位置并频繁做中间插删时才可能占优，实际使用远少于教程给人的感觉。
>
> **机制：** `ArrayList` 是连续数组，随机访问 O(1)，尾部追加均摊 O(1)，扩容要复制；`LinkedList` 是双向链表，按下标访问 O(n)，每个元素还有节点对象开销。
>
> **容易踩坑：** 只看“大 O”就认定链表插入快，忽略找到插入位置、缓存局部性和额外对象分配；并发下两者都不是线程安全容器。
>
> **适用场景：** 查询和遍历为主用 `ArrayList`；真正的队列/双端队列通常直接用 `ArrayDeque`，并发队列用 JUC 提供的实现。

### Q009：`HashMap` 在 Java 8 里的结构和扩容过程是什么？

> **结论：** Java 8 的 `HashMap` 是数组加链表或红黑树，平均查询接近 O(1)，但它不保证线程安全。
>
> **机制：** key 的 hash 经过扰动后定位桶；冲突先挂链表，链表长度达到阈值且数组容量足够才树化。容量通常按 2 的幂扩张，迁移时节点根据旧容量对应 bit 分到原位置或原位置加旧容量。
>
> **容易踩坑：** 初始容量设置不当会频繁扩容；差的 `hashCode()` 会造成严重冲突；并发读写可能丢更新或看到不一致状态。
>
> **适用场景：** 单线程或外部已同步的键值存储；已知数据量时按负载因子预估容量，作为 key 的对象要稳定且正确实现 equals/hashCode。

### Q010：【丰泊实问】`HashMap` 和 `ConcurrentHashMap` 有什么区别？Java 8 怎么保证并发安全？

> **结论：** `HashMap` 不支持并发写；`ConcurrentHashMap` 支持高并发访问，并提供 `putIfAbsent`、`compute` 等原子复合操作，但容器安全不等于整段业务逻辑原子。
>
> **机制：** Java 8 不再用早期 Segment。空桶插入主要用 CAS，桶内冲突时锁桶头节点；读依赖 volatile 可见性，扩容时多个线程可以协助迁移。
>
> **容易踩坑：** 先 `containsKey()` 再 `put()` 仍有竞态，应使用原子 API；它不允许 null key/value，是为了避免并发读取时无法区分“没值”和“值为 null”。
>
> **适用场景：** 进程内共享缓存、计数和注册表；跨进程一致性不能靠它，仍需数据库、Redis 或分布式协调。

### Q011：`CopyOnWriteArrayList` 为什么读快写慢？

> **结论：** 它通过“写时复制”让读操作基本无锁，适合读远多于写、数据量不大的场景，不适合高频更新。
>
> **机制：** 写操作加锁并复制底层数组，修改完成后用新数组替换；读线程持有旧快照也能稳定遍历，因此迭代器看到的是快照。
>
> **容易踩坑：** 每次写都复制数组，数据大或写频繁时 CPU 和内存开销很高；迭代期间看不到刚发生的更新，不能用于要求强实时视图的逻辑。
>
> **适用场景：** 监听器列表、配置订阅者这类少写多读集合；普通生产消费队列应选阻塞队列或并发队列。

### Q012：什么是 fail-fast？它能保证并发安全吗？

> **结论：** fail-fast 只是迭代器发现集合结构可能被意外修改后尽快抛 `ConcurrentModificationException`，它不是线程安全保证。
>
> **机制：** 迭代器记录预期修改次数，遍历时与集合当前修改次数比较；不一致时抛异常。这是尽力检测，不是并发协议。
>
> **容易踩坑：** 在增强 for 里直接调用集合 `remove()`；以为没有抛异常就说明并发访问正确；`Collections.synchronizedList` 迭代时仍需要在外部持锁。
>
> **适用场景：** 单线程遍历时要删除元素，用迭代器自己的 `remove()`；并发遍历则选合适的并发容器或快照方案。

## 2. JMM、JUC 与线程池

### Q013：JMM 主要解决什么问题？

> **结论：** Java 内存模型主要定义多线程之间的可见性、有序性和 happens-before 规则，不是 JVM 内存区域那张图。
>
> **机制：** 每个线程可能使用寄存器和缓存，编译器与 CPU 也会重排；JMM 规定锁、volatile、线程启动/结束等操作之间的可见和排序关系。
>
> **容易踩坑：** 只要代码在单线程看起来有顺序，就以为并发也能看到同样顺序；把“原子性、可见性、有序性”混成一件事。
>
> **适用场景：** 双重检查、状态发布、停止标志和无锁算法，都要用 happens-before 证明正确，不能靠压测没出错来证明。

### Q014：`volatile` 能保证什么，不能保证什么？

> **结论：** `volatile` 保证对该变量的写对后续读可见，并提供一定的有序性，但对 `count++` 这种复合操作不保证原子。
>
> **机制：** volatile 读写建立 happens-before，并通过内存屏障限制相关重排；线程读取时会看到较新的值。
>
> **容易踩坑：** 用 volatile 做多线程计数、依赖多个 volatile 字段保持联合不变量、以为它能替代锁保护临界区。
>
> **适用场景：** 单一状态标志、配置快照引用和一个线程写多个线程读；复合更新用锁、原子类或更高层并发结构。

### Q015：`synchronized` 锁的是什么？和 `volatile` 怎么选？

> **结论：** `synchronized` 既保证互斥，也保证进入和退出临界区的可见性；需要保护一组状态或复合操作时用锁，只需要发布单一状态时才考虑 volatile。
>
> **机制：** 实例同步方法锁当前对象，静态同步方法锁 Class 对象，同步块锁显式对象；锁释放 happens-before 后续对同一锁的获取。
>
> **容易踩坑：** 锁了不同对象却以为互斥；把可变字符串、装箱数字当锁对象；临界区里做慢 IO，导致锁持有时间过长。
>
> **适用场景：** 余额与流水一起更新、集合多步修改这类联合不变量；锁范围要小，但不能小到破坏原子边界。

### Q016：【丰泊实问】什么是可重入锁？`ReentrantLock` 比 `synchronized` 多什么？

> **结论：** 可重入表示同一线程持锁后还能再次获取同一把锁；`ReentrantLock` 适合需要可中断、超时、公平策略或多个条件队列的场景。
>
> **机制：** 锁记录 owner 和重入次数，同一线程每获取一次计数加一，释放到零才真正交出锁。`ReentrantLock` 通过 AQS 实现独占获取。
>
> **容易踩坑：** 忘记在 `finally` 中 `unlock()` 会永久占锁；公平锁吞吐通常更低；可重入只解决自我死锁，不解决不同锁之间的循环等待。
>
> **适用场景：** 需要 `tryLock(timeout)`、响应中断或多个 `Condition` 时选它；普通短临界区优先可读性更好的 `synchronized`。

### Q017：【丰泊实问】AQS 是什么？为什么很多 JUC 同步器都基于它？

> **结论：** AQS 是同步器框架，用一个 state 加一个等待队列，把“抢不到就排队、释放后唤醒”的通用逻辑封装起来。
>
> **机制：** 子类通过 CAS 读写 volatile state，定义独占或共享获取规则；竞争失败的线程进入 FIFO 风格的 CLH 变体队列并 park，条件满足后再 unpark。
>
> **容易踩坑：** 把 AQS 说成一把具体锁；认为队列绝对严格公平；忽略取消、超时和中断节点的清理。
>
> **适用场景：** `ReentrantLock`、`Semaphore`、`CountDownLatch` 等都复用了它；业务代码一般使用这些成熟同步器，不直接造 AQS 子类。

### Q018：CAS 有什么优点？ABA 问题怎么处理？

> **结论：** CAS 通过比较旧值并原子替换实现无锁更新，低竞争下很高效；但竞争激烈时会自旋浪费 CPU，还可能出现 ABA。
>
> **机制：** ABA 是值从 A 变 B 又变回 A，CAS 只看当前值会误以为没变化。可以给值附版本号，用 `AtomicStampedReference`，或改用不依赖历史身份的算法。
>
> **容易踩坑：** CAS 只保护一个变量，不能天然维护多个字段的一致性；无限自旋会放大热点；“无锁”不代表没有内存屏障或绝对更快。
>
> **适用场景：** 原子计数、状态位和短小更新；高竞争计数可以用 `LongAdder`，复杂业务状态更适合锁或数据库条件更新。

### Q019：【丰泊实问】`ThreadLocal` 是什么？在线程池里为什么危险？

> **结论：** `ThreadLocal` 给每个线程保存独立值，它解决线程隔离，不是把共享对象变安全；线程池复用线程时必须在 `finally` 中清理。
>
> **机制：** 每个 Thread 内部持有 `ThreadLocalMap`，key 是弱引用、value 是强引用。key 被回收后，value 仍可能跟长寿命线程一起存活。
>
> **容易踩坑：** 忘记 `remove()` 会造成内存泄漏和请求上下文串号；切到异步线程后上下文不会自动传播；`InheritableThreadLocal` 也不适合直接解决线程池传播。
>
> **适用场景：** traceId、租户和事务上下文通常由框架管理；业务能显式传参就显式传，确实使用时要统一入口设置、出口清理。

### Q020：线程的 `interrupt()` 是强制停止吗？

> **结论：** 不是。中断是协作式取消信号，线程是否退出取决于代码有没有检查中断状态或响应 `InterruptedException`。
>
> **机制：** 阻塞方法可能清除中断标记并抛异常；捕获后如果不能处理，通常要恢复标记 `Thread.currentThread().interrupt()` 或向上抛。
>
> **容易踩坑：** catch 后什么都不做会吞掉取消；用废弃的 `Thread.stop()` 强停可能破坏共享状态；长 CPU 循环不检查标记就无法及时取消。
>
> **适用场景：** 服务关闭、超时任务和批处理取消；取消之外仍要设计资源释放、幂等和外部副作用补偿。

### Q021：`CompletableFuture` 适合解决什么问题？

> **结论：** 它适合组合多个异步任务、表达依赖和汇总结果，但不会自动让阻塞代码变快，也不能代替完整任务系统。
>
> **机制：** `thenApply` 转换结果，`thenCompose` 串联异步任务，`thenCombine` 合并两个结果，`allOf` 等待一组任务；异步方法未指定 Executor 时可能进入公共 ForkJoinPool。
>
> **容易踩坑：** 在公共池里跑阻塞 IO、忘记异常链、`join()` 到处阻塞、超时后只停止等待却没有取消底层调用。
>
> **适用场景：** 同一请求内并行调用独立下游；跨进程长任务、可靠重试和断点恢复应交给 MQ 或工作流系统。

### Q022：线程池七个核心参数分别控制什么？

> **结论：** 面试时我会按执行顺序讲：核心线程、最大线程、空闲存活时间、时间单位、工作队列、线程工厂和拒绝策略共同决定池如何接任务和过载。
>
> **机制：** 新任务先建核心线程；核心满后入队；队列满才扩到最大线程；再满触发拒绝。无界队列通常意味着最大线程数形同虚设。
>
> **容易踩坑：** 直接用 `Executors.newFixedThreadPool` 的无界队列导致内存堆积，或 cached pool 的线程数无界导致线程耗尽；线程工厂不命名也会增加排障难度。
>
> **适用场景：** 生产池应显式配置有界队列、命名线程、拒绝策略和监控，并把不同延迟与资源特征的任务隔离到不同池。

### Q023：`execute()` 和 `submit()` 有什么区别？

> **结论：** `execute()` 接收 Runnable，没有返回结果；`submit()` 返回 Future，可以拿结果和异常，但异常可能被包装后延迟到 `get()` 才看到。
>
> **机制：** submit 通常把任务包装成 FutureTask；任务异常被记录在 Future 中，不一定走线程的 UncaughtExceptionHandler。
>
> **容易踩坑：** submit 后从不检查 Future，任务其实失败了但日志没有明显异常；在同一个小线程池里提交子任务后同步 `get()`，可能造成线程饥饿死锁。
>
> **适用场景：** 只触发且统一捕获异常可用 execute；需要结果、取消和超时用 submit，但必须消费 Future 或集中处理完成结果。

### Q024：四种拒绝策略怎么选？

> **结论：** 拒绝策略不是最后随便填一个参数，它决定系统过载时丢任务、让调用方背压还是直接失败。
>
> **机制：** AbortPolicy 抛异常；CallerRuns 由提交线程执行形成背压；Discard 丢当前任务；DiscardOldest 丢队首后重试。也可以自定义记录和降级。
>
> **容易踩坑：** 静默丢任务不告警；在 Web 请求线程使用 CallerRuns 后把接口拖死；拒绝后无业务补偿却仍返回成功。
>
> **适用场景：** 关键任务通常快速失败或可靠落 MQ；允许降采样的非关键日志可丢，但要有指标；选择前先明确任务能不能丢。

### Q025：线程池大小怎么估算？

> **结论：** 没有一个固定公式能替代压测。CPU 密集型接近核数，IO 密集型可以更多，但最终要受下游容量、连接池和延迟目标约束。
>
> **机制：** IO 等待比例越高，理论上可容纳更多线程；线程过多会增加上下文切换、栈内存和下游并发压力。
>
> **容易踩坑：** 只按 CPU 核数算，不看数据库连接池；把线程池调大掩盖慢 SQL；不同任务共享一个池造成相互拖垮。
>
> **适用场景：** 先测单任务 CPU/等待时间，再设置有界队列和并发上限，通过活跃线程、队列长度、拒绝数和下游 P95 持续调整。

### Q026：死锁的四个必要条件是什么？怎么在线上定位？

> **结论：** 互斥、持有并等待、不可剥夺和循环等待同时成立才会死锁；工程上最有效的是固定加锁顺序并缩小锁范围。
>
> **机制：** 两个线程分别持有一把锁又等待对方，形成等待环。`jstack`、`jcmd Thread.print` 或监控平台的线程 dump 可以看到 BLOCKED 线程和锁拥有者。
>
> **容易踩坑：** 只重启不保留 dump；把数据库死锁和 JVM monitor 死锁混为一谈；为了避免死锁给所有路径加一把大锁，吞吐反而崩掉。
>
> **适用场景：** 多资源更新使用全局顺序，必要时 `tryLock` 加超时；数据库事务也要统一访问表和行的顺序。

## 3. JVM、类加载与 GC

### Q027：JVM 运行时数据区怎么划分？

> **结论：** 线程私有的主要有程序计数器、虚拟机栈和本地方法栈；线程共享的主要有堆和方法区的实现元空间。直接内存不属于运行时数据区，但同样可能 OOM。
>
> **机制：** 堆放大多数对象，栈帧保存局部变量、操作数栈和返回信息，元空间放类元数据并使用本地内存。
>
> **容易踩坑：** 把“对象一定都在堆上”说死，JIT 可能通过逃逸分析做标量替换；把元空间和字符串常量池位置混成旧版本结论。
>
> **适用场景：** 排查 OOM 先区分 heap、metaspace、direct buffer、native thread 还是 stack，而不是一律调大 `-Xmx`。

### Q028：类加载的生命周期和双亲委派是什么？

> **结论：** 类通常经历加载、验证、准备、解析、初始化和使用卸载；双亲委派优先让父加载器加载，避免核心类被重复或恶意替换。
>
> **机制：** 加载器先向父级请求，父级找不到才自己加载；类的身份由“全限定名加类加载器”共同决定。
>
> **容易踩坑：** 以为所有框架都严格遵守双亲委派，SPI、Tomcat 和热部署会有有意打破或调整；同名类由不同加载器加载后不能互相强转。
>
> **适用场景：** 插件、容器隔离、热部署和依赖冲突排查；业务代码一般不要自己随意创建类加载器。

### Q029：对象从创建到分配内存大致经历什么？

> **结论：** JVM 先确认类已加载，再在堆上分配空间、初始化零值和对象头，执行构造逻辑，最后返回引用；常见小对象会优先在 TLAB 中快速分配。
>
> **机制：** 多线程共享 Eden 时可以用 CAS 分配，TLAB 则给每个线程一小块私有分配区，减少竞争。是否逃逸还会影响 JIT 优化。
>
> **容易踩坑：** 把“new 一定是昂贵系统调用”说死；只关心分配速度不关心对象存活时间；创建大量临时大对象会直接增加 GC 压力。
>
> **适用场景：** 高频序列化、批量查询和大集合处理要关注分配率；优化前先看 JFR 或 GC 日志，不凭感觉做对象池。

### Q030：哪些对象可以作为 GC Roots？可达性分析怎么判断垃圾？

> **结论：** GC 从一组根对象出发遍历引用图，不可达对象才有资格回收；常见根包括活动线程栈引用、静态字段、JNI 引用和 JVM 内部引用。
>
> **机制：** 可达性分析解决循环引用无法靠引用计数回收的问题。不同引用类型还会影响回收时机，例如弱引用通常在下一次 GC 被清理。
>
> **容易踩坑：** 对象“业务上不用了”但仍被静态集合、ThreadLocal、监听器或缓存引用，就仍然可达；手动设 null 也不一定有意义。
>
> **适用场景：** 内存泄漏排查要从 heap dump 的 GC Root 路径找谁在持有对象，而不是只看哪个类实例最多。

### Q031：为什么要分代回收？对象一定会从年轻代晋升吗？

> **结论：** 分代是基于“大多数对象朝生夕死、少量对象长期存活”的经验，把不同生命周期对象用不同策略回收；但大对象或特殊配置下可能直接进入老年代。
>
> **机制：** 新对象通常进入 Eden，Young GC 后存活对象在 Survivor 之间复制并增加年龄，达到阈值或 Survivor 放不下时晋升；动态年龄判断也会影响晋升。
>
> **容易踩坑：** 把年龄阈值说成永远固定 15；忽略大对象、晋升担保和不同收集器的差异；为了减少 Young GC 盲目把年轻代调得很大，反而增加停顿。
>
> **适用场景：** 观察分配率、对象年龄和晋升速率，再判断是短命对象过多、缓存活太久还是堆布局不合理。

### Q032：【丰泊实问】Minor GC、Major GC 和 Full GC 怎么区分？

> **结论：** Minor 或 Young GC 主要回收年轻代；Full GC 通常处理整个堆并可能带上元空间，停顿更重。Major GC 在不同资料里含义不统一，回答时要先限定收集器。
>
> **机制：** 以 G1 为例，更准确的术语是 Young GC、Mixed GC 和 Full GC；Mixed 会回收年轻代加部分老年代 Region，不等于 Full GC。
>
> **容易踩坑：** 说 Minor GC 完全不停顿；把 Mixed GC 当 Full GC；背触发条件却不结合收集器和日志中的真正 cause。
>
> **适用场景：** 面试先说通用概念，排障时直接依据 GC 日志中的 collector、cause、停顿阶段和回收前后占用判断。

### Q033：G1 的 Region、Remembered Set 和 Mixed GC 是什么？

> **结论：** G1 把堆切成多个 Region，按收益优先回收垃圾多的区域，目标是对停顿时间做更可控的预测，而不是保证绝不超时。
>
> **机制：** Region 动态扮演 Eden、Survivor、Old 或 Humongous；Remembered Set 记录跨 Region 引用，避免每次扫描全堆；并发标记后选择部分老年代 Region 做 Mixed GC。
>
> **容易踩坑：** 认为 G1 没有 STW；Humongous 对象会占连续 Region 并带来碎片；把 `MaxGCPauseMillis` 当硬 SLA。
>
> **适用场景：** 中大堆、希望在吞吐与停顿之间平衡的服务；调优仍要看分配、晋升、并发标记是否来得及和 Mixed 回收效果。

### Q034：什么时候会考虑 ZGC，而不是继续调 G1？

> **结论：** 当堆较大且低停顿比极限吞吐更重要时，可以评估 ZGC；不能因为它“低停顿”就直接替换并宣称一定更快。
>
> **机制：** ZGC 把大量标记、转移工作并发化，通过染色指针、加载屏障等机制降低 STW，现代 JDK 版本还在持续演进分代能力。
>
> **容易踩坑：** 忽略 JDK 版本、CPU 开销和应用分配特征；只看平均停顿，不看尾延迟、吞吐和内存余量；迁移后不做压测。
>
> **适用场景：** 延迟敏感且堆较大的服务做同负载 A/B；普通堆和吞吐型任务先把代码分配问题、堆容量和 G1 配置查清。

### Q035：常见 OOM 和 `StackOverflowError` 分别怎么产生？

> **结论：** Heap OOM、Metaspace OOM、Direct Buffer OOM、无法创建 native thread 等原因不同；StackOverflow 通常是递归过深或栈帧过大，不能都靠调大堆解决。
>
> **机制：** 堆对象无法回收或容量不足会 heap OOM；类加载器泄漏会撑满元空间；堆外缓冲未释放会耗尽直接内存；线程数过多会耗尽本地内存。
>
> **容易踩坑：** 一看到 OOM 就重启和加 `-Xmx`，丢失现场；heap dump 本身可能占磁盘；线程 OOM 时堆看起来还很空。
>
> **适用场景：** 预先配置 OOM dump、错误退出和告警；根据错误类型分别抓 heap、NMT、线程数、类加载和 direct buffer 证据。

### Q036：GC 频繁或停顿变长，排查顺序是什么？

> **结论：** 我会先确认是分配过快、存活集变大、堆配置不合理，还是收集器退化，而不是第一步就改 GC 参数。
>
> **机制：** 结合 GC 日志看频率、cause、各代回收前后、晋升、并发周期和停顿阶段；再用 JFR、heap histogram 或 dump 找分配热点与保留对象。
>
> **容易踩坑：** 只看一次 Full GC；线上随意 `jmap -dump` 造成更大停顿；忽略容器内存限制、直接内存和系统 swap。
>
> **适用场景：** 先保留日志和时间线，对齐发布、流量和配置变化；确认根因后才在压测环境调整堆、收集器或代码。

## 4. Spring、AOP 与事务

### Q037：IoC 和 DI 是一回事吗？Spring 容器到底做了什么？

> **结论：** IoC 是控制权从业务代码转给容器的设计思想，DI 是实现 IoC 的主要方式；Spring 负责 Bean 定义、创建、依赖解析、生命周期和扩展点调用。
>
> **机制：** 配置类、组件扫描等先形成 BeanDefinition，BeanFactory 再按依赖关系实例化 Bean，并经过各种 PostProcessor 完成注入、代理和初始化。
>
> **容易踩坑：** 把容器当全局 Service Locator，到处主动 `getBean()`；构造器里做慢 IO；依赖关系不清导致循环依赖和启动变慢。
>
> **适用场景：** 业务组件、基础设施适配和策略实现由容器装配；领域核心仍保持普通 Java 对象，降低框架侵入。

### Q038：【丰泊实问】`@Autowired` 和 `@Resource` 有什么区别，底层谁处理？

> **结论：** `@Autowired` 是 Spring 注解，默认按类型解析；`@Resource` 来自 Jakarta/JSR-250，常见语义是先按名称，再回退类型。实际优先推荐构造器注入。
>
> **机制：** 前者主要由 `AutowiredAnnotationBeanPostProcessor` 处理，后者主要由 `CommonAnnotationBeanPostProcessor` 处理，最终都向 BeanFactory 解析候选 Bean。
>
> **容易踩坑：** 同类型多个实现时不消歧；把字段名碰巧匹配当稳定契约；只背“一个按类型一个按名称”，忽略 `@Qualifier`、`@Primary` 和显式 name。
>
> **适用场景：** 默认用单构造器注入；确实按名称选择时用明确的 `@Qualifier` 或 `@Resource(name=...)`。

### Q039：为什么推荐构造器注入，不推荐字段注入？

> **结论：** 构造器注入让依赖显式、支持 `final`、便于单测，也能在对象创建时保证必需依赖齐全。
>
> **机制：** Spring 解析构造参数后再创建实例；单构造器通常无需写 `@Autowired`。字段注入则在实例化后通过反射填充。
>
> **容易踩坑：** 构造参数太多往往暴露类职责过重，不能靠字段注入把问题藏起来；可选依赖也不应滥用 null。
>
> **适用场景：** 必需依赖全部走构造器；真正可选或为打破特定初始化环的依赖要重新审视设计，必要时使用 provider/lazy。

### Q040：Spring Bean 生命周期怎么讲才完整？

> **结论：** 我会按“BeanDefinition、实例化、属性填充、Aware、前置处理、初始化、后置处理、使用、销毁”这条线讲，代理通常由后置处理器创建。
>
> **机制：** 初始化阶段可能执行 `@PostConstruct`、`InitializingBean`、自定义 init method；关闭容器时执行 `@PreDestroy`、`DisposableBean` 或 destroy method。
>
> **容易踩坑：** 以为构造函数执行时依赖已经全部注入；prototype Bean 的销毁不由容器完整管理；初始化里做长任务拖慢启动。
>
> **适用场景：** 连接和资源在专门生命周期组件中管理；启动预热要可超时、可失败并能从 readiness 状态反映。

### Q041：Spring Bean 有哪些常见作用域？Singleton 就线程安全吗？

> **结论：** 默认 singleton 表示每个容器一个实例，不表示线程安全；Web 中还有 request、session 等作用域，prototype 每次获取创建新对象。
>
> **机制：** singleton Bean 被多个请求线程共享，所以无状态 Service 最安全；可变状态若放成员字段就需要并发控制。
>
> **容易踩坑：** 把用户、请求参数或中间 List 放进 singleton 字段；prototype 注入 singleton 后误以为每次调用都会新建；滥用 session scope 增加内存和集群会话问题。
>
> **适用场景：** Service 尽量无状态，状态放参数、数据库或明确的上下文；有生命周期要求时再选特殊 scope。

### Q042：Spring 循环依赖为什么有时能解决、有时不能？

> **结论：** 历史上单例属性注入的部分循环依赖可通过提前暴露引用解决，但构造器循环、prototype 循环通常不行；设计上仍应消除循环。
>
> **机制：** 三级缓存用于保存完整单例、早期引用和生成早期引用的工厂，以便 AOP 场景尽量拿到一致代理。
>
> **容易踩坑：** 把“Spring 能解决循环依赖”说成所有情况；依赖配置项允许循环也只是掩盖职责纠缠；早期引用和代理可能带来复杂行为。
>
> **适用场景：** 通过拆职责、引入领域事件或中介服务解除环；`@Lazy` 只能作为临时缓解，不应成为默认设计。

### Q043：Spring AOP 的核心机制是什么？它能拦截私有方法吗？

> **结论：** Spring AOP 主要通过代理拦截 Bean 方法调用，适合事务、日志、鉴权等横切逻辑；私有方法和绕过代理的调用通常拦不到。
>
> **机制：** 容器在 BeanPostProcessor 阶段根据 Advisor 创建 JDK 动态代理或 CGLIB 子类代理，调用进入拦截器链后再到目标方法。
>
> **容易踩坑：** 同类 `this.method()` 自调用绕过代理；final 类或 final 方法限制子类代理；切点过宽导致所有请求额外开销和意外行为。
>
> **适用场景：** 稳定横切关注点适合 AOP；核心业务流程最好显式调用，避免隐藏控制流让调试困难。

### Q044：JDK 动态代理和 CGLIB 有什么区别？

> **结论：** JDK 代理基于接口，代理对象实现同一接口；CGLIB 通过生成目标类子类覆盖方法，适合没有接口的类。
>
> **机制：** JDK 调用由 InvocationHandler 转发；CGLIB 依靠字节码生成和 MethodInterceptor。现代 Spring 会按配置和目标类型选择。
>
> **容易踩坑：** CGLIB 不能覆盖 final 方法，private 方法也不参与；强转代理为具体实现类在 JDK 代理下会失败；把性能差异当主要选型依据通常没有意义。
>
> **适用场景：** 业务优先面向接口；没有接口时可用类代理，但更重要的是确认调用是否经过容器代理。

### Q045：`@Transactional` 底层是怎么工作的？

> **结论：** 声明式事务本质是代理在方法前后开启、提交或回滚事务，把数据库连接绑定到当前执行上下文；注解本身不会直接修改数据库行为。
>
> **机制：** 事务拦截器根据 TransactionAttribute 选择事务管理器，获取连接、设置隔离级别和传播行为，目标方法正常结束提交，符合回滚规则的异常则回滚。
>
> **容易踩坑：** 自调用、非 Spring 管理对象、方法不可代理会导致注解失效；异步切线程后事务上下文不会自动跟过去；事务里调慢接口会长期占连接和锁。
>
> **适用场景：** 事务边界放在 Service 的完整业务原子操作上，外部网络调用尽量移出数据库事务，必要时用 Outbox 衔接。

### Q046：【丰泊实问】Spring 七种事务传播行为主要解决什么？

> **结论：** 它解决“一个事务方法调用另一个事务方法时，内层要加入、另开、挂起还是禁止事务”。默认 `REQUIRED`，不是七个都要在业务里使用。
>
> **机制：** `REQUIRES_NEW` 挂起外层并独立提交；`NESTED` 通常基于 savepoint 局部回滚；`SUPPORTS`、`NOT_SUPPORTED`、`MANDATORY`、`NEVER` 分别表达可选、禁用或强制边界。
>
> **容易踩坑：** 把 `NESTED` 和 `REQUIRES_NEW` 混淆；内层事务通过自调用而未经过代理；外层捕获异常后继续提交，造成与预期不符。
>
> **适用场景：** 普通业务写用 REQUIRED；真正独立的审计可评估 REQUIRES_NEW，但要注意额外连接和“主业务回滚、审计已提交”的语义。

### Q047：Spring 事务隔离级别和数据库隔离级别是什么关系？

> **结论：** Spring 只是把隔离级别请求交给底层数据库连接，最终语义由数据库和存储引擎实现；`DEFAULT` 表示沿用数据库默认值。
>
> **机制：** 常见等级从 Read Uncommitted 到 Serializable，逐步约束脏读、不可重复读和幻读，但实现可以是锁、MVCC 或组合。
>
> **容易踩坑：** 认为提高隔离级别就免费获得正确性；不同数据库对 Repeatable Read 的幻读处理不同；连接池复用时要由框架正确恢复连接状态。
>
> **适用场景：** 先用业务唯一约束和条件更新保证关键不变量，再按一致性需求选择隔离级别，而不是所有事务都 Serializable。

### Q048：哪些情况会导致事务没有回滚？

> **结论：** 常见原因是没有经过代理、异常被吞、异常类型不符合回滚规则、事务管理器选错，或真正的副作用根本不在同一数据库事务里。
>
> **机制：** Spring 默认对 RuntimeException 和 Error 回滚；checked exception 需要配置 `rollbackFor`。代理只能控制它拿到的连接和资源。
>
> **容易踩坑：** catch 后返回成功；同类私有方法加注解；多数据源却只开启一个事务管理器；数据库提交后发消息失败却误以为能一起回滚。
>
> **适用场景：** 测试要验证提交和回滚结果；跨资源一致性使用 Outbox、可靠消息或分布式事务方案，不靠一个注解幻想原子性。

### Q049：Spring MVC 一次请求的执行链路是什么？

> **结论：** 请求先经过容器 Filter，再到 DispatcherServlet，匹配 Handler、执行拦截器和 Controller，返回值经消息转换后写回响应，异常由 HandlerExceptionResolver 处理。
>
> **机制：** HandlerMapping 找方法，HandlerAdapter 负责参数解析和调用，HttpMessageConverter 做 JSON 等序列化，ViewResolver 只在视图渲染模式需要。
>
> **容易踩坑：** 混淆 Filter、Interceptor 和 AOP 的层级；在 Controller 做大量业务和事务；异常响应返回 200 加错误文本，破坏协议语义。
>
> **适用场景：** Filter 处理跨框架请求事项，Interceptor 做登录和审计上下文，业务逻辑下沉 Service，统一异常处理器输出稳定错误结构。

### Q050：Spring Boot 自动配置为什么能“开箱即用”？

> **结论：** 自动配置是根据 classpath、已有 Bean、配置属性等条件，有选择地注册默认 Bean；它不是扫描到依赖就无条件创建一切。
>
> **机制：** 自动配置类通过导入机制加载，配合 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConfigurationProperties` 等决定是否生效。
>
> **容易踩坑：** 不看 Condition Evaluation Report 就猜 Bean 为什么没创建；自定义 Bean 与默认配置冲突；升级 Boot 后依赖和属性行为变化却没有回归测试。
>
> **适用场景：** 标准基础设施交给 Starter 和自动配置；关键参数显式配置并做启动校验，必要时排除不需要的自动配置。

## 5. MyBatis 与数据访问

### Q051：MyBatis 的 `#{}` 和 `${}` 有什么区别？

> **结论：** `#{}` 使用预编译参数，默认安全；`${}` 是字符串直接替换，有 SQL 注入风险，只能用于经过严格白名单的表名、列名等结构位置。
>
> **机制：** `#{}` 生成 `?` 并由 PreparedStatement 绑定类型；`${}` 在 SQL 生成阶段直接拼文本。
>
> **容易踩坑：** 排序字段、动态表名直接接收用户输入后用 `${}`；误以为 PreparedStatement 能参数化列名；模糊查询手工拼引号。
>
> **适用场景：** 业务值一律 `#{}`；不可参数化的结构只能从服务端枚举映射，绝不原样拼接前端字符串。

### Q052：MyBatis 一级缓存和二级缓存分别是什么？

> **结论：** 一级缓存默认是 SqlSession 级；二级缓存是 Mapper namespace 级且需要配置。生产里不能把它们当成通用一致性缓存。
>
> **机制：** 同一 SqlSession 相同查询可能复用本地结果，更新或提交会清理相关缓存；二级缓存跨 Session，但要求对象序列化和明确失效策略。
>
> **容易踩坑：** 多表查询后另一个 Mapper 更新，二级缓存可能不知道该失效；Spring 管理下 SqlSession 生命周期让开发者对一级缓存范围产生误解。
>
> **适用场景：** 默认依赖数据库和明确的业务缓存；二级缓存只在读多写少、失效边界清楚时评估。

### Q053：MyBatis 怎么避免 N+1 查询？

> **结论：** 列表页先查 N 条主记录，再为每条查一次关联数据就是 N+1；应按结果规模选择 join、批量 `IN`、分两段批查或专用聚合查询。
>
> **机制：** ResultMap 的 association/collection 可以嵌套查询，也可以映射 join 结果；懒加载只是推迟查询，不等于消除 N+1。
>
> **容易踩坑：** 一对多 join 导致主记录重复和分页错乱；超大 `IN` 列表；序列化阶段触发懒加载，让 SQL 在意外位置爆发。
>
> **适用场景：** 列表先分页主键，再批量加载关联；详情页数据量小可 join；通过 SQL 日志和测试断言查询次数。

### Q054：【丰泊实问】MyBatis-Plus Lambda 怎么统计年龄大于 20 且性别为男的学生数？

> **结论：** 我会用类型安全的 LambdaQueryWrapper，并让数据库直接 `count`，不先查列表再在 Java 里取 size。
>
> **机制：** 核心写法是 `Wrappers.<Student>lambdaQuery().gt(Student::getAge, 20).eq(Student::getGender, Gender.MALE)`，再传给 `selectCount`。
>
> **容易踩坑：** 忘记泛型导致方法引用推断失败；性别字段实际是编码却直接传枚举；把可空条件无脑拼进去；逻辑删除条件是否自动生效要核对配置。
>
> **适用场景：** 简单单表动态条件适合 Wrapper；复杂 join、窗口函数和关键性能 SQL 应写清晰 XML/注解 SQL 并做执行计划验证。

### Q055：分页插件能自动解决深分页吗？

> **结论：** 不能。插件只是生成 limit/offset 和 count SQL，offset 很大时数据库仍要扫描并丢弃大量记录。
>
> **机制：** 深分页可以改成基于稳定排序键的 seek/keyset pagination，例如 `id > lastId order by id limit n`；复杂查询的 count 也可能成为瓶颈。
>
> **容易踩坑：** 排序字段不唯一导致翻页重复或漏数；分页期间数据变化造成漂移；插件自动 count 包装复杂 SQL 后执行计划很差。
>
> **适用场景：** 后台跳页可接受普通分页；时间线、流水和大表接口优先游标分页，并给排序字段建匹配索引。

### Q056：MyBatis 批量插入和逐条循环插入有什么差别？

> **结论：** 真正批量要减少网络往返和提交次数；Java 循环调用单条 insert 即使写在一个事务里，也不等于一条批量 SQL。
>
> **机制：** 可以使用多 values SQL、JDBC batch 或 MyBatis BATCH executor，按数据库参数和包大小分块提交。
>
> **容易踩坑：** 一次拼几万行 SQL 超过参数/报文限制；批处理中间失败后不知道哪条成功；自动生成主键和错误定位更复杂。
>
> **适用场景：** 离线导入和补数按固定批大小处理，记录批次与失败明细；在线请求不应为了批量长期占用大事务。

## 6. MySQL、InnoDB、索引与锁

### Q057：为什么业务表通常选 InnoDB？

> **结论：** InnoDB 提供事务、行级锁、崩溃恢复、MVCC 和外键等能力，是 MySQL 事务业务的默认选择。
>
> **机制：** 聚簇索引组织数据，redo log 保证已提交修改可恢复，undo 支持回滚和 MVCC，buffer pool 缓存数据页。
>
> **容易踩坑：** “行锁”不代表任何 update 都只锁一行，缺索引可能扫描并锁大量记录；事务能力也不能自动解决业务幂等和跨服务一致性。
>
> **适用场景：** 订单、支付、状态机和普通 OLTP；分析型大扫描要评估专用数仓或只读副本，避免拖垮主库。

### Q058：MySQL 索引为什么常用 B+Tree，不用普通二叉树或 Hash？

> **结论：** B+Tree 分支多、树高低、节点按页组织，适合磁盘随机 IO，也天然支持范围和有序扫描；Hash 更适合等值，不支持范围和顺序。
>
> **机制：** 非叶节点主要存键和子页指针，叶节点有序并相连；一次页读取能容纳很多 key，所以几层就能覆盖大量记录。
>
> **容易踩坑：** 说查询永远 O(logN) 就忽略回表、范围行数和缓存命中；索引越多写入维护越贵；低选择性字段单独索引未必有收益。
>
> **适用场景：** 等值、范围、排序和前缀匹配；索引设计要从真实 SQL 的过滤、连接和排序组合出发。

### Q059：聚簇索引和二级索引怎么查到一行数据？

> **结论：** InnoDB 聚簇索引叶子存整行，通常以主键组织；二级索引叶子存索引列加主键，查非覆盖列时要再回主键索引。
>
> **机制：** 二级索引先定位主键，再回表取整行；如果查询列都在二级索引中，就可以覆盖索引直接返回。
>
> **容易踩坑：** 主键过长会放大所有二级索引；随机 UUID 可能造成页分裂和局部性差；`select *` 让本可覆盖的查询被迫回表。
>
> **适用场景：** 选择短、稳定、尽量递增的主键；高频列表接口只取必要列，评估覆盖索引。

### Q060：联合索引的最左前缀原则怎么理解？

> **结论：** 联合索引按列顺序排序，查询要利用从左到右连续的有序前缀；不是 SQL 条件书写顺序必须一样，而是可用的索引顺序受谓词影响。
>
> **机制：** 等值条件通常可以继续利用后续列；遇到范围后，后续列往往不能再用于缩小扫描区间，但可能用于索引下推或覆盖。
>
> **容易踩坑：** 只按选择性机械排序，忽略真实等值、范围和 order by；重复创建可被已有联合索引覆盖的前缀索引；把 `a=? and c=?` 误认为能完整用 `(a,b,c)`。
>
> **适用场景：** 根据最常见查询组合设计 `(tenant_id, status, created_at)` 这类索引，再用 EXPLAIN 和实际数据验证。

### Q061：什么是覆盖索引和索引下推？

> **结论：** 覆盖索引是查询需要的列都能从索引返回，省掉回表；索引下推是存储引擎在扫描索引时提前判断可用条件，减少回表次数。
>
> **机制：** 二级索引包含索引列和主键，所以查询这些列时可以直接返回；ICP 则把部分 where 条件下推到 InnoDB 层过滤。
>
> **容易踩坑：** 为了覆盖把很多大字段塞进索引，导致索引膨胀和写放大；看到 Extra 里的 `Using index` 就认定查询一定快，仍要看扫描行数。
>
> **适用场景：** 高频窄查询和列表页；用真实 select 列、过滤和排序设计紧凑索引，不追求“万能联合索引”。

### Q062：哪些写法容易让索引失效或利用不充分？

> **结论：** 对索引列做函数或隐式类型转换、前导通配符、违反联合索引前缀、低选择性大范围等，都可能让优化器放弃索引或扫描很多行。
>
> **机制：** 索引保存的是原始有序值，`date(create_time)=?` 这类计算无法直接定位原值区间；字符串列与数字比较还可能触发隐式转换。
>
> **容易踩坑：** 把“用了索引”与“高效”画等号；`OR`、`IN` 是否走索引要看代价和数据分布，不能背绝对规则；参数类型和列类型不一致很隐蔽。
>
> **适用场景：** 时间查询改写为闭开区间，模糊搜索评估全文索引，所有判断最终用 EXPLAIN ANALYZE 和真实数据确认。

### Q063：看一份 `EXPLAIN` 主要看什么？

> **结论：** 我会先看访问类型、候选/实际 key、估算扫描行数、filtered 和 Extra，再结合连接顺序判断瓶颈；不能只看有没有 key。
>
> **机制：** `type` 从 const/ref/range 到 index/all 大致反映访问方式；Extra 中 filesort、temporary、index condition 等提示额外工作，但要结合数据量解释。
>
> **容易踩坑：** 估算 rows 不是实际行数；优化器选错索引可能源于统计信息过期；“Using filesort”不一定灾难，小结果集可能很便宜。
>
> **适用场景：** 慢 SQL 先拿真实参数和执行计划，条件允许使用 EXPLAIN ANALYZE 看实际耗时与行数，优化后再对比而不是凭感觉。

### Q064：InnoDB 的 MVCC 是怎么实现的？

> **结论：** MVCC 通过隐藏事务信息、undo 版本链和 Read View，让普通一致性读在不加排他锁的情况下看到符合事务视图的版本。
>
> **机制：** 记录含创建/修改事务标识，旧版本在 undo 链中；Read View 根据活跃事务集合判断某个版本对当前事务是否可见。
>
> **容易踩坑：** MVCC 不代表所有读都无锁，`select ... for update` 是当前读；长事务会让旧版本长期不能清理，undo 膨胀。
>
> **适用场景：** 高并发读写下减少读写阻塞；关键抢占和状态迁移仍使用当前读、条件更新或唯一约束。

### Q065：Read Committed 和 Repeatable Read 在 Read View 上有什么差别？

> **结论：** RC 通常每条一致性读语句创建新 Read View，所以能看到其他事务后来提交的数据；RR 通常在事务首次一致性读时建立视图并复用，保证重复读一致。
>
> **机制：** 两者都依赖版本链，可见性边界不同；InnoDB 在 RR 下还结合 next-key lock 处理当前读的幻读问题。
>
> **容易踩坑：** 把快照读和当前读混着讨论；认为 RR 下任何查询都不会出现业务竞态；长 RR 事务会保留旧版本。
>
> **适用场景：** 普通业务按数据库默认和团队规范选择；真正防并发写冲突要用锁、条件更新和约束，不只靠隔离级别。

### Q066：记录锁、间隙锁和 next-key lock 分别锁什么？

> **结论：** 记录锁锁索引记录，间隙锁锁索引值之间的范围，next-key 是记录锁加前一段间隙，主要用于范围当前读防止插入幻影。
>
> **机制：** InnoDB 锁加在索引上；是否退化为记录锁、锁住哪些间隙，取决于唯一索引等值、范围条件和隔离级别。
>
> **容易踩坑：** 没有合适索引导致扫描并锁大量记录；以为 where 只匹配一行就一定只锁一行；间隙锁之间的兼容语义与普通排他锁不同。
>
> **适用场景：** 订单抢占和范围更新要先设计索引、缩短事务，并在并发测试中观察实际锁等待。

### Q067：乐观锁和悲观锁怎么选？

> **结论：** 冲突少、允许失败重试时用版本号或条件更新的乐观锁；冲突高且必须串行处理时才考虑 `for update` 等悲观锁。
>
> **机制：** 乐观锁执行 `update ... where id=? and version=?` 并检查影响行数；悲观锁在事务中持有数据库锁直到提交或回滚。
>
> **容易踩坑：** 只给 version 加一却不带旧 version 条件，不算乐观锁；悲观锁事务里调用远程接口；乐观锁无限重试形成活锁。
>
> **适用场景：** 普通状态更新优先 CAS；库存热点要结合原子扣减、分段、排队或业务降级，而不是简单把锁模式互换。

### Q068：MySQL 发生死锁后应该怎么办？

> **结论：** InnoDB 会检测死锁并回滚其中一个事务，应用必须把死锁当作可识别的短暂失败做有限重试，同时修正访问顺序和索引。
>
> **机制：** 多事务形成行锁等待环；数据库根据代价选择 victim。可以从 `SHOW ENGINE INNODB STATUS`、performance_schema 或日志获取最近死锁图。
>
> **容易踩坑：** 只加重试不修根因；重试没有退避和上限；事务访问相同表却按不同顺序；范围扫描过大导致锁集合超预期。
>
> **适用场景：** 保留业务 key、SQL、事务顺序和锁等待证据；统一资源访问顺序，缩短事务，必要时降低单批更新行数。

### Q069：redo log、undo log 和 binlog 各解决什么？

> **结论：** redo 主要保证 InnoDB 崩溃恢复，undo 支持回滚和 MVCC，binlog 是 MySQL Server 层的逻辑变更日志，用于复制和时间点恢复。
>
> **机制：** 事务提交要协调 redo 与 binlog，常见通过两阶段提交避免一边成功一边失败；脏页可以稍后刷盘，因为 redo 能重放。
>
> **容易踩坑：** 把三者都叫“事务日志”；只备份 binlog 不做全量备份和恢复演练；binlog 已写不代表下游消费完成。
>
> **适用场景：** 数据库恢复、主从复制、CDC 和审计；业务消息仍需要 Outbox 或 CDC 设计，不能直接把数据库日志当业务契约。

### Q070：大表深分页和高成本 count 怎么优化？

> **结论：** 深分页优先改游标/seek 分页；精确 count 很贵时要明确业务是否真需要实时精确值，不能让每次列表查询都扫大范围。
>
> **机制：** 先按覆盖索引定位主键再回表，或用 `where sort_key < last_key` 延续上页；count 可以缓存、异步汇总或给近似值，但要说明一致性。
>
> **容易踩坑：** 游标排序不唯一；缓存 count 与筛选条件版本不一致；为了快返回错误总数却不告诉产品语义。
>
> **适用场景：** 流水和时间线用稳定复合游标；运营报表可离线汇总；后台小表才保留自由跳页和实时 count。

## 7. Redis 与缓存

### Q071：Redis 常用数据结构和典型场景有哪些？

> **结论：** String 做缓存和计数，Hash 存对象字段，List 做简单队列，Set 去重，ZSet 做排行榜和延迟排序；Stream、Bitmap、HyperLogLog、Geo 各有专门用途。
>
> **机制：** Redis 命令在单线程执行路径上保持单命令原子，底层编码会按元素数量和大小变化，以平衡内存和性能。
>
> **容易踩坑：** 单命令原子不等于多命令业务原子；把超大对象塞进一个 key；用 List 自制关键 MQ 却没有确认、重试和死信。
>
> **适用场景：** 先按访问模式和一致性选结构；需要可靠消息优先成熟 MQ，复杂检索和持久真相仍在数据库。

### Q072：Cache Aside 的标准读写流程是什么？

> **结论：** 常见做法是读缓存，未命中查数据库并回填；写时先更新数据库，成功后删除缓存，而不是同时强行维护两个真相。
>
> **机制：** 删除缓存能让后续读重新加载新值，但数据库提交与删缓存之间仍有短暂不一致窗口，需要重试、消息或过期时间兜底。
>
> **容易踩坑：** 先删缓存再更新数据库，期间并发读可能把旧值回填；缓存没有 TTL；删除失败完全无监控。
>
> **适用场景：** 读多写少且允许短暂最终一致的数据；余额、库存最终判断仍以数据库原子操作为准。

### Q073：缓存穿透是什么？怎么处理？

> **结论：** 穿透是大量请求查询本来就不存在的数据，缓存一直 miss，压力直接落数据库。
>
> **机制：** 可以做参数校验、缓存短 TTL 空值、布隆过滤器和访问控制；布隆过滤器有假阳性，不能证明数据一定存在。
>
> **容易踩坑：** 空值缓存时间过长导致新数据创建后仍查不到；过滤器和数据库更新不同步；攻击者遍历随机 key 绕过普通热点策略。
>
> **适用场景：** 公开查询接口、ID 枚举风险场景；同时做限流和权限，不能只靠缓存技术防攻击。

### Q074：缓存击穿是什么？单飞和互斥锁怎么用？

> **结论：** 击穿是一个热点 key 失效时，大量并发同时回源；目标是让一个请求加载，其他请求等待、复用旧值或快速降级。
>
> **机制：** 进程内可用 singleflight，分布式可用短租约锁；也可以逻辑过期，由后台刷新并暂时返回旧值。
>
> **容易踩坑：** 锁没有租约或持有者崩溃；等待者无限阻塞；回源失败后立刻全量重试；多个实例各自单飞仍同时打数据库。
>
> **适用场景：** 热门配置和商品详情；根据是否允许旧值选择等待、stale-while-revalidate 或降级。

### Q075：缓存雪崩是什么？

> **结论：** 雪崩是大量 key 同时过期或 Redis 整体不可用，回源流量集中冲击数据库和下游。
>
> **机制：** TTL 加随机抖动、分批预热、多级缓存、限流熔断和 Redis 高可用可以降低风险，但每层都要有容量边界。
>
> **容易踩坑：** 所有 key 使用整点相同 TTL；Redis 恢复后预热流量再次打满；只做主从不演练故障切换和数据丢失窗口。
>
> **适用场景：** 大促和集中配置刷新；预案要同时保护缓存、数据库和调用方，明确降级数据从哪里来。

### Q076：怎么保证数据库和缓存一致？能做到强一致吗？

> **结论：** 普通 Cache Aside 一般是最终一致，想做到严格强一致代价很高。关键数据应以数据库为真相，缓存只做加速。
>
> **机制：** 更新数据库后删缓存，删除失败通过事务消息、Outbox/CDC 或重试队列补偿；TTL 是最后兜底。读写竞争仍需结合版本号避免旧值覆盖新值。
>
> **容易踩坑：** 延迟双删被当万能方案；消息乱序导致旧版本回填；缓存写成功但数据库事务后来回滚。
>
> **适用场景：** 商品和配置允许短暂不一致；资金状态不从缓存独立裁决，读取缓存也要带版本和明确失效策略。

### Q077：Redis 分布式锁的正确最小实现是什么？

> **结论：** 加锁至少要原子地 `SET key token NX PX ttl`，解锁用 Lua 比较 token 后删除；锁只减少并发，不替代数据库约束和幂等。
>
> **机制：** token 标识持有者，TTL 防止持有者崩溃后永久死锁；长任务需要受控续租，并在临界写入处验证所有权。
>
> **容易踩坑：** `SETNX` 和 `EXPIRE` 分两步；任何线程都能 delete；业务超过 TTL 后两个持有者同时执行；续租线程失联。
>
> **适用场景：** 定时任务抢占、缓存重建等可容忍租约语义的协调；关键状态仍用唯一索引、版本号或 fencing token 兜底。

### Q078：RedLock 和 fencing token 为什么会被一起讨论？

> **结论：** RedLock 试图通过多个独立 Redis 实例提高锁可用性，但分布式暂停和时钟等问题下，旧持有者仍可能晚到写资源；fencing token 让资源端拒绝旧租约更关键。
>
> **机制：** 每次成功抢锁得到单调递增 token，下游只接受比已见 token 更新的请求，即使旧进程恢复也不能覆盖新结果。
>
> **容易踩坑：** 下游不验证 token，发了 token 也没意义；把 Redis 锁宣传成 CP 强一致锁；忽略网络分区下的业务取舍。
>
> **适用场景：** 强协调优先数据库条件更新、ZooKeeper/etcd 等有明确一致性语义的系统；Redis 锁适合边界更弱的场景。

### Q079：热 key 和 big key 分别有什么危害？

> **结论：** 热 key 把请求集中到单节点或单核，big key 让网络、删除、持久化和迁移成本突增，两者都可能拖慢整个实例。
>
> **机制：** 热 key 可以本地缓存、拆分 key 或请求合并；big key 要拆 Hash/Set、限制单值大小，并用渐进删除。
>
> **容易踩坑：** 只看内存总量不看 key 分布；直接 `DEL` 巨大集合造成阻塞；拆热 key 后统计和一致性合并没有设计。
>
> **适用场景：** 用 slowlog、命令统计、采样和集群热点工具定位；改造前先确认是单 key、单命令还是网络带宽瓶颈。

### Q080：RDB、AOF 和淘汰策略怎么选？

> **结论：** RDB 恢复快但可能丢快照间数据，AOF 记录写操作更细但体积和恢复成本更高；可以组合使用。淘汰策略则决定内存满时删哪些 key。
>
> **机制：** AOF 的 fsync 策略在性能和持久性间取舍，重写压缩历史命令；LRU/LFU 常是近似算法，allkeys 与 volatile 策略适用范围不同。
>
> **容易踩坑：** 把 Redis 当唯一数据源却没有备份恢复演练；maxmemory-policy 配成 noeviction 后写请求直接失败；缓存 key 没 TTL 却使用 volatile 淘汰。
>
> **适用场景：** 纯缓存可接受重建，重点是容量和淘汰；承担会话或队列状态时必须明确可丢窗口、复制和恢复方案。

## 8. MQ、幂等与分布式一致性

### Q081：为什么引入 MQ？它带来哪些新问题？

> **结论：** MQ 用于异步解耦、削峰和事件驱动，但会引入重复、乱序、延迟、积压、消息丢失和最终一致性，不能只讲好处。
>
> **机制：** 生产者把消息持久化到 Broker，消费者按订阅读取并确认；各产品在分区、副本和消费模型上不同。
>
> **容易踩坑：** 把同步强依赖改成异步后没有状态查询；消息体成为隐式数据库表；Schema 升级破坏旧消费者。
>
> **适用场景：** 通知、异步处理和可重试流程；用户必须立即知道结果的核心校验仍走同步或明确返回“处理中”。

### Q082：生产者怎么尽量避免消息丢失？

> **结论：** 要同时处理发送前、本地事务后、Broker 确认前后的不确定状态，不能只调用一次 send 就算成功。
>
> **机制：** 开启可靠确认、持久化和副本；发送失败有限重试。数据库与 MQ 双写更稳妥的是 Outbox：同一事务写业务表和事件表，再由投递器发送并记录状态。
>
> **容易踩坑：** 超时后直接换消息 ID 重发造成重复；异步发送回调失败没人处理；Outbox 发送成功但标记失败会再次发送，所以消费者仍要幂等。
>
> **适用场景：** 关键业务事件用稳定 eventId、Outbox/CDC、告警和对账；非关键遥测才可接受有损策略。

### Q083：At-most-once、At-least-once 和 Exactly-once 怎么理解？

> **结论：** 最常见可靠语义是 at-least-once，也就是可能重复但尽量不丢；端到端 exactly-once 很难，通常靠幂等把效果做成 effectively-once。
>
> **机制：** 先 ack 后处理可能丢，处理后 ack 可能因 ack 丢失而重复；事务性 Broker 也只覆盖它声明的边界，不自动包含外部数据库和 HTTP。
>
> **容易踩坑：** 把 Kafka 等产品的 exactly-once 宣传直接扩展到所有下游副作用；消费者失败后无重试上限；重复消息改变结果。
>
> **适用场景：** 每个消息带业务事件 ID，消费记录和业务更新放同一本地事务，重复到达直接返回已有结果。

### Q084：消费者幂等有哪些实现方式？

> **结论：** 最可靠的是稳定业务键加数据库唯一约束或状态条件更新，Redis 去重只能作为加速，不能成为唯一兜底。
>
> **机制：** 本地事务先插入 eventId 消费记录，再执行业务更新；唯一冲突说明已处理。或者状态机只允许合法前态迁移到目标态。
>
> **容易踩坑：** 去重记录和业务更新不在同一事务；Redis TTL 过后旧消息重放；把消息 offset 当跨主题业务幂等键。
>
> **适用场景：** 支付回调、订单状态和积分发放；需要返回第一次处理结果时还要保存结果快照。

### Q085：如何保证消息顺序？

> **结论：** 通常只能保证同一业务 key 在同一分区或队列中的局部顺序，不能低成本保证全局顺序。
>
> **机制：** 生产时按 orderId 等 key 路由到同一 partition，消费端对该分区串行或按 key 排队；消息携带版本号可拒绝旧事件。
>
> **容易踩坑：** 消费失败重试时后续消息已经成功；扩分区改变路由；多个生产者对同一 key 没有统一序号。
>
> **适用场景：** 订单状态流用业务 key 加版本状态机；无需顺序的独立任务应并行，避免为全局有序牺牲吞吐。

### Q086：重试、延迟队列和死信队列怎么配合？

> **结论：** 短暂故障有限重试，避免立即热循环；超过阈值进入死信并告警，死信不是垃圾桶，必须有查看、修复和重放流程。
>
> **机制：** 按异常类型决定是否重试，采用退避和抖动；消息记录 attempt、首次时间和最后错误，重放保持原业务 eventId。
>
> **容易踩坑：** 参数错误也无限重试；重放生成新幂等键；死信长期无人处理；一条毒消息阻塞整个有序分区。
>
> **适用场景：** 下游超时和 5xx 可重试，业务校验失败直接终止；有序消费要提供跳过、隔离和人工决策机制。

### Q087：消息积压时先扩消费者就一定有用吗？

> **结论：** 不一定。吞吐上限可能在分区数、数据库、外部接口或单条处理时间；盲目扩容会把下游打垮。
>
> **机制：** 先看生产速率、消费速率、lag、分区分布、处理耗时和错误率，确认可并行度，再做扩容、批量、降级或旁路处理。
>
> **容易踩坑：** 消费者数超过分区数没有收益；积压期间仍执行非关键慢逻辑；扩容后数据库连接池和锁等待暴涨。
>
> **适用场景：** 制定 backlog 清理速度和 ETA，关键实时消息可与历史积压分级；清理后及时缩容并复盘根因。

### Q088：Outbox 为什么能解决数据库和 MQ 双写问题？

> **结论：** Outbox 把业务数据和待发送事件写进同一个本地事务，先消除“数据库成功、事件根本没记录”的窗口，再异步可靠投递。
>
> **机制：** 投递器轮询或 CDC 读取未发送事件，发到 Broker 后更新状态；重复发送允许存在，靠 eventId 和消费者幂等收口。
>
> **容易踩坑：** 把 Outbox 说成 exactly-once；投递表无索引和归档；发送成功后进程崩溃会重复；事件 payload 没有 Schema 版本。
>
> **适用场景：** 订单创建后发事件、报告生成后通知；要求同步跨系统原子提交的场景需要另评一致性方案。

### Q089：【丰泊实问】什么是幂等？接口里怎么保证？

> **结论：** 幂等不是请求只到一次，而是同一个业务请求重复执行后，最终业务效果和第一次一致。关键是稳定业务键、唯一约束、状态机和结果复用。
>
> **机制：** 客户端或服务端生成 idempotency key，数据库唯一索引抢占；本地事务中做条件更新并保存处理中/成功/失败及响应，重复请求返回已有状态。
>
> **容易踩坑：** 只用分布式锁，锁过期后仍可能重复；key 没绑定用户和请求内容；失败重试时改变 key；先产生副作用再写幂等记录。
>
> **适用场景：** 支付回调、创建订单、消息消费和对外通知；读接口天然较容易幂等，写接口要按每种副作用逐一设计。

### Q090：【丰泊实问】微服务怎么保证分布式事务一致性？强一致和最终一致怎么选？

> **结论：** 我会先缩小强一致边界，把不可拆的核心记账留在同一数据库事务；跨服务通知和长流程通常用 Outbox、幂等消费、状态机、补偿和对账实现最终一致。
>
> **机制：** 强一致常依赖 XA/2PC 或具备相应能力的数据库，参与者在提交前协调；最终一致则由一组本地事务和可靠事件推进，失败后重试或补偿。
>
> **容易踩坑：** 为所有微服务调用默认上 2PC；把“最终”理解成可以无限期不一致；补偿操作不可执行或本身不幂等；没有对账发现静默失败。
>
> **适用场景：** 金融核心账务优先单一强一致边界；订单履约、通知等可用 Saga/事件驱动。没有主导过框架选型时应如实说明，再讲清方案取舍。

### Q091：CAP 和 BASE 应该怎么用在实际选型里？

> **结论：** 网络分区发生时，分布式系统必须在一致性和可用性之间取舍；CAP 不是平时三选二口号，BASE 也不是“数据随便错”。
>
> **机制：** CP 系统在无法确认一致结果时拒绝或阻塞部分请求，AP 系统继续服务并在之后合并；BASE 强调基本可用、软状态和最终一致。
>
> **容易踩坑：** 把数据库事务 ACID 的 C 和 CAP 的 consistency 混淆；说系统永远没有网络分区；没有定义“最终多久”和冲突规则。
>
> **适用场景：** 注册中心、配置、缓存和业务状态的取舍不同；每个场景要明确分区时允许读旧、拒绝写还是降级。

### Q092：XA/2PC、TCC 和 Saga 各适合什么场景？

> **结论：** XA/2PC 对资源协调强但耦合与阻塞成本高；TCC 控制细但业务侵入最大；Saga 用本地事务加补偿，适合长流程但只保证最终一致。
>
> **机制：** 2PC 先 prepare 再统一 commit；TCC 分 Try、Confirm、Cancel；Saga 每步提交本地事务，后续失败按相反顺序执行补偿。
>
> **容易踩坑：** TCC 的空回滚、悬挂和重复 Confirm/Cancel 没处理；Saga 补偿不等于数据库回滚，外部世界可能已看到中间状态；2PC 协调者和锁持有成为瓶颈。
>
> **适用场景：** 极少数必须同步协调的短事务评估 XA/TCC；订单履约等长业务流程更适合 Saga/事件，前提是补偿可定义。

### Q093：分布式 ID 有哪些方案？怎么选？

> **结论：** 数据库自增简单但跨库难，UUID 去中心化但长且无序，Snowflake 类方案有序高吞吐但要处理时钟回拨和 workerId；没有万能 ID。
>
> **机制：** Snowflake 通常把时间戳、节点和序列拼成 64 位；号段模式从数据库批量申请区间，在本地发号降低 DB 压力。
>
> **容易踩坑：** 多实例 workerId 冲突；时钟回拨产生重复或停发；把业务敏感顺序直接暴露在 ID；JavaScript 前端丢失 64 位整数精度。
>
> **适用场景：** 数据库主键可用趋势递增 ID；对外 ID 可再编码或使用 UUID/ULID；选型要结合排序、长度、可用性和容量。

### Q094：超时、重试、熔断和限流是什么关系？

> **结论：** 超时限制单次等待，重试应对短暂失败，熔断阻止持续打坏下游，限流保护容量；四者要统一预算，否则重试会放大故障。
>
> **机制：** 端到端 deadline 向下游传剩余时间；重试用指数退避加抖动；熔断器在 closed/open/half-open 间转换；限流按令牌或漏桶控制进入速率。
>
> **容易踩坑：** 每层各重试三次形成指数放大；对非幂等写重试；超时后底层任务仍执行；熔断阈值没有按接口隔离。
>
> **适用场景：** 调用链只在最合适的一层重试，写请求携带幂等键；给不同下游独立连接池、并发和熔断状态。

## 9. 微服务与 HTTP

### Q095：微服务边界应该按表拆，还是按业务拆？

> **结论：** 应按业务能力、数据所有权和变化边界拆，不按一张表一个服务。拆分后每个服务对自己的数据负责，其他服务通过契约访问。
>
> **机制：** 领域边界内保持强一致，边界间用 API 或事件协作；团队和部署边界也应尽量与业务边界对齐。
>
> **容易踩坑：** 过早拆成大量纳米服务；多个服务直接写同一张表；一个请求同步串十几个服务；共享 DTO 让版本升级锁死。
>
> **适用场景：** 先做清晰模块化单体，再依据独立扩缩容、发布和团队所有权演进；不是为了“微服务”标签而拆。

### Q096：服务注册发现和配置中心分别解决什么？

> **结论：** 注册发现解决服务实例在哪里、是否健康；配置中心解决运行参数如何集中管理、版本化和动态下发，两者职责不同。
>
> **机制：** 实例注册并续约，客户端或网关获取可用列表并负载均衡；配置通过长轮询、推送或 watch 更新，应用监听变更。
>
> **容易踩坑：** 只靠心跳认定业务健康；配置推送后所有实例同时重连下游；敏感配置明文存储；动态修改没有审计和回滚。
>
> **适用场景：** readiness 检查真实关键依赖但不能过重；高风险配置灰度发布，密钥交给专门 Secret 系统。

### Q097：API Gateway 应该做什么，不应该做什么？

> **结论：** 网关适合统一认证、路由、限流、协议转换和审计，不应塞入大量领域业务，否则会成为难发布的单点巨石。
>
> **机制：** 网关验证 token 并把可信身份上下文传给下游，做路由和流量策略；下游仍要基于身份和资源做授权，不能只信网关“放进来了”。
>
> **容易踩坑：** 仅在网关鉴权，内部绕过网关即可越权；把用户可控 header 当可信租户；日志记录完整 token 和敏感请求体。
>
> **适用场景：** 南北向统一入口交给网关，东西向服务间使用 mTLS/服务身份和细粒度授权，业务校验留在服务内部。

### Q098：REST 和 RPC 怎么选？

> **结论：** REST/HTTP 对外兼容、可调试和生态好；RPC 在内部强类型、低延迟和双向流场景更方便。选型看契约和运维，不是看哪个名字更先进。
>
> **机制：** REST 以资源和 HTTP 语义表达，常用 JSON；gRPC 等 RPC 用 IDL 生成客户端和二进制协议，支持 deadline 和 streaming。
>
> **容易踩坑：** REST 接口全做成 `/doSomething`；RPC schema 删除字段或复用字段号破坏兼容；只看序列化速度忽略跨语言调试和网关支持。
>
> **适用场景：** 开放 API 常用 REST；稳定内部高频调用可用 RPC；无论哪种都要有超时、版本、错误模型和观测。

### Q099：HTTP 的 GET、POST、PUT、PATCH、DELETE 哪些应该幂等？

> **结论：** GET、PUT、DELETE 从协议语义上应幂等，POST 默认不保证，PATCH 取决于补丁语义；“幂等”不等于每次响应完全相同。
>
> **机制：** PUT 表示对指定资源做完整替换，重复提交目标状态相同；DELETE 重复后资源仍不存在；POST 创建通常需额外 idempotency key。
>
> **容易踩坑：** GET 产生扣费或写状态；DELETE 重复调用不断新增审计副作用却宣称完整幂等；所有错误都返回 200。
>
> **适用场景：** 创建订单 POST 带业务幂等键；更新状态使用资源版本和条件请求；错误用合理 4xx/5xx 及稳定业务码表达。

### Q100：固定窗口、滑动窗口、漏桶和令牌桶怎么选？

> **结论：** 固定窗口简单但边界突刺明显，滑动窗口更平滑但成本高，漏桶强调恒定输出，令牌桶允许受控突发，是接口限流常见选择。
>
> **机制：** 令牌按速率加入桶，请求消耗令牌；分布式实现要原子更新时间和令牌数，并考虑时钟与热点 key。
>
> **容易踩坑：** 只按 IP 限流误伤 NAT 用户；所有接口共享一个桶；被限流后客户端无退避；本地限流无法控制集群总量。
>
> **适用场景：** 按租户、用户、接口和成本分层限流，返回 `Retry-After` 或明确错误；关键流量预留独立配额。

### Q101：分布式 Trace 里 traceId、spanId 和 baggage 分别是什么？

> **结论：** traceId 串起一次端到端请求，spanId 标识其中一个操作，baggage 是随上下文传播的少量业务元数据，不能当无限字段包。
>
> **机制：** 入口创建或接收 trace context，下游 HTTP/MQ 传播父子关系；每个 span 记录时间、状态和必要属性。
>
> **容易踩坑：** 异步线程和消息消费丢上下文；把身份证、token 等敏感信息放 baggage；采样后只剩错误日志却无法关联。
>
> **适用场景：** API、数据库、缓存、MQ 和外部调用统一传播；高基数属性谨慎上指标，详细数据留 Trace/日志并做脱敏。

### Q102：接口怎么做向后兼容？

> **结论：** 新增可选字段通常兼容，删除/改名/改变含义通常不兼容；服务端要容忍旧客户端，消费者也要忽略不认识的新字段。
>
> **机制：** 用版本化 Schema、默认值、扩展字段和弃用周期演进；消息和 RPC IDL 还要遵守字段号规则。
>
> **容易踩坑：** 把字段从可空改必填；枚举新增值让旧客户端反序列化失败；一次发布同时改生产者和消费者却没有先后兼容窗口。
>
> **适用场景：** 采用 expand-and-contract：先让读取端兼容新旧，再写新格式，观察完成后才移除旧字段。

## 10. 测试、CI 与发布

### Q103：单元测试、集成测试和端到端测试怎么分工？

> **结论：** 单测验证小单元和边界，集成测试验证数据库、消息和框架协作，端到端验证关键用户链路；数量应大致呈测试金字塔，而不是全靠 E2E。
>
> **机制：** 单测隔离外部依赖、反馈快；集成测试用真实协议或容器；E2E 从入口到最终结果但成本和不稳定性最高。
>
> **容易踩坑：** 单测全部 mock 到只验证调用次数；集成测试共享脏数据库；E2E 失败却无法定位哪一层；只测 happy path。
>
> **适用场景：** 状态机、幂等和边界条件优先单测；SQL、事务和序列化必须有集成测试；支付等关键旅程保留少量 E2E。

### Q104：`@SpringBootTest`、`@WebMvcTest` 和 `@DataJpaTest`/MyBatis 测试怎么选？

> **结论：** `@SpringBootTest` 加载接近完整上下文，适合少量集成验证；slice test 只加载 Web 或数据层，速度更快、失败定位更清楚。
>
> **机制：** `@WebMvcTest` 配合 MockMvc 测 Controller、参数和异常映射；数据层测试加载 Mapper/Repository 和数据库相关配置。
>
> **容易踩坑：** 所有测试都启动完整 Spring 导致 CI 很慢；slice 中 mock 太多变成实现细节测试；使用 H2 却和生产 MySQL 方言行为不同。
>
> **适用场景：** 普通业务类纯 JUnit；Web 协议用 slice；事务、SQL 和迁移最好用 Testcontainers 跑真实数据库版本。

### Q105：Mock 最容易让测试失真在哪里？

> **结论：** Mock 适合隔离慢或不稳定边界，不应把被测对象内部每一步都 mock 掉；好的测试断言业务结果，而不是复制实现。
>
> **机制：** Stub 提供输入，Mock 可验证交互，Fake 是可工作的简化实现。不同测试替身适合不同边界。
>
> **容易踩坑：** 重构方法调用顺序后业务没变，测试却全坏；mock 数据库无法发现 SQL 和事务问题；默认返回 null 掩盖不完整配置。
>
> **适用场景：** 外部支付、时钟、随机数等用接口注入和 fake/mock；Repository 至少补真实数据库集成测试。

### Q106：什么是契约测试？它为什么适合微服务？

> **结论：** 契约测试验证提供方和消费方对请求、响应、字段和错误的共同约定，能比全链路 E2E 更早发现不兼容变更。
>
> **机制：** 消费方定义期望，提供方在 CI 中用契约验证真实实现；也可以由 OpenAPI/IDL 做 schema compatibility 检查。
>
> **容易踩坑：** 契约只验证结构不验证关键语义；旧消费者契约没有保留；把所有业务场景都塞进契约导致难维护。
>
> **适用场景：** 多团队 API、消息 Schema 和 SDK 发布；契约测试不能替代提供方单测、集成测试和少量 E2E。

### Q107：一条合格的 Java CI 流水线至少包含什么？

> **结论：** 至少应有可重复构建、格式/静态检查、单测、关键集成测试、依赖与安全扫描、制品构建和可追溯版本；发布与构建制品要分开。
>
> **机制：** 同一个 commit 产出不可变制品，后续环境提升复用该制品；缓存依赖但不缓存错误结果，测试报告和覆盖趋势留档。
>
> **容易踩坑：** 每个环境重新编译；跳过失败测试仍发布；把密钥写进 CI 日志；只追覆盖率数字不关注关键路径。
>
> **适用场景：** PR 走快速门禁，主干补较重集成与扫描；发布需要审批、变更记录和自动回滚条件。

### Q108：数据库 Schema 变更怎么安全发布？

> **结论：** 采用向后兼容的 expand-and-contract，小步迁移；应用和数据库不能假设同一瞬间全部升级。
>
> **机制：** 先新增可空列/新表和双读兼容，再回填、切写、观察，最后删除旧字段；迁移脚本版本化且只能前进执行。
>
> **容易踩坑：** 大表直接加高成本索引或改列锁表；新代码先读不存在字段；回填一个大事务；失败后手工改库却不更新迁移记录。
>
> **适用场景：** Flyway/Liquibase 等管理版本，生产变更先评估锁和时长，回填做小批次、限速、可暂停和对账。

### Q109：蓝绿、滚动和金丝雀发布怎么选？

> **结论：** 蓝绿切换快、回滚直观但资源成本高；滚动节省资源但新旧版本共存；金丝雀先让少量真实流量验证，最适合风险渐进控制。
>
> **机制：** 发布平台按实例或流量比例替换，健康检查和指标门槛决定继续或回滚；数据库和消息契约必须兼容新旧版本。
>
> **容易踩坑：** 只看进程存活就放量；回滚应用却无法回滚已写的新数据；会话粘性让灰度样本失真；缓存 key 版本冲突。
>
> **适用场景：** 无状态服务常用滚动，关键变更结合金丝雀；高风险且资源允许时蓝绿，所有方式都要先做兼容设计。

### Q110：日志、指标和 Trace 各自最适合回答什么问题？

> **结论：** 指标告诉我系统是否异常和影响多大，Trace 告诉我慢或错在哪段调用，日志提供具体事件细节；三者要用统一业务和链路 ID 关联。
>
> **机制：** RED 看请求率、错误、延迟，USE 看资源利用、饱和和错误；结构化日志便于检索，Trace 保存调用树和时间。
>
> **容易踩坑：** 日志全是自由文本；高基数 userId 直接做 metrics label；记录完整请求造成隐私泄漏；只告警 CPU 不告警业务失败。
>
> **适用场景：** 先从 SLI/告警定位时间窗口，再用 Trace 缩小服务和依赖，最后查日志和数据状态确认根因。

## 11. 常见故障排查

### Q111：Java 服务 CPU 突然 100%，怎么排查？

> **结论：** 先确认是单进程、单核还是整机，再抓多次线程 CPU 和线程栈做关联，避免只凭一张 top 截图下结论。
>
> **机制：** 用 top/pidstat 找进程和高 CPU 线程，把线程 ID 转十六进制后在 `jstack` 中定位；JFR/async-profiler 可看热点方法、锁和分配。
>
> **容易踩坑：** 立刻重启丢失现场；只抓一次栈碰到瞬时状态；把 GC 线程高 CPU 当业务死循环；线上直接使用高开销 profiler。
>
> **适用场景：** 区分死循环、正则回溯、JSON/加密热点、频繁 GC、锁自旋或流量增长，再针对根因限流、回滚或修复。

### Q112：内存持续上涨但还没 OOM，怎么判断泄漏还是正常缓存？

> **结论：** 看 Full GC 后的存活基线是否持续上升，并结合对象保留路径判断；内存高不等于泄漏，缓存和堆预留也可能是设计行为。
>
> **机制：** 观察 old gen、metaspace、direct memory 和 RSS；用 class histogram 对比多个时间点，必要时 heap dump 分析 dominator tree 和 GC roots。
>
> **容易踩坑：** 只看堆使用锯齿峰值；dump 生产大堆导致停顿和磁盘满；忽略 native memory、线程栈和 mmap。
>
> **适用场景：** 常见根因有无界缓存、ThreadLocal、监听器、类加载器、未关闭资源；修复后要用同负载验证存活基线稳定。

### Q113：Full GC 频繁，临时止损和根因修复分别做什么？

> **结论：** 止损可以限流、回滚、减少批量、临时扩容或调整内存余量，但最终必须找分配和保留对象、晋升失败或收集器退化原因。
>
> **机制：** 对齐 GC cause、老年代占用、晋升和 humongous 对象；查看是否元空间、显式 GC、内存泄漏或堆太小。
>
> **容易踩坑：** 只加堆把故障推迟；禁用显式 GC 后掩盖直接内存问题；调整十几个参数却没有基线和回归。
>
> **适用场景：** 先保存 GC 日志/JFR 和发布时间线，单变量修改并压测；代码层减少无界对象和大批结果通常比参数微调更持久。

### Q114：线程池队列满、请求大量超时时怎么排查？

> **结论：** 先看任务到达速率、执行耗时、活跃线程、队列、拒绝和下游连接池，判断是突发过载、任务变慢还是资源互等。
>
> **机制：** 线程 dump 看工作线程卡在数据库、HTTP、锁还是 CPU；Little's Law 能帮助理解并发、吞吐和时延关系，但最终用实测数据。
>
> **容易踩坑：** 第一反应只加线程，导致 DB 连接和下游更拥塞；队列无界没有拒绝却最终 OOM；超时任务仍在后台占资源。
>
> **适用场景：** 临时限流和降级，隔离慢任务；长期修复慢依赖、配置 deadline、有界队列和匹配下游容量的并发。

### Q115：怀疑 Java 死锁或锁竞争，怎么区分？

> **结论：** 死锁是等待环且不会自行恢复，锁竞争只是很多线程等待同一热点锁；线程 dump、JFR 锁事件和吞吐趋势能区分。
>
> **机制：** 多次 dump 中相同线程一直 BLOCKED 并形成 ownership cycle 是强证据；大量 BLOCKED 但持有者持续变化更像竞争。
>
> **容易踩坑：** 看到 BLOCKED 就说死锁；忽略 `LockSupport.park` 可能是正常线程池等待；优化锁时破坏业务原子性。
>
> **适用场景：** 死锁统一锁顺序，竞争则缩小临界区、分段、读写分离或移除共享热点，并用压测验证正确性和吞吐。

### Q116：一条 SQL 突然变慢，排查步骤是什么？

> **结论：** 用真实参数确认慢 SQL 和等待时间，查看执行计划、扫描行数、锁等待、统计信息和数据分布，再对比近期 Schema、数据量和参数变化。
>
> **机制：** 慢可能来自索引缺失/失效、优化器计划变化、回表过多、排序临时表、锁等待、IO 或连接池排队。
>
> **容易踩坑：** 直接加索引不看写成本；测试环境小数据计划与生产不同；只看 SQL 执行时间，不看拿连接和锁等待时间。
>
> **适用场景：** 先止损限流或回滚，再用 EXPLAIN ANALYZE、performance_schema 和慢日志验证优化前后变化。

### Q117：Redis 延迟突然升高，怎么排查？

> **结论：** 同时检查服务端 slowlog、CPU、内存、网络、big key、热 key、持久化和集群迁移，客户端连接池和超时也不能漏。
>
> **机制：** 大命令、Lua、fork、AOF fsync、swap、主从同步或单节点热点都可能造成尾延迟；客户端排队会把服务端小延迟放大。
>
> **容易踩坑：** 在线上执行 `KEYS *`；直接删除 big key；只扩客户端连接让 Redis 更拥塞；把网络抖动误判为服务端慢。
>
> **适用场景：** 临时熔断非关键缓存、降低大请求和热点；长期做 key 大小限制、渐进删除、分片和容量监控。

### Q118：MQ 出现积压、重复消费和乱序，怎么一起处理？

> **结论：** 先把三个问题拆开：积压看容量，重复靠幂等，乱序靠业务 key、版本和状态机；扩消费者不能替代后两者。
>
> **机制：** 检查 partition lag 和消费者错误；保持原 eventId 重试，按 key 路由并用 version 拒绝旧消息，毒消息隔离到 DLQ。
>
> **容易踩坑：** 为清积压关闭幂等检查；重放换新 ID；并行消费同一订单状态；跳过失败消息却不记录缺口。
>
> **适用场景：** 制定恢复优先级和 ETA，保护数据库；清理后对账消息数与业务状态，并补充自动告警和容量预案。

### Q119：接口 P99 超时，但平均延迟正常，怎么定位？

> **结论：** 平均值会掩盖尾部问题，要按路由、实例、下游、状态码和时间分桶，沿 Trace 看慢请求到底卡在排队、GC、锁、DB 还是网络。
>
> **机制：** 少量慢依赖、连接池耗尽、重试放大、单个坏实例或大请求都能拉高 P99；协调遗漏会让下游超时大于入口预算。
>
> **容易踩坑：** 只扩容入口服务；每层设置相同 3 秒超时，整链路叠加更长；采样丢掉恰好最慢的 Trace。
>
> **适用场景：** 先隔离坏实例、限流和关闭无效重试；长期传递 deadline、优化慢路径并单独监控队列与连接池等待。

### Q120：数据库显示成功但下游没收到，怎么排查并修复？

> **结论：** 这是典型双写一致性窗口。先按业务 ID 对齐数据库事务、事件记录、Broker 和消费者状态，不能只看某一侧“成功日志”。
>
> **机制：** 如果业务提交后发送失败，需要补发；如果发送成功但本地未记状态，可能重复。长期用 Outbox/CDC、稳定 eventId、幂等消费和定时对账收口。
>
> **容易踩坑：** 手工补发生成新业务 ID；把消息发送日志当 Broker 已持久化证明；修复状态但不补审计和失败根因。
>
> **适用场景：** 报告通知、订单事件、支付结果等跨系统链路；恢复脚本要可重复执行、先 dry-run，并输出受影响业务清单。
